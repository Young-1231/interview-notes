  1. 介绍一下实习经历。
  2. 组内 GC 问题的排查思路是什么?
  3. GC 发生很正常,为什么要想办法减少 Full GC 次数?
  4. MySQL 为什么用 B+ 树?和红黑树相比有什么好处?
  5. B+ 树的扇出很大是好事还是坏事?
  6. 讲一下 Redis 的跳表。
  7. TCP 为什么是三次握手、四次挥手?
  8. 把三次握手改成两次会有什么问题?
  9. 讲一下 IO 多路复用模型。一台服务器开 60000 个端口,最多能建立多少个 TCP 连接?

要点

  • 问题比较刁钻,从实习的 GC 优化追问到数据结构和网络细节;算法量大。
  • 减少 Full GC:Full GC 停顿长,直接影响接口 RT 和吞吐,频繁出现通常意味着内存泄漏或参数不合理。
  • 扇出大是好事:树更矮、磁盘 IO 次数更少,代价是单节点更大、页分裂成本更高。
  • 两次握手:无法确认客户端的接收能力,历史 SYN 会让服务端建立无效连接并浪费资源。
  • 连接数:TCP 连接由四元组标识,服务端连接上限取决于内存和文件描述符,而不是端口数。

Function Calling 原理 5高频 0

什么是 Function Calling？它本质上怎么让大模型调用外部工具？模型真的调用了函数吗？

Function Calling 是让模型按开发者事先声明的函数 Schema 输出一段结构化调用请求，再由应用程序真正执行函数的机制。模型本身没有执行任何函数，它只负责“决定调不调、调哪个、传什么参数”。

完整流程

  1. 开发者在请求里声明可用函数：名称、描述、参数 JSON Schema。
  2. 模型理解用户意图后，不直接回答，而是返回一个结构化调用请求：
{
  "name": "get_weather",
  "arguments": { "city": "北京", "date": "明天" }
}
  1. 应用程序拿到函数名和参数，做参数校验、权限检查，再调用本地代码或外部 API。
  2. 执行结果作为一条新消息（tool / function 结果）回传给模型。
  3. 模型决定继续调用下一个工具，还是基于结果生成最终回答。

要点

  • 模型负责“决策 + 生成参数”，宿主程序负责“执行 + 兜底”，真正的副作用都发生在模型外部。
  • 正因为模型只是“提议”，服务端必须校验参数和权限，不能无条件信任模型输出。
  • 一轮对话里可以有多次调用，形成“调用 → 观察结果 → 再调用”的循环，这也是 Agent 的基础。

大模型为什么会“主动”调用工具？LLM 是怎么学会 Tool Use 的？

模型并没有主观意识，所谓“主动”调用，是它在训练中学会了一种模式：当问题需要实时数据、精确计算或系统操作时，就输出工具调用格式而不是直接作答。

学会 Tool Use 依赖三种能力

  • 理解意图：判断用户是要查询、计算、下单、发邮件还是修改数据，以及靠自身知识能否回答。
  • 理解工具说明：根据工具的名称、描述、参数 Schema 判断哪个工具适合当前任务。
  • 生成结构化参数：把自然语言转换成工具能接收的 JSON 参数。

举例：用户说“帮我订明天下午 3 点和张三的会议”，模型要识别出动作是创建日程、时间是明天 15:00、参与人是张三，选择 create_calendar_event 工具并填好参数；若缺少必要信息（如会议时长），应先追问而不是乱填。

能力来源：训练阶段用大量“问题 → 工具调用 → 工具结果 → 最终回答”的轨迹数据做监督微调，再用偏好优化 / 强化学习强化“该调时调、不该调时不调、参数正确”的行为；推理阶段则依赖运行时传入的工具描述做选择。

Function Calling 能力是怎么训练出来的？它属于 Prompt 还是模型能力？

结论：它是“模型能力 + 运行时工具 Schema + Prompt 引导”三者结合，核心是模型能力，不是单纯的 Prompt 技巧。

训练侧

  • 用包含工具定义和调用轨迹的数据做指令微调 / SFT，让模型学会特定的调用格式（如特殊 token 或固定 JSON 结构）。
  • 再通过偏好优化或强化学习，提升选择工具的准确率和参数的合法性。

推理侧

  • 开发者把工具列表、描述、参数格式放进请求，模型根据上下文决定是否调用。
  • 部分平台还提供结构化输出 / 约束解码（strict 模式），保证参数严格符合 JSON Schema。

为什么不是纯 Prompt

  • 没经过工具调用训练的模型，仅靠 Prompt 很难稳定输出正确结构，也不擅长判断“什么时候该调”。
  • 但它也不是固化在参数里的：具体有哪些工具、参数长什么样，完全取决于运行时传入的定义，所以换一批工具不需要重新训练。

Tool 在 Agent 体系里扮演什么角色？Function Calling 算真正的 Agent 吗？

Tool 是 Agent 接触外部世界的“手脚”；Function Calling 只是构建 Agent 的关键能力之一，单独使用还不算完整的 Agent。

Tool 的角色

  • 大模型本身只能生成文本，Tool 扩展了它的行动能力：搜索工具获取实时信息，数据库工具查业务数据，代码执行工具做计算验证，业务 API 工具操作企业系统。
  • 在 Agent 的“感知 - 决策 - 行动”循环中，Tool 承担“行动”和“获取观察结果”两部分。

Function Calling 不等于 Agent

  • Function Calling 解决的是“怎么以结构化方式调用一个工具”。
  • 完整的 Agent 还需要：目标理解、任务规划、多步执行、观察结果后调整、错误恢复、记忆管理，以及停止条件。
  • 一次“问天气 → 调接口 → 回答”只是工具增强的问答；只有当模型在循环中自主规划并多步调用、根据结果调整策略时，才构成 Agent 行为。

Tool Use 和 Function Calling 有什么区别？

Tool Use 是上层能力概念，Function Calling 是实现它的一种接口机制，两者不是同义词。

维度 Tool Use Function Calling
含义 模型决定何时用工具、用哪个、怎么组合、如何处理结果 模型按函数 Schema 输出结构化调用请求
层级 Agent 的行为能力和决策过程 模型与程序之间的结构化通信方式
范围 搜索、查库、代码执行、浏览器操作、MCP 工具等都算 一种具体协议，各厂商格式不完全相同
  • Function Calling 可以支撑 Tool Use，但一次函数调用本身未必构成完整的 Agent 行为。
  • Tool Use 也不一定只靠 Function Calling 实现，例如让模型输出 ReAct 文本格式再解析、或直接生成 CLI 命令执行。

Tool Calling 工程实践 6高频 4

Tool Calling 一般怎么做？和普通函数调用有什么区别？高频

核心区别：普通函数调用由开发者写死“谁调哪个函数、传什么参数”；Tool Calling 是模型根据上下文提出调用意图，宿主系统决定能不能执行，所以中间必须加一层校验和调度。

工程上一般分四层

  • 工具注册层：定义每个工具的名称、描述、参数 Schema，注册到可调用列表。模型只看得到声明，看不到实现。
  • 校验层：模型输出候选调用后，服务端先做白名单校验、参数 Schema 校验、权限校验；不通过直接拦截，并把错误信息回传给模型让它修正。
  • 执行器层：校验通过才执行，包含超时控制、幂等控制、异常包装，结果统一格式化后回传模型。
  • 审计日志层：记录工具名、入参、出参、耗时、成功 / 失败状态，串成完整调用链，方便排查和回放。

与普通函数调用的对比

维度 普通函数调用 Tool Calling
调用决策 代码确定 模型在运行时决定
参数来源 程序构造，类型安全 模型生成，可能缺失或错误
可信度 可信 不可信，必须校验
失败处理 抛异常 错误要回传给模型，让其重试或换方案

你项目里的工具调用是怎么做的？怎么让模型更稳定地选对工具？高频

回答时先讲架构（工具注册 → 模型决策 → 服务端校验 → 执行 → 结果回传），再讲稳定性手段，核心是“描述清晰、减少重叠、缩小候选、规则兜底、线上监控”。

  • 工具描述写清楚：写明适用场景、输入参数含义、返回结果、不适用场景。模糊描述是选错工具的首要原因。
  • 减少语义重叠：功能相近的工具要么合并成一个、内部按参数路由，要么在描述里明确彼此边界。
  • 控制候选规模：工具很多时先做一层 Tool Routing（规则 / embedding 召回），把候选缩小到 Top K 再交给模型。候选越少越不容易选错。
  • 强约束参数：用严格的 JSON Schema（必填、枚举、格式），开启结构化输出 / strict 模式，减少参数错误。
  • Few-shot 示例：对易混淆场景给出正反示例。
  • 规则兜底：高风险操作走白名单和权限校验，即使模型选对工具，参数或权限不对也不能执行。
  • 线上监控：不能只看调没调，要统计命中率、误调用率、漏调用率、参数错误率、超时率，用错误案例反哺描述优化。

怎么并行做 Tool Calling，既提升吞吐又保证一致性和可回放？高频

核心是解决四个问题：依赖关系、状态一致性、结果合并、失败处理。只有互不依赖的调用才能并行。

  • 依赖分析：后一个工具依赖前一个的输出就必须串行；无依赖的（如同时查天气和查股价）放进同一并行批次。主流模型 API 本身支持一次返回多个 tool call（parallel tool calls），由宿主并发执行。
  • 状态一致性：不让多个工具直接改共享状态，而是先把结果写到临时观察区，再由调度器统一合并，避免并发写导致状态污染。
  • 结果合并：同一批次全部完成（或超时）后，按调用 id 把结果统一回填上下文，让模型一次看到完整信息再决策。
  • 失败隔离：按工具粒度设置超时和重试，一个工具失败不丢弃整批结果，失败项单独标记，模型在信息不全时做降级决策。
  • 副作用幂等：发消息、建订单、提工单等写操作必须带幂等键，否则重试会造成重复执行。
  • 可回放：每次调用记录 trace_id、step_id、入参、出参、耗时，组成执行 DAG；出问题时可以回溯到任意节点重放。对外部结果做快照，回放时用快照而不是重新请求，保证结果可复现。

Tool Calling 中最容易出现哪些问题？如何避免误调用和循环调用？

Tool Calling 的核心风险不是模型不会调，而是在错误的时机、用错误的参数、调用错误的工具，或者停不下来。

问题 表现 应对
误调用 不需要工具时强行调用，或选错工具 写清适用 / 禁用场景；路由缩小候选；设置置信度阈值；高风险工具人工确认
参数错误 缺字段、类型错、格式错 严格 JSON Schema、枚举和默认值；校验失败把错误回传让模型修正
权限越界 调用用户无权访问的工具或数据 按用户角色动态暴露工具；执行前服务端再校验；数据层做权限过滤
结果不可信 接口返回错误、空值、过期数据 返回结构化状态码；异常处理；关键结果二次校验
循环调用 反复调用同一工具无法停止 限制最大调用次数 / 步数；检测相同工具 + 相同参数的重复调用；工具结果明确返回终止状态；用状态机约束流程
副作用风险 发邮件、下单、删数据造成真实影响 二次确认、幂等设计、操作审计、沙箱执行、可回滚

总结：权限、校验、限次、审计、人工确认缺一不可，安全边界由后端保证而不是依赖模型自觉。

Agent 工具调用失败或超时怎么办？高频

分两层处理：工具层做重试和降级，Agent 层做错误感知、全局超时和监控告警。

工具层

  • 有限重试 + 指数退避：只对网络抖动、限流等临时性错误重试，间隔按 1s、2s、4s 递增并加随机抖动，设置最大次数；参数错误、权限错误不重试。写操作重试前必须保证幂等。
  • 熔断：某工具持续失败时熔断一段时间，避免拖垮整个 Agent。
  • 降级：重试失败后走备选工具、缓存结果或简化方案；无降级方案就明确告知该能力暂不可用。

Agent 层

  • 错误感知：把失败原因作为工具结果回传模型，让它换工具、调整参数或如实告知用户，而不是编造结果。
  • 全局超时：单个工具有超时，整个任务也有总超时和最大步数，避免因一个工具卡死而整体瘫痪；超时后返回部分结果或提示稍后重试。
  • 监控告警：统计每个工具的失败率、超时率、P99 耗时，超阈值告警，长期数据用于定位不稳定工具。

通过 CLI 命令调用工具和调用 MCP 服务有什么区别？

本质区别：CLI 是 Agent 直接生成并执行本地命令；MCP 是把工具按标准协议封装成带 Schema 的能力，由 Agent 通过 Client 调用。

维度 CLI MCP
调用方式 生成命令执行，如 git status、npm test Client 发送 tools/call 请求，Server 执行
工具描述 依赖模型对命令和参数的已有知识 显式声明名称、描述、inputSchema
返回结果 stdout / stderr 纯文本，需模型自行解析 结构化内容（text、image、resource 等）
安全控制 能力强、风险高，依赖沙箱和命令白名单 Server 侧可做权限、参数校验、密钥隔离
Token 开销 不需要预先注入工具定义 工具定义要放进上下文，工具多时开销大

适用场景

  • CLI：本地开发环境里本身就是命令行形态的工具，如 Git、构建、测试、日志分析、脚本执行。链路短、模型对常见命令很熟悉。
  • MCP：需要标准化接入数据库、企业内部 API、知识库、SaaS 服务，或者需要明确的参数约束、鉴权和安全边界的生产场景，以及跨多个 AI 应用复用同一批工具。

两者经常并存：编码类 Agent 用 CLI 操作本地仓库，同时用 MCP 接入 Issue 系统、数据库等外部服务。

MCP 基础与架构 7高频 5

什么是 MCP？它主要解决什么问题？高频

MCP（Model Context Protocol，模型上下文协议）是 Anthropic 于 2024 年 11 月开源的开放协议，用来标准化 AI 应用与外部工具、数据源之间的连接方式，常被比作 AI 应用的“USB-C 接口”。

解决的问题

  • 没有 MCP 时，每个 AI 应用接 GitHub、数据库、文件系统、浏览器、企业系统都要单独写适配代码，不同应用、不同 Agent 框架之间无法复用，形成 M×N 的集成成本。
  • MCP 让外部能力以统一协议暴露（MCP Server），任何支持 MCP 的应用（MCP Host）都能发现并使用，降低接入成本，让模型从“只有静态知识”变成“能检索信息、执行动作”。

核心组成

  • 三个角色：Host（AI 应用）、Client（Host 内与 Server 一对一连接的协议客户端）、Server（能力提供方）。
  • 三类服务端能力：Tools（可执行动作）、Resources（可读取的上下文数据）、Prompts（可复用提示模板）。
  • 协议基础：消息格式用 JSON-RPC 2.0，传输层支持 stdio 和 Streamable HTTP。

和 Function Calling 的关系：Function Calling 解决“模型如何发起工具调用”，MCP 解决“工具和资源如何标准化接入模型应用”，两者是配合关系。

怎么理解“MCP 是 AI 的 USB-C 接口”？

这个比喻强调的是“一个标准接口，连接任意设备”：USB-C 让键盘、显示器、硬盘用同一个口接电脑；MCP 让任意 AI Host 用同一套协议接入任意 MCP Server（GitHub、数据库、Slack、文件系统等）。

  • 统一接口：设备厂商只需实现 USB-C，电脑只需提供 USB-C 口；工具方只需实现一个 MCP Server，AI 应用只需实现 MCP Client。
  • 统一交互模式：USB-C 统一了数据、视频、供电；MCP 统一了工具调用、资源读取、提示模板获取三种交互，对应 Tools、Resources、Prompts 三种原语。
  • 可扩展：USB-C 通过替代模式承载多种协议；MCP 用这三种原语承载任意下游能力，并在初始化时做能力协商。
  • 双向通信：MCP 不只是 Client 请求 Server，Server 也能主动发通知（如工具列表变更）或反向请求 Client（如 sampling 请求 Host 调用模型）。

比喻的局限：MCP 只规定“怎么连、怎么说话”，不保证工具本身的质量和安全，也不负责模型如何选择工具。

M×N 集成问题是什么？MCP 怎么解决？

M×N 问题：有 M 个 AI 应用和 N 个工具 / 数据源，传统方式下每个应用要给每个工具单独写集成代码，工作量是 M×N；而且每个工具的协议、认证、数据格式各不相同，维护成本很高。

MCP 的解法

  • 每个工具或数据源只实现一次 MCP Server。
  • 每个 AI 应用只实现一次 MCP Client 协议。
  • 集成复杂度从 M×N 降为 M+N：新增一个工具，所有支持 MCP 的应用都能直接使用；新增一个应用，现有所有 MCP Server 都能直接接入。

这和 LSP（Language Server Protocol）解决“编辑器 × 编程语言”问题的思路一致，MCP 的设计也参考了 LSP。

MCP 的优势是什么？高频

MCP 的优势不在于单次调用比 Function Calling 更强，而在于标准化、解耦和可治理，适合工具多、链路复杂、需要长期维护的系统。

  • 统一接入：所有工具按同一协议暴露，应用侧不需要逐个适配，降低集成成本。
  • 一次实现，多处复用：同一个 MCP Server 可被 Claude Desktop、IDE、自研 Agent 等多个 Host 使用。
  • 解耦：工具实现与模型、应用解耦，换模型或换应用不用重写工具。
  • 动态发现：Client 运行时通过 tools/list 等获取能力，Server 增删工具后可发 list_changed 通知，无需改应用代码。
  • 能力更丰富：除了 Tools，还有 Resources、Prompts，以及 sampling、elicitation 等客户端能力，支持有状态会话和进度通知。
  • 便于治理：工具集中在 Server 侧，权限控制、参数校验、密钥管理、审计可以统一做。
  • 生态：主流 AI 应用和厂商普遍支持，已有大量现成的 MCP Server 可直接使用。

需要注意的代价：每个工具的定义都要放进上下文，接入工具过多会占用大量 Token 并降低选择准确率；第三方 Server 也带来供应链和 Prompt 注入风险。

MCP 的 Host、Client、Server 分别有什么作用？三者如何协同？高频

一句话：Host 负责理解用户需求和调度整体流程，Client 负责协议通信，Server 负责提供具体能力。

  • Host：用户直接交互的 AI 应用，如 Claude Desktop、IDE、Agent 平台。负责接收输入、调用大模型、决定何时用哪个工具、管理多个 Client，并负责用户授权和安全策略。
  • Client：运行在 Host 内部，与某个 Server 保持一对一连接。负责连接建立、initialize 能力协商、发送 tools/list、tools/call 等 JSON-RPC 请求、接收响应和通知。Host 连几个 Server 就有几个 Client。
  • Server：独立的能力提供程序（本地进程或远程服务），暴露 Tools、Resources、Prompts，接收请求、执行业务逻辑并返回结果，例如文件系统、数据库、GitHub、搜索服务的 MCP Server。

协同流程：用户在 Host 提需求 → Client 连接 Server 并发现能力 → Host 把工具定义交给模型 → 模型决定调用 → Host 通过 Client 发 tools/call → Server 执行并返回 → Host 把结果交给模型生成回答。

Server 侧典型配置参数

  • 连接参数：stdio 模式下是 command、args、env；远程模式下是 url 和认证信息（如 OAuth / Token）。
  • 能力声明：初始化时声明支持 tools、resources、prompts 等。
  • 工具参数 Schema：每个工具的 name、description、inputSchema（JSON Schema），模型按它构造 tools/call 的参数。
# 使用官方 Python SDK 的 FastMCP 快速写一个 Server
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("weather")

@mcp.tool()
def get_weather(city: str) -> str:
    """查询指定城市的天气"""
    return f"{city}：晴，25℃"

if __name__ == "__main__":
    mcp.run()  # 默认使用 stdio 传输

MCP 支持哪些能力类型？高频

MCP Server 向 Client 提供三类核心能力（原语），每类都有对应的“列出 / 获取”方法：

能力 含义 控制方 主要方法
Tools 可执行动作，如搜索、查库、写文件、调 API 模型决定调用 tools/list、tools/call
Resources 可读取的上下文数据，如文件、数据库 Schema、日志、文档，用 URI 标识 应用决定读取 resources/list、resources/read、resources/subscribe
Prompts 可复用的提示模板或任务流程，可带参数 用户选择（如斜杠命令） prompts/list、prompts/get

Client 侧也提供能力供 Server 反向使用

  • Sampling：Server 请求 Host 调用模型生成内容，Server 无需自己持有模型 Key。
  • Roots：Client 告知 Server 可操作的文件系统范围。
  • Elicitation：Server 在执行中向用户请求补充信息。

此外还有通知机制（如 notifications/tools/list_changed）、进度通知、日志、取消等工具性功能。

MCP 基于什么协议？底层通信方式是什么，为什么这么设计？高频

MCP 的消息格式基于 JSON-RPC 2.0，传输层与消息格式解耦，标准传输有两种：stdio 和 Streamable HTTP。

消息格式：请求（带 id 和 method）、响应（result 或 error）、通知（无 id，无需响应）。

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": { "name": "search", "arguments": { "query": "MCP" } }
}

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [{ "type": "text", "text": "MCP 是 Model Context Protocol……" }],
    "isError": false
  }
}

注意两类错误的区别：协议层错误（方法不存在、参数非法）用 JSON-RPC 的 error 返回；工具执行失败一般放在 result 里并设 isError: true，让模型能看到错误并自行调整。

传输方式

  • stdio：Host 以子进程方式启动 Server，通过标准输入输出交换消息。适合本地工具（文件系统、Git、本地脚本），部署简单、无需网络端口。
  • Streamable HTTP：Server 作为独立服务提供一个 HTTP 端点，Client 用 POST 发送消息，Server 可直接返回 JSON，也可升级为 SSE 流式推送多条消息，支持会话 ID 和断线恢复。2025-03-26 版规范用它取代了早期的 HTTP+SSE 双端点方案。适合远程和企业级部署，便于接入认证、网关、监控和横向扩展。

为什么这么设计

  • JSON-RPC 简单、成熟、语言无关，天然支持请求 / 响应和双向通知。
  • 协议与传输解耦，本地和远程场景可以各选合适的传输。
  • 基于 HTTP 的远程传输能复用现有的 OAuth 鉴权、负载均衡和网关基础设施。

MCP 调用流程与对比 9高频 6

一次完整的 MCP 工具调用流程是什么？高频

关键点：不是模型直接调函数，而是模型提出调用意图，真正发请求的是 Host 里的 MCP Client，Server 只负责按协议暴露工具并返回结果。以“查北京天气”为例：

  1. 建立连接：Host 按配置启动本地 Server 子进程（stdio）或连接远程 Server（Streamable HTTP）。
  2. 初始化：Client 发 initialize 协商协议版本和能力，Server 响应后 Client 发 notifications/initialized。
  3. 能力发现：Client 发 tools/list，拿到工具名称、描述、inputSchema。
  4. 模型决策：用户问“帮我查北京的天气”，Host 把工具列表转成 Function Calling 格式连同问题发给模型，模型返回调用 get_weather，参数 {"city": "北京"}。
  5. 用户确认（可选）：敏感工具先展示工具名和参数，经用户批准再执行。
  6. 调用与执行：Client 发 tools/call 请求，Server 执行业务逻辑（如调真实天气 API），返回 text、image、资源链接等结构化内容。
  7. 生成回答：Host 把结果交给模型，模型生成“北京今天晴，25℃”，或继续下一次调用。

前置条件：工具方提供 MCP Server（通常封装自家 API），用户在 Host 中配置好 Server 的启动方式或地址以及所需密钥。

MCP 的工具发现/调用是主动拉取还是被动推送？高频

以 Client 主动拉取为主，Server 推送通知为辅。

  • 发现：会话初始化后，Client 主动发送 tools/list、resources/list、prompts/list 拉取能力列表（支持分页）。
  • 调用：由 Host 根据模型决策，通过 Client 主动发起 tools/call。Server 不会主动执行工具并把结果推给模型。
  • 变更通知：如果 Server 在初始化时声明了 listChanged 能力，工具列表变化时会发送 notifications/tools/list_changed，Client 收到后再重新拉取一次。Resources 还支持 resources/subscribe 订阅，资源更新时 Server 推送 notifications/resources/updated。

所以准确的说法是：调用是请求 - 响应式的主动拉取；变更感知可以由 Server 通知触发，但拿数据仍是 Client 去拉。

MCP 和 Function Calling 有什么核心区别？高频

两者解决的问题层级不同：Function Calling 是模型能力，解决“模型怎么决定调哪个函数、怎么生成参数”；MCP 是系统层的开放协议，解决“工具怎么被标准化接入、发现和调用”。两者是配合关系，不是替代关系。

维度 Function Calling MCP
本质 模型 API 提供的能力，推理层 应用层开放协议，与具体模型解耦
定义方 各模型厂商，格式不完全通用 Anthropic 发起的开放标准，社区共建
工具位置 定义和实现写在当前应用里 由独立的 MCP Server 暴露，可跨应用复用
通信 应用调模型 API 时带上工具定义 Client 与 Server 之间走 JSON-RPC 2.0，经 stdio 或 Streamable HTTP
发现方式 开发者硬编码工具列表 运行时 tools/list 动态发现
状态 每次请求都要带上工具定义 Client 与 Server 有会话，支持能力协商和通知
能力范围 只有函数调用 Tools、Resources、Prompts，及 sampling 等双向能力

两者如何配合：Host 把 Server 的工具列表转换成模型的 Function Calling 定义；模型通过 Function Calling 输出调用意图，Host 再经 MCP Client 转发给 Server。MCP 负责“工具从哪来、怎么执行”，Function Calling 负责“模型怎么表达要调用”。

什么场景选 Function Calling，什么场景更适合 MCP？

判断标准是工具的数量、复用范围和治理要求。

选 Function Calling

  • 工具少、业务边界清晰、只服务一个应用。
  • 例如查天气、算价格、查订单、创建日程、调用一个内部接口。
  • 开发成本低、链路短、延迟小，无需额外部署 Server 进程。

选 MCP

  • 工具多，或者多个 AI 应用 / Agent 要复用同一批工具。
  • 需要接入文件系统、数据库、Git、浏览器、Jira、知识库等现成生态。
  • 例如公司内多个 Agent 都要访问知识库、GitLab、Jira；IDE Agent 要读代码、查 Git 状态；企业 AI 平台要统一接入多个业务系统。
  • 需要工具独立部署、独立升级，以及统一的鉴权、审计。

两者并不冲突：简单场景直接 Function Calling，规模化后把工具下沉到 MCP Server，模型侧仍通过 Function Calling 表达调用。

MCP 和 HTTP API 调用有什么区别？高频

HTTP API 是通用的服务间接口调用方式；MCP 是面向大模型应用的工具接入协议。两者是不同层级的东西，MCP 不替代 HTTP API。

维度 HTTP API MCP
定位 通用传输与接口，服务对服务 AI 应用专用的上下文与工具协议
能力描述 靠接口文档，调用方硬编码 运行时自动发现，带自然语言描述和 JSON Schema，模型可直接理解
交互模型 各接口格式自定，主要是请求 / 响应 统一的 JSON-RPC 消息，内置能力协商、通知、进度、取消
能力类型 只有接口 Tools、Resources、Prompts
会话 一般无状态 有会话生命周期（初始化、能力协商）

关系：很多 MCP Server 底层仍调用已有的 HTTP API，只是把它包装成模型可理解、可调用的 tools 或 resources。而 MCP 的远程传输 Streamable HTTP 本身就跑在 HTTP 之上。可以理解为 MCP 是在 HTTP API 之上面向 Agent 的标准化封装层。

MCP 和 RAG 有什么区别？高频

两者不是同一类东西：RAG 是一种问答增强方案，补充外部知识；MCP 是一种工具接入协议，标准化连接外部能力。

维度 RAG MCP
定位 解决知识不足：检索相关文档片段放进上下文 解决能力接入：统一暴露工具、资源、提示模板
处理对象 文本知识：文档、FAQ、知识库 工具能力和数据：查库、读文件、搜网页、调业务接口
输出 增强后的上下文，模型据此生成回答 工具调用结果，模型据此继续推理或回答
是否有副作用 只读 可读可写（如发消息、建工单）

相似点与结合：两者都会根据用户 Query 做匹配，RAG 召回相关文本，MCP 场景下模型根据工具描述选工具。它们可以组合：把向量检索封装成一个 MCP Server 的 search 工具，或把知识库文档作为 MCP Resources 暴露，这就是 Agentic RAG 的常见做法。

为什么有些推理模型不支持 MCP？MCP 对模型能力有哪些要求？

严格说 MCP 是协议，不是模型能力。模型本身并不“支持 MCP”，而是 Host / Agent 框架实现了 MCP Client，并把 MCP 工具转换成模型能理解的工具调用格式。所谓“模型不支持 MCP”，通常是以下原因：

  • 模型不支持或不擅长 Tool Calling / 结构化输出：无法稳定选择工具、生成合法参数。
  • 模型 API 不开放工具调用接口：只支持纯文本输入输出，不支持 tools 参数或 JSON Schema 约束。
  • 推理过程不支持中途调用工具：部分推理模型擅长长链思考，但不支持边推理边调工具，或在早期版本中未开放该能力。
  • 宿主应用没有实现 MCP Client：模型能调工具，但所在平台无法连接 MCP Server。

MCP 对模型能力的要求

  • 理解工具描述，判断是否需要工具。
  • 在多个工具中选对工具，生成符合 Schema 的参数。
  • 理解工具返回结果，进行多轮调用和错误恢复。
  • 在工具很多时保持选择准确率（长上下文能力）。
  • 具备一定的安全边界意识，不被工具返回内容中的注入指令带偏。

基于 MCP 做过多工具编排吗？怎么做？

可以这样设计：Agent 同时接入多个 MCP Server，Host 统一聚合工具，由模型或编排引擎决定调用顺序。

  1. 多 Server 接入与聚合：每个 Server 对应一个 Client，Host 汇总所有 tools/list 结果形成统一工具目录；不同 Server 可能有同名工具，需要加命名空间前缀（如 github__create_issue）避免冲突。
  2. 意图识别与工具路由：工具很多时，先按意图或 embedding 召回 Top K 工具再交给模型，减少 Token 和误选。
  3. 编排模式：
    • 串行：上一个工具的结果作为下一个工具的入参。
    • 并行：无依赖的工具并发调用后统一合并。
    • 条件分支：根据中间结果决定走哪条路径。
  4. 上下文维护：保存每一步工具结果和状态，供后续步骤和下一轮对话使用。
  5. 复杂流程固化：稳定的长流程可以用 DAG / 工作流引擎编排，节点内部仍通过 MCP 标准调用工具；灵活场景用 ReAct 让模型动态决策。
  6. 治理：统一超时、重试、权限和审计，避免一个 Server 故障拖垮整体流程。

MCP 有哪些安全机制？沙箱隔离、密钥管理怎么做？高频

MCP 安全的核心是把工具调用限制在可控边界内，依赖权限控制、用户确认、参数校验、沙箱隔离、密钥管理和审计，而不是依赖模型自己判断安全。

  • 鉴权：远程 Server 按规范使用 OAuth 2.1 授权，Client 携带访问令牌；Server 校验令牌的受众是否为自己，禁止把令牌透传给下游服务。本地 stdio Server 一般从环境变量获取凭证。
  • 权限控制：Server 只暴露必要工具，遵循最小权限原则。文件工具只能访问指定目录（可结合 Roots），数据库工具只读或仅能访问授权表。按用户 / 角色过滤可见工具。
  • 用户确认：对写文件、执行命令、发送消息等高风险调用，Host 展示工具名、参数和影响范围，由用户确认后才执行。
  • 参数校验：Server 不信任模型传入的参数，校验路径穿越、SQL 是否只读、命令是否危险，防止注入。
  • 沙箱隔离：高风险 Server 运行在容器、虚拟机或受限进程中，限制文件系统、网络、环境变量和系统命令权限。
  • 密钥管理：API Key、Token、数据库密码不写进 Prompt、不暴露给模型，存放在环境变量、配置中心或密钥管理服务中，由 Server 侧使用；定期轮换。
  • 超时与限流：每个工具设置超时和调用频率上限。
  • 审计日志：记录工具名、参数、调用时间、结果和用户身份，便于追溯。
  • Prompt 注入与供应链防护：工具返回的内容只当数据不当指令；警惕工具描述中被植入恶意指令（tool poisoning）；只使用可信来源的 Server，固定版本并审查更新。

WebSocket 和 SSE 有什么区别？在 AI 场景下各适合什么？

两者都能实现服务端实时推送，区别在于方向和协议：SSE 是基于 HTTP 的服务端单向推送，WebSocket 是独立的全双工协议。

维度 SSE（Server-Sent Events） WebSocket
方向 服务端 → 客户端单向 双向全双工
协议 普通 HTTP 响应，Content-Type: text/event-stream HTTP Upgrade 握手后切换为 ws / wss 协议
数据格式 UTF-8 文本事件 文本或二进制帧
重连 浏览器 EventSource 内置自动重连和 Last-Event-ID 需要自己实现心跳和重连
基础设施兼容 天然兼容 HTTP 网关、鉴权、负载均衡 需要代理支持长连接和 Upgrade

AI 场景选择

  • SSE：大模型逐 token 流式输出，是主流模型 API（OpenAI、Anthropic 等）流式响应的标准做法；MCP 的 Streamable HTTP 也用 SSE 做流式返回。简单、稳定、易于接入现有 HTTP 生态。
  • WebSocket：实时语音、多人协作、需要客户端频繁发送中间状态或随时打断的复杂双向交互，例如 OpenAI Realtime API 就提供 WebSocket 接口。

为什么实时 AI 语音场景通常用 WebRTC？相比 WebSocket 有什么优势？

WebRTC 是专为实时音视频设计的技术栈，而 WebSocket 只是通用的双向数据通道，没有针对音视频优化。

WebRTC 的优势

  • 低延迟传输：媒体走基于 UDP 的 RTP / SRTP，不受 TCP 队头阻塞和重传的影响；WebSocket 基于 TCP，弱网下一个包丢失会阻塞后续数据，延迟抖动明显。
  • 内置音频处理：Opus 编解码、抖动缓冲、回声消除（AEC）、噪声抑制、自动增益，这些对语音对话体验很关键，用 WebSocket 需要自己实现。
  • 网络自适应：带宽估计、拥塞控制、码率自适应，丢包时用 FEC / PLC 等手段恢复。
  • NAT 穿透：通过 ICE、STUN、TURN 建立连接，支持点对点和媒体服务器（SFU）架构。
  • 浏览器原生支持：可直接采集麦克风并推流，前端接入方便，传输天然加密。

取舍：WebRTC 部署更复杂（信令服务、TURN 服务器）。服务端到服务端、或对延迟要求没那么高的语音场景，用 WebSocket 传音频分片更简单；面向终端用户的实时语音 Agent，客户端到服务端通常用 WebRTC。

什么是 A2A（Agent to Agent）协议？它和 MCP 有什么核心区别？

A2A 是 Google 在 2025 年 4 月发布的开放协议（后移交 Linux 基金会），用于让不同厂商、不同框架构建的 Agent 之间互相发现、通信和委托任务。

A2A 核心概念

  • Agent Card：Agent 的 JSON 描述文件（通常位于 /.well-known/agent-card.json），声明名称、能力（skills）、端点和认证方式，用于发现。
  • Task：协作的基本单位，有生命周期状态（submitted、working、input-required、completed、failed 等），支持长时间运行的任务。
  • Message / Artifact：Agent 之间交换的消息和最终产出物，可包含文本、文件、结构化数据等多种 Part。
  • 传输：基于 HTTP，使用 JSON-RPC 2.0，支持 SSE 流式更新和推送通知。

与 MCP 的区别

维度 MCP A2A
连接对象 Agent ↔ 工具 / 数据源 Agent ↔ Agent
对方的性质 被动的能力提供者，按调用执行 自主的智能体，内部逻辑不透明，可多轮协商
交互粒度 单次工具调用 任务委托，可长时间运行、中途要求补充输入
典型场景 让 Agent 查库、读文件、调 API 跨团队 / 跨厂商 Agent 协作，如采购 Agent 委托报价 Agent

两者互补：一个 Agent 对外用 A2A 与其他 Agent 协作，对内用 MCP 接入自己的工具。

用过哪些 AI 网关框架？为什么 AI 系统需要单独做网关层？

常见的大模型网关方案包括：LiteLLM（开源，统一 OpenAI 兼容接口、支持 100+ 模型、带成本统计）、One API / New API（国内常用的多渠道分发和额度管理）、OpenRouter（托管式多模型路由服务）、Portkey、Kong AI Gateway、Higress（基于 Envoy 的 AI 网关），以及基于 Spring Cloud Gateway、Nginx、Envoy 自研扩展的 LLM Gateway。

为什么要单独做网关层：普通 API 网关关注路由、鉴权、限流、负载均衡；大模型调用还有一系列特有需求：

  • 多厂商接口格式不同，需要统一协议适配。
  • 计费按 Token 而不是请求次数，限流也需要按 Token（TPM）维度。
  • 响应是长时间的流式 SSE，对超时和连接管理要求不同。
  • 需要 Prompt / 响应审计、敏感信息脱敏、内容安全审核。
  • 需要按成本、延迟、能力做模型路由，以及供应商故障时自动切换。
  • 需要控制上下文长度、做语义缓存来降成本。

AI 网关一般解决哪些问题？为什么不能让业务系统直接调大模型？

AI 网关解决的问题

  • 统一接入：屏蔽 OpenAI、Claude、Gemini、通义、本地模型等的接口差异，对外统一请求和响应格式。
  • 统一鉴权与密钥托管：业务系统只访问内部网关，厂商 API Key 集中保管、不外泄。
  • 限流配额：按用户、部门、应用、模型维度限制 RPM / TPM。
  • 计费与成本：统计 Token 消耗、调用次数、费用，支持预算告警。
  • 模型路由：按任务类型、成本、延迟、可用性选择模型。
  • 熔断降级：某个模型或供应商不可用时自动切换备用模型。
  • 审计：记录请求、响应和上下文，用于排查和合规。
  • 安全治理：敏感信息脱敏、Prompt 注入检测、输出内容审核。
  • 缓存：对高频请求做精确缓存或语义缓存，降低成本和延迟。

业务系统直接调模型的问题

  • 接入方式不统一，每个系统重复开发适配。
  • API Key 分散在各系统，泄露风险高。
  • 成本无法统一统计和管控。
  • 限流、熔断、重试各自实现，难以统一治理。
  • 切换模型要改每个业务系统，成本高。
  • Prompt 和响应日志分散，难以审计。

公司内部接了多个大模型，如何设计统一的大模型网关层？

可以按分层架构设计，对上提供统一 API（通常兼容 OpenAI 格式，降低业务改造成本），对下适配各家模型。

  • 接入层：统一的 Chat、Embedding、Rerank 等接口，支持同步和 SSE 流式。
  • 鉴权层：API Key、JWT、OAuth2，按应用、用户、部门做权限和模型白名单。
  • 路由层：按请求类型和策略选模型：
    • 简单问答走低成本模型，复杂推理走高能力模型；
    • Embedding 走向量模型，代码任务走代码模型；
    • 敏感数据业务走私有化部署模型；
    • 同一模型多个渠道按权重和健康度负载均衡。
  • 策略层：限流（RPM / TPM）、超时、重试、熔断、降级、灰度发布和 A/B 测试。
  • 安全层：Prompt 注入检测、敏感信息脱敏、输出内容审核。
  • 成本层：Token 计量、费用统计、预算控制和超额告警。
  • 缓存层：精确缓存、语义缓存，以及 Embedding 结果缓存；同时利用厂商的 Prompt Caching。
  • 观测层：日志、Trace、首 token 延迟、总耗时、错误率、Token 消耗、模型命中率。
  • 适配层：每家厂商一个 Adapter，如 OpenAIAdapter、ClaudeAdapter、QwenAdapter、vLLMAdapter，负责请求转换、流式协议转换和错误码映射。

设计要点：网关本身无状态便于水平扩展；流式转发要注意背压和连接超时；路由和配额配置支持热更新。

Skill 概念与对比 8高频 6

什么是 Agent Skill？有什么作用？本质上解决了大模型什么问题？高频

Agent Skill 是把某类任务的流程、领域知识、脚本和模板封装成一个可发现、可复用的能力包，让 Agent 在相关任务出现时按需加载。可以类比成给 Agent 的一份“岗位手册”：固定流程、注意事项、工具用法沉淀下来，不用每次重新解释。

标准形态：Anthropic 在 2025 年 10 月推出 Agent Skills，随后作为开放标准发布，已被多个 Agent 产品采用。一个 Skill 就是一个文件夹，以 SKILL.md 为入口：YAML frontmatter 写 name 和 description，正文写执行指令，另可附带 scripts/、references/、assets/ 等文件。

核心作用

  • 渐进式披露：启动时只加载每个 Skill 的 name + description，命中后才读 SKILL.md 正文，执行时再按需读参考文件或运行脚本。
  • 封装经验：不只是一个工具接口，而是把标准流程、业务规则和最佳实践打包，教模型“如何系统性地完成一类任务”。
  • 即插即用：不改 Agent 代码或模型，放进 Skill 目录即生效，可跨项目共享和版本管理。

本质上解决的问题

  • 上下文与专业知识的矛盾：知识全塞 System Prompt 浪费 Token、干扰推理，Skill 让知识按需进入上下文。
  • Prompt 不稳定：复杂流程靠临时 Prompt 难复现，Skill 把流程固化，输出更一致。
  • 确定性操作不可靠：模型现场写代码处理文件易出错，Skill 附带验证过的脚本，模型只需执行。

企业 Agent 平台里的“Skill”也常指带参数 Schema、执行器、权限配置的业务能力单元（如“退款处理”），思想一致：在原子工具之上封装面向任务的能力。

Skill 和普通 Tool 有什么区别？高频

Tool 是原子能力，“能做一个动作”；Skill 是把 Tool、流程策略和约束包装成的任务能力，“能完成一类任务”。

维度 Tool Skill
粒度 单个操作：查库、读文件、发请求、发邮件 完整任务：审合同风险、生成周报、排查线上故障
内容 名称 + 描述 + 参数 Schema + 实现 指令流程、领域知识、脚本、模板，内部可用多个 Tool
模型负担 每次要自己规划如何组合 按 Skill 给出的流程执行，稳定性更高
进入上下文的方式 工具定义通常常驻上下文 只有元数据常驻，正文按需加载
工程管理 管接口层 管能力层，便于版本管理、效果评估、权限控制

举例：send_email 是 Tool；“为销售生成客户跟进邮件并发送”是 Skill，内部可能包括查询客户信息、总结历史沟通、按模板生成邮件、调用发送工具、记录 CRM 日志。

只暴露 Tool 会让模型每次从零组合，结果波动大；做成 Skill 后，模型在更高层级复用经过验证的做法。

Skill 和 Tool Calling 相比有什么不同？高频

Skill 是 Tool Calling 之上的封装：Tool Calling 解决“调哪个函数、怎么传参”，Skill 解决“怎么把这件事做好”。

  • 交给模型的内容不同：Tool Calling 只给函数定义（JSON Schema），调完即结束；Skill 给的是完整任务包，包括步骤说明、配套脚本、模板、参考文档。
  • 解决的问题不同：Tool Calling 是单一动作的调用机制；Skill 让模型完整掌握一项任务，把工具用法、领域知识、输出规范、最佳实践一起注入。
  • 作用方式不同：Skill 本质是按需注入上下文的指令和资源，能引导模型完成多步骤推理、创作、测试等任务，而不只是一次接口调用。
  • 依赖关系：Skill 执行时仍要依靠 Tool Calling（如执行脚本、读文件、调 MCP 工具）来真正动手，两者是上下层关系，不是替代关系。

Skill 和 Function Calling、Tool、Plugin 的核心区别是什么？

四者处于不同层级，可以这样区分：

概念 层级 核心内容 特点
Function Calling 模型层 模型按函数 Schema 输出调用请求 只定义入参出参，不含业务语义和流程
Tool 工具层 单个可执行能力，如查天气、联网搜索 原子操作，不含复杂业务流程
Plugin 框架 / 生态层 第三方扩展包，可能包含多个工具、命令、配置 偏分发和集成形态，对使用方常是黑盒
Skill 任务 / 业务层 指令 + 知识 + 脚本 + 资源，可调用多个 Tool 带意图描述和执行方法，按需加载，可组合、可治理
  • Function Calling 是“表达调用”的机制，Tool 是“被调用”的能力，Plugin 是“打包分发”的形式，Skill 是“完成任务的方法”。
  • 一些产品中 Plugin 可以把 Skills、MCP Server、命令、Hooks 打包在一起分发，所以 Plugin 和 Skill 是包含关系而不是并列关系。

Skill 和 System Prompt / Prompt 有什么区别？各自适用性？高频

Prompt 是一次性的任务指令，System Prompt 是每次请求都生效的全局指令；Skill 是持久化、按需加载的能力封装。

维度 System Prompt 普通 Prompt Skill
生效方式 每次请求都常驻 当前对话有效 任务匹配时才加载正文
内容 角色、风格、全局约束 本次任务要求 特定任务的流程、知识、脚本、资源
能力范围 只影响模型输出 只影响模型输出 可附带脚本和资源，配合工具执行操作
Token 成本 全量常驻，越长越贵 每次重复输入 平时只占元数据，命中后才加载
稳定性 稳定但难以容纳大量领域知识 表述不同结果易波动 流程固定，输出更一致
复用 绑定单个应用 难复用 可跨项目、跨 Agent 复用

适合用 Prompt

  • 一次性任务，不需要沉淀。
  • 简单直接的指令，如“修复这个 bug”“总结这段内容”。
  • 探索性任务、需求和流程还不明确。
  • 快速验证想法。

适合用 Skill

  • 反复出现的工作流。
  • 需要固化的专业知识、业务规则、SOP。
  • 多步骤协调任务，需要脚本或模板保证确定性。
  • 需要跨项目或跨 Agent 复用。
  • 任务复杂且频繁使用，对 Token 成本敏感。

适合放 System Prompt：所有任务都需要遵守的角色设定、安全边界和全局输出风格。

Skill 和 MCP 有什么关系？如何配合使用？系统设计层面最大区别是什么？高频

两者互补：MCP 是协议层，解决“Agent 能连接哪些外部系统、以统一方式访问工具和数据”；Skill 是能力层，解决“拿到这些能力之后按什么流程、什么标准把任务做对”。一个偏连接，一个偏方法。

维度 MCP Skill
设计层级 协议 / 接入层 任务 / 知识层
本质 Client-Server 协议，JSON-RPC 2.0 文件夹：SKILL.md + 脚本 + 资源
提供什么 可调用的工具、可读取的资源 执行步骤、领域知识、最佳实践、配套脚本
运行形态 需要运行 Server 进程或远程服务 静态文件，由 Agent 读取和执行
上下文开销 工具定义通常常驻上下文 只有元数据常驻，按需加载

配合方式：Agent 先加载某个 Skill，再按 Skill 的指引调用通过 MCP 接入的外部工具。例如故障排查 Skill 规定排查步骤、判断标准和报告模板，具体的日志查询、监控数据获取、数据库访问由 MCP Server 完成。Skill 里也可以写明“使用哪个 MCP 工具、参数怎么填、结果怎么解读”，弥补 MCP 工具只给接口不给用法的不足。

Tool Calling、Function Call、MCP、Skill 分别解决什么问题？它们是什么关系？高频

四者在不同层级各管一件事：

  • Tool Calling：总称性的范式，指模型自主决定调用外部工具完成任务的整套机制。
  • Function Calling：Tool Calling 在模型 API 层的具体实现，模型输出函数名和参数 JSON，格式由各厂商定义、互不完全通用。解决“模型如何表达调用”。
  • MCP：工具接入的开放协议，标准化工具的暴露、发现和调用，让工具与模型、应用解耦。解决“工具从哪来、如何标准化接入”。
  • Skill：在工具之上的任务能力包，注入流程、领域知识和输出规范，内部依赖 Tool Calling / MCP 来真正执行操作。解决“怎么把一类任务做好”。

关系：MCP 提供工具生态，Function Calling 负责让模型发起调用，Skill 负责组织任务流程，三者共同构成 Tool Calling 的完整体系。

举例：自动生成日报的 Agent 中，MCP Server 提供读取项目管理系统、查询 Git 提交、查询日历、读取文档等工具；模型通过 Function Calling 调用这些工具；日报 Skill 规定“读取任务 → 汇总进展 → 提取风险 → 按模板生成日报 → 发送邮件”的流程。

怎么理解 Harness 工程？和 Prompt、Context 工程有什么区别？

Harness 工程是围绕模型构建“运行外壳”的工程：把模型、提示词、上下文、工具、记忆、状态、权限、评估和监控组合成一个稳定可运行的 Agent 系统。三者是逐层扩大的关系。

维度 Prompt 工程 Context 工程 Harness 工程
关注点 怎么写指令让模型答得好 每一步给模型放什么信息、放多少 模型之外的整套运行机制
典型手段 角色设定、Few-shot、输出格式、思维链 RAG 检索、记忆管理、上下文压缩、工具结果裁剪、Skill 按需加载 Agent 循环、工具执行与沙箱、权限与人工确认、子 Agent、重试与恢复、评估与可观测性
作用范围 单次调用 多轮 / 多步调用中的上下文窗口 整个 Agent 生命周期

同一个模型放在不同的 Harness 里表现差异很大，例如编码类 Agent 的效果很大程度上取决于工具设计、上下文管理和执行循环，而不只是模型本身。Skill、MCP 都可以看作 Harness 的组成部分。

Skill 结构与运行机制 8高频 5

Agent Skill 由哪些核心结构组成？标准目录结构是什么？高频

一个 Skill 就是一个目录，SKILL.md 必需，其余可选：

your-skill-name/
├── SKILL.md            # 必需：frontmatter 元数据 + 正文指令
├── scripts/            # 可选：可执行脚本
│   ├── process_data.py
│   └── validate.sh
├── references/         # 可选：参考文档，按需读取
│   └── api-guide.md
└── assets/             # 可选：模板、样例、静态资源
    └── report-template.md

SKILL.md 的结构

---
name: pdf-processing
description: 提取 PDF 文本和表格、填写表单、合并文件。当用户处理 PDF 文件或提到表单、文档提取时使用。
---

PDF 处理流程：
1. 用 scripts/extract.py 提取文本……
2. 表单填写详见 references/forms.md
  • frontmatter：name（小写字母、数字、连字符，最长 64 字符，通常与目录名一致）和 description（最长 1024 字符，写清做什么、何时使用）为必填；可选字段有 license、compatibility、metadata、allowed-tools（预先授权可用的工具，部分实现支持）等。
  • 正文：执行步骤、示例、注意事项，以及指向其他文件的引用。建议控制在 500 行以内，详细内容拆到 references。
  • scripts/：确定性、可重复的操作，如数据处理、校验、格式转换，由 Agent 执行而不必阅读源码。
  • references/：API 文档、规范、示例等，只在正文要求时读取。
  • assets/：报告模板、配置样例、图片等执行时使用的材料。

企业平台自定义的 Skill 还常包含 input_schema（参数 JSON Schema）、executor（执行器类型、超时、重试）、version、权限字段（required_role、白名单）、output_schema 等，用于参数校验、调度和治理。

Skill 的运行流程是怎样的？高频

从任务识别到按需加载，再到执行和反馈，不会一开始把所有 Skill 内容塞进上下文。

  1. 启动时加载元数据：Agent 扫描 Skill 目录，只把每个 Skill 的 name 和 description 放入系统上下文，形成一份技能目录。
  2. 触发与匹配：
    • 自动匹配：模型根据用户任务和 description 判断是否需要某个 Skill；
    • 用户显式调用：通过斜杠命令或菜单指定 Skill；
    • 平台推荐：先分析需求，再推荐可用 Skill 供选择。
  3. 加载 SKILL.md：命中后读取完整正文注入上下文，Agent 相当于拿到了这项任务的操作手册。
  4. 执行工作流：按 SKILL.md 的步骤执行，过程中可能运行 scripts/ 中的脚本（只把输出放进上下文）、按需读取 references/ 文件、调用其他工具或 MCP 服务。
  5. 状态管理：复杂任务记录当前步骤、中间产物、异常情况，便于重试和追踪；长任务可对历史过程做压缩。
  6. 输出与反馈：返回结果，记录日志和使用情况，用于后续优化 Skill。

运行依赖的前提是 Agent 具备文件读取和代码执行环境（如沙箱中的 bash），这样才能按需读文件和运行脚本。

Skill 如何节省 Token？什么是渐进式披露？高频

渐进式披露（Progressive Disclosure）是指把大量说明、文档和代码放在文件系统中，只在需要时才把需要的那部分读进上下文。这样既省 Token，也减少无关信息对推理的干扰。

层级 内容 何时加载 大致开销
第一层：元数据 frontmatter 中的 name + description Agent 启动时，所有 Skill 都加载 每个 Skill 约百来个 token
第二层：指令 SKILL.md 正文 任务命中该 Skill 时 建议控制在 5k token 以内
第三层：资源与代码 references、assets、scripts 正文指引需要时 按需，理论上不设上限

为什么能省

  • 未使用的 Skill 只占一行目录，安装很多 Skill 也不会撑爆上下文。
  • 参考资料、数据库 Schema 等大文件默认不进上下文，需要时才读取相应文件甚至相应片段。
  • 脚本直接执行，模型只接收运行结果，不需要阅读源码，也不需要现场生成大段代码。

对比：MCP 工具定义和 System Prompt 通常是全量常驻的，工具和知识越多开销越大；Skill 的成本与实际使用量相关。

主 Skill 和子 Skill 分别有什么作用？高频

主 Skill 管全局流程，子 Skill 管局部能力，二者是“总 - 分”关系。

  • 主 Skill：面向一个完整任务提供统一入口，定义整体目标、执行顺序、各步骤调用哪个子能力、结果如何汇总产出。偏编排。
  • 子 Skill：封装某一类具体能力或某个细分步骤，如“数据提取”“图表生成”“格式校验”，可被多个主 Skill 复用。偏能力复用。

设计要点

  • 子 Skill 职责单一、输入输出清晰，便于独立测试和复用。
  • 主 Skill 只写流程和衔接逻辑，细节下沉到子 Skill，保持主文件精简。
  • 避免层级过深，否则加载链路变长、上下文和延迟都会增加；通常两层足够。

例如“生成周度经营分析报告”主 Skill 依次调度数据查询、指标分析、图表生成、报告排版几个子 Skill。

如何设计一个高质量的 Skill？高频

目标不是写得越多越好，而是让 Agent 能快速判断是否该用、清楚知道怎么执行、并尽量少占上下文。

  • 单一职责：一个 Skill 聚焦一类任务或一个完整工作流，不把无关能力堆在一起，便于维护和准确匹配。
  • 粒度合适：太粗则内容庞杂、边界不清；太细则简单任务也要组合多个 Skill。一般以“一个相对完整的工作流”为单位。
  • description 写清楚：说明做什么、适用场景、触发关键词，必要时写明不适用场景。这是决定能否命中的关键。
  • 正文结构清晰：用步骤、列表、检查清单组织，突出执行顺序、关键操作和注意事项，避免大段散文。
  • 简洁高密度：只写模型不知道的内容，不解释常识；正文建议 500 行以内。
  • 资源外部化：长文档放 references，模板放 assets，确定性逻辑写成 scripts，正文只保留核心流程和引用，符合渐进式披露。
  • 自由度匹配任务：易错、需要一致性的操作给出精确步骤或脚本；需要判断的任务给原则和示例。
  • 可测试：明确输出标准，提供样例输入输出或校验脚本，用真实任务评估并迭代。
  • 安全：脚本避免危险操作，不在 Skill 里硬编码密钥；引入第三方 Skill 前审查其脚本和内容。

Skill 的 description 为什么重要？写得不好导致误调用怎么办？

模型并不读取所有 Skill 的正文，判断“要不要用、用哪个”几乎完全依赖 description，所以它决定了 Skill 的召回率和准确率。很多路由问题本质上都是 description 设计问题。

常见问题

  • 范围过大：如“负责查询信息”，会和搜索、数据库、RAG 等多个 Skill 冲突，导致误调用。
  • 过于抽象：只写“处理文档”，没写触发场景，导致该用时没用（漏调用）。
  • 多个 Skill 描述雷同，模型无法区分。

改进方法

  • 同时写清“做什么”和“什么时候用”，包含用户常用的关键词和文件类型等触发信号。
  • 写明输入输出、边界条件和不适用场景。
  • 使用第三人称、具体动词，避免空泛形容词。
  • 收集误调用和漏调用的线上案例，构造测试集反复评估 description，迭代到命中率稳定。

Skill 的入参 Schema 怎么设计？为什么要做参数约束？

对于带执行器的业务 Skill，入参一般用 JSON Schema（或 Pydantic 等模型类生成 Schema）定义，让模型从用户问句中抽取关键信息并填充结构化参数。

{
  "type": "object",
  "required": ["to", "subject", "body"],
  "properties": {
    "to": { "type": "string", "format": "email", "description": "收件人地址" },
    "subject": { "type": "string", "maxLength": 100, "description": "邮件主题" },
    "body": { "type": "string", "description": "邮件正文" },
    "priority": { "type": "string", "enum": ["low", "normal", "high"], "default": "normal" }
  }
}

设计要点

  • 明确类型、必填字段、枚举值、默认值、取值范围和格式。
  • 每个字段写清楚 description，模型据此抽取参数。
  • 参数尽量少而精，能由系统推导的（如当前用户 ID）不要让模型填。
  • 缺少必填参数时引导模型向用户追问，而不是猜测。

为什么必须约束

  • 模型生成的参数不稳定，可能字段缺失、类型错误或格式不对。
  • 执行前做 Schema 校验能拦截非法参数，提高调用成功率，并把错误信息回传给模型修正。
  • 枚举和范围约束可以限制危险输入，降低 Prompt Injection 诱导出恶意参数的风险。

什么是 Skill 的自进化机制？

Skill 自进化是让系统在运行中根据反馈持续改进 Skill，形成“调用 → 反馈 → 优化 → 再调用”的闭环，提升路由准确率、参数正确率、执行成功率和结果质量。

常见实现方式

  • description / 指令优化：收集误调用、漏调用和失败案例，迭代 Skill 的描述和步骤说明。
  • Few-shot 沉淀：把历史成功案例整理成示例写入 Skill 或 references，提升后续表现。
  • 经验召回：将历史任务向量化，执行时检索相似成功案例供模型参考。
  • 生成新 Skill：识别高频出现的多步操作组合，由 Agent 自动总结成新的复合 Skill（部分 Agent 支持让模型自己创建或更新 Skill 文件）。

注意点：自动修改的内容要经过评估集验证和人工审核后再上线，做好版本管理和回滚，防止效果退化或被恶意输入污染。

Skill 路由与冲突 5高频 1

用户一句话进来，Agent 如何做意图识别并路由到对应 Skill？

Skill 少时，直接把所有 Skill 的元数据交给模型决策即可；Skill 多时，通常采用“召回 + 决策”两阶段架构。

完整链路

用户输入 → 预处理（结合历史补全指代）
        → 候选召回（embedding 向量检索 + 关键词 / 规则）→ Top-K 候选 Skill
        → LLM 决策（结合 description、参数 Schema、上下文）→ 选定 Skill 或反问澄清
        → 参数抽取与 Schema 校验 → 权限校验 → 执行 → 返回结果

三种匹配手段

  • 规则路由：关键词、正则、优先级硬匹配，适合高确定性或高风险场景，防止模型乱选。
  • 语义召回：对用户问题和 Skill 描述做向量化，按相似度召回候选。
  • 模型决策：把候选 Skill 的元信息交给大模型，由模型判断是否调用、调用哪一个，或判断信息不足需要澄清。

Skill 路由是纯 Prompt、分类模型还是 embedding 向量召回？会考虑用户信息吗？

取决于 Skill 规模：Demo 和 Skill 较少时通常纯 Prompt 路由（Anthropic 的 Agent Skills 就是让模型读 description 自行判断）；Skill 数量达到几十上百时，生产系统一般引入 embedding 召回或分类模型先缩小范围，再由 LLM 精排。

为什么不能一直用纯 Prompt

  • Skill 越多，元数据越长，Token 成本和延迟上升。
  • 候选越多越容易混淆，误调用率升高。

召回 + 排序方案：对 Skill 描述预先向量化，用户问题向量化后做 ANN 检索召回 Top-K，再交给 LLM 选择。本质是把搜索系统的 Recall + Rank 思想用于 Agent 路由。也可以训练轻量意图分类模型做第一层分流，延迟更低。

会考虑用户信息

  • 历史上下文：用户常用省略表达，例如上一轮在聊 Redis，这一轮问“为什么会死锁”，不带历史就无法正确路由。召回前应结合最近几轮对话改写 Query。
  • 用户身份与权限：先按角色过滤可见 Skill，再做路由。
  • 用户偏好：冲突时可参考用户近期常用的 Skill。

Agent 怎么知道“下一步该调用哪个 Skill”？

Agent 根据当前目标、已执行步骤、历史 Observation 和上下文状态，动态推理下一步动作。常见实现：

  • ReAct：Thought → Action → Observation 循环，每步根据上一步结果决定下一个动作，灵活但步数不可控。
  • Plan-and-Execute：先生成完整计划，再逐步执行，必要时根据结果重新规划，适合步骤较多、可预先拆解的任务。
  • Skill 自身指引：Skill 的 SKILL.md 中写明步骤顺序和条件分支，模型按手册推进。
  • 状态机 / 工作流约束：用状态机或 DAG 定义合法的状态转移，模型只在允许的动作中选择。

实际系统常把 LLM Planner 与状态机结合：既保留灵活性，又通过最大步数、合法转移和终止条件避免无限乱调用。

用户需求模糊、同时命中多个 Skill 时怎么处理冲突？

先判断多个 Skill 之间是什么关系，再分别处理。

按关系分类

  • 互斥关系：只应执行一个，如 send_email 和 send_sms 同时被触发，选置信度最高的或按预设规则优先。
  • 可并行关系：如“查天气 + 查航班”，可以都执行，并发调用后合并结果。
  • 链式关系：如“先搜索再总结”，按依赖顺序进入工作流编排。

互斥时的消歧手段

  • LLM 二次决策：把用户输入和候选 Skill 一起交给模型，要求输出最匹配的一个，或输出“需要澄清”。
  • 置信度 + 优先级：用 embedding 相似度或分类模型给出匹配分，结合预设 priority 排序，低于阈值不调用。
  • 互斥规则：配置冲突组和默认优先项。
  • 用户历史偏好：参考用户近期常用的 Skill。
  • 主动澄清：置信度相近或都较低时，直接问用户“是要发邮件还是发短信”，高风险操作尤其应该先确认。

生产中可为每个 Skill 配置 priority、dependency、execution policy 等元信息，避免模型随意组合。

两个 Skill 内容不同但 description 很相似，导致总是加载错，怎么解决？高频

核心思路是增加判别信息，从模糊的语义匹配升级为结构化的精确路由。

  • 改写 description，拉开区分度：突出两者在对象、场景、输入类型上的差异，例如“处理国内订单退款”和“处理跨境订单退款”，并在各自描述中写明“不适用于……”。
  • 结构化定义：除 description 外，补充适用场景、禁用场景、输入参数、前置条件、调用示例等字段，供路由时参考。
  • 加入负样本：明确列出什么情况下不要调用该 Skill，用反例告诉模型边界。
  • 两阶段选择：先向量检索或规则召回 Top-K，再让模型结合参数约束和示例做 Rerank。
  • 执行前校验：用参数 Schema 和业务规则做最后一道拦截，参数对不上就阻断并提示重选。
  • 评估回归：用易混淆的样例构建测试集，每次修改描述都回归测试命中率。
  • 考虑合并：如果两个 Skill 长期难以区分，往往说明它们本应是一个 Skill，合并后由内部参数或分支处理不同逻辑，从根源上消除歧义。

Skill 编排与上下文 6高频 0

有没有编排多个基础 Skill 完成复杂业务流程？

可以这样设计：把复杂业务拆成多个原子 Skill，由编排层按流程调度，对外暴露一个完整的业务能力。

例子：“生成周报”拆成 数据查询 Skill → 数据分析 Skill → 总结生成 Skill → 邮件发送 Skill。

编排模式

  • 串行：A 的输出作为 B 的输入。
  • 条件分支：根据上一步结果决定走 C 还是 D。
  • 并行：无依赖的 Skill 并发执行后合并。
  • 循环 / 重试：结果不达标时回到某一步重做，设置最大次数。

实现方式

  • 固定流程：用 DAG、状态机或工作流引擎定义，可控、可观测、便于回放，适合稳定的业务流程。
  • 动态流程：由 LLM Planner 或 ReAct 根据每步 Observation 决定下一个 Skill，灵活但需限制步数。
  • 主 Skill 编排：用一个主 Skill 写明步骤和各子 Skill 的调用时机。

关键点：各 Skill 之间约定清晰的输入输出结构；中间结果持久化，失败时可从断点恢复；写操作保证幂等。本质上是把 Agent 从“单次工具调用”升级为“任务执行系统”。

做过并行 Skill 调用吗？多 Skill 并发执行后结果怎么聚合？

很多任务天然可并行，例如“规划出差”可以同时查天气、航班、酒店、日程。

实现

  • 先做依赖判断，只有互不依赖的 Skill 才能并行。
  • Java 中可用 CompletableFuture（配合独立线程池）或 Reactor，Python 中用 asyncio.gather；也可以利用模型一次返回多个 tool call 的能力，由宿主并发执行。
CompletableFuture<String> weather = CompletableFuture
        .supplyAsync(() -> weatherSkill.run(req), skillPool)
        .completeOnTimeout("天气暂不可用", 3, TimeUnit.SECONDS);
CompletableFuture<String> flight = CompletableFuture
        .supplyAsync(() -> flightSkill.run(req), skillPool)
        .exceptionally(e -> "航班查询失败");
CompletableFuture.allOf(weather, flight).join();

聚合方式

  • 结构化聚合：把各 Skill 结果按 key 合并成统一 JSON，适合下游程序继续处理。
  • Observation 聚合：把所有结果作为工具结果一起交给 LLM 做综合总结，是最常见的做法。

难点在治理而不是并发

  • 每个 Skill 单独设置超时，避免一个慢调用拖住整体。
  • 失败隔离：部分失败时返回已有结果并标注缺失项，由模型做降级说明。
  • 独立线程池隔离，防止某个 Skill 耗尽资源。
  • 带副作用的 Skill 并行前要确认无冲突，并保证幂等。

Skill 执行过程中上下文怎么维护？多轮对话里怎么保留执行状态、拿到历史信息？

本质是 Agent 的 Memory 和状态管理问题：Skill 一般不自己维护状态，而是由 Agent 的会话层统一管理，再把需要的部分组装进上下文。

会话存储

  • 每个会话分配唯一 sessionId，在 Redis（热数据）和数据库（持久化）中保存历史消息、已调用 Skill、入参出参、中间结果、变量。

执行状态

  • 把 Skill 的执行步骤、当前节点、已收集参数都记录在会话状态中，下一轮请求时一起交给模型，模型知道上一步做了什么、不必重复询问参数。
  • 复杂 Skill 用状态机：待补参 → 执行中 → 成功 / 失败 / 终止，多轮对话按状态流转，自动引导用户补全缺失参数。
  • 长任务的进度可以写入文件或任务记录，便于中断后恢复。

组装上下文：当前问题 + 最近几轮对话 + 历史摘要 + 相关的工具结果 / Observation + 用户画像。长对话不全量传递，而是采用“最近对话 + 摘要记忆 + 向量召回”的混合方案。

上下文是全量传递还是摘要传递？

通常采用“短对话全量、长对话摘要”的混合模式。

  • 为什么不一直全量：Token 成本和延迟随对话线性增长，接近窗口上限时会被截断，而且上下文过长会稀释注意力、降低回答质量。
  • 常见做法：
    • 保留最近 N 轮完整对话，保证短期指代和细节准确；
    • 更早的历史压缩成摘要（Summary Memory），在 Token 达到阈值时触发；
    • 用户偏好、长期项目信息等向量化存储，按语义按需召回；
    • 大体积的工具结果只保留关键字段或摘要，必要时保存到外部存储并保留引用。
  • 本质是在上下文完整性、Token 成本和推理效果之间取平衡。

上下文太长时如何控制 Token 消耗？

从“少放、压缩、复用”三个方向入手：

  • 滑动窗口：只保留最近几轮对话。
  • 摘要记忆：把早期历史压缩成摘要，替代完整的历史消息。
  • 向量记忆：历史信息向量化，只召回与当前问题相关的部分。
  • 控制 RAG 召回量：限制 Top-K 和 chunk 大小，用 Rerank 去掉低相关片段。
  • 工具结果裁剪：工具返回只保留必要字段，大结果分页或落盘后引用。
  • 按需加载：工具和 Skill 采用渐进式披露，不把所有定义常驻上下文；工具多时先路由再注入。
  • 子 Agent 隔离：把搜索、探索类任务交给子 Agent，在独立上下文中执行，只返回结论。
  • Prompt 模板化：精简系统提示，结构化表达；保持前缀稳定以命中厂商的 Prompt Caching，降低重复部分的费用和延迟。

多 Agent 系统中如何跨 Agent 共享和管理 Skill？

核心是把 Skill 从各 Agent 本地硬编码中抽离出来，集中注册、统一治理、按需分发。

  • 统一注册中心：所有 Skill 在 Skill 中心注册，管理元信息（名称、描述、版本、负责人、依赖）。文件型 Skill 可以放在共享仓库中，通过 Plugin 或包管理分发到各个 Agent。
  • 远程调用：执行型 Skill 部署为服务（可以以 MCP Server 形式暴露），各 Agent 远程调用，一次开发多处复用。
  • 权限隔离：按 Agent 维度配置可调用 Skill 白名单，按用户维度再做一层过滤，防止越权。
  • 版本管理：Skill 带版本号，支持灰度发布和回滚，避免一次修改影响所有 Agent。
  • 能力互补：Agent 之间可以相互委托任务（如通过 A2A 协议），A Agent 借助 B Agent 擅长的 Skill 完成复杂任务。
  • 统一网关：调用经过统一网关做鉴权、限流、熔断和审计。
  • 可观测性：统计每个 Skill 在各 Agent 中的调用量、成功率和耗时，用于治理和下线。

Skill 生产化：安全、性能与评估 6高频 0

做过 Skill 的权限管控吗？如何限制不同用户只能调用指定 Skill？

可以用 RBAC（必要时叠加租户和资源范围）做两道控制：暴露前过滤，执行前校验。权限边界必须由后端保证，不能依赖模型。

  1. 身份解析：在 Agent 入口从 Token 或 Session 中解析 user_id、角色、租户。
  2. Skill 权限声明：每个 Skill 定义 required_role、permission（如 email:send）或白名单字段。
  3. 暴露前过滤：根据用户权限过滤可用 Skill 列表，只把有权限的 Skill 交给模型选择，模型根本看不到无权调用的 Skill，也减少了 Token 和误选。
  4. 执行前校验：在 Skill 执行器入口再次校验调用者身份和权限，防止通过 Prompt 注入或绕过 Agent 直接调用。
  5. 数据层控制：Skill 内部访问数据时也按用户权限过滤（如行级权限），而不是只控制入口。
def get_visible_skills(user) -> list[Skill]:
    return [s for s in all_skills
            if s.required_role in user.roles or user.id in s.allow_list]

例如普通用户只能用查询类 Skill，管理员才能用删除、审批、支付类 Skill；高风险 Skill 再叠加人工确认。

用户通过 Prompt Injection 诱导模型调用危险 Skill，怎么防？

基本原则：假设模型一定会被诱导成功，靠模型之外的确定性机制兜底。通常分多层防护：

  • 输入检测：识别“忽略之前的指令”“执行系统命令”等恶意模式，可用规则加专门的检测模型（Prompt Guard）。
  • 指令与数据隔离：System Prompt 中明确安全边界；工具返回、网页、文档等外部内容只作为数据，用标记隔离，不当作指令执行（防间接注入）。
  • 最小暴露：按用户权限只暴露必要 Skill，危险 Skill 默认不对普通用户可见。
  • 服务端权限校验：执行前再次校验身份和权限，模型说什么都不能越权。
  • 参数校验：Schema 校验、白名单、枚举约束，拦截路径穿越、SQL 注入、危险命令。
  • 人工确认：删除、支付、发送外部消息等高风险操作必须 Human-in-the-loop。
  • 沙箱与最小权限：脚本在沙箱中执行，限制网络和文件访问，凭证不暴露给模型。
  • 审计与告警：记录完整调用链，检测异常调用模式并及时告警。

Skill 调用失败后，怎么做重试、熔断和降级？

结合 Retry、Circuit Breaker、Fallback 三套机制，外加超时、隔离和限流。Java 中可用 Resilience4j 实现。

  • 重试：只对临时性错误（网络抖动、超时、429 限流）做有限次数重试，指数退避加随机抖动；参数错误、权限错误直接失败不重试；写操作必须幂等才能重试。
  • 熔断：失败率或慢调用比例超过阈值时打开熔断，直接走降级，避免持续失败拖垮整个 Agent；半开状态放少量请求探测恢复。
  • 降级：
    • 搜索失败 → 使用缓存结果；
    • 天气接口失败 → 返回基础信息或告知暂不可用；
    • 主模型超时 → 切换备用或较小的模型；
    • 无降级方案 → 明确告知用户，不编造结果。
  • 超时：单个 Skill 有超时，整个任务有总超时。
  • 隔离：不同 Skill 使用独立线程池或信号量（舱壁模式），防止一个慢 Skill 耗尽资源。
  • 限流：保护下游服务，也保护 Token 预算。
  • 错误回传：把失败原因作为 Observation 回传给模型，让它选择替代方案。

如何优化 Skill 首次响应时间？做过 Skill 缓存吗？瓶颈一般在哪？

常见瓶颈（按影响大小排序）

  • LLM 推理：路由决策、参数生成、最终总结都要调模型，尤其是首 token 延迟和多轮调用累加，通常是最大瓶颈。
  • 外部 API 和 RAG 检索：第三方接口慢、向量检索和 Rerank 耗时。
  • 冷启动：首次加载 Skill 文件、初始化运行环境、启动 MCP Server 或沙箱、建立连接。

优化手段

  • 结果缓存：对天气、汇率、搜索结果等短期变化不大的数据，用 Redis 按 Skill + 规范化参数做缓存，设置合适的 TTL。
  • LLM 缓存：利用厂商的 Prompt Caching（保持 System Prompt、工具定义等前缀稳定）降低首 token 延迟；对完全相同的请求做精确缓存，高频相似问题可做语义缓存。
  • 减少模型调用轮数：简单意图用规则或小模型路由，确定性步骤用脚本执行，不让大模型逐步决策。
  • 预热：提前加载 Skill 元数据、预启动 Server 和沙箱、预热连接池。
  • 连接复用：HTTP 连接池、gRPC 长连接，避免频繁建连。
  • 并行化：独立 Skill 和工具并发执行。
  • 流式输出：尽早向用户返回首个 token 和中间进度，降低感知延迟。
  • 模型分级：路由、抽取等简单环节用更快的小模型。

如何评估一个 Skill 的效果？有哪些监控指标？

从离线评估和线上监控两方面做，指标分四类：

类别 指标
路由 命中率（召回率）、误调用率、漏调用率
执行 成功率、参数错误率、超时率、平均和 P99 耗时、平均步数
结果 答案正确率、输出格式合规率、用户满意度（点赞 / 点踩）、人工评分或 LLM-as-Judge 评分
业务与成本 任务完成率、转化率、人工接管率、单次 Token 消耗和成本

离线评估：为每个 Skill 构建测试集，包括正例、易混淆反例和边界用例；每次修改 Skill 描述或指令都跑回归，对比加载 Skill 前后的效果。

线上监控：记录完整调用链，包括 Thought、Action、Observation、耗时、Token Cost，使用 OpenTelemetry 打通 Trace，接入 Prometheus + Grafana 做指标看板、ELK 做日志检索，或者使用 Langfuse、LangSmith 等 LLM 可观测平台。对失败和差评案例做定期复盘，反哺 Skill 优化。

生产级 Agent/Skill 系统和 Demo 最大的区别是什么？

Demo 追求“能跑通”，生产系统追求“稳定、可控、可治理、可度量”。Demo 通常只有“模型 + 几个 Tool”，生产系统更接近一个 AI 微服务平台。

维度 Demo 生产级
权限 无或写死 身份认证、RBAC、Skill 白名单、执行前校验
安全 信任模型输出 Prompt 注入防护、参数校验、沙箱、人工确认
稳定性 失败就报错 超时、重试、熔断、降级、幂等
上下文 全量拼接 Memory 分层、摘要、按需加载
编排 单次调用 工作流 / 状态机、最大步数、断点恢复
工具治理 随手定义 统一注册、版本管理、description 规范、评估回归
可观测性 打日志 全链路 Trace、指标看板、告警
成本 不关注 Token 计量、缓存、模型分级、预算控制
质量 主观感受 离线测试集、线上指标、持续迭代

结论：生产级 Agent 的竞争力不只在模型本身，更在于围绕模型构建的整套工程能力，也就是 Harness 工程。

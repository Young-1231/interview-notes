IoC 与依赖注入 5高频 4

什么是 IoC 和 AOP？高频

IoC 管"对象怎么来"，AOP 管"公共逻辑怎么加"，两者是 Spring 的两大核心。

  • IoC（Inversion of Control，控制反转）：对象的创建权和依赖关系的管理权从业务代码转交给 Spring 容器。业务类不再自己 new 依赖，而是声明需要什么，由容器创建并注入。DI（依赖注入）是 IoC 的具体实现方式。
  • AOP（Aspect Oriented Programming，面向切面编程）：把日志、事务、权限校验、限流、幂等、监控埋点等横切逻辑从业务代码中抽出来，集中写在切面里，在不修改源码的前提下对方法做增强。
  • AOP 的实现：Spring AOP 基于运行时动态代理。容器为目标 Bean 生成代理对象，调用方拿到的是代理，代理在目标方法前后织入增强逻辑。代理方式有 JDK 动态代理（基于接口）和 CGLIB（基于继承生成子类）两种。

IoC 有什么好处？相比直接 new 对象高频交通银行淘天

核心好处是解耦：对象的使用方只依赖抽象，不关心具体实现由谁创建、怎么创建。

  • 解耦、易替换：OrderService 依赖 PayProcessor 接口，具体是支付宝还是微信实现由容器注入；更换实现只改配置或 Bean 定义，不改业务代码。
  • 创建与使用分离：复杂对象的构造、参数、依赖关系集中在配置里，业务代码更干净。
  • 生命周期统一管理：初始化、销毁回调、作用域都交给容器，不必手动管理资源。
  • 对象复用：Bean 默认单例，避免重复创建无状态对象。
  • 便于测试：依赖通过构造器传入，单元测试时可以直接传 Mock 对象。
  • 扩展能力：容器统一创建对象，才有了 BeanPostProcessor、AOP 代理、事务等在创建过程中"插一脚"的机会。

DI（Dependency Injection，依赖注入）是 IoC 的实现方式：容器创建 Bean 时，把它依赖的对象自动注入进去。

方式 写法 特点
构造器注入 依赖作为构造参数 依赖不可变（可 final）、创建即完整、易测试；Spring 官方推荐。单构造器时 Spring 4.3+ 可省略 @Autowired
Setter 注入 @Autowired 标在 setter 上 适合可选依赖、可重新注入
字段注入 @Autowired/@Resource 标在字段上 写法最简单，但隐藏依赖、不能 final、脱离容器难以测试

"接口注入"是早期 IoC 理论中的一种方式，Spring 并不支持。实际开发推荐构造器注入，配合 Lombok 的 @RequiredArgsConstructor 很简洁。

注入 Bean 的方式有哪些？为什么不推荐字段上直接用 @Autowired？银行阿里

注入方式就是构造器、Setter、字段三种。IDEA 提示 "Field injection is not recommended"，针对的是字段注入这种方式，而不是 @Autowired 注解本身：

  • 字段不能声明为 final，对象可能处于依赖未注入的状态，脱离容器 new 出来时直接 NPE。
  • 依赖关系藏在字段里，类依赖过多也不容易察觉（构造器参数一长就会暴露设计问题）。
  • 单元测试必须靠反射或启动容器才能注入 Mock。
  • 字段注入会掩盖循环依赖问题，构造器注入则会在启动时直接暴露。
  • @Autowired 是 Spring 专有注解，与容器强绑定；@Resource 是 Jakarta 标准注解。

推荐做法：必选依赖用构造器注入，可选依赖用 Setter 注入。

@Autowired 和 @Resource 的区别高频

两者都能完成依赖注入，主要区别在来源和匹配规则。

对比 @Autowired @Resource
来源 Spring 注解 JSR-250 标准（Boot 3 / Spring 6 为 jakarta.annotation.Resource，之前是 javax.annotation.Resource）
匹配规则 先按类型；找到多个时再看 @Primary、@Priority，最后按字段名/参数名匹配 先按名称（name 属性，未指定则用字段名）；按名称找不到再按类型
指定 Bean 配合 @Qualifier("xxx") 直接 @Resource(name = "xxx")
必须性 required = true 默认，找不到抛异常；可设为 false 找不到抛异常
可用位置 构造器、方法、字段、参数 字段、Setter 方法，不支持构造器

同一接口有多个实现时：@Autowired 会因为找到多个候选而报 NoUniqueBeanDefinitionException（除非字段名恰好等于某个 Bean 名或有 @Primary），一般用 @Qualifier 解决。

Bean 的定义、作用域与生命周期 4高频 2

什么是 Bean？声明 Bean 的方式有哪些？怎么控制创建顺序？农业银行交通银行

Bean 就是由 Spring IoC 容器创建、装配和管理生命周期的对象。容器先把配置解析成 BeanDefinition，再按定义通过反射实例化。

声明方式

  • XML：<bean id="..." class="..."/>（老项目）。
  • 注解扫描：@Component 及其派生 @Controller、@Service、@Repository，配合 @ComponentScan。
  • Java 配置类：@Configuration + @Bean 方法，适合注册第三方类。
  • @Import 导入配置类、ImportSelector、ImportBeanDefinitionRegistrar（Spring Boot 自动配置和 @EnableXxx 就靠这个）。
  • 编程式注册：BeanDefinitionRegistryPostProcessor、FactoryBean。

控制创建顺序

  • 依赖关系天然决定顺序：A 注入了 B，B 一定先创建。
  • 没有直接依赖但需要先初始化时，用 @DependsOn("b") 显式声明。
  • @Lazy 可推迟到第一次使用时才创建。
  • @Order / Ordered 不控制 Bean 的创建顺序，它只影响注入 List<X> 时的排序、切面和过滤器的执行顺序。

Spring Bean 的作用域有哪些？高频交通银行阿里

通过 @Scope 指定，默认 singleton。

作用域 含义 适用环境
singleton 每个容器只有一个实例（默认） 所有
prototype 每次 getBean 或注入都新建一个实例 所有
request 每个 HTTP 请求一个实例 Web
session 每个 HTTP Session 一个实例 Web
application 每个 ServletContext 一个实例 Web

注意点：

  • 无状态的 Service、DAO、工具类用 singleton；需要隔离状态的对象才考虑 prototype。
  • prototype Bean 容器只负责创建，不管理销毁，@PreDestroy 不会被调用。
  • 把 prototype/request Bean 注入 singleton 时，只会注入一次，后续不会变。需要每次拿新实例可以用 ObjectProvider<T>、@Lookup 方法，或 @Scope(proxyMode = ScopedProxyMode.TARGET_CLASS) 作用域代理。

Bean 的生命周期高频

主线是：实例化 → 属性填充 → 初始化 → 使用 → 销毁，扩展点穿插在初始化前后。

  1. 实例化：按 BeanDefinition 反射调用构造器或工厂方法创建对象，属性为空。循环依赖的提前暴露就在这之后。
  2. 属性填充（populateBean）：注入 @Autowired、@Value、@Resource 等依赖。
  3. Aware 回调：BeanNameAware、BeanFactoryAware 等；ApplicationContextAware 由 ApplicationContextAwareProcessor 在下一步回调。
  4. BeanPostProcessor 前置：postProcessBeforeInitialization()，@PostConstruct 在这里执行。
  5. 初始化：InitializingBean.afterPropertiesSet() → 自定义 init-method。
  6. BeanPostProcessor 后置：postProcessAfterInitialization()，AOP 代理通常在这里生成，容器里最终放的可能是代理对象。
  7. 使用：单例放入一级缓存 singletonObjects。
  8. 销毁：容器关闭时 @PreDestroy → DisposableBean.destroy() → destroy-method。prototype Bean 不走这一步。

Spring 的单例 Bean 是线程安全的吗？滴滴银行农业银行

不是。Spring 只保证单例 Bean 在容器中只有一个实例，不做任何并发控制，是否线程安全取决于 Bean 自身有没有可变的共享状态。

  • 无状态 Bean 是安全的：常见的 Controller、Service、DAO 只持有其他 Bean 的引用，方法内用局部变量，不存在共享可变状态，所以实际开发中大多没有问题。
  • 有状态 Bean 不安全：如果单例里有可修改的成员变量（计数器、缓存的 Map、当前用户等），多线程并发读写就会出问题。

解决办法：

  • 首选把 Bean 设计成无状态，状态放到方法局部变量或参数中。
  • 必须保存线程相关状态时用 ThreadLocal（用完 remove()，防止线程池复用导致串数据和内存泄漏）。
  • 共享状态使用并发容器（ConcurrentHashMap）、原子类或加锁。
  • 改用 prototype / request 作用域，让每个线程或请求拿到独立实例。

IoC 容器原理 5高频 0

IoC 容器的初始化过程（refresh 流程）招商银行交通银行PDD

一句话：先把配置解析成 BeanDefinition 注册进 BeanFactory，经过后置处理器加工，最后实例化所有非懒加载的单例 Bean。入口是 AbstractApplicationContext.refresh()，主要步骤：

  1. prepareRefresh()：初始化并校验 Environment。
  2. obtainFreshBeanFactory()：获取 DefaultListableBeanFactory，XML 方式在这里加载 BeanDefinition。
  3. prepareBeanFactory() / postProcessBeanFactory()：设置类加载器、内置后置处理器，留给子类扩展。
  4. invokeBeanFactoryPostProcessors()：ConfigurationClassPostProcessor 解析 @Configuration、@ComponentScan、@Import、@Bean，注解方式的大部分 BeanDefinition 在此注册（Spring Boot 自动配置也在此生效）。
  5. registerBeanPostProcessors()：注册所有 BeanPostProcessor。
  6. initMessageSource()、initApplicationEventMulticaster()、registerListeners()：国际化、事件广播器、监听器。
  7. onRefresh()：Spring Boot 在这里创建并启动内嵌 Tomcat。
  8. finishBeanFactoryInitialization()：实例化所有非懒加载单例（含 AOP 代理）。
  9. finishRefresh()：发布 ContextRefreshedEvent。

BeanFactory 和 ApplicationContext 有什么区别？

BeanFactory 是最底层的 IoC 容器接口，ApplicationContext 是它的子接口，在其基础上提供企业级功能。

对比 BeanFactory ApplicationContext
定位 基础容器，只负责 Bean 的创建、获取、依赖注入 完整的应用上下文，实际开发都用它
单例加载时机 懒加载，第一次 getBean 时才创建 启动 refresh 时预先实例化所有非懒加载单例，配置错误能尽早暴露
扩展功能 无 国际化 MessageSource、事件发布、资源加载 ResourceLoader、Environment 环境与 Profile
后置处理器 需手动注册 BeanPostProcessor 自动检测并注册 BeanFactoryPostProcessor / BeanPostProcessor

常见实现：AnnotationConfigApplicationContext、ClassPathXmlApplicationContext，Spring Boot Web 应用用的是 AnnotationConfigServletWebServerApplicationContext。

BeanDefinition 是什么？

BeanDefinition 是 Bean 的"图纸"：Spring 先把 XML、注解、配置类解析成 BeanDefinition，注册到 BeanDefinitionRegistry（即 DefaultListableBeanFactory 内部的 beanDefinitionMap），后续一切 Bean 的创建都按它来。

包含的信息：

  • Bean 的类名 beanClassName、工厂方法（@Bean 方法对应 factoryBean + factoryMethod）。
  • 作用域、是否懒加载 lazyInit、是否 primary、dependsOn。
  • 构造器参数值、属性值。
  • 初始化方法、销毁方法名。

意义：把"定义"和"实例化"分开，因此可以在实例化之前通过 BeanFactoryPostProcessor 修改定义（例如 PropertySourcesPlaceholderConfigurer 替换 ${} 占位符）。

BeanPostProcessor 是什么？和 BeanFactoryPostProcessor 有什么区别？

BeanPostProcessor 是 Bean 的后置处理器，在每个 Bean 初始化前后提供扩展点，可以修改甚至替换 Bean 实例。

public interface BeanPostProcessor {
    default Object postProcessBeforeInitialization(Object bean, String beanName) { return bean; }
    default Object postProcessAfterInitialization(Object bean, String beanName) { return bean; }
}

典型实现：

  • AutowiredAnnotationBeanPostProcessor：处理 @Autowired、@Value 注入（属于其子接口 InstantiationAwareBeanPostProcessor，在属性填充阶段工作）。
  • CommonAnnotationBeanPostProcessor：处理 @Resource、@PostConstruct、@PreDestroy。
  • AnnotationAwareAspectJAutoProxyCreator：在 postProcessAfterInitialization 中为需要增强的 Bean 生成 AOP 代理，@Transactional、@Async 的代理也是这一类机制。
对比 BeanFactoryPostProcessor BeanPostProcessor
作用对象 BeanDefinition（元数据） Bean 实例
执行时机 所有 Bean 实例化之前，执行一次 每个 Bean 初始化前后都执行
典型用途 解析配置类、替换占位符、注册额外的 BeanDefinition 依赖注入、生命周期注解、AOP 代理

FactoryBean 和 BeanFactory 的区别？

名字相似，完全是两回事：BeanFactory 是容器，FactoryBean 是容器里一种能"生产对象"的特殊 Bean。

  • BeanFactory：IoC 容器的顶层接口，负责管理所有 Bean。
  • FactoryBean<T>：一个接口，实现它的 Bean 通过 getObject() 自定义复杂对象的创建逻辑，还有 getObjectType()、isSingleton()。
  • 按名字 getBean("xxx") 时，拿到的是 getObject() 返回的产品对象；要拿 FactoryBean 本身，需要用 getBean("&xxx")。
  • 典型场景：MyBatis 的 MapperFactoryBean 为每个 Mapper 接口生成代理对象，SqlSessionFactoryBean 创建 SqlSessionFactory；OpenFeign 的 FeignClientFactoryBean 生成远程调用代理。适合创建过程复杂、需要整合第三方框架的对象。

循环依赖与三级缓存 4高频 1

什么是循环依赖？Spring 能解决哪些？

循环依赖是指两个或多个 Bean 互相持有对方的引用，形成闭环：A 依赖 B、B 依赖 A，或 A → B → C → A，甚至 A 依赖自己。创建 A 时要先有 B，创建 B 时又要先有 A，不处理就会无限递归。

Spring 用三级缓存"提前暴露半成品对象"来解决，但有条件：

场景 能否解决
单例 + 字段 / Setter 注入 能（前提是允许循环引用，见下文 Spring Boot 2.6 的变化）
单例 + 双方都是构造器注入 不能，启动报 BeanCurrentlyInCreationException
一方构造器、一方 Setter 取决于创建顺序：先创建的那个是 Setter 注入才能成功
prototype 作用域 不能，prototype 不进缓存，直接报错
含 @Async 的 Bean 参与循环 通常失败，因为其代理在初始化后才生成，与提前暴露出去的原始对象不一致

Spring Boot 2.6+ 的变化：从 Spring Boot 2.6 开始，spring.main.allow-circular-references 默认为 false，即默认禁止循环引用，存在循环依赖时启动直接失败，并打印 "The dependencies of some of the beans in the application context form a cycle"。Spring Framework 本身的三级缓存机制仍然存在（Spring 6 也是如此），只是 Boot 默认把它关掉了。

处理方式：

  • 首选重构，消除循环（抽出公共逻辑到第三个 Bean、改用事件解耦）。
  • 在注入点加 @Lazy，注入的是一个延迟代理，真正使用时才去容器取，构造器循环也能用这种方式打破。
  • 实在需要兼容老代码，再配置 spring.main.allow-circular-references=true。

三级缓存是什么？怎么解决循环依赖？高频

三级缓存是 DefaultSingletonBeanRegistry 中的三个 Map：

缓存 字段 存放内容
一级 singletonObjects 完全创建好的单例 Bean（成品），日常 getBean 从这里取
二级 earlySingletonObjects 提前暴露的早期引用（半成品，可能已是代理），保证多次获取拿到同一个对象
三级 singletonFactories ObjectFactory 工厂 lambda：() -> getEarlyBeanReference(beanName, mbd, bean)，需要时才生成早期引用

getSingleton 查找顺序：一级 → 二级 → 三级；从三级拿到工厂后调用 getObject() 生成早期引用，放入二级缓存并删除三级缓存中的工厂。

以 A ↔ B（Setter / 字段注入）为例：

  1. 创建 A：实例化 A（构造器执行完，属性为空），把 A 的 ObjectFactory 放入三级缓存。
  2. 填充 A 的属性，发现需要 B，getBean(B)。
  3. 创建 B：实例化 B，B 的工厂放入三级缓存；填充 B 的属性，发现需要 A。
  4. getBean(A)：一级、二级没有，三级有 A 的工厂，调用它得到 A 的早期引用（如果 A 需要 AOP，这里会提前生成 A 的代理），放入二级缓存，移除三级。
  5. B 拿到 A 的早期引用，完成属性填充和初始化，放入一级缓存。
  6. 回到 A，拿到成品 B 完成注入和初始化。初始化后检查：A 的代理已经提前生成过（记录在 earlyProxyReferences 中），不会再生成第二个，最终把二级缓存里的那个对象放入一级缓存。

关键点：Bean 的创建分成"实例化"和"初始化"两步，正是这个间隙让 Spring 可以把半成品提前暴露出去。

为什么需要三级缓存，两级不行吗？

如果只为了打破循环，两级缓存（成品 + 半成品）就够了。第三级缓存是为了 AOP 代理 和 不打乱代理创建时机。

  • 正常情况下，AOP 代理在 Bean 生命周期最后一步 postProcessAfterInitialization 才创建。
  • 发生循环依赖时，B 需要拿到 A 的"最终形态"。如果 A 最终要被代理，B 拿到的必须是代理对象，否则 B 持有的是原始对象，容器里的却是代理，两者不一致，增强（如事务）在 B 中会失效。
  • 如果只有两级缓存，想保证这一点，就必须在每个 Bean 实例化后立刻创建代理放入二级缓存，这样所有 Bean（哪怕根本没有循环依赖）都提前代理，违背了"初始化完成后再代理"的设计。
  • 三级缓存存的是工厂，只有真的发生循环依赖、有人来取早期引用时，才调用 getEarlyBeanReference 提前生成代理；没有循环依赖的 Bean 仍按正常时机代理。
  • 二级缓存则保证工厂只被调用一次，多个 Bean 同时依赖 A 时拿到的是同一个早期引用（同一个代理），而不是每次都新建。

总结：一级存成品，二级存半成品保证唯一，三级存工厂实现"按需、延迟"地生成早期代理。

为什么构造器注入的循环依赖无法解决？

三级缓存的前提是"先实例化、再提前暴露"。构造器注入时依赖是构造参数，A 必须先拿到 B 才能执行构造器，而 B 的构造器又需要 A，两者谁都实例化不出来，连半成品对象都没有，自然没东西可以放进三级缓存。

Spring 在创建前把 Bean 名放入"正在创建"集合 singletonsCurrentlyInCreation，再次进入时发现已在集合中，就抛出 BeanCurrentlyInCreationException。

解决：在构造参数上加 @Lazy，注入一个延迟解析的代理对象，构造器能正常执行，第一次调用方法时才去容器里拿真正的 Bean；或者把其中一方改为 Setter 注入；根本上还是建议重构消除循环。

AOP 与动态代理 4高频 2

AOP 把横切逻辑从业务代码中抽离成切面，通过代理在指定方法前后织入。

  • 通知 Advice：在切点上执行的增强逻辑。
  • 目标对象 Target、代理对象 Proxy、织入 Weaving（把切面应用到目标、生成代理的过程）。

@AfterThrowing 抛出异常后，可获取异常

@Around 包裹整个调用，通过 ProceedingJoinPoint.proceed() 决定是否、何时执行目标方法，可修改参数和返回值，功能最强

同一切面内（Spring 5.2.7+）的顺序：@Around 前半段 → @Before → 目标方法 → @AfterReturning / @AfterThrowing → @After → @Around 后半段。

常见场景：日志与审计、权限校验、声明式事务 @Transactional、接口限流与幂等、性能监控耗时统计、缓存 @Cacheable、异步 @Async、统一异常转换、分布式锁注解。

@Aspect
@Component
public class LogAspect {
    @Around("@annotation(com.example.annotation.Log)")
    public Object around(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            return pjp.proceed();
        } finally {
            log.info("{} 耗时 {} ms", pjp.getSignature(), System.currentTimeMillis() - start);
        }
    }
}

多个切面的执行顺序怎么控制？

用 @Order 注解或实现 Ordered 接口，值越小优先级越高。

  • 优先级高的切面在外层：进入方法时先执行，退出时最后执行，像洋葱一样层层包裹。例如 @Order(1) 的日志切面和 @Order(2) 的权限切面：日志前置 → 权限前置 → 目标方法 → 权限后置 → 日志后置。
  • 不指定顺序时，两个切面都是最低优先级，执行顺序不确定，不能依赖类名或注册顺序。
  • @Order 要加在 @Aspect 切面类上，加在通知方法上无效。同一切面内多个同类型通知的顺序也不保证，需要严格顺序就拆成多个切面。
  • 实际例子：Spring 的事务切面默认是最低优先级，自定义的分布式锁切面如果要包在事务外面（先加锁、事务提交后再释放锁），就要给锁切面设置更小的 order。

AOP 的实现原理？JDK 动态代理和 CGLIB 的区别？高频

Spring AOP 基于运行时动态代理：在 Bean 初始化完成后，由 AbstractAutoProxyCreator（BeanPostProcessor）判断该 Bean 是否匹配某个切点，匹配就用 ProxyFactory 生成代理替换原 Bean 放入容器。调用代理方法时，会把匹配的通知组成拦截器链（MethodInterceptor）依次执行，最后反射调用目标方法。

对比 JDK 动态代理 CGLIB
原理 运行时生成实现相同接口的代理类，调用转发到 InvocationHandler.invoke() 基于 ASM 生成目标类的子类，重写方法，调用转发到 MethodInterceptor.intercept()
要求 目标类必须实现接口，只能代理接口中的方法 不需要接口；不能代理 final 类和 final 方法
依赖 JDK 自带 Spring 3.2 起已内置到 spring-core
注入时的类型 只能按接口类型注入，按实现类注入会报错 可以按实现类注入

Spring 怎么选

  • Spring Framework 默认（proxyTargetClass = false）：目标实现了接口用 JDK 动态代理，否则用 CGLIB。
  • Spring Boot 2.x 起默认使用 CGLIB：spring.aop.proxy-target-class 默认为 true，即使目标实现了接口也用 CGLIB，避免按实现类注入时类型不匹配；配置为 false 才会对有接口的类用 JDK 代理。Spring Boot 3.x 保持这个默认。

两种方式都拦截不到 private、static 方法，也拦截不到类内部的 this.xxx() 自调用，这是事务失效等问题的根源。性能上，JDK 8 之后两者差距已经很小，不是选择的主要依据。

Spring 事务的实现方式和原理高频

Spring 事务分编程式和声明式两种，底层都由 PlatformTransactionManager 统一管理，声明式事务通过 AOP 代理实现。

编程式事务：用 TransactionTemplate（推荐）或 PlatformTransactionManager 手动控制，粒度细到代码块，但侵入业务。

transactionTemplate.executeWithoutResult(status -> {
    orderMapper.insert(order);
    stockMapper.deduct(skuId, 1);   // 抛出运行时异常或调用 status.setRollbackOnly() 即回滚
});

声明式事务：加 @Transactional，业务无感知。Spring Boot 通过 TransactionAutoConfiguration 自动开启，无需 @EnableTransactionManagement。

原理

  1. 启动时 BeanFactoryTransactionAttributeSourceAdvisor 匹配带 @Transactional 的 Bean，生成代理。
  2. 调用时进入 TransactionInterceptor.invokeWithinTransaction()，解析传播行为、隔离级别、超时、只读、回滚规则。
  3. PlatformTransactionManager.getTransaction() 按传播行为新建、加入或挂起事务。新建时拿连接、setAutoCommit(false)，并绑定到 TransactionSynchronizationManager 的 ThreadLocal。
  4. 执行目标方法，MyBatis、JdbcTemplate 从当前线程取同一个连接，所以处于同一事务。
  5. 正常返回 commit，异常按回滚规则 rollback；最后释放连接，恢复挂起的外层事务。

事务管理器：JDBC / MyBatis 用 DataSourceTransactionManager（较新的 Spring Boot 默认注册子类 JdbcTransactionManager），JPA 用 JpaTransactionManager。

Spring 事务的隔离级别有哪些？高频

通过 @Transactional(isolation = Isolation.XXX) 设置，本质是在拿到连接后调用 Connection.setTransactionIsolation()，最终由数据库实现，所以要和 MySQL 的隔离级别一起理解。

级别 脏读 不可重复读 幻读
DEFAULT（默认） 使用数据库自己的默认级别
READ_UNCOMMITTED 读未提交 可能 可能 可能
READ_COMMITTED 读已提交 避免 可能 可能
REPEATABLE_READ 可重复读 避免 避免 标准中可能
SERIALIZABLE 串行化 避免 避免 避免，性能最差
  • MySQL InnoDB 默认是 REPEATABLE_READ，并通过 MVCC（快照读）和 Next-Key Lock（当前读）在很大程度上避免了幻读，但快照读与当前读混用时仍可能出现幻读；Oracle、PostgreSQL、SQL Server 默认是 READ_COMMITTED。
  • 非 DEFAULT 的隔离级别只在新开启事务时生效，加入已有事务时沿用外层事务的级别。

Spring 事务的传播行为有哪些？高频

传播行为定义了"一个事务方法被另一个方法调用时，事务该怎么处理"，通过 propagation 设置，共 7 种：

传播行为 当前有事务 当前无事务
REQUIRED（默认） 加入当前事务 新建事务
REQUIRES_NEW 挂起当前事务，新建一个独立事务 新建事务
NESTED 在当前事务中创建嵌套事务（保存点） 新建事务（同 REQUIRED）
SUPPORTS 加入当前事务 以非事务方式执行
NOT_SUPPORTED 挂起当前事务，以非事务方式执行 以非事务方式执行
MANDATORY 加入当前事务 抛异常 IllegalTransactionStateException
NEVER 抛异常 以非事务方式执行

最容易混的三个

  • REQUIRED：内外是同一个事务，任何一处回滚都整体回滚。内层抛异常被外层 catch 住时，事务已被标记为 rollback-only，外层提交会抛 UnexpectedRollbackException。
  • REQUIRES_NEW：内外是两个独立事务、两个连接。内层提交后不受外层回滚影响；内层回滚，外层只要捕获异常就能正常提交。适合记录操作日志、审计这种"无论如何都要落库"的场景。注意它会多占一个连接，大量使用可能耗尽连接池。
  • NESTED：同一个事务、同一个连接，进入内层时打一个 savepoint。内层回滚只回到保存点，外层可继续提交；外层回滚则内层一起回滚。依赖 JDBC 保存点，DataSourceTransactionManager 支持，JpaTransactionManager 默认不支持。

@Transactional 在什么情况下会失效？高频

根本原因只有两类：调用没有经过代理对象，或者异常没有被事务拦截器感知 / 不在回滚规则内。

代理相关

  1. 同类自调用：this.b() 调的是原始对象，绕过代理，最常见。
  2. 访问权限：private 一定不生效。Spring 6.0 之前只有 public 生效；Spring 6.0+（Boot 3.x）在 CGLIB 类代理下 protected 和包可见方法也能生效；JDK 接口代理只对接口的 public 方法生效。
  3. final / static 方法：CGLIB 无法重写增强。
  4. 类不归 Spring 管理：自己 new 的对象没有代理。
  5. 多线程：连接绑定在当前线程 ThreadLocal 上，新线程的操作不在原事务中。

异常与配置相关 6. 异常被 catch 吞掉：拦截器以为成功，照常提交。确需 catch 时可手动 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()。 7. 异常类型不匹配：默认只回滚 RuntimeException 和 Error，检查型异常需 rollbackFor = Exception.class。 8. 传播行为不当：NOT_SUPPORTED、NEVER、SUPPORTS（外层无事务时）以非事务执行。 9. 数据库不支持事务：如 MyISAM。 10. 事务管理器与数据源不对应：多数据源时常见。

自调用解决：拆到另一个 Bean（最推荐）；@Lazy 注入自身代理；exposeProxy = true 后用 AopContext.currentProxy()；或改用 TransactionTemplate。

为什么 Spring 事务基于 ThreadLocal？

数据库事务是绑定在同一个连接上的：只有同一个 Connection 上执行的多条 SQL 才属于同一个事务。Service 方法内会调用多个 DAO / Mapper，它们之间并没有显式传递连接。

Spring 的做法是：事务开启时把连接（ConnectionHolder）放进 TransactionSynchronizationManager 中的 ThreadLocal（key 是 DataSource），之后同一线程里的 MyBatis、JdbcTemplate 通过 DataSourceUtils.getConnection() 都能拿到这个连接。好处是：

  • 不需要在方法参数里一路传递 Connection，业务代码无感知。
  • 不同线程（不同请求）的事务天然隔离，互不干扰。
  • 挂起和恢复（REQUIRES_NEW、NOT_SUPPORTED）也就是把当前线程绑定的资源暂存起来，再绑定新的。

代价是：事务只在当前线程内有效，在事务方法里开新线程、用线程池或 @Async 执行的数据库操作都不在原事务中。

声明式事务有什么局限？大事务有什么问题？

@Transactional 用起来方便，但有几个局限：

  • 粒度是整个方法：方法里只要有一部分需要事务，整个方法都会在事务中执行，容易形成大事务。
  • 事务边界不直观：调用链上某处加了 @Transactional，下游方法可能不知不觉处于事务中。
  • 受代理机制限制：自调用、非 public、final、异常被吞等都会失效。
  • 不可回滚的操作：事务里的 RPC 调用、发 MQ、写缓存、写文件，数据库回滚了它们不会回滚，容易产生不一致；比如事务还没提交消息就被消费，消费方查不到数据。

大事务的危害：长时间占用数据库连接导致连接池耗尽；行锁持有时间变长，并发下锁等待和死锁增多；undo log 堆积；主从延迟增加；回滚代价大。

优化建议：

  • 查询、远程调用、计算等放到事务外，事务里只保留必要的写操作；可以用 TransactionTemplate 精确控制边界。
  • 需要在提交后执行的动作（发消息、删缓存）用 @TransactionalEventListener(phase = AFTER_COMMIT) 或 TransactionSynchronization.afterCommit()。
  • 设置 timeout，纯读方法可以设置 readOnly = true。

@Component、@Controller、@Service、@Repository 的区别

四个注解都会把类注册为 Bean，后三个都是 @Component 的派生注解（源码上标注了 @Component），对容器而言功能几乎一样，区别主要是分层语义：

  • @Controller：表现层。配合 Spring MVC 时，被识别为处理器，其中的 @RequestMapping 方法会注册为请求映射。
  • @Service：业务层，纯语义标识，没有额外行为。
  • @Repository：持久层。配合 PersistenceExceptionTranslationPostProcessor，会把底层数据访问异常（如 JPA / Hibernate 异常）统一转换为 Spring 的 DataAccessException 体系。
  • @Component：不属于以上分层的通用组件，如工具类、拦截器。

按分层使用，可读性更好，也便于用切点表达式按层做增强。MyBatis 的 Mapper 接口通常由 @Mapper / @MapperScan 注册，不依赖 @Repository。

@Configuration 和 @Component 有什么区别？

两者都能让类成为 Bean，也都能在里面写 @Bean 方法，区别在于 @Bean 方法之间互相调用时的语义。

  • @Configuration（默认 proxyBeanMethods = true，Full 模式）：配置类本身会被 CGLIB 增强。在配置类里调用另一个 @Bean 方法时，会被拦截并返回容器中已有的单例，保证单例语义。
  • @Component 或 @Configuration(proxyBeanMethods = false)（Lite 模式）：不做 CGLIB 增强，@Bean 方法互调就是普通 Java 方法调用，每调用一次就 new 一个新对象，不是容器里的那个 Bean。
@Configuration
public class AppConfig {
    @Bean public DataSource dataSource() { return new HikariDataSource(); }
    @Bean public JdbcTemplate jdbcTemplate() {
        return new JdbcTemplate(dataSource());   // Full 模式下返回的是同一个 DataSource 单例
    }
}

Spring Boot 的自动配置类普遍使用 proxyBeanMethods = false，减少 CGLIB 开销、加快启动；这时 Bean 之间的依赖通过方法参数注入，而不是方法互调。

Spring 中容易混淆的几组概念

  • IoC 与 DI：IoC 是思想（控制权交给容器），DI 是实现方式（容器把依赖注入进来）。
  • BeanFactory 与 ApplicationContext：前者是基础容器、懒加载；后者是子接口，启动时预实例化单例，并提供事件、国际化、资源加载等功能。
  • BeanFactory 与 FactoryBean：前者是容器，后者是一个能生产对象的 Bean，&name 拿它本身。
  • BeanFactoryPostProcessor 与 BeanPostProcessor：前者在实例化前改 BeanDefinition，后者在初始化前后处理 Bean 实例（AOP 代理在这里生成）。
  • @Autowired 与 @Resource：前者 Spring 注解、先按类型；后者 Jakarta 标准注解、先按名称。
  • JDK 代理与 CGLIB：前者基于接口，后者基于继承、不能代理 final；Spring Boot 2.x 起默认 CGLIB。
  • 循环依赖：只能解决单例 + 属性 / Setter 注入，构造器和 prototype 不行；三级缓存的第三级是为了按需生成早期 AOP 代理；Spring Boot 2.6+ 默认禁止循环引用。
  • 事务失效：多数是没走代理（自调用、非 public、final、未被管理）或异常没抛到拦截器（被 catch、检查型异常未配置 rollbackFor）。
  • REQUIRES_NEW 与 NESTED：前者是独立的新事务和新连接；后者是同一事务内的保存点，外层回滚会连带内层。
  • 自动装配：Spring Boot 自动配置不是无条件装配，而是通过 @Conditional 系列注解按 classpath、已有 Bean、配置项等条件按需生效，用户自定义的 Bean 优先（@ConditionalOnMissingBean）。

SpringMVC是什么？

Spring MVC 是 Spring Framework 中基于 Servlet API 的 Web 框架（模块名 spring-webmvc），按 MVC 模式把 Web 层分为模型、视图、控制器，核心是前端控制器 DispatcherServlet。

  • Model：封装业务数据，比如 Model、ModelAndView 中的数据，或者直接返回的对象。
  • View：渲染页面，比如 Thymeleaf、JSP；前后端分离时通常不用视图，直接返回 JSON。
  • Controller：接收请求、调用业务逻辑、返回结果，用 @Controller / @RestController 标注。

核心特性

  • 前端控制器统一接收请求、分发给处理器，各组件职责单一、可替换。
  • 基于注解的请求映射（@RequestMapping 系列），参数自动绑定、类型转换和校验（@Valid）。
  • 通过 HttpMessageConverter 支持 RESTful 接口和 JSON 序列化（默认 Jackson）。
  • 灵活的视图解析、拦截器、统一异常处理、文件上传、国际化等。

Spring 还有一个响应式 Web 框架 Spring WebFlux，基于 Reactor 和非阻塞 IO，和 Spring MVC 是并列关系。

SpringMVC有哪些重要组件

核心组件都由 DispatcherServlet 调度：它通过 HandlerMapping 找处理器，通过 HandlerAdapter 执行处理器，再通过 ViewResolver 或 HttpMessageConverter 产出响应。

组件 作用

SpringMVC的执行流程是怎样的？高频农业银行PDD阿里云

一句话：请求 → DispatcherServlet → HandlerMapping 找到 Handler 和拦截器链 → HandlerAdapter 执行 Controller → 返回视图交给 ViewResolver 渲染，或者返回对象由 HttpMessageConverter 写成 JSON → 响应。

  1. 请求先经过 Servlet 容器的 Filter 链，然后进入 DispatcherServlet，在 doDispatch() 中处理。
  2. DispatcherServlet 遍历 HandlerMapping，根据 URL、请求方法等找到对应的 Handler，返回 HandlerExecutionChain（Handler + 拦截器列表）。找不到就返回 404。
  3. 根据 Handler 类型找到支持它的 HandlerAdapter。
  4. 依次执行拦截器的 preHandle()，任意一个返回 false 就终止请求。
  5. HandlerAdapter 调用 Controller 方法：先用参数解析器把请求参数、路径变量、请求体（经 HttpMessageConverter 反序列化）绑定到方法参数，执行方法后再用返回值处理器处理返回值。
  6. 倒序执行拦截器的 postHandle()。
  7. 处理结果：
    • 有 @ResponseBody / @RestController 时，返回值在第 5 步就由 HttpMessageConverter 序列化为 JSON 写入响应体，不再经过视图解析。
    • 返回视图时，ViewResolver 把逻辑视图名解析成 View，View 用模型数据渲染页面。
    • 出现异常时由 HandlerExceptionResolver 处理（如 @ExceptionHandler）。
  8. 倒序执行拦截器的 afterCompletion()，最后响应经 Filter 链返回客户端。

Spring MVC为什么需要HandlerAdapter？

因为 Handler 的类型不统一，HandlerAdapter 用适配器模式把各种 Handler 的调用方式统一成 handle() 方法，让 DispatcherServlet 不需要知道 Handler 具体怎么执行。

Handler 有多种形式

  • @RequestMapping 注解的方法 → RequestMappingHandlerAdapter，要做参数解析、数据绑定、返回值处理。
  • 实现 Controller 接口的类 → SimpleControllerHandlerAdapter，调用 handleRequest()。
  • 实现 HttpRequestHandler 接口的类 → HttpRequestHandlerAdapter。
  • 函数式端点 RouterFunction → HandlerFunctionAdapter。

好处

  • 如果没有适配器，DispatcherServlet 里要写一堆 if (handler instanceof ...)，每增加一种 Handler 都要修改它，违反开闭原则。
  • 有了适配器，DispatcherServlet 只需要遍历所有 HandlerAdapter，调用 supports(handler) 找到支持的那个，再调用 handle()。新增 Handler 类型只需要新增一个适配器。
public interface HandlerAdapter {
    boolean supports(Object handler);
    ModelAndView handle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception;
}

什么是springmvc的父子容器

传统 Spring + Spring MVC 项目中有两个 IoC 容器：ContextLoaderListener 创建的根容器（父容器）管理 Service、DAO、数据源、事务等；DispatcherServlet 创建的 Web 容器（子容器）管理 Controller、视图解析器、HandlerMapping 等 Web 组件。子容器可以访问父容器的 Bean，父容器不能访问子容器的 Bean。

为什么这样设计

  • 职责分离：业务层与 Web 层解耦，替换 Web 框架时业务层不受影响。
  • 一个应用可以配置多个 DispatcherServlet，各自有子容器，共享同一个父容器中的业务 Bean。

常见问题

  • 子容器查找 Bean 时先找自己，找不到再到父容器找，所以 Controller 可以注入 Service，Service 不能注入 Controller。
  • 如果两个容器都扫描了全部包，Service 会在两个容器中各创建一份。子容器中的那份没有被父容器的事务配置增强，Controller 注入到的是它，导致 @Transactional 失效。所以子容器只扫描 @Controller，父容器排除 @Controller。
  • 后置处理器只对所在容器的 Bean 生效，在父容器配置的 AOP 不会作用于子容器的 Controller。

Spring Boot 中：默认只有一个容器，DispatcherServlet 直接使用应用的 ApplicationContext，所以不存在父子容器问题。

Spring MVC中拦截器和过滤器的区别？高频

Filter 是 Servlet 规范的组件，作用在 DispatcherServlet 之前，面向所有请求；Interceptor 是 Spring MVC 的组件，作用在 DispatcherServlet 内部、Handler 执行前后，面向映射到 Controller 的请求。

对比 过滤器 Filter 拦截器 Interceptor
规范 Servlet（jakarta.servlet.Filter，Boot 2.x 是 javax.servlet） Spring MVC（HandlerInterceptor）
实现 Servlet 容器的 FilterChain 回调 DispatcherServlet.doDispatch() 中调用
时机 进入 DispatcherServlet 前、响应返回后 preHandle、postHandle、afterCompletion
范围 所有请求，包括静态资源 只拦截找到了 Handler 的请求
信息 原始 request、response 额外能拿到 HandlerMethod（可读方法注解）、ModelAndView

执行顺序：Filter → DispatcherServlet → preHandle → Controller → postHandle → 视图渲染 → afterCompletion → Filter 返回。

如何实现SpringMVC拦截器

实现 HandlerInterceptor 接口重写需要的方法，再通过 WebMvcConfigurer.addInterceptors() 注册并指定拦截路径。

三个方法（JDK 8 起都是 default 方法，按需重写）

  • preHandle：Handler 执行前调用。返回 true 继续执行，返回 false 中断请求（需要自己写响应）。常用于登录校验、权限校验。
  • postHandle：Handler 正常执行后、视图渲染前调用，可以修改 ModelAndView。对 @ResponseBody 接口来说，响应体此时已经写出，不能再修改。
  • afterCompletion：整个请求完成后调用，无论是否异常都会执行（前提是 preHandle 返回了 true），适合清理资源、记录耗时。

多个拦截器时，preHandle 按注册顺序执行，postHandle 和 afterCompletion 倒序执行。

@Component
public class LoginInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse resp, Object handler) {
        String token = req.getHeader("Authorization");
        if (token == null || !tokenService.verify(token)) {
            resp.setStatus(HttpStatus.UNAUTHORIZED.value());
            return false;
        }
        UserContext.set(tokenService.parse(token));     // 存入 ThreadLocal
        return true;
    }
    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse resp, Object handler, Exception ex) {
        UserContext.remove();                            // 防止线程复用导致数据串用和内存泄漏
    }
}

@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Autowired
    private LoginInterceptor loginInterceptor;
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(loginInterceptor)
                .addPathPatterns("/**")
                .excludePathPatterns("/login", "/static/**")
                .order(1);
    }
}

tokenService 这里省略了注入。如果拦截器用 new 创建再注册，它就不是 Spring 管理的对象，内部无法 @Autowired 注入 Bean，所以上例把它声明为 Bean 再注入。

SpringBoot如何进行全局异常处理？

最常用的是 @RestControllerAdvice + @ExceptionHandler：在一个类中集中处理所有 Controller 抛出的异常，返回统一的响应格式。

@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BusinessException.class)
    public Result<Void> handleBiz(BusinessException e) {
        return Result.fail(e.getCode(), e.getMessage());
    }
    @ExceptionHandler(MethodArgumentNotValidException.class)   // @Valid 校验失败
    public Result<Void> handleValid(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().get(0).getDefaultMessage();
        return Result.fail(400, msg);
    }
    @ExceptionHandler(Exception.class)                          // 兜底
    public Result<Void> handleOther(Exception e) {
        log.error("系统异常", e);
        return Result.fail(500, "系统繁忙");
    }
}

要点

  • @RestControllerAdvice = @ControllerAdvice + @ResponseBody。可以用 basePackages 或 annotations 限定作用范围。
  • 匹配规则：按异常类型找最接近的处理方法，子类异常优先于父类异常。Controller 内部定义的 @ExceptionHandler 优先于全局的。
  • 可以配合 @ResponseStatus 设置 HTTP 状态码，或者返回 ResponseEntity。

其他方式

  • ErrorController：Spring Boot 默认由 BasicErrorController 处理 /error 路径，没有被处理的异常、404 等最终都会转到这里，返回默认的错误页或 JSON。可以自定义实现来改变默认的错误响应。
  • 实现 HandlerExceptionResolver 接口：更底层的方式，@ExceptionHandler 就是由其中的 ExceptionHandlerExceptionResolver 支持的。
  • Spring Boot 3.x 支持 RFC 9457 的 ProblemDetail 标准错误格式，可以通过 spring.mvc.problemdetails.enabled=true 开启。

局限：全局异常处理只能捕获 DispatcherServlet 内部（Controller、拦截器）抛出的异常，Filter 中的异常要在 Filter 里自己处理。

SpringBoot如何进行跨域请求的处理？

浏览器的同源策略会拦截协议、域名、端口任一不同的跨域请求响应，服务端要通过 CORS 响应头声明允许跨域。Spring Boot 中有三种方式：@CrossOrigin 注解、WebMvcConfigurer 全局配置、注册 CorsFilter。

1. @CrossOrigin 注解：加在 Controller 类或方法上，作用范围小。

@CrossOrigin(origins = "http://localhost:8081")
@RestController
public class UserController { }

2. 全局配置

@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/**")
                .allowedOriginPatterns("https://*.example.com")
                .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
                .allowedHeaders("*")
                .allowCredentials(true)
                .maxAge(3600);       // 预检请求结果缓存 1 小时
    }
}

3. CorsFilter：注册一个 CorsFilter Bean，在过滤器层面处理，优先级最高。项目中有登录拦截器时更可靠：浏览器发出的 OPTIONS 预检请求不带认证信息，可能先被拦截器拒绝，导致跨域失败；用过滤器可以在拦截器之前处理掉预检请求。使用 Spring Security 时要在安全配置中开启 cors()。

注意点

  • allowCredentials(true) 时不能用 allowedOrigins("*")，Spring 会直接报错，要列出具体的域名，或者用 Spring 5.3 起提供的 allowedOriginPatterns。
  • 非简单请求（如 Content-Type: application/json、自定义请求头）会先发 OPTIONS 预检请求。
  • 也可以不在应用里处理，由 Nginx 或网关统一添加 CORS 响应头，或者用反向代理让前后端同源。

一句话：@EnableAutoConfiguration 导入 AutoConfigurationImportSelector，读取各 jar 声明的自动配置类，过滤后按条件创建 Bean。

流程

  1. @Import(AutoConfigurationImportSelector.class) 是 DeferredImportSelector，在用户配置类处理完后才执行，所以用户的 Bean 优先，自动配置靠 @ConditionalOnMissingBean 让位。
  2. 读取候选自动配置类：Spring Boot 2.7 起是 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（每行一个全限定名）；2.6 及以前是 META-INF/spring.factories 中 EnableAutoConfiguration 的值。2.7 两种都支持，3.0 起只能用 .imports。
  3. 去重并去掉 exclude / spring.autoconfigure.exclude 排除的类；再基于编译期生成的 spring-autoconfigure-metadata.properties 提前做 @ConditionalOnClass 过滤，不用加载类。
  4. 解析剩余配置类，类上和 @Bean 方法上的条件注解决定最终注册哪些 Bean。

常用条件注解：@ConditionalOnClass（引入依赖才生效）、@ConditionalOnMissingBean（用户自定义了就不创建）、@ConditionalOnProperty（配置项满足才生效）。

例子：引入 spring-boot-starter-web 后类路径有了 DispatcherServlet 和 Tomcat，自动注册二者，属性来自 ServerProperties（server.*）。

排查：debug=true 打印条件评估报告，或访问 /actuator/conditions。

Starter 是"依赖描述 + 自动配置"的组合：引入一个 Starter，就通过 Maven 依赖传递引入了某个功能所需的一组库，同时带来对应的自动配置类，Spring Boot 启动时按条件自动创建相关 Bean。

两部分

  • 依赖聚合：Starter 基本没有代码，主要是一个 pom。比如 spring-boot-starter-web 引入 Spring MVC、Jackson、内嵌 Tomcat、日志等。版本由 spring-boot-dependencies 统一管理，引入时不用写版本号。
  • 自动配置：官方的集中在 spring-boot-autoconfigure 模块，第三方一般自带 xxx-spring-boot-autoconfigure，在 AutoConfiguration.imports（2.7 起）或 spring.factories（2.6 及以前）中注册。

生效过程：引入 Starter → 类出现在类路径 → AutoConfigurationImportSelector 加载自动配置类 → @ConditionalOnClass 等条件满足 → 用 @ConfigurationProperties 绑定的配置创建默认 Bean → 用户自定义同类 Bean 时通过 @ConditionalOnMissingBean 让位。

命名规范：官方 spring-boot-starter-xxx，第三方 xxx-spring-boot-starter（如 mybatis-spring-boot-starter）。

实现一个 Spring Boot Starter 该如何做高频

步骤：写属性类和自动配置类 → 用条件注解控制 Bean 的创建 → 在 AutoConfiguration.imports 中注册自动配置类 → 打包发布，使用方引入依赖即可。

1. 建模块：官方推荐拆成 xxx-spring-boot-autoconfigure（代码）和 xxx-spring-boot-starter（只有 pom），简单场景可合并。依赖 spring-boot-autoconfigure，可选 spring-boot-configuration-processor 生成配置元数据供 IDE 提示。

2. 属性类 + 自动配置类

@ConfigurationProperties(prefix = "sms")
public class SmsProperties {
    private boolean enabled = true;
    private String accessKey;
    private String secretKey;
    // getter / setter
}

@AutoConfiguration
@ConditionalOnClass(SmsClient.class)
@ConditionalOnProperty(prefix = "sms", name = "enabled", havingValue = "true", matchIfMissing = true)
@EnableConfigurationProperties(SmsProperties.class)
public class SmsAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean           // 使用方自定义了 SmsClient 就不再创建
    public SmsClient smsClient(SmsProperties props) {
        return new SmsClient(props.getAccessKey(), props.getSecretKey());
    }
}

3. 注册自动配置类

  • Spring Boot 2.7 / 3.x：META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 中写一行 com.example.sms.SmsAutoConfiguration。
  • Spring Boot 2.6 及以前：META-INF/spring.factories 中写 org.springframework.boot.autoconfigure.EnableAutoConfiguration=com.example.sms.SmsAutoConfiguration。

4. 打包发布：发布到私服，使用方引入 sms-spring-boot-starter，配置 sms.access-key 即可注入 SmsClient。

易错点：自动配置类不要放在使用方 @ComponentScan 能扫到的包下，否则会被当成普通配置类，条件注解的顺序保证失效；第三方 Starter 命名不要以 spring-boot 开头。

SpringBoot的启动流程？高频

一句话：SpringApplication.run() 先创建 SpringApplication，再准备 Environment、创建上下文、执行 refresh()（自动配置、Bean 实例化、启动内嵌服务器），最后执行 Runner 并发布就绪事件。

1. 创建 SpringApplication：推断应用类型（SERVLET / REACTIVE / NONE）；从 META-INF/spring.factories 加载 ApplicationContextInitializer 和 ApplicationListener（这两类仍用 spring.factories，与自动配置类的注册文件不同）；推断主启动类。

2. 执行 run()

  1. 通过 SpringApplicationRunListener 发布 ApplicationStartingEvent。
  2. 准备 Environment：命令行参数、系统属性、环境变量、application.yml，发布 ApplicationEnvironmentPreparedEvent。
  3. 打印 Banner，按类型创建 ApplicationContext。
  4. 准备上下文：执行 ApplicationContextInitializer，注册启动类，发布 ApplicationPreparedEvent。
  5. refresh()：解析配置类并导入自动配置类 → 注册 BeanPostProcessor → onRefresh() 创建内嵌 Tomcat → 实例化非懒加载单例 → finishRefresh() 启动服务器监听端口并发布 ContextRefreshedEvent。
  6. 发布 ApplicationStartedEvent，执行 ApplicationRunner 和 CommandLineRunner。
  7. 发布 ApplicationReadyEvent，对外服务；出错则发布 ApplicationFailedEvent。

Spring Boot 中的 Bean 是单例吗？会不会有线程安全问题？怎么解决高频

默认是单例（singleton 作用域），每个容器中一个 Bean 定义只有一个实例，所有线程共享。单例本身不会导致线程安全问题，问题出在 Bean 有可变的成员变量并被多个线程同时修改时。

为什么大多数 Bean 是安全的：Controller、Service、DAO 一般是无状态的，成员变量只有注入的其他 Bean（初始化后不再改变），业务数据都在方法的局部变量里，局部变量在各自线程的栈上，不会共享。

有问题的例子

@Service
public class CounterService {
    private int count;                 // 可变成员变量，多线程 count++ 会丢失更新
    public void incr() { count++; }
}

解决办法

  • 设计成无状态：首选。不要用成员变量保存请求相关的数据，改用方法参数和局部变量。
  • ThreadLocal：每个线程一份数据，比如保存当前登录用户。线程池复用线程，用完必须 remove()。
  • 并发工具：用 AtomicInteger、LongAdder、ConcurrentHashMap 替代普通类型和集合，或者用 synchronized / ReentrantLock 保护临界区。
  • 不可变对象：成员变量声明为 final 且不对外提供修改。
  • 改变作用域：@Scope("prototype") 每次获取都创建新实例；Web 应用中可以用 request / session 作用域。注意 prototype Bean 注入到单例 Bean 中时只会注入一次，要每次拿新实例需要用 ObjectProvider 或 @Lookup。

其他作用域：singleton（默认）、prototype、request、session、application、websocket。

spring-boot-starter-web 默认依赖 spring-boot-starter-tomcat。替换方法是在 pom 中把它排除，再引入 Jetty 或 Undertow 的 Starter，Spring Boot 会根据类路径自动配置对应的内嵌服务器。

<dependency>

    <artifactId>spring-boot-starter-web</artifactId>
    <exclusions>
        <exclusion>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-tomcat</artifactId>
        </exclusion>
    </exclusions>
</dependency>

</dependency>

原理：ServletWebServerFactoryAutoConfiguration 中按 @ConditionalOnClass 判断类路径中有 Tomcat、Jetty 还是 Undertow 的类，创建对应的 TomcatServletWebServerFactory / JettyServletWebServerFactory / UndertowServletWebServerFactory。

SpringBoot怎么实现定时任务？

最简单的是 Spring 自带的 @EnableScheduling + @Scheduled；需要集群调度、分片、可视化管理时，使用 XXL-Job、ElasticJob、Quartz 等框架。

@SpringBootApplication
@EnableScheduling
public class App { }

@Component
public class ReportTask {
    @Scheduled(cron = "0 0 * * * ?")          // 每小时整点执行
    public void hourly() { }

    @Scheduled(fixedRate = 5000)              // 每次开始执行后 5 秒再次执行
    public void rate() { }

    @Scheduled(fixedDelay = 5000, initialDelay = 10000)   // 上次执行结束 5 秒后再执行，启动 10 秒后首次执行
    public void delay() { }
}

三种触发方式

  • fixedRate：按固定频率，从上一次开始执行的时间点计算间隔。
  • fixedDelay：从上一次执行结束的时间点计算间隔。
  • cron：Spring 的 cron 表达式有 6 位：秒 分 时 日 月 周（不支持年），比如 0 0 2 * * ? 是每天凌晨 2 点。可以用 zone 指定时区。

注意点

  • 默认所有定时任务共用一个单线程的调度器，一个任务执行慢会阻塞其他任务。Spring Boot 2.1 起可以用 spring.task.scheduling.pool.size 调整线程数，或者自定义 TaskScheduler / 结合 @Async。
  • 集群部署时每个实例都会执行一次，需要用分布式锁（如 ShedLock、Redisson）保证只有一个实例执行，或者改用分布式调度框架。
  • 任务内部要捕获异常并记录日志，避免问题被吞掉。
  • 需要动态修改执行时间时，可以实现 SchedulingConfigurer 注册 Trigger。

SpringBoot如何实现热部署？

开发环境最常用的是 spring-boot-devtools：它在类路径文件变化时自动重启应用，速度比手动冷启动快。需要真正不重启地替换类时，可以用 JRebel 这类工具。

devtools 原理

  • 使用两个类加载器：不变的第三方 jar 由 base 类加载器加载，项目自己的类由 restart 类加载器加载。
  • 检测到类路径变化时，丢弃 restart 类加载器并新建一个重新加载项目类，第三方库不用重新加载，所以比冷启动快。严格来说这是快速重启，不是热替换。
  • 静态资源和模板修改不需要重启，配合浏览器的 LiveReload 插件可以自动刷新页面。
  • 还会禁用模板缓存等开发期不需要的缓存。

使用

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-devtools</artifactId>
    <scope>runtime</scope>
    <optional>true</optional>
</dependency>

devtools 是根据类路径变化触发的，所以 IDE 中要让代码修改后重新编译：IntelliJ IDEA 中手动 Build，或者开启 "Build project automatically" 和运行时自动编译选项。以 java -jar 运行打包后的应用时 devtools 会自动禁用，不会影响生产环境。

其他方式

  • IDE 自带的 HotSwap（JVM 的类重定义能力）：调试模式下可以替换方法体，但不支持新增方法、字段或修改类结构。
  • JRebel：商业插件，不重启 JVM 就能重新加载修改后的类，支持结构变化。

SpringBoot怎么配置多数据源？

有两种思路：按包或 Mapper 静态划分（每个数据源配一套 DataSource、SqlSessionFactory、事务管理器），或者用 AbstractRoutingDataSource 在运行时动态切换。实际项目中也常直接用 dynamic-datasource 这类开源组件。

方式一：静态多数据源（不同业务库分别访问）

spring:
  datasource:
    primary:
      jdbc-url: jdbc:mysql://localhost:3306/primary_db   # HikariCP 绑定时用 jdbc-url 而不是 url
      username: root
      password: ${PRIMARY_DB_PASSWORD}
    secondary:
      jdbc-url: jdbc:mysql://localhost:3306/secondary_db
      username: admin
      password: ${SECONDARY_DB_PASSWORD}

@Configuration
@MapperScan(basePackages = "com.example.mapper.primary", sqlSessionFactoryRef = "primarySqlSessionFactory")
public class PrimaryDataSourceConfig {
    @Primary @Bean
    @ConfigurationProperties(prefix = "spring.datasource.primary")
    public DataSource primaryDataSource() { return DataSourceBuilder.create().build(); }

    @Primary @Bean
    public SqlSessionFactory primarySqlSessionFactory(@Qualifier("primaryDataSource") DataSource ds) throws Exception {
        SqlSessionFactoryBean factory = new SqlSessionFactoryBean();
        factory.setDataSource(ds);
        return factory.getObject();
    }

    @Primary @Bean
    public PlatformTransactionManager primaryTransactionManager(@Qualifier("primaryDataSource") DataSource ds) {
        return new DataSourceTransactionManager(ds);
    }
}
// SecondaryDataSourceConfig 同理，扫描 com.example.mapper.secondary，不加 @Primary

要点：

  • 自定义 DataSource 后 DataSourceAutoConfiguration 因 @ConditionalOnMissingBean 不再生效，每个数据源要自己配。
  • @Primary 标记默认数据源，其余用 @Qualifier 注入；事务指定管理器：@Transactional(transactionManager = "secondaryTransactionManager")。
  • 直接绑定 HikariDataSource 时属性名是 jdbc-url；写 url 需先绑定 DataSourceProperties 再 initializeDataSourceBuilder()。

方式二：动态数据源（读写分离、多租户）：继承 AbstractRoutingDataSource 重写 determineCurrentLookupKey() 从 ThreadLocal 取 key；真实数据源放进 targetDataSources；自定义注解（如 @DS("slave")）+ AOP 在方法前写入 key、结束后清除。

易错点

  • 事务开始后切换数据源不生效，切换切面必须在事务切面之前执行。
  • 跨数据源写不能靠本地事务保证一致，需要 Seata 等分布式事务或业务补偿。
  • 开源方案：dynamic-datasource-spring-boot-starter（@DS 切换）；分库分表用 ShardingSphere。

SpringBoot如何优雅停机？

优雅停机是指应用关闭时先停止接收新请求，等正在处理的请求完成后再释放资源退出，避免请求中断和数据不一致。Spring Boot 2.3 起内置支持，3.4 起默认开启。

server:
  shutdown: graceful                    # 2.3 ~ 3.3 默认是 immediate，3.4 起默认 graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s     # 每个生命周期阶段的最长等待时间，默认 30s

过程

  1. 进程收到 SIGTERM（kill PID、docker stop、Kubernetes 删除 Pod）后，JVM 执行 Spring 注册的 shutdown hook，开始关闭 ApplicationContext。
  2. Web 服务器停止接收新请求：Tomcat、Jetty、Reactor Netty 在网络层停止接收连接，Undertow 对新请求返回 503。
  3. 等待正在处理的请求完成，超过 timeout-per-shutdown-phase 就强制结束。
  4. 依次停止其他 SmartLifecycle 组件，销毁 Bean（执行 @PreDestroy、DisposableBean），关闭连接池等资源。

注意点

  • 必须用 kill PID（SIGTERM）停止进程，kill -9 不会触发 shutdown hook，优雅停机不会生效。
  • 自己的线程池要在销毁时 shutdown() 并 awaitTermination()；Spring 管理的 ThreadPoolTaskExecutor 可以设置 setWaitForTasksToCompleteOnShutdown(true) 和等待时间。
  • 微服务场景下还要先从注册中心下线实例，等调用方刷新地址列表后再停机，否则调用方仍会把请求发过来。
  • Kubernetes 中，Pod 的 terminationGracePeriodSeconds（默认 30s）要大于应用的停机等待时间，常配合 preStop hook 先 sleep 几秒，等流量摘除。

mybatis有哪些优缺点？工商银行

MyBatis 是一个半自动的持久层框架：SQL 由开发者自己写，框架负责参数绑定、执行 SQL 和把结果集映射成对象，省掉了 JDBC 的样板代码。

优点

  • SQL 完全可控：可以针对复杂查询、多表关联、索引做精细优化，适合业务复杂、对性能敏感的系统。
  • SQL 和代码解耦：SQL 集中写在 XML（或注解）里，便于统一管理和审查。
  • 消除 JDBC 样板代码：不用手动获取连接、设置参数、遍历 ResultSet、关闭资源。
  • 映射灵活：通过 resultMap 支持字段名和属性名不一致、一对一、一对多等复杂映射；也可以直接返回 Map。
  • 动态 SQL：<if>、<where>、<foreach> 等标签按条件拼接 SQL。
  • 学习成本低，和 Spring 集成方便（mybatis-spring、mybatis-spring-boot-starter）。

缺点

  • 单表 CRUD 也要手写 SQL，工作量大（MyBatis-Plus 解决了这一点）。
  • SQL 依赖具体数据库方言，换数据库时 SQL 可能要改，移植性不如 Hibernate。
  • 项目大时 XML 文件多，SQL 写错要到运行时才发现。
  • 用 ${} 不当会有 SQL 注入风险。

MyBatis-Plus（MP）是在 MyBatis 基础上的增强工具，只做增强不做改变：原有 MyBatis 的 XML、注解写法全部照常可用，额外提供通用 CRUD 和一批常用插件。

对比 MyBatis MyBatis-Plus

其他 无 代码生成器、逻辑删除（@TableLogic）、乐观锁（@Version）、字段自动填充、主键策略（默认 ASSIGN_ID，雪花算法）

Mybatis和Hibernate有哪些区别？

MyBatis 是半自动 ORM，SQL 自己写；Hibernate 是全自动 ORM（JPA 规范的主流实现），根据对象映射自动生成 SQL。

对比 MyBatis Hibernate
ORM 程度 半自动，映射 SQL 结果和对象 全自动，映射对象和表，操作对象即可
SQL 手写，可精细优化 自动生成，也可以写 HQL/JPQL 或原生 SQL
数据库移植性 差，SQL 和方言绑定 好，通过 Dialect 适配不同数据库
对象管理 无实体状态管理 有持久化上下文：实体状态、脏检查（修改对象自动生成 update）、级联、延迟加载
学习和调优 简单，SQL 直观 门槛较高，生成的 SQL 不直观，容易出现 N+1 查询
适用场景 业务复杂、需求变化快、对 SQL 性能要求高（国内互联网主流） 业务模型稳定、以单表 CRUD 为主、需要跨数据库

两者都有一级、二级缓存。不能简单说 Hibernate 性能差，性能问题多来自生成的 SQL 不可控，复杂查询时调优比 MyBatis 难。

#{} 和 ${} 的区别是什么？MyBatis 是如何防止 SQL 注入的高频工商银行农业银行腾讯

#{} 是预编译占位符，${} 是字符串替换。传参数一律用 #{}；${} 只用于表名、列名、排序字段这类不能用占位符的地方，并且必须做白名单校验。

#{}

  • MyBatis 把它解析成 ?，通过 JDBC 的 PreparedStatement 的 setXxx() 设置参数。
  • SQL 结构先编译好，参数只作为值传给数据库，不参与 SQL 语法解析，所以注入的 ' OR '1'='1 只会被当成普通字符串，这就是防注入的原理。
  • 自动处理类型转换（通过 TypeHandler），字符串不用自己加引号。

${}

  • 在生成 SQL 时把参数值原样拼进 SQL 文本，不做转义。
  • 有 SQL 注入风险，比如 ORDER BY ${col} 传入 id; DROP TABLE user。
  • 必须用的场景：动态表名（分表）、动态列名、ORDER BY 字段和方向，因为占位符只能代表值，不能代表标识符。
<!-- 安全：参数走占位符 -->
<select id="findByName" resultType="User">
  SELECT * FROM user WHERE name = #{name}
</select>
<!-- 排序字段只能用 ${}，调用前要在代码里校验 sortCol 属于允许的列名 -->
<select id="listSorted" resultType="User">
  SELECT * FROM user ORDER BY ${sortCol}
</select>

补充

  • 模糊查询不要写 '%${name}%'，用 CONCAT('%', #{name}, '%')，或者在 Java 里拼好 % 再传给 #{}。
  • IN 查询用 <foreach> 生成多个 #{}，不要把逗号拼接的字符串塞进 ${}。

MyBatis查询有哪几种方式高频

最常用的是 Mapper 接口代理 + XML，其次是注解方式；另外还有直接通过 SqlSession 按 statement ID 调用、Provider 动态生成 SQL，以及 MyBatis-Plus 的条件构造器。

1. Mapper 接口 + XML（最常用，适合复杂 SQL）

UserMapper mapper = sqlSession.getMapper(UserMapper.class);  // Spring 中直接注入 Mapper
User user = mapper.selectById(1);

<mapper namespace="com.example.mapper.UserMapper">
  <select id="selectById" resultType="com.example.entity.User">
    SELECT * FROM user WHERE id = #{id}
  </select>
</mapper>

2. 注解方式（适合简单 SQL）

@Select("SELECT * FROM user WHERE id = #{id}")
User selectById(Integer id);

3. SqlSession 直接调用：sqlSession.selectOne("com.example.mapper.UserMapper.selectById", 1)，是早期写法，字符串 ID 容易写错。

4. Provider 注解：@SelectProvider(type = UserSqlProvider.class, method = "build")，用 Java 代码（如 SQL 构建类）动态生成 SQL。

5. MyBatis-Plus：BaseMapper 的通用方法加 LambdaQueryWrapper。

按返回形式还可以分为：返回单个对象、List、Map（用 @MapKey 指定 key 列）；大结果集用 ResultHandler 逐行处理，或者返回 Cursor<T> 流式读取，避免一次性把数据全部载入内存。

xml映射文件中有哪些常见的标签？

映射文件的标签分三类：CRUD 语句标签、结果映射与复用标签、动态 SQL 标签。

语句标签

  • <select>、<insert>、<update>、<delete>：id 对应 Mapper 方法名，常用属性有 parameterType、resultType / resultMap。
  • <insert> 的 useGeneratedKeys="true" keyProperty="id" 可以回填自增主键；<selectKey> 用于不支持自增的数据库（如 Oracle 序列）获取主键。

映射与复用

  • <resultMap>：定义列和属性的映射，子标签有 <id>、<result>、<association>（一对一）、<collection>（一对多）、<discriminator>（按列值选择映射）。
  • <sql> + <include>：抽取可复用的 SQL 片段，比如公共列列表。
  • <cache> / <cache-ref>：开启当前 namespace 的二级缓存 / 引用其他 namespace 的缓存。
  • <parameterMap>：旧的参数映射方式，已经废弃，现在用 parameterType 和 #{} 内联参数代替。

动态 SQL

  • <if>：条件成立才拼接。
  • <choose> / <when> / <otherwise>：多选一，相当于 switch。
  • <where>：有条件时才加 WHERE，并去掉开头多余的 AND / OR。
  • <set>：用于 UPDATE，去掉末尾多余的逗号。
  • <trim>：自定义前缀、后缀和要去掉的内容，<where>、<set> 都可以用它实现。
  • <foreach>：遍历集合，常用于 IN (...) 和批量插入。
  • <bind>：创建一个变量，比如拼接模糊查询的 %。

mybatis的动态sql有什么好处？举例说明？动态sql的执行原理是什么？邮政储蓄银行网易蚂蚁

动态 SQL 让一条映射语句根据参数在运行时生成不同的 SQL，避免在 Java 里手工拼字符串，也避免为每种条件组合写一条 SQL。原理是把标签解析成 SqlNode 树，执行时用 OGNL 对参数求值，拼出最终 SQL。

好处

  • 多条件查询、选择性更新、批量操作只需写一条语句。
  • 不用处理多余的 AND、逗号等拼接细节。
  • 参数仍然走 #{} 预编译，比手工拼接安全。

例子：多条件查询和批量查询

<select id="search" resultType="User">
  SELECT * FROM user
  <where>
    <if test="name != null and name != ''">AND name LIKE CONCAT('%', #{name}, '%')</if>
    <if test="status != null">AND status = #{status}</if>
    <if test="ids != null and ids.size() > 0">
      AND id IN
      <foreach collection="ids" item="id" open="(" separator="," close=")">#{id}</foreach>
    </if>
  </where>
</select>

执行原理

  1. 启动解析阶段：XMLScriptBuilder 把含动态标签（或含 ${}）的语句解析成一棵 SqlNode 树（IfSqlNode、WhereSqlNode、ForEachSqlNode 等，根节点是 MixedSqlNode），封装为 DynamicSqlSource。不含动态内容的语句解析成 RawSqlSource，启动时就确定了 SQL。
  2. 执行阶段：调用 getBoundSql(参数)，各 SqlNode 依次 apply，<if test> 等表达式用 OGNL 对参数求值，满足条件的片段追加到 DynamicContext 中，同时完成 ${} 的文本替换。
  3. 拼好的 SQL 再交给 SqlSourceBuilder，把 #{} 替换成 ? 并记录参数映射，得到 BoundSql，最后交给 PreparedStatement 执行。

Mybatis中Dao接口和xml文件有什么作用？Dao接口支持重载吗？

Dao（Mapper）接口声明方法，XML 提供方法对应的 SQL；二者通过"namespace = 接口全限定名、语句 id = 方法名"绑定。接口方法可以重载，但所有同名重载方法只能对应同一条 SQL 语句。

绑定原理

  • XML 的 namespace 写接口全限定名，每条语句的 id 写方法名，MyBatis 启动时把每条语句解析成 MappedStatement，以 namespace.id 为 key 存入 Configuration。
  • 接口没有实现类。getMapper() 通过 MapperProxyFactory 用 JDK 动态代理生成代理对象；调用方法时 MapperProxy 用"接口全限定名.方法名"找到 MappedStatement，再交给 SqlSession 执行。

重载

  • 语句的 key 只有"接口名.方法名"，不包含参数类型，所以 XML 里同一个 namespace 下不能有两个相同的 id，启动时会报 Mapped Statements collection already contains value。
  • 可以在接口中声明重载方法，但它们都会映射到同一条 SQL。要让它们表现不同，只能在这条 SQL 里用动态 SQL 判断参数（如 _parameter、@Param 指定的名字）。
  • 实际开发中不推荐重载 Mapper 方法，用不同的方法名更清晰。

其他注意点：Mapper 接口方法有多个参数时，用 @Param("name") 命名，XML 里才能用 #{name} 引用。

mybatis的执行机制是怎样的？高频

一句话：启动时把配置和映射文件解析成 Configuration，运行时 Mapper 代理把方法调用转给 SqlSession，再由 Executor → StatementHandler → JDBC 执行 SQL，最后 ResultSetHandler 把结果映射成对象。

启动阶段：SqlSessionFactoryBuilder 解析 mybatis-config.xml 和 Mapper XML / 注解，生成全局唯一的 Configuration，每条 SQL 对应一个 MappedStatement；再创建线程安全的 SqlSessionFactory，应用中只需一个。

执行阶段

  1. openSession() 获取 SqlSession 并创建 Executor。SqlSession 非线程安全，用完关闭；Spring 中注入的是线程安全的 SqlSessionTemplate，为当前事务绑定 SqlSession。
  2. getMapper() 返回 JDK 动态代理，MapperProxy 按"接口全限定名.方法名"找到 MappedStatement，转成 sqlSession.selectList/update 等调用。
  3. Executor 调度和缓存：开二级缓存时外层是 CachingExecutor，再查一级缓存，未命中查库。基础执行器有 SimpleExecutor（默认）、ReuseExecutor（复用 Statement）、BatchExecutor（批量）。
  4. StatementHandler 创建 PreparedStatement，ParameterHandler 用 TypeHandler 设参后执行。
  5. ResultSetHandler 按 resultType / resultMap 映射结果。
  6. 非自动提交模式下增删改需 commit()，最后 close()。

mybatis缓存机制是怎么样的，两级缓存分别在什么时候用高频

MyBatis 有两级缓存：一级缓存是 SqlSession 级别，默认开启；二级缓存是 namespace（Mapper）级别，需要在映射文件里显式开启。查询顺序是：二级缓存 → 一级缓存 → 数据库。

一级缓存（本地缓存）

  • 范围是同一个 SqlSession，底层是 BaseExecutor 里的 PerpetualCache（HashMap）；key 由 statement ID、分页参数、SQL、参数值、环境 ID 组成。
  • 增删改、commit()、rollback()、clearCache()、关闭 SqlSession 时清空；localCacheScope 改为 STATEMENT 等于关闭。
  • 易错点：Spring 中没有事务时每次 Mapper 调用都新开 SqlSession，一级缓存基本不起作用；同一个 @Transactional 内才生效。

二级缓存

  • 范围是同一个 namespace，跨 SqlSession 共享。
  • cacheEnabled 默认 true，但还需映射文件加 <cache/>（或 @CacheNamespace）；单条语句可 useCache="false"。
  • 默认 LRU、最多 1024 个对象；readOnly=false 时序列化返回副本，实体需实现 Serializable。
  • SqlSession commit() 或 close() 后才写入；同 namespace 增删改会清空；可实现 Cache 接口接入 Redis。

什么时候用：一级缓存自动生效，适合同一事务内重复查询。二级缓存只适合读多写少、实时性要求低、只在单表 namespace 内修改的数据；生产一般不开，因为别的 namespace 改数据不会清空这里的缓存，多实例间也不一致，通常改在业务层用 Redis。

mybatis支持延迟加载吗？原理是什么？

支持。延迟加载只对 <association> 和 <collection> 里的嵌套查询（select 属性指定的另一条语句）生效：查主对象时先不查关联对象，等真正访问关联属性时才执行那条查询。原理是返回主对象的动态代理，拦截 getter 触发加载。

配置

  • 全局：lazyLoadingEnabled=true（默认 false）；aggressiveLazyLoading=false（3.4.1 起默认 false，为 true 时访问任意属性都会加载全部延迟属性）。
  • 单个关联：fetchType="lazy" 或 "eager"，优先级高于全局配置。
<resultMap id="userMap" type="User">
  <id column="id" property="id"/>
  <collection property="orders" column="id" fetchType="lazy"
              select="com.example.mapper.OrderMapper.selectByUserId"/>
</resultMap>

原理

  1. 映射结果时，如果有延迟加载的属性，MyBatis 用代理工厂（默认 Javassist，3.5.10 起 CGLIB 已被标记为废弃）为结果对象创建子类代理，并把待执行的嵌套查询保存在 ResultLoaderMap 中。
  2. 调用代理对象的 getter（如 getOrders()）时，拦截器发现该属性还没加载，就执行对应的嵌套查询，把结果 set 进去，再返回。
  3. 调用 equals、clone、hashCode、toString 默认会触发加载全部延迟属性（由 lazyLoadTriggerMethods 配置）。

注意：嵌套查询有 N+1 问题（1 条主查询 + N 条关联查询），延迟加载只是把它推迟了。一次就要拿全部数据时，用连接查询 + 嵌套结果映射更高效。

Mybatis中的插件是如何运行的？怎样自己编写一个插件？

MyBatis 插件就是拦截器：它只能拦截四大核心对象 Executor、StatementHandler、ParameterHandler、ResultSetHandler 的方法。这四个对象创建时，InterceptorChain.pluginAll() 用 JDK 动态代理把它们层层包装，调用被拦截的方法时先进入插件逻辑。

对象 可拦截方法
Executor update、query、commit、rollback 等
StatementHandler prepare、parameterize、batch、update、query
ParameterHandler getParameterObject、setParameters
ResultSetHandler handleResultSets、handleOutputParameters

运行原理

  1. 插件按配置顺序存入 InterceptorChain。
  2. 创建四大对象时依次调用 plugin()，默认 Plugin.wrap(target, this)：目标实现了 @Signature 声明的接口就生成 JDK 代理，否则返回原对象。
  3. 多个插件形成多层代理，后配置的在最外层、最先执行。
  4. Plugin.invoke() 判断方法在签名中就调用 intercept(invocation)，插件内 invocation.proceed() 继续原方法。

编写步骤：实现 Interceptor 重写 intercept()（3.5.2 起 plugin()、setProperties() 有默认实现）；用 @Intercepts + @Signature 声明类型、方法名、参数类型；XML 用 <plugins> 注册，Spring Boot 中声明为 Bean 即可自动注册。

@Intercepts({@Signature(type = StatementHandler.class, method = "prepare",
        args = {Connection.class, Integer.class})})
public class SlowSqlInterceptor implements Interceptor {
    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            return invocation.proceed();
        } finally {
            StatementHandler handler = (StatementHandler) invocation.getTarget();
            long cost = System.currentTimeMillis() - start;
            // 记录 handler.getBoundSql().getSql() 和耗时
        }
    }
}

注意这里只统计了 prepare 的耗时，真正的执行耗时应拦截 query / update。常见应用：PageHelper / MyBatis-Plus 分页、慢 SQL 监控、数据权限、字段加解密、多租户。

mybatis连接池是什么？

连接池负责预先创建并复用数据库连接，避免每次执行 SQL 都要做 TCP 连接和数据库认证。MyBatis 自带简单的连接池实现，但实际项目里一般由 Spring Boot 管理数据源，默认是 HikariCP。

MyBatis 内置的数据源类型（<dataSource type="...">）

  • UNPOOLED：UnpooledDataSource，每次请求都新建连接，用完关闭。
  • POOLED：PooledDataSource，维护空闲连接和活跃连接两个列表，可以配置最大活跃连接数（poolMaximumActiveConnections，默认 10）、最大空闲连接数、获取连接的最长等待时间等。调用 close() 时连接归还到池中而不是真正关闭，这是通过代理 Connection 实现的。
  • JNDI：从应用服务器的 JNDI 上下文获取数据源。

和 Spring Boot 集成时：MyBatis 直接使用容器里的 DataSource Bean。Spring Boot 2.0 起默认连接池是 HikariCP，也可以换成 Druid（自带监控和 SQL 防火墙）等。连接池的关键参数有最大连接数、最小空闲连接数、连接超时、空闲超时和连接最大存活时间。

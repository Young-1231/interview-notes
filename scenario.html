秒杀与抢购 5高频 3

设计一个支持百万级用户的秒杀系统，整体思路是什么？高频

一句话结论：秒杀的本质是「海量请求抢极少库存」，设计核心是层层过滤流量、库存原子扣减、下单异步化，让真正到达数据库的请求数量级接近库存数。

1. 先澄清需求

  • 库存多少、参与人数多少、峰值 QPS 预估；是否限购（一人一单）；下单后多久必须支付；对超卖零容忍还是可以少卖。

2. 分层设计（从外到内逐层削减流量）

  • 前端 / 客户端：页面静态化、静态资源走 CDN；按钮在开始前置灰、点击后置灰防重复提交；验证码或答题把瞬时峰值拉平；秒杀地址动态生成（开始时才下发带签名的 path），防止脚本提前刷接口。
  • 接入层：Nginx / 网关做 IP、用户维度限流，黑名单拦截刷子。
  • 应用层：服务无状态、水平扩容；本地缓存（Caffeine）存商品详情和售罄标记，售罄后直接在内存里拒绝；按用户做频率限制。
  • 缓存层：活动开始前把库存预热到 Redis，用 Lua 脚本原子完成「校验是否已购 + 判断库存 + 扣减 + 记录购买用户」。
  • 消息队列：Redis 扣减成功后发 MQ，立即返回「排队中」，由消费者异步创建订单，起到削峰填谷、保护数据库的作用。
  • 数据库层：库存用条件更新兜底，订单表建 (user_id, activity_id) 唯一索引兜底防重。

3. 关键权衡

  • Redis 预扣减和数据库最终扣减之间是最终一致：消费失败要回补 Redis 库存，并配合定时对账。
  • 下单成功但超时未支付：用延迟消息在 15 分钟（按业务定）后关单并回补库存。
  • 秒杀服务要与普通交易链路隔离部署，避免秒杀流量拖垮主站。

4. 要盯的瓶颈

  • Redis 单个库存 key 是热点 key，必要时把库存拆成多个分段 key；数据库热点行更新是写入瓶颈；MQ 堆积要监控消费速率。

秒杀如何防止超卖和一人多单？高频

一句话结论：Redis 原子预扣减挡住绝大多数请求，数据库条件更新 + 唯一索引做最终兜底，任何一层都不能用「先查再改」的非原子写法。

1. Redis 层：Lua 脚本原子扣减

-- KEYS[1]=stock:{sku}  KEYS[2]=bought:{sku}  ARGV[1]=userId
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return -1 end  -- 已购买
local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
if stock <= 0 then return 0 end                                        -- 售罄
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1
  • Lua 脚本在 Redis 中单线程原子执行，不会出现两个请求同时读到库存 1 的情况。
  • Redis Cluster 下脚本涉及的多个 key 必须在同一个 slot，所以用 {sku} 这样的 hash tag。

2. 数据库层：条件更新（乐观锁思想）

UPDATE stock SET count = count - 1 WHERE sku_id = ? AND count > 0;
-- 影响行数为 0 即扣减失败，回滚事务

也可以用版本号 WHERE version = ?，但高并发下版本号冲突重试多，count > 0 这种条件更新更合适。

3. 防一人多单

  • 订单表建 (user_id, activity_id) 联合唯一索引，重复插入直接失败。
  • 接口层用请求唯一 ID 做幂等。

4. 其他保障

  • 限流和验证码减少无效请求；MQ 消费失败时回补 Redis 库存；超时未支付通过延迟消息关单回补库存；定时对账 Redis 与数据库库存。

百万级用户抢 10 个商品，缓存怎么设计？缓存里具体存什么？高频

一句话结论：只有 10 个人能成功，所以设计目标是尽早让 99.99% 的请求失败，缓存既存库存，也存各种「快速拒绝」用的标记。

缓存里存的内容

内容 Key 示例 结构 作用
库存 seckill:stock:{sku} String Lua 原子扣减
已购用户 seckill:bought:{sku} Set 一人一单校验
售罄标记 seckill:soldout:{sku} String，同时放 JVM 本地 售罄后直接拒绝，不再访问 Redis
商品静态信息 item:{sku} Hash / 本地缓存 名称、价格、图片，减少 DB 查询
活动信息 seckill:activity:{id} Hash 开始/结束时间、限购数量

设计要点

  • 预热：活动开始前把库存、商品信息、活动信息加载到 Redis 和本地缓存。
  • 本地售罄标记：某实例扣减返回售罄后，把标记写入本地内存，并通过 Redis Pub/Sub 或 MQ 广播给其他实例；之后所有请求在 JVM 内就被拒绝，Redis 压力骤降。
  • 令牌 / 资格前置：也可以只发放少量（例如库存的数倍）购买令牌，拿不到令牌的请求不进入扣减逻辑。
  • 商品详情是热点 key：放本地缓存，避免所有请求打到同一个 Redis 节点。
  • 落库：扣减成功的请求进 MQ 异步建单，活动结束后以数据库为准与 Redis 对账。

秒杀场景下，事务并行会有哪些问题？十万请求同时到达怎么办？

一句话结论：并发事务的核心问题是丢失更新、热点行锁竞争和死锁；十万请求同时到达时不能让它们直接竞争数据库，而要先在前面几层削峰。

事务并行的典型问题

  • 丢失更新：两个事务都先 SELECT 读到库存 1，再各自 UPDATE 成 0，导致超卖。解决：用 UPDATE ... SET count = count - 1 WHERE count > 0 原子条件更新，或 SELECT ... FOR UPDATE 加行锁。
  • 热点行锁竞争：所有事务更新同一行库存，InnoDB 行锁让它们串行排队，单行更新吞吐通常只有几百到一两千 TPS，大量线程等锁导致连接池耗尽、接口超时。
  • 死锁：多个事务以不同顺序锁多行（如库存行和账户行），InnoDB 会检测死锁并回滚其中一个。解决：固定加锁顺序、缩小事务范围。
  • 长事务：事务里夹杂 RPC、远程调用会让锁持有时间变长，放大竞争。

优化方向

  • 缩短事务，把热点行更新放在事务尽量靠后的位置，减少持锁时间。
  • 库存拆分成多行（分段库存），分散行锁。
  • 请求在 Redis 预扣减 + MQ 排队后再落库，让数据库只承受与库存数同量级的写。
  • MySQL InnoDB 默认隔离级别是可重复读（RR），一般不需要为秒杀调整隔离级别，正确性依赖原子更新和锁，而不是隔离级别。

十万请求同时到达：前端置灰和验证码 → 网关限流 → 本地售罄标记 → Redis 原子扣减 → MQ 异步建单，同时服务水平扩容，并对秒杀服务做独立部署和降级预案。

在 5000 人的群里发 50 个随机金额红包，要考虑哪些技术问题？

一句话结论：核心是金额怎么随机分配、并发抢怎么保证不超发不重复、资金怎么最终一致。

1. 金额分配算法

  • 金额统一用「分」的整数计算，避免浮点误差。
  • 常用二倍均值法：剩余金额 M、剩余个数 N 时，本次金额在 1 分到 2*M/N 分之间（不含上界）随机，最后一个直接拿剩余金额。每个红包至少 1 分，每次的期望约等于当前剩余均值，整体比较公平。
  • 两种时机：发红包时预先拆好放入 Redis List（抢时直接弹出，逻辑简单）；或抢时实时计算（需要原子性保护剩余金额和个数）。
  • 随机数用 SecureRandom 等不可预测的生成器，防止被推测。

2. 并发抢红包

  • Redis Lua 原子完成：判断用户是否已抢（Set / Hash）→ LPOP 弹出一个金额 → 记录用户与金额。List 为空即抢完。
  • 5000 人量级单个 key 能扛住；大群或超大并发时可在前面加限流和排队。

3. 一致性与幂等

  • 抢到后发 MQ，异步写领取记录、给用户钱包入账；(red_packet_id, user_id) 唯一索引保证不重复入账。
  • 红包状态机：进行中 → 已领完 / 已过期。
  • 24 小时未领完：延迟任务把剩余金额退回发送者。
  • 定时对账：领取总额 + 退款 = 红包总额。

4. 防刷与安全

  • 校验用户确实在群内；同一账号、设备、IP 限频；异常账号拉黑。
  • 完整记录发、抢、入账、退款日志，便于审计和客诉排查。

5. 降级

  • 抢红包与入账解耦：入账慢时用户仍可看到「已抢到」，后台异步重试；外部依赖统一设超时。

高并发与性能优化 3高频 1

如果接口 QPS 突增 10 倍，怎么保证系统性能？高频

回答时先澄清，再分层给方案。

1. 澄清

  • 是读多还是写多？是短时尖峰还是长期增长？目前瓶颈在哪（应用 CPU、DB、Redis、下游依赖）？压测数据如何？

2. 应急（尖峰）

  • 限流：网关 / Sentinel 按接口和用户维度限流，超出部分快速失败或排队，保护系统不被打垮。
  • 降级与熔断：关闭非核心功能（推荐、评论、积分），对不稳定下游熔断。
  • 扩容：无状态服务水平扩容，K8s HPA 自动扩缩容。

3. 长期优化

  • 缓存：多级缓存（Caffeine 本地缓存 + Redis），热点数据预热，CDN 和网关缓存静态资源。
  • 异步化：日志、通知、统计等非核心逻辑放到 MQ 异步处理。
  • 数据库：慢 SQL 优化和索引调整；读写分离分担读压力；写入或数据量成为瓶颈时分库分表。
  • 代码层：批量化（批量查询、批量写）、并行调用无依赖的下游、连接池和线程池调优、减少不必要的序列化和对象创建，JVM 参数和 GC 调优。

4. 要盯的瓶颈

  • 应用层通常容易扩，数据库和有状态组件最难扩，扩容前要确认 DB 连接数、Redis 单节点、MQ 分区数能否同步扩展；扩容后用全链路压测验证。

订单系统压力过大，经常超时，怎么优化？

一句话结论：先定位瓶颈再对症下药，不要直接上分库分表。

1. 定位

  • 监控：CPU、内存、GC 频率与停顿、线程池活跃数与队列长度、DB 连接池使用率。
  • 链路追踪（SkyWalking、Zipkin 等）找出耗时最长的环节：是慢 SQL、锁等待、下游 RPC，还是 Full GC。
  • 数据库：慢查询日志、SHOW PROCESSLIST、information_schema.innodb_trx 和锁等待信息。

2. 常见对策

  • SQL 与索引：补索引、改写慢 SQL、避免大事务和长事务。
  • 缩短主链路：下单主流程只做校验、扣库存、写订单；发券、积分、通知、物流等用 MQ 异步执行。
  • 缓存：商品、用户、配置等读多写少的数据放 Redis。
  • 资源隔离：线程池按业务隔离，合理设置核心线程数、队列长度和拒绝策略，避免任务堆积。
  • 保护：Sentinel / Resilience4j 限流熔断，超时快速失败。
  • 扩容与拆分：应用实例和从库扩容；单表数据量过大或写入成为瓶颈时再分库分表、冷热数据归档。

订单表每秒几千条写入，怎么设计才能同时支持高并发插入和实时查询？

一句话结论：写入路径保证顺序写和批量写，查询路径按查询维度做异构——用户维度查 MySQL 分片，复杂多条件查询走 ES。

1. 写入侧

  • 主键用趋势递增的分布式 ID（雪花算法），保证 B+ 树顺序追加，减少页分裂；不要用 UUID 做主键。
  • 控制二级索引数量，每多一个索引就多一份写放大。
  • 批量插入（多值 INSERT）、短事务；必要时用 MQ 缓冲，由消费者批量落库，削平峰值。
  • 单机写入到瓶颈后水平分库分表：分片键选 user_id，订单号里嵌入 user_id 的分片基因，这样按订单号也能直接定位分片。

2. 查询侧

  • 按用户 / 订单号查：直接路由到分片，配合 Redis 缓存热点订单和用户最近订单列表。
  • 按商家、状态、时间等多条件查：通过 Canal 订阅 binlog 或 MQ 把订单同步到 Elasticsearch，复杂查询走 ES。注意 ES 是近实时（默认 1 秒 refresh），需要「写后立即读」的场景（如下单后跳详情页）直接查主库。
  • 读写分离：普通读走从库，注意主从延迟。

3. 数据治理

  • 冷热分离：历史订单归档到归档库或 HBase、对象存储，在线表只保留近期数据。

4. 总结

维度 策略
写入 递增主键 + 批量写 + MQ 缓冲 + 分库分表
查询 分片路由 + Redis 缓存 + ES 异构索引 + 读写分离
一致性 binlog / MQ 同步，最终一致
容量 冷热分离、历史归档

限流 3高频 0

令牌桶和漏桶算法的原理是什么？怎么实现？

一句话结论：令牌桶限制平均速率但允许一定突发，漏桶强制匀速输出；另外还有固定窗口、滑动窗口两种计数类算法。

算法 原理 突发流量 典型实现
固定窗口 每个时间窗口计数，超阈值拒绝 窗口边界可能出现 2 倍流量 Redis INCR + EXPIRE
滑动窗口 把窗口切成多个小格或记录请求时间戳，按滑动区间统计 比固定窗口平滑 Redis ZSet、Sentinel 的滑动窗口统计
漏桶 请求进入队列，按固定速率流出处理，队列满则拒绝 不允许，输出严格匀速 Nginx limit_req、Sentinel 匀速排队
令牌桶 以速率 r 往容量为 N 的桶里放令牌，请求拿到令牌才执行 允许，最多一次消耗 N 个积累的令牌 Guava RateLimiter、Spring Cloud Gateway Redis 限流

令牌桶的实现要点：不需要定时线程往桶里加令牌，而是惰性计算——每次请求时根据「当前时间 - 上次补充时间」× 速率算出应补充的令牌数，tokens = min(capacity, tokens + 新增)，够用就扣减放行，否则拒绝。

怎么选

  • 需要容忍合理突发（如接口限流）用令牌桶。
  • 需要保护下游、严格匀速（如调用第三方支付、短信通道）用漏桶。

单机限流和分布式限流有什么区别？分布式限流系统怎么实现？

一句话结论：单机限流只控制单个实例，分布式限流用共享存储（通常是 Redis）统一计数，控制整个集群的总流量。

区别

维度 单机限流 分布式限流
实现 内存计数（Guava RateLimiter、Sentinel 单机模式） Redis + Lua、Sentinel 集群流控、网关限流
性能 纳秒级，无网络开销 每次请求多一次网络往返
准确性 只能把总阈值按实例数平摊，负载不均或扩缩容时不准 精确控制集群总 QPS
依赖 无 依赖 Redis 可用性，需考虑 Redis 故障时的降级

分布式限流系统的设计

  • 限流维度：key 设计为 rate_limit:{resource}:{identity}，resource 是接口或功能（api_pay、sms_send），identity 是用户、IP、设备、租户或 global。同一个请求可以同时校验多级 key（用户级 + 接口全局级）。
  • 原子性：「读状态 → 计算 → 写回」必须放进 Lua 脚本，保证原子。
  • 扩展性：Redis Cluster 按 key 分片，不同限流维度自然分散到不同节点；超热的全局 key 可以拆成多个子 key 或改为「本地预取令牌」。
  • 规则管理：限流阈值放配置中心动态下发。
  • 容错：Redis 不可用时降级为单机限流，而不是直接放行或全部拒绝。
  • 分层：网关层做粗粒度限流（IP、接口），应用层做业务维度的细粒度限流。

用 Redis 实现一个令牌桶限流工具

一句话结论：用 Hash 保存 tokens 和 last_ms 两个字段，Lua 脚本里惰性补充令牌并扣减，保证原子性。

-- KEYS[1]: 限流 key   ARGV: capacity, rate(每秒令牌数), now_ms, requested
local capacity  = tonumber(ARGV[1])
local rate      = tonumber(ARGV[2])
local now       = tonumber(ARGV[3])
local requested = tonumber(ARGV[4])

local data   = redis.call('HMGET', KEYS[1], 'tokens', 'last_ms')
local tokens = tonumber(data[1]) or capacity
local last   = tonumber(data[2]) or now

-- 惰性补充令牌（保留小数，避免精度丢失）
local delta = math.max(0, now - last)
tokens = math.min(capacity, tokens + delta * rate / 1000)

local allowed = 0
if tokens >= requested then
  tokens = tokens - requested
  allowed = 1
end

redis.call('HSET', KEYS[1], 'tokens', tokens, 'last_ms', now)
-- 过期时间取「桶从空到满所需时间」的两倍，避免冷 key 长期占内存
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 1000) * 2)
return allowed

// Spring Data Redis 调用
DefaultRedisScript<Long> script = new DefaultRedisScript<>(LUA, Long.class);
Long ok = redisTemplate.execute(script, List.of("rate_limit:api_pay:user_123"),
        "100", "10", String.valueOf(System.currentTimeMillis()), "1");
boolean allowed = ok != null && ok == 1L;

注意点

  • now_ms 由调用方传入时，各实例时钟要同步（NTP）；Redis 5 起脚本默认按效果复制，也可以在脚本内用 TIME 命令取 Redis 服务器时间，消除各实例的时钟差异。
  • 生产中可直接用 Redisson 的 RRateLimiter、Sentinel 或 Spring Cloud Gateway 的 RequestRateLimiter，不必重复造轮子。
  • 被限流的请求要返回明确的错误码（如 HTTP 429），方便前端提示和重试。

线上 CPU 100% 或者出现 OOM，怎么排查？高频

CPU 100%

  1. top 找到 CPU 占用最高的 Java 进程 PID。
  2. top -Hp <pid> 找到占用最高的线程 TID。
  3. printf "%x\n" <tid> 转成十六进制。
  4. jstack <pid> | grep -A 30 'nid=0x<十六进制tid>' 查看该线程栈，定位到具体代码。
  5. 常见原因：死循环、正则回溯、大量计算；如果是 GC 线程，用 jstat -gcutil <pid> 1000 看是否频繁 Full GC，转为内存问题。也可用 Arthas thread -n 3 直接列出最忙线程。

OOM

  1. 先看报错类型：Java heap space（堆不足或泄漏）、GC overhead limit exceeded、Metaspace（动态生成类过多）、Direct buffer memory（堆外泄漏）、unable to create native thread（线程过多）。
  2. 提前配置 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path 自动 dump；手动 jmap -dump:live,... 会触发 Full GC，线上慎用。
  3. 用 MAT 看 Dominator Tree 和 Leak Suspects，找到大对象及其 GC Roots 引用链。
  4. 常见原因：无界缓存、无界队列（LinkedBlockingQueue 任务堆积）、一次加载过多数据、ThreadLocal 未 remove、连接未关闭。

通用流程：先止血（重启、扩容、摘流量，保留现场 dump 和线程栈）→ 再定位 → 修复后补监控告警。

调用外部供应商的 HTTP 接口很慢（平均 2 秒）且偶尔超时，如何避免拖垮整个应用线程池？

一句话结论：超时 + 隔离 + 熔断降级三件套，必要时把同步调用改成异步。

  1. 超时设置：HTTP 客户端分别设置连接超时（如 1 秒）和读取超时（略高于接口 P99，例如 3 秒），绝不能使用默认的无限等待。
  2. 线程池隔离（舱壁模式）：给该供应商单独一个有界线程池（固定最大线程数和有界队列，拒绝策略快速失败），即使它全部卡住，也只占满自己的池子，不会耗尽 Tomcat 工作线程。也可以用信号量限制并发数。
  3. 异步化：CompletableFuture.supplyAsync(task, vendorPool).orTimeout(3, TimeUnit.SECONDS)（orTimeout 为 JDK 9+）；如果业务不需要同步拿结果，直接改成 MQ 异步处理再回调通知。
  4. 熔断降级：用 Resilience4j 或 Sentinel（Hystrix 已停止维护），失败率或慢调用比例超阈值时熔断，直接走降级逻辑（缓存数据、默认值、提示稍后再试），一段时间后半开探测恢复。
  5. 重试要克制：只对幂等请求、可重试错误（超时、5xx）重试，次数少（1～2 次）并加指数退避和随机抖动，否则重试会放大压力。
  6. 缓存：对非实时数据缓存结果，减少调用次数。
  7. 限流：控制对供应商的调用频率，避免超出对方配额。

补充：JDK 21 的虚拟线程能降低阻塞等待的线程成本，但并不能替代超时和熔断，下游慢的问题仍然存在。

你是 A 模块的开发者，要调用不稳定的 B 模块，该怎么处理？

一句话结论：短期在 A 侧做防御，中期做观测，长期推动 B 治理或降低对 B 的依赖。

短期：防御性调用

  • 超时：每次调用设严格超时，防止 A 被长时间阻塞。
  • 重试：只对可重试错误（网络超时、503）做指数退避重试，最多 2～3 次，并保证接口幂等。
  • 熔断：Resilience4j / Sentinel 监控失败率，超过阈值（如 50%）暂时熔断，直接走降级路径，避免持续调用加重 B 的负担。
  • 降级：返回缓存的上一次成功结果、默认值或简化功能（如推荐服务挂了返回静态热门列表）。
  • 隔离：B 的调用使用独立线程池或信号量，故障不扩散。
  • 异步解耦：能异步的调用改为 MQ，B 恢复后再消费。

中期：监控与数据

  • 记录调用成功率、耗时分布、错误类型、熔断状态，接入 Prometheus + Grafana 告警；用数据定位 B 的故障模式（特定参数、特定时间段）。

长期：根本改进

  • 把监控数据同步给 B 团队推动修复，约定 SLA。
  • 在 A 中通过适配层封装对 B 的依赖，必要时可以切换到备用实现或冗余实例。
  • 弱依赖化：梳理 B 在 A 业务中是强依赖还是弱依赖，弱依赖的失败不应影响 A 的主流程。

分布式系统中如何保证接口幂等，防止用户重复下单？

一句话结论：幂等的本质是给每次业务操作一个唯一标识，并让「判重 + 执行」具备原子性，最终一定要有数据库层的兜底。

方案 做法 适用
数据库唯一索引 订单号或 (user_id, biz_id) 建唯一索引，重复插入报 DuplicateKeyException 后按「已处理」返回 新增类操作，最可靠的兜底
Token 机制 进入下单页先获取 token 存 Redis；提交时用 Lua 或 DEL 的返回值原子校验并删除，删除成功才继续 防表单重复提交
请求唯一 ID + 去重 客户端生成 requestId，服务端 SET requestId 1 NX EX 600，设置失败说明重复 MQ 消费、接口重试
去重表 单独一张表，以业务唯一键为主键，与业务操作放在同一事务插入 跨表业务、消息消费
状态机 + 条件更新 UPDATE order SET status='PAID' WHERE id=? AND status='UNPAID'，影响行数 0 即重复 更新类操作
分布式锁 对业务 key 加锁，防止同一时刻并发处理 配合其他方案，解决并发而非重复

注意点

  • Token 校验和删除必须原子，否则两个并发请求可能都校验通过。
  • Redis 判重可能因宕机丢失记录，所以关键业务仍要靠唯一索引或状态机兜底。
  • 查询和删除天然幂等；UPDATE x = x + 1 这种相对更新不幂等，要改为带条件的更新或配合去重。
  • 前端按钮置灰只能改善体验，不能替代后端幂等。

网络抖动或用户疯狂点击，支付接口收到两次相同请求，如何保证不扣两次钱？

一句话结论：每笔支付有唯一支付单号，「创建支付单」靠唯一索引防重，「状态变更」靠状态机条件更新防重，调用第三方渠道时再利用渠道侧的幂等。

  1. 唯一支付单号：同一订单发起支付时，先按订单号查询或创建支付单（order_id 唯一索引），重复请求拿到的是同一张支付单，而不是新建一张。
  2. 状态机 + 条件更新：
    UPDATE pay_order SET status = 'PAYING' WHERE pay_no = ? AND status = 'INIT';
    只有影响行数为 1 的请求才继续扣款，另一个请求直接返回「处理中」或查询已有结果。
  3. 扣款流水唯一约束：账户扣款时写流水表，pay_no 唯一索引，扣余额和插流水在同一事务里，重复扣款会因唯一键冲突回滚。
  4. 第三方渠道幂等：支付宝、微信等渠道以商户订单号（out_trade_no）做幂等，同一单号不会重复扣款。
  5. 并发控制：可对支付单号加分布式锁，避免两个请求同时走到调用渠道这一步；但锁只是减少并发，正确性仍靠上面的状态机和唯一约束。
  6. 结果不确定时查询，而不是重试扣款：调用渠道超时，应该主动查询渠道支付结果或等异步回调，回调处理同样要幂等（按状态判断，已支付直接返回成功）。
  7. 对账：每日与渠道对账，发现重复扣款自动退款。

如何设计一个分布式锁？基于 Redis 实现要注意哪些点？

一句话结论：Redis 分布式锁的要点是加锁原子（SET NX PX）、解锁校验持有者（Lua）、锁过期续期（看门狗），并清楚它在主从切换时可能失效。

加锁与解锁

SET lock:order:123 <uuid:threadId> NX PX 30000

-- 解锁：只有持有者才能删除
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0

注意点

  • 原子加锁：SETNX 和 EXPIRE 分两步执行时，中间宕机会导致锁永不过期，必须用一条 SET NX PX。
  • 防误删：value 写唯一标识，解锁时比较后删除，并且「比较 + 删除」要放在 Lua 中原子执行。
  • 过期时间与续期：业务执行时间超过锁过期时间会导致锁提前释放。Redisson 在不指定 leaseTime 时启用看门狗，默认锁超时 30 秒，每 10 秒续期一次；进程宕机后续期停止，锁自然过期。
  • 可重入：Redisson 用 Hash 结构，field 是 UUID:threadId，value 是重入次数，加锁 +1、解锁 -1，为 0 时删除。
  • 获取失败的处理：不要无限自旋，使用超时等待（tryLock(waitTime, leaseTime, unit)）；Redisson 基于 Pub/Sub 通知等待者，减少空轮询。
  • 主从切换丢锁：主节点加锁后还没同步到从节点就宕机，新主上没有这把锁，另一个客户端可以再次加锁。RedLock 通过向多数独立节点加锁缓解，但仍有时钟漂移和 GC 停顿的争议；需要强一致时用 ZooKeeper（临时顺序节点）或 etcd（lease + revision），或者在资源侧使用 fencing token（单调递增的版本号）拒绝过期持有者的写入。
  • 锁粒度：锁具体的业务 key（如订单 ID），不要锁全局。

处理上亿流量的分布式锁，与 ToB 场景相比需要多考虑什么？

一句话结论：ToC 海量流量下，核心思路是能不用锁就不用锁，必须用时把锁拆细、持有时间缩短、获取失败快速返回；ToB 场景并发低，更看重锁的强一致和长任务支持。

ToC 上亿流量要额外考虑的点

  • 避免单点和热点：使用 Redis Cluster，锁 key 按业务 ID 分散到不同分片；单个爆款商品的锁是热点 key，可以把库存拆成 N 段，每段一把锁，请求随机或按用户哈希选择一段。
  • 能用原子操作就不用锁：扣库存直接用 DECR / Lua 脚本原子完成，比「加锁 → 查 → 改 → 解锁」少多次网络往返。
  • 缩小锁范围和持有时间：只锁关键的扣减步骤，日志、通知等非关键路径异步化，不在锁内做 RPC。
  • 获取失败快速失败：不要大量线程自旋重试，否则形成重试风暴；失败直接返回「活动太火爆」，或者带随机抖动的有限次退避重试，或者进入 MQ 排队。
  • 前置过滤：限流、令牌、本地售罄标记先挡掉大部分请求，让抢锁的请求量级下降。
  • 故障兜底：Redis 主从切换可能丢锁，数据库唯一索引和条件更新必须兜底，保证即使锁失效也不会出现资损。
  • 成本：看门狗续期在海量锁时会产生大量续期请求，短任务显式指定较短的 leaseTime。

ToB 场景的侧重点

  • QPS 低但业务长（审批、批量任务、报表），更关注正确性和长时间持有，常用 ZooKeeper、etcd 或数据库行锁 / 唯一键；还要考虑锁的可观测（谁持有、持有多久）和人工释放。

如何设计一个全局唯一的分布式 ID 生成器？高频

一句话结论：常用方案是雪花算法和号段模式，生产中多用美团 Leaf、百度 UidGenerator 这类成熟实现；关键诉求是全局唯一、趋势递增、高可用、高性能。

方案 原理 优点 缺点
UUID 128 位随机或基于时间 本地生成，无依赖 36 字符太长、无序，做 InnoDB 主键会频繁页分裂
数据库自增 单库 AUTO_INCREMENT，多库设起始值和步长 简单、有序 单点瓶颈，扩容要重新规划步长
号段模式 每次从数据库取一段 ID（如 1000 个）缓存在内存中发放 数据库压力降为原来的千分之一，趋势递增 依赖 DB；Leaf 用双 buffer 在号段用到一定比例时异步预取下一段
Redis INCR 原子自增 性能高 依赖 Redis 持久化，宕机可能重复
雪花算法 64 位 = 1 位符号 + 41 位毫秒时间戳 + 10 位机器 ID + 12 位序列号 本地生成、趋势递增、单机每毫秒 4096 个 依赖时钟，需要处理时钟回拨和机器 ID 分配

雪花算法细节

  • 41 位毫秒时间戳约可用 69 年（相对自定义纪元）；10 位机器 ID 通常拆成 5 位数据中心 + 5 位机器，共 1024 个节点；12 位序列号每毫秒 4096 个，用完则等待下一毫秒。
  • 时钟回拨：回拨较小（如几毫秒）时等待追上；回拨较大时拒绝服务并告警，或切换备用 workerId；也可以使用「借用未来时间」的方案（如百度 UidGenerator 的 CachedUidGenerator）。
  • 机器 ID 分配：靠 ZooKeeper 或数据库注册分配（Leaf-snowflake 用 ZooKeeper 持久顺序节点分配 workerId），避免手工配置冲突。

注意：雪花 ID 暴露时间和大致的业务量，对外暴露的订单号可以在此基础上再做混淆。

如何实现一个高性能的延迟任务系统？

一句话结论：根据量级和可靠性选型，单机用时间轮，分布式常用 Redis ZSet 或 MQ 延迟消息，海量且要求可靠时用「数据库持久化 + 内存时间轮」分层设计。

方案 原理 优缺点
JDK DelayQueue 堆按到期时间取出 简单，但单机、重启丢失
时间轮（Netty HashedWheelTimer、Kafka 分层时间轮） 环形数组 + 指针按 tick 转动，任务挂到对应槽位 增删 O(1)，适合海量任务；精度受 tick 限制，单机内存
Redis ZSet score 为到期时间戳，轮询 ZRANGEBYSCORE key 0 now LIMIT 0 100 性能好；取出和删除要 Lua 原子完成（或看 ZREM 返回值），否则多实例重复执行
RocketMQ 延迟消息 4.x 只有 18 个固定级别；5.x 支持任意时间 可靠、可扩展，延迟有上限
RabbitMQ TTL + 死信，或 delayed-message 插件 TTL 方案同队列按顺序过期，不同延迟要分队列
数据库扫表 按 execute_time 建索引定时扫描 最可靠，但延迟和 DB 压力大

高性能设计要点

  • 分层存储：任务全部持久化到数据库，调度器把未来几分钟到期的任务加载到内存时间轮精准触发。
  • 分片：任务按 ID 哈希到多个分片，每个调度实例负责一部分，避免热点和重复调度。
  • 调度与执行分离：调度线程只投递到 MQ 或线程池，不执行业务。
  • 可靠性：至少一次投递 + 执行端幂等，失败退避重试，超限进死信告警。

缓存与典型系统设计 3高频 1

设计一个缓存系统，从高性能、持久化、一致性的角度怎么考虑？

一句话结论：高性能靠多级缓存和合理的数据结构，持久化靠 Redis 的 RDB/AOF 加主从副本，一致性靠 Cache-Aside「先更新数据库再删缓存」并用 binlog 订阅兜底，同时处理好穿透、击穿、雪崩。

1. 澄清需求：数据量、读写比、能容忍多久的不一致、缓存丢失是否可接受。

2. 高性能

  • 多级缓存：L1 Caffeine（W-TinyLFU）+ L2 Redis Cluster（16384 个哈希槽分片）。L1 放极热、少变的数据，TTL 更短。
  • 数据结构：按字段访问用 Hash，避免大 key，用紧凑序列化；MGET、Pipeline 减少往返。
  • 淘汰策略：设置 maxmemory 和 allkeys-lru / allkeys-lfu（LFU 自 Redis 4.0 起支持）。

3. 持久化与高可用

  • RDB 恢复快但丢最后一次快照后的数据；AOF everysec 最多丢约 1 秒；Redis 4.0 起支持混合持久化，Redis 7.0 起为 Multi Part AOF。
  • 主从 + Sentinel 或 Cluster 自动故障转移，复制异步，切换可能丢少量数据。
  • 数据库才是最终真相；Write-Behind 必须先写 MQ 或 WAL 保证不丢。

4. 一致性

  • Cache-Aside：读未命中回填并设 TTL；写时先更新数据库再删除缓存（更新缓存有并发覆盖顺序问题）。
  • 删除失败或并发回填旧值：延迟双删，或 Canal 订阅 binlog 异步删除，失败进 MQ 重试。
  • 库存、余额等强一致需求不依赖缓存读。

5. 典型问题

问题 现象 方案
穿透 查询不存在的数据，每次都打到 DB 缓存空值（短 TTL）、布隆过滤器、参数校验
击穿 热点 key 过期瞬间大量请求打到 DB 互斥锁重建缓存、逻辑过期（后台异步刷新）、热点 key 不过期
雪崩 大量 key 同时过期或 Redis 宕机 TTL 加随机值、多级缓存、Redis 高可用、限流降级

6. 监控：命中率、延迟、内存、大 key / 热 key、淘汰数。

如何设计一个短链系统（短网址服务）？高频

一句话结论：核心是为长链接生成唯一短码，再通过缓存 + 302 重定向完成高性能跳转。

1. 澄清需求

  • 每天生成多少条、读写比（通常读远多于写，如 100:1）、短码长度、是否需要过期、是否需要统计点击、同一长链接是否返回同一短码。

2. 短码生成

  • 发号器 + Base62（推荐）：用分布式 ID（号段模式、Redis INCR 或雪花算法）得到唯一整数，转成 [0-9a-zA-Z] 62 进制。7 位 Base62 约 3.5 万亿（62^7），容量充足。自增 ID 转出来的短码可被遍历，可先对 ID 做可逆混淆（如乘法逆元、Feistel 置换）再编码。
  • 哈希：对长链接做 MurmurHash 等哈希后取 Base62，有冲突概率，需要在插入时用唯一索引检测冲突，冲突则加盐重新哈希；可以用布隆过滤器快速判断短码是否已存在。
  • 同一长链接去重：如需返回同一短码，对长链接（或其哈希）建索引查询，或用 Redis 记录长链接到短码的映射。

3. 存储

  • MySQL 表：short_code（唯一索引）、long_url、create_time、expire_time；数据量大时按短码分库分表。
  • Redis 缓存 short_code → long_url，热点短码放本地缓存。

4. 跳转

  • 收到请求查本地缓存 → Redis → MySQL，返回重定向。
  • 301 还是 302：301 永久重定向会被浏览器缓存，后续请求不再经过服务端，节省压力但无法统计点击；302 临时重定向每次都会请求服务端，便于统计和修改目标，大多数短链服务用 302。
  • 不存在的短码缓存空值或用布隆过滤器拦截，防止穿透。

5. 其他

  • 统计：访问日志异步写 MQ，再聚合到 ClickHouse 等分析库，不阻塞跳转。
  • 安全：生成接口限流、恶意链接检测与黑名单。
  • 过期：记录过期时间，访问时校验，定期清理。

千万级用户表的深分页（如跳过 100 万条取 10 条）怎么优化？

一句话结论：LIMIT 1000000, 10 慢在要先扫描并丢弃前 100 万行（且每行可能都要回表），优化思路是减少回表或用游标代替偏移量。

1. 延迟关联（子查询走覆盖索引）

SELECT u.* FROM user u
JOIN (SELECT id FROM user ORDER BY id LIMIT 1000000, 10) t ON u.id = t.id;

子查询只扫描索引拿 id，不回表，最后只对 10 行回表。仍需扫描 100 万个索引项，但比回表 100 万次快很多。

2. 游标分页 / Keyset 分页（推荐）

SELECT * FROM user WHERE id > #{lastId} ORDER BY id LIMIT 10;

记住上一页最后一条的 id，直接通过索引定位，与页码无关，性能恒定。按非唯一字段排序时用组合条件：WHERE (create_time, id) > (?, ?) ORDER BY create_time, id。缺点是不能随机跳页，适合「下一页」「无限滚动」。

3. 子查询定位起点

SELECT * FROM user WHERE id >= (SELECT id FROM user ORDER BY id LIMIT 1000000, 1)
ORDER BY id LIMIT 10;

仅在 id 连续递增、按 id 排序时适用。

4. 业务限制

  • 限制最大可翻页数（如最多 100 页），引导用户用搜索条件缩小范围。
  • 搜索类场景用 Elasticsearch：from + size 默认受 max_result_window = 10000 限制，深分页使用 search_after（配合 PIT）。

联合索引 (a, b, c)，SQL 有时很快有时全表扫描，哪些情况会导致索引失效？

一句话结论：一类是写法导致索引用不上，另一类是优化器基于成本估算主动放弃索引；「时快时慢」往往是后者，与传入参数的数据分布有关。

写法导致的失效

  • 不满足最左前缀：只查 b、c 无法常规使用索引（MySQL 8.0.13+ 特定条件下可用 Skip Scan）。a and c 只有 a 用于定位，c 靠索引下推过滤。
  • 范围查询之后的列不能用于定位：a > 10 AND b = 5 中 b 不能缩小扫描范围，但 MySQL 5.6+ 的索引下推（ICP）可在索引层过滤 b。
  • 对索引列用函数或运算：DATE(a) = ...、a + 1 = 10。MySQL 8.0.13+ 可建函数索引。
  • 隐式类型转换：varchar 列用数字比较（a = 123）会失效；整数列用字符串比较不影响。
  • LIKE 以通配符开头：'%abc' 失效，'abc%' 可用。
  • OR 中有非索引列、!=、NOT IN 等过滤性差的条件，常走全表扫描（不是绝对失效）。

优化器成本选择导致的「时快时慢」：不同参数命中行数差别很大，估算回表行数占比较高（经验上二三成以上）时优化器认为全表扫描更便宜；统计信息不准也会误判，可执行 ANALYZE TABLE。

排查手段：EXPLAIN 看 type、key、rows、Extra；optimizer_trace 看成本计算；必要时 FORCE INDEX 或改为覆盖索引。

(name, school) 建唯一索引和普通联合索引，在写入场景下哪个效率更高？高频

一句话结论：普通索引写入更快，主要原因是普通二级索引可以使用 Change Buffer，而唯一索引每次写入都必须读取索引页做唯一性校验。

原因

  • 唯一性校验需要读页：插入时唯一索引必须确认不存在相同的 (name, school)，所以要把对应的索引页读入 Buffer Pool；如果页不在内存中，就要产生一次随机磁盘 I/O。
  • Change Buffer 只对非唯一二级索引生效：普通索引的页不在内存时，InnoDB 可以把修改先记录在 Change Buffer 中，之后在页被读取或后台 merge 时再合并，把随机 I/O 变成延迟批量写。唯一索引已经读了页，没法利用这个优化。
  • 加锁更多：可重复读隔离级别下，唯一索引插入遇到重复或已标记删除的记录时，会加共享的 next-key lock 做检查，并发插入时更容易锁等待甚至死锁。

场景差异

  • 数据页大多已经在 Buffer Pool 中时，两者差距很小（只多一次内存中的比较）。
  • 写多读少、表很大、索引页大多不在内存中（如日志、流水类）时，普通索引的优势明显。
  • 写入后马上就要读这条数据时，Change Buffer 会立刻 merge，收益不大。

选型：业务上需要保证唯一（如同一学校不能有重名账号）时必须用唯一索引，这是数据正确性的最后一道防线，不能为写入性能牺牲；如果唯一性由上游保证，且以写为主，可以用普通索引。

千万级群聊表因逻辑删除越来越大，如何物理删除这些数据？写出 SQL

一句话结论：先备份或归档，再在低峰期按主键范围小批量删除，避免一条大 DELETE 造成长事务、锁冲突和主从延迟；删除比例很高时，直接「新建表拷贝有效数据再切换」更快。

考虑点

  • 备份 / 归档：删除前把数据导出到归档库或冷存储，以备追溯。
  • 关联数据：群成员、群消息等关联表要一起清理，注意顺序和一致性。
  • 分批：单次删除 1000～5000 行，批次间短暂 sleep，监控主从延迟和数据库负载；每批是独立的小事务。
  • 按主键范围扫描：按 id 递增推进，避免 WHERE is_deleted = 1 LIMIT n 每次从头扫描已处理过的区间（is_deleted 区分度低，单独建索引意义不大）。
  • 空间回收：InnoDB 删除后表空间不会自动缩小，需要 OPTIMIZE TABLE 或 ALTER TABLE ... ENGINE=InnoDB 重建（MySQL 5.6+ 支持 Online DDL，但大表重建仍耗时耗 I/O，低峰执行，或使用 gh-ost / pt-online-schema-change）。
  • 长期治理：定时任务定期清理，或按时间分区表直接 DROP PARTITION。

-- 1. 取本批次的 id 上界（返回 NULL 说明已处理完）
SELECT MAX(id) FROM (
  SELECT id FROM group_chat WHERE id > ? ORDER BY id LIMIT 5000
) t;

-- 2. 按主键范围删除本批次中被逻辑删除的数据
DELETE FROM group_chat
WHERE id > ? AND id <= ? AND is_deleted = 1;

也可以简单写成每次删除固定数量（需要 (is_deleted, id) 联合索引才能高效定位）：

DELETE FROM group_chat WHERE is_deleted = 1 ORDER BY id LIMIT 1000;

注意：MySQL 的 LIMIT 不能直接写用户变量（如 LIMIT @batch_size），需要写常量或用预处理语句传参。

删除比例很高时的方案

CREATE TABLE group_chat_new LIKE group_chat;
INSERT INTO group_chat_new SELECT * FROM group_chat WHERE is_deleted = 0;  -- 大表同样要分批拷贝
RENAME TABLE group_chat TO group_chat_old, group_chat_new TO group_chat;

有 100 亿个 URL，怎么找出重复的 URL？

一句话结论：内存放不下就分治——按哈希把 URL 拆成若干小文件，相同 URL 必然落在同一个文件里，再逐个文件用 HashMap 统计；允许误判时可以用布隆过滤器。

1. 估算：每个 URL 平均按 64 字节算，100 亿条约 640 GB，单机内存放不下。

2. 方案一：哈希分片 + 逐个统计（精确）

  • 顺序读取，按 hash(url) % 1000 写入 1000 个小文件，每个约 640 MB；相同 URL 哈希值相同，一定在同一个文件中。
  • 逐个读入小文件，用 HashMap<String, Integer> 统计次数，输出次数 ≥ 2 的 URL；文件之间没有交集，不需要跨文件合并。
  • 如果某个小文件因数据倾斜仍然过大，换一个哈希函数对它再拆分。
  • 多机时就是 MapReduce / Spark 的思路：map 阶段按 URL 分区，reduce 阶段同一 URL 聚合计数（groupBy(url).count().filter(cnt > 1)）。

3. 方案二：布隆过滤器（近似）

  • 顺序遍历，先查布隆过滤器：不存在则加入；存在则认为重复。
  • 内存估算：误判率 1% 时每个元素约需 9.6 bit，100 亿个元素约 12 GB；误判率 0.1% 约 18 GB。
  • 缺点：有误判（把不重复的判为重复，不会漏判），无法精确计数；适合允许少量误判的去重场景，比如爬虫 URL 去重。

4. 变种

  • 找两个文件的公共 URL：两个文件用同一个哈希函数分片，只需比较编号相同的小文件对。
  • 找出现次数 Top K：分片统计后每个文件用大小为 K 的小顶堆取局部 Top K，再合并所有局部结果得到全局 Top K。

海量数据中找出现频率最高的 Top K（如热门搜索词）怎么做？

一句话结论：分治统计 + 小顶堆；实时场景用流式计算或 Redis ZSet。

离线

  1. 数据量超过内存时，先按 hash(word) % N 分片，保证同一个词在同一个分片。
  2. 每个分片用 HashMap 统计词频。
  3. 每个分片维护大小为 K 的小顶堆：堆未满直接放入；堆满后新元素频率大于堆顶才替换堆顶。复杂度 O(n log K)。
  4. 合并所有分片的局部 Top K，再取一次 Top K。

为什么求 Top K 大用小顶堆：堆顶是当前 K 个里最小的，新元素只需和堆顶比较即可决定是否入堆，内存只需要 K 个元素。

实时

  • 流式计算（Flink）按滑动窗口计数，再求 Top K。
  • 小规模可以直接用 Redis ZSet：ZINCRBY hot_words 1 word，ZREVRANGE hot_words 0 K-1 WITHSCORES 取 Top K；注意单 key 过大时按时间分 key 并合并。
  • 允许近似时用 Count-Min Sketch + 小顶堆，内存固定。

一个很大的数组在内存中放不下，如何对其整体排序？

一句话结论：使用外部排序：分块内部排序生成有序小文件，再用小顶堆做 K 路归并。

1. 分块排序

  • 按可用内存大小（例如 1 GB）把数据切成 N 块，逐块读入内存，用快速排序等算法排序后写入临时文件，得到 N 个有序文件。

2. K 路归并

  • 每个有序文件打开一个读缓冲区，各取第一个元素放入大小为 K 的小顶堆（元素记录值和来源文件）。
  • 每次弹出堆顶写入输出文件，再从该元素所在文件读取下一个元素入堆，直到所有文件读完。
  • 每个元素的出入堆代价是 O(log K)，总复杂度 O(n log K)。

3. 多轮归并

  • 块数 N 很大时，同时打开的文件数和缓冲区受限，分多轮归并：每轮 K 个一组合并，生成 ⌈N/K⌉ 个更大的有序文件，重复直到只剩 1 个。例如 N=100、K=10，两轮完成。

4. 优化

  • 用较大的读写缓冲区减少 I/O 次数，顺序读写；
  • 置换选择排序可以生成比内存更长的初始有序段，减少归并轮数；
  • 数据范围有限时（如整数范围小），可以直接用计数排序或位图，一次扫描完成。
  • 分布式环境下用 MapReduce / Spark 的 sortByKey（按范围分区 + 分区内排序）。

有一天的登录日志 {userid, login_time, logout_time}，如何求一天内的最大在线人数，以及维持最大在线人数的最长持续时间？

一句话结论：典型扫描线问题：把每条记录拆成「登录 +1」和「登出 -1」两个事件，按时间排序后扫描累加。

1. 最大在线人数

  • 每条日志生成两个事件：(login_time, +1)、(logout_time, -1)。
  • 按时间升序排序；同一时刻先处理登出再处理登录（区间按 [login, logout) 半开区间处理，登出那一秒不再算在线；如果业务规定登出那一秒仍算在线，则同一时刻先处理登录）。
  • 遍历累加 cur，过程中更新 max。

2. 维持最大在线人数的最长持续时间

  • 第一遍求出 max。
  • 第二遍扫描：cur 变为 max 时记录开始时间 start；cur 从 max 降下来时，用当前时间 - start 计算本段持续时间，更新最长时长。
  • 注意同一时刻的多个事件要先全部处理完再判断 cur，否则同一秒内 +1、-1 会产生长度为 0 的假区间。

3. 利用时间单位是秒的优化

  • 一天只有 86400 秒，可以用差分数组：diff[login]++、diff[logout]--，再做前缀和得到每一秒的在线人数，O(n + 86400)，不需要排序，并且容易求最长连续区间。
  • 跨天的记录要截断到当天 [0, 86400) 范围。
  • 日志量极大时，可以分片统计各自的差分数组，最后逐位相加（差分数组可加），天然适合并行。
int[] diff = new int[86401];
for (Log log : logs) { diff[log.login]++; diff[log.logout]--; }
int cur = 0, max = 0, best = 0, run = 0;
int[] online = new int[86400];
for (int t = 0; t < 86400; t++) { cur += diff[t]; online[t] = cur; max = Math.max(max, cur); }
for (int t = 0; t < 86400; t++) {
    run = online[t] == max ? run + 1 : 0;
    best = Math.max(best, run);
}
// max 为最大在线人数，best 为维持最大在线人数的最长连续秒数

只有能生成 1～5 随机数的 rand5()，如何实现 rand7()？

一句话结论：用两次 rand5 构造 0～24 的均匀分布，只保留 0～20 映射到 1～7，其余拒绝重新采样。

int rand7() {
    while (true) {
        int num = (rand5() - 1) * 5 + (rand5() - 1); // 0~24 均匀分布
        if (num < 21) return num % 7 + 1;            // 21 = 7*3，保证每个结果概率都是 3/25 ÷ 21/25 = 1/7
    }
}

为什么是均匀的

  • (rand5()-1)*5 取 {0,5,10,15,20}，rand5()-1 取 {0,1,2,3,4}，两次独立，组合成 25 个结果，每个概率 1/25，相当于两位 5 进制数。
  • 0～20 共 21 个数，% 7 后 1～7 各对应 3 个数，概率相等。
  • 21～24 丢弃重来，这就是拒绝采样。

效率：每轮成功概率 21/25 = 84%，期望轮数约 1.19，期望调用 rand5 约 2.38 次。

常见错误：rand5() + rand5() 不是均匀分布（中间值概率更高）；rand5() * 7 / 5 之类的缩放也不均匀。

推广：用 randM 构造 randN 时，用多次 randM 拼出范围 [0, M^k)，取不超过它的最大的 N 的倍数作为保留区间，其余拒绝。还可以把被拒绝的余数（如 21～24 对应 0～3）作为新的随机源继续利用，进一步减少调用次数。

核心处理链路

  1. 意图识别与路由：先判断问题类型（FAQ、知识问答、业务办理、投诉 / 转人工），不同类别走不同分支；可以用小模型或分类模型降低成本。
  2. FAQ 匹配：高频固定问题先走 FAQ 库（关键词 + 向量相似度），命中且置信度高则直接返回标准答案。成本最低、响应最快，能拦截大量重复问题。
  3. RAG 知识问答：FAQ 未命中但知识库有覆盖的问题，检索相关文档后约束模型只依据检索内容回答，并给出引用；无依据时明确说不知道，不编造。
  4. 工具调用：查订单、查物流、退换货等需要实时数据或执行操作的问题，由 Agent 调用后端接口；写操作需要用户二次确认。
  5. 转人工：高风险场景（投诉、纠纷、法律问题）、置信度低于阈值、用户明确要求、连续负面情绪时转人工，并把对话摘要和上下文一起交给坐席，避免用户重复描述。

配套机制

  • 会话管理：多轮上下文、话题切换、会话中断恢复。
  • 权限校验：工具调用前校验用户身份，只能查询和操作本人数据，参数中的用户 ID 由服务端注入，不信任模型生成的值。
  • 安全合规：输入输出双向做敏感内容过滤、Prompt 注入防护、隐私信息脱敏。
  • 可观测性：记录意图、检索结果、工具调用、模型输入输出、耗时和用户反馈，支持全链路追踪。
  • 效果评估：意图识别准确率、FAQ 命中率、回答准确率、工具调用成功率、转人工率、问题解决率和用户满意度，持续迭代。

设计一个会话记忆要考虑哪些维度？

一句话结论：会话记忆主要分短期记忆（当前会话上下文）和长期记忆（跨会话的用户事实和偏好），设计时还要考虑写入、检索、压缩、遗忘、隔离等维度。

1. 短期记忆

  • 当前会话的对话历史，直接放在模型的上下文窗口中。
  • 问题：窗口有限且越长越慢越贵。处理方式：滑动窗口保留最近 N 轮、超过阈值后对旧内容做摘要、按 token 预算裁剪。

2. 长期记忆

  • 用户偏好、关键事实、历史结论等，跨会话复用。存储常用向量库（按语义检索）+ 结构化存储（用户画像字段、KV）。
  • 写入：不是保存所有对话，而是由模型或规则抽取有价值的信息，带上时间戳、来源和重要性。
  • 读取：新会话或新问题时检索相关记忆注入上下文。

3. 其他关键维度

  • 写入策略：什么值得记（重要性评分），新旧冲突时如何更新（用户搬家后旧地址要被覆盖，而不是两条并存）。
  • 检索策略：相关性、时间新近度、重要性综合打分。
  • 遗忘机制：时间衰减、长期不被访问的记忆降权或清理、低分记忆定期清理。
  • 隔离与安全：按用户、会话、租户隔离；敏感信息脱敏或不入库；支持用户查看和删除自己的记忆。
  • 成本与性能：检索延迟、存储成本、注入上下文的 token 预算。

用户对话时一直切换话题，会话记忆怎么设计？

一句话结论：不要把所有历史直接拼进 Prompt，而是按话题组织记忆，每轮先判断话题，再按需召回对应话题的上下文。

设计要点

  1. 话题识别：每轮输入先判断是延续当前话题、回到历史话题，还是开启新话题（可以用 LLM 分类或与各话题摘要做向量相似度比较）。
  2. 话题级记忆：每个话题维护一份结构化摘要，包括用户目标、关键事实、当前进展、待解决问题；话题切换时把当前话题摘要保存，激活目标话题。
  3. 话题栈：最近活跃的话题按顺序入栈，「刚才那个」「回到上一个问题」这类指代优先从栈顶附近的话题恢复。
  4. 动态拼装上下文：每轮的上下文由最近几轮原始对话 + 当前话题摘要 + 检索出的相关历史话题 + 长期用户画像组成，控制在 token 预算内。
  5. 分层管理：短期记忆保证当前对话连贯，话题级记忆负责跨话题恢复，长期记忆只保存稳定偏好和长期事实。

收益：避免不同话题的信息互相污染，控制上下文长度，同时能准确回到之前的话题继续。

如何设计一个 RAG 系统？最容易出问题的是哪一层？

一句话结论：RAG 分为离线知识处理（解析、切块、向量化、入库）和在线检索生成（改写、召回、重排、拼接、生成）两段；最容易出问题的是知识处理和检索，体验差往往是「检不到、检不准」，而不是模型不会写答案。

离线链路

  • 文档解析：PDF、Word、网页、数据库等多源接入，保留标题层级、表格、图片说明等结构信息。
  • 切块清洗：按结构或语义切块并保留重叠，清理页眉页脚、水印等噪声。
  • 向量化与入库：选择适合领域和语言的 Embedding 模型；向量、原始文本和元数据（来源、标题、页码、版本、权限）一起存储。

在线链路

  • Query 处理：多轮问题改写为独立查询，复杂问题拆分子查询。
  • 混合召回：向量检索覆盖语义相近的表述，BM25 关键词检索覆盖专有名词、型号、编号等精确匹配，结果用 RRF 等方式融合。
  • 重排：Cross-Encoder 类 Reranker 对候选精排，取 Top N。
  • 上下文拼接：带来源标注和分隔符，控制总长度。
  • 生成：约束模型只依据提供的内容回答，给出引用，无依据时拒答。

最容易出问题的环节

  • 解析与切块决定召回上限：表格被打散、标题丢失、语义被切断，后面无论怎么调召回和重排都救不回来。
  • 单一召回的盲区：纯向量检索对精确术语和编号不敏感，纯关键词检索不理解同义改写，常常上线后才暴露。混合召回 + Rerank 是工程上的常规方案。
  • 知识更新与版本：新旧文档并存导致矛盾答案。

评估：分开评估检索（Recall@K、MRR）和生成（忠实度、答案相关性），定位问题出在哪一层。

如何处理 RAG 召回不准的问题？

一句话结论：逐层定位问题出在 Query、切块、Embedding 还是排序环节，再对症优化；工程上的常规组合是 Query 改写 + 混合召回 + Rerank + 元数据过滤。

1. 先定位：构建带标注的评测集，计算 Recall@K，抽查失败样例，看相关文档是根本没召回、召回了但排序靠后，还是召回了但被截断。

2. 分层优化

  • Query 层：口语化、指代不清的多轮问题先改写成独立规范的检索语句；复杂问题拆分子查询分别检索后合并；也可以用 HyDE（先让模型生成假设答案再用它检索）。
  • 切块层：按文档类型调整切块粒度，保留标题层级和重叠；表格、FAQ、代码使用专门的切块策略；可以用「小块检索、返回父块」的方式兼顾精度和上下文完整。
  • Embedding 层：选用适配中文和垂直领域的模型，必要时用领域数据微调；把标题等信息拼进待编码文本。
  • 召回层：向量 + BM25 混合召回；利用元数据（时间、类别、产品线、权限）做过滤，缩小检索范围。
  • 排序层：用 Reranker 对候选重排，适当增大召回数量、减少最终注入数量。

3. 知识治理

  • 入库去重、记录版本号和更新时间，召回时优先使用最新版本，避免模型同时看到矛盾信息而产生幻觉。
  • 收集线上 bad case 回流到评测集，持续迭代。

要切分的文档是 Markdown、Word 或 PDF，分块怎么做？

一句话结论：先把文档解析成带结构的文本，再优先按结构切分，过长部分用递归字符切分兜底，并保留重叠和元数据。

常见切分方式

方式 做法 特点
固定长度 按固定 token 数或字符数切 简单，易切断语义
递归字符切分 按段落、换行、句号等分隔符逐级切分直到满足长度 通用默认选择，保留句子完整
结构切分 按 Markdown / HTML 标题层级切；代码按函数、类切（如 tree-sitter） 利用文档天然边界
语义切分 计算相邻句子 Embedding 相似度，在相似度骤降处切 语义完整，计算成本较高
LLM / Agentic 切分 让 LLM 理解内容后决定切分边界或生成命题 最灵活，成本最高

按文档类型

  • Markdown：按标题层级切分，每个块带上所属的各级标题路径；代码块和表格作为整体不拆；内容过长再递归字符切分。
  • Word：先转成结构化文本或 Markdown（如 pandoc、python-docx 读取标题样式），再按 Markdown 方式处理；表格单独解析为结构化文本。
  • PDF：最难处理。文本型 PDF 用解析工具提取并做版面分析（多栏、页眉页脚、表格区域）；扫描件先 OCR；复杂版面可以用多模态模型或文档解析模型转成 Markdown；清洗页眉页脚和页码后再按结构切分，表格转为 Markdown 表格或独立成块。

切分后的处理

  • 相邻块保留约 10%～20% 重叠，避免关键信息落在边界上。
  • 每个块保存元数据：来源文档、标题路径、页码、版本，便于过滤和引用溯源。
  • 块大小根据 Embedding 模型的最佳长度和问题类型调整，常见在几百 token。

如何设计一个 Agent 的执行链路？

一句话结论：Agent 的执行本质是**「感知 → 思考 → 行动 → 观察」的循环**，链路可以拆成输入理解、规划、工具调用、观察、记忆、决策、输出，必要时加上反思纠错，再配合终止条件和安全控制。

核心步骤

  1. 输入理解：解析用户意图和约束条件，结合会话上下文补全信息；信息不足时先追问。
  2. 规划：LLM 把任务拆成可执行的子步骤（Plan-and-Execute），或者每一步即时决定下一步动作（ReAct）。
  3. 工具调用：模型通过 Function Calling 选择工具并生成参数，由系统执行（调用 API、查询数据库、执行代码）。这是 Agent 与普通聊天机器人的主要区别。
  4. 观察：工具结果作为 Observation 返回给模型，更新当前状态。
  5. 记忆：关键结果写入短期状态，必要时沉淀到长期记忆。
  6. 决策：根据观察和目标判断任务是否完成、继续下一步还是重新规划。
  7. 输出：汇总结果返回用户。
  8. 反思纠错（可选）：对结果自检，发现错误就修正或重新规划。

工程保障

  • 最大步数、超时、相同调用重复检测等终止条件。
  • 工具参数校验、权限控制、高风险操作人工确认。
  • 每一步记录日志和 Trace，便于调试和评估。
  • 状态持久化以支持中断恢复。

如何优化一个 Agent 系统？通常从哪里下手？

一句话结论：先用 Trace 定位瓶颈，而不是直接改 Prompt 或换模型；问题通常属于规划、执行、观察三类之一，优化的关键是缩短错误链条。

1. 先定位：建立评测集和全链路追踪，统计每个任务的步数、工具调用次数、耗时、token 消耗和失败点。

2. 三类问题

  • 规划问题：路径选错、过度拆解、选错或多选工具、遗漏关键步骤。优化：精简和规范工具描述、减少候选工具数量（按场景动态加载）、对固定流程用工作流代替自由规划、在 Prompt 中加入少量示例。
  • 执行问题：工具慢、超时、参数错误导致反复重试。优化：工具参数 schema 严格化并在执行前校验、返回清晰的错误信息帮助模型自我修正、无依赖的工具并行调用、对重复调用加缓存。
  • 观察问题：上下文噪声大，工具返回内容冗长或格式混乱，模型每一步都判断不准。优化：工具返回结构化且精简的结果、历史对话压缩摘要、检索结果去噪。

3. 性能视角

  • 先减少调用次数（少一次 LLM 调用往往比优化单次耗时更有效），再压缩上下文长度；简单步骤使用小模型，开启 Prompt 缓存，流式输出改善首字延迟。

4. 效果视角

  • 关注错误集中的状态转移，例如信息不足就过早进入执行、证据不足时直接猜测而不追问用户。
  • 在错误链条的起点切断：在关键决策节点加确认、追问或校验，而不是修补最后一步的输出。

ReAct 模式下 Agent 思考进入死循环怎么办？

一句话结论：死循环的本质是模型无法判断任务已完成或无法推进，常见表现是反复调用同一工具却得不到新信息；解决方式是模型侧给提示 + 系统侧硬性兜底。

模型侧

  • 在 Observation 中追加元信息：如「这是你第 3 次以相同参数调用该工具，之前的结果是……」，让模型意识到自己在重复。
  • 在 Prompt 中写明终止规则：如「连续两次调用同一工具且结果无实质变化时，停止调用并基于已有信息给出当前最佳答案」。
  • 改进工具反馈：工具失败时返回明确原因和建议，而不是空结果或模糊错误，避免模型盲目重试。

系统侧（更可靠）

  • 最大步数限制：如 LangGraph 的 recursion_limit，超过就强制停止。
  • 重复检测：记录（工具名 + 参数）的哈希，相同调用超过阈值即中断；或检测关键状态在多轮之间是否有变化。
  • 超时和 token 预算：整体执行时间或 token 消耗超限时停止。
  • 兜底策略：中断后让模型整理已获取的信息，向用户说明当前进展和卡点，或转人工，而不是无限空转。

根因治理：分析死循环的 Trace，常见原因是工具描述不清、工具返回无法判断成功与否、任务本身缺少必要信息，从这些源头修正。

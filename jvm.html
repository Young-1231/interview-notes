JVM 概览

JVM 的核心功能可以归为四块：类加载、内存管理（运行时数据区）、垃圾回收、执行引擎（解释器 + JIT）。复习和回答时可以按一条主线串起来：

  • 内存结构：程序计数器、虚拟机栈、本地方法栈（线程私有），堆、方法区（线程共享），外加直接内存。
  • 对象：创建过程、内存布局、TLAB、逃逸分析。
  • 垃圾回收：可达性分析与 GC Roots → 回收算法 → 分代模型 → 收集器（CMS / G1 / ZGC）→ 三色标记。
  • 类加载：加载 → 验证 → 准备 → 解析 → 初始化，类加载器与双亲委派。
  • 实战：OOM 与内存泄漏排查、调优参数、监控工具。

面试中可以主动把话题引向自己熟悉的主线，例如从 GC 原理讲到回收算法，再讲到具体收集器。

讲一下 JVM高频

JVM（Java Virtual Machine）是运行 Java 字节码的虚拟机。javac 把 .java 编译成平台无关的 .class 字节码，再由各平台对应的 JVM 加载执行，这就是 Java 跨平台的基础。

JVM 主要负责：

  • 类加载：把 .class 加载进内存，完成加载、链接（验证、准备、解析）、初始化。
  • 内存管理：划分运行时数据区（程序计数器、虚拟机栈、本地方法栈、堆、方法区），为对象创建、方法调用提供内存。
  • 垃圾回收：自动识别并回收不再使用的对象，开发者不用手动释放内存。
  • 执行引擎：解释器逐条解释字节码，热点代码由 JIT 编译成本地机器码以提升性能。
  • 本地接口：通过 JNI 调用 C/C++ 实现的本地方法。

常见实现是 HotSpot（OpenJDK / Oracle JDK 默认），此外还有 OpenJ9、GraalVM 等。JVM 不只运行 Java，Kotlin、Scala、Groovy 等编译成字节码的语言也能在上面运行。

编译型语言和解释型语言有什么区别？

编译型语言在运行前把源码一次性编译成目标平台的机器码；解释型语言在运行时由解释器逐行翻译执行。

对比 编译型 解释型
执行方式 先编译成机器码，再直接执行 运行时由解释器边翻译边执行
执行效率 高 相对低
跨平台 需要为每个平台分别编译 有解释器即可运行
开发调试 修改后要重新编译 修改后直接运行
代表 C、C++、Go、Rust Python、JavaScript（现代引擎也有 JIT）

Java 两种特点兼有：先编译成字节码，再由 JVM 解释执行，热点代码再由 JIT 编译成机器码。

Java 是编译型语言还是解释型语言？

Java 既不是纯编译型，也不是纯解释型，而是"先编译、后解释，热点代码再 JIT 编译"的混合模式。

  • 前端编译：javac 把 .java 编译成 .class 字节码，字节码不是机器码，操作系统不能直接执行。
  • 解释执行：JVM 的解释器逐条解释字节码，启动快，但执行慢。
  • JIT 编译：运行中被频繁执行的热点代码会被 JIT 编译成本地机器码并缓存，之后直接执行机器码。
  • AOT 编译：GraalVM Native Image 可以提前把程序编译成本地可执行文件，启动快、内存小，但会失去部分运行时优化和动态特性。

所以说 Java 是"半编译半解释"的语言更准确。

什么是 JIT 编译器？

JIT（Just-In-Time，即时编译器）是 JVM 执行引擎的一部分，它在运行时把热点字节码编译成本地机器码，后续直接执行机器码，从而提升性能。

怎么识别热点代码：HotSpot 用基于计数器的热点探测，方法调用计数器统计方法调用次数，回边计数器统计循环执行次数，超过阈值就触发编译（循环体可以通过 OSR 栈上替换在执行中途切换到编译版本）。

两个编译器与分层编译：

  • C1（Client Compiler）：编译快，优化较少。
  • C2（Server Compiler）：编译慢，优化激进，生成的代码更快。
  • JDK 8 起默认开启分层编译（Tiered Compilation）：先解释执行，较热的代码先用 C1 编译并收集 profile，更热的再交给 C2。

常见优化：方法内联（最重要的优化，是其他优化的基础）、逃逸分析（栈上分配、标量替换、锁消除）、循环展开、死代码消除、常量折叠等。

优缺点：

  • 优点：热点代码以机器码运行，并且能利用运行时信息做激进优化，性能可以接近甚至超过静态编译。
  • 缺点：启动初期要先解释执行，需要预热；编译本身占用 CPU，编译后的代码存放在 Code Cache 里，占用额外内存（-XX:ReservedCodeCacheSize）。

为什么 Java 可以一次编译、到处运行？

因为 Java 源码编译成的是平台无关的字节码，而不是某个平台的机器码。字节码由各个平台上的 JVM 负责解释或 JIT 编译成该平台的机器码执行。

  • 统一的字节码格式：.class 文件格式和指令集由 JVM 规范定义，与操作系统、CPU 无关。
  • 平台相关的 JVM：Windows、Linux、macOS、x86、ARM 各有对应的 JVM 实现，屏蔽了底层差异。
  • 统一的语言规范和类库：基本类型长度固定（例如 int 恒为 32 位），标准类库在各平台行为一致。

注意：跨平台的是字节码，JVM 本身并不跨平台。另外，如果代码调用了 JNI 本地库，或者依赖特定系统路径、命令，就失去了跨平台性。

程序计数器有什么作用？为什么是线程私有的？高频

程序计数器（Program Counter Register）是一块很小的线程私有内存，记录当前线程正在执行的字节码指令地址。

作用：

  • 字节码解释器通过改变计数器的值选取下一条指令，分支、循环、跳转、异常处理、线程恢复都依赖它。
  • 线程切换后，靠它恢复到正确的执行位置。
  • 执行 Native 方法时，计数器的值为空（undefined）。

为什么线程私有：Java 多线程通过 CPU 时间片轮转实现，同一时刻一个核只执行一个线程的指令。线程被切换出去再切回来时，需要知道自己上次执行到哪里。每个线程执行的代码和进度都不同，如果共享一个计数器就会互相覆盖，所以每个线程都要有独立的程序计数器。

特点：生命周期与线程相同；占用空间极小且固定，是 JVM 规范中唯一没有规定 OutOfMemoryError 的区域。

Java 虚拟机栈有什么作用？高频

虚拟机栈（JVM Stack）是线程私有的，描述 Java 方法执行的内存模型：每调用一个方法就创建一个栈帧压栈，方法返回（正常返回或抛异常）时栈帧出栈。

栈帧组成：

  • 局部变量表：存放方法参数和局部变量，包括基本类型的值和对象引用，容量在编译期确定，以 slot 为单位（long、double 占两个 slot）。
  • 操作数栈：字节码指令计算时的临时工作区。
  • 动态链接：指向运行时常量池中该方法的引用，用于把符号引用转换为直接引用（支持多态等）。
  • 方法返回地址：方法退出后回到调用者的位置。

特点与异常：

  • 生命周期与线程相同，线程之间互不影响，栈上数据天然线程安全。
  • 栈大小用 -Xss 设置（64 位 Linux 默认 1MB）。
  • 调用层次过深（比如无限递归）超过栈容量，抛 StackOverflowError。
  • 创建线程时无法申请到栈内存（例如线程过多），抛 OutOfMemoryError: unable to create native thread。HotSpot 的栈不能动态扩展，所以 OOM 主要出现在创建线程时。

本地方法栈有什么作用？高频

本地方法栈（Native Method Stack）是线程私有的，作用与虚拟机栈类似，区别是它为 Native 方法服务，而虚拟机栈为 Java 方法服务。

  • 服务 Native 方法：Java 通过 JNI 调用 C/C++ 实现的方法（如 Object.hashCode()、Thread.start0()、文件和网络 I/O 的底层实现）时，用的是本地方法栈。
  • 实现方式：JVM 规范没有强制规定它的结构，HotSpot 直接把本地方法栈和虚拟机栈合二为一。
  • 异常：和虚拟机栈一样，可能抛 StackOverflowError 和 OutOfMemoryError。

Java 堆有什么作用？高频

Java 堆（Heap）是 JVM 管理的最大一块内存，所有线程共享，在 JVM 启动时创建，用来存放对象实例和数组，也是 GC 管理的主要区域（因此也叫 GC 堆）。

  • 存放对象：几乎所有对象实例和数组都在堆上分配。JIT 经过逃逸分析后，未逃逸的对象可能被标量替换，不在堆上分配。
  • 其他内容：HotSpot 从 JDK 7 起，字符串常量池和类的静态变量（随 Class 对象）也存放在堆中。
  • 分代管理：传统分代收集器把堆分为年轻代（Eden + 两个 Survivor）和老年代，默认 NewRatio=2（年轻代:老年代 = 1:2）、SurvivorRatio=8（Eden:S0:S1 = 8:1:1）。G1 在物理上把堆划分成等大的 Region，分代只是逻辑概念。
  • TLAB：为减少并发分配的锁竞争，Eden 中为每个线程划出私有的分配缓冲区。
  • 大小设置：-Xms 初始大小，-Xmx 最大大小，生产环境通常设成相等，避免运行时扩缩容。
  • 异常：对象无法分配且堆无法再扩展时，抛 OutOfMemoryError: Java heap space。

方法区有什么作用？高频

方法区（Method Area）是 JVM 规范定义的线程共享区域，用于存放已加载类的元数据。它是一个逻辑概念，不同 JDK 版本有不同实现。

存放内容（HotSpot JDK 8+）：

  • 类元数据：类名、父类、接口、字段、方法、访问修饰符等（InstanceKlass）。
  • 方法的字节码、运行时常量池（类文件常量池在类加载后的运行时形式）。
  • JIT 编译后的代码（实际在 Code Cache 中）。

静态变量和字符串常量池在哪里：规范层面它们属于方法区的概念，但在 HotSpot 中，JDK 6 及之前它们在永久代里；JDK 7 起已经移到 Java 堆中（静态变量随 Class 对象存放在堆里），JDK 8 的元空间里没有它们。所以被问到 HotSpot 的具体位置时，要回答在堆中。

实现变迁：

  • JDK 7 及之前：永久代（PermGen），位于 JVM 内存中，大小由 -XX:MaxPermSize 固定。
  • JDK 8 及之后：元空间（Metaspace），使用本地内存，用 -XX:MetaspaceSize、-XX:MaxMetaspaceSize 控制。

回收：方法区也会被 GC，主要回收废弃常量和不再使用的类（类卸载），但条件苛刻、收益较低。

方法区是 JVM 规范中的逻辑区域；永久代和元空间是 HotSpot 对方法区的两种实现，前者用于 JDK 7 及之前，后者用于 JDK 8 及之后。

对比 永久代（PermGen） 元空间（Metaspace）
版本 JDK 7 及之前 JDK 8 及之后
内存位置 JVM 管理的内存，与堆连续 本地内存（Native Memory）
大小 固定上限，-XX:MaxPermSize 默认只受物理内存限制，可用 -XX:MaxMetaspaceSize 设上限
存放内容 类元数据；JDK 6 还有字符串常量池、静态变量 只有类元数据
OOM 信息 PermGen space Metaspace

为什么要替换：

  • 大小难以确定：动态代理、CGLIB、反射、JSP、热部署等会动态生成大量类，永久代上限固定，容易 OutOfMemoryError: PermGen space。元空间用本地内存，空间更充裕，也可以按需增长。
  • GC 更简单：永久代需要由 GC 专门管理，回收效率低、调优复杂。元空间按类加载器分配内存块，类加载器被回收时整块释放。
  • 合并 JRockit：Oracle 合并 HotSpot 和 JRockit，JRockit 本来就没有永久代，统一后移除永久代。

注意：元空间不设上限时，类泄漏会一直吃本地内存，生产环境建议设置 -XX:MaxMetaspaceSize。

为什么要区分堆和栈？

堆和栈的生命周期、共享方式和管理方式完全不同，分开设计可以让两类数据各用最合适的管理方式。

对比 栈 堆
存放内容 栈帧：局部变量、操作数栈、返回地址 对象实例、数组
线程 私有，天然线程安全 共享，需要同步
生命周期 随方法调用入栈、返回出栈 不确定，由 GC 判断回收
分配释放 移动栈顶指针，极快，不需要 GC 需要分配算法和 GC
大小 小，-Xss 大，-Xms / -Xmx
异常 StackOverflowError OOM: Java heap space
  • 体现程序的不同视角：栈代表处理逻辑（方法怎么执行），堆代表数据（对象是什么），分离后逻辑更清晰。
  • 共享与隔离：对象放堆上，多个线程、多个栈帧可以通过引用共享同一份数据；栈私有则不需要同步。
  • 性能与 GC：短生命周期的局部数据放栈上随方法结束自动释放，GC 只需关注堆，回收范围更小。
  • 问题定位：栈溢出和堆溢出是两类不同问题，分开后更容易排查。

JDK7 为什么把字符串常量池移到堆中？

主要原因是永久代空间小且回收效率低，字符串常量池放在里面容易 OOM，也不能及时回收。

  • 避免 PermGen OOM：永久代大小固定且通常较小（默认几十 MB），大量使用 intern() 或字符串常量很多的应用容易抛 OutOfMemoryError: PermGen space。堆空间大得多。
  • 回收更及时：永久代只有 Full GC 时才回收，字符串常量池里不再使用的字符串迟迟释放不了。放到堆里后，年轻代 GC 和老年代 GC 都能回收它们。
  • 为移除永久代铺路：JDK 7 先把字符串常量池和静态变量移出永久代，JDK 8 再彻底用元空间替代永久代。

字符串常量池本质上是一个 StringTable（固定桶数的哈希表），JDK 7u40 起默认桶数为 60013，可用 -XX:StringTableSize 调整。

new String("abc") 会在哪些地方创建对象？intern() 有什么作用？

new String("abc") 会创建一个或两个对象：如果常量池里还没有 "abc"，类加载解析字面量时会在字符串常量池创建一个；执行 new 时一定会在堆中再创建一个新的 String 对象。

String s1 = "abc";              // 指向常量池里的 "abc"
String s2 = new String("abc");  // 堆上的新对象，内部共享同一个 value 数组
System.out.println(s1 == s2);   // false
System.out.println(s1 == s2.intern()); // true

intern() 的作用：如果字符串常量池中已有相等的字符串，返回池中的引用；如果没有：

  • JDK 6：把该字符串复制一份到永久代的常量池，返回这份副本的引用。
  • JDK 7+：不再复制，直接把当前堆中这个 String 对象的引用记录到常量池，并返回它本身。
String s = new String("a") + new String("b"); // 堆上的 "ab"，常量池里还没有 "ab"
s.intern();
System.out.println(s == "ab"); // JDK 7+ 为 true，JDK 6 为 false

用途：大量重复字符串（如从数据库读出的城市名、状态码）调用 intern() 可以让它们共享一份，节省内存；但常量池是固定桶数的哈希表，滥用会让查找变慢。

什么是直接内存？

直接内存（Direct Memory）是 JVM 堆外、由操作系统分配的本地内存，不属于运行时数据区，Java 通过 NIO 的 ByteBuffer.allocateDirect() 申请，Netty 等框架大量使用。

为什么用：堆内的 ByteBuffer 做 I/O 时，JVM 需要先把数据拷贝到一块堆外临时内存再交给系统调用（GC 可能移动堆上对象，地址不稳定）。直接内存省掉了这次拷贝，适合大块、长期复用的 I/O 缓冲区。

怎么管理和释放：

  • 堆上只有一个很小的 DirectByteBuffer 对象，它关联一个 Cleaner（虚引用）。当 DirectByteBuffer 被 GC 回收后，Cleaner 会调用 Unsafe.freeMemory 释放对应的本地内存，不需要也没有公开 API 手动释放。
  • 大小受 -XX:MaxDirectMemorySize 限制，默认与 -Xmx 大致相同。
  • 申请时如果达到上限，JDK 会主动调用 System.gc() 尝试回收，再重试分配，仍不够才抛 OutOfMemoryError: Direct buffer memory。所以开启 -XX:+DisableExplicitGC 可能导致直接内存 OOM。

缺点：申请和释放比堆内存开销大，适合池化复用；回收依赖堆上小对象的 GC，堆很空闲而直接内存吃紧时容易积压；Heap Dump 里看不到它的内容，排查比较麻烦（可用 NMT -XX:NativeMemoryTracking 辅助）。

什么是 Java 内存模型（JMM）？主要目的是什么？

JMM（Java Memory Model）是 Java 语言规范定义的一套规则，规定多线程下共享变量的读写如何对其他线程可见、哪些重排序是允许的。它和 JVM 内存结构（堆、栈等）不是一回事。

抽象模型：所有共享变量存在主内存，每个线程有自己的工作内存（对应 CPU 缓存、寄存器的抽象），线程操作的是变量副本，再与主内存同步。

主要目的：屏蔽不同硬件和操作系统的内存访问差异，让 Java 程序在各平台都有一致的并发语义，围绕三个特性：

  • 原子性：synchronized、Lock、原子类保证复合操作不可分割（基本类型的读写本身是原子的，64 位 long/double 在 32 位 JVM 上不加 volatile 不保证原子）。
  • 可见性：volatile、synchronized、final 保证一个线程的修改能被其他线程看到。
  • 有序性：volatile（内存屏障）、synchronized 禁止特定的指令重排序。

happens-before 规则：JMM 的核心，前一个操作的结果对后一个操作可见。常见规则有程序次序规则、监视器锁规则（解锁 happens-before 后续加锁）、volatile 规则（写 happens-before 后续读）、线程启动规则、线程终止规则、传递性等。

对象的创建过程是怎样的？对象的内存布局是怎样的？高频

创建过程：执行 new 时，HotSpot 依次完成五步。

  1. 类加载检查：类还没加载、链接、初始化就先执行类加载。
  2. 分配内存：大小在类加载后已确定。堆规整用指针碰撞，不规整用空闲列表；并发安全靠 TLAB 优先 + CAS 失败重试。
  3. 初始化零值：内存（不含对象头）置零，所以字段不赋值也有默认值。
  4. 设置对象头：写入 Mark Word 和类型指针。
  5. 执行 <init>：字段初始化和构造方法执行完，对象才真正可用。

内存布局：对象头、实例数据、对齐填充三部分。

  • Mark Word：64 位 JVM 上 8 字节，存哈希码、GC 分代年龄（4 位，所以最大 15）、锁状态、偏向线程 ID 等，内容随锁状态变化。
  • 类型指针：指向元空间中的 InstanceKlass（不是堆里的 java.lang.Class 对象，Class 对象只是它的镜像）。默认开启压缩类指针时 4 字节，否则 8 字节。
  • 数组长度：只有数组有，4 字节。
  • 实例数据：含父类字段，JVM 会重排字段减少空隙。
  • 对齐填充：对象大小补齐到 8 字节整数倍。

常见追问：默认开启压缩指针时 new Object() 占 16 字节（8 Mark Word + 4 类型指针 + 4 填充），可用 JOL 查看。JDK 24 实验性引入、JDK 25 转正的 Compact Object Headers（-XX:+UseCompactObjectHeaders，默认不开启）能把对象头压到 8 字节。

访问方式：HotSpot 用直接指针，引用直接指向堆中对象；句柄访问多一次间接，但对象移动时引用不变。

对象分配内存的方式有哪些？

分配方式有指针碰撞和空闲列表两种，选哪种取决于堆是否规整，而堆是否规整又取决于垃圾收集器有没有压缩整理能力。

  • 指针碰撞（Bump the Pointer）：已用内存和空闲内存各在一边，中间放一个指针作为分界，分配时只要把指针往空闲一侧移动对象大小的距离。速度快，适用于 Serial、ParNew、Parallel、G1 等带复制或整理的收集器。
  • 空闲列表（Free List）：已用和空闲内存相互交错，JVM 维护一个记录可用内存块的列表，分配时找一块足够大的。适用于基于标记-清除的 CMS（CMS 的老年代用空闲列表）。

并发安全问题：多个线程同时分配时，可能出现两个线程拿到同一块内存。解决方式有两种：

  • CAS + 失败重试：保证更新指针的原子性。
  • TLAB：每个线程预先在 Eden 中分到一小块私有缓冲区，在自己的 TLAB 里分配不需要同步，TLAB 用完再用 CAS 申请新的。HotSpot 默认开启（-XX:+UseTLAB）。

什么是 TLAB？

TLAB（Thread Local Allocation Buffer，线程本地分配缓冲区）是 JVM 在 Eden 区为每个线程划分的一小块私有内存，用来减少多线程分配对象时的竞争。

  • 工作原理：线程创建对象时优先在自己的 TLAB 中用指针碰撞分配，不需要加锁。TLAB 用完后，用 CAS 从 Eden 再申请一块新的 TLAB；对象太大放不进 TLAB 时，直接在 Eden 中用 CAS 分配。
  • 大小：默认动态调整，初始约占 Eden 的 1%，JVM 会根据线程分配速率自适应。相关参数有 -XX:+UseTLAB（默认开启）、-XX:TLABSize、-XX:+ResizeTLAB。
  • 优势：把并发分配的同步开销降到"每申请一块 TLAB 同步一次"，大幅提升多线程下的分配速度。

注意：

  • TLAB 属于 Eden，Eden 属于堆，TLAB 只是堆上的一种分配方式，不是独立的内存区域。
  • TLAB 只是分配时私有，分配出来的对象其他线程照样可以访问，TLAB 不保证对象线程安全。
  • TLAB 剩余空间不够放一个对象时，会根据浪费阈值决定是丢弃当前 TLAB 重新申请，还是直接在 Eden 共享区分配，有一定的空间浪费。

对象一定分配在堆上吗？高频

不一定。绝大多数对象分配在堆上，但 JIT 经过逃逸分析，发现对象不会逃逸出方法时，可以不在堆上分配。

  • 默认在堆上：解释执行和未被优化的代码里，对象都在堆上分配，优先走 Eden 中的 TLAB。TLAB 本身就是堆的一部分，在 TLAB 中分配仍然是堆分配。
  • 标量替换：HotSpot 实际采用的优化。对于未逃逸的对象，JIT 不创建对象，而是把它拆成若干个基本类型的局部变量（标量），放在栈帧或寄存器里。效果上等同于"对象没有在堆上分配"，随方法结束自动消失，不给 GC 增加负担。
  • 栈上分配：理论上可以把整个对象分配在栈上，但 HotSpot 并没有实现真正的栈上分配，是通过标量替换达到类似效果。
  • 前提条件：只对 JIT 编译后的热点代码生效；需要开启逃逸分析（-XX:+DoEscapeAnalysis）和标量替换（-XX:+EliminateAllocations），JDK 8 起默认都开启；对象不能太大，数组等无法拆分的对象一般不行。
public int sum() {
    Point p = new Point(1, 2); // p 未逃逸，可能被标量替换为 int x = 1, y = 2
    return p.x + p.y;
}

什么是逃逸分析？

逃逸分析（Escape Analysis）是 JIT 编译器的一种分析技术，判断对象的作用范围是否会超出当前方法或当前线程，本身不是优化，而是为后续优化提供依据。

三种逃逸状态：

  • 不逃逸：对象只在方法内部创建和使用。
  • 方法逃逸：对象作为返回值返回，或作为参数传给其他方法（且该方法未被内联）。
  • 线程逃逸：对象被赋值给静态变量、其他线程可访问的成员变量等，可能被其他线程访问。

基于逃逸分析的优化：

  • 标量替换：不逃逸的对象被拆成基本类型字段，不在堆上分配（HotSpot 的"栈上分配"就是靠它实现的）。
  • 锁消除：对象不会线程逃逸时，对它加的锁可以去掉，例如方法内部局部 StringBuffer 的 append 同步。
  • 同步消除和栈上分配本质都依赖"对象不被外部访问"这一结论。

局限：分析本身耗费编译时间，并且是保守的；只作用于 C2 编译的热点代码。JDK 8 起 -XX:+DoEscapeAnalysis 默认开启。编码时尽量缩小对象作用域、避免不必要地把对象暴露出去，有利于 JIT 优化。

对象的分配策略是怎样的？

HotSpot 分代收集器下，对象分配遵循几条规则：

  1. 优先在 Eden 分配：新对象优先在 Eden 区（具体是线程的 TLAB）分配。Eden 空间不足时触发一次 Minor GC。
  2. 大对象直接进入老年代：需要大量连续内存的对象（大数组、长字符串）可以直接在老年代分配，避免在 Eden 和 Survivor 之间反复复制。Serial 和 ParNew 通过 -XX:PretenureSizeThreshold 设置阈值（Parallel Scavenge 不支持该参数）；G1 中超过 Region 一半大小的对象会被放入 Humongous Region。
  3. 长期存活的对象进入老年代：对象在 Eden 出生，经过第一次 Minor GC 存活并被移入 Survivor 后年龄为 1，此后每熬过一次 Minor GC 年龄加 1，达到 -XX:MaxTenuringThreshold（默认 15）时晋升到老年代。
  4. 动态年龄判定：按年龄从小到大累加 Survivor 中对象的大小，累加到年龄 N 时超过 Survivor 容量的 TargetSurvivorRatio（默认 50%），就把晋升阈值调整为 N，年龄大于等于 N 的对象直接晋升。
  5. 空间分配担保：Minor GC 前，JVM 检查老年代最大可用连续空间是否大于新生代所有对象总大小，或大于历次晋升的平均大小（JDK 6u24 之后的规则），满足则进行 Minor GC，否则改为 Full GC。Minor GC 后 Survivor 放不下的存活对象，直接由老年代担保接收。

垃圾识别与引用类型 4高频 3

什么是垃圾回收？高频

垃圾回收（Garbage Collection，GC）是 JVM 自动识别不再被使用的对象并释放其内存的机制，开发者不需要像 C/C++ 那样手动 free/delete。

回收范围：主要是 Java 堆，其次是方法区（废弃常量、无用类）。程序计数器、虚拟机栈、本地方法栈随线程生灭，栈帧随方法进出自动分配和释放，不需要 GC。

GC 要解决的三个问题：

  • 哪些内存需要回收：通过可达性分析判断对象是否存活。
  • 什么时候回收：Eden 满时触发 Minor GC，老年代或元空间不足等情况触发 Full GC 等。
  • 怎么回收：标记-清除、标记-复制、标记-整理等算法，由 Serial、Parallel、CMS、G1、ZGC 等收集器具体实现。

优点：降低开发成本，避免野指针、重复释放、大部分内存泄漏问题。

代价：GC 会占用 CPU，部分阶段需要 STW 暂停用户线程，影响延迟和吞吐量；对象仍被无意持有时 GC 也无能为力，内存泄漏依然存在。

如何识别垃圾？对象可以被回收就一定会被回收吗？高频

识别垃圾的两种算法：

  • 引用计数法：每个对象维护一个引用计数器，被引用加 1，引用失效减 1，为 0 即可回收。实现简单、判定及时，但无法处理循环引用（A 引用 B、B 引用 A，外部已无引用，计数却都不为 0），而且每次赋值都要更新计数。Python（配合循环检测）、Objective-C 的 ARC 使用它，HotSpot 不使用。
  • 可达性分析：HotSpot 实际使用的算法。以一组 GC Roots 为起点，沿引用关系向下搜索，走过的路径称为引用链。从 GC Roots 不可达的对象判定为可回收，循环引用的孤岛也能被正确识别。

可以回收不等于一定会回收：

  1. 两次标记与 finalize()：对象第一次被判定不可达后会被标记一次。如果它重写了 finalize() 且还没执行过，会被放进 F-Queue，由低优先级的 Finalizer 线程执行。如果在 finalize() 中把自己重新挂到引用链上（如赋值给某个静态变量），就能"自救"，第二次标记时被移出回收集合。finalize() 只会执行一次，所以第二次就无法自救了。
  2. 回收时机由 GC 决定：对象变成垃圾后，要等到下一次覆盖它所在区域的 GC 才会被回收。例如老年代的垃圾在 Minor GC 中不会被回收；并发收集时产生的浮动垃圾也要等下一轮。
  3. 软引用：软引用对象只在内存不足时才回收。

finalize() 执行时机不确定、开销大、可能让对象复活，JDK 9 已标记为废弃，JDK 18 起（JEP 421）被标记为将要移除。资源清理应使用 try-with-resources 或 java.lang.ref.Cleaner。

哪些对象可以作为 GC Roots？高频

GC Roots 是可达性分析的起点，是一组当前一定存活、外部可以直接访问到的引用。HotSpot 中主要包括：

  1. 虚拟机栈中引用的对象：各线程栈帧局部变量表里的引用，如方法参数、局部变量。
  2. 本地方法栈中 JNI 引用的对象：Native 方法持有的引用。
  3. 类静态属性引用的对象：如 static User admin = new User()（JDK 7 起静态变量在堆中，但它仍然是根）。
  4. 常量引用的对象：如字符串常量池里的引用。
  5. 被同步锁持有的对象：synchronized 锁住的对象。
  6. JVM 内部引用：基本类型对应的 Class 对象、常驻的异常对象（如 NullPointerException、OutOfMemoryError）、系统类加载器。
  7. 活动线程对象本身，以及反映 JVM 内部情况的 JMXBean、JVMTI 中注册的回调、本地代码缓存等。

补充：

  • 分代或局部回收时（如 Minor GC、G1 回收部分 Region），其他区域指向回收区域的引用也要临时当作根。为了避免扫描整个老年代，HotSpot 用卡表（Card Table）/ 记忆集（Remembered Set）记录跨代引用。
  • 枚举根节点必须在一致性快照中进行，所以这一步需要 STW；HotSpot 借助 OopMap 记录引用位置，并只在安全点（Safepoint）暂停线程，以缩短停顿。

强引用、软引用、弱引用、虚引用有什么区别？

分代回收与 GC 类型 9高频 9

分代回收是什么？JVM 堆内存分为几个部分？高频

分代回收是按对象存活时间把堆划分成不同区域，各区域用不同频率和算法回收的策略。传统分代收集器把堆分为年轻代和老年代两部分。

  • 年轻代（Young Generation）：存放新创建的对象，又分为一个 Eden 区和两个 Survivor 区（S0/S1，也叫 From/To）。默认 Eden:S0:S1 = 8:1:1（-XX:SurvivorRatio=8），同一时刻只有一个 Survivor 在使用，所以年轻代可用空间是 90%。
  • 老年代（Old Generation）：存放多次 GC 后仍存活的对象和大对象。默认年轻代:老年代 = 1:2（-XX:NewRatio=2），也可用 -Xmn 直接指定年轻代大小。

一次典型的分代回收：

  1. 新对象在 Eden 分配，Eden 满时触发 Minor GC。
  2. Eden 和 From Survivor 中的存活对象复制到 To Survivor，年龄加 1，然后清空 Eden 和 From，两个 Survivor 角色互换。
  3. 年龄达到阈值、动态年龄判定命中、或 To 区放不下的对象晋升到老年代。
  4. 老年代满了触发 Major GC / Full GC。

注意：

  • 元空间（JDK 8+）存类元数据，不属于堆；JDK 7 及之前的永久代在实现上与堆相邻，所以老资料会说"堆分为年轻代、老年代、永久代"。
  • G1 把堆划分为大小相等的 Region，分代只是逻辑上的；ZGC 在 JDK 21 之前不分代，JDK 21 起支持分代模式。

为什么要分代收集？年轻代和老年代分别用什么算法？高频

分代收集基于两个经验假说：绝大多数对象朝生夕死（弱分代假说）；熬过越多次 GC 的对象越难消亡（强分代假说）。把两类对象分开放，就能针对各自特点选择算法和回收频率，减少每次 GC 的扫描和复制量。

区域 特点 常用算法 原因
年轻代 存活率低，回收频繁 标记-复制 只需复制少量存活对象，速度快且无碎片；Eden:S0:S1 = 8:1:1，只浪费 10% 空间
老年代 存活率高，没有额外空间做担保 标记-清除或标记-整理 复制大量存活对象成本高，还需要等量空闲空间

收益：

  • 频繁的 Minor GC 只扫描年轻代，耗时短；老年代回收次数少。
  • 对象晋升前已经被年轻代过滤掉大部分垃圾，老年代压力小。

代价：存在跨代引用（老年代对象引用年轻代对象），为了 Minor GC 时不扫描整个老年代，需要用卡表 / 记忆集记录跨代引用，并用写屏障维护。

收集器对应：Serial / ParNew / Parallel Scavenge 负责年轻代（复制算法）；Serial Old、Parallel Old 用标记-整理，CMS 用标记-清除；G1 整体看是标记-整理，Region 之间是复制。

Eden 区大小会怎样影响程序？高频

Eden 区大小直接决定 Minor GC 的频率，也会影响单次停顿和晋升速度。

  • Eden 过小：很快被填满，Minor GC 非常频繁。每次 Minor GC 都要 STW，接口延迟抖动增多；而且对象还没来得及"死"就被频繁 GC，年龄增长快、过早晋升，进而让老年代 GC 也变得频繁。
  • Eden 过大：Minor GC 次数减少，大部分短命对象在 GC 前已经死亡。Minor GC 的耗时主要取决于存活对象的数量（需要扫描根和复制存活对象），而不是 Eden 大小，所以单次耗时一般只是略增。代价是老年代空间被压缩，在堆总大小固定时老年代更容易满。
  • 怎么调：结合对象分配速率、存活率和延迟目标，用 -Xmn 或 -XX:NewRatio 调整。一般经验是让 Minor GC 间隔不要太短，同时老年代留足空间。使用 G1 时不要手动固定年轻代大小，否则会干扰 G1 根据 MaxGCPauseMillis 的自适应调整。

Survivor 区大小会怎样影响程序？高频

Survivor 区大小决定了 Minor GC 后存活对象能否留在年轻代，从而影响对象晋升到老年代的速度。

  • Survivor 过小：
    • Minor GC 后存活对象放不下，多出来的直接通过分配担保进入老年代。
    • 动态年龄判定的阈值是 Survivor 容量 × TargetSurvivorRatio（默认 50%），Survivor 小时很容易超过，晋升阈值会被调低到 1，短命对象被过早晋升（过早晋升 premature promotion）。
    • 结果是老年代增长快，Old GC / Full GC 更频繁。
  • Survivor 过大：两个 Survivor 同一时刻只用一个，空间浪费大；Eden 相应变小，Minor GC 更频繁；还可能让本该晋升的长寿对象在两个 Survivor 之间来回复制。
  • 怎么调：用 -XX:SurvivorRatio 调整比例，开启 -XX:+PrintTenuringDistribution（JDK 9+ 用 -Xlog:gc+age=trace）观察各年龄对象大小和实际晋升阈值。如果阈值经常被调成 1、2，说明 Survivor 偏小。

对象什么时候会进入老年代？高频

对象有四种进入老年代的途径：

  1. 年龄达到晋升阈值：对象在 Survivor 中每熬过一次 Minor GC 年龄加 1，达到 -XX:MaxTenuringThreshold（默认 15）时晋升。年龄存在 Mark Word 的 4 位里，所以最大只能设到 15。
  2. 大对象直接进入老年代：大数组、长字符串等需要大块连续内存的对象，为避免在年轻代来回复制，可以直接在老年代分配。Serial / ParNew 通过 -XX:PretenureSizeThreshold 设置阈值；G1 中超过半个 Region 的对象会直接分配到 Humongous Region（逻辑上属于老年代）。
  3. 动态年龄判定：每次 Minor GC 后，按年龄从小到大累加 Survivor 中各年龄对象的大小，累加到年龄 N 时一旦超过 Survivor 容量 × TargetSurvivorRatio（默认 50%），就把晋升阈值设为 N（不超过 MaxTenuringThreshold），年龄大于等于 N 的对象晋升到老年代。
  4. 空间分配担保：Minor GC 后存活对象太多，To Survivor 放不下，多出来的对象直接进入老年代。如果老年代也放不下，就会发生 promotion failed，转为 Full GC。

Java 的 GC 垃圾回收过程是怎样的？高频

可以按"判断垃圾 → 回收算法 → 分代流程 → 收集器"这条主线回答。

  1. 判断垃圾：HotSpot 用可达性分析，从 GC Roots 出发遍历引用链，不可达的对象就是垃圾；软、弱、虚引用按各自规则处理，重写了 finalize() 的对象还有一次自救机会。
  2. 回收算法：标记-清除（有碎片）、标记-复制（无碎片但要预留空间）、标记-整理（无碎片但要移动对象）。
  3. 分代流程：
    • 新对象在 Eden 分配，Eden 满时触发 Minor GC，存活对象复制到 Survivor，年龄加 1。
    • 年龄达到阈值、动态年龄判定命中、或 Survivor 放不下的对象晋升到老年代；大对象直接进老年代。
    • 老年代达到阈值时进行 Old GC / Mixed GC，空间严重不足时触发 Full GC。
  4. 收集器：算法由具体收集器实现。JDK 8 默认 Parallel（Parallel Scavenge + Parallel Old），追求吞吐量；CMS 追求低停顿，JDK 14 已移除；JDK 9 起默认 G1，基于 Region、停顿可预测；ZGC（JDK 15 转正）停顿通常在 1ms 以内。
  5. 并发标记：CMS、G1、ZGC 用三色标记让标记与用户线程并发执行，用增量更新或 SATB 解决漏标问题。

实际项目中再根据业务特点选择收集器，调整堆大小、新生代比例、晋升阈值等参数，在吞吐量、停顿和内存占用之间取得平衡。

什么是 STW？高频

STW（Stop The World）指 JVM 在执行某些操作时暂停所有用户线程，等操作完成后再恢复，期间应用无法响应请求。

为什么需要 STW：GC 需要在一致的快照下分析对象引用关系。如果用户线程同时修改引用，就可能把存活对象误判为垃圾。另外移动对象后还要修正所有指向它的引用，这些都需要用户线程暂停配合。

怎么暂停：JVM 不能在任意位置停下线程，只能等线程运行到安全点（Safepoint，如方法调用、循环回边、异常跳转处）再挂起；处于 Sleep、Blocked 的线程所在的代码区域属于安全区域（Safe Region）。

哪些操作会 STW：

  • Serial、ParNew、Parallel 的整个回收过程，以及所有 Minor GC、Full GC。
  • CMS 的初始标记、重新标记；G1 的初始标记（随 Young GC 一起）、最终标记、筛选回收（复制存活对象）。
  • ZGC、Shenandoah 只在根扫描等少量阶段 STW，停顿很短且不随堆变大而增加。
  • 非 GC 操作也会：偏向锁撤销（JDK 15 起偏向锁默认关闭）、类重定义、jmap -dump、jstack 等需要进入安全点的操作。

影响：STW 直接增加请求延迟。例如接口本身耗时 10ms，期间遇到一次 50ms 的 GC 停顿，这次请求就变成约 60ms；Full GC 停顿到秒级时会造成大量超时。

怎么减少：选择低延迟收集器（G1、ZGC），合理设置堆大小和年轻代比例减少 GC 次数，减少对象分配和过早晋升，避免频繁 Full GC。

垃圾回收算法有哪些？各有什么优缺点？高频

基础算法有三种：标记-清除、标记-复制、标记-整理；分代收集是在此基础上按区域组合使用的策略。

算法 过程 优点 缺点 典型使用
标记-清除（Mark-Sweep） 标记需要回收的对象（或存活对象），然后统一清除垃圾 实现简单，不移动对象 产生内存碎片，大对象可能找不到连续空间而提前触发 GC；对象多时标记和清除效率都会下降 CMS 老年代
标记-复制（Copying） 内存分两块，只用一块；把存活对象复制到另一块，再整块清空 无碎片，分配可用指针碰撞，存活率低时效率很高 要预留空闲空间；存活率高时复制开销大 年轻代（Serial、ParNew、Parallel Scavenge），G1 的 Region 间复制
标记-整理（Mark-Compact） 标记存活对象，把它们移向内存一端，清理边界以外的内存 无碎片，内存利用率高 移动对象并更新引用，开销大、停顿长 Serial Old、Parallel Old，G1 的 Full GC

复制算法的空间浪费：朴素的半区复制浪费 50%。HotSpot 年轻代用 Eden + 两个 Survivor（8:1:1），每次只浪费一个 Survivor，也就是 10%，Survivor 放不下时由老年代做分配担保。

分代收集：根据对象存活周期把堆分为年轻代和老年代，年轻代用复制算法，老年代用标记-清除或标记-整理，是当前商用 JVM 的主流做法。

移动还是不移动：移动对象（整理）让内存分配更简单、无碎片，但回收时停顿更长；不移动（清除）回收快，但分配时更复杂。关注吞吐量的 Parallel 选择整理，关注延迟的 CMS 选择清除，碎片多了再用一次整理的 Full GC 兜底。

什么是三色标记法？高频

三色标记法是并发标记阶段遍历对象图的算法，用三种颜色记录每个对象的扫描进度，使标记过程可以和用户线程并发执行，CMS、G1、ZGC、Shenandoah 都基于它。

三种颜色：

  • 白色：还没有被访问过。标记开始时所有对象都是白色，标记结束后仍为白色的对象不可达，会被回收。
  • 灰色：已经被访问，但它引用的对象还没有全部扫描完。
  • 黑色：已经被访问，且它引用的所有对象都已扫描。黑色对象一定存活，不会再被重新扫描。

标记过程：

  1. 初始时全部为白色，把 GC Roots 直接引用的对象标为灰色（初始标记，STW）。
  2. 从灰色集合中取出对象，把它引用的白色对象标为灰色，再把它自己标为黑色。
  3. 重复第 2 步，直到灰色集合为空（并发标记）。
  4. 修正并发期间的引用变化（重新标记 / 最终标记，STW），剩下的白色对象就是垃圾。

并发带来的问题：用户线程和 GC 线程同时运行，引用关系会变化，可能出现两类错误：

  • 多标：本该回收的对象被标成存活，产生浮动垃圾，可以容忍。
  • 漏标：本该存活的对象最终还是白色，被误回收，必须解决。

为此需要借助写屏障记录并发期间的引用变化，CMS 用增量更新，G1 用 SATB。

三色标记的漏标问题是什么？高频

漏标是指并发标记期间，一个本来存活的对象因为引用关系变化，标记结束时仍是白色，被当成垃圾回收。这会导致程序访问到已释放的对象，后果严重，必须解决。

发生条件（Wilson 1994 证明，两个条件同时满足才会漏标）：

  1. 用户线程让一个黑色对象新增了指向白色对象的引用；
  2. 用户线程删除了所有灰色对象到该白色对象的直接或间接引用。

例子：灰色 B 引用白色 C。用户线程执行 A.c = B.c; B.c = null;，A 已是黑色不会再扫描，B 再也到不了 C，C 就被漏掉了。

解决方案：破坏两个条件之一即可，都靠写屏障实现。

方案 破坏的条件 做法 使用者
增量更新（Incremental Update） 条件 1 黑色对象新增指向白色对象的引用时，把这个黑色对象记录下来（相当于重新变灰），重新标记阶段再以它为根扫描一遍 CMS
原始快照（SATB，Snapshot At The Beginning） 条件 2 删除引用时，把被删除的旧引用指向的对象记录下来，最终标记时以它为根扫描，按照标记开始那一刻的快照进行标记 G1、Shenandoah

对比：

  • 增量更新精确，但重新标记时要重新扫描被记录的黑色对象及其引用链，CMS 的重新标记可能较长。
  • SATB 只需处理被删除的引用，最终标记更快，代价是会产生更多浮动垃圾（标记开始后才死掉的对象也被当成存活）。
  • 标记开始后新分配的对象，G1 通过 TAMS 指针一律视为存活。
  • ZGC 借助染色指针和读屏障处理并发标记和并发转移。

三色标记的多标问题是什么？高频

多标是指一个已经被标成灰色或黑色的对象，在并发标记期间失去了所有引用，变成了真正的垃圾，但本轮 GC 不会再把它改回白色，于是它被当作存活对象保留下来，这类对象叫浮动垃圾（Floating Garbage）。

  • 产生原因：例如方法执行结束，局部变量引用的对象已经被标记过；或者对象引用被置为 null 时它已经是灰色、黑色。并发标记期间新创建的对象一般也直接视为存活。SATB 方案下浮动垃圾更多。
  • 影响：不影响程序正确性，只是让这部分内存晚一轮才释放。
  • 处理：不需要特殊处理，等下一次 GC 回收即可。但因为并发阶段会持续产生浮动垃圾和新分配的对象，CMS、G1 都不能等老年代满了才开始回收，需要预留空间（CMS 的 CMSInitiatingOccupancyFraction、G1 的 InitiatingHeapOccupancyPercent）。

和漏标的对比：多标是"该回收的没回收"，只是延迟回收；漏标是"不该回收的被回收了"，会破坏程序正确性。所以 GC 设计上宁可多标，也绝不能漏标。

如何选择垃圾回收器？高频

主要看 JDK 版本、堆大小、CPU 核数，以及业务更关心吞吐量还是停顿时间。没有特殊需求时，先用当前 JDK 的默认收集器，再根据监控和压测结果调整。

各版本默认收集器：JDK 8 默认 Parallel（Parallel Scavenge + Parallel Old）；JDK 9 起默认 G1。在 CPU 少于 2 核或内存小于约 1792MB 的非服务器级机器上，JVM 会自动选择 Serial。

场景 推荐 理由
单核、小内存（几百 MB）、客户端或小工具 Serial 开销最小，堆小停顿也短
批处理、离线计算、后台任务，关注吞吐量 Parallel 吞吐量最高，不在意偶尔较长的停顿
在线服务，堆约 4GB~几十 GB，希望停顿可控 G1 默认选择，平衡吞吐和延迟，用 MaxGCPauseMillis 设定目标
超大堆（几十 GB 到 TB）、延迟敏感（金融交易、实时推荐） ZGC（JDK 21+ 用分代 ZGC）或 Shenandoah 停顿通常在 1ms 以内且不随堆增大，代价是 CPU 占用更高、吞吐量略低
还在 JDK 8 上的低延迟服务 CMS 或 G1 CMS 在 JDK 14 已移除，长期应迁移到 G1

ZGC 演进：JDK 11 实验性引入，JDK 15 转正，JDK 21 增加分代模式（-XX:+UseZGC -XX:+ZGenerational），JDK 23 起默认使用分代模式，JDK 24 移除了非分代模式。

选择原则：小堆看简单和吞吐量，大堆看停顿；先用默认值，用 GC 日志和压测数据说话，而不是凭感觉切换收集器。容器环境下注意 JVM 能否正确识别 CPU 和内存限制（JDK 8u191+ / JDK 10+ 默认支持容器感知）。

类加载的过程是怎样的？高频

类加载过程分为加载、链接、初始化三个阶段，其中链接又分为验证、准备、解析，完整流程是：加载 → 验证 → 准备 → 解析 → 初始化。

  1. 加载：按全限定名获取字节流（jar、网络、动态生成等），转成元空间中的运行时数据结构，并在堆中生成 java.lang.Class 对象作为访问入口。
  2. 验证：确保字节流符合规范、不危害虚拟机，包括文件格式（魔数 0xCAFEBABE、版本号）、元数据、字节码、符号引用验证。
  3. 准备：为 static 变量分配内存并设零值。static int a = 10; 此时 a 为 0，初始化时才赋 10；static final int B = 10; 这类编译期常量在准备阶段就是 10。实例变量不在这里分配。
  4. 解析：把常量池中的符号引用替换为直接引用，HotSpot 通常在第一次使用时才解析。
  5. 初始化：执行编译器生成的 <clinit>()，按源码顺序执行静态赋值和 static 块；父类先于子类；JVM 保证多线程下只执行一次，静态内部类单例正是利用这一点。

各阶段开始顺序固定，但可以交叉进行，解析也可能在初始化之后。

类的生命周期是怎样的？

类的生命周期是从被加载到内存到被卸载的全过程，共七个阶段：加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载。其中验证、准备、解析合称链接，前五个阶段合称类加载。

  • 加载：读取字节码，在元空间生成类元数据，在堆中生成 Class 对象。
  • 验证：校验字节码合法、安全。
  • 准备：为静态变量分配内存并赋零值。
  • 解析：把符号引用替换为直接引用。
  • 初始化：执行 <clinit>()，完成静态变量赋值和静态代码块。
  • 使用：创建实例、调用方法、访问字段等。
  • 卸载：类的 Class 对象、所有实例和加载它的类加载器都被回收后，类元数据从方法区中卸载。

顺序上，加载、验证、准备、初始化、卸载的开始顺序是固定的；解析为了支持动态绑定，可以在初始化之后再进行。

类加载器负责根据全限定名获取类的字节流并生成 Class 对象。JVM 判断两个类是否相同，要求全限定名相同且由同一个类加载器加载。

JDK 8 的三层类加载器：

  • 启动类加载器（Bootstrap）：C++ 实现，Java 中获取到的是 null，加载 jre/lib 下的核心类库如 rt.jar。
  • 扩展类加载器（Extension）：加载 jre/lib/ext 或 java.ext.dirs 下的类库。
  • 应用程序类加载器（Application）：加载 classpath 下的类，业务代码默认由它加载。

JDK 9 起：模块化后 rt.jar 和 ext 机制移除，扩展类加载器被**平台类加载器（Platform ClassLoader）**取代。

父子关系：Bootstrap ← Extension / Platform ← Application ← 自定义。易错点：这里的"父"是 parent 字段组合，不是继承。

自定义类加载器：继承 ClassLoader，重写 findClass()，读取字节码后调用 defineClass()。这样仍保持双亲委派：loadClass() 先委派父加载器，找不到才调 findClass()。

public class MyClassLoader extends ClassLoader {
    private final Path baseDir;

    public MyClassLoader(Path baseDir, ClassLoader parent) {
        super(parent);
        this.baseDir = baseDir;
    }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        Path file = baseDir.resolve(name.replace('.', '/') + ".class");
        try {
            byte[] bytes = Files.readAllBytes(file); // 可以在这里解密、校验
            return defineClass(name, bytes, 0, bytes.length);
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }
}

常见用途：加载非 classpath 来源的类、字节码加解密、热部署与插件化、应用隔离（Tomcat、OSGi）。要打破双亲委派则重写 loadClass()。

哪些情况会触发类的初始化？

JVM 规范严格规定了有且只有以下六种"主动使用"会触发类初始化（前提是还没初始化过）：

  1. 遇到 new、getstatic、putstatic、invokestatic 字节码：new 对象、读写静态字段（编译期常量除外）、调用静态方法。
  2. 通过 java.lang.reflect 对类进行反射调用，如 Class.forName("X")（默认初始化）。
  3. 初始化一个类时，如果父类还没初始化，先初始化父类（接口例外，初始化子接口不要求父接口初始化）。
  4. JVM 启动时，包含 main() 方法的主类。
  5. MethodHandle 解析结果为 REF_getStatic、REF_putStatic、REF_invokeStatic、REF_newInvokeSpecial 的方法句柄时。
  6. 接口中定义了 default 方法（JDK 8+），其实现类初始化时，该接口要先初始化。

不会触发初始化的被动引用：

  • 通过子类访问父类的静态字段：只初始化父类，不初始化子类。
  • 创建该类的数组：new User[10] 不会初始化 User（只会初始化 JVM 自动生成的数组类）。
  • 访问编译期常量：static final int A = 1; 在编译时已经内联到调用方的常量池，不会触发定义它的类初始化。注意 static final Integer 或 static final int A = random() 这种非编译期常量会触发。
  • ClassLoader.loadClass() 只加载、不初始化；Class.forName(name, false, loader) 也不初始化。
  • 访问 User.class 不会触发初始化。

类什么时候会被卸载？

类卸载需要同时满足三个条件，因此由 JVM 内置类加载器加载的类基本不会被卸载，只有自定义类加载器加载的类才可能卸载。

卸载条件：

  1. 该类的所有实例都已被回收，堆中不存在该类及其子类的实例。
  2. 加载该类的类加载器已经被回收。
  3. 该类对应的 java.lang.Class 对象没有在任何地方被引用，无法通过反射访问。

满足条件后，JVM 也只是"允许"回收，具体还取决于 GC 是否执行类卸载（-XX:+ClassUnloading 默认开启，CMS 需要 -XX:+CMSClassUnloadingEnabled，JDK 8 中默认已开启）。

为什么内置加载器的类不会卸载：Bootstrap、Platform（Extension）、Application 类加载器在 JVM 整个生命周期中都存活，它们始终引用着自己加载的类。

常见场景与问题：

  • 热部署、插件化、Tomcat 重新加载 Web 应用时，丢弃旧的类加载器，旧类随之卸载。
  • 如果旧类加载器被某个长期存活的对象引用（如 ThreadLocal、静态缓存、注册的 JDBC 驱动、未停止的线程），类就无法卸载，多次重新部署后会出现元空间泄漏，最终 OutOfMemoryError: Metaspace。
  • 大量使用 CGLIB、Groovy 脚本、Lambda 动态生成类时，也要关注元空间的增长。可以用 -Xlog:class+unload（JDK 9+）或 -XX:+TraceClassUnloading（JDK 8）观察卸载情况。

ClassNotFoundException 和 NoClassDefFoundError 有什么区别？

两者都和"找不到类"有关，但一个是加载时显式查找失败的受检异常，另一个是编译时存在、运行时链接失败的错误。

对比 ClassNotFoundException NoClassDefFoundError
类型 受检异常，继承 ReflectiveOperationException → Exception 错误，继承 LinkageError → Error
触发场景 通过字符串名动态加载类时找不到：Class.forName()、ClassLoader.loadClass()、findSystemClass() 编译时类存在，运行时 JVM 隐式加载（new、调用静态方法等）时找不到类定义
常见原因 类名写错、jar 包不在 classpath、驱动依赖缺失 打包时漏了依赖、jar 版本冲突、类在别的类加载器下不可见，或者类的静态初始化失败
处理 可以 catch 后降级处理 一般需要修复部署或依赖

常见追问：静态初始化块抛出异常时，第一次访问该类会抛 ExceptionInInitializerError，之后再访问就会抛 NoClassDefFoundError: Could not initialize class X。排查 NoClassDefFoundError 时要往前翻日志，找第一次出现的 ExceptionInInitializerError。

什么是双亲委派模型？高频

双亲委派模型是类加载器的工作方式：一个类加载器收到加载请求时，不会先自己加载，而是先委派给父加载器，层层向上直到启动类加载器；只有父加载器在自己的搜索范围内找不到这个类时，子加载器才尝试自己加载。

执行流程（ClassLoader.loadClass() 默认实现）：

  1. 调用 findLoadedClass() 检查该类是否已经加载过，加载过直接返回。
  2. 没有则交给父加载器的 loadClass()；父加载器为 null 时交给启动类加载器。
  3. 父加载器都加载失败（抛 ClassNotFoundException）后，调用自己的 findClass() 加载。
  4. 自己也找不到，就抛出 ClassNotFoundException。
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                if (parent != null) {
                    c = parent.loadClass(name, false);
                } else {
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // 父加载器无法加载
            }
            if (c == null) {
                c = findClass(name);
            }
        }
        if (resolve) {
            resolveClass(c);
        }
        return c;
    }
}

要点：

  • "双亲"是翻译的叫法，实际是单亲，每个加载器只有一个 parent。
  • 父子关系是组合（parent 字段），不是继承。
  • 双亲委派是 JVM 推荐的模型，不是强制约束，可以被打破。
  • JDK 9 起，平台和应用类加载器会先根据类所在的模块找到负责的加载器，再进行委派。

双亲委派有什么好处？

  • 避免重复加载：父加载器已经加载过的类，子加载器不会再加载一次，同一个类在 JVM 中只有一份由同一加载器定义的 Class。
  • 保证核心类库的安全：java.lang.Object、java.lang.String 等核心类总是由启动类加载器加载。即使用户在 classpath 写了一个同名的 java.lang.String，请求也会先委派到启动类加载器，加载到的是 JDK 自带的版本，恶意或错误的类无法替换核心 API。此外 JVM 禁止用户类加载器定义 java.* 包下的类（defineClass 会抛 SecurityException）。
  • 保证类的一致性：类的唯一性由"类加载器 + 全限定名"决定。双亲委派让同一个类在各处都由同一个加载器加载，避免出现同名但不相容的两个类（例如 ClassCastException: X cannot be cast to X）。
  • 层次清晰：每个加载器只负责自己的范围，职责分明。

怎么打破双亲委派？高频

双亲委派的逻辑写在 ClassLoader.loadClass() 中，要打破它，就要自定义类加载器并重写 loadClass()，让它不先委派父加载器（或改变委派顺序）。只重写 findClass() 不会打破双亲委派，因为 loadClass() 仍然先走父加载器。

@Override
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            if (name.startsWith("java.")) {
                c = super.loadClass(name, false);  // 核心类仍交给父加载器
            } else {
                try {
                    c = findClass(name);           // 先自己加载
                } catch (ClassNotFoundException e) {
                    c = super.loadClass(name, false);
                }
            }
        }
        if (resolve) resolveClass(c);
        return c;
    }
}

典型的打破场景：

  • SPI 与线程上下文类加载器：JDBC 的 DriverManager 由启动类加载器加载，但 MySQL 驱动等实现在 classpath 上，启动类加载器看不到。于是 ServiceLoader 通过 Thread.currentThread().getContextClassLoader()（默认是应用类加载器）去加载实现类，相当于父加载器反过来请求子加载器。JNDI、JAXP 也类似。
  • Tomcat：每个 Web 应用的 WebappClassLoader 先加载自己 WEB-INF 下的类，再委派父加载器，实现应用隔离。
  • OSGi / 热部署：每个模块一个类加载器，按网状依赖委派，替换模块时连同类加载器一起替换。
  • JDK 9 模块化：委派前先判断类属于哪个模块，交给对应的加载器，也不再是严格的自下而上。

Tomcat 为什么要打破双亲委派？高频

一个 Tomcat 会部署多个 Web 应用，它们需要彼此隔离，还要和 Tomcat 自身的类隔离，严格的双亲委派做不到这一点。

需要解决的问题：

  • 应用之间的隔离：应用 A 依赖 Spring 5，应用 B 依赖 Spring 6，同名类必须能各自加载自己的版本。如果统一由应用类加载器按双亲委派加载，先加载的版本会被所有应用共用。
  • 共享公共类库：多个应用都用的相同版本的类库，应该只加载一份，节省内存。
  • 容器与应用隔离：Tomcat 自己依赖的类不应被应用看到或覆盖。
  • 热部署：JSP 修改后、应用重新部署时，需要丢弃旧类重新加载，这要求每个应用（甚至每个 JSP）有自己的类加载器。

Tomcat 的类加载器结构：

  • Bootstrap → System（加载 Tomcat 启动所需的类）→ Common（Tomcat 和所有应用共享的 lib 目录）。
  • Common 下有 Catalina（Tomcat 内部私有）和 Shared（应用间共享，默认合并进 Common）。
  • 每个 Web 应用一个 WebappClassLoader，每个 JSP 一个 JasperLoader。

WebappClassLoader 的加载顺序：

  1. 先查本地缓存是否已加载。
  2. 先交给 Bootstrap / Platform 加载 JDK 核心类，防止应用覆盖 java.* 等类。
  3. 再自己在 WEB-INF/classes、WEB-INF/lib 中查找。
  4. 找不到才委派给 Common 等父加载器。

所以 Tomcat 并不是完全抛弃双亲委派：JDK 核心类仍然向上委派，只是应用自己的类优先由自己加载（可以通过 <Loader delegate="true"/> 改回父优先）。由于类的唯一性由"类加载器 + 全限定名"决定，不同 WebappClassLoader 加载的同名类在 JVM 中是不同的类，从而实现隔离。

影响范围 堆是共享的，一个线程触发 OOM 往往意味着其他线程也分配不到内存 通常只影响出错的那个线程
排查 Heap Dump + MAT 分析大对象和引用链 看异常栈中重复出现的方法，找到递归点

容易混淆的点：同样和栈有关，递归太深是 StackOverflowError；线程太多，无法再为新线程分配栈空间，则是 OutOfMemoryError: unable to create native thread。调大 -Xss 能缓解前者，但会让后者更容易发生，因为每个线程占用的栈变大了。

栈溢出会影响其他进程吗？高频

一般不会。操作系统为每个进程分配独立的虚拟地址空间，一个 JVM 进程里发生栈溢出，不会破坏其他进程的内存。

对当前 JVM 的影响：

  • StackOverflowError 是在单个线程里抛出的，线程栈私有，默认只会让当前线程的调用失败；没有被捕获时该线程终止，其他线程和 JVM 进程通常继续运行。
  • 但要注意间接影响：如果它发生在 main 线程且没有其他非守护线程，JVM 会退出；如果业务线程持有锁时异常退出，synchronized 会自动释放锁，但 Lock 没在 finally 中释放就可能让其他线程永久阻塞；线程池中的工作线程也会因此被替换。

可能导致整个 JVM 进程退出的情况：

  • JNI 调用的本地代码发生栈溢出或段错误，JVM 直接崩溃并生成 hs_err_pid.log。
  • JVM 自身的内部错误。
  • 代码调用 System.exit() 或 Runtime.getRuntime().halt()。
  • 进程内存超过限制，被操作系统 OOM Killer 杀死。

对其他进程的间接影响：只存在于资源层面，例如一个进程疯狂创建线程或占用大量 CPU、内存，会挤占同一台机器上其他进程的资源，但这不是栈溢出本身直接造成的。

什么是内存泄漏？哪些情况会导致内存泄漏？阿里

内存泄漏（Memory Leak）是指对象已经不再被使用，但仍然被某条从 GC Roots 出发的引用链持有，导致 GC 无法回收。泄漏不断积累，堆使用率越来越高，Full GC 后也降不下来，最终 OOM。

内存泄漏与内存溢出：泄漏是原因（该释放的没释放），溢出是结果（内存不够了）。溢出不一定是泄漏造成的，也可能只是堆太小或者瞬时数据量太大。

常见原因：

  • 静态集合：static Map/List 只放不删，生命周期与类相同，元素永远不会被回收。
  • 无上限的本地缓存：用 HashMap 做缓存却没有过期和容量淘汰，应使用 Caffeine、Guava Cache 等带淘汰策略的缓存。
  • ThreadLocal 未 remove：线程池中线程长期存活，ThreadLocalMap 中的 value 一直被持有。
  • 监听器、回调未注销：注册到全局事件总线的监听器没有移除，对象一直被引用。
  • 资源未关闭：数据库连接、Statement、ResultSet、流、Socket 没关闭，同时占用堆外资源。用 try-with-resources。
  • 长生命周期对象持有短生命周期对象：单例、Spring Bean 中把请求级对象存进成员变量。
  • 对象放入 HashSet 后修改了参与 hashCode 计算的字段：之后 remove 找不到它，对象一直留在集合里。
  • 内部类持有外部类引用：非静态内部类、匿名内部类（如线程、Handler）隐式持有外部类实例，导致外部对象无法释放。
  • 线程未终止：创建了线程或线程池却不关闭，线程以及它引用的对象都无法回收。
  • 类加载器泄漏：热部署时旧类加载器被引用，导致元空间泄漏。

ThreadLocal 为什么可能导致内存泄漏？

每个 Thread 内部有一个 ThreadLocalMap，它的 Entry 以 ThreadLocal 对象为 key（弱引用），以存入的值为 value（强引用）。在线程长期存活的场景下，value 可能一直无法回收。

泄漏过程：

  1. 引用链是：Thread → ThreadLocalMap → Entry → value，以及 Entry --弱引用--> ThreadLocal。
  2. 当外部不再持有 ThreadLocal 的强引用时（比如它是个局部变量，或者所在对象被回收），下一次 GC 时作为 key 的 ThreadLocal 被回收，Entry 的 key 变成 null。
  3. 但 value 仍被 Entry 强引用，而 Entry 又被线程的 ThreadLocalMap 持有。只要线程不结束，这个 value 就一直无法访问、也无法回收。
  4. 线程池中的核心线程会一直存活，这类 key 为 null 的 Entry 就会越积越多。

为什么 key 要设计成弱引用：如果 key 是强引用，ThreadLocal 对象本身也会跟着泄漏。用弱引用至少让 ThreadLocal 能被回收，并且 ThreadLocalMap 在 get()、set()、remove() 时会顺带清理 key 为 null 的过期 Entry。但这种清理是被动的、不保证及时，所以不能依赖它。

正确用法：

private static final ThreadLocal<UserContext> CTX = new ThreadLocal<>();

try {
    CTX.set(context);
    // 业务逻辑
} finally {
    CTX.remove(); // 用完必须清理
}
  • 用完后在 finally 中调用 remove()，这是最关键的一点。
  • 一般把 ThreadLocal 声明为 static final，避免重复创建，也让 key 一直有强引用。
  • 线程池场景下不 remove 除了泄漏，还会导致线程复用时读到上一个请求遗留的数据，造成数据错乱，这个问题往往比泄漏更严重。

内存泄漏的排查思路是什么？

思路是：先从监控确认是否泄漏，再拿到 Heap Dump，分析大对象和它的 GC Roots 引用链，最后定位到代码。

  1. 确认现象：老年代使用率阶梯式上升，每次 Full GC 后的"底线"越来越高，最终频繁 Full GC 或 OOM。用 jstat -gcutil <pid> 1000 看 O 和 FGC 的趋势。
  2. 获取堆快照：jmap -dump:live,format=b,file=heap.hprof <pid> 或 jcmd <pid> GC.heap_dump（live 会先触发 Full GC）；或提前配 -XX:+HeapDumpOnOutOfMemoryError。dump 大堆会长时间停顿，线上先摘流量；可先用 jmap -histo:live <pid> | head -20 看对象排行。
  3. 分析快照：用 MAT 看 Leak Suspects 和 Dominator Tree，找 Retained Heap 最大的对象，再查 Path to GC Roots（排除软、弱引用）找到持有者；必要时对比两个时间点的 dump。
  4. 定位修复：常见是静态集合、无上限缓存、ThreadLocal 未 remove、监听器未注销、连接未关闭。修复后看 Full GC 后内存能否回落稳定。

堆内正常但进程 RSS 持续增长，要怀疑堆外泄漏（直接内存、元空间、JNI），用 -XX:NativeMemoryTracking=summary 配合 jcmd <pid> VM.native_memory 分析。

JVM 为什么需要调优？高频

JVM 默认参数已经能满足大多数应用，没有性能问题时不需要刻意调优。但在高并发、低延迟、大内存场景下，GC 的频率和停顿会直接影响响应时间和稳定性，这时才需要调优。

调优的目标：

  • 降低停顿：GC 的 STW 会直接叠加到请求耗时上。例如接口本身 10ms，期间发生一次 50ms 的 Young GC，这次请求就变成约 60ms；秒级 Full GC 会导致大量超时。
  • 减少 GC 频率：尤其是减少 Full GC，降低 GC 占用的 CPU，提高吞吐量。
  • 避免 OOM：合理设置堆、元空间、直接内存和线程栈，防止服务崩溃。
  • 匹配业务特点：根据对象生命周期和流量特征配置堆大小、新生代比例和收集器，提高内存利用率。

三个核心指标：吞吐量、延迟（停顿时间）、内存占用，三者不能同时达到最优，调优是在它们之间根据业务取舍。

原则：调优是最后手段。大多数 GC 问题根源在代码（内存泄漏、大对象、不合理的缓存、一次查询过多数据），应该先优化代码和架构，再调 JVM 参数；任何调整都要基于监控、GC 日志和压测数据，而不是凭经验套参数。

你调优过 JVM 吗？高频

回答时要真实，按"监控发现 → 分析定位 → 针对性优化 → 验证效果"的思路展开。没有独立主导过调优，可以说明系统了解调优思路、参与过线上问题排查。

可以这样回答：

  1. 先说原则：JVM 默认参数能满足大多数场景，没有问题不会随意调整；调优之前先排除代码问题。
  2. 日常监控：关注 GC 次数和耗时（尤其 Full GC）、堆和老年代使用率、元空间使用率、线程数、接口 P99 延迟等指标，并配置告警。
  3. 发现问题：例如 GC 频繁、Full GC 过多、单次 GC 耗时长、接口耗时周期性抖动。
  4. 分析定位：开启 GC 日志（JDK 8 用 -XX:+PrintGCDetails -Xloggc:，JDK 9+ 用 -Xlog:gc*），用 GCeasy 等工具分析；结合 jstat 看各区变化，必要时 Heap Dump 用 MAT 分析。
  5. 针对性优化：内存泄漏就改代码；过早晋升就调大年轻代或 Survivor；元空间不足就调整 MaxMetaspaceSize 或排查动态类生成；停顿过长考虑换 G1 或 ZGC。
  6. 验证：灰度上线后对比 GC 频率、停顿和接口延迟。

最好能准备一个具体案例（场景、现象、原因、方案、效果），比如下面"JVM 调优案例"中的过早晋升、CMS 碎片导致的 Full GC 等。

讲一个 JVM 调优案例高频

回答时按"环境 → 现象 → 分析 → 方案 → 效果"组织。下面三个是 JDK 8 下常见的典型案例。

案例一：年轻代过小，Young GC 和 Old GC 都频繁（ParNew + CMS，JDK 8）

  • 现象：Young GC 每分钟几十次，Old GC 几分钟一次。
  • 分析：为降低单次停顿把年轻代设得很小，Young GC 太频繁，对象还没"死"年龄就涨上去；Survivor 小又让动态年龄阈值很低，短命对象过早晋升。
  • 方案与效果：增大 -Xmn 和 Survivor。单次 Young GC 耗时只略增（耗时取决于存活对象数量而非 Eden 大小），Young GC 和 Old GC 频率都明显下降。

案例二：CMS 碎片导致长耗时 Full GC（ParNew + CMS，JDK 8，延迟敏感接口）

  • 现象：高峰期偶发 Full GC，停顿 1 秒以上，请求超时。
  • 分析：GC 日志中老年代总剩余空间很大，但最大连续空闲块很小，晋升 promotion failed，退化为 Serial Old 单线程 Full GC。
  • 方案：低峰期摘流量后主动触发一次整理式 Full GC，降低高峰期发生概率；长期方案是升级到 G1。

案例三：G1 停顿目标过小导致 Young GC 频繁

  • 分析：MaxGCPauseMillis 设成 20ms，G1 为满足目标自动缩小年轻代，Young GC 变频繁、吞吐下降。
  • 方案：调回 100~200ms，去掉手动 -Xmn，让 G1 自适应年轻代大小。

频繁 Full GC 可能是什么原因？如何排查？

常见原因：

  • 内存泄漏：静态集合、缓存、ThreadLocal 持续持有对象，每次 Full GC 回收很少。
  • 大对象或瞬时大量数据：查全表、导出大文件、大报文，迅速填满老年代。
  • 过早晋升：年轻代或 Survivor 太小，短命对象大量进入老年代。
  • 堆本身太小：业务增长后原 -Xmx 不够。
  • 元空间不足：动态生成大量类。
  • 显式 System.gc()：代码、第三方库或 RMI 定时 GC。
  • 收集器相关：CMS 碎片导致 promotion failed、Concurrent Mode Failure；G1 Mixed GC 跟不上分配速度退化为 Full GC。

排查步骤：

  1. 看 GC 日志：确认频率、耗时、GC cause（Allocation Failure、Metadata GC Threshold、System.gc()、promotion failed 等）和每次 Full GC 后老年代剩余量。
  2. jstat 实时观察：jstat -gcutil <pid> 1000 看 Old、Metaspace 和 FGC 变化。
  3. 判断类型：
    • Full GC 后底线越来越高：泄漏，dump 分析。
    • 能降下来但老年代涨得快：过早晋升或大对象，看年龄分布（-Xlog:gc+age=trace）。
    • Metaspace 接近上限：查动态类生成和类加载器泄漏。
    • cause 是 System.gc()：找调用方，或开 -XX:+ExplicitGCInvokesConcurrent。
  4. Dump 分析：MAT 看 Dominator Tree 和 GC Roots 引用链定位代码。
  5. 对症处理：修复泄漏、分页限制数据量；调整 -Xmx、-Xmn、SurvivorRatio、元空间；JDK 8 + CMS 考虑升级 G1。改后观察 Full GC 频率是否回落。

线上 OOM 如何排查？蚂蚁阿里巴巴拼多多招商银行

排查步骤：

  1. 止血：重启、摘流量或扩容，重启前确认 dump 已生成（或手动 jcmd GC.heap_dump），保留 GC 日志和应用日志。
  2. 看错误类型定位区域：
    • Java heap space / GC overhead limit exceeded：堆，重点分析 dump。
    • Metaspace：动态类生成或类加载器泄漏，jcmd <pid> VM.classloader_stats 查看。
    • Direct buffer memory：检查 Netty ByteBuf 是否释放、MaxDirectMemorySize、DisableExplicitGC。
    • unable to create native thread：jstack 统计线程数和线程名，查线程池配置和 ulimit -u。

GC 问题排查的真实场景

以 API 网关（JDK 8，ParNew + CMS，堆 5G）为例：CMS GC 1 小时近 20 次，偶发数秒 Full GC。根因是晋升太多太快（内部减少晋升和泄漏，外部调大 Survivor），长耗时 Full GC 则是 CMS 退化为 Serial Old 单线程整理。

场景一：配置定时全量更新。现象：摘流量后老年代仍每小时规律上涨。原因：配置中心每小时全量推送几万条配置且逐条打日志。处理：改增量更新、减少日志。

场景二：threshold 退化为 1。现象：promotion failed 引发长 STW。原因：日志 new threshold 1 (max 15)，年龄 1 的对象就超过 Desired survivor size（= Survivor × TargetSurvivorRatio，默认 50%），存活对象全部晋升。

场景三：大响应体。现象：只有大流量机器出现，日志有 concurrent mode failure 和 promotion failed。原因：解码转换大响应体产生大对象，提前晋升。处理：推动业务方治理大响应体。

场景四：增大新生代和 Survivor。现象：治理后 CMS GC 仍每天约 20 次。原因：Survivor 不足 250MB。处理：-Xmn 2G 调到 3G，SurvivorRatio 8 改 4，Survivor 512MB，threshold 不再退化。

场景五：CMS 碎片化。现象：老年代剩余超过 2G，却因 65538 字节的对象 promotion failure。原因：Max Chunk Size 只有约 64KB。处理：低峰期摘流量后主动触发整理式 Full GC。

-XX:+UseConcMarkSweepGC -XX:CMSInitiatingOccupancyFraction=80
Full GC 耗时 703ms，触发时老年代约 50%，回收后降到 750MB
Young GC：存活 183MB，耗时 0.02s；Desired survivor size 358MB，new threshold 15

分析：年轻代健康（threshold 保持 15）；老年代 50% 就"Full GC"而阈值 80%，要先看 cause，可能是没设 UseCMSInitiatingOccupancyOnly，或监控把 CMS 并发回收算成 Full GC；回收后降得多，不是泄漏；13G 堆加堆外已接近 16G，有 OOM Killer 风险。

建议：加 UseCMSInitiatingOccupancyOnly；堆缩到约 10G；更推荐换 G1 并去掉 -Xmn；压缩响应体；先灰度一台再推广。

JVM 中容易混淆的概念有哪些？

  1. 方法区与永久代 / 元空间：方法区是规范，永久代（JDK 7 及之前）和元空间（JDK 8+）是 HotSpot 的实现。
  2. 元空间不在堆中：元空间使用本地内存，只存类元数据；JDK 7 起字符串常量池和静态变量已经在堆中，不在元空间。
  3. 对象不一定在堆上：逃逸分析后可以通过标量替换避免堆分配（HotSpot 并没有真正的栈上分配）。
  4. TLAB 不是独立区域：TLAB 属于 Eden，只优化分配过程的并发竞争，不保证对象线程安全。
  5. Young GC 也会 STW：所有收集器的 Young GC 都要暂停用户线程，只是时间较短。
  6. CMS 的代价：低停顿，但有内存碎片、浮动垃圾和 Concurrent Mode Failure 的风险；JDK 14 已被移除。
  7. G1 不是整代回收：G1 按 Region 管理，优先回收收益最高的 Region，Mixed GC 只回收部分老年代。
  8. ClassNotFoundException 与 NoClassDefFoundError：前者是受检异常，发生在显式按名称加载时；后者是 Error，发生在编译时存在、运行时找不到类定义时。
  9. 打破双亲委派：要重写 loadClass()；只重写 findClass() 仍然遵循双亲委派。
  10. Full GC 不等于 Old GC：Full GC 回收整个堆和元空间，停顿通常更长；只有 CMS 有独立的 Old GC。
  11. StackOverflowError 不是 OOM：递归太深是 StackOverflowError，线程太多无法分配栈才是 OOM。
  12. JMM 与 JVM 内存结构：JMM 是并发可见性和有序性的规范，内存结构是运行时数据区的划分，两者不是一回事。

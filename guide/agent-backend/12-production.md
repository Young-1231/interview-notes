## 12. 生产环境全景：把前面的知识拼起来 {进阶}
> 前面各章分别解决一个问题;生产环境要求它们同时成立。本章按「一次请求从进来到结束」把各章串起来,再给出上线前的检查清单和常见事故的处理方式。

### 一次 Run 在生产环境里经历了什么
以「调研 X 公司并发邮件」为例,把每一步用到的机制标出来:

| 阶段 | 发生了什么 | 依赖的机制 |
| --- | --- | --- |
| 接入 | 网关/Nginx 终止 TLS,转发到 API;API 校验 JWT,检查该用户的 QPS 和 token 配额 | §1 鉴权与限流、§8 Redis 计数、§7 认证 |
| 创建 | 带 `Idempotency-Key` 请求头创建 Run,重复提交返回同一个 `run_id`;同一事务里写 Run 和 outbox 记录 | §3 事务与唯一约束、§9 Outbox |
| 排队 | 投递任务消息;队列积压时新任务排队而不是压垮下游模型接口 | §9 队列、削峰 |
| 领取 | Worker 原子地把 Run 改为 `running`,写入租约持有者和过期时间,开始定期心跳 | §10 租约与心跳、§3 `SKIP LOCKED` |
| 推理 | 调用模型:连接复用、单次调用超时、429 按 `Retry-After` 退避、主模型不可用时切换备用模型 | §2 超时、§4 重试与降级、§11 连接池 |
| 工具 | 只读工具并发执行并限制并发度;工具参数在服务端按 schema 校验;工具使用最小权限凭证 | §2 并发、§7 工具权限 |
| 副作用 | `send_email` 进入审批或带幂等键执行;结果不确定时查询状态,不盲目重发 | §4 幂等、§7 人工确认 |
| 检查点 | 每个 Step 完成后落库;Worker 被杀后,新 Worker 接手并从最后一个完成的 Step 继续 | §4 Checkpoint、§10 故障恢复 |
| 推送 | 事件写入 Redis Stream,API 通过 SSE 推给前端,断线后按 `Last-Event-ID` 补发 | §1 SSE、§8 Streams |
| 结束 | Run 置为终态,记录 token 用量和成本;释放租约;发出完成通知 | §3 状态机、§5 成本指标 |
| 观测 | 全链路 Trace 带 `run_id`;慢步骤、错误率、成本异常触发告警 | §5 可观测性 |

### 生产架构的几个关键决定
- **API 与 Worker 分开部署、分开扩容**。API 是大量长连接(SSE)、计算很轻;Worker 是长任务、受模型接口限速约束。两者的瓶颈不同,扩容依据也不同:API 看连接数和 CPU,Worker 看队列积压和等待时间。
- **API 保持无状态**。任何实例都能处理任何请求;SSE 连接落在哪个实例都能从 Redis Stream 读到事件。这样发布、扩缩容时连接断开,客户端重连到其他实例也能续上。
- **数据库是唯一真相源,其他都可以重建**。队列消息丢了,可以由定时任务扫描「`queued` 太久」的 Run 重新投递;Redis 丢了,取消标记和事件缓冲可以从数据库状态恢复或降级处理。
- **对外部依赖都设上限**:每次调用有超时、每个任务有总时长上限、每个用户有并发和 token 配额、每种工具有调用次数上限。Agent 可能陷入循环调用工具,没有上限就会把成本和下游打爆。
- **成本是一等指标**。按 Run、用户、模型统计 token 和费用;对单个 Run 设置 token 或步数上限,超过就终止并提示。

### 上线前检查清单
**接入与安全**
- 所有接口都有认证;用户只能访问自己的 Run(查询条件里带 `user_id`,而不是只按 `run_id` 查)。
- API Key 等密钥来自 Secret 管理或环境变量,不进代码仓库、不进镜像、不进 Prompt、不进日志。
- 工具按角色白名单开放;有副作用的工具有参数校验、金额/次数限制,高危操作需要人工确认;工具调用写审计日志。
- 读取外部内容(网页、文档)后的工具调用受限,防御间接 Prompt 注入。

**可靠性**
- 模型和工具调用都有超时;重试有次数上限、指数退避和抖动;只对可重试错误重试。
- 写操作工具有幂等键,数据库有唯一约束兜底。
- 每个 Step 落库;Worker 崩溃后任务能被接手并从检查点继续;有清理「卡住的 Run」的定时任务。
- 取消能生效:从用户点击到任务停止有明确的最长时间。
- 优雅停机:收到 SIGTERM 后停止领取新任务,等待当前步骤完成或写检查点,再释放租约退出。

**可观测与运维**
- 日志结构化并带 `run_id`、`trace_id`;敏感信息脱敏。
- 有核心指标看板:成功率、各阶段延迟分位数、首 token 时间、队列积压、错误率、token 与成本。
- 有告警:错误率突增、队列积压、单任务成本异常、模型接口持续 429。
- 部署可回滚;数据库迁移向后兼容(先加列、再改代码、最后删旧列)。

### 常见事故与处理思路
| 现象 | 常见原因 | 处理思路 |
| --- | --- | --- |
| 大量 Run 卡在 `running` | Worker 崩溃后租约没有过期机制,或心跳线程被阻塞 | 租约 + 心跳;定时扫描过期租约;心跳不要和阻塞调用跑在同一个线程/事件循环里 |
| 用户收到重复邮件 | 超时后直接重试了有副作用的工具;消息重投后被重复执行 | 幂等键 + 唯一约束;执行前检查 ToolCall 状态;结果未知时查询而不是重发 |
| 模型接口持续 429 | 并发过高,所有 Worker 同时重试形成重试风暴 | 全局限流(按 token 和请求数)、退避加抖动、重试预算、按优先级排队 |
| SSE 不出字、最后一次性全部出来 | 反向代理缓冲了响应 | 关闭代理缓冲(Nginx `proxy_buffering off` 或响应头 `X-Accel-Buffering: no`);定期发心跳注释 |
| 发布时进行中的任务失败 | 进程被直接杀掉,没有优雅停机 | 处理 SIGTERM;设置足够的停机等待时间;依靠检查点让新实例接手 |
| 单个任务成本异常高 | 模型反复调用同一工具,陷入循环 | 步数/token 上限;检测重复的工具调用;成本告警 |
| 某次任务特别慢但不知道原因 | 只有零散日志,没有串起来 | 全链路 Trace,按 Span 耗时定位是排队、模型、工具还是数据库 |

### 规模变大之后
- **流量更大**:API 和 Worker 水平扩容;数据库读写分离或分区(按时间分区 `agent_step` 这类增长快的表);历史数据归档。
- **任务更长、更复杂**:考虑 Temporal 这类持久化执行(durable execution)引擎,把重试、超时、状态持久化、恢复交给框架,而不是自己用租约和检查点拼。
- **多租户**:按租户隔离配额、队列和数据;大客户可以用独立的 Worker 池,避免互相影响。
- **多模型、多供应商**:引入模型网关统一做路由、限流、计费、降级和日志。

### 自测
- **API 和 Worker 为什么要分开部署?** 两者瓶颈不同:API 承载大量轻量长连接,Worker 执行长任务且受模型限速约束;分开后可以按各自指标独立扩容,发布和故障也互不影响。
- **怎样保证「用户只能看到自己的 Run」?** 在数据访问层强制带上 `user_id` 条件(或使用行级安全策略),不能只靠前端隐藏或只按 `run_id` 查询。
- **发布新版本时,正在执行的长任务怎么办?** Worker 收到 SIGTERM 后停止领取新任务,当前步骤完成或写入检查点后释放租约退出;新 Worker 领取后从检查点继续;前端 SSE 断线后自动重连续读。
- **Agent 陷入循环反复调用工具,怎么防?** 设置单个 Run 的最大步数、最大 token 和最长时长;检测连续重复的相同工具调用;对成本异常告警。
- **什么时候该考虑 Temporal 这类引擎?** 当任务很长、步骤多、需要可靠的定时与重试、并且自研租约和检查点的维护成本越来越高时;代价是引入新的基础设施,并要遵守它对确定性代码的约束。

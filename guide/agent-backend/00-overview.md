## 0. 总览：Agent 服务的后端全景 {必学}
> 一个能交给别人用的 Agent,本质是一个「会调用模型和工具的长任务系统」:后端要解决的是怎么接请求、怎么跑长任务、失败了怎么办、出了问题怎么查、权限怎么管。

### 为什么 Agent 开发离不开后端
写一个能在笔记本里跑通的 Agent 很容易:一个循环,调模型、解析工具调用、执行工具、把结果喂回去,直到模型给出最终答案。但把它做成**别人可以用的服务**,立刻会遇到一串和模型无关的问题:

| 现象 | 背后的后端问题 | 对应章节 |
| --- | --- | --- |
| 任务要跑两分钟,浏览器先超时断开了 | 长任务不能挂在一个 HTTP 请求里;结果要流式推送 | [§1](#c1) Web、[§9](#c9) 队列 |
| 三个工具串行调用太慢,用户点了停止却停不下来 | 并发、超时、取消 | [§2](#c2) 异步 |
| 服务重启后,跑到一半的任务没了,也不知道跑到哪一步 | 任务状态、每一步的输入输出要落库 | [§3](#c3) 数据库 |
| 模型接口偶尔 429/超时;邮件工具超时后重试,用户收到两封 | 有限重试、退避、幂等、检查点 | [§4](#c4) 可靠性 |
| 用户说「这次特别慢」,却说不清慢在哪 | 日志、指标、Trace 串起一次任务 | [§5](#c5) 可观测性 |
| 换台机器就跑不起来;API Key 写在代码里 | 容器化、配置与 Secret 管理 | [§6](#c6) 部署 |
| 模型被网页里的一段话诱导去调用了不该调用的工具 | 鉴权、工具权限、Prompt 注入防护、审计 | [§7](#c7) 安全 |

这些问题传统后端也有,但 Agent 场景把它们放大了:**任务更长、每一步都可能失败、模型输出不可信、工具可能有副作用、成本按 token 计**。本页就是围绕这些放大的难点来组织的。

### 贯穿全文的例子
所有章节都用同一个例子讲解,便于把知识点串起来:

**研报助手 Agent**:用户提交「调研 X 公司,整理成报告并发邮件给我」。

- 工具:`web_search`(只读)、`query_db`(只读,查内部数据)、`send_email`(**有副作用**,不能随便重试)。
- 一次任务叫一个 **Run**;Run 由多个 **Step** 组成,每个 Step 是一次 LLM 调用或一次工具调用;每次工具调用记录为一条 **ToolCall**。
- 任务耗时几十秒到几分钟,中间过程用 SSE 流式推给前端,用户可以随时点「停止」。

### 总体架构
<!-- svg:arch -->

图中编号就是一次 Run 的完整链路:

1. **客户端提交任务**:`POST /runs`,API 完成鉴权、限流、参数校验。
2. **落库**:在 `agent_run` 里插入一条 `status='queued'` 的记录。数据库是整个系统的**唯一真相源**,其他组件里的状态都可以丢,它不能丢。
3. **入队并立即返回**:把 `run_id` 投递到任务队列,接口返回 `202 Accepted` 和 `run_id`,不等任务跑完。
4. **Worker 领取任务**:Worker 用带租约的方式把 Run 改成 `running`(保证同一时刻只有一个 Worker 在跑它),开始 Agent Loop。
5. **调用模型和工具**:模型决定下一步;只读工具可以并发调用;每次调用都有超时,失败按策略有限重试;`send_email` 这类写操作带幂等键,高危操作先进入人工审批。
6. **每一步落库**:每完成一个 Step 就写入 `agent_step` / `tool_call`(这就是检查点),Worker 崩溃后可以从最后一步恢复,而不是从头再来。
7. **推送过程事件**:Worker 把 token 增量、工具开始/结束等事件写入 Redis Stream;持有 SSE 连接的 API 实例读出来推给前端,断线后凭 `Last-Event-ID` 续上。
8. **取消**:用户点停止 → API 写取消标记 → Worker 在步骤之间检查到后取消进行中的调用,把 Run 置为 `cancelled`。

全程的日志、指标和 Trace 都带上 `run_id`,一次任务从 API 到队列、Worker、模型、工具、数据库能串成一条完整的调用链。

### 一次任务的状态机
<!-- svg:states -->

状态只在数据库里改,并且每次修改都带条件(如 `WHERE id=? AND status='running'`),检查影响行数,防止两个进程同时推进同一个 Run。[§3](#c3) 讲具体 SQL,[§10](#c10) 讲 Worker 崩溃、租约过期后怎么安全地接手。

### 自测
- **为什么说数据库是 Agent 服务的「唯一真相源」?** 队列消息可能重投、Redis 可能丢数据、Worker 可能崩溃,只有数据库里持久化的 Run/Step 状态是可信的;其他组件都应能根据它重建或纠正。
- **长任务为什么要先返回 202 再异步执行?** HTTP 连接会被网关、代理或客户端超时断开,发布重启也会中断请求;异步执行后进度通过 SSE 推送、状态通过查询接口获取,连接断了任务也不丢。
- **Agent 后端相比普通 CRUD 后端,多了哪些难点?** 任务长且多步、每一步都可能失败、模型输出不可信需要校验、工具可能有副作用需要幂等和审批、需要流式输出和随时取消、成本按 token 计需要计量和限额。
- **Redis 和消息队列是一开始就必须上的吗?** 不是。单实例、小流量时数据库加进程内后台任务就够;多实例需要共享限流/取消状态时引入 Redis,需要独立 Worker、可靠重试和削峰时引入任务队列。

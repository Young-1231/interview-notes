OSI七层模型和TCP/IP四层模型的结构及作用高频

结论:OSI 从下到上是物理层、数据链路层、网络层、传输层、会话层、表示层、应用层;TCP/IP 四层是网络接口层、网络层、传输层、应用层。教学中常用折中的五层模型。

OSI 七层 作用 典型协议/设备 TCP/IP 四层
应用层 为应用程序提供网络服务 HTTP、DNS、FTP、SMTP、SSH 应用层
表示层 数据格式转换、编码、压缩、加密 JPEG、ASCII,TLS 常被归入这一层附近 应用层
会话层 建立、管理、终止会话 RPC 会话管理 应用层
传输层 端到端(进程到进程)通信,端口寻址 TCP、UDP 传输层
网络层 IP 寻址、路由选择、分组转发 IP、ICMP、路由器 网络层
数据链路层 相邻节点间的帧传输,MAC 寻址,差错检测 以太网、PPP、交换机 网络接口层
物理层 在介质上传输比特流 网线、光纤、集线器 网络接口层

五层模型:应用层、传输层、网络层、数据链路层、物理层,即把 OSI 上三层合并为应用层,保留下面两层的区分。

数据单元:应用层叫报文(message),传输层 TCP 叫报文段(segment)、UDP 叫数据报(datagram),网络层叫分组/包(packet),链路层叫帧(frame),物理层是比特(bit)。

OSI 是理论参考模型,TCP/IP 是实际使用的协议栈。

HTTP工作在哪一层？TCP呢？常见协议分别在哪一层？高频

结论:HTTP 在应用层,TCP 在传输层。

层 常见协议
应用层 HTTP、HTTPS、DNS、FTP、SMTP、POP3、IMAP、SSH、WebSocket
传输层 TCP、UDP(QUIC 基于 UDP,在用户态实现传输层功能)
网络层 IP、ICMP、IGMP
数据链路层 以太网、PPP、ARP(ARP 直接封装在以太网帧中,教材多把它归在网络层,也有说法归在链路层)
物理层 网线、光纤、无线电信号等传输介质的电气规范

HTTPS 是 HTTP 运行在 TLS 之上,TLS 位于应用层和传输层之间。

IP报文和MAC帧分别解决什么问题？

结论:IP 解决跨网络的端到端寻址和路由,MAC 解决当前链路上下一跳交给哪块网卡。

  • IP 地址是逻辑地址,标识主机在网络中的位置。数据包从源到目的的整个过程中,源 IP 和目的 IP 一般不变(经过 NAT 时会被改写)。
  • MAC 地址是网卡的硬件地址,只在一个广播域(局域网)内有效。每经过一个路由器,帧会被重新封装,源 MAC 和目的 MAC 都会变成这一跳的设备。
  • 两者配合:主机根据目的 IP 判断是否在同一网段,同网段直接 ARP 查目标的 MAC;不同网段则 ARP 查网关的 MAC,把帧发给网关,由路由器逐跳转发。

一句话:IP 负责「最终送到哪」,MAC 负责「下一步交给谁」。

ARP协议是什么？工作原理是什么？

结论:ARP(Address Resolution Protocol)根据 IP 地址查询同一局域网内对应的 MAC 地址。

工作流程

  1. 主机 A 要给 IP 为 B 的主机发数据,先查本地 ARP 缓存,有就直接用。
  2. 缓存没有,A 广播 ARP 请求(目的 MAC 为 FF:FF:FF:FF:FF:FF):「谁是 IP B?请告诉 A」,请求中带有 A 的 IP 和 MAC。
  3. 局域网内所有主机都会收到,只有 IP 匹配的 B 回复 ARP 响应,以单播方式把自己的 MAC 发给 A;B 也会顺便缓存 A 的映射。
  4. A 把 IP → MAC 映射写入 ARP 缓存(有过期时间),之后按这个 MAC 封装帧。

跨网段:目标不在同一网段时,A 查询的是默认网关的 MAC,帧发给网关转发。

相关点

  • 免费 ARP(Gratuitous ARP):主机询问自己的 IP,用于检测 IP 冲突和通告 MAC 变化。
  • ARP 欺骗:ARP 没有认证,攻击者可以伪造响应把流量引到自己这里,是中间人攻击的常见手段。
  • IPv6 不使用 ARP,改用 NDP(邻居发现协议)。

TCP和UDP的区别是什么？各自的应用场景有哪些？高频

结论:TCP 面向连接、可靠、面向字节流,有流量控制和拥塞控制;UDP 无连接、不保证可靠、面向报文,开销小、实时性好。

维度 TCP UDP
连接 面向连接,三次握手建立 无连接,直接发送
可靠性 保证不丢、不重、按序到达 尽最大努力交付,可能丢包、乱序
传输形式 面向字节流,无消息边界 面向报文,保留消息边界
流量/拥塞控制 有 没有
首部开销 20~60 字节 固定 8 字节
通信方式 只支持一对一 支持一对一、一对多、多对多,支持广播和多播
状态 需要维护连接状态 无状态
速度 较慢 较快

应用场景

  • TCP:可靠性优先,如 HTTP/1.1、HTTP/2、HTTPS、FTP、SMTP、SSH、数据库连接。
  • UDP:实时性优先或请求-响应很短,如 DNS 查询、音视频通话、直播、在线游戏、DHCP、QUIC/HTTP/3。

补充:UDP 本身不可靠,但应用层可以在 UDP 上自己实现可靠传输,QUIC 就是例子。

有哪些协议是基于TCP的？哪些基于UDP？高频

结论:需要可靠传输的协议基于 TCP;追求低延迟、或交互短小的协议基于 UDP。

  • 基于 TCP:HTTP/1.x、HTTP/2、HTTPS(TLS over TCP)、WebSocket、FTP、SMTP、POP3、IMAP、SSH、Telnet、MySQL 和 Redis 的客户端协议。
  • 基于 UDP:DNS 查询(默认)、DHCP、SNMP、NTP、TFTP、RTP 音视频、QUIC 和 HTTP/3。
  • 两者都用:DNS 一般查询用 UDP 53;响应超过 UDP 允许的大小(无 EDNS0 时为 512 字节)会被截断并设置 TC 标志,客户端改用 TCP 53 重查;主从之间的区域传送(AXFR/IXFR)也用 TCP。

TCP和UDP可以使用同一个端口吗？高频

结论:可以。TCP 和 UDP 是两个独立的协议,各自维护自己的端口空间,TCP 80 和 UDP 80 互不冲突。

  • 内核按「协议 + IP + 端口」区分监听和连接,收到数据包时先根据 IP 头里的协议字段交给 TCP 或 UDP 模块,再按端口查找对应的 socket。
  • 典型例子:DNS 同时监听 UDP 53 和 TCP 53;HTTP/3 场景下服务器同时监听 TCP 443(HTTP/1.1、HTTP/2)和 UDP 443(QUIC)。

延伸:同一协议下,多个 TCP 连接也可以共用同一个服务端端口,因为 TCP 连接由四元组(源 IP、源端口、目的 IP、目的端口)唯一标识。多个进程监听同一端口需要 SO_REUSEPORT(Linux 3.9 起支持)。

在浏览器中输入URL到页面呈现,整个过程发生了什么？涉及哪些协议？高频

结论:URL 解析 → 查缓存 → DNS 解析 → 建立 TCP 连接(HTTPS 还要 TLS 握手)→ 发送 HTTP 请求 → 服务器处理并响应 → 浏览器解析渲染 → 连接复用或关闭。

  1. 解析 URL:确定协议、域名、端口、路径;域名在 HSTS 列表中时直接改用 https。
  2. 查缓存:强缓存(Cache-Control/Expires)命中且未过期就不发请求。
  3. DNS 解析:浏览器缓存 → 操作系统缓存(含 hosts)→ 本地 DNS,本地 DNS 再迭代查询根、顶级域、权威服务器。
  4. 建立连接:TCP 三次握手;HTTPS 再做 TLS 握手(TLS 1.3 为 1-RTT,TLS 1.2 为 2-RTT);HTTP/3 基于 UDP 的 QUIC,传输和 TLS 1.3 握手合并,首次 1-RTT。
  5. 发送 HTTP 请求:请求行、请求头(Host、Cookie、If-None-Match 等)、请求体。
  6. 网络传输:逐层封装(ARP 获取网关 MAC),经路由器逐跳转发,中间可能经过 CDN、负载均衡、Nginx。
  7. 服务器处理:返回状态码、响应头、响应体;协商缓存命中返回 304。
  8. 浏览器渲染:HTML 构建 DOM,CSS 构建 CSSOM,合成渲染树后布局、绘制、合成;普通 <script> 会阻塞 HTML 解析(defer/async 不阻塞)。
  9. 连接处理:HTTP/1.1 默认 keep-alive 复用,空闲超时后四次挥手关闭。

涉及的协议:HTTP/HTTPS、TLS、DNS、TCP 或 UDP(QUIC)、IP、ARP,以及链路层的以太网等。

DNS的域名解析过程是什么？高频

结论:先查各级本地缓存,未命中时由本地 DNS 服务器从根域名服务器开始迭代查询,最终从权威域名服务器拿到 IP,结果沿途缓存。

  1. 浏览器缓存:浏览器缓存的 DNS 记录。
  2. 操作系统缓存:包括 hosts 文件(如 /etc/hosts)。
  3. 本地 DNS 服务器(递归解析器,通常由运营商或公共 DNS 如 8.8.8.8、114.114.114.114 提供):客户端对它发起递归查询,有缓存直接返回。
  4. 本地 DNS 没有缓存,开始迭代查询:
    • 问根域名服务器,得到 .com 顶级域名服务器的地址。
    • 问 .com 顶级域名服务器,得到 example.com 权威域名服务器的地址。
    • 问权威域名服务器,得到 www.example.com 的 IP(或 CNAME,需要继续解析)。
  5. 本地 DNS 把结果按 TTL 缓存,返回给客户端,客户端也会缓存。

递归 vs 迭代

  • 客户端 → 本地 DNS:递归查询,本地 DNS 负责给出最终结果。
  • 本地 DNS → 根/顶级/权威:迭代查询,每一级只告诉「下一步去问谁」。

补充

  • DNS 默认基于 UDP 53 端口,响应被截断时改用 TCP。
  • 常见记录类型:A(IPv4)、AAAA(IPv6)、CNAME(别名,CDN 常用)、MX(邮件)、NS(权威服务器)、TXT。
  • 加密 DNS:DoH(DNS over HTTPS)、DoT(DNS over TLS),防止被窃听和篡改。

CDN是什么？

结论:CDN(Content Delivery Network,内容分发网络)把内容缓存到离用户更近的边缘节点,用户就近访问,降低延迟、减轻源站压力。

工作原理

  1. 网站把域名 CNAME 到 CDN 厂商的域名。
  2. 用户解析域名时,请求被转到 CDN 的智能调度 DNS(GSLB),根据用户 IP 所在地域、运营商、节点负载返回最合适的边缘节点 IP。
  3. 用户访问边缘节点:命中缓存直接返回;未命中则回源站拉取,缓存后返回。
  4. 缓存过期按 Cache-Control 或 CDN 配置的 TTL,内容更新时可以主动刷新或预热。

好处

  1. 降低访问延迟,提高下载速度。
  2. 分担源站带宽和负载。
  3. 提高可用性,单节点故障可以切换。
  4. 一定程度抵御 DDoS。

适用资源:图片、视频、CSS、JS、安装包等静态资源;也支持动态加速(优化回源链路)。

注意:静态资源文件名带内容哈希(如 app.3f2a1c.js),发布新版本时不用担心 CDN 缓存旧文件。

TCP连接管理 8高频 6

详细描述TCP三次握手的过程高频

结论:SYN → SYN+ACK → ACK。三次握手交换并确认双方的初始序列号(ISN),同时确认双方收发能力正常。

假设客户端初始序列号为 x,服务端为 y:

  1. 第一次握手:客户端发送 SYN 报文,SYN=1, seq=x,进入 SYN_SENT。
  2. 第二次握手:服务端回复 SYN+ACK,SYN=1, ACK=1, seq=y, ack=x+1,进入 SYN_RCVD(Linux 中显示为 SYN_RECV)。
  3. 第三次握手:客户端回复 ACK,ACK=1, seq=x+1, ack=y+1,进入 ESTABLISHED;服务端收到 ACK 后也进入 ESTABLISHED。

要点

  • SYN 报文虽然不携带数据,但会消耗一个序列号,所以确认号是 x+1、y+1。
  • 第一、二次握手不能携带应用数据;第三次握手可以携带数据。
  • ISN 是随机生成的(基于时钟和四元组哈希),防止旧连接的报文被误认,也增加伪造报文的难度。

各次握手确认的能力

  • 第一次后:服务端确认「客户端能发、自己能收」。
  • 第二次后:客户端确认「自己能发能收、服务端能发能收」。
  • 第三次后:服务端确认「自己能发、客户端能收」。

相关:半连接队列和全连接队列

  • 服务端收到 SYN 后,连接放入半连接队列(SYN 队列);收到第三次 ACK 后移入全连接队列(accept 队列),等待应用调用 accept() 取走。
  • 全连接队列长度取 listen() 的 backlog 与 net.core.somaxconn 的较小值。
  • SYN Flood 攻击就是伪造大量 SYN 占满半连接队列,常用防护是开启 net.ipv4.tcp_syncookies。

为什么握手是三次,不是两次或四次？高频

结论:三次是保证双方都确认对方初始序列号、并能阻止历史连接的最少次数。两次不够,四次没必要。

为什么不是两次

  1. 阻止历史连接(RFC 793 给出的首要原因):客户端先发的旧 SYN 因网络滞留,在新 SYN 之前到达服务端。如果两次握手,服务端回复 SYN+ACK 后就直接建立连接、分配资源,甚至发送数据,浪费资源。三次握手时,客户端收到 SYN+ACK 后发现确认号不对,会回复 RST 终止这个历史连接。
  2. 同步双方初始序列号:序列号是可靠传输的基础。客户端的 ISN 由服务端的 ACK 确认,服务端的 ISN 也必须由客户端的 ACK 确认。两次握手时服务端无法知道客户端是否收到了自己的 ISN。
  3. 避免资源浪费:两次握手下,客户端每次重发 SYN,服务端都会建立一个新连接。

为什么不是四次:服务端的 ACK(确认客户端 SYN)和 SYN(发送自己的 ISN)可以合并在一个报文里发送,所以三次就够了,拆开成四次只是多一次往返。

TCP四次挥手的过程是怎样的？高频

结论:FIN → ACK → FIN → ACK。主动关闭方最后进入 TIME_WAIT,等待 2MSL 后才彻底关闭。

以客户端主动关闭为例:

  1. 第一次挥手:客户端发送 FIN,FIN=1, seq=u,进入 FIN_WAIT_1,表示自己不再发送数据。
  2. 第二次挥手:服务端回复 ACK,ack=u+1,进入 CLOSE_WAIT;客户端收到后进入 FIN_WAIT_2。此时连接处于半关闭状态,服务端仍可以继续向客户端发送数据。
  3. 第三次挥手:服务端数据发送完毕,应用调用 close(),发送 FIN,FIN=1, seq=v,进入 LAST_ACK。
  4. 第四次挥手:客户端回复 ACK,ack=v+1,进入 TIME_WAIT,等待 2MSL 后进入 CLOSED;服务端收到 ACK 后立即进入 CLOSED。

要点

  • FIN 和 SYN 一样消耗一个序列号。
  • FIN_WAIT_2 状态如果长期收不到对方的 FIN,Linux 中由 net.ipv4.tcp_fin_timeout(默认 60 秒)控制超时(针对调用 close() 后的孤儿连接)。
  • 主动关闭方不一定是客户端,服务端也可以主动关闭。

状态口诀

  • 主动方:ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED
  • 被动方:ESTABLISHED → CLOSE_WAIT → LAST_ACK → CLOSED

为什么挥手需要四次,而握手只需三次？高频

结论:TCP 是全双工的,两个方向需要分别关闭。被动方收到 FIN 时可能还有数据没发完,所以 ACK 和 FIN 通常不能合并发送。

  • 握手时,服务端收到 SYN 后没有其他事情要做,可以立刻把 ACK 和自己的 SYN 合并成一个 SYN+ACK 报文。
  • 挥手时,主动方发 FIN 只代表「我不再发数据了」,但还能接收。被动方要先回 ACK 告诉对方「收到了」,然后继续发完剩余数据,等应用层调用 close() 后才发送自己的 FIN。ACK 由内核立即回复,FIN 的时机由应用决定,两者之间可能间隔很久,所以一般分开发送,共四次。

四次挥手会退化成三次吗？

结论:会。被动方收到 FIN 时如果没有数据要发,并且开启了 TCP 延迟确认(Linux 默认开启),ACK 可以和自己的 FIN 合并为一个 FIN+ACK 报文,挥手就变成 FIN → FIN+ACK → ACK。

条件

  • 被动方在延迟确认的时间窗口内(Linux 最小 40ms 左右)已经没有待发送数据,且应用很快调用了 close()。
  • 抓包时经常能看到三次挥手,就是这个原因。

同时关闭

  • 双方同时发 FIN,都进入 FIN_WAIT_1;收到对方 FIN 后回 ACK 并进入 CLOSING;收到对方 ACK 后进入 TIME_WAIT。
  • 这种情况仍然交换四个报文,但双方都会进入 TIME_WAIT,属于特殊情形,不是「退化成三次」。

TIME_WAIT是什么？为什么要等待2MSL？高频

结论:TIME_WAIT 是主动关闭方发送最后一个 ACK 后进入的状态,持续 2MSL。目的有两个:保证最后的 ACK 能被对方收到(丢了可以重传),以及让本连接的旧报文在网络中全部消失,不干扰后续相同四元组的新连接。

MSL:Maximum Segment Lifetime,报文在网络中的最大生存时间。RFC 793 建议为 2 分钟,实际实现常用 30 秒到 1 分钟。Linux 中 TIME_WAIT 时长固定为 60 秒(内核宏 TCP_TIMEWAIT_LEN,不能通过 sysctl 修改)。

原因 1:保证被动方能正常关闭

  • 如果最后一个 ACK 丢失,被动方在 LAST_ACK 状态超时后会重发 FIN。
  • 主动方还在 TIME_WAIT,可以收到重发的 FIN 并再次回复 ACK(同时重置 2MSL 计时)。
  • 如果主动方直接关闭,收到重发的 FIN 会回 RST,被动方会以异常方式结束连接。

原因 2:防止旧连接的报文混入新连接

  • 如果立刻用相同四元组建立新连接,网络中延迟的旧报文可能恰好落在新连接的接收窗口内,被当作有效数据。
  • 等待 2MSL 能保证两个方向上的旧报文都已经过期消失。

为什么是 2MSL:最后一个 ACK 最多存活 1 个 MSL 到达对方;如果它丢了,对方重发的 FIN 最多再经过 1 个 MSL 到达。一来一回最长 2MSL。

服务器上出现大量TIME_WAIT是什么原因？有什么影响？怎么解决？高频

结论:大量 TIME_WAIT 说明本机作为主动关闭方频繁关闭短连接。影响主要是占用端口(作为客户端时)和内存等资源,解决优先改用长连接,其次调整内核参数。

常见原因

  1. HTTP 短连接(没开 keep-alive),或 keep-alive 空闲超时、达到最大请求数,由服务端主动关闭。
  2. 本机作为客户端频繁访问下游(Nginx 到上游、调用 Redis/MySQL 没用连接池),每次新建并主动关闭。

影响

  • 端口耗尽:主要发生在本机作为客户端时。连向同一目的 IP + 端口只能靠本地端口区分,临时端口范围由 net.ipv4.ip_local_port_range 决定(默认 32768~60999),占满就无法建新连接。服务端监听端口不会因此耗尽。
  • 占用内存、socket 结构和 conntrack 表项。

解决方案

  1. 改用长连接(根本办法):keep-alive、HTTP/2、Nginx 上游 keepalive、连接池。
  2. 让客户端主动关闭,把 TIME_WAIT 分散到客户端。
  3. net.ipv4.tcp_tw_reuse=1:只对主动发起连接的一方生效,复用 TIME_WAIT 超过 1 秒的端口,依赖 tcp_timestamps=1。
  4. 扩大 ip_local_port_range;tcp_max_tw_buckets 限制总数(粗暴)。
  5. 不推荐:tcp_tw_recycle 在 NAT 下出问题,Linux 4.12 已移除;SO_LINGER 超时设 0 直接发 RST,可能丢数据。

注意:tcp_fin_timeout 控制的是 FIN_WAIT_2 的超时,不能缩短 TIME_WAIT。

CLOSE_WAIT过多是什么原因？

结论:CLOSE_WAIT 是被动关闭方收到对方 FIN 并回复 ACK 后的状态,需要应用主动调用 close() 才会发 FIN 离开。大量 CLOSE_WAIT 几乎都是应用程序没有及时关闭连接导致的,问题在本机代码。

常见原因

  1. 代码没有关闭 socket,比如异常分支没走到 close()。
  2. 连接池中的连接已被对端关闭,但应用没有检测和回收,也没有归还连接。
  3. 业务线程阻塞(死锁、慢 SQL、下游超时),迟迟走不到关闭逻辑。
  4. 使用 HTTP 客户端时没有关闭响应流(如 Apache HttpClient 没有 close 响应或消费完实体)。

排查与解决

  • ss -tanp | grep CLOSE-WAIT 或 netstat -anp 找到对应进程和对端地址,判断是哪类连接。
  • jstack 查看线程是否阻塞。
  • 代码层面用 try-with-resources 或在 finally 中关闭连接;连接池开启空闲检测和有效性校验。
  • 内核没有针对 CLOSE_WAIT 的超时回收,只能由应用关闭或进程退出后释放。

TCP是如何保证可靠传输的？高频

结论:靠连接管理、序列号与确认应答、超时重传和快速重传、校验和、流量控制、拥塞控制共同保证数据不丢、不重、不乱、不错。

  1. 连接管理:三次握手同步双方初始序列号,四次挥手可靠释放连接。
  2. 序列号:每个字节都有序列号。接收方据此按序重组、丢弃重复数据,乱序到达的数据先缓存。
  3. 确认应答(ACK):接收方返回累计确认号,表示该序号之前的数据都已收到。可以配合 SACK(选择性确认)告诉发送方哪些段已经收到,只重传缺失部分。
  4. 超时重传:发送后启动定时器,超时(RTO,根据 RTT 动态计算)未收到 ACK 就重传,每次重传 RTO 翻倍。
  5. 快速重传:连续收到 3 个重复 ACK,不等超时直接重传缺失的报文段。
  6. 校验和:首部和数据的校验和,检测传输中的比特错误,出错直接丢弃,等待重传。
  7. 流量控制:接收方通过窗口字段告诉发送方自己还能接收多少,防止接收缓冲区溢出。
  8. 拥塞控制:根据网络状况调整拥塞窗口,避免网络拥塞导致大面积丢包。

什么是TCP滑动窗口？它的作用是什么？

结论:滑动窗口允许发送方在收到确认前连续发送一个窗口大小的数据,收到 ACK 后窗口向前滑动。它既提高了传输效率,也是实现流量控制的手段。

为什么需要:如果每发一个报文都要等 ACK 再发下一个(停等协议),一个 RTT 只能发一个报文,带宽利用率很低。

发送窗口的四部分

  1. 已发送且已确认。
  2. 已发送但未确认(在窗口内)。
  3. 未发送但允许发送(在窗口内)。
  4. 未发送且不允许发送(窗口外)。

收到 ACK 后,左边界右移,窗口向前滑动,新的数据进入可发送范围。

接收窗口:接收方根据剩余缓冲区大小,在 TCP 首部的窗口字段(16 位,配合窗口扩大选项 Window Scale 可以超过 64KB)中通告给发送方。

作用

  1. 提高吞吐:可以连续发送多个报文,流水线传输。
  2. 流量控制:发送窗口受接收方通告窗口限制,接收方处理不过来时可以缩小窗口,甚至通告零窗口暂停发送。
  3. 配合累计确认,一个 ACK 可以确认多个报文,部分 ACK 丢失不影响。

零窗口:接收方通告窗口为 0 后,发送方启动持续计时器,定期发送窗口探测报文,防止窗口更新报文丢失导致双方死等。

TCP流量控制和拥塞控制有什么区别？分别由谁控制？高频

结论:流量控制防止发送方把接收方压垮,拥塞控制防止发送方把网络压垮。两者最终都由发送方执行,实际发送窗口 = min(rwnd, cwnd)。

TCP的拥塞控制机制有哪些？详细说一下高频

结论:经典的 Reno 拥塞控制包括慢启动、拥塞避免、快速重传、快速恢复四个算法,围绕拥塞窗口 cwnd 和慢启动阈值 ssthresh 工作。

1. 慢启动

  • 连接建立后 cwnd 从一个较小的初始值开始。早期标准是 1 个 MSS,RFC 6928 将初始窗口提高到 10 个 MSS,Linux 2.6.39 起默认 10。
  • 每收到一个 ACK,cwnd 增加 1 个 MSS,效果是每个 RTT 翻倍,指数增长。
  • 当 cwnd 达到 ssthresh 时,进入拥塞避免。

2. 拥塞避免

  • 每收到一个 ACK,cwnd 增加 1/cwnd 个 MSS,效果是每个 RTT 增加 1 个 MSS,线性增长。

3. 发生拥塞时

  • 超时重传:说明网络拥塞严重。ssthresh = cwnd / 2,cwnd 重置为 1 个 MSS(RFC 5681 规定的丢失窗口),重新慢启动。
  • 收到 3 个重复 ACK:说明只是个别报文丢失,网络还能传输。触发快速重传和快速恢复。

4. 快速重传

  • 收到 3 个重复 ACK 时,不等 RTO 超时,立即重传丢失的报文段。

5. 快速恢复

  • ssthresh = cwnd / 2,cwnd = ssthresh + 3(3 个重复 ACK 说明已有 3 个报文离开网络)。
  • 之后每收到一个重复 ACK,cwnd 加 1;收到新数据的 ACK 后,cwnd = ssthresh,进入拥塞避免,线性增长。

算法演进

  • Reno、NewReno:上面描述的经典算法,基于丢包。
  • CUBIC:Linux 2.6.19 起的默认算法,cwnd 按三次函数增长,适合高带宽长延迟网络。
  • BBR:Google 提出,Linux 4.9 引入,基于测量瓶颈带宽和最小 RTT 控制发送速率,不以丢包作为拥塞信号。

慢启动和拥塞避免有什么区别？高频

结论:慢启动阶段 cwnd 指数增长,快速探测可用带宽;拥塞避免阶段 cwnd 线性增长,谨慎逼近网络容量。分界点是 ssthresh。

维度 慢启动 拥塞避免
触发时机 连接建立后、超时重传后 cwnd ≥ ssthresh 时
增长方式 每个 ACK +1 MSS,每 RTT 翻倍 每个 ACK +1/cwnd MSS,每 RTT +1 MSS
目标 快速找到可用带宽 避免过快增长引起拥塞

注意:「慢启动」的「慢」是指起点小,不是增长慢,它实际上是指数增长。

TCP粘包/拆包问题是如何产生的？如何解决？高频

结论:TCP 是面向字节流的协议,不保留应用层的消息边界。多条消息可能被一次读到(粘包),一条消息也可能被分多次读到(拆包)。需要由应用层协议自己定义消息边界。

产生原因

  1. 发送端:Nagle 算法会把多个小数据合并发送;应用写入的数据大于发送缓冲区剩余空间或 MSS 时会被拆分发送。
  2. 接收端:应用读取不及时,多个报文的数据堆积在接收缓冲区,一次 read() 读出多条;或者读缓冲区比消息小,一条消息要读多次。
  3. 根本原因:TCP 只保证字节有序可靠,本身没有「消息」概念。

解决方案

  1. 固定长度:每条消息固定字节数,不足补齐。简单但浪费空间。
  2. 特殊分隔符:用换行符等标记消息结束,如 Redis RESP、HTTP 头部的 \r\n。消息内容中需要转义分隔符。
  3. 长度字段(最常用):消息头固定字段存储消息体长度,接收方先读头,再按长度读消息体,如 HTTP 的 Content-Length、各种 RPC 协议。
  4. 使用成熟协议:HTTP、WebSocket、gRPC(HTTP/2 帧)等。Netty 提供了 FixedLengthFrameDecoder、LineBasedFrameDecoder、DelimiterBasedFrameDecoder、LengthFieldBasedFrameDecoder 等解码器。

注意:UDP 面向报文,一次 recvfrom() 读一个完整数据报,有消息边界,不存在粘包问题。

TCP为什么是面向字节流的？

结论:TCP 把应用层写入的数据看作一串无结构的字节序列,只负责把这串字节可靠、有序地交给对端,发送时怎么切分报文段由 TCP 根据 MSS、窗口、Nagle 等自行决定。

  • 应用调用一次 write() 写入的数据,可能被拆成多个报文段,也可能和前后数据合并成一个报文段。
  • 接收方一次 read() 拿到的字节数,与发送方 write() 的次数没有对应关系。
  • 对比 UDP:应用每次 sendto() 发送一个完整的数据报,接收方每次 recvfrom() 收到一个完整数据报,边界保留。

这就是粘包和拆包问题的根源。粘包不是 TCP 的缺陷,而是应用层没有处理消息边界。

TCP Nagle算法是什么？

结论:Nagle 算法用于减少网络上的小包:只要还有已发送但未确认的数据,新的小数据就先在缓冲区攒着,等收到 ACK 或攒够一个 MSS 再发送。

规则

  1. 如果数据量达到 MSS,立即发送。
  2. 如果没有未确认的数据,立即发送。
  3. 否则缓存起来,直到收到前面数据的 ACK 或数据量达到 MSS。

优缺点

  • 优点:减少大量小包(如 Telnet 每次只发 1 个字节,TCP/IP 头部就有 40 字节),提高网络利用率。
  • 缺点:增加延迟。和接收方的延迟确认(Delayed ACK)叠加时,可能出现几十到上百毫秒的额外延迟。

关闭方式:设置 socket 选项 TCP_NODELAY。Java 中是 socket.setTcpNoDelay(true),Netty 中是 ChannelOption.TCP_NODELAY。RPC、游戏、实时交互等低延迟场景通常关闭 Nagle。Linux 默认开启 Nagle。

HTTP是什么？

结论:HTTP(HyperText Transfer Protocol,超文本传输协议)是应用层的请求-响应协议,用于客户端和服务器之间传输超文本、图片、JSON 等各种数据。它本身是无状态的。

特点

  1. 请求-响应模型:客户端发起请求,服务器返回响应,服务器不能主动发起请求(HTTP/2 的服务器推送也必须依附于某个客户端请求)。
  2. 无状态:协议不保存之前请求的信息,每个请求都是独立的。需要保持会话时用 Cookie、Session、Token 等机制。
  3. 灵活可扩展:通过 Content-Type 可以传输任意类型数据,头部可以自定义扩展。
  4. 基于可靠传输:HTTP/1.x 和 HTTP/2 基于 TCP,HTTP/3 基于 QUIC(UDP)。

报文结构

  • 请求:请求行(方法、URL、版本)+ 请求头 + 空行 + 请求体。
  • 响应:状态行(版本、状态码、原因短语)+ 响应头 + 空行 + 响应体。
  • HTTP/2 起改为二进制帧,但语义不变。

当前标准:HTTP 语义统一定义在 RFC 9110(2022),各版本的报文格式分别在 RFC 9112(HTTP/1.1)、RFC 9113(HTTP/2)、RFC 9114(HTTP/3)中定义。

结论:根本区别在语义:GET 用于获取资源,是安全且幂等的;POST 用于提交数据让服务器处理,既不安全也不幂等。其余区别大多是约定和实现带来的,不是协议的强制规定。

HTTP是无状态的,怎么保持登录状态？Cookie、Session、Token有什么区别？

结论:常见三种方案:Cookie + Session(服务端存状态)、Token/JWT(客户端携带凭证,服务端校验)。Cookie 是浏览器端的存储和自动携带机制,Session 是服务端的会话存储,Token 是服务端签发的访问凭证。

  • JWT 为 Header.Payload.Signature,服务端只校验签名,无需存储,适合分布式。

WebSocket是什么？

结论:WebSocket(RFC 6455)是基于 TCP 的全双工通信协议,通过一次 HTTP 升级握手建立连接后,客户端和服务端可以随时互相推送消息,适合实时场景。

握手过程

  1. 客户端发送 HTTP/1.1 GET 请求,携带 Upgrade: websocket、Connection: Upgrade、Sec-WebSocket-Key(随机 Base64 值)、Sec-WebSocket-Version: 13。
  2. 服务端返回 101 Switching Protocols,带上 Sec-WebSocket-Accept(对 Key 拼接固定 GUID 后做 SHA-1 再 Base64)。
  3. 之后同一条 TCP 连接切换为 WebSocket 帧格式通信。

特点

  • 全双工、服务端可主动推送。
  • 帧头很小(2~14 字节),比 HTTP 轮询每次带完整头部节省开销。
  • 支持文本帧和二进制帧,有 Ping/Pong 控制帧用于心跳保活。
  • ws:// 默认 80 端口,wss:// 基于 TLS,默认 443 端口。
  • 自带消息边界,应用层不需要处理粘包。

和其他实时方案对比

  • 短轮询:定时发请求,延迟高、浪费资源。
  • 长轮询:服务端挂起请求直到有数据,仍然每次都要重建请求。
  • SSE(Server-Sent Events):基于 HTTP 的服务端单向推送,实现简单,适合通知、大模型流式输出等只需服务端推送的场景。
  • WebSocket:双向实时,适合即时聊天、在线游戏、实时行情、协同编辑。

HTTP/2有什么缺陷？

结论:最大的问题是 TCP 层的队头阻塞:所有 Stream 共用一条 TCP 连接,一个 TCP 报文丢失会阻塞所有 Stream。此外还有 TCP + TLS 握手延迟和无法连接迁移的问题。

  1. TCP 队头阻塞:TCP 是可靠有序的字节流,丢了一个报文段,后面已经到达的数据也只能留在内核缓冲区,不能交给应用,必须等重传。HTTP/2 中多个 Stream 的帧交错在同一个字节流里,一个包丢失就会卡住全部 Stream。丢包率高时,HTTP/2 的表现甚至可能不如开多个连接的 HTTP/1.1。
  2. 建连延迟:TCP 握手 1-RTT,加上 TLS 1.2 握手 2-RTT(TLS 1.3 为 1-RTT),首次请求前需要 2~3 个 RTT。
  3. 无法连接迁移:TCP 连接由四元组标识,手机从 Wi-Fi 切到 4G,IP 变化后连接断开,需要重新握手。
  4. 协议僵化:TCP 在操作系统内核中实现,改进需要升级内核,中间设备也会干扰新特性的部署。

这些问题由 HTTP/3 和 QUIC 解决。

HTTP/3做了哪些优化？

结论:HTTP/3(RFC 9114,2022 年)把传输层从 TCP 换成基于 UDP 的 QUIC(RFC 9000,2021 年),解决了 TCP 队头阻塞,建连更快,并支持连接迁移。

  1. 消除 TCP 队头阻塞:QUIC 在一个连接内实现多个独立 Stream,每个 Stream 单独保证有序,一个 Stream 丢包只阻塞这个 Stream,不影响其他 Stream。
  2. 更快的建连:QUIC 把传输握手和 TLS 1.3 握手合并在一起,首次连接 1-RTT 就能发送请求数据;恢复之前的会话可以 0-RTT,第一个包就带上应用数据。0-RTT 数据有被重放的风险,一般只用于幂等请求。
  3. 连接迁移:QUIC 用连接 ID(Connection ID)而不是四元组标识连接,客户端 IP 或端口变化(网络切换、NAT 重绑定)后,只要连接 ID 能对上就可以继续使用原连接。
  4. 强制加密:内置 TLS 1.3,不仅加密数据,大部分 QUIC 包头也被加密或认证,中间设备难以篡改。
  5. 改进的可靠传输:QUIC 在用户态实现了确认、重传、流量控制和可插拔的拥塞控制。包号严格递增,重传使用新包号,消除了 TCP 中「重传歧义」导致的 RTT 估算不准问题。
  6. 头部压缩 QPACK:HPACK 依赖严格有序传输,在 QUIC 中会重新引入队头阻塞,所以改用 QPACK。

怎么启用:客户端通常先用 HTTP/1.1 或 HTTP/2 连接,服务器在响应头 Alt-Svc 中声明支持 h3,或在 DNS 的 HTTPS 记录中声明,之后客户端再尝试 QUIC;如果 UDP 被拦截会回退到 TCP。

一句话:QUIC ≈ TCP 的可靠传输 + TLS 1.3 + HTTP/2 的多路复用,在 UDP 之上的用户态实现。

QUIC为什么基于UDP？

结论:因为 TCP 无法改,新的传输层协议又过不了现有网络,所以选择在 UDP 之上的用户态重新实现可靠传输。

  1. TCP 改不动:TCP 在操作系统内核中实现,新特性需要升级各端操作系统,推广周期以年计;而且中间设备(NAT、防火墙、负载均衡)会检查甚至改写 TCP 头,不认识的新选项可能被丢弃,这叫协议僵化(ossification)。
  2. 新的传输协议过不去:像 SCTP 这样的新传输层协议,大量中间设备只认识 TCP 和 UDP,无法穿透。UDP 几乎所有网络都能通过。
  3. UDP 足够简单:UDP 只提供端口复用和校验和,不干预上层逻辑,QUIC 可以在其上完全自定义可靠传输、多路复用、拥塞控制和加密。
  4. 用户态实现,迭代快:QUIC 作为库集成在浏览器和服务器中,升级应用就能升级协议,拥塞控制算法也可以灵活替换。

代价

  • 部分企业网络和运营商会限速或拦截 UDP 443,客户端需要回退到 TCP。
  • 用户态处理和全加密带来更高的 CPU 开销,内核对 UDP 大流量的优化(如 GSO)也不如 TCP 成熟。
  • 抓包和排障更困难。

HTTPS是怎样加密的？为什么同时使用对称加密和非对称加密？高频

结论:HTTPS 采用混合加密:握手阶段用非对称算法(密钥交换 + 证书签名)安全地协商出会话密钥,数据传输阶段用对称加密。数字证书用来确认服务器公钥确实属于这个网站。

为什么混合

  • 非对称加密(RSA、ECC)不需要提前共享密钥,但计算慢,比对称加密慢几个数量级。
  • 对称加密(AES、ChaCha20)速度快,但密钥本身需要安全地传给对方。
  • 所以用非对称机制安全地交换密钥,再用对称加密传输大量数据。

为什么需要证书

  • 只有公钥还不够:中间人可以把自己的公钥发给客户端,冒充服务器。
  • 证书由 CA 用自己的私钥对「服务器公钥 + 域名 + 有效期等信息」的摘要签名。客户端用操作系统或浏览器内置的根 CA 公钥逐级验证证书链,确认公钥属于该域名。

客户端验证证书的内容

  1. 证书链能追溯到受信任的根 CA,每一级签名都正确。
  2. 证书在有效期内。
  3. 证书的域名(SAN 字段)与访问的域名匹配。
  4. 证书未被吊销(CRL、OCSP 或 OCSP Stapling)。

密钥交换的两种方式

  • RSA 密钥交换(仅 TLS 1.2 及以前):客户端生成预主密钥,用服务器证书中的公钥加密后发送,服务器用私钥解密。缺点是没有前向安全性,服务器私钥一旦泄露,之前抓包的所有流量都能被解密。
  • ECDHE 密钥交换(TLS 1.2 推荐,TLS 1.3 强制):双方各自生成临时的 DH 密钥对并交换公钥,各自计算出相同的共享密钥,预主密钥从未在网络上传输。证书私钥只用来签名,证明身份。每次连接的临时密钥用完即丢,具有前向安全性。

最终会话密钥由双方随机数和预主密钥(或 DH 共享密钥)共同派生。

HTTPS的TLS握手过程是怎样的？TLS 1.2和TLS 1.3有什么区别？高频

结论:TLS 1.2 完整握手 2-RTT;TLS 1.3 删掉不安全算法,客户端第一个消息就带密钥交换参数,完整握手 1-RTT,会话恢复可 0-RTT。

TLS 1.2 握手(ECDHE,2-RTT)

  1. ClientHello:版本、密码套件、Client Random、SNI。
  2. ServerHello + Certificate + ServerKeyExchange + ServerHelloDone:Server Random、证书链、签名后的 ECDHE 临时公钥。
  3. 客户端验证证书,发送 ClientKeyExchange(自己的 ECDHE 公钥),双方结合两个随机数派生会话密钥,再发 ChangeCipherSpec 和 Finished。
  4. 服务器回 ChangeCipherSpec 和 Finished。(RSA 方式改为客户端用服务器公钥加密预主密钥发送。)

TLS 1.3 握手(1-RTT)

  1. ClientHello 直接带 key_share。
  2. ServerHello 带自己的 key_share,双方算出握手密钥,随后加密发送 Certificate、CertificateVerify、Finished。
  3. 客户端验证后发 Finished,同时即可发应用数据。

0-RTT:用 PSK 恢复会话,ClientHello 携带 Early Data;无前向安全、可被重放,只适合幂等请求。

Socket是什么？

结论:Socket 是操作系统提供给应用程序的网络通信编程接口,是通信的端点。一个 TCP 连接由两端的 Socket 组成,通过四元组(源 IP、源端口、目的 IP、目的端口)唯一标识。

Socket 类型

  1. 流式 Socket(SOCK_STREAM):基于 TCP。
  2. 数据报 Socket(SOCK_DGRAM):基于 UDP。
  3. Unix Domain Socket:同一台机器上的进程间通信,不经过网络协议栈,性能更好(如 MySQL、Docker 的本地 socket 文件)。

TCP 编程流程

  • 服务端:socket() → bind() → listen() → accept() 阻塞等待连接 → read()/write() → close()。
  • 客户端:socket() → connect()(触发三次握手) → read()/write() → close()(触发挥手)。
  • listen() 后内核完成三次握手,accept() 只是从全连接队列中取出已建立的连接,返回一个新的已连接 socket,监听 socket 继续监听。

Java 中的对应类:ServerSocket / Socket(BIO,TCP)、DatagramSocket(UDP)、NIO 的 ServerSocketChannel / SocketChannel 配合 Selector。

在 Linux 中,Socket 也是一种文件描述符(fd),可以用 read/write 操作,也能交给 select/poll/epoll 监听。

select、poll、epoll有什么区别？

结论:三者都是 Linux 的 IO 多路复用机制,让一个线程同时监听多个 fd。select 和 poll 每次调用都要把全部 fd 拷贝到内核并线性遍历,复杂度 O(n);epoll 在内核维护关注列表和就绪列表,只返回就绪的 fd,适合大量连接、少量活跃的场景。

fd 存储 固定大小位图 fd_set pollfd 数组 红黑树 + 就绪链表
fd 数量上限 FD_SETSIZE,默认 1024 无固定上限 无固定上限
每次调用拷贝 全部 fd 拷到内核 同 select 不需要,epoll_ctl 一次注册
查找就绪 fd 内核和用户态都要遍历 同 select 回调把就绪 fd 放入就绪链表
时间复杂度 O(n) O(n) O(就绪数)
触发方式 水平触发 水平触发 水平触发(默认)和边缘触发

epoll 的三个接口:epoll_create 创建实例;epoll_ctl 增删改监听的 fd 并注册回调;epoll_wait 把就绪事件拷贝到用户态返回。

常见误区:epoll 不是用 mmap 共享内存返回事件,epoll_wait 仍会拷贝,只是只拷贝就绪的部分。

应用:Nginx、Redis、Netty、Java NIO Selector(Linux 下底层是 epoll)。连接多、活跃比例低时 epoll 优势明显;连接少且都活跃时差距不大。

epoll的LT和ET模式有什么区别？

结论:LT(水平触发)只要 fd 还处于可读/可写状态,每次 epoll_wait 都会通知;ET(边缘触发)只在状态发生变化(如新数据到达)时通知一次,必须一次把数据读完。

计算机网络有哪些容易混淆的点？

  1. HTTP 是应用层协议,TCP 是传输层协议;HTTPS 不是新协议,本质是 HTTP + TLS。
  2. HTTPS 数据传输用对称加密,非对称算法用于密钥交换和证书签名;TLS 1.3 已删除 RSA 密钥交换,只用 (EC)DHE。
  3. TLS 1.2 完整握手 2-RTT,TLS 1.3 为 1-RTT,会话恢复可以 0-RTT。
  4. GET 和 POST 的规范都没有长度限制,限制来自浏览器和服务器实现;明文 HTTP 下两者一样不安全。
  5. TCP 面向字节流,UDP 面向报文;粘包是应用层没处理消息边界,不是 TCP 的缺陷,UDP 没有粘包问题。
  6. 三次握手的首要原因是阻止历史连接并同步双方初始序列号。
  7. 主动关闭方进入 TIME_WAIT,持续 2MSL(Linux 固定 60 秒);被动关闭方进入 CLOSE_WAIT,大量 CLOSE_WAIT 通常是应用没有调用 close()。
  8. tcp_tw_reuse 只对发起连接的客户端生效;tcp_tw_recycle 已在 Linux 4.12 移除;tcp_fin_timeout 控制的是 FIN_WAIT_2,不是 TIME_WAIT。
  9. 流量控制看接收方(rwnd),拥塞控制看网络(cwnd),都由发送方执行,发送窗口 = min(rwnd, cwnd)。
  10. 慢启动是指数增长,「慢」指起点小;超时后 cwnd 回到 1,三个重复 ACK 后 cwnd 减半进入快速恢复。

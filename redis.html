Redis 基础与使用场景 5高频 1

你在项目中用 Redis 做什么？有哪些业务场景？为什么选 Redis 而不是其他缓存？高频

Redis 是基于内存的 KV 数据库，最常见的用途是做缓存，此外还能借助丰富的数据结构做分布式锁、计数器、排行榜、限流、Session 共享等。

常见业务场景

  • 缓存：用户信息、商品详情等热点数据，降低数据库压力。
  • 分布式锁：SET key uuid NX PX 30000 一条命令原子加锁（2.6.12 起支持）；生产上常用 Redisson。
  • 计数器：INCR/HINCRBY 原子自增，如点赞数、阅读量，可先写 Redis 再定时同步数据库。
  • 全局 ID：INCRBY userid 1000 一次取一段号段，用于分库分表。
  • 排行榜：ZSet 以热度为 score，ZREVRANGE 取榜单，ZREVRANK 取排名。
  • 限流：INCR 固定窗口、ZSet 滑动窗口、Lua 令牌桶。
  • 消息队列：List（LPUSH + BRPOP）或 5.0 起的 Stream（消费者组、ACK）。
  • 分布式 Session：Session 存 Redis，应用无状态。

为什么选 Redis（对比 Memcached、本地缓存）

  • 数据结构丰富，Memcached 只有简单 KV。
  • 支持持久化（RDB、AOF、混合），重启可恢复。
  • 主从、Sentinel、Cluster 提供高可用与扩展。
  • 单命令原子执行，配合 Lua 可原子完成复杂逻辑。
  • 内存操作 + I/O 多路复用，单实例可达 10 万级 QPS。

为什么用 Redis 做缓存？为什么不用本地缓存？

Redis 是独立部署的集中式缓存，多个应用实例共享同一份数据；本地缓存只在单个进程内有效。两者不是互斥的，热点数据常常做「本地缓存 + Redis」两级缓存。

对比 本地缓存（Caffeine、Guava） Redis
访问速度 最快，进程内访问，无网络开销 需要一次网络往返，亚毫秒级
数据共享 每个实例各存一份，多实例之间不一致 所有实例共享，一致性好维护
容量 受 JVM 堆限制，过大会加重 GC 可单独扩容，Cluster 可水平扩展
可靠性 应用重启即丢失 支持持久化和主从高可用
功能 简单 KV 丰富数据结构、过期、分布式锁、Pub/Sub 等

不单独用本地缓存的原因：分布式部署下各节点的缓存难以同步，更新时要广播失效；容量受堆内存限制；重启后缓存全部失效，容易产生大量回源。 注意：Redis 是集中式依赖，要做好高可用，并处理穿透、击穿、雪崩问题。

Redis 有事务吗？支持回滚吗？滴滴小红书银行阿里招商银行

Redis 有事务（MULTI、EXEC、DISCARD、WATCH），但不支持回滚，只保证事务内的命令按顺序、不被其他客户端命令插入地执行。

执行流程

  • MULTI 开启事务，之后的命令只入队（返回 QUEUED），不执行。
  • EXEC 一次性按顺序执行队列中的所有命令；DISCARD 放弃事务。
  • WATCH key：乐观锁。被 WATCH 的 key 在 EXEC 之前被其他客户端修改，EXEC 返回 nil，整个事务不执行，业务可以重试。

出错时的行为

  • 入队时就出错（命令不存在、参数个数错误）：2.6.5 起 EXEC 直接拒绝，整个事务都不执行。
  • 执行时出错（如对 String 执行 LPUSH）：只有出错的那条命令失败，其他命令照常执行，已执行的不会回滚。

为什么不支持回滚：运行时错误基本都是编程错误（类型用错），应在开发阶段发现；不做回滚可以保持实现简单、性能高。

补充：Lua 脚本同样能保证执行期间不被其他命令插入，且可以写条件逻辑，实际项目中比 MULTI 更常用；但脚本中途报错，已执行的写操作同样不会回滚。

Redis 管道（Pipeline）有什么作用？

Pipeline 让客户端把多条命令一次性发送给服务端，再一次性读取所有结果，把 N 次网络往返（RTT）压缩成 1 次，大幅提升批量操作的吞吐量。

  • 原理：客户端不等每条命令的响应就继续发送，服务端按顺序执行并把结果缓存起来一起返回。同时也减少了 read/write 系统调用次数。
  • 不保证原子性：Pipeline 中的命令之间可能穿插其他客户端的命令，某条失败不影响其他命令。需要原子性用事务或 Lua 脚本。
  • 注意：单个 Pipeline 不宜过大，否则客户端等待时间长、服务端要缓存大量回复占用内存，一般分批（如每批几百到上千条）发送。Cluster 模式下，Pipeline 中的 key 需要按槽分组发送到对应节点。

如何从海量 key 中找出某一固定前缀的 key？（SCAN）

用 SCAN 渐进式遍历，不要用 KEYS prefix:*。KEYS 会一次性遍历全部 key，在单线程执行模型下会长时间阻塞，线上一般禁用。

SCAN 0 MATCH user:* COUNT 1000
# 返回下一个游标和本批 key，用返回的游标继续 SCAN，直到游标为 0

要点

  • 游标迭代：每次调用只扫描全局哈希表的一小部分桶，返回新游标，直到游标返回 0 才算遍历完整。
  • COUNT 只是提示：表示每次迭代大致要做多少工作量（默认 10），不是返回数量上限。返回的 key 数可能多于或少于 COUNT；带 MATCH 时过滤在扫描之后进行，可能返回空列表但游标还没结束，必须继续迭代。
  • 可能返回重复 key：遍历过程中如果发生 rehash，同一个 key 可能被返回多次，业务侧要去重。遍历期间新增或删除的 key 不保证一定被返回。
  • 集合类型：HSCAN、SSCAN、ZSCAN 用同样方式遍历大集合的元素。
  • Cluster 模式：SCAN 只扫描当前节点，需要对每个主节点分别执行。
  • 更好的做法：如果经常需要按前缀查找，应在业务上额外维护一个索引集合（如 Set），而不是依赖全库扫描。

数据类型与底层结构 6高频 6

Redis 有哪些数据类型？各自特点和使用场景？高频农业银行交通银行

常用的 5 种基本类型是 String、Hash、List、Set、ZSet，另外还有 Bitmap、HyperLogLog、GEO、Stream 等特殊类型。

类型 特点 典型场景
String 可存字符串、整数、浮点数、二进制，单值最大 512MB，支持 INCR 原子自增 缓存对象（JSON）、计数器、分布式锁、Session
Hash field-value 映射，类似 Map<String, String>，可单独读写某个字段 存对象（用户信息、购物车），字段级更新
List 按插入顺序排列，可两端插入、弹出 消息队列（LPUSH + BRPOP）、最新消息列表、时间线
Set 无序、元素唯一，支持交集、并集、差集 标签、去重、共同好友、抽奖
ZSet 元素唯一，每个元素带一个 score，按 score 排序 排行榜、延迟队列、按权重排序
Bitmap（2.2） 基于 String 的位操作 签到、在线状态、布隆过滤器
HyperLogLog（2.8.9） 基数估算，固定约 12KB，标准误差 0.81% UV 统计、独立 IP 数
GEO（3.2） 基于 ZSet 存经纬度（GeoHash 作 score） 附近的人、距离计算
Stream（5.0） 持久化消息流，支持消费者组、ACK 可靠的轻量级消息队列

底层结构（详见下一题）：SDS、listpack（7.0 起全面取代 ziplist）、dict（扩缩容时渐进式 rehash，每次增删改查顺带迁移一个桶）、quicklist、intset、skiplist。

Redis 常见 5 种数据结构的底层实现是什么？高频

每种类型都会根据数据量和元素大小在「紧凑编码」和「通用编码」之间切换，可以用 OBJECT ENCODING key 查看。

类型 底层编码 切换条件（默认配置）
String int、embstr、raw（都基于 SDS） 整数用 int；短字符串（≤ 44 字节）用 embstr，与对象头一次分配；更长用 raw
List quicklist；7.2 起元素少时用 listpack quicklist 节点在 7.0 前是 ziplist、7.0 起是 listpack；7.2 起小列表直接用 listpack
Hash listpack（7.0 前 ziplist）、hashtable 元素数 ≤ 128 且每个值 ≤ 64 字节用 listpack，否则转 hashtable
Set intset、listpack（7.2+）、hashtable 全是整数且数量 ≤ 512 用 intset；7.2 起元素少（≤ 128）且不全是整数时用 listpack；其余用 hashtable
ZSet listpack（7.0 前 ziplist）、skiplist + dict 元素数 ≤ 128 且每个元素 ≤ 64 字节用 listpack，否则用 skiplist + dict

要点

  • SDS 相比 C 字符串：O(1) 获取长度、二进制安全、杜绝缓冲区溢出、预分配减少重分配。
  • listpack 取代 ziplist：ziplist 节点记录前一节点长度，插入大元素可能引发连锁更新；listpack 只记录自身长度，避免了这个问题。
  • 编码只升级不降级：转成 hashtable/skiplist 后，即使元素减少也不会转回紧凑编码。

跳表节点的查询过程是怎样的？高频

跳表是在有序链表上加多级「索引」的结构。查询时从最高层的头节点开始：右边节点小于目标就向右走，大于等于目标（或到头）就下降一层，直到在第 0 层找到目标或确认不存在，平均时间复杂度 O(log N)。

示例：查找 40

Level 2：HEAD ───────────────► 30 ─────────────► NULL
Level 1：HEAD ─────► 10 ─────► 30 ─────► 50 ───► NULL
Level 0：HEAD ─► 10 ─► 20 ─► 30 ─► 40 ─► 50 ─► NULL
  1. Level 2：HEAD 右边是 30，30 < 40，右移到 30；30 右边是 NULL，下降。
  2. Level 1：30 右边是 50，50 > 40，不能右移，下降。
  3. Level 0：30 右边是 40，命中。

Redis 跳表的实现细节

  • 节点按 score 升序排列，score 相同时按 member 字典序排列。
  • 每个节点的层高随机生成：每多一层的概率是 1/4，最大 32 层（5.0 前为 64 层），因此插入、删除无需全局调整，只修改相邻节点指针。
  • 每层指针带 span（跨度），查找过程中累加跨度即可得到排名，所以 ZRANK 也是 O(log N)。
  • 第 0 层有 backward 后退指针，支持 ZREVRANGE 等逆序遍历。

ZSet 用的什么数据结构？为什么用跳表而不用 B+ 树？高频

ZSet 小数据量时用 listpack（7.0 前是 ziplist）；超过阈值（128 个元素或单个元素超过 64 字节）后用 skiplist + dict 组合。

为什么同时用 skiplist 和 dict

  • dict：member → score 的映射，ZSCORE、判断成员是否存在都是 O(1)。
  • skiplist：按 score 有序，支持 ZRANGEBYSCORE 范围查询和 ZRANK 排名，O(log N)。
  • 两者共享同一个 member 对象，不会存两份字符串。

为什么用跳表不用 B+ 树

  • 场景不同：B+ 树的设计目标是减少磁盘 I/O，一个节点对应一个磁盘页，树矮、扇出大；Redis 是纯内存操作，没有磁盘 I/O 的问题，B+ 树的优势用不上。
  • 实现简单：跳表本质是多层链表，代码量小、易调试；B+ 树要处理节点分裂、合并、重平衡，实现复杂。
  • 写入更稳定：跳表插入只需随机层高并修改相邻节点指针，不需要页分裂和数据搬移。
  • 范围查询同样高效：定位到起点后沿第 0 层链表顺序遍历即可，效果和 B+ 树叶子链表类似。
  • 内存可控：平均每个节点约 1.33 个指针（p = 1/4），内存开销不比平衡树大。

跳表 vs 平衡树（红黑树）：两者查找复杂度相当，但红黑树范围查询需要中序遍历，实现也更复杂；跳表范围查询更直接，并发改造也更容易。

用户会话 Session 用什么数据类型存？高频

一般用 String 存序列化后的 JSON，并设置过期时间；如果 Session 里的字段需要频繁单独修改，用 Hash。

SETEX session:token:abc123 1800 '{"userId":1001,"username":"Tom","role":"admin"}'

选 String 的理由

  • 存储简单：Session 一般按 token 整体读取、整体写入，序列化成 JSON 直接存即可。
  • 天然支持过期：SETEX 或 SET ... EX 设置 TTL，和 Session 的有效期机制对应；用户每次访问时刷新 TTL 即可实现滑动过期。
  • 读取效率高：一次 GET 取回全部数据。

选 Hash 的场景：只需更新最后访问时间、权限等个别字段时，HSET 改单个 field，不必反序列化、重写整个对象。注意 Hash 的过期时间只能设在整个 key 上（7.4 起支持 field 级过期 HEXPIRE）。

大模型会话场景：多轮对话消息更适合用 List 按时间顺序 RPUSH，读取时用 LRANGE key -N -1 只取最近 N 条，避免 Session 变成大 key。

Redis 的 Set 是否有序、是否可重复？高频

Set 是无序、不可重复的集合。

  • 无序：元素没有固定顺序，SMEMBERS 的返回顺序不保证一致。intset 编码下内部恰好按整数大小有序存储，但这是实现细节，不能依赖。需要有序请用 ZSet。
  • 不可重复：重复 SADD 同一个元素不会报错，返回 0，集合不变。
  • 底层实现：intset（全是整数且元素少）、listpack（7.2 起，元素少且不全是整数）、hashtable（其他情况，value 为 NULL 的 dict），因此 SADD、SREM、SISMEMBER 平均 O(1)。
  • 常用场景：去重、标签、关注/粉丝、共同好友（SINTER）、抽奖（SRANDMEMBER/SPOP）。

线程模型与性能 7高频 1

Redis 是单线程的，为什么还这么快？高频招商银行农业银行滴滴

先澄清：Redis 只是命令执行是单线程的。快的原因主要有四点：纯内存操作、I/O 多路复用、单线程执行没有锁竞争和上下文切换、底层数据结构高效。

  • 基于内存（最主要原因）：数据都在内存中，读写不涉及磁盘 I/O，单次操作是纳秒到微秒级。
  • I/O 多路复用：用 epoll（Linux）/ kqueue（BSD、macOS）让一个线程同时监听成千上万个连接，只处理已就绪的事件，不用为每个连接建线程。
  • 单线程执行命令：没有多线程的锁竞争、线程切换和上下文切换开销，命令天然串行、原子。
  • 高效的数据结构：SDS、dict（渐进式 rehash）、skiplist、listpack、intset 等，大部分操作是 O(1) 或 O(log N)，小数据量还用紧凑编码节省内存。
  • 瓶颈不在 CPU：多数命令计算量很小，性能瓶颈通常是内存和网络带宽，单线程已足够。

线程模型补充

  • Redis 6.0 起可开启 I/O 多线程（io-threads，默认关闭），把网络读写和协议解析分给多个线程，命令执行仍在主线程。
  • 另有后台 bio 线程负责关闭文件、AOF fsync、lazy free 异步释放内存。
  • RDB 快照和 AOF 重写由 fork 出的子进程完成，不是线程。

Redis 是单线程还是多线程？

不能简单说单线程或多线程：命令执行（读写内存数据）一直是单线程，但整个 Redis 进程从来不是只有一个线程。

版本 变化
早期 网络 I/O 与命令执行都在主线程，靠 I/O 多路复用支撑高并发
2.4 起 引入后台 bio 线程，处理关闭文件、AOF fsync
4.0 起 新增 lazy free：UNLINK、FLUSHALL ASYNC、FLUSHDB ASYNC 以及 lazyfree-* 配置，让大 key 的内存释放交给后台线程
6.0 起 引入网络 I/O 多线程（默认关闭），多个 I/O 线程并行读请求、解析协议、写回响应，命令仍由主线程串行执行

注意区分

  • bgsave、bgrewriteaof 是 fork 出的子进程，利用 Copy-On-Write 生成文件，不是后台线程。
  • 多线程只是用来分担耗时任务和网络 I/O，不会有多个线程同时修改数据，所以 Redis 命令依然不需要加锁、天然原子。

Redis 为什么用单线程执行命令？

因为 Redis 的瓶颈不在 CPU，而在内存和网络 I/O；单线程执行命令能让实现简单、性能稳定，同时避免多线程带来的额外开销。

  • 避免锁竞争：所有数据结构共享在内存中，多线程执行命令就需要对每个结构加锁，既复杂又损耗性能；单线程串行执行天然线程安全，每条命令都是原子的。
  • 减少上下文切换：Redis 命令通常在微秒级完成，多线程切换的开销可能比命令本身还大。
  • 内存操作本身够快：简单命令单线程即可达到每秒 10 万级 QPS。
  • 配合 I/O 多路复用：一个线程即可管理大量连接，并发能力不依赖多线程。
  • 实现与调试简单：没有死锁、竞态问题，数据结构可以针对单线程优化（如渐进式 rehash）。

代价：单个慢命令（KEYS *、大 key 的 HGETALL/DEL、复杂 Lua 脚本）会阻塞所有请求；也无法用多核做计算。多核扩展一般靠部署多个实例或 Cluster。

为什么 Redis 6.0 之后引入多线程？一定比单线程快吗？

6.0 引入的多线程只针对网络 I/O（读 socket、解析协议、写回响应），命令执行仍是单线程。目的是在高并发、网络 I/O 成为瓶颈时利用多核 CPU。

为什么引入

  • 随着硬件发展，单个 Redis 实例在高并发小请求下，CPU 大量时间花在 socket 读写和协议解析上，主线程成为瓶颈，而多核闲置。
  • 把 I/O 交给多个线程并行处理，主线程只专注执行命令，简单命令为主的高并发场景下吞吐量可以明显提升。
  • 命令执行保持单线程，不需要引入复杂的并发控制，兼容原有的原子语义。

配置

io-threads 4            # 默认 1，即关闭；一般设置为小于 CPU 核数，如 4 核设 2~3
io-threads-do-reads yes # 默认只用多线程写回响应，开启后读请求也用多线程

一定比单线程快吗？不一定

  • 适合：高并发、连接多、网络流量大、CPU 核数充足的场景。
  • 帮助不大：QPS 不高时网络本来不是瓶颈；瓶颈在慢命令或大 key（命令执行仍在主线程）；CPU 核数少时线程反而争抢资源。
  • 所以默认关闭，需要压测确认收益后再开启。

Redis 的 IO 多路复用原理是什么？

I/O 多路复用是让一个线程同时监听多个 socket：把所有连接的文件描述符交给内核监听，内核在某些描述符就绪（可读/可写）时通知 Redis，Redis 只处理就绪的连接，从而用单线程处理大量并发连接。

Redis 的事件驱动模型（Reactor）

  • 多路复用器：封装了 epoll / kqueue / evport / select，按平台自动选择效率最高的实现（Linux 下是 epoll）。
  • 事件循环 aeEventLoop：主线程循环调用 epoll_wait 等待事件。
  • 事件分派器与处理器：
    • 连接应答处理器：监听 socket 可读时 accept 新连接，并为它注册读事件。
    • 命令请求处理器：客户端 socket 可读时读取数据、解析命令并执行。
    • 命令回复处理器：结果写入输出缓冲区，socket 可写时发回客户端。
  • 时间事件：同一循环中还处理定时任务 serverCron（过期 key 定期删除、rehash、统计等）。

好处：不用为每个连接创建线程，没有线程切换开销；配合非阻塞 I/O，线程不会阻塞在某个连接的读写上。

IO 多路复用有哪些实现方式？（select / poll / epoll）

常见实现有 select、poll、epoll（Linux），以及 BSD/macOS 上的 kqueue。Redis 在 Linux 上使用 epoll。

对比 select poll epoll
fd 存储 fd_set 位图，有上限（默认 1024） pollfd 数组，没有固定上限 内核红黑树存监听的 fd，就绪链表存就绪 fd
每次调用 把整个 fd 集合从用户态拷贝到内核态 同 select 通过 epoll_ctl 注册一次，epoll_wait 无需重复拷贝
就绪检测 内核线性遍历所有 fd，O(n) 同 select，O(n) 回调机制把就绪 fd 加入就绪链表，O(1) 获取
返回 用户还要再遍历一遍找就绪 fd 同 select 只返回就绪的 fd
触发方式 水平触发 水平触发 支持水平触发（LT）和边缘触发（ET）

结论：select/poll 的开销随连接数线性增长，适合连接少的场景；epoll 只关心活跃连接，在大量连接、少量活跃的场景下性能优势明显。kqueue 是 BSD 系统上的同类实现，机制与 epoll 类似。

Redis 后台线程是做什么的？

Redis 的后台线程（bio，background I/O）用来处理可能阻塞主线程的耗时操作，主要有三类，各有一个线程和任务队列：

  • 关闭文件（BIO_CLOSE_FILE）：如 AOF 重写完成后关闭旧文件，close 大文件可能很慢。
  • AOF 刷盘（BIO_AOF_FSYNC）：appendfsync everysec 时，每秒的 fsync 由后台线程执行。
  • 惰性释放内存（BIO_LAZY_FREE，4.0 起）：UNLINK、FLUSHALL ASYNC、FLUSHDB ASYNC，以及开启 lazyfree-lazy-eviction、lazyfree-lazy-expire、lazyfree-lazy-server-del 等配置后，对淘汰、过期、隐式删除的 key 的内存释放。

容易混淆的点

  • RDB 快照（bgsave）和 AOF 重写（bgrewriteaof）由 fork 出的子进程完成，不是后台线程。
  • 内存淘汰策略的判断和执行在主线程中进行，只有开启 lazyfree-lazy-eviction 后，被淘汰 key 的内存释放才交给后台线程。
  • 6.0 的 I/O 线程是另一套线程，负责网络读写，与 bio 线程不同。

持久化 5高频 5

Redis 持久化机制有哪些？RDB 和 AOF 有什么区别、各自优缺点？高频邮政储蓄银行字节网易

Redis 有三种持久化方式：RDB 快照、AOF 日志，以及 4.0 引入的混合持久化。默认配置下 RDB 开启、AOF 关闭（appendonly no）；两者同时开启时，重启优先用 AOF 恢复。

  • RDB：按条件（save 900 1 等）或手动 bgsave 把某一时刻的内存数据生成压缩的二进制快照文件 dump.rdb。
  • AOF：把每条写命令以 RESP 协议文本追加到日志，重启时按顺序重放。开启后默认 appendfsync everysec。
  • 混合持久化：AOF 重写时先写 RDB 格式的全量数据，再追加增量命令。aof-use-rdb-preamble 从 5.0 起默认 yes。
对比 RDB AOF
内容 某时刻的数据快照（二进制、压缩） 写命令日志（文本）
数据安全 会丢失最后一次快照之后的数据，通常是分钟级 取决于刷盘策略：everysec 最多丢约 1 秒，always 几乎不丢，no 由操作系统决定
文件体积 小，适合备份和全量复制 大，需要定期重写
恢复速度 快，直接加载 慢，要逐条重放命令
性能影响 fork 子进程时有短暂阻塞，数据量大时生成成本高 每次写都要追加，always 策略对性能影响大
可读性 不可读 可读，误操作（如 FLUSHALL）后可手工编辑 AOF 恢复

如何选择：只做缓存可只开 RDB 甚至不开；数据安全要求高时开 AOF（everysec）+ 混合持久化，保留 RDB 做冷备。always 性能下降明显，一般不用。

版本变化：7.0 起为 Multi Part AOF（base 文件 + incr 增量文件 + manifest），重写不再需要重写缓冲区。

RDB 异步持久化（bgsave）的原理是什么？高频

bgsave 由主进程 fork 出子进程，子进程把内存数据写成 RDB 文件，主进程继续处理请求；两者通过操作系统的 Copy-On-Write 共享内存。

触发方式

save 900 1      # 900 秒内至少 1 个 key 被修改
save 300 10     # 300 秒内至少 10 个 key 被修改
save 60 10000   # 60 秒内至少 10000 个 key 被修改
  • 满足 save 条件时自动执行 bgsave；主从全量复制、正常 SHUTDOWN 时也会触发。
  • save 命令：主进程直接执行，期间阻塞所有客户端请求，线上不推荐。
  • bgsave 命令：fork 子进程执行，是常用方式。

执行过程

  1. fork 子进程：主进程 fork 时要复制页表（不复制物理内存），这一步会阻塞主进程，内存越大页表越大，阻塞时间越长（可通过 INFO stats 的 latest_fork_usec 观察）。
  2. 子进程写文件：子进程遍历共享内存中的数据，写入临时 RDB 文件，完成后原子替换旧文件。
  3. Copy-On-Write：fork 后主子进程共享物理页，页被标记为只读。主进程修改某个页时，内核先复制该页，主进程在副本上修改，子进程看到的仍是 fork 那一刻的数据，所以快照是一致的。

注意点

  • 写入频繁时大量页被复制，内存最坏可能接近翻倍，要预留内存，避免 OOM。
  • 建议关闭 Linux 透明大页（THP），否则一次写入就复制 2MB 的大页，放大 COW 开销。
  • 同一时间只允许一个 bgsave 或 bgrewriteaof 子进程。

AOF 持久化的原理和刷盘策略？高频

AOF（Append Only File）把每条写命令追加到日志文件，重启时按顺序重放来恢复数据。

写入流程

  1. 主线程先执行写命令、修改内存。
  2. 把命令按 RESP 格式追加到 aof_buf 缓冲区。
  3. 在事件循环中把 aof_buf 写入（write）AOF 文件，此时数据在内核的 page cache 中。
  4. 按刷盘策略调用 fsync 真正落盘。

先执行命令再写日志的好处：不用校验命令是否合法（错误命令不会被记录），也不阻塞当前命令；代价是命令执行后、写日志前宕机，这条命令会丢失。

三种刷盘策略（appendfsync）

策略 做法 数据安全 性能
always 每次写命令后同步 fsync 最高，几乎不丢 最差
everysec（默认） 每秒由后台线程执行一次 fsync 最多丢约 1 秒数据（磁盘慢时可能略多） 折中
no 不主动 fsync，由操作系统决定（Linux 通常约 30 秒） 可能丢较多 最好

为什么需要 AOF 重写？重写是怎么做的？高频

AOF 只追加，文件会越来越大，恢复也越来越慢；而同一个 key 的多次修改只有最终状态有意义。AOF 重写就是根据当前内存中的数据生成一份最精简的命令集合，替换旧 AOF。

SET name a
SET name b
SET name c      # 重写后只需要保留 SET name c

注意：重写不读取、分析旧 AOF 文件，而是直接遍历当前数据库，每个 key 生成一条（或几条批量）写入命令。

触发方式

  • 手动：BGREWRITEAOF。
  • 自动：同时满足两个条件
    • auto-aof-rewrite-percentage 100：当前 AOF 比上次重写后增长了 100%。
    • auto-aof-rewrite-min-size 64mb：AOF 至少达到 64MB，避免文件很小时频繁重写。

重写过程（7.0 之前）

  1. 主进程 fork 子进程，子进程根据内存快照写新的 AOF 临时文件。
  2. 重写期间主进程继续处理命令，新命令同时写入 aof_buf（保证旧 AOF 正常）和 AOF 重写缓冲区。
  3. 子进程完成后通知主进程，主进程把重写缓冲区的内容追加到新文件，再原子替换旧文件。

7.0 起（Multi Part AOF）：重写时主进程直接打开一个新的 incr 文件写入增量命令，子进程只生成新的 base 文件，完成后更新 manifest，不再需要重写缓冲区，减少了内存开销和主进程的拷贝工作。

重写会消耗 CPU、内存（COW）和磁盘 I/O，应避开业务高峰。

什么是混合持久化（RDB + AOF）？高频

混合持久化是 4.0 引入、5.0 起默认开启（aof-use-rdb-preamble yes）的 AOF 重写方式：重写时新 AOF 文件的开头是 RDB 格式的全量数据，后面是 AOF 格式的增量命令，兼顾 RDB 恢复快和 AOF 丢数据少的优点。

[RDB 格式的全量数据][AOF 格式的增量写命令]
  • RDB 部分：重写开始时，子进程把当前内存数据以 RDB 格式写入文件开头，加载速度和 RDB 一样快。
  • AOF 部分：重写期间及之后的写命令以 AOF 格式追加在后面，保留最新变更，丢失数据量和 AOF 一致（everysec 最多约 1 秒）。
  • 7.0 起体现为 Multi Part AOF 中 base 文件是 RDB 格式，incr 文件是 AOF 格式。

优点：恢复速度比纯 AOF 快，数据安全性比纯 RDB 高。 缺点：AOF 文件中 RDB 部分是二进制，不再完全可读；4.0 之前的版本无法识别这种格式，不向下兼容。

过期删除与内存淘汰 4高频 3

Redis 的过期删除策略是什么？内存满了怎么办？高频

Redis 用「惰性删除 + 定期删除」处理过期 key；内存达到 maxmemory 上限后，再由内存淘汰策略（maxmemory-policy）决定删除哪些 key。这是两套不同的机制。

常见的过期删除策略

策略 做法 优缺点
定时删除 为每个 key 设定时器，到期立即删除 内存最友好，但定时器多，CPU 开销最大；Redis 不采用
惰性删除 访问 key 时才检查是否过期，过期就删 CPU 最友好，但不被访问的过期 key 会一直占内存
定期删除 周期性随机抽查一批设置了过期时间的 key，删除其中过期的 折中，需要控制频率和时长

Redis 的实现

  • 惰性删除：所有读写命令执行前都会调用 expireIfNeeded 检查 key 是否过期。
  • 定期删除：serverCron 默认每秒 10 次（hz 10，即每 100ms）执行：从带过期时间的 key 中随机抽取 20 个，删除其中已过期的；如果过期比例超过 25%，就继续抽取下一轮，同时有执行时长上限（默认不超过 25ms），避免长时间阻塞主线程。
  • 两者结合：惰性删除保证访问时不会读到过期数据，定期删除回收不被访问的过期 key。

内存满了怎么办：内存使用超过 maxmemory 时，每次执行命令前按 maxmemory-policy 淘汰 key。默认 noeviction，写命令直接报错，读命令照常执行；纯缓存场景一般配置 allkeys-lru 或 allkeys-lfu。详见下面两题。

删除一个 key 会立刻被清理吗？持久化时对过期键怎么处理？滴滴小红书银行阿里

主动删除时：DEL 立即删除并同步释放内存；UNLINK（4.0 起）立即从键空间摘除，内存交给后台线程异步释放。而过期 key 不会到点立刻删除，要等惰性删除（被访问时）或定期删除（被抽查到）。

RDB 对过期键的处理

  • 生成 RDB 时：跳过已过期的 key，不写入文件。
  • 加载 RDB 时：主节点会检查并忽略已过期的 key；从节点会全部载入，但随后主从全量同步时会被主节点的数据覆盖，因此没有影响。

AOF 对过期键的处理

  • 写入阶段：过期 key 被惰性或定期删除时，向 AOF 追加一条 DEL 命令。
  • 重写阶段：AOF 重写时会跳过已过期的 key。

主从复制中的过期键

  • 从节点不会主动删除过期 key，统一等主节点删除后同步过来的 DEL，保证主从一致。
  • 3.2 起客户端读从节点时，如果 key 已逻辑过期，会返回空，避免读到过期数据。

删除大 key：推荐用 UNLINK，或开启 lazyfree-lazy-expire、lazyfree-lazy-server-del 等配置，避免同步释放大量内存阻塞主线程。

Redis 有哪些内存淘汰策略？高频

内存达到 maxmemory 后，Redis 按 maxmemory-policy 选择淘汰对象。目前共 8 种（4.0 新增两种 LFU），默认 noeviction。

范围 策略 说明
不淘汰 noeviction（默认） 不删除任何 key，写命令返回 OOM 错误，读命令正常
只在设置了过期时间的 key 中淘汰 volatile-lru 淘汰最久未使用的
volatile-lfu（4.0+） 淘汰访问频率最低的
volatile-random 随机淘汰
volatile-ttl 优先淘汰剩余 TTL 最短的
在所有 key 中淘汰 allkeys-lru 淘汰最久未使用的
allkeys-lfu（4.0+） 淘汰访问频率最低的
allkeys-random 随机淘汰

volatile-* 策略下，如果没有设置过期时间的 key 可淘汰，行为与 noeviction 相同。

Redis 的 LRU 和 LFU 都是近似实现

  • 近似 LRU：对象头 24 位 lru 字段记录最近访问时间，淘汰时随机采样 maxmemory-samples（默认 5）个 key，淘汰最久未访问的；不用维护全局链表，省内存也省移动开销。
  • LFU（4.0+）：复用 24 位字段，高 16 位存上次访问时间，低 8 位存对数增长的访问计数（最大 255），长时间不访问会衰减，解决 LRU 的缓存污染（偶尔访问一次的冷数据长期驻留）。

内存淘汰策略如何选择？高频

核心看两点：是不是所有数据都允许被淘汰、访问模式是看「最近」还是看「频率」。

  • 纯缓存场景（所有数据都能从数据库重建）：用 allkeys-lru，最通用；如果热点长期稳定、存在大量偶尔访问的冷数据，用 allkeys-lfu。
  • 缓存与持久数据混用：需要长期保存的 key 不设过期时间，缓存 key 设过期时间，选 volatile-lru 或 volatile-lfu，只在缓存 key 中淘汰。更推荐把两类数据拆到不同实例。
  • 数据访问概率均匀：allkeys-random。
  • 希望按过期时间先后淘汰：volatile-ttl，适合 TTL 能反映数据价值的场景。
  • 不允许丢任何数据（Redis 当存储用）：noeviction，必须配合内存监控、告警和扩容，否则写入会失败。

大模型会话 Session 场景：Session 是临时上下文，所有 Session key 都应设置 TTL，选 volatile-lru，长时间不活跃的会话优先淘汰，同时不影响未设置 TTL 的关键数据；如果存在少量高频会话（如企业知识库、客服连续对话），可选 volatile-lfu。不建议用 noeviction。

配套建议：合理设置 maxmemory（一般为物理内存的 60%~70%，给 fork 的 COW 和碎片留空间）；开启 lazyfree-lazy-eviction 让淘汰大 key 时异步释放内存。

主从复制与哨兵 9高频 4

Redis 如何保证高可用和高并发？宕机后的容灾能力如何？高频

高并发靠内存访问、I/O 多路复用、单线程执行命令和高效数据结构，横向再靠读写分离和 Cluster 分片；高可用和容灾靠持久化、主从复制、Sentinel、Cluster 四层机制。

高并发

  • 内存读写，不涉及磁盘 I/O。
  • I/O 多路复用（epoll），一个线程管理大量连接；6.0 起可开启 I/O 多线程。
  • 单线程执行命令，没有锁竞争和上下文切换。
  • 高效的底层结构（SDS、dict、skiplist、listpack）。
  • 架构层面：主从读写分离分担读流量，Cluster 分片分担写流量和容量。

高可用与宕机容灾

  • 持久化：RDB / AOF / 混合持久化，实例重启后能恢复数据；只保证数据可恢复，不保证服务不中断。
  • 主从复制：一主多从，数据冗余，从节点可分担读请求。主节点宕机时，若没有 Sentinel 需要人工执行 REPLICAOF NO ONE 切换。复制是异步的，切换时可能丢失少量未同步的数据。
  • Sentinel：监控主从节点，主节点宕机后自动故障转移，选出新主并通知客户端，切换通常在秒级到十几秒完成。
  • Redis Cluster：数据分片到多个主节点，每个主节点配从节点；某个主节点故障时其从节点自动接管，其他分片不受影响。只要每个分片都至少有一个节点可用，集群就能继续服务。

补充：跨机房容灾可以部署异地从节点或双集群，配合定期把 RDB 备份到其他存储。

为什么 Redis 需要多节点架构？高频

单节点 Redis 在容量、可用性和吞吐上都有上限，多节点架构用来突破这些限制。

  • 突破内存容量：数据都在内存里，单机内存有限；而且单实例内存过大会让 fork、RDB 生成、全量同步都变慢。分片后每个节点只存一部分数据。
  • 提高可用性：单节点宕机即服务不可用；主从 + Sentinel 或 Cluster 可以自动故障转移。
  • 提升并发能力：单实例命令执行是单线程的，只能用一个核做计算；多节点可以分摊连接数和读写请求。
  • 缓解网络带宽瓶颈：大量客户端访问同一节点时，网卡可能先打满，多节点能分散流量。

为什么要分主从、做读写分离？高频

Redis 常见场景是读多写少。主节点负责写，从节点只读并同步主节点数据，用来提升读性能、提高可用性，同时保持数据流向单一、一致性简单。

  • 分担读压力：读请求分散到多个从节点，主节点专注写入和同步，整体吞吐提升；从节点也可以承担 RDB 备份等耗时任务，减轻主节点负担。
  • 数据冗余与故障切换：从节点就是数据副本，主节点宕机时可以提升为主（配合 Sentinel 自动完成）。
  • 一致性模型简单：只有主节点写，数据单向从主流向从，不存在多节点并发写冲突。如果所有节点都能写，就要解决冲突合并、同步顺序等问题，复杂度大幅增加。

代价：主从复制是异步的，从节点可能读到旧数据（复制延迟）。对一致性要求高的读请求应走主节点；可以监控 master_repl_offset 与从节点 offset 的差值，延迟过大时把读请求切回主节点。

Redis 主从复制（同步）的原理是什么？高频

主从复制分三个阶段：首次连接时全量同步，之后通过长连接命令传播，断线重连后尽量增量同步。从节点通过 PSYNC replid offset 告诉主节点自己的复制进度，主节点据此决定全量还是增量。

关键标识：replid 标识一份数据集（从节点同步后继承主节点的 replid）；offset 是复制偏移量，主从各自记录同步进度。

全量同步（第一次同步）

  1. 从节点发送 PSYNC ? -1，主节点判断 replid 不一致，回复 FULLRESYNC <replid> <offset>。
  2. 主节点 bgsave 生成 RDB，期间新的写命令记录到复制缓冲区（replication buffer）。
  3. 从节点清空旧数据并加载 RDB，再执行缓冲区中积累的写命令。

命令传播：之后主从维持 TCP 长连接，主节点每条写命令异步发给从节点。

增量同步（断线重连）：从节点发送 PSYNC <replid> <offset>，如果 replid 一致且 offset 之后的数据仍在 repl_backlog_buffer 中，主节点回复 CONTINUE 并只发缺失部分，否则退化为全量同步。

repl_backlog_buffer：所有从节点共享的环形缓冲区，默认 1MB（repl-backlog-size），写满覆盖旧数据，断线太久就只能全量同步。应按「写入速率 × 预期断线时长」调大。

版本差异：4.0 之前依赖主节点 runid，主节点重启或切换后都要全量同步；4.0 起 PSYNC2 用 replid 代替 runid，新主会把旧主 replid 保存为 replid2，其他从节点切换后仍能增量同步。

什么是哨兵（Sentinel）？它解决了什么问题？

Sentinel 是 Redis 官方的高可用方案，用来解决主从架构下主节点故障需要人工切换的问题：它监控主从节点，主节点故障时自动把一个从节点提升为新主，并通知客户端新的主节点地址。Sentinel 本身是独立运行的进程（redis-sentinel），不存数据。

四个功能

  • 监控：每秒向主节点、从节点和其他 Sentinel 发送 PING，检测是否存活；每 10 秒向主节点发 INFO 获取从节点信息。
  • 自动故障转移：主节点被判定客观下线后，选出新主，让其他从节点复制新主，旧主恢复后变为从节点。
  • 配置中心：客户端连接 Sentinel 查询当前主节点地址（如 SENTINEL get-master-addr-by-name mymaster），不需要写死主节点 IP。
  • 通知：节点故障或主从切换时，通过 Pub/Sub 频道（如 +switch-master）或脚本通知客户端和管理员。

部署：Sentinel 自身以集群形式部署，至少 3 个且为奇数，分布在不同机器上，避免自身单点和误判。Sentinel 之间通过订阅主节点的 __sentinel__:hello 频道互相发现。

局限：Sentinel 只解决高可用，所有节点保存同一份完整数据，不能突破单主节点的容量和写性能上限，这需要 Cluster。

Sentinel 如何判断 Master 宕机？

通过**主观下线（SDOWN）和客观下线（ODOWN）**两个阶段，避免单个 Sentinel 因网络问题误判。

  • 主观下线：某个 Sentinel 向主节点发送 PING，在 down-after-milliseconds（默认 30 秒）内没有收到有效回复，就认为该主节点主观下线。对从节点和其他 Sentinel 也会做主观下线判断。
  • 客观下线：判定主观下线的 Sentinel 通过 SENTINEL is-master-down-by-addr 询问其他 Sentinel。认为主节点下线的 Sentinel 数量达到配置的 quorum 后，主节点被标记为客观下线。客观下线只针对主节点。
  • 进入客观下线后，Sentinel 之间选出 Leader 执行故障转移。

quorum 的设置：一般设为 Sentinel 数量的一半加一（如 3 个 Sentinel 设 2）。注意 quorum 只决定「是否客观下线」，真正执行故障转移还需要 Leader 获得多数 Sentinel（超过半数）的投票。

Sentinel 如何完成故障转移？

主节点被判定客观下线后，故障转移分四步：选 Leader、选新主、主从切换、通知客户端。

  1. 选举 Leader Sentinel：判定客观下线的 Sentinel 发起投票（类 Raft 机制），每个 Sentinel 在一个纪元（epoch）内只投一票，先到先得。获得超过半数且不少于 quorum 票数的 Sentinel 成为 Leader；没选出来就等待一段时间后进入下一纪元重选。由 Leader 单独执行后续操作，避免多个 Sentinel 同时切换。
  2. 选出新主节点：Leader 按规则从从节点中挑选（见下一题）。
  3. 主从切换：
    • 对选中的从节点执行 REPLICAOF NO ONE，使其成为新主。
    • 让其他从节点执行 REPLICAOF 新主IP 端口，复制新主。
    • 把旧主标记为从节点，它恢复上线后会自动成为新主的从节点。
  4. 通知客户端：更新配置，通过 +switch-master 频道发布新主地址，客户端（如 Jedis、Lettuce 的 Sentinel 模式）收到后切换连接。

整个过程通常在数秒到十几秒内完成，主要取决于 down-after-milliseconds 和网络情况。

主节点宕机后，Sentinel 如何选举新的 Master？

Leader Sentinel 先过滤掉不健康的从节点，再按优先级、复制进度、runid 依次比较，目标是选出数据最完整、状态最稳定的节点。

第一步：过滤

  • 去掉已下线或网络断开的从节点。
  • 去掉与原主节点断开时间过长的从节点（超过 down-after-milliseconds * 10 加上主节点已下线的时长），这类节点数据缺失较多。
  • 去掉 replica-priority（旧称 slave-priority）为 0 的从节点，它们永远不会被提升为主。

第二步：依次比较

  1. 优先级：replica-priority 数值越小越优先，可以让配置更好的机器优先当主。
  2. 复制偏移量：优先级相同时，offset 越大说明复制的数据越多，越优先。
  3. runid：前两项都相同时，选 runid 字典序最小的。

选出后：Leader 执行 REPLICAOF NO ONE 将其提升为新主，其他从节点改为复制新主，旧主恢复后降为从节点，最后向客户端发布新主地址。

什么是集群脑裂？如何避免？

脑裂是指因网络分区，集群中同时出现两个主节点对外提供写服务。旧主恢复后被降为从节点，会清空自己的数据并从新主全量同步，分区期间写入旧主的数据就全部丢失。

发生过程

  1. 原主节点与 Sentinel、从节点之间网络分区，但与部分客户端仍然连通。
  2. Sentinel 判定原主客观下线，把某个从节点提升为新主。
  3. 原主并没有宕机，仍在接受这些客户端的写请求，此时存在两个主节点。
  4. 网络恢复后，原主被降为新主的从节点，执行全量同步，分区期间写入的数据丢失。

Redis Cluster 中也会出现类似情况：被隔离在少数派分区中的主节点，在被判定下线前也可能继续接受写入。

缓解措施（脑裂无法彻底避免，只能缩小损失）

  • 配置写保护：
    min-replicas-to-write 1     # 至少要有 1 个从节点保持正常复制
min-replicas-max-lag 10     # 从节点的复制延迟不超过 10 秒
    条件不满足时主节点拒绝写请求，被孤立的旧主很快停止写入，丢失的数据被限制在一个较小的时间窗口内。代价是从节点都故障时主节点也无法写入。
  • 合理设置 down-after-milliseconds：避免网络瞬时抖动导致误判下线。
  • Sentinel 部署至少 3 个且跨机器/机房，依靠多数派判断，减少误判。
  • 客户端通过 Sentinel 获取主节点地址，不写死某个节点，切换后能及时连到新主。

注意：quorum 只用于判定客观下线和选 Leader，并不能保证同一时刻只有一个主节点可写；Redis 的复制是异步的，本身不提供强一致性。

Redis Cluster 4高频 0

什么是 Redis Cluster？它是如何实现数据分片的？

Redis Cluster 是 Redis 3.0 起官方提供的分布式方案，通过哈希槽分片 + 主从复制 + 自动故障转移，同时解决容量、写性能和高可用问题。它是去中心化的，不需要 Sentinel 和代理。

数据分片

  • 整个 key 空间分为 16384 个哈希槽，每个 key 通过 CRC16(key) % 16384 计算所属槽。
  • 每个主节点负责一部分槽，例如 A 负责 0~5460，B 负责 5461~10922，C 负责 10923~16383。
  • Hash Tag：key 中包含 {} 时只用花括号内的内容计算槽，例如 user:{1001}:name 和 user:{1001}:order 落到同一个槽，便于执行多 key 操作。

与主从 / Sentinel 的区别：后者每个节点存全量数据，只解决高可用；Cluster 把数据分散到多个主节点，可水平扩展容量和写能力。

其他关键机制

  • 主从复制：每个主节点配从节点，异步复制，从节点默认不处理读请求。
  • 去中心化：节点间通过 Cluster Bus 和 Gossip 协议交换状态、槽分配和故障信息。
  • 客户端路由：key 不在当前节点时返回 MOVED，客户端更新槽映射后重试；槽迁移中返回 ASK，只对本次请求转发，不更新映射。Smart Client（如 Lettuce）缓存槽映射直连正确节点。
  • 扩缩容：只需迁移部分槽及其数据（redis-cli --cluster reshard）。

一致性：复制是异步的，故障切换时可能丢失少量写入，Cluster 不保证强一致性。

Redis Cluster 为什么使用 16384 个槽？

16384（2^14）是在心跳包大小、数据均衡和集群规模之间的平衡，作者 antirez 也给出过这个解释。

  • 心跳包不能太大：节点之间每次 Gossip 心跳（PING/PONG）都会携带自己负责的槽位图。16384 个槽的位图是 16384 / 8 = 2KB；如果用 65536 个槽，位图就是 8KB，心跳包明显变大，浪费带宽。
  • 集群规模有限：官方建议主节点数不超过约 1000 个。节点越多 Gossip 通信开销越大，Cluster 本来就不适合超大规模，16384 个槽足以均匀分给这些节点。
  • 槽数足够多：即使有几百个主节点，每个节点也能分到几十上百个槽，迁移粒度细，便于均衡。
  • 便于压缩：节点数少时，每个节点负责的槽很多，槽位图中 1 的比例高，压缩率高。
  • 计算方便：16384 是 2 的幂，CRC16(key) % 16384 等价于取低 14 位，CRC16(key) & 16383。

Redis Cluster 如何实现高可用？

Cluster 靠主从复制、Gossip 故障检测、从节点自动选举和客户端路由更新实现高可用，不依赖 Sentinel。

  • 主从复制：每个主节点至少配一个从节点，异步复制数据。
  • 故障检测：
    • 节点之间定期发送 PING/PONG，某节点在 cluster-node-timeout（默认 15 秒）内没有响应，就被标记为疑似下线（PFAIL）。
    • 通过 Gossip 传播 PFAIL 信息，当超过半数的主节点都认为它 PFAIL 时，标记为已下线（FAIL），并广播 FAIL 消息。
  • 自动故障转移：
    • 故障主节点的从节点发起选举，复制 offset 越大的从节点越早发起，越容易当选。
    • 向所有主节点请求投票，获得超过半数主节点投票的从节点当选，升级为新主，接管原主的全部槽并广播新配置。
    • 旧主恢复后变为新主的从节点。
  • 客户端路由更新：客户端访问到旧节点时收到 MOVED，据此刷新槽映射，后续请求直接发往新主。

注意点

  • 某个分片的主从都不可用时，默认 cluster-require-full-coverage yes，整个集群停止服务；设为 no 时其他分片仍可服务。
  • 可以通过 cluster-migration-barrier 让从节点多的主节点把从节点迁移给「孤儿」主节点，提高整体可用性。
  • 异步复制意味着故障切换时可能丢失少量数据，提供的是高可用而非强一致。

Redis Cluster 有哪些限制？

主要限制来自分片（多 key 操作必须在同一个槽）和异步复制（不保证强一致）。

  • 多 key 操作受限：MGET、MSET、SUNION、RENAME 等涉及多个 key 的命令，要求所有 key 在同一个槽，否则报 CROSSSLOT 错误。用 Hash Tag 解决，但要注意 Hash Tag 用得太集中会造成数据倾斜。
  • 事务和 Lua 受限：事务和 Lua 脚本中的所有 key 必须在同一个槽（同一节点），不支持跨节点事务。
  • 只有 db 0：Cluster 模式不支持 SELECT 多数据库。
  • 不支持跨节点的 Pipeline、SCAN、KEYS：需要客户端按节点拆分，SCAN 要对每个主节点分别执行。
  • 大 key 和热 key 无法分散：一个 key 只能在一个槽里，大 key 迁移慢、热 key 会压垮单个节点。
  • 复制结构只有一层：从节点只能复制主节点，不支持级联复制。
  • 数据可能丢失：异步复制，主节点宕机时未同步到从节点的数据会丢失。
  • 运维和客户端要求更高：扩缩容要迁移槽，客户端必须支持 MOVED/ASK 重定向和拓扑刷新。

缓存穿透的成因和解决方案（布隆过滤器、缓存空值）？高频

缓存穿透是指请求的数据在 Redis 和数据库中都不存在，每次请求都无法命中缓存，最终全部落到数据库；由于数据库也查不到，缓存永远不会被建立。常见于恶意请求（如用 id = -1 或随机 id 攻击）或业务 bug。

方案一：缓存空值 数据库查不到时，也把空结果写入 Redis，并设置较短的 TTL。

SET user:999999 "" EX 60
  • 优点：实现简单。
  • 缺点：大量不同的不存在 key 会占用额外内存；空值存在期间如果数据库新增了这条数据，会短暂不一致，所以 TTL 要短，或在新增数据时主动删除空值缓存。

方案二：布隆过滤器 在访问 Redis 之前先查布隆过滤器，判断「一定不存在」的直接拦截。

  • 原理：一个很长的二进制位数组加 k 个哈希函数。写入时用 k 个哈希函数算出 k 个位置并置为 1；查询时如果这 k 个位置有任意一个是 0，数据一定不存在；全为 1 则可能存在（不同元素的位可能重叠，存在误判）。
  • 特点：占用内存极小；误判率可以通过位数组大小和哈希函数个数控制；不支持删除（需要删除可用计数布隆过滤器或定期重建）。
  • 实现：Redisson 的 RBloomFilter、Redis Stack 的 BF.ADD/BF.EXISTS（RedisBloom 模块）、Guava BloomFilter（本地）。
  • 注意：需要在系统启动时把已有数据的 key 全部预热到布隆过滤器，新增数据时同步写入。

其他手段：接口层做参数校验（如 id 必须大于 0），对异常 IP / 用户限流和拉黑。

缓存击穿的成因和解决方案（互斥锁、逻辑过期）？高频

缓存击穿是指某个高并发访问的热点 key 在过期的瞬间，大量请求同时发现缓存未命中，一起去查数据库并重建缓存，导致数据库瞬时压力过大。

方案一：互斥锁 只允许一个线程查数据库并重建缓存，其他线程等待后重试。

  1. 查 Redis 未命中。
  2. 尝试获取锁（SET lock:key uuid NX EX 10）。
  3. 获取成功的线程再查一次缓存（double check），仍未命中才查数据库，写回 Redis 后释放锁。
  4. 获取失败的线程短暂休眠后重新查询缓存。
  • 优点：保证一致性，数据库只被一个请求访问。
  • 缺点：其他线程需要等待，响应变慢；锁的实现要注意超时和误删。

方案二：逻辑过期（热点 key 不设 TTL） Redis key 不设置过期时间，而是在 value 中额外保存一个 expireTime 字段。

  1. 命中缓存后判断 expireTime：未过期直接返回。
  2. 已过期：尝试获取互斥锁，获取成功就开启异步线程查数据库、重建缓存、更新 expireTime；当前线程直接返回旧数据。
  3. 获取锁失败的线程也直接返回旧数据。
  • 优点：不阻塞请求，可用性高。
  • 缺点：重建完成前会返回旧数据，有短暂不一致；需要提前把热点数据预热进缓存。

选择：对一致性要求高用互斥锁；对可用性和响应时间要求高、能容忍短暂旧数据用逻辑过期。另外也可以由后台定时任务在过期前主动刷新热点数据。

缓存雪崩是指大量 key 在同一时间过期，或者 Redis 服务宕机，导致大量请求同时落到数据库，数据库压力骤增甚至被打垮，进而引发连锁故障。

针对大量 key 同时过期

  • TTL 加随机值：在基础过期时间上加一个随机偏移，让 key 分散过期。

redisTemplate.opsForValue().set(key, value, ttl, TimeUnit.SECONDS);
  • 热点数据不过期或逻辑过期，由后台任务定期刷新。
  • 缓存预热：系统上线或大促前把热点数据提前加载进缓存，并错开过期时间。
  • 互斥锁重建：限制同一个 key 只有一个线程回源。

针对 Redis 宕机

  • 高可用架构：主从 + Sentinel 或 Redis Cluster，节点故障时自动切换。
  • 服务熔断、限流、降级：Redis 不可用时通过 Alibaba Sentinel、Resilience4j 等组件限流或直接返回默认值，保护数据库。
  • 多级缓存：本地缓存（Caffeine）+ Redis，Redis 故障时本地缓存还能扛住一部分热点请求。
  • 持久化：Redis 重启后能快速恢复数据，缩短缓存空窗期。

缓存与数据库一致性 5高频 3

如何保证缓存与数据库的双写一致性？项目中怎么做的？高频滴滴小红书银行阿里

最常用的方案是 Cache-Aside（旁路缓存）：先更新数据库，再删除缓存，删除失败用消息队列重试或订阅 binlog 异步删除，并给缓存设置 TTL 兜底，保证最终一致。强一致需求一般不建议放缓存。

Cache-Aside 读写流程

  • 读：先读缓存，命中直接返回；未命中读数据库，再写入缓存。
  • 写：先更新数据库，成功后删除缓存。

为什么是删除缓存而不是更新缓存

  • 两个并发写可能因为执行顺序不同，导致缓存里留下旧值（A 写库、B 写库、B 写缓存、A 写缓存）。
  • 缓存值可能需要复杂计算，写多读少时频繁更新缓存浪费资源；删除后由下次读请求懒加载即可。

为什么不能先删缓存再更新数据库 A 删除缓存后还没来得及更新数据库，B 读缓存未命中，读到数据库旧值并写回缓存，然后 A 才更新数据库，缓存里就一直是旧数据。读请求很快，这种情况发生概率高。可以用延迟双删缓解，但不如「先更新库再删缓存」可靠。

先更新数据库再删缓存仍可能不一致吗 理论上可能：缓存刚好过期，A 读数据库旧值，B 更新数据库并删除缓存，A 再把旧值写入缓存。但这要求「读数据库 + 写缓存」比「写数据库 + 删缓存」还慢，实际概率很低，再加上 TTL 兜底即可。

项目中常见的组合

  1. 采用先更新数据库、再删除缓存。
  2. 删除失败时把 key 发到消息队列重试，直到成功。
  3. 对一致性要求更高、或不想侵入业务代码时，用 Canal 订阅 MySQL binlog，由独立服务异步删除缓存。
  4. 所有缓存都设置 TTL 兜底，即使出现脏数据也会在过期后自愈。

其他方案

  • Read/Write Through：缓存服务负责读写数据库，业务只操作缓存，Redis 一般不直接支持。
  • Write Behind：只写缓存，异步批量写库，性能高但可能丢数据，适合点赞数、浏览量等场景。
  • 强一致：读写都加分布式读写锁（如 Redisson RReadWriteLock），性能下降明显，一般只用于少量关键数据。

先更新数据库再删缓存，缓存删除失败了怎么办？高频

核心思路是保证删除最终成功：消息队列异步重试，或订阅 binlog 异步删除，同时用 TTL 兜底。

为什么会删除失败

  • Redis 超时、网络抖动。
  • Redis 主从切换、节点不可用。
  • 应用在提交事务后、删除缓存前崩溃或重启。

解决方案

  • 消息队列重试：删除失败后把 key 发送到 MQ，消费者负责重试删除，失败则继续重试，超过次数后记录告警人工处理。缺点是对业务代码有侵入。
  • 订阅 binlog（推荐）：用 Canal 等工具伪装成 MySQL 从库订阅 binlog，解析出变更的数据后删除对应缓存，删除失败再借助 MQ 重试。与业务代码解耦，而且只要数据库提交成功，binlog 就一定存在，可以覆盖「应用崩溃没来得及删」的情况。
  • TTL 兜底：所有缓存都设置过期时间，即使上述机制都失败，脏数据也只会存在到过期为止。
  • 延迟双删：更新数据库前后各删一次缓存，第二次延迟执行，进一步缩小不一致窗口。
更新数据库 → MySQL 写 binlog → Canal 订阅 → 投递 MQ → 消费者删除缓存（失败重试）

什么是延迟双删？

延迟双删是针对「先删缓存，再更新数据库」并发读导致脏数据的改进方案：在更新数据库后，延迟一段时间再删一次缓存。

步骤

  1. 删除缓存。
  2. 更新数据库。
  3. 休眠一段时间（如几百毫秒到 1 秒），再次删除缓存。

为什么需要第二次删除：第一次删缓存后、数据库更新前，其他读请求可能读到旧值并写回缓存。第二次删除就是为了清掉这段时间写入的脏数据。

延迟时间怎么定：要大于「一次读请求从读数据库到写回缓存」的耗时，主从数据库读写分离时还要加上主从复制延迟，一般通过压测评估。

缺点

  • 延迟时间难以精确设定，只能降低而不能完全消除不一致。
  • 同步休眠会拖慢写请求，通常把第二次删除放到异步线程或延迟消息里执行。
  • 第二次删除同样可能失败，仍需重试机制。

本地缓存（Caffeine）+ Redis + MySQL 两级缓存如何保证数据一致性？高频

两级缓存的读路径是「Caffeine → Redis → MySQL」逐级回填；写路径仍是先更新数据库再删除缓存，难点在于每个应用实例都有自己的本地缓存，需要广播失效通知所有节点删除。

读流程

  1. 先查本地 Caffeine，命中直接返回。
  2. 未命中查 Redis，命中后回填本地缓存再返回。
  3. Redis 也未命中则查数据库，回填 Redis 和本地缓存后返回（可配合互斥锁防击穿）。

写流程

  1. 更新数据库。
  2. 删除 Redis 中对应的 key。
  3. 广播缓存失效消息，所有应用节点收到后删除本地 Caffeine 中的对应 key。

广播方式

  • Redis Pub/Sub：发布失效事件到某个频道，各节点订阅后删除本地缓存。实现简单，但消息不持久化，节点断线期间的消息会丢失。
  • 消息队列（Kafka / RocketMQ）：发送失效消息，每个节点以独立消费组（广播模式）消费，可持久化、可重试，可靠性更高。
  • Canal + MQ：订阅 binlog 统一产生失效消息，业务代码无侵入。

兜底

  • 本地缓存设置较短的过期时间（如几秒到几十秒），即使漏收失效消息也能尽快自愈，且本地缓存 TTL 应短于 Redis。
  • 本地缓存只放少量热点、对一致性不敏感的数据，并限制容量，避免占用过多堆内存。

为什么 AI 应用中经常需要做二级缓存？

AI 应用的链路（Embedding 计算、向量检索、Rerank、LLM 生成）成本高、延迟高，缓存能直接省掉重复计算的钱和时间。二级缓存一般是「本地缓存 + Redis」：本地缓存解决进程内的高频热点，Redis 解决多实例共享。

可以缓存的环节

  • Embedding 结果：同一段文本（按内容哈希作为 key）的向量结果直接复用，避免重复调用 Embedding 模型。
  • 检索与重排结果：高频查询的召回 + Rerank 结果缓存后直接返回，省掉一次完整的检索链路。
  • LLM 生成结果：完全相同的问题直接命中；语义相近的问题可以做语义缓存（用向量相似度匹配历史问题，超过阈值才命中），既降成本也让响应时间更稳定。
  • Prompt 模板、模型配置、用户画像等变化少的数据适合放本地缓存。

设计注意点

  • 缓存穿透：空结果也要缓存，避免对同一无结果问题反复调用模型。
  • 热点 key：加本地缓存层分担 Redis 压力。
  • 版本失效：知识库更新、模型或 Prompt 版本变更时要同步失效相关缓存，可以把版本号纳入 key。
  • 语义缓存的阈值：阈值太低会返回不相关的答案，需要结合业务评估；涉及用户隐私或实时数据的问题不应跨用户共享缓存。

什么是大 Key 和热 Key？分别有什么危害？怎么处理？高频

大 Key 是 value 体积过大或集合元素过多的 key；热 Key 是短时间内被大量访问的 key。前者的问题是单次操作慢、阻塞主线程，后者的问题是单节点负载过高。

对比 大 Key 热 Key
定义 String 过大（如超过 10KB~1MB，按业务定），或 Hash/List/Set/ZSet 元素过多（如超过 5000 个） 访问 QPS 远高于其他 key，集中打到一个节点
危害 读写、DEL 耗时长阻塞主线程；网络带宽占用高；Cluster 数据倾斜；fork、迁移、主从同步变慢 单节点 CPU、带宽、连接数被打满；过期瞬间可能引发缓存击穿
发现 redis-cli --bigkeys、--memkeys、MEMORY USAGE、离线分析 RDB（redis-rdb-tools） redis-cli --hotkeys（需 LFU 策略）、客户端或代理层统计、云厂商监控
处理 拆分为多个小 key；压缩；选合适的数据结构；用 UNLINK 异步删除 本地缓存、key 分片打散、读写分离、限流降级、提前预热

具体阈值与处理见下面两题。

多大算大 Key？会导致什么问题？怎么解决？高频

没有绝对标准，常见经验值是：String 类型超过 10KB（严格场景）或 1MB，集合类型元素超过 5000 个或总大小超过 10MB，具体按业务的延迟要求和实例规格判断。

会导致的问题

  • 阻塞主线程：命令执行是单线程的，对大 key 执行 HGETALL、LRANGE 0 -1、SMEMBERS，或者用 DEL 删除，都可能耗时几十毫秒到秒级，期间其他请求全部排队。
  • 网络带宽压力：一次读取几 MB 数据，QPS 一高就打满网卡。
  • Cluster 数据倾斜：大 key 所在节点的内存和负载明显高于其他节点，且一个 key 无法拆到多个槽。
  • 持久化和复制变慢：fork 时页表更大、COW 复制的内存更多；主从全量同步、槽迁移时传输慢，迁移大 key 甚至会阻塞节点。
  • 过期删除和淘汰时阻塞：大 key 过期或被淘汰时，同步释放内存也会阻塞主线程。

解决方案

  • 拆分：大 Hash 按 field 哈希取模拆成多个小 Hash（如 user:info:{id%100}）；大 List 按时间或序号分段；大 String 拆成多段或换存储。
  • 压缩与精简：value 用 Protobuf、压缩算法压缩，去掉不需要的字段；Hash 存对象时只读需要的字段（HMGET）。
  • 异步删除：用 UNLINK 代替 DEL，开启 lazyfree-lazy-expire、lazyfree-lazy-eviction、lazyfree-lazy-server-del；也可以用 HSCAN、SSCAN、ZSCAN 分批删除元素。
  • 读取时分批：用 HSCAN 或 LRANGE 分页读取，避免一次全量读取。
  • 监控与预防：定期扫描大 key 并告警，设计阶段对集合类型设置上限，必要时把大数据放到 MySQL、对象存储中，Redis 只存索引。

QPS 多少算热 Key？会导致什么问题？怎么解决？高频

也没有固定标准，通常把单个 key 的 QPS 达到所在节点总 QPS 的较大比例（如几千到上万 QPS），或明显高于其他 key 视为热 Key，常见于秒杀商品、热点新闻、首页配置等。

会导致的问题

  • 单节点过载：同一个 key 只会落在一个节点（Cluster 中只在一个槽），流量无法通过扩容分散，该节点的 CPU、带宽、连接数被打满，响应变慢甚至宕机，进而影响该节点上的其他 key。
  • 缓存击穿：热 key 过期的瞬间，大量请求直接打到数据库。
  • 连锁故障：节点故障后流量转移到从节点或数据库，可能把它们也打垮。

发现热 Key

  • redis-cli --hotkeys（要求淘汰策略为 LFU）、MONITOR（开销大，短时间使用）。
  • 客户端埋点或代理层（如 Twemproxy、Codis）统计。
  • 京东 hotkey 等热点探测框架，实时发现并推送到本地缓存。

解决方案

  • 本地缓存：在应用层用 Caffeine 缓存热点数据，设置较短 TTL，大部分请求不再访问 Redis。
  • key 分片打散：复制多份 hot_key_1 ~ hot_key_N，请求随机访问其中一个，在 Cluster 中分散到不同节点；更新时要同时更新所有副本。
  • 读写分离：增加从节点，把读请求分散到多个从节点。
  • 防击穿：热 key 不设 TTL 或用逻辑过期，配合互斥锁重建。
  • 限流降级：对热 key 的访问做限流，超出部分返回默认值或排队。
  • 提前预热：大促、活动开始前把可预见的热点数据加载到本地缓存和 Redis。

如何避免大模型的会话 Session 过大？高频

大模型会话的上下文会随着对话轮数不断累积，导致 Session 成为大 key、读写变慢，同时也会超出模型上下文窗口。核心思路是控制 Redis 里只保留当前推理需要的轻量上下文。

  • 只保留最近 N 轮：用 List 存消息，写入后执行 LTRIM 只保留最近 N 条（如 20 条），读取时 LRANGE key -N -1。
  • 历史摘要化：较早的对话用 LLM 压缩成摘要，只保留用户偏好、关键事实、任务进度和重要结论；上下文采用「历史摘要 + 最近 N 轮对话」。
  • 冷热分离：完整对话历史持久化到 MySQL、MongoDB 或对象存储，Redis 只存摘要和最近消息，需要回溯时再加载。
  • 大内容只存引用：工具调用结果、检索到的文档片段、文件内容不直接放进 Session，只存摘要或文档 ID。
  • 按 Token 预算裁剪：按 Token 数而不是消息条数控制上下文长度，更贴合模型上下文窗口限制。
  • 设置 TTL：会话设置过期时间，用户活跃时刷新 TTL，长时间不活跃自动清理。

分布式锁的标准写法是：SET key uniqueValue NX PX ttl 原子加锁，释放时用 Lua 脚本比对 value 后再删除；业务耗时不确定时用看门狗续期。生产上一般直接用 Redisson。

加锁

SET lock:order:1001 <uuid:threadId> NX PX 30000
  • NX 实现互斥，PX 防止持有者宕机后死锁，value 用 UUID + 线程 ID 标识持有者。
  • 不要用 SETNX + EXPIRE 两条命令：中间崩溃锁就永不过期。2.6.12 起 SET 一条命令完成。

释放锁：直接 DEL 可能删掉别人的锁（自己的已过期、别人重新加了锁），要用 Lua 原子地比对 value 再删除：

if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end

可能出现的问题与解决

问题 原因 解决
死锁 持有者崩溃未释放 设置过期时间
误删他人的锁 锁过期后被别人获取，自己又执行了 DEL value 存唯一标识，Lua 比对后删除
锁提前过期 业务执行时间超过 TTL 看门狗续期（默认锁 30 秒，每 10 秒续期）
不可重入 同一线程再次加锁会失败 Redisson 用 Hash（field 为 UUID:threadId，value 为重入次数）
获取失败无法等待 SET NX 失败就直接返回 自旋重试，或 Redisson 基于 Pub/Sub 的等待唤醒
主从切换锁丢失 主节点加锁后未同步到从节点就宕机，新主上没有这把锁 RedLock，或改用 ZooKeeper/etcd

Redisson 的实现

RLock lock = redissonClient.getLock("lock:order:1001");
if (lock.tryLock(3, TimeUnit.SECONDS)) {  // 最多等 3 秒，不指定 leaseTime 才会启用看门狗
    try {
        // 业务逻辑
    } finally {
        lock.unlock();
    }
}

RedLock（红锁）

  • 做法：向 N 个（通常 5 个）独立主节点依次加锁，过半成功且总耗时小于 TTL 才算成功，否则向所有节点释放。用于解决主从切换丢锁。
  • 争议：依赖各节点时钟大致同步，且防不住 GC 停顿后锁已过期的情况；严格互斥需要 fencing token 或 ZooKeeper/etcd。部署成本高，Redisson 已将 RedissonRedLock 标记为废弃。

分布式锁怎么延长过期时间？（看门狗）高频

用看门狗（Watchdog）机制：加锁成功后启动一个后台定时任务，定期检查锁是否仍被当前线程持有，是就重置过期时间，直到业务执行完、锁被释放。

Redisson 的看门狗

  • 只有不指定 leaseTime 时才启用（lock() 或 tryLock(waitTime, unit)）；指定了 leaseTime 就不会续期，到期自动释放。
  • 默认锁过期时间是 lockWatchdogTimeout = 30 秒，每隔 1/3 即 10 秒续期一次，把过期时间重置回 30 秒。
  • 续期通过 Lua 脚本执行：先判断 Hash 中是否存在当前线程的 field，存在才执行 PEXPIRE，保证只续自己的锁。
  • unlock() 时取消续期任务。如果应用宕机，续期任务随之停止，锁最多 30 秒后自动过期，不会死锁。

自己实现时的注意点

  • 续期必须校验锁的持有者（value 是否等于自己的唯一标识），并用 Lua 原子执行「判断 + 续期」。
  • 续期任务要在释放锁或业务异常时可靠地取消，否则会无限续期。
  • 续期间隔应明显小于 TTL（如 TTL 的 1/3），给网络延迟留余量。
  • 看门狗解决的是「业务执行时间超过 TTL」，不能解决主从切换导致的锁丢失，也不能完全解决 GC 长停顿导致续期不及时的问题。

Redisson 分布式锁存在什么问题？高频

Redisson 解决了手写锁的误删、不可重入、提前过期等问题，但仍有几个风险，其中最主要的是主从异步复制导致的锁丢失。

  • 主从切换锁丢失：客户端在主节点加锁成功，锁还没同步到从节点，主节点就宕机了；从节点被提升为新主后没有这把锁，其他客户端可以再次加锁成功，两个客户端同时进入临界区。
  • GC 停顿或网络延迟：客户端发生长时间 GC（STW）时，看门狗线程也无法续期，锁过期被别人获取，客户端恢复后仍以为自己持有锁。
  • 看门狗的使用陷阱：指定了 leaseTime 就不会续期；忘记 unlock 或续期任务没有停止，会导致锁长期占用。
  • 性能开销：加锁、解锁、续期都要访问 Redis，高并发场景下对单个锁的竞争会成为瓶颈，需要考虑分段锁等优化。

解决思路

  • MultiLock（联锁）：向多个独立节点同时加锁，全部成功才算成功，安全性更高，但任一节点不可用就无法加锁，可用性差。
  • RedLock（红锁）：向多个独立主节点加锁，过半成功才算成功，在一致性和可用性之间折中。但它依赖各节点时钟，也防不住 GC 停顿导致的锁过期，存在公认的争议，Redisson 已将 RedissonRedLock 标记为废弃。
  • fencing token：每次加锁获得一个单调递增的令牌，写共享资源时由存储端校验令牌，拒绝旧令牌的写入，从根本上防止「过期锁持有者」的写入。
  • 改用强一致的协调服务：对正确性要求极高时用 ZooKeeper 或 etcd；或在数据库层用唯一索引、乐观锁（版本号）做最终兜底。

为什么用 Redis 做分布式锁？什么情况下用 Zookeeper 等其他分布式锁？交通银行PDD

Redis 锁的优势是性能高、实现简单，适合高并发、能容忍极小概率锁失效的场景；ZooKeeper / etcd 基于共识协议，可靠性更高，适合对正确性要求严格的场景。

ZooKeeper 锁原理：在锁节点下创建临时顺序节点，序号最小的获得锁，其他客户端只监听前一个节点；会话断开节点自动删除，不会死锁，天然公平。常用 Curator 的 InterProcessMutex。etcd 则基于 Raft + Lease，Revision 可直接当 fencing token。数据库锁（唯一索引、FOR UPDATE）实现简单但性能差。

对比 Redis ZooKeeper
一致性 主从异步复制（AP 倾向），主从切换可能丢锁 ZAB 协议，写入过半节点才成功（CP），锁不会因单节点故障丢失
性能 高，内存操作，适合高并发 较低，写操作要过半节点确认，频繁创建删除节点开销大
锁释放 依赖 TTL，需要看门狗续期 会话断开临时节点自动删除，不需要设置过期时间
等待机制 自旋或 Pub/Sub 通知 Watcher 监听前一个节点，公平排队
风险 主从切换、GC 停顿导致锁失效 网络抖动导致会话超时，锁被误释放

怎么选：高并发、偶发失效可由业务兜底（幂等、唯一约束）时用 Redis，如秒杀、防重复提交；互斥正确性要求严格、并发不高或已有 ZooKeeper/etcd 时用后者，如调度选主、金融关键操作。关键业务都应在数据层再做幂等或版本校验。

有哪几种限流算法？

经典的限流算法有四种：固定窗口、滑动窗口、漏桶、令牌桶。

算法 原理 优点 缺点
固定窗口计数器 把时间切成固定窗口（如 1 秒），窗口内计数，超过阈值拒绝，窗口结束计数清零 实现最简单 临界问题：在两个窗口交界处前后各打满，短时间内实际通过 2 倍流量
滑动窗口 统计「当前时间往前一个窗口长度」内的请求数；可以把窗口拆成多个小格子，或记录每个请求的时间戳 平滑，解决临界问题 实现更复杂，记录时间戳的方式内存开销大
漏桶 请求先进入桶（队列），以固定速率流出处理，桶满则拒绝 输出速率恒定，保护下游 无法应对突发流量，即使系统空闲也只能匀速处理
令牌桶 以固定速率往桶里放令牌，桶有容量上限；请求拿到令牌才能通过，没有令牌则拒绝或等待 既限制平均速率，又允许一定的突发流量（桶内积累的令牌） 实现稍复杂，需要合理设置速率和桶容量

实际应用：令牌桶最常用，Guava RateLimiter、Redisson RRateLimiter（基于令牌桶思想）、Spring Cloud Gateway 的 Redis 限流都采用它；Sentinel（阿里）的 QPS 流控默认用滑动窗口统计；Nginx 的 limit_req 采用漏桶。

Redis 如何实现限流算法？

单机限流用 Guava RateLimiter 即可；多实例需要全局限流时，用 Redis 集中保存限流状态，并用 Lua 脚本保证「判断 + 计数」原子执行。限流维度由 key 决定，如 rate:user:1001、rate:ip:1.2.3.4。

固定窗口：INCR + EXPIRE

-- KEYS[1]=限流key  ARGV[1]=阈值  ARGV[2]=窗口秒数
local current = redis.call("INCR", KEYS[1])
if current == 1 then
    redis.call("EXPIRE", KEYS[1], ARGV[2])
end
if current > tonumber(ARGV[1]) then
    return 0
end
return 1

滑动窗口：ZSet：请求时间戳作 score，先 ZREMRANGEBYSCORE 删除窗口外记录，再 ZCARD 统计，未超阈值就 ZADD（member 用唯一请求 ID）并设置过期。

-- KEYS[1]=限流key  ARGV: now(毫秒) window(毫秒) limit requestId
local now, window = tonumber(ARGV[1]), tonumber(ARGV[2])
redis.call("ZREMRANGEBYSCORE", KEYS[1], 0, now - window)
if redis.call("ZCARD", KEYS[1]) >= tonumber(ARGV[3]) then
    return 0
end
redis.call("ZADD", KEYS[1], now, ARGV[4])
redis.call("PEXPIRE", KEYS[1], window)
return 1

注意：每个请求占一个元素，阈值大时内存开销大；时间戳最好统一用 redis.call("TIME")，避免各服务器时钟不一致。

令牌桶：Hash + Lua：Hash 保存「当前令牌数」和「上次补充时间」，请求时按经过时间补充令牌（不超过容量），足够就扣减放行，不需要后台线程放令牌。

Redisson RRateLimiter：trySetRate(RateType.OVERALL, 100, 1, RateIntervalUnit.SECONDS) 设置全局每秒 100 个，tryAcquire() 获取；PER_CLIENT 表示按客户端实例单独限流，底层同样是 Lua。

Redis 如何实现 Agent 的短期记忆？

把当前会话的上下文存到 Redis 并设置 TTL：Agent 每次推理前从 Redis 读取最近对话和任务状态拼进 Prompt，生成回复后再把本轮的用户输入、模型回复和中间状态写回 Redis，从而在多轮对话中保持上下文连续。

存储结构

  • List：多轮对话最常用，按时间顺序 RPUSH 消息，读取时只取最近 N 条。
  • String：把整个会话状态序列化成 JSON，适合整体读写的简单场景。
  • Hash：存任务状态、槽位信息、用户偏好等结构化字段，可单独更新某个字段。
RPUSH session:1001 '{"role":"user","content":"介绍一下订单状态"}'
RPUSH session:1001 '{"role":"assistant","content":"订单状态包括待支付、已支付、已发货"}'
LTRIM session:1001 -20 -1        # 只保留最近 20 条
EXPIRE session:1001 1800         # 30 分钟不活跃自动清理
LRANGE session:1001 -20 -1       # 推理前读取最近上下文

流程

  1. 读取：推理前 LRANGE 读取最近 N 条消息（加上历史摘要），拼接到 Prompt。
  2. 写回：生成回复后追加本轮消息、工具调用结果或任务状态。工具返回的大段内容、检索文档只存摘要或引用 ID，避免 Session 膨胀。
  3. 过期与刷新：每次交互刷新 TTL，长时间不活跃的会话自动清理，防止无效 Session 占满内存。
  4. 控制大小：保留最近 N 轮，较早的历史由 LLM 压缩为摘要，最终上下文为「历史摘要 + 最近 N 轮对话」；也可以按 Token 预算裁剪。

注意点

  • 同一会话的并发请求（如用户连续发送）可能同时读写上下文，可以按会话加分布式锁或串行化处理。
  • 短期记忆只负责会话内的上下文；跨会话的长期记忆（用户偏好、历史事实）应持久化到数据库或向量库，按需检索。
  • 会话数据可能包含用户隐私，key 要按用户隔离，并设置合理的过期时间。

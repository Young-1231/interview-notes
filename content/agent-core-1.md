## Agent 概念与架构

### 谈谈你对 AI Agent 的理解？它和普通大模型调用有什么本质区别？
AI Agent 是以大模型为"大脑"、能围绕目标自主规划并调用工具完成任务的系统。它不是某个模型，而是一套架构：LLM + 规划 + 记忆 + 工具 + 反馈循环。

**和普通大模型调用的本质区别**

| 维度 | 普通 LLM 调用 | Agent |
| --- | --- | --- |
| 驱动方式 | 被动响应：Prompt → LLM → Response | 目标驱动：围绕最终目标持续行动 |
| 能力来源 | 主要依赖模型内部知识 | 可调用搜索、数据库、代码执行、业务 API 等外部能力 |
| 执行形态 | 一次生成，没有执行闭环 | "规划 → 行动 → 观察 → 反思"循环，根据工具结果继续决策 |
| 状态 | 无状态，每次只看传入的上下文 | 维护任务状态、短期 / 长期记忆 |

**为什么现在能做 Agent**
- 以前做"智能体"主要有两条路：规则系统（专家写规则，扩展性差、容错低）和强化学习（依赖大量交互数据，训练贵、通用性弱）。
- 大模型在推理、规划、指令遵循和结构化输出（Function Calling）上足够强，才可以当作通用决策中枢。

**三项核心能力**：能思考（CoT、任务拆解）、能记忆（上下文与经验）、能行动（调用工具真正改变外部状态）。

**人机关系的变化**：SaaS + AI（AI 是功能模块，人主导）→ Copilot（AI 辅助人做事）→ Agent（人给目标，AI 规划和执行，人负责监督和反馈）。Agent 让 AI 从"回答者"变成"执行者"。

### Agent 包含哪些核心模块？如果从 0 设计一个 Agent，核心模块有哪些？ | 高频
经典概括：**Agent = LLM（规划决策）+ Memory（记忆）+ Tools（手脚）+ Feedback Loop（反馈纠错）**。

**四个基础模块**
- **规划（Planning）**：LLM 作为决策中枢，判断是否需要多步、是否调用工具、调用顺序，把任务拆成子步骤。
- **记忆（Memory）**：短期记忆保存当前会话和中间结果，保证多轮连贯；长期记忆沉淀用户偏好、历史经验和业务知识。
- **工具使用（Tool Use）**：搜索、数据库、计算器、代码解释器、API 等，弥补模型在实时性、精确计算和执行操作上的不足。模型决定"何时用什么工具"，工具负责执行。
- **反馈循环（Feedback Loop）**：根据中间结果自我校正，判断是否需要重试、重新规划或换工具。

**从 0 设计时的工程化拆分**
1. 输入理解：解析用户意图、目标、约束和上下文。
2. 规划模块：把复杂任务拆成可执行、可验证的步骤。
3. 工具管理与调用：工具注册、描述、参数 Schema、鉴权、超时重试。
4. 执行器：按计划逐步执行，接收工具返回。
5. 记忆模块：短期上下文 + 长期记忆，按需检索注入。
6. 观察与反馈：每一步判断结果是否符合预期，不满足就调整策略。
7. 安全与权限：工具权限、数据访问权限、高风险操作人工确认。
8. 日志与监控：记录每步模型调用、工具调用、耗时、Token、失败原因，支撑排查和评估。

一句话：Agent 的核心不是"调一次大模型"，而是形成"理解目标 → 制定计划 → 调用工具 → 观察结果 → 持续修正"的闭环。

### Agent 的架构设计是怎样的？
一个可落地的 Agent 通常分五层。难点不在于模型"能不能想"，而在于"想完能不能稳定执行"。

- **任务入口层**：接收用户问题和上下文，做输入清洗、标准化、鉴权。
- **决策层**：意图识别、任务拆解、规划和工具选择，决定"做什么、怎么做、用什么做"。
- **执行层**：调用工具、查询知识库、访问外部服务，把规划落地。
- **记忆与状态层**：维护多轮上下文、历史执行结果和中间变量，让 Agent 知道"做过什么、下一步做什么"。
- **校验层**：执行前校验参数合法性和权限，执行后校验返回结构和结果一致性。模型的规划和参数不一定总是对的，校验层是稳定执行的最后保障。

横切能力：日志 / Trace、限流与超时、成本控制、人工确认。

### Agent 设计中你觉得最重要的部分是什么？
最关键的是**上下文工程（Context Engineering）**：给模型正确的信息，而不是更多的信息。

Agent 是持续决策的系统，每一步决策质量取决于模型此刻看到了什么：当前目标、约束、可用工具、历史状态、证据，以及它们的顺序和优先级。上下文做得好，模型像一个受控执行器；做得差，即使模型很强，也会出现目标漂移、工具误选、记忆污染、长对话失真。

**上下文工程的关键点**
- **角色隔离**：System、Developer、User、Tool Output、Memory 分区存放，明确来源和权威等级。外部文本（网页、工具返回）不能和系统规则混在一起，这也是防提示注入的基础。
- **信息裁剪**：只保留与当前任务相关的历史、检索结果和工具说明，无关信息就是噪声。
- **格式控制**：结构化优于纯自然语言。工具结果用 JSON，任务状态单独字段化，长历史做摘要。
- **可信度分层**：冲突时系统规则 > 用户输入，工具结果 > 模型猜测，有证据 > 无证据生成。
- **压缩与淘汰**：长任务定期压缩、淘汰过期信息，避免旧状态污染新决策。

### RAG 接到 Agent 里一般怎么设计？
RAG 在 Agent 里不应是固定的"先查再答"，而是一个**决策节点**：模型先判断是否需要外部知识，再决定怎么检索。

- **封装为工具**：把检索做成独立工具（如 `search_knowledge_base`），由 Agent 决定是否调用、调用几次，而不是每轮强制检索。这种形态常被称为 Agentic RAG。
- **检索前处理查询**：Query Rewrite 把多轮对话改写成独立可检索的查询；Query Decomposition 把复杂问题拆成多个子查询，可并发检索。
- **检索后处理结果**：去重、截断、Rerank 重排、标注来源，不把原始召回结果直接塞给模型。
- **生成强约束**：要求只基于检索证据回答并引用来源；证据不足时明确说不确定。这是降低幻觉的关键。
- **分层注入**：检索结果放在独立的 Knowledge 上下文块，和 System 指令、用户原话隔离，模型能区分"外部知识"和"用户说的话"。
- **可迭代**：结果不够时 Agent 可以换关键词或换知识源再检索，但要限制检索轮数。

### 有哪些 Agent 开发平台？
按形态分三类：低代码平台、开源应用平台 / 开发框架、多 Agent 框架。

| 类别 | 代表 | 特点 |
| --- | --- | --- |
| 低代码平台 | Coze（扣子，字节）、阿里云百炼、腾讯元器、文心智能体平台 | 可视化编排、插件、工作流，一键发布；Coze 于 2025 年 7 月开源了 Coze Studio、Coze Loop |
| 开源应用平台 | Dify、FastGPT | 支持私有化部署；Dify 内置 RAG、工作流、Agent，FastGPT 侧重知识库问答 |
| 开发框架 | LangChain、LangGraph | LangChain 组件生态最广；LangGraph 把流程建模为有状态的图，支持循环、分支、持久化和人工介入 |
| 多 Agent 框架 | CrewAI、AutoGen（微软）、MetaGPT、AgentScope（阿里） | 角色化协作、对话式协作、模拟软件公司分工等；AutoGen 后续与 Semantic Kernel 合并演进为 Microsoft Agent Framework |

**选型思路**
- 快速上线、低运维：Coze、百炼等平台。
- 私有化、深度定制：Dify、FastGPT；需要灵活编排用 LangChain / LangGraph（Java 技术栈可选 Spring AI、Spring AI Alibaba）。
- 复杂多角色协作：CrewAI、AutoGen 等，或用 LangGraph 自行编排。

### OpenClaw 和 Hermes 有什么区别？
两者都是开源、可自托管的个人 Agent，区别在于侧重点：OpenClaw 侧重"网关 + 技能"的多渠道助手，Hermes Agent（Nous Research）侧重内置学习闭环、越用越会做。

| 维度 | OpenClaw | Hermes Agent |
| --- | --- | --- |
| 核心定位 | 以 Gateway 为中心，把 WhatsApp、Telegram、Slack 等消息渠道接到同一个 Agent | Agent 运行时本身，强调自我改进 |
| 能力扩展 | 主要靠安装 / 编写 Skills，能力由人预先配置 | 完成任务后可自动沉淀为可复用的 Skill，并在使用中改进 |
| 记忆 | 会话记忆 + 基于文件的记忆 | 强调跨会话持久记忆和用户画像 |
| 适用场景 | 多渠道接入、标准化的日常任务自动化 | 长期使用的个人助理、编码与重复工作流自动化 |

两者都能执行 Shell、读写文件，权限很大，部署时都要做沙箱隔离、命令审批和凭证保护。

## Agent 与 Workflow

### Agent 和 Workflow 有什么区别？为什么 Agent 不等同于工作流？ | 高频
Workflow 是人按规则预先编排好的固定流程，系统照着执行；Agent 是人给出目标，由模型根据实时状态自主决定下一步的系统。

- **Workflow**：步骤、分支、工具调用顺序都提前定义，分支由规则（如字段值）控制。流程不会因中间结果自我调整，没有自主判断和纠错能力，适合标准化、逻辑确定的重复任务。即使某个节点调用了 LLM，路径也仍然是人定的。
- **Agent**：具备推理、规划、记忆和反思能力，通过"思考 → 行动 → 观察"循环，根据工具返回动态选择工具、调整路径，能处理目标明确但路径不确定的开放式任务。

**为什么 Agent 不等于工作流**：区别在于**控制流归谁**。工作流的控制流写在代码 / 配置里；Agent 的控制流由模型在运行时生成。工作流里放了 LLM 节点，仍然是工作流。

两者常组合使用：Agent 做顶层规划，内部调用固定 Workflow 处理标准化子流程；或者 Workflow 做主干，在复杂节点嵌入 Agent。

### Agent 和 Workflow 各有什么优缺点？ | 高频

| | 优点 | 缺点 |
| --- | --- | --- |
| Agent | 自主决策，灵活；能根据中间结果调整路径；能处理未预见的情况和非标准化任务 | 行为不可完全预控，输出不稳定，可能跑偏或循环；对模型能力要求高；延迟和 Token 成本高；调试和复现困难 |
| Workflow | 严格按预设执行，结果稳定可预期；易测试、监控、审计和复现；执行快、资源消耗低；适合标准化、批量化任务 | 灵活性差，无法根据中间结果动态调整；遇到流程未覆盖的边界情况无法自主处理；扩展依赖人工改流程 |

### 如何根据业务场景选择 Agent 还是 Workflow（固定 DAG）？ | 高频
核心看流程是否确定：**能提前写清楚的部分用 Workflow / DAG，只有无法提前确定的部分交给 Agent**。实际落地很少二选一。

| 判断项 | Workflow / 固定 DAG | Agent |
| --- | --- | --- |
| 执行步骤 | 提前确定 | 运行时动态决定 |
| 分支决策 | 规则控制，分支有限 | 模型根据目标、上下文、工具结果判断 |
| 稳定性 | 高 | 有随机性 |
| 可解释性 / 审计 | 容易追踪 | 需要记录完整执行轨迹 |
| 容错要求 | 适合出错代价大的场景 | 适合允许探索、错误可发现可撤销的场景 |
| 工具调用 | 顺序固定（查库 → 总结 → 生成文件） | 工具多，需按问题动态选择 |
| 成本和延迟 | 模型调用次数可控 | 多轮调用，成本更高，需设步数和预算上限 |
| 异常恢复 | 可预先设计重试、断点续跑 | 情况更复杂 |

**典型场景**
- Workflow：发票报销审批、订单退款、数据 ETL、定时同步、合同审核流程、客服分流、标准 RAG 问答。金融、医疗、审批等强合规场景优先。
- Agent：资料调研、竞品分析、代码排错、故障排查、复杂客服问题、跨系统信息查询和数据分析。

**组合方式**：主流程由 Workflow 编排，在需要复杂判断的节点调用 Agent，Agent 决策完再回到固定流程。这样既保留灵活性，又用 Workflow 控制执行边界和业务风险。一个简单判据：如果业务人员能提前画出流程图并枚举异常，就用 Workflow。

### 哪些场景不应该用 Agent，而该用确定性工作流？
规则能写清、异常能枚举的任务，都应优先用确定性工作流。具体包括：

- 输入输出规则明确，步骤固定，几乎不会因中间结果改变。
- 需要严格复现：同一输入必须得到同一输出。
- 延迟和成本约束很严、请求量大，但单次任务很简单。
- 可以直接用 SQL、普通代码或规则引擎完成。
- 合规要求给出可验证的决策路径。
- 缺少可靠的测试、监控和失败恢复机制。
- 错误会造成不可逆损失，而系统又无法在动作前做校验或请求人工批准。

Agent 适合规则无法穷举、执行路径依赖现场信息，并且错误能被发现、拦截或撤销的任务。

## Agent 范式

### Agent 有哪些主流范式？分别适合什么场景？ | 高频
最常考的三种是 **ReAct、Plan-and-Execute、Reflection**，再加上 Tool-Use 这一基础能力，以及多 Agent、路由等组织形态。

![](images/Java八股（后端\)+Agent八股8-image-5.png)

| 范式 | 核心思想 | 适合场景 |
| --- | --- | --- |
| Tool-Use / Function Calling | 模型选择工具并生成参数，单步或少量调用 | 查天气、查订单等简单工具任务 |
| ReAct | Thought → Action → Observation 交替循环，边想边做 | 信息不完整、需要边查边判断：搜索问答、故障排查 |
| Plan-and-Execute | 先生成全局计划，再逐步执行，可重规划 | 步骤可预判的长链路任务：调研报告、代码迁移、数据处理 |
| Reflection / Reflexion | 生成后自我评审、批改、重做 | 正确率要求高：代码生成、文档审核、复杂推理 |
| Tree of Thoughts | 多条思路并行探索、评估、回溯 | 规划、谜题、组合搜索等需要比较多方案的问题 |
| Self-Ask | 拆成子问题逐个回答（可配合搜索） | 多跳问答 |
| Multi-Agent | 多个角色分工协作（规划、检索、执行、审核） | 复杂企业级任务 |
| Router Agent | 按意图路由到不同专家 Agent 或工具 | 智能客服、企业助手的统一入口 |
| Human-in-the-loop | 关键节点人工确认 | 转账、审批、生产变更等高风险操作 |

Reflection 通常不单独构成完整流程，而是叠加在 ReAct 或 Plan-and-Execute 之上的增强模块。

### ReAct 范式的基本流程是什么？它是怎么实现“边思考边行动”的？有什么优缺点？ | 高频
ReAct = Reasoning + Acting（Yao et al., 2022），让模型在"推理 → 行动 → 观察"之间循环，根据真实的工具结果逐步决策，而不是一次性给答案。

![](images/Java八股（后端\)+Agent八股8-image-6.png)

**流程**
1. **Thought**：分析当前缺什么信息、下一步该做什么、调用哪个工具。
2. **Action**：发起工具调用（搜索、接口、数据库、代码解释器等）。
3. **Observation**：拿到工具返回，追加到上下文。
4. 回到 Thought，继续推理，直到得出最终答案或触发终止条件。

![](images/Java八股（后端\)+Agent八股8-image-7.png)

例：用户问"北京明天要不要带伞"，Agent 先想到需要查天气 → 调用天气工具 → 观察到降雨概率 80% → 回答需要带伞。

**为什么经典**：它把 CoT 的推理和外部行动结合起来。CoT 只在模型内部推理，可能凭空编造事实；ReAct 每一步都有 Observation 作为依据，推理和行动互相校正。生产中通常只记录动作、参数和观察结果，不必暴露完整推理文本。

**优点**
- 能根据环境反馈随时调整，适合信息不完整、结果不可预知的任务。
- 有观察结果作依据，比一次性生成更少幻觉。
- 工具调用轨迹清晰，便于调试和审计。
- 实现直接，不需要先产出完整计划。

**缺点**
- 每一步都要调模型和工具，延迟和成本高。
- 容易重复搜索、无效尝试或死循环。
- 决策偏局部贪心，长任务中可能偏离整体目标。
- 上下文不断累积，早期信息容易被稀释。
- 工具返回的外部内容可能带来提示注入。

**生产防护**：最大迭代次数、明确停止条件、工具白名单、参数校验、超时、重复动作检测、Trace 日志、高风险动作人工确认。

### ReAct 范式和 Agent Loop 有什么区别？ | 高频
**Agent Loop 是外壳，ReAct 是壳里的一种具体实现。**

- **Agent Loop**：通用执行框架，只规定"调用模型 → 若有工具调用就执行并把结果喂回 → 再调用模型 → 直到模型给出最终回复或达到上限"这一循环结构，不规定每轮内部怎么思考。
- **ReAct**：规定每一轮内部按"先推理再行动、再观察"运转的具体范式，是用 Agent Loop 思想构建的经典实例。

同一个 Agent Loop 里也可以跑 Plan-and-Execute、Reflection 等其他策略。现代基于原生 Function Calling 的 Agent（如 Claude Code 这类 CLI Agent）本质上就是一个 Agent Loop，推理过程不一定显式输出成 "Thought:" 文本。

### 为什么确定性强的流程不适合用 ReAct？
因为 ReAct 的价值在于动态决策，而确定性流程不需要动态决策，只会白白引入成本和不确定性。

1. **浪费**：步骤完全已知，每一步仍让 LLM 推理，多出大量 Token 和延迟。
2. **引入随机性**：模型可能乱调工具、跳步骤、重复执行，破坏固定业务逻辑。
3. **难以管控**：审批、表单流转、固定计算要求 100% 标准化，自主决策会带来不可预期的分支，难测试、难审计。
4. **额外工程成本**：还得为 ReAct 写提示约束、终止判断、异常拦截，不如直接用代码或 Workflow 编排稳定。

结论：确定性流程直接用 Workflow，只在不确定的节点引入模型。

### Plan-and-Execute 范式是什么？ | 高频
Plan-and-Execute（也叫 Plan-Executor）是**先拆任务、再逐步执行**的范式：Planner 先产出全局计划，Executor 按计划执行每一步，必要时 Replanner 根据执行结果修改剩余计划。

![](images/Java八股（后端\)+Agent八股8-image-8.png)

![](<images/Java八股（后端)+Agent八股8-截屏2026-06-05 17.52.37.png>)

**流程**：用户目标 → Planner 生成步骤列表 → Executor 逐步执行（单步内部可以用 ReAct 调工具）→ 汇总结果 → 判断是否需要重规划 → 输出最终结果。

例：做一份竞品分析报告，Planner 拆成"确定竞品 → 收集信息 → 对比功能 → 分析价格 → 输出结论"，Executor 依次完成。

**要点**
- **优势**：全局视角，结构清晰，计划可供人工审核；执行阶段可以用更便宜的模型，降低成本。
- **风险**：初始计划错了，后续会沿错误方向走，因此需要**重规划机制**（每步或失败后回到 Planner 修订）。
- **Planner 和 Executor 不一定是两个模型**：可以是同一模型扮演两个角色，也可以强模型做规划、小模型做执行。

### ReAct 和 Plan-and-Execute 有什么核心区别？
ReAct 是试错式的边想边做，Plan-and-Execute 是先画全局蓝图再执行。

| 维度 | ReAct | Plan-and-Execute |
| --- | --- | --- |
| 执行逻辑 | 每步推理后行动，动态迭代 | 先完整规划，再按步骤执行 |
| 思考粒度 | 细粒度，单步决策 | 粗粒度，全局规划 |
| 调整能力 | 每步都可改思路、换工具、改路线 | 依赖重规划，没有重规划就比较僵硬 |
| 适合任务 | 开放、信息未知、下一步依赖上一步结果 | 步骤可预判、依赖关系稳定、目标明确 |
| 成本 | 每步都调用强模型，长任务成本高 | 规划一次，执行可用小模型 |
| 主要缺点 | 链路长、易循环、易丢失全局目标 | 遇到意外数据或分支时计划失效 |

**选择方法**：如果现在无法可靠预测第三步做什么，偏向 ReAct；如果能画出相对稳定的依赖图，偏向 Plan-and-Execute。实际常用混合：Plan-and-Execute 做全局，单步内部用 ReAct。

### Reflection（反思机制）是什么？为什么能提升 Agent 效果？实际怎么实现？ | 高频
Reflection 是让 Agent 对自己的输出或执行过程做**检查、批评、修正**的机制：先生成，再评审，再改写，循环到满足标准或达到次数上限。

![](images/Java八股（后端\)+Agent八股8-image-9.png)

![](<images/Java八股（后端)+Agent八股8-截屏2026-06-05 18.06.07.png>)

**为什么有效**：模型第一次输出常有遗漏、逻辑漏洞、格式错误或幻觉。把"生成"和"评审"拆开，相当于多了一层 Review，评审时可以对照明确标准发现问题。Reflexion（Shinn et al., 2023）进一步把失败后的反思文本存入记忆，供下一次尝试参考，相当于用语言反馈代替梯度更新。

**三种实现方式**
1. **Self-Reflection**：同一模型自评自改，成本最低。
2. **独立 Critic / Reviewer**：另一个角色或另一个模型评审，减少"自己看不出自己的错"。
3. **规则 / 外部验证 + 模型**：先用确定性手段检查（编译、单元测试、JSON Schema、字段校验、权限检查），再让模型检查语义和逻辑。关键任务应优先依赖外部验证器。

例：代码生成后，先跑编译和测试，再让 Reviewer 检查空指针、事务边界、SQL 注入、性能问题，最后输出修订版。

**风险与注意**
- 增加模型调用次数，带来额外 Token 和延迟，适合高价值、高风险任务。
- 没有明确评估标准时，可能"自信地错误修正"，把对的改成错的。
- 必须设反思轮数上限，防止无限修改。

### Tool-Use Agent 是什么？ | 高频
Tool-Use Agent 的重点不是模型自己多聪明，而是**知道什么时候该用哪个工具、参数怎么填**，把执行交给可靠的外部系统。

![](images/Java八股（后端\)+Agent八股8-image-10.png)

工具可以是搜索引擎、数据库、代码解释器、浏览器、企业 API、邮件、CRM、订单系统等。例：把发票金额录入表格，模型不应靠猜，而应调用 OCR → 校验 → 表格写入工具。

**常见追问**
- **Function Calling 和 Tool Use 的关系**：Function Calling 是模型输出结构化工具调用的能力；Tool-Use Agent 是围绕目标决定何时、如何、按什么顺序调用工具，并处理结果的系统。
- **工具描述为什么重要**：模型只能依据工具名、description 和参数 Schema 判断是否调用、怎么填参，描述不清或边界重叠会直接导致误用。
- **如何防止危险调用**：最小权限、工具白名单、参数校验、限流超时、审计日志、高风险动作人工确认。

### Tree of Thoughts、Self-Ask 和 Plan-and-Solve 分别解决什么问题？
- **Tree of Thoughts（ToT）**：在每一步生成多个候选思路，对中间状态打分，用 BFS / DFS 搜索并允许回溯。解决单一路径过早选错的问题，适合规划、谜题（如 24 点）、组合搜索。代价是分支数爆炸，需要限制深度、宽度和评估次数。Graph of Thoughts 进一步允许思路之间合并、聚合。
- **Self-Ask**：模型先显式提出子问题（"Follow up: ..."），逐个回答（可交给搜索工具），再组合成最终答案。解决多跳问答中隐含步骤没被处理的问题。弱点是子问题拆错时，后面即使每个都答对也答不了原问题。
- **Plan-and-Solve**：一种 Prompt 策略，先让模型列出解题计划，再按计划逐步求解（"先理解问题并制定计划，再逐步执行"）。用来减少 Zero-shot CoT 中的漏步骤、顺序混乱和计算错误。比 ToT 便宜，但只沿一套计划走，受初始计划质量影响。

### 不同 Agent 范式各有什么优缺点？ | 高频

| 范式 | 优点 | 缺点 |
| --- | --- | --- |
| ReAct | 灵活，可根据每步 Observation 调整；适合搜索、问答、实时查询等动态任务；轨迹清晰，易调试解释 | 多轮调用，延迟和成本高；局部贪心，缺少全局规划；长任务易走弯路、循环、丢失目标 |
| Plan-and-Execute | 任务拆解清晰，路径稳定；计划可人工审核；执行阶段可用小模型降本；适合代码重构、报告生成、数据处理 | 计划在执行前生成，对中间变化适应差；某步失败或环境变化时后续步骤可能失效，需要重规划，否则一错到底 |
| Reflection | 自我评估和纠错，降低错误率、提升鲁棒性；适合代码生成、复杂推理、结果校验 | 额外模型调用，成本和耗时增加；依赖评估标准，标准不清时可能无效反思甚至把对的改错 |

### ReAct、Plan-and-Execute、Reflection 在实际项目中如何选型？ | 高频
按任务特征决策，并且通常是组合使用。

![](images/Java+AI八股-image-38.png)

**决策步骤**
1. **先判断要不要 Agent**：流程 100% 固定、步骤已知 → 直接 Workflow。
2. **单 Agent 内部选型**
   - 单次工具调用即可（查一次、算一次）：直接 Function Calling。
   - 路径不确定、需要边查边判断（智能问答、搜索增强、故障排查）：ReAct。
   - 任务复杂但能先拆成大步骤（调研报告、数据分析、代码重构）：Plan-and-Execute。
   - 正确率要求高、允许多花成本（代码生成、合同审查、关键决策）：叠加 Reflection。
3. **是否升级多 Agent**：任务需要多个专业领域、上下文过大、需要并行或互相校验时再考虑。
   - 有总指挥、任务分层：主从（Supervisor）架构。
   - 有固定工序（调研 → 写作 → 审核）：流水线。
   - 各 Agent 平级、需要协商或辩论：对等 / 辩论式架构。
   - 大型系统：主从 + 流水线混合。

**常见组合**：Plan-and-Execute 做整体规划，每一步内部用 ReAct 调工具，关键步骤或最终结果用 Reflection 把关。

## 任务规划与 TodoList

### Agent 的 Planning 是如何实现的？大模型不擅长长链路规划，如何赋予它规划能力？ | 高频
Planning 是让 Agent 把目标拆解并逐步完成的能力。主流实现不是让模型完全自由规划，而是**规则保证底线，模型提供灵活性**：程序固定主干流程，模型在需要判断的环节做局部规划。

**分工**
- 强约束、高可靠的环节（身份验证、订单处理、售后规则）用代码硬编码。
- 需要灵活性的环节（客服回复、调研、分析）用 Prompt 引导模型规划和生成。

**增强长链路规划的手段**
1. **独立 Planner**：先输出结构化计划（如 JSON 任务列表），而不是直接执行。
2. **分解模板**：要求每个步骤写明目标、输入、工具、预期输出、校验标准。
3. **状态机 / 任务 DAG 管理执行**：由程序推进状态、维护依赖，模型不能随意跳步。
4. **反馈与重规划**：某步失败时把错误信息交回 Planner 修订剩余计划，而不是直接终止。
5. **外部状态记录**：用 TodoList / 进度文件保存计划和完成情况，避免长上下文中遗忘目标。
6. **工程兜底**：最大步数、工具权限、结果校验、关键节点人工确认，不完全信任模型的计划。

典型闭环：目标识别 → 任务拆分 → 工具选择 → 执行 → 观察结果 → 判断是否完成 → 必要时重规划。

### 你了解哪些常见的 Planning 方法？ | 高频
- **CoT（Chain of Thought）**：引导模型逐步推理，把问题拆成中间步骤再得到答案。Few-shot CoT 给带推理过程的示例；Zero-shot CoT 只需在 Prompt 加"Let's think step by step"。提升算术、常识、逻辑推理效果，代价是输出更长、更慢。
- **ToT（Tree of Thoughts）**：把 CoT 的单一路径扩展为树状搜索，每步生成多个候选并评估，结合 BFS / DFS 选择最优路径，可回溯。
- **ReAct**：Thought → Action → Observation 循环，推理中穿插工具调用和环境交互，适合需要动态获取信息的任务，过程可解释。
- **Reflexion**：在 ReAct 等方法基础上加入自我反思，任务失败后生成反思文本存入记忆，下次尝试时参考，类似一种不更新权重的"语言强化学习"。
- **Plan-and-Execute / Plan-and-Solve**：先产出完整计划再执行，适合可预判步骤的长任务。

### 不同 Planning 方法的适用性如何？ | 高频
一句话：线性推理用 CoT，多方案搜索用 ToT，需要交互用 ReAct，需要多次尝试持续改进用 Reflexion。

| 方法 | 适用任务 | 优点 | 缺点 |
| --- | --- | --- | --- |
| CoT | 单路径、逻辑清晰的推理：算术、常识、简单多步问题 | 实现简单，效果稳定 | 只走一条路，中间错一步结果就错；推理开销增加 |
| ToT | 需要比较多方案的复杂决策：规划、博弈、谜题 | 多路径探索，更可能找到全局较优解 | 计算成本高、慢，工程实现复杂 |
| ReAct | 需要与外部环境交互或调用工具：搜索问答、代码执行 | 能处理信息不完整的问题，动态调整 | 链路长，依赖工具质量，错误可能多轮累积 |
| Reflexion | 允许多轮尝试的任务：代码生成（有测试反馈）、复杂推理 | 通过反馈迭代提升质量 | 多次迭代效率低，依赖可靠的评估信号和记忆机制 |

### 复杂任务如何让 Agent 做任务拆分？为什么拆分后效果更好？
先识别目标、约束和交付物，再拆成多个**可验证**的小步骤，由 Planner 输出结构化任务列表。

**拆分方法**
- 例："生成竞品分析报告"拆成：确定分析维度 → 搜索竞品信息 → 提取核心数据 → 对比功能 → 分析优劣势 → 撰写报告 → 检查结论。
- 每个子任务包含：目标、输入、所需工具、预期输出、校验标准、依赖关系。
- 粒度以"一个子任务能用一两次工具调用完成、结果能被检查"为宜，过细会增加调度开销。

**为什么效果更好**
1. **降低单次推理难度**：一次性完成复杂任务容易漏步、逻辑混乱；子任务上下文更聚焦。
2. **每步可以用合适的工具或模型**：检索用搜索，计算用代码执行，写作用生成模型。
3. **便于检查纠错**：每个子任务都有中间结果，可以及时发现问题、局部重试，而不是最后才发现整体错误。
4. **可并行**：无依赖的子任务可以并发执行，缩短总耗时。

### TodoList 是什么？
TodoList 是 Agent 中 **Planning 模块的具体落地形式**：把模糊复杂的目标拆成一组按顺序或依赖关系组织的可执行子任务，并持续维护其状态。

- **任务拆解**：把非结构化目标转成清晰、可执行的步骤，降低复杂度。
- **边界控制**：每一步明确处理内容、可用工具和预期输出，让执行过程可控。
- **进度追踪**：记录每项是待办、进行中还是已完成，避免长流程中偏离目标、重复执行或遗漏步骤。

TodoList 通常作为外部状态保存（甚至写入文件），每轮重新注入上下文，相当于给模型一个"复述目标"的锚点。Claude Code 等编码 Agent 就通过 TodoWrite 类工具让模型显式维护待办列表。

### TodoItem 是什么，包含哪些元素？
TodoItem 是 TodoList 中的基本执行单元，描述一个具体子任务。常见字段：

| 字段 | 含义 |
| --- | --- |
| `task_id` | 唯一标识，用于索引、追踪和依赖引用 |
| `description` | 自然语言描述，说明这个子任务要做什么 |
| `status` | 状态：`pending`、`in_progress`、`completed`、`failed`、`skipped` |
| `dependencies` | 依赖的任务 ID，决定执行顺序 |
| `priority` | 优先级，多个可执行任务时决定先后 |
| `tools_required` | 需要调用的工具，提前约束执行方式 |
| `input` / `output` | 执行所需输入和产出结果，供后续任务使用 |
| `retry_count` | 失败重试次数，用于异常处理和上限控制 |
| `created_at` / `updated_at` | 生命周期时间，便于调度、排序和日志追踪 |

```json
{
  "task_id": "t3",
  "description": "对比三款竞品的定价方案",
  "status": "pending",
  "dependencies": ["t1", "t2"],
  "priority": 2,
  "tools_required": ["web_search"],
  "input": {"competitors": ["A", "B", "C"]},
  "output": null,
  "retry_count": 0
}
```

### TodoList 属于 ReAct 等 Agent 框架中的哪个部分？
TodoList 属于 **Planning 部分**，位于 Thought 到 Action 的转化环节，把思考结果落地为可执行、可追踪的任务。

- **在基础 ReAct 中**：通常不显式存在，任务规划隐含在连续的 Thought-Action-Observation 里，模型边想边决定下一步，没有单独维护任务列表。
- **在更复杂的框架中**：TodoList 是显式的任务管理模块。BabyAGI 有独立的 Task Creation、Task Prioritization 和 Execution Agent 维护任务队列；Plan-and-Execute 中计划本身就是 TodoList。
- **运行方式**：调度器不断从 TodoList 取出优先级最高且依赖已满足的任务执行，根据结果更新状态，必要时追加新的子任务或重排，形成持续迭代的闭环。

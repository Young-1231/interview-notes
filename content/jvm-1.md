## JVM 概述与编译执行
### JVM 概览
JVM 的核心功能可以归为四块：类加载、内存管理（运行时数据区）、垃圾回收、执行引擎（解释器 + JIT）。复习和回答时可以按一条主线串起来：

- **内存结构**：程序计数器、虚拟机栈、本地方法栈（线程私有），堆、方法区（线程共享），外加直接内存。
- **对象**：创建过程、内存布局、TLAB、逃逸分析。
- **垃圾回收**：可达性分析与 GC Roots → 回收算法 → 分代模型 → 收集器（CMS / G1 / ZGC）→ 三色标记。
- **类加载**：加载 → 验证 → 准备 → 解析 → 初始化，类加载器与双亲委派。
- **实战**：OOM 与内存泄漏排查、调优参数、监控工具。

面试中可以主动把话题引向自己熟悉的主线，例如从 GC 原理讲到回收算法，再讲到具体收集器。

### 讲一下 JVM | 高频
JVM（Java Virtual Machine）是运行 Java 字节码的虚拟机。`javac` 把 `.java` 编译成平台无关的 `.class` 字节码，再由各平台对应的 JVM 加载执行，这就是 Java 跨平台的基础。

JVM 主要负责：

- **类加载**：把 `.class` 加载进内存，完成加载、链接（验证、准备、解析）、初始化。
- **内存管理**：划分运行时数据区（程序计数器、虚拟机栈、本地方法栈、堆、方法区），为对象创建、方法调用提供内存。
- **垃圾回收**：自动识别并回收不再使用的对象，开发者不用手动释放内存。
- **执行引擎**：解释器逐条解释字节码，热点代码由 JIT 编译成本地机器码以提升性能。
- **本地接口**：通过 JNI 调用 C/C++ 实现的本地方法。

常见实现是 HotSpot（OpenJDK / Oracle JDK 默认），此外还有 OpenJ9、GraalVM 等。JVM 不只运行 Java，Kotlin、Scala、Groovy 等编译成字节码的语言也能在上面运行。

### 编译型语言和解释型语言有什么区别？
编译型语言在运行前把源码一次性编译成目标平台的机器码；解释型语言在运行时由解释器逐行翻译执行。

| 对比 | 编译型 | 解释型 |
| --- | --- | --- |
| 执行方式 | 先编译成机器码，再直接执行 | 运行时由解释器边翻译边执行 |
| 执行效率 | 高 | 相对低 |
| 跨平台 | 需要为每个平台分别编译 | 有解释器即可运行 |
| 开发调试 | 修改后要重新编译 | 修改后直接运行 |
| 代表 | C、C++、Go、Rust | Python、JavaScript（现代引擎也有 JIT） |

Java 两种特点兼有：先编译成字节码，再由 JVM 解释执行，热点代码再由 JIT 编译成机器码。

### Java 是编译型语言还是解释型语言？
Java 既不是纯编译型，也不是纯解释型，而是"先编译、后解释，热点代码再 JIT 编译"的混合模式。

- **前端编译**：`javac` 把 `.java` 编译成 `.class` 字节码，字节码不是机器码，操作系统不能直接执行。
- **解释执行**：JVM 的解释器逐条解释字节码，启动快，但执行慢。
- **JIT 编译**：运行中被频繁执行的热点代码会被 JIT 编译成本地机器码并缓存，之后直接执行机器码。
- **AOT 编译**：GraalVM Native Image 可以提前把程序编译成本地可执行文件，启动快、内存小，但会失去部分运行时优化和动态特性。

所以说 Java 是"半编译半解释"的语言更准确。

### 什么是 JIT 编译器？
JIT（Just-In-Time，即时编译器）是 JVM 执行引擎的一部分，它在运行时把热点字节码编译成本地机器码，后续直接执行机器码，从而提升性能。

**怎么识别热点代码**：HotSpot 用基于计数器的热点探测，方法调用计数器统计方法调用次数，回边计数器统计循环执行次数，超过阈值就触发编译（循环体可以通过 OSR 栈上替换在执行中途切换到编译版本）。

**两个编译器与分层编译**：
- C1（Client Compiler）：编译快，优化较少。
- C2（Server Compiler）：编译慢，优化激进，生成的代码更快。
- JDK 8 起默认开启分层编译（Tiered Compilation）：先解释执行，较热的代码先用 C1 编译并收集 profile，更热的再交给 C2。

**常见优化**：方法内联（最重要的优化，是其他优化的基础）、逃逸分析（栈上分配、标量替换、锁消除）、循环展开、死代码消除、常量折叠等。

**优缺点**：
- 优点：热点代码以机器码运行，并且能利用运行时信息做激进优化，性能可以接近甚至超过静态编译。
- 缺点：启动初期要先解释执行，需要预热；编译本身占用 CPU，编译后的代码存放在 Code Cache 里，占用额外内存（`-XX:ReservedCodeCacheSize`）。

### 为什么 Java 可以一次编译、到处运行？
因为 Java 源码编译成的是平台无关的字节码，而不是某个平台的机器码。字节码由各个平台上的 JVM 负责解释或 JIT 编译成该平台的机器码执行。

- **统一的字节码格式**：`.class` 文件格式和指令集由 JVM 规范定义，与操作系统、CPU 无关。
- **平台相关的 JVM**：Windows、Linux、macOS、x86、ARM 各有对应的 JVM 实现，屏蔽了底层差异。
- **统一的语言规范和类库**：基本类型长度固定（例如 `int` 恒为 32 位），标准类库在各平台行为一致。

注意：跨平台的是字节码，JVM 本身并不跨平台。另外，如果代码调用了 JNI 本地库，或者依赖特定系统路径、命令，就失去了跨平台性。

## 内存结构
### JVM 内存结构（运行时数据区）是怎样的？哪些区域线程私有，哪些共享？ | 高频 | 农业银行、交通银行
JVM 运行时数据区分为五块：程序计数器、虚拟机栈、本地方法栈是线程私有的，堆和方法区是线程共享的。直接内存不属于运行时数据区，但也常被一起问到。

| 区域 | 线程 | 存放内容 | 异常 |
| --- | --- | --- | --- |
| 程序计数器 | 私有 | 当前线程执行的字节码指令地址 | 唯一不会 OOM 的区域 |
| 虚拟机栈 | 私有 | 栈帧：局部变量表、操作数栈、动态链接、方法返回地址 | StackOverflowError、OOM |
| 本地方法栈 | 私有 | Native 方法的栈帧 | StackOverflowError、OOM |
| 堆 | 共享 | 对象实例、数组；JDK 7 起还有字符串常量池和静态变量 | OOM: Java heap space |
| 方法区 | 共享 | 类元数据、运行时常量池、JIT 编译后的代码 | OOM: PermGen space / Metaspace |

**版本差异（HotSpot）**：
- JDK 6 及之前：方法区由永久代实现，字符串常量池、静态变量都在永久代。
- JDK 7：字符串常量池和静态变量移到堆中，永久代还在。
- JDK 8 及之后：永久代被移除，方法区由元空间（Metaspace）实现，使用本地内存。元空间只存类元数据，不存字符串常量池和静态变量。

**直接内存**：不属于运行时数据区，是 NIO 通过 `ByteBuffer.allocateDirect()` 申请的堆外内存，减少堆与内核之间的数据拷贝，受 `-XX:MaxDirectMemorySize` 限制，超出也会 OOM。

### 程序计数器有什么作用？为什么是线程私有的？ | 高频
程序计数器（Program Counter Register）是一块很小的线程私有内存，记录当前线程正在执行的字节码指令地址。

**作用**：
- 字节码解释器通过改变计数器的值选取下一条指令，分支、循环、跳转、异常处理、线程恢复都依赖它。
- 线程切换后，靠它恢复到正确的执行位置。
- 执行 Native 方法时，计数器的值为空（undefined）。

**为什么线程私有**：Java 多线程通过 CPU 时间片轮转实现，同一时刻一个核只执行一个线程的指令。线程被切换出去再切回来时，需要知道自己上次执行到哪里。每个线程执行的代码和进度都不同，如果共享一个计数器就会互相覆盖，所以每个线程都要有独立的程序计数器。

**特点**：生命周期与线程相同；占用空间极小且固定，是 JVM 规范中唯一没有规定 OutOfMemoryError 的区域。

### Java 虚拟机栈有什么作用？ | 高频
虚拟机栈（JVM Stack）是线程私有的，描述 Java 方法执行的内存模型：每调用一个方法就创建一个栈帧压栈，方法返回（正常返回或抛异常）时栈帧出栈。

**栈帧组成**：
- **局部变量表**：存放方法参数和局部变量，包括基本类型的值和对象引用，容量在编译期确定，以 slot 为单位（`long`、`double` 占两个 slot）。
- **操作数栈**：字节码指令计算时的临时工作区。
- **动态链接**：指向运行时常量池中该方法的引用，用于把符号引用转换为直接引用（支持多态等）。
- **方法返回地址**：方法退出后回到调用者的位置。

**特点与异常**：
- 生命周期与线程相同，线程之间互不影响，栈上数据天然线程安全。
- 栈大小用 `-Xss` 设置（64 位 Linux 默认 1MB）。
- 调用层次过深（比如无限递归）超过栈容量，抛 `StackOverflowError`。
- 创建线程时无法申请到栈内存（例如线程过多），抛 `OutOfMemoryError: unable to create native thread`。HotSpot 的栈不能动态扩展，所以 OOM 主要出现在创建线程时。

### 本地方法栈有什么作用？ | 高频
本地方法栈（Native Method Stack）是线程私有的，作用与虚拟机栈类似，区别是它为 Native 方法服务，而虚拟机栈为 Java 方法服务。

- **服务 Native 方法**：Java 通过 JNI 调用 C/C++ 实现的方法（如 `Object.hashCode()`、`Thread.start0()`、文件和网络 I/O 的底层实现）时，用的是本地方法栈。
- **实现方式**：JVM 规范没有强制规定它的结构，HotSpot 直接把本地方法栈和虚拟机栈合二为一。
- **异常**：和虚拟机栈一样，可能抛 `StackOverflowError` 和 `OutOfMemoryError`。

### Java 堆有什么作用？ | 高频
Java 堆（Heap）是 JVM 管理的最大一块内存，所有线程共享，在 JVM 启动时创建，用来存放对象实例和数组，也是 GC 管理的主要区域（因此也叫 GC 堆）。

- **存放对象**：几乎所有对象实例和数组都在堆上分配。JIT 经过逃逸分析后，未逃逸的对象可能被标量替换，不在堆上分配。
- **其他内容**：HotSpot 从 JDK 7 起，字符串常量池和类的静态变量（随 Class 对象）也存放在堆中。
- **分代管理**：传统分代收集器把堆分为年轻代（Eden + 两个 Survivor）和老年代，默认 `NewRatio=2`（年轻代:老年代 = 1:2）、`SurvivorRatio=8`（Eden:S0:S1 = 8:1:1）。G1 在物理上把堆划分成等大的 Region，分代只是逻辑概念。
- **TLAB**：为减少并发分配的锁竞争，Eden 中为每个线程划出私有的分配缓冲区。
- **大小设置**：`-Xms` 初始大小，`-Xmx` 最大大小，生产环境通常设成相等，避免运行时扩缩容。
- **异常**：对象无法分配且堆无法再扩展时，抛 `OutOfMemoryError: Java heap space`。

### 方法区有什么作用？ | 高频
方法区（Method Area）是 JVM 规范定义的线程共享区域，用于存放已加载类的元数据。它是一个逻辑概念，不同 JDK 版本有不同实现。

**存放内容（HotSpot JDK 8+）**：
- 类元数据：类名、父类、接口、字段、方法、访问修饰符等（InstanceKlass）。
- 方法的字节码、运行时常量池（类文件常量池在类加载后的运行时形式）。
- JIT 编译后的代码（实际在 Code Cache 中）。

**静态变量和字符串常量池在哪里**：规范层面它们属于方法区的概念，但在 HotSpot 中，JDK 6 及之前它们在永久代里；JDK 7 起已经移到 Java 堆中（静态变量随 Class 对象存放在堆里），JDK 8 的元空间里没有它们。所以被问到 HotSpot 的具体位置时，要回答在堆中。

**实现变迁**：
- JDK 7 及之前：永久代（PermGen），位于 JVM 内存中，大小由 `-XX:MaxPermSize` 固定。
- JDK 8 及之后：元空间（Metaspace），使用本地内存，用 `-XX:MetaspaceSize`、`-XX:MaxMetaspaceSize` 控制。

**回收**：方法区也会被 GC，主要回收废弃常量和不再使用的类（类卸载），但条件苛刻、收益较低。

### 方法区、永久代、元空间有什么区别？为什么用元空间替换永久代？ | 高频 | 邮政储蓄银行、拼多多、华为、得物
方法区是 JVM 规范中的逻辑区域；永久代和元空间是 HotSpot 对方法区的两种实现，前者用于 JDK 7 及之前，后者用于 JDK 8 及之后。

| 对比 | 永久代（PermGen） | 元空间（Metaspace） |
| --- | --- | --- |
| 版本 | JDK 7 及之前 | JDK 8 及之后 |
| 内存位置 | JVM 管理的内存，与堆连续 | 本地内存（Native Memory） |
| 大小 | 固定上限，`-XX:MaxPermSize` | 默认只受物理内存限制，可用 `-XX:MaxMetaspaceSize` 设上限 |
| 存放内容 | 类元数据；JDK 6 还有字符串常量池、静态变量 | 只有类元数据 |
| OOM 信息 | `PermGen space` | `Metaspace` |

**为什么要替换**：
- **大小难以确定**：动态代理、CGLIB、反射、JSP、热部署等会动态生成大量类，永久代上限固定，容易 `OutOfMemoryError: PermGen space`。元空间用本地内存，空间更充裕，也可以按需增长。
- **GC 更简单**：永久代需要由 GC 专门管理，回收效率低、调优复杂。元空间按类加载器分配内存块，类加载器被回收时整块释放。
- **合并 JRockit**：Oracle 合并 HotSpot 和 JRockit，JRockit 本来就没有永久代，统一后移除永久代。

注意：元空间不设上限时，类泄漏会一直吃本地内存，生产环境建议设置 `-XX:MaxMetaspaceSize`。

### 变量和基本数据类型存在堆还是栈？ | 高频 | 农业银行、淘天
存放位置取决于变量定义在哪里，而不是它是不是基本类型。

| 变量 | 存放位置（HotSpot） |
| --- | --- |
| 方法内的局部变量（基本类型） | 虚拟机栈栈帧的局部变量表，直接存值 |
| 方法内的局部变量（引用类型） | 引用在局部变量表，引用指向的对象在堆 |
| 成员变量（实例字段，包括基本类型） | 随对象一起存放在堆中 |
| 静态变量 | JDK 7 起随 Class 对象存放在堆中（JDK 6 及之前在永久代） |
| 包装类对象（Integer 等） | 对象在堆中；`Integer.valueOf` 对 -128~127 使用缓存对象 |
| 字符串字面量 | 字符串常量池，JDK 7 起在堆中 |
| `static final` 编译期常量 | 编译时直接内联进使用方的字节码，类文件常量池里也有一份 |

**常见追问**：
- "基本类型都在栈上"是错的，作为对象字段的基本类型随对象存在堆里。
- 元空间（JDK 8+）只存类的元数据，既不放静态变量的值，也不放字符串常量池。
- JIT 经过逃逸分析，对未逃逸的对象做标量替换后，对象字段会被拆成局部变量放在栈上或寄存器里，不再分配在堆上。

### 为什么要区分堆和栈？
堆和栈的生命周期、共享方式和管理方式完全不同，分开设计可以让两类数据各用最合适的管理方式。

| 对比 | 栈 | 堆 |
| --- | --- | --- |
| 存放内容 | 栈帧：局部变量、操作数栈、返回地址 | 对象实例、数组 |
| 线程 | 私有，天然线程安全 | 共享，需要同步 |
| 生命周期 | 随方法调用入栈、返回出栈 | 不确定，由 GC 判断回收 |
| 分配释放 | 移动栈顶指针，极快，不需要 GC | 需要分配算法和 GC |
| 大小 | 小，`-Xss` | 大，`-Xms` / `-Xmx` |
| 异常 | StackOverflowError | OOM: Java heap space |

- **体现程序的不同视角**：栈代表处理逻辑（方法怎么执行），堆代表数据（对象是什么），分离后逻辑更清晰。
- **共享与隔离**：对象放堆上，多个线程、多个栈帧可以通过引用共享同一份数据；栈私有则不需要同步。
- **性能与 GC**：短生命周期的局部数据放栈上随方法结束自动释放，GC 只需关注堆，回收范围更小。
- **问题定位**：栈溢出和堆溢出是两类不同问题，分开后更容易排查。

### JDK7 为什么把字符串常量池移到堆中？
主要原因是永久代空间小且回收效率低，字符串常量池放在里面容易 OOM，也不能及时回收。

- **避免 PermGen OOM**：永久代大小固定且通常较小（默认几十 MB），大量使用 `intern()` 或字符串常量很多的应用容易抛 `OutOfMemoryError: PermGen space`。堆空间大得多。
- **回收更及时**：永久代只有 Full GC 时才回收，字符串常量池里不再使用的字符串迟迟释放不了。放到堆里后，年轻代 GC 和老年代 GC 都能回收它们。
- **为移除永久代铺路**：JDK 7 先把字符串常量池和静态变量移出永久代，JDK 8 再彻底用元空间替代永久代。

字符串常量池本质上是一个 `StringTable`（固定桶数的哈希表），JDK 7u40 起默认桶数为 60013，可用 `-XX:StringTableSize` 调整。

### new String("abc") 会在哪些地方创建对象？intern() 有什么作用？
`new String("abc")` 会创建一个或两个对象：如果常量池里还没有 `"abc"`，类加载解析字面量时会在字符串常量池创建一个；执行 `new` 时一定会在堆中再创建一个新的 String 对象。

```java
String s1 = "abc";              // 指向常量池里的 "abc"
String s2 = new String("abc");  // 堆上的新对象，内部共享同一个 value 数组
System.out.println(s1 == s2);   // false
System.out.println(s1 == s2.intern()); // true
```

**intern() 的作用**：如果字符串常量池中已有相等的字符串，返回池中的引用；如果没有：
- JDK 6：把该字符串复制一份到永久代的常量池，返回这份副本的引用。
- JDK 7+：不再复制，直接把当前堆中这个 String 对象的引用记录到常量池，并返回它本身。

```java
String s = new String("a") + new String("b"); // 堆上的 "ab"，常量池里还没有 "ab"
s.intern();
System.out.println(s == "ab"); // JDK 7+ 为 true，JDK 6 为 false
```

**用途**：大量重复字符串（如从数据库读出的城市名、状态码）调用 `intern()` 可以让它们共享一份，节省内存；但常量池是固定桶数的哈希表，滥用会让查找变慢。

### 什么是直接内存？
直接内存（Direct Memory）是 JVM 堆外、由操作系统分配的本地内存，不属于运行时数据区，Java 通过 NIO 的 `ByteBuffer.allocateDirect()` 申请，Netty 等框架大量使用。

**为什么用**：堆内的 ByteBuffer 做 I/O 时，JVM 需要先把数据拷贝到一块堆外临时内存再交给系统调用（GC 可能移动堆上对象，地址不稳定）。直接内存省掉了这次拷贝，适合大块、长期复用的 I/O 缓冲区。

**怎么管理和释放**：
- 堆上只有一个很小的 `DirectByteBuffer` 对象，它关联一个 `Cleaner`（虚引用）。当 `DirectByteBuffer` 被 GC 回收后，Cleaner 会调用 `Unsafe.freeMemory` 释放对应的本地内存，不需要也没有公开 API 手动释放。
- 大小受 `-XX:MaxDirectMemorySize` 限制，默认与 `-Xmx` 大致相同。
- 申请时如果达到上限，JDK 会主动调用 `System.gc()` 尝试回收，再重试分配，仍不够才抛 `OutOfMemoryError: Direct buffer memory`。所以开启 `-XX:+DisableExplicitGC` 可能导致直接内存 OOM。

**缺点**：申请和释放比堆内存开销大，适合池化复用；回收依赖堆上小对象的 GC，堆很空闲而直接内存吃紧时容易积压；Heap Dump 里看不到它的内容，排查比较麻烦（可用 NMT `-XX:NativeMemoryTracking` 辅助）。

### 什么是 Java 内存模型（JMM）？主要目的是什么？
JMM（Java Memory Model）是 Java 语言规范定义的一套规则，规定多线程下共享变量的读写如何对其他线程可见、哪些重排序是允许的。它和 JVM 内存结构（堆、栈等）不是一回事。

**抽象模型**：所有共享变量存在主内存，每个线程有自己的工作内存（对应 CPU 缓存、寄存器的抽象），线程操作的是变量副本，再与主内存同步。

**主要目的**：屏蔽不同硬件和操作系统的内存访问差异，让 Java 程序在各平台都有一致的并发语义，围绕三个特性：
- **原子性**：`synchronized`、`Lock`、原子类保证复合操作不可分割（基本类型的读写本身是原子的，64 位 `long`/`double` 在 32 位 JVM 上不加 `volatile` 不保证原子）。
- **可见性**：`volatile`、`synchronized`、`final` 保证一个线程的修改能被其他线程看到。
- **有序性**：`volatile`（内存屏障）、`synchronized` 禁止特定的指令重排序。

**happens-before 规则**：JMM 的核心，前一个操作的结果对后一个操作可见。常见规则有程序次序规则、监视器锁规则（解锁 happens-before 后续加锁）、volatile 规则（写 happens-before 后续读）、线程启动规则、线程终止规则、传递性等。

## 对象创建与内存分配
### 对象的创建过程是怎样的？对象的内存布局是怎样的？ | 高频
**创建过程**：执行 `new` 时，HotSpot 依次完成五步。

1. **类加载检查**：类还没加载、链接、初始化就先执行类加载。
2. **分配内存**：大小在类加载后已确定。堆规整用指针碰撞，不规整用空闲列表；并发安全靠 TLAB 优先 + CAS 失败重试。
3. **初始化零值**：内存（不含对象头）置零，所以字段不赋值也有默认值。
4. **设置对象头**：写入 Mark Word 和类型指针。
5. **执行 `<init>`**：字段初始化和构造方法执行完，对象才真正可用。

**内存布局**：对象头、实例数据、对齐填充三部分。

- **Mark Word**：64 位 JVM 上 8 字节，存哈希码、GC 分代年龄（4 位，所以最大 15）、锁状态、偏向线程 ID 等，内容随锁状态变化。
- **类型指针**：指向元空间中的 InstanceKlass（不是堆里的 `java.lang.Class` 对象，Class 对象只是它的镜像）。默认开启压缩类指针时 4 字节，否则 8 字节。
- **数组长度**：只有数组有，4 字节。
- **实例数据**：含父类字段，JVM 会重排字段减少空隙。
- **对齐填充**：对象大小补齐到 8 字节整数倍。

**常见追问**：默认开启压缩指针时 `new Object()` 占 16 字节（8 Mark Word + 4 类型指针 + 4 填充），可用 JOL 查看。JDK 24 实验性引入、JDK 25 转正的 Compact Object Headers（`-XX:+UseCompactObjectHeaders`，默认不开启）能把对象头压到 8 字节。

**访问方式**：HotSpot 用直接指针，引用直接指向堆中对象；句柄访问多一次间接，但对象移动时引用不变。

### 创建对象有哪些方式？
常见有五种方式：

| 方式 | 示例 | 是否调用构造方法 |
| --- | --- | --- |
| `new` 关键字 | `new User()` | 是 |
| 反射 | `User.class.getDeclaredConstructor().newInstance()` | 是 |
| clone | 实现 `Cloneable`，调用 `obj.clone()` | 否 |
| 反序列化 | `ObjectInputStream.readObject()` | 否（会调用第一个非 Serializable 父类的无参构造） |
| Unsafe | `Unsafe.allocateInstance(User.class)` | 否 |

- `Class.newInstance()` 在 JDK 9 已被标记为废弃，推荐用 `Constructor.newInstance()`。
- `clone()` 默认是浅拷贝，引用类型字段只复制引用。
- 工厂方法、Builder、Spring 容器等本质上还是上面某种方式。

### 对象分配内存的方式有哪些？
分配方式有指针碰撞和空闲列表两种，选哪种取决于堆是否规整，而堆是否规整又取决于垃圾收集器有没有压缩整理能力。

- **指针碰撞（Bump the Pointer）**：已用内存和空闲内存各在一边，中间放一个指针作为分界，分配时只要把指针往空闲一侧移动对象大小的距离。速度快，适用于 Serial、ParNew、Parallel、G1 等带复制或整理的收集器。
- **空闲列表（Free List）**：已用和空闲内存相互交错，JVM 维护一个记录可用内存块的列表，分配时找一块足够大的。适用于基于标记-清除的 CMS（CMS 的老年代用空闲列表）。

**并发安全问题**：多个线程同时分配时，可能出现两个线程拿到同一块内存。解决方式有两种：
- **CAS + 失败重试**：保证更新指针的原子性。
- **TLAB**：每个线程预先在 Eden 中分到一小块私有缓冲区，在自己的 TLAB 里分配不需要同步，TLAB 用完再用 CAS 申请新的。HotSpot 默认开启（`-XX:+UseTLAB`）。

### 什么是 TLAB？
TLAB（Thread Local Allocation Buffer，线程本地分配缓冲区）是 JVM 在 Eden 区为每个线程划分的一小块私有内存，用来减少多线程分配对象时的竞争。

- **工作原理**：线程创建对象时优先在自己的 TLAB 中用指针碰撞分配，不需要加锁。TLAB 用完后，用 CAS 从 Eden 再申请一块新的 TLAB；对象太大放不进 TLAB 时，直接在 Eden 中用 CAS 分配。
- **大小**：默认动态调整，初始约占 Eden 的 1%，JVM 会根据线程分配速率自适应。相关参数有 `-XX:+UseTLAB`（默认开启）、`-XX:TLABSize`、`-XX:+ResizeTLAB`。
- **优势**：把并发分配的同步开销降到"每申请一块 TLAB 同步一次"，大幅提升多线程下的分配速度。

**注意**：
- TLAB 属于 Eden，Eden 属于堆，TLAB 只是堆上的一种分配方式，不是独立的内存区域。
- TLAB 只是分配时私有，分配出来的对象其他线程照样可以访问，TLAB 不保证对象线程安全。
- TLAB 剩余空间不够放一个对象时，会根据浪费阈值决定是丢弃当前 TLAB 重新申请，还是直接在 Eden 共享区分配，有一定的空间浪费。

### 对象一定分配在堆上吗？ | 高频
不一定。绝大多数对象分配在堆上，但 JIT 经过逃逸分析，发现对象不会逃逸出方法时，可以不在堆上分配。

- **默认在堆上**：解释执行和未被优化的代码里，对象都在堆上分配，优先走 Eden 中的 TLAB。TLAB 本身就是堆的一部分，在 TLAB 中分配仍然是堆分配。
- **标量替换**：HotSpot 实际采用的优化。对于未逃逸的对象，JIT 不创建对象，而是把它拆成若干个基本类型的局部变量（标量），放在栈帧或寄存器里。效果上等同于"对象没有在堆上分配"，随方法结束自动消失，不给 GC 增加负担。
- **栈上分配**：理论上可以把整个对象分配在栈上，但 HotSpot 并没有实现真正的栈上分配，是通过标量替换达到类似效果。
- **前提条件**：只对 JIT 编译后的热点代码生效；需要开启逃逸分析（`-XX:+DoEscapeAnalysis`）和标量替换（`-XX:+EliminateAllocations`），JDK 8 起默认都开启；对象不能太大，数组等无法拆分的对象一般不行。

```java
public int sum() {
    Point p = new Point(1, 2); // p 未逃逸，可能被标量替换为 int x = 1, y = 2
    return p.x + p.y;
}
```

### 什么是逃逸分析？
逃逸分析（Escape Analysis）是 JIT 编译器的一种分析技术，判断对象的作用范围是否会超出当前方法或当前线程，本身不是优化，而是为后续优化提供依据。

**三种逃逸状态**：
- **不逃逸**：对象只在方法内部创建和使用。
- **方法逃逸**：对象作为返回值返回，或作为参数传给其他方法（且该方法未被内联）。
- **线程逃逸**：对象被赋值给静态变量、其他线程可访问的成员变量等，可能被其他线程访问。

**基于逃逸分析的优化**：
- **标量替换**：不逃逸的对象被拆成基本类型字段，不在堆上分配（HotSpot 的"栈上分配"就是靠它实现的）。
- **锁消除**：对象不会线程逃逸时，对它加的锁可以去掉，例如方法内部局部 `StringBuffer` 的 `append` 同步。
- **同步消除和栈上分配**本质都依赖"对象不被外部访问"这一结论。

**局限**：分析本身耗费编译时间，并且是保守的；只作用于 C2 编译的热点代码。JDK 8 起 `-XX:+DoEscapeAnalysis` 默认开启。编码时尽量缩小对象作用域、避免不必要地把对象暴露出去，有利于 JIT 优化。

### 对象的分配策略是怎样的？
HotSpot 分代收集器下，对象分配遵循几条规则：

1. **优先在 Eden 分配**：新对象优先在 Eden 区（具体是线程的 TLAB）分配。Eden 空间不足时触发一次 Minor GC。
2. **大对象直接进入老年代**：需要大量连续内存的对象（大数组、长字符串）可以直接在老年代分配，避免在 Eden 和 Survivor 之间反复复制。Serial 和 ParNew 通过 `-XX:PretenureSizeThreshold` 设置阈值（Parallel Scavenge 不支持该参数）；G1 中超过 Region 一半大小的对象会被放入 Humongous Region。
3. **长期存活的对象进入老年代**：对象在 Eden 出生，经过第一次 Minor GC 存活并被移入 Survivor 后年龄为 1，此后每熬过一次 Minor GC 年龄加 1，达到 `-XX:MaxTenuringThreshold`（默认 15）时晋升到老年代。
4. **动态年龄判定**：按年龄从小到大累加 Survivor 中对象的大小，累加到年龄 N 时超过 Survivor 容量的 `TargetSurvivorRatio`（默认 50%），就把晋升阈值调整为 N，年龄大于等于 N 的对象直接晋升。
5. **空间分配担保**：Minor GC 前，JVM 检查老年代最大可用连续空间是否大于新生代所有对象总大小，或大于历次晋升的平均大小（JDK 6u24 之后的规则），满足则进行 Minor GC，否则改为 Full GC。Minor GC 后 Survivor 放不下的存活对象，直接由老年代担保接收。

## 垃圾识别与引用类型
### 什么是垃圾回收？ | 高频
垃圾回收（Garbage Collection，GC）是 JVM 自动识别不再被使用的对象并释放其内存的机制，开发者不需要像 C/C++ 那样手动 `free`/`delete`。

**回收范围**：主要是 Java 堆，其次是方法区（废弃常量、无用类）。程序计数器、虚拟机栈、本地方法栈随线程生灭，栈帧随方法进出自动分配和释放，不需要 GC。

**GC 要解决的三个问题**：
- **哪些内存需要回收**：通过可达性分析判断对象是否存活。
- **什么时候回收**：Eden 满时触发 Minor GC，老年代或元空间不足等情况触发 Full GC 等。
- **怎么回收**：标记-清除、标记-复制、标记-整理等算法，由 Serial、Parallel、CMS、G1、ZGC 等收集器具体实现。

**优点**：降低开发成本，避免野指针、重复释放、大部分内存泄漏问题。

**代价**：GC 会占用 CPU，部分阶段需要 STW 暂停用户线程，影响延迟和吞吐量；对象仍被无意持有时 GC 也无能为力，内存泄漏依然存在。

### 如何识别垃圾？对象可以被回收就一定会被回收吗？ | 高频
**识别垃圾的两种算法**：

- **引用计数法**：每个对象维护一个引用计数器，被引用加 1，引用失效减 1，为 0 即可回收。实现简单、判定及时，但无法处理循环引用（A 引用 B、B 引用 A，外部已无引用，计数却都不为 0），而且每次赋值都要更新计数。Python（配合循环检测）、Objective-C 的 ARC 使用它，HotSpot 不使用。
- **可达性分析**：HotSpot 实际使用的算法。以一组 GC Roots 为起点，沿引用关系向下搜索，走过的路径称为引用链。从 GC Roots 不可达的对象判定为可回收，循环引用的孤岛也能被正确识别。

**可以回收不等于一定会回收**：

1. **两次标记与 finalize()**：对象第一次被判定不可达后会被标记一次。如果它重写了 `finalize()` 且还没执行过，会被放进 F-Queue，由低优先级的 Finalizer 线程执行。如果在 `finalize()` 中把自己重新挂到引用链上（如赋值给某个静态变量），就能"自救"，第二次标记时被移出回收集合。`finalize()` 只会执行一次，所以第二次就无法自救了。
2. **回收时机由 GC 决定**：对象变成垃圾后，要等到下一次覆盖它所在区域的 GC 才会被回收。例如老年代的垃圾在 Minor GC 中不会被回收；并发收集时产生的浮动垃圾也要等下一轮。
3. **软引用**：软引用对象只在内存不足时才回收。

`finalize()` 执行时机不确定、开销大、可能让对象复活，JDK 9 已标记为废弃，JDK 18 起（JEP 421）被标记为将要移除。资源清理应使用 try-with-resources 或 `java.lang.ref.Cleaner`。

### 哪些对象可以作为 GC Roots？ | 高频
GC Roots 是可达性分析的起点，是一组当前一定存活、外部可以直接访问到的引用。HotSpot 中主要包括：

1. **虚拟机栈中引用的对象**：各线程栈帧局部变量表里的引用，如方法参数、局部变量。
2. **本地方法栈中 JNI 引用的对象**：Native 方法持有的引用。
3. **类静态属性引用的对象**：如 `static User admin = new User()`（JDK 7 起静态变量在堆中，但它仍然是根）。
4. **常量引用的对象**：如字符串常量池里的引用。
5. **被同步锁持有的对象**：`synchronized` 锁住的对象。
6. **JVM 内部引用**：基本类型对应的 Class 对象、常驻的异常对象（如 NullPointerException、OutOfMemoryError）、系统类加载器。
7. **活动线程对象本身**，以及反映 JVM 内部情况的 JMXBean、JVMTI 中注册的回调、本地代码缓存等。

**补充**：
- 分代或局部回收时（如 Minor GC、G1 回收部分 Region），其他区域指向回收区域的引用也要临时当作根。为了避免扫描整个老年代，HotSpot 用卡表（Card Table）/ 记忆集（Remembered Set）记录跨代引用。
- 枚举根节点必须在一致性快照中进行，所以这一步需要 STW；HotSpot 借助 OopMap 记录引用位置，并只在安全点（Safepoint）暂停线程，以缩短停顿。

### 强引用、软引用、弱引用、虚引用有什么区别？
JDK 1.2 起 Java 把引用分为四种，强度依次递减，区别在于对象被 GC 回收的时机。

| 类型 | 回收时机 | 能否 get 到对象 | 典型用途 |
| --- | --- | --- | --- |
| 强引用 | 只要强引用还在，永远不回收，宁可 OOM | 能 | 普通的 `Object o = new Object()` |
| 软引用 `SoftReference` | 内存不足、即将 OOM 前回收 | 能（回收前） | 内存敏感的缓存，如图片缓存 |
| 弱引用 `WeakReference` | 下一次 GC 时，不论内存是否充足都回收 | 能（回收前） | `WeakHashMap`、`ThreadLocalMap` 的 Key |
| 虚引用 `PhantomReference` | 不影响对象生命周期 | 不能，`get()` 恒为 null | 跟踪对象被回收，如 `Cleaner` 释放直接内存 |

```java
SoftReference<byte[]> soft = new SoftReference<>(new byte[1024]);
WeakReference<Object> weak = new WeakReference<>(new Object());
ReferenceQueue<Object> queue = new ReferenceQueue<>();
PhantomReference<Object> phantom = new PhantomReference<>(new Object(), queue); // 必须配合队列
```

**补充**：
- 软、弱、虚引用都可以配合 `ReferenceQueue` 使用：引用的对象被回收后（虚引用是对象即将被回收时），引用本身会被放入队列，程序可以借此做清理工作。
- 软引用的实际回收策略还与 `-XX:SoftRefLRUPolicyMSPerMB` 有关，空闲越久、可用堆越少，越容易被回收。
- 让对象"只剩弱引用"是避免缓存类内存泄漏的常用手段。

## 分代回收与 GC 类型
### 分代回收是什么？JVM 堆内存分为几个部分？ | 高频
分代回收是按对象存活时间把堆划分成不同区域，各区域用不同频率和算法回收的策略。传统分代收集器把堆分为年轻代和老年代两部分。

- **年轻代（Young Generation）**：存放新创建的对象，又分为一个 Eden 区和两个 Survivor 区（S0/S1，也叫 From/To）。默认 Eden:S0:S1 = 8:1:1（`-XX:SurvivorRatio=8`），同一时刻只有一个 Survivor 在使用，所以年轻代可用空间是 90%。
- **老年代（Old Generation）**：存放多次 GC 后仍存活的对象和大对象。默认年轻代:老年代 = 1:2（`-XX:NewRatio=2`），也可用 `-Xmn` 直接指定年轻代大小。

**一次典型的分代回收**：
1. 新对象在 Eden 分配，Eden 满时触发 Minor GC。
2. Eden 和 From Survivor 中的存活对象复制到 To Survivor，年龄加 1，然后清空 Eden 和 From，两个 Survivor 角色互换。
3. 年龄达到阈值、动态年龄判定命中、或 To 区放不下的对象晋升到老年代。
4. 老年代满了触发 Major GC / Full GC。

**注意**：
- 元空间（JDK 8+）存类元数据，不属于堆；JDK 7 及之前的永久代在实现上与堆相邻，所以老资料会说"堆分为年轻代、老年代、永久代"。
- G1 把堆划分为大小相等的 Region，分代只是逻辑上的；ZGC 在 JDK 21 之前不分代，JDK 21 起支持分代模式。

### 为什么要分代收集？年轻代和老年代分别用什么算法？ | 高频
分代收集基于两个经验假说：绝大多数对象朝生夕死（弱分代假说）；熬过越多次 GC 的对象越难消亡（强分代假说）。把两类对象分开放，就能针对各自特点选择算法和回收频率，减少每次 GC 的扫描和复制量。

| 区域 | 特点 | 常用算法 | 原因 |
| --- | --- | --- | --- |
| 年轻代 | 存活率低，回收频繁 | 标记-复制 | 只需复制少量存活对象，速度快且无碎片；Eden:S0:S1 = 8:1:1，只浪费 10% 空间 |
| 老年代 | 存活率高，没有额外空间做担保 | 标记-清除或标记-整理 | 复制大量存活对象成本高，还需要等量空闲空间 |

**收益**：
- 频繁的 Minor GC 只扫描年轻代，耗时短；老年代回收次数少。
- 对象晋升前已经被年轻代过滤掉大部分垃圾，老年代压力小。

**代价**：存在跨代引用（老年代对象引用年轻代对象），为了 Minor GC 时不扫描整个老年代，需要用卡表 / 记忆集记录跨代引用，并用写屏障维护。

**收集器对应**：Serial / ParNew / Parallel Scavenge 负责年轻代（复制算法）；Serial Old、Parallel Old 用标记-整理，CMS 用标记-清除；G1 整体看是标记-整理，Region 之间是复制。

### Eden 区大小会怎样影响程序？ | 高频
Eden 区大小直接决定 Minor GC 的频率，也会影响单次停顿和晋升速度。

- **Eden 过小**：很快被填满，Minor GC 非常频繁。每次 Minor GC 都要 STW，接口延迟抖动增多；而且对象还没来得及"死"就被频繁 GC，年龄增长快、过早晋升，进而让老年代 GC 也变得频繁。
- **Eden 过大**：Minor GC 次数减少，大部分短命对象在 GC 前已经死亡。Minor GC 的耗时主要取决于存活对象的数量（需要扫描根和复制存活对象），而不是 Eden 大小，所以单次耗时一般只是略增。代价是老年代空间被压缩，在堆总大小固定时老年代更容易满。
- **怎么调**：结合对象分配速率、存活率和延迟目标，用 `-Xmn` 或 `-XX:NewRatio` 调整。一般经验是让 Minor GC 间隔不要太短，同时老年代留足空间。使用 G1 时不要手动固定年轻代大小，否则会干扰 G1 根据 `MaxGCPauseMillis` 的自适应调整。

### Survivor 区大小会怎样影响程序？ | 高频
Survivor 区大小决定了 Minor GC 后存活对象能否留在年轻代，从而影响对象晋升到老年代的速度。

- **Survivor 过小**：
  - Minor GC 后存活对象放不下，多出来的直接通过分配担保进入老年代。
  - 动态年龄判定的阈值是 Survivor 容量 × `TargetSurvivorRatio`（默认 50%），Survivor 小时很容易超过，晋升阈值会被调低到 1，短命对象被过早晋升（过早晋升 premature promotion）。
  - 结果是老年代增长快，Old GC / Full GC 更频繁。
- **Survivor 过大**：两个 Survivor 同一时刻只用一个，空间浪费大；Eden 相应变小，Minor GC 更频繁；还可能让本该晋升的长寿对象在两个 Survivor 之间来回复制。
- **怎么调**：用 `-XX:SurvivorRatio` 调整比例，开启 `-XX:+PrintTenuringDistribution`（JDK 9+ 用 `-Xlog:gc+age=trace`）观察各年龄对象大小和实际晋升阈值。如果阈值经常被调成 1、2，说明 Survivor 偏小。

### 对象什么时候会进入老年代？ | 高频
对象有四种进入老年代的途径：

1. **年龄达到晋升阈值**：对象在 Survivor 中每熬过一次 Minor GC 年龄加 1，达到 `-XX:MaxTenuringThreshold`（默认 15）时晋升。年龄存在 Mark Word 的 4 位里，所以最大只能设到 15。
2. **大对象直接进入老年代**：大数组、长字符串等需要大块连续内存的对象，为避免在年轻代来回复制，可以直接在老年代分配。Serial / ParNew 通过 `-XX:PretenureSizeThreshold` 设置阈值；G1 中超过半个 Region 的对象会直接分配到 Humongous Region（逻辑上属于老年代）。
3. **动态年龄判定**：每次 Minor GC 后，按年龄从小到大累加 Survivor 中各年龄对象的大小，累加到年龄 N 时一旦超过 Survivor 容量 × `TargetSurvivorRatio`（默认 50%），就把晋升阈值设为 N（不超过 MaxTenuringThreshold），年龄大于等于 N 的对象晋升到老年代。
4. **空间分配担保**：Minor GC 后存活对象太多，To Survivor 放不下，多出来的对象直接进入老年代。如果老年代也放不下，就会发生 promotion failed，转为 Full GC。

### 什么是 Minor GC、Major GC、Full GC？分别什么时候发生？ | 高频 | 交通银行、字节、农业银行
按回收范围，HotSpot 的 GC 分为部分收集（Partial GC）和整堆收集（Full GC）。

| 类型 | 回收范围 | 触发时机 | 停顿 |
| --- | --- | --- | --- |
| Minor GC / Young GC | 只回收年轻代（Eden + Survivor） | Eden 空间不足，无法分配新对象 | 短，频繁 |
| Major GC / Old GC | 只回收老年代，目前只有 CMS 有单独的老年代并发收集 | 老年代占用超过阈值，如 CMS 的 `CMSInitiatingOccupancyFraction` | 视收集器而定 |
| Mixed GC | 整个年轻代 + 部分老年代 Region，G1 特有 | 堆占用达到 `InitiatingHeapOccupancyPercent`（默认 45%，JDK 9 起还会自适应调整）并完成并发标记后 | 受 MaxGCPauseMillis 控制 |
| Full GC | 整个堆 + 方法区（元空间） | 见下 | 长，应尽量避免 |

**Full GC 常见触发条件**：
- 老年代空间不足：大对象或晋升对象放不下（promotion failed）。
- 空间分配担保失败：Minor GC 前预判老年代连续空间不足以容纳平均晋升大小。
- 元空间达到 `MetaspaceSize` 高水位线（触发 GC 卸载类，到 `MaxMetaspaceSize` 仍不够则 OOM）。
- `System.gc()`（只是建议，可用 `-XX:+DisableExplicitGC` 屏蔽）、`jmap -dump:live` / `-histo:live`。
- CMS 并发失败（Concurrent Mode Failure）、G1 Mixed GC 跟不上分配速度时退化为 Full GC。

**易错点**："Major GC" 含义不统一，有人指老年代 GC，有人等同 Full GC，回答时说明指哪个范围。

### Old GC 和 Full GC 有什么区别？ | 高频
Old GC 只回收老年代，Full GC 回收整个堆和方法区，Full GC 范围更大、停顿通常也更长。

| 对比 | Old GC | Full GC |
| --- | --- | --- |
| 回收范围 | 只有老年代 | 年轻代 + 老年代 + 元空间 |
| 典型实现 | CMS 的老年代并发回收，大部分阶段与用户线程并发 | Serial Old / Parallel Old 的整堆标记-整理，G1 的 Full GC，全程 STW |
| 触发 | 老年代占用超过阈值 | 老年代或元空间不足、分配担保失败、`System.gc()`、CMS 并发失败等 |
| 影响 | 停顿较短，但占用 CPU | 停顿长，可能达到秒级 |

**补充**：
- 只有 CMS 有真正独立的 Old GC；Parallel 收集器老年代回收时其实会连带年轻代，等同 Full GC；G1 没有单独的 Old GC，而是用 Mixed GC 回收部分老年代。
- CMS 的 Old GC 如果失败（Concurrent Mode Failure 或 promotion failed），会退化为 Serial Old 单线程整理的 Full GC，停顿明显增加。
- 很多监控系统把 CMS 的 Old GC 也统计成 "Full GC"，排查时要结合 GC 日志区分，不能只看监控指标名。

### Java 的 GC 垃圾回收过程是怎样的？ | 高频
可以按"判断垃圾 → 回收算法 → 分代流程 → 收集器"这条主线回答。

1. **判断垃圾**：HotSpot 用可达性分析，从 GC Roots 出发遍历引用链，不可达的对象就是垃圾；软、弱、虚引用按各自规则处理，重写了 `finalize()` 的对象还有一次自救机会。
2. **回收算法**：标记-清除（有碎片）、标记-复制（无碎片但要预留空间）、标记-整理（无碎片但要移动对象）。
3. **分代流程**：
   - 新对象在 Eden 分配，Eden 满时触发 Minor GC，存活对象复制到 Survivor，年龄加 1。
   - 年龄达到阈值、动态年龄判定命中、或 Survivor 放不下的对象晋升到老年代；大对象直接进老年代。
   - 老年代达到阈值时进行 Old GC / Mixed GC，空间严重不足时触发 Full GC。
4. **收集器**：算法由具体收集器实现。JDK 8 默认 Parallel（Parallel Scavenge + Parallel Old），追求吞吐量；CMS 追求低停顿，JDK 14 已移除；JDK 9 起默认 G1，基于 Region、停顿可预测；ZGC（JDK 15 转正）停顿通常在 1ms 以内。
5. **并发标记**：CMS、G1、ZGC 用三色标记让标记与用户线程并发执行，用增量更新或 SATB 解决漏标问题。

实际项目中再根据业务特点选择收集器，调整堆大小、新生代比例、晋升阈值等参数，在吞吐量、停顿和内存占用之间取得平衡。

### 什么是 STW？ | 高频
STW（Stop The World）指 JVM 在执行某些操作时暂停所有用户线程，等操作完成后再恢复，期间应用无法响应请求。

**为什么需要 STW**：GC 需要在一致的快照下分析对象引用关系。如果用户线程同时修改引用，就可能把存活对象误判为垃圾。另外移动对象后还要修正所有指向它的引用，这些都需要用户线程暂停配合。

**怎么暂停**：JVM 不能在任意位置停下线程，只能等线程运行到安全点（Safepoint，如方法调用、循环回边、异常跳转处）再挂起；处于 Sleep、Blocked 的线程所在的代码区域属于安全区域（Safe Region）。

**哪些操作会 STW**：
- Serial、ParNew、Parallel 的整个回收过程，以及所有 Minor GC、Full GC。
- CMS 的初始标记、重新标记；G1 的初始标记（随 Young GC 一起）、最终标记、筛选回收（复制存活对象）。
- ZGC、Shenandoah 只在根扫描等少量阶段 STW，停顿很短且不随堆变大而增加。
- 非 GC 操作也会：偏向锁撤销（JDK 15 起偏向锁默认关闭）、类重定义、`jmap -dump`、`jstack` 等需要进入安全点的操作。

**影响**：STW 直接增加请求延迟。例如接口本身耗时 10ms，期间遇到一次 50ms 的 GC 停顿，这次请求就变成约 60ms；Full GC 停顿到秒级时会造成大量超时。

**怎么减少**：选择低延迟收集器（G1、ZGC），合理设置堆大小和年轻代比例减少 GC 次数，减少对象分配和过早晋升，避免频繁 Full GC。

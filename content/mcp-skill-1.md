## Function Calling 原理
### 什么是 Function Calling？它本质上怎么让大模型调用外部工具？模型真的调用了函数吗？
Function Calling 是让模型按开发者事先声明的函数 Schema 输出一段结构化调用请求，再由应用程序真正执行函数的机制。模型本身没有执行任何函数，它只负责“决定调不调、调哪个、传什么参数”。

**完整流程**
1. 开发者在请求里声明可用函数：名称、描述、参数 JSON Schema。
2. 模型理解用户意图后，不直接回答，而是返回一个结构化调用请求：

```json
{
  "name": "get_weather",
  "arguments": { "city": "北京", "date": "明天" }
}
```

3. 应用程序拿到函数名和参数，做参数校验、权限检查，再调用本地代码或外部 API。
4. 执行结果作为一条新消息（tool / function 结果）回传给模型。
5. 模型决定继续调用下一个工具，还是基于结果生成最终回答。

**要点**
- 模型负责“决策 + 生成参数”，宿主程序负责“执行 + 兜底”，真正的副作用都发生在模型外部。
- 正因为模型只是“提议”，服务端必须校验参数和权限，不能无条件信任模型输出。
- 一轮对话里可以有多次调用，形成“调用 → 观察结果 → 再调用”的循环，这也是 Agent 的基础。

### 大模型为什么会“主动”调用工具？LLM 是怎么学会 Tool Use 的？
模型并没有主观意识，所谓“主动”调用，是它在训练中学会了一种模式：当问题需要实时数据、精确计算或系统操作时，就输出工具调用格式而不是直接作答。

**学会 Tool Use 依赖三种能力**
- **理解意图**：判断用户是要查询、计算、下单、发邮件还是修改数据，以及靠自身知识能否回答。
- **理解工具说明**：根据工具的名称、描述、参数 Schema 判断哪个工具适合当前任务。
- **生成结构化参数**：把自然语言转换成工具能接收的 JSON 参数。

**举例**：用户说“帮我订明天下午 3 点和张三的会议”，模型要识别出动作是创建日程、时间是明天 15:00、参与人是张三，选择 `create_calendar_event` 工具并填好参数；若缺少必要信息（如会议时长），应先追问而不是乱填。

**能力来源**：训练阶段用大量“问题 → 工具调用 → 工具结果 → 最终回答”的轨迹数据做监督微调，再用偏好优化 / 强化学习强化“该调时调、不该调时不调、参数正确”的行为；推理阶段则依赖运行时传入的工具描述做选择。

### Function Calling 能力是怎么训练出来的？它属于 Prompt 还是模型能力？
结论：它是“模型能力 + 运行时工具 Schema + Prompt 引导”三者结合，核心是模型能力，不是单纯的 Prompt 技巧。

**训练侧**
- 用包含工具定义和调用轨迹的数据做指令微调 / SFT，让模型学会特定的调用格式（如特殊 token 或固定 JSON 结构）。
- 再通过偏好优化或强化学习，提升选择工具的准确率和参数的合法性。

**推理侧**
- 开发者把工具列表、描述、参数格式放进请求，模型根据上下文决定是否调用。
- 部分平台还提供结构化输出 / 约束解码（strict 模式），保证参数严格符合 JSON Schema。

**为什么不是纯 Prompt**
- 没经过工具调用训练的模型，仅靠 Prompt 很难稳定输出正确结构，也不擅长判断“什么时候该调”。
- 但它也不是固化在参数里的：具体有哪些工具、参数长什么样，完全取决于运行时传入的定义，所以换一批工具不需要重新训练。

### Tool 在 Agent 体系里扮演什么角色？Function Calling 算真正的 Agent 吗？
Tool 是 Agent 接触外部世界的“手脚”；Function Calling 只是构建 Agent 的关键能力之一，单独使用还不算完整的 Agent。

**Tool 的角色**
- 大模型本身只能生成文本，Tool 扩展了它的行动能力：搜索工具获取实时信息，数据库工具查业务数据，代码执行工具做计算验证，业务 API 工具操作企业系统。
- 在 Agent 的“感知 - 决策 - 行动”循环中，Tool 承担“行动”和“获取观察结果”两部分。

**Function Calling 不等于 Agent**
- Function Calling 解决的是“怎么以结构化方式调用一个工具”。
- 完整的 Agent 还需要：目标理解、任务规划、多步执行、观察结果后调整、错误恢复、记忆管理，以及停止条件。
- 一次“问天气 → 调接口 → 回答”只是工具增强的问答；只有当模型在循环中自主规划并多步调用、根据结果调整策略时，才构成 Agent 行为。

### Tool Use 和 Function Calling 有什么区别？
Tool Use 是上层能力概念，Function Calling 是实现它的一种接口机制，两者不是同义词。

| 维度 | Tool Use | Function Calling |
| --- | --- | --- |
| 含义 | 模型决定何时用工具、用哪个、怎么组合、如何处理结果 | 模型按函数 Schema 输出结构化调用请求 |
| 层级 | Agent 的行为能力和决策过程 | 模型与程序之间的结构化通信方式 |
| 范围 | 搜索、查库、代码执行、浏览器操作、MCP 工具等都算 | 一种具体协议，各厂商格式不完全相同 |

- Function Calling 可以支撑 Tool Use，但一次函数调用本身未必构成完整的 Agent 行为。
- Tool Use 也不一定只靠 Function Calling 实现，例如让模型输出 ReAct 文本格式再解析、或直接生成 CLI 命令执行。

## Tool Calling 工程实践
### Tool Calling 一般怎么做？和普通函数调用有什么区别？ | 高频
核心区别：普通函数调用由开发者写死“谁调哪个函数、传什么参数”；Tool Calling 是模型根据上下文提出调用意图，宿主系统决定能不能执行，所以中间必须加一层校验和调度。

**工程上一般分四层**
- **工具注册层**：定义每个工具的名称、描述、参数 Schema，注册到可调用列表。模型只看得到声明，看不到实现。
- **校验层**：模型输出候选调用后，服务端先做白名单校验、参数 Schema 校验、权限校验；不通过直接拦截，并把错误信息回传给模型让它修正。
- **执行器层**：校验通过才执行，包含超时控制、幂等控制、异常包装，结果统一格式化后回传模型。
- **审计日志层**：记录工具名、入参、出参、耗时、成功 / 失败状态，串成完整调用链，方便排查和回放。

**与普通函数调用的对比**

| 维度 | 普通函数调用 | Tool Calling |
| --- | --- | --- |
| 调用决策 | 代码确定 | 模型在运行时决定 |
| 参数来源 | 程序构造，类型安全 | 模型生成，可能缺失或错误 |
| 可信度 | 可信 | 不可信，必须校验 |
| 失败处理 | 抛异常 | 错误要回传给模型，让其重试或换方案 |

### 你项目里的工具调用是怎么做的？怎么让模型更稳定地选对工具？ | 高频
回答时先讲架构（工具注册 → 模型决策 → 服务端校验 → 执行 → 结果回传），再讲稳定性手段，核心是“描述清晰、减少重叠、缩小候选、规则兜底、线上监控”。

- **工具描述写清楚**：写明适用场景、输入参数含义、返回结果、不适用场景。模糊描述是选错工具的首要原因。
- **减少语义重叠**：功能相近的工具要么合并成一个、内部按参数路由，要么在描述里明确彼此边界。
- **控制候选规模**：工具很多时先做一层 Tool Routing（规则 / embedding 召回），把候选缩小到 Top K 再交给模型。候选越少越不容易选错。
- **强约束参数**：用严格的 JSON Schema（必填、枚举、格式），开启结构化输出 / strict 模式，减少参数错误。
- **Few-shot 示例**：对易混淆场景给出正反示例。
- **规则兜底**：高风险操作走白名单和权限校验，即使模型选对工具，参数或权限不对也不能执行。
- **线上监控**：不能只看调没调，要统计命中率、误调用率、漏调用率、参数错误率、超时率，用错误案例反哺描述优化。

### 怎么并行做 Tool Calling，既提升吞吐又保证一致性和可回放？ | 高频
核心是解决四个问题：依赖关系、状态一致性、结果合并、失败处理。只有互不依赖的调用才能并行。

- **依赖分析**：后一个工具依赖前一个的输出就必须串行；无依赖的（如同时查天气和查股价）放进同一并行批次。主流模型 API 本身支持一次返回多个 tool call（parallel tool calls），由宿主并发执行。
- **状态一致性**：不让多个工具直接改共享状态，而是先把结果写到临时观察区，再由调度器统一合并，避免并发写导致状态污染。
- **结果合并**：同一批次全部完成（或超时）后，按调用 id 把结果统一回填上下文，让模型一次看到完整信息再决策。
- **失败隔离**：按工具粒度设置超时和重试，一个工具失败不丢弃整批结果，失败项单独标记，模型在信息不全时做降级决策。
- **副作用幂等**：发消息、建订单、提工单等写操作必须带幂等键，否则重试会造成重复执行。
- **可回放**：每次调用记录 trace_id、step_id、入参、出参、耗时，组成执行 DAG；出问题时可以回溯到任意节点重放。对外部结果做快照，回放时用快照而不是重新请求，保证结果可复现。

### Tool Calling 中最容易出现哪些问题？如何避免误调用和循环调用？
Tool Calling 的核心风险不是模型不会调，而是在错误的时机、用错误的参数、调用错误的工具，或者停不下来。

| 问题 | 表现 | 应对 |
| --- | --- | --- |
| 误调用 | 不需要工具时强行调用，或选错工具 | 写清适用 / 禁用场景；路由缩小候选；设置置信度阈值；高风险工具人工确认 |
| 参数错误 | 缺字段、类型错、格式错 | 严格 JSON Schema、枚举和默认值；校验失败把错误回传让模型修正 |
| 权限越界 | 调用用户无权访问的工具或数据 | 按用户角色动态暴露工具；执行前服务端再校验；数据层做权限过滤 |
| 结果不可信 | 接口返回错误、空值、过期数据 | 返回结构化状态码；异常处理；关键结果二次校验 |
| 循环调用 | 反复调用同一工具无法停止 | 限制最大调用次数 / 步数；检测相同工具 + 相同参数的重复调用；工具结果明确返回终止状态；用状态机约束流程 |
| 副作用风险 | 发邮件、下单、删数据造成真实影响 | 二次确认、幂等设计、操作审计、沙箱执行、可回滚 |

总结：权限、校验、限次、审计、人工确认缺一不可，安全边界由后端保证而不是依赖模型自觉。

### Agent 工具调用失败或超时怎么办？ | 高频
分两层处理：工具层做重试和降级，Agent 层做错误感知、全局超时和监控告警。

**工具层**
- **有限重试 + 指数退避**：只对网络抖动、限流等临时性错误重试，间隔按 1s、2s、4s 递增并加随机抖动，设置最大次数；参数错误、权限错误不重试。写操作重试前必须保证幂等。
- **熔断**：某工具持续失败时熔断一段时间，避免拖垮整个 Agent。
- **降级**：重试失败后走备选工具、缓存结果或简化方案；无降级方案就明确告知该能力暂不可用。

**Agent 层**
- **错误感知**：把失败原因作为工具结果回传模型，让它换工具、调整参数或如实告知用户，而不是编造结果。
- **全局超时**：单个工具有超时，整个任务也有总超时和最大步数，避免因一个工具卡死而整体瘫痪；超时后返回部分结果或提示稍后重试。
- **监控告警**：统计每个工具的失败率、超时率、P99 耗时，超阈值告警，长期数据用于定位不稳定工具。

### 通过 CLI 命令调用工具和调用 MCP 服务有什么区别？
本质区别：CLI 是 Agent 直接生成并执行本地命令；MCP 是把工具按标准协议封装成带 Schema 的能力，由 Agent 通过 Client 调用。

| 维度 | CLI | MCP |
| --- | --- | --- |
| 调用方式 | 生成命令执行，如 `git status`、`npm test` | Client 发送 `tools/call` 请求，Server 执行 |
| 工具描述 | 依赖模型对命令和参数的已有知识 | 显式声明名称、描述、`inputSchema` |
| 返回结果 | stdout / stderr 纯文本，需模型自行解析 | 结构化内容（text、image、resource 等） |
| 安全控制 | 能力强、风险高，依赖沙箱和命令白名单 | Server 侧可做权限、参数校验、密钥隔离 |
| Token 开销 | 不需要预先注入工具定义 | 工具定义要放进上下文，工具多时开销大 |

**适用场景**
- **CLI**：本地开发环境里本身就是命令行形态的工具，如 Git、构建、测试、日志分析、脚本执行。链路短、模型对常见命令很熟悉。
- **MCP**：需要标准化接入数据库、企业内部 API、知识库、SaaS 服务，或者需要明确的参数约束、鉴权和安全边界的生产场景，以及跨多个 AI 应用复用同一批工具。

两者经常并存：编码类 Agent 用 CLI 操作本地仓库，同时用 MCP 接入 Issue 系统、数据库等外部服务。

## MCP 基础与架构
### 什么是 MCP？它主要解决什么问题？ | 高频
MCP（Model Context Protocol，模型上下文协议）是 Anthropic 于 2024 年 11 月开源的开放协议，用来标准化 AI 应用与外部工具、数据源之间的连接方式，常被比作 AI 应用的“USB-C 接口”。

**解决的问题**
- 没有 MCP 时，每个 AI 应用接 GitHub、数据库、文件系统、浏览器、企业系统都要单独写适配代码，不同应用、不同 Agent 框架之间无法复用，形成 M×N 的集成成本。
- MCP 让外部能力以统一协议暴露（MCP Server），任何支持 MCP 的应用（MCP Host）都能发现并使用，降低接入成本，让模型从“只有静态知识”变成“能检索信息、执行动作”。

**核心组成**
- 三个角色：Host（AI 应用）、Client（Host 内与 Server 一对一连接的协议客户端）、Server（能力提供方）。
- 三类服务端能力：Tools（可执行动作）、Resources（可读取的上下文数据）、Prompts（可复用提示模板）。
- 协议基础：消息格式用 JSON-RPC 2.0，传输层支持 stdio 和 Streamable HTTP。

**和 Function Calling 的关系**：Function Calling 解决“模型如何发起工具调用”，MCP 解决“工具和资源如何标准化接入模型应用”，两者是配合关系。

### 怎么理解“MCP 是 AI 的 USB-C 接口”？
这个比喻强调的是“一个标准接口，连接任意设备”：USB-C 让键盘、显示器、硬盘用同一个口接电脑；MCP 让任意 AI Host 用同一套协议接入任意 MCP Server（GitHub、数据库、Slack、文件系统等）。

- **统一接口**：设备厂商只需实现 USB-C，电脑只需提供 USB-C 口；工具方只需实现一个 MCP Server，AI 应用只需实现 MCP Client。
- **统一交互模式**：USB-C 统一了数据、视频、供电；MCP 统一了工具调用、资源读取、提示模板获取三种交互，对应 Tools、Resources、Prompts 三种原语。
- **可扩展**：USB-C 通过替代模式承载多种协议；MCP 用这三种原语承载任意下游能力，并在初始化时做能力协商。
- **双向通信**：MCP 不只是 Client 请求 Server，Server 也能主动发通知（如工具列表变更）或反向请求 Client（如 sampling 请求 Host 调用模型）。

比喻的局限：MCP 只规定“怎么连、怎么说话”，不保证工具本身的质量和安全，也不负责模型如何选择工具。

### M×N 集成问题是什么？MCP 怎么解决？
M×N 问题：有 M 个 AI 应用和 N 个工具 / 数据源，传统方式下每个应用要给每个工具单独写集成代码，工作量是 M×N；而且每个工具的协议、认证、数据格式各不相同，维护成本很高。

**MCP 的解法**
- 每个工具或数据源只实现一次 MCP Server。
- 每个 AI 应用只实现一次 MCP Client 协议。
- 集成复杂度从 M×N 降为 M+N：新增一个工具，所有支持 MCP 的应用都能直接使用；新增一个应用，现有所有 MCP Server 都能直接接入。

这和 LSP（Language Server Protocol）解决“编辑器 × 编程语言”问题的思路一致，MCP 的设计也参考了 LSP。

### MCP 的优势是什么？ | 高频
MCP 的优势不在于单次调用比 Function Calling 更强，而在于标准化、解耦和可治理，适合工具多、链路复杂、需要长期维护的系统。

- **统一接入**：所有工具按同一协议暴露，应用侧不需要逐个适配，降低集成成本。
- **一次实现，多处复用**：同一个 MCP Server 可被 Claude Desktop、IDE、自研 Agent 等多个 Host 使用。
- **解耦**：工具实现与模型、应用解耦，换模型或换应用不用重写工具。
- **动态发现**：Client 运行时通过 `tools/list` 等获取能力，Server 增删工具后可发 `list_changed` 通知，无需改应用代码。
- **能力更丰富**：除了 Tools，还有 Resources、Prompts，以及 sampling、elicitation 等客户端能力，支持有状态会话和进度通知。
- **便于治理**：工具集中在 Server 侧，权限控制、参数校验、密钥管理、审计可以统一做。
- **生态**：主流 AI 应用和厂商普遍支持，已有大量现成的 MCP Server 可直接使用。

需要注意的代价：每个工具的定义都要放进上下文，接入工具过多会占用大量 Token 并降低选择准确率；第三方 Server 也带来供应链和 Prompt 注入风险。

### MCP 的 Host、Client、Server 分别有什么作用？三者如何协同？ | 高频
一句话：Host 负责理解用户需求和调度整体流程，Client 负责协议通信，Server 负责提供具体能力。

- **Host**：用户直接交互的 AI 应用，如 Claude Desktop、IDE、Agent 平台。负责接收输入、调用大模型、决定何时用哪个工具、管理多个 Client，并负责用户授权和安全策略。
- **Client**：运行在 Host 内部，与某个 Server 保持一对一连接。负责连接建立、`initialize` 能力协商、发送 `tools/list`、`tools/call` 等 JSON-RPC 请求、接收响应和通知。Host 连几个 Server 就有几个 Client。
- **Server**：独立的能力提供程序（本地进程或远程服务），暴露 Tools、Resources、Prompts，接收请求、执行业务逻辑并返回结果，例如文件系统、数据库、GitHub、搜索服务的 MCP Server。

**协同流程**：用户在 Host 提需求 → Client 连接 Server 并发现能力 → Host 把工具定义交给模型 → 模型决定调用 → Host 通过 Client 发 `tools/call` → Server 执行并返回 → Host 把结果交给模型生成回答。

**Server 侧典型配置参数**
- **连接参数**：stdio 模式下是 `command`、`args`、`env`；远程模式下是 `url` 和认证信息（如 OAuth / Token）。
- **能力声明**：初始化时声明支持 `tools`、`resources`、`prompts` 等。
- **工具参数 Schema**：每个工具的 `name`、`description`、`inputSchema`（JSON Schema），模型按它构造 `tools/call` 的参数。

```python
# 使用官方 Python SDK 的 FastMCP 快速写一个 Server
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("weather")

@mcp.tool()
def get_weather(city: str) -> str:
    """查询指定城市的天气"""
    return f"{city}：晴，25℃"

if __name__ == "__main__":
    mcp.run()  # 默认使用 stdio 传输
```

### MCP 支持哪些能力类型？ | 高频
MCP Server 向 Client 提供三类核心能力（原语），每类都有对应的“列出 / 获取”方法：

| 能力 | 含义 | 控制方 | 主要方法 |
| --- | --- | --- | --- |
| Tools | 可执行动作，如搜索、查库、写文件、调 API | 模型决定调用 | `tools/list`、`tools/call` |
| Resources | 可读取的上下文数据，如文件、数据库 Schema、日志、文档，用 URI 标识 | 应用决定读取 | `resources/list`、`resources/read`、`resources/subscribe` |
| Prompts | 可复用的提示模板或任务流程，可带参数 | 用户选择（如斜杠命令） | `prompts/list`、`prompts/get` |

**Client 侧也提供能力供 Server 反向使用**
- **Sampling**：Server 请求 Host 调用模型生成内容，Server 无需自己持有模型 Key。
- **Roots**：Client 告知 Server 可操作的文件系统范围。
- **Elicitation**：Server 在执行中向用户请求补充信息。

此外还有通知机制（如 `notifications/tools/list_changed`）、进度通知、日志、取消等工具性功能。

### MCP 基于什么协议？底层通信方式是什么，为什么这么设计？ | 高频
MCP 的消息格式基于 JSON-RPC 2.0，传输层与消息格式解耦，标准传输有两种：stdio 和 Streamable HTTP。

**消息格式**：请求（带 `id` 和 `method`）、响应（`result` 或 `error`）、通知（无 `id`，无需响应）。

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": { "name": "search", "arguments": { "query": "MCP" } }
}
```

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [{ "type": "text", "text": "MCP 是 Model Context Protocol……" }],
    "isError": false
  }
}
```

注意两类错误的区别：协议层错误（方法不存在、参数非法）用 JSON-RPC 的 `error` 返回；工具执行失败一般放在 `result` 里并设 `isError: true`，让模型能看到错误并自行调整。

**传输方式**
- **stdio**：Host 以子进程方式启动 Server，通过标准输入输出交换消息。适合本地工具（文件系统、Git、本地脚本），部署简单、无需网络端口。
- **Streamable HTTP**：Server 作为独立服务提供一个 HTTP 端点，Client 用 POST 发送消息，Server 可直接返回 JSON，也可升级为 SSE 流式推送多条消息，支持会话 ID 和断线恢复。2025-03-26 版规范用它取代了早期的 HTTP+SSE 双端点方案。适合远程和企业级部署，便于接入认证、网关、监控和横向扩展。

**为什么这么设计**
- JSON-RPC 简单、成熟、语言无关，天然支持请求 / 响应和双向通知。
- 协议与传输解耦，本地和远程场景可以各选合适的传输。
- 基于 HTTP 的远程传输能复用现有的 OAuth 鉴权、负载均衡和网关基础设施。

## MCP 调用流程与对比
### 一次完整的 MCP 工具调用流程是什么？ | 高频
关键点：不是模型直接调函数，而是模型提出调用意图，真正发请求的是 Host 里的 MCP Client，Server 只负责按协议暴露工具并返回结果。以“查北京天气”为例：

1. **建立连接**：Host 按配置启动本地 Server 子进程（stdio）或连接远程 Server（Streamable HTTP）。
2. **初始化**：Client 发 `initialize` 协商协议版本和能力，Server 响应后 Client 发 `notifications/initialized`。
3. **能力发现**：Client 发 `tools/list`，拿到工具名称、描述、`inputSchema`。
4. **模型决策**：用户问“帮我查北京的天气”，Host 把工具列表转成 Function Calling 格式连同问题发给模型，模型返回调用 `get_weather`，参数 `{"city": "北京"}`。
5. **用户确认（可选）**：敏感工具先展示工具名和参数，经用户批准再执行。
6. **调用与执行**：Client 发 `tools/call` 请求，Server 执行业务逻辑（如调真实天气 API），返回 `text`、`image`、资源链接等结构化内容。
7. **生成回答**：Host 把结果交给模型，模型生成“北京今天晴，25℃”，或继续下一次调用。

前置条件：工具方提供 MCP Server（通常封装自家 API），用户在 Host 中配置好 Server 的启动方式或地址以及所需密钥。

### MCP 的工具发现/调用是主动拉取还是被动推送？ | 高频
以 Client 主动拉取为主，Server 推送通知为辅。

- **发现**：会话初始化后，Client 主动发送 `tools/list`、`resources/list`、`prompts/list` 拉取能力列表（支持分页）。
- **调用**：由 Host 根据模型决策，通过 Client 主动发起 `tools/call`。Server 不会主动执行工具并把结果推给模型。
- **变更通知**：如果 Server 在初始化时声明了 `listChanged` 能力，工具列表变化时会发送 `notifications/tools/list_changed`，Client 收到后再重新拉取一次。Resources 还支持 `resources/subscribe` 订阅，资源更新时 Server 推送 `notifications/resources/updated`。

所以准确的说法是：调用是请求 - 响应式的主动拉取；变更感知可以由 Server 通知触发，但拿数据仍是 Client 去拉。

### MCP 和 Function Calling 有什么核心区别？ | 高频
两者解决的问题层级不同：Function Calling 是模型能力，解决“模型怎么决定调哪个函数、怎么生成参数”；MCP 是系统层的开放协议，解决“工具怎么被标准化接入、发现和调用”。两者是配合关系，不是替代关系。

| 维度 | Function Calling | MCP |
| --- | --- | --- |
| 本质 | 模型 API 提供的能力，推理层 | 应用层开放协议，与具体模型解耦 |
| 定义方 | 各模型厂商，格式不完全通用 | Anthropic 发起的开放标准，社区共建 |
| 工具位置 | 定义和实现写在当前应用里 | 由独立的 MCP Server 暴露，可跨应用复用 |
| 通信 | 应用调模型 API 时带上工具定义 | Client 与 Server 之间走 JSON-RPC 2.0，经 stdio 或 Streamable HTTP |
| 发现方式 | 开发者硬编码工具列表 | 运行时 `tools/list` 动态发现 |
| 状态 | 每次请求都要带上工具定义 | Client 与 Server 有会话，支持能力协商和通知 |
| 能力范围 | 只有函数调用 | Tools、Resources、Prompts，及 sampling 等双向能力 |

**两者如何配合**：Host 把 Server 的工具列表转换成模型的 Function Calling 定义；模型通过 Function Calling 输出调用意图，Host 再经 MCP Client 转发给 Server。MCP 负责“工具从哪来、怎么执行”，Function Calling 负责“模型怎么表达要调用”。

### 什么场景选 Function Calling，什么场景更适合 MCP？
判断标准是工具的数量、复用范围和治理要求。

**选 Function Calling**
- 工具少、业务边界清晰、只服务一个应用。
- 例如查天气、算价格、查订单、创建日程、调用一个内部接口。
- 开发成本低、链路短、延迟小，无需额外部署 Server 进程。

**选 MCP**
- 工具多，或者多个 AI 应用 / Agent 要复用同一批工具。
- 需要接入文件系统、数据库、Git、浏览器、Jira、知识库等现成生态。
- 例如公司内多个 Agent 都要访问知识库、GitLab、Jira；IDE Agent 要读代码、查 Git 状态；企业 AI 平台要统一接入多个业务系统。
- 需要工具独立部署、独立升级，以及统一的鉴权、审计。

两者并不冲突：简单场景直接 Function Calling，规模化后把工具下沉到 MCP Server，模型侧仍通过 Function Calling 表达调用。

### MCP 和 HTTP API 调用有什么区别？ | 高频
HTTP API 是通用的服务间接口调用方式；MCP 是面向大模型应用的工具接入协议。两者是不同层级的东西，MCP 不替代 HTTP API。

| 维度 | HTTP API | MCP |
| --- | --- | --- |
| 定位 | 通用传输与接口，服务对服务 | AI 应用专用的上下文与工具协议 |
| 能力描述 | 靠接口文档，调用方硬编码 | 运行时自动发现，带自然语言描述和 JSON Schema，模型可直接理解 |
| 交互模型 | 各接口格式自定，主要是请求 / 响应 | 统一的 JSON-RPC 消息，内置能力协商、通知、进度、取消 |
| 能力类型 | 只有接口 | Tools、Resources、Prompts |
| 会话 | 一般无状态 | 有会话生命周期（初始化、能力协商） |

**关系**：很多 MCP Server 底层仍调用已有的 HTTP API，只是把它包装成模型可理解、可调用的 tools 或 resources。而 MCP 的远程传输 Streamable HTTP 本身就跑在 HTTP 之上。可以理解为 MCP 是在 HTTP API 之上面向 Agent 的标准化封装层。

### MCP 和 RAG 有什么区别？ | 高频
两者不是同一类东西：RAG 是一种问答增强方案，补充外部知识；MCP 是一种工具接入协议，标准化连接外部能力。

| 维度 | RAG | MCP |
| --- | --- | --- |
| 定位 | 解决知识不足：检索相关文档片段放进上下文 | 解决能力接入：统一暴露工具、资源、提示模板 |
| 处理对象 | 文本知识：文档、FAQ、知识库 | 工具能力和数据：查库、读文件、搜网页、调业务接口 |
| 输出 | 增强后的上下文，模型据此生成回答 | 工具调用结果，模型据此继续推理或回答 |
| 是否有副作用 | 只读 | 可读可写（如发消息、建工单） |

**相似点与结合**：两者都会根据用户 Query 做匹配，RAG 召回相关文本，MCP 场景下模型根据工具描述选工具。它们可以组合：把向量检索封装成一个 MCP Server 的 `search` 工具，或把知识库文档作为 MCP Resources 暴露，这就是 Agentic RAG 的常见做法。

### 为什么有些推理模型不支持 MCP？MCP 对模型能力有哪些要求？
严格说 MCP 是协议，不是模型能力。模型本身并不“支持 MCP”，而是 Host / Agent 框架实现了 MCP Client，并把 MCP 工具转换成模型能理解的工具调用格式。所谓“模型不支持 MCP”，通常是以下原因：

- **模型不支持或不擅长 Tool Calling / 结构化输出**：无法稳定选择工具、生成合法参数。
- **模型 API 不开放工具调用接口**：只支持纯文本输入输出，不支持 tools 参数或 JSON Schema 约束。
- **推理过程不支持中途调用工具**：部分推理模型擅长长链思考，但不支持边推理边调工具，或在早期版本中未开放该能力。
- **宿主应用没有实现 MCP Client**：模型能调工具，但所在平台无法连接 MCP Server。

**MCP 对模型能力的要求**
- 理解工具描述，判断是否需要工具。
- 在多个工具中选对工具，生成符合 Schema 的参数。
- 理解工具返回结果，进行多轮调用和错误恢复。
- 在工具很多时保持选择准确率（长上下文能力）。
- 具备一定的安全边界意识，不被工具返回内容中的注入指令带偏。

### 基于 MCP 做过多工具编排吗？怎么做？
可以这样设计：Agent 同时接入多个 MCP Server，Host 统一聚合工具，由模型或编排引擎决定调用顺序。

1. **多 Server 接入与聚合**：每个 Server 对应一个 Client，Host 汇总所有 `tools/list` 结果形成统一工具目录；不同 Server 可能有同名工具，需要加命名空间前缀（如 `github__create_issue`）避免冲突。
2. **意图识别与工具路由**：工具很多时，先按意图或 embedding 召回 Top K 工具再交给模型，减少 Token 和误选。
3. **编排模式**：
   - 串行：上一个工具的结果作为下一个工具的入参。
   - 并行：无依赖的工具并发调用后统一合并。
   - 条件分支：根据中间结果决定走哪条路径。
4. **上下文维护**：保存每一步工具结果和状态，供后续步骤和下一轮对话使用。
5. **复杂流程固化**：稳定的长流程可以用 DAG / 工作流引擎编排，节点内部仍通过 MCP 标准调用工具；灵活场景用 ReAct 让模型动态决策。
6. **治理**：统一超时、重试、权限和审计，避免一个 Server 故障拖垮整体流程。

### MCP 有哪些安全机制？沙箱隔离、密钥管理怎么做？ | 高频
MCP 安全的核心是把工具调用限制在可控边界内，依赖权限控制、用户确认、参数校验、沙箱隔离、密钥管理和审计，而不是依赖模型自己判断安全。

- **鉴权**：远程 Server 按规范使用 OAuth 2.1 授权，Client 携带访问令牌；Server 校验令牌的受众是否为自己，禁止把令牌透传给下游服务。本地 stdio Server 一般从环境变量获取凭证。
- **权限控制**：Server 只暴露必要工具，遵循最小权限原则。文件工具只能访问指定目录（可结合 Roots），数据库工具只读或仅能访问授权表。按用户 / 角色过滤可见工具。
- **用户确认**：对写文件、执行命令、发送消息等高风险调用，Host 展示工具名、参数和影响范围，由用户确认后才执行。
- **参数校验**：Server 不信任模型传入的参数，校验路径穿越、SQL 是否只读、命令是否危险，防止注入。
- **沙箱隔离**：高风险 Server 运行在容器、虚拟机或受限进程中，限制文件系统、网络、环境变量和系统命令权限。
- **密钥管理**：API Key、Token、数据库密码不写进 Prompt、不暴露给模型，存放在环境变量、配置中心或密钥管理服务中，由 Server 侧使用；定期轮换。
- **超时与限流**：每个工具设置超时和调用频率上限。
- **审计日志**：记录工具名、参数、调用时间、结果和用户身份，便于追溯。
- **Prompt 注入与供应链防护**：工具返回的内容只当数据不当指令；警惕工具描述中被植入恶意指令（tool poisoning）；只使用可信来源的 Server，固定版本并审查更新。

## 通信协议与 AI 网关
### WebSocket 和 SSE 有什么区别？在 AI 场景下各适合什么？
两者都能实现服务端实时推送，区别在于方向和协议：SSE 是基于 HTTP 的服务端单向推送，WebSocket 是独立的全双工协议。

| 维度 | SSE（Server-Sent Events） | WebSocket |
| --- | --- | --- |
| 方向 | 服务端 → 客户端单向 | 双向全双工 |
| 协议 | 普通 HTTP 响应，`Content-Type: text/event-stream` | HTTP Upgrade 握手后切换为 ws / wss 协议 |
| 数据格式 | UTF-8 文本事件 | 文本或二进制帧 |
| 重连 | 浏览器 `EventSource` 内置自动重连和 `Last-Event-ID` | 需要自己实现心跳和重连 |
| 基础设施兼容 | 天然兼容 HTTP 网关、鉴权、负载均衡 | 需要代理支持长连接和 Upgrade |

**AI 场景选择**
- **SSE**：大模型逐 token 流式输出，是主流模型 API（OpenAI、Anthropic 等）流式响应的标准做法；MCP 的 Streamable HTTP 也用 SSE 做流式返回。简单、稳定、易于接入现有 HTTP 生态。
- **WebSocket**：实时语音、多人协作、需要客户端频繁发送中间状态或随时打断的复杂双向交互，例如 OpenAI Realtime API 就提供 WebSocket 接口。

### 为什么实时 AI 语音场景通常用 WebRTC？相比 WebSocket 有什么优势？
WebRTC 是专为实时音视频设计的技术栈，而 WebSocket 只是通用的双向数据通道，没有针对音视频优化。

**WebRTC 的优势**
- **低延迟传输**：媒体走基于 UDP 的 RTP / SRTP，不受 TCP 队头阻塞和重传的影响；WebSocket 基于 TCP，弱网下一个包丢失会阻塞后续数据，延迟抖动明显。
- **内置音频处理**：Opus 编解码、抖动缓冲、回声消除（AEC）、噪声抑制、自动增益，这些对语音对话体验很关键，用 WebSocket 需要自己实现。
- **网络自适应**：带宽估计、拥塞控制、码率自适应，丢包时用 FEC / PLC 等手段恢复。
- **NAT 穿透**：通过 ICE、STUN、TURN 建立连接，支持点对点和媒体服务器（SFU）架构。
- **浏览器原生支持**：可直接采集麦克风并推流，前端接入方便，传输天然加密。

**取舍**：WebRTC 部署更复杂（信令服务、TURN 服务器）。服务端到服务端、或对延迟要求没那么高的语音场景，用 WebSocket 传音频分片更简单；面向终端用户的实时语音 Agent，客户端到服务端通常用 WebRTC。

### 什么是 A2A（Agent to Agent）协议？它和 MCP 有什么核心区别？
A2A 是 Google 在 2025 年 4 月发布的开放协议（后移交 Linux 基金会），用于让不同厂商、不同框架构建的 Agent 之间互相发现、通信和委托任务。

**A2A 核心概念**
- **Agent Card**：Agent 的 JSON 描述文件（通常位于 `/.well-known/agent-card.json`），声明名称、能力（skills）、端点和认证方式，用于发现。
- **Task**：协作的基本单位，有生命周期状态（submitted、working、input-required、completed、failed 等），支持长时间运行的任务。
- **Message / Artifact**：Agent 之间交换的消息和最终产出物，可包含文本、文件、结构化数据等多种 Part。
- **传输**：基于 HTTP，使用 JSON-RPC 2.0，支持 SSE 流式更新和推送通知。

**与 MCP 的区别**

| 维度 | MCP | A2A |
| --- | --- | --- |
| 连接对象 | Agent ↔ 工具 / 数据源 | Agent ↔ Agent |
| 对方的性质 | 被动的能力提供者，按调用执行 | 自主的智能体，内部逻辑不透明，可多轮协商 |
| 交互粒度 | 单次工具调用 | 任务委托，可长时间运行、中途要求补充输入 |
| 典型场景 | 让 Agent 查库、读文件、调 API | 跨团队 / 跨厂商 Agent 协作，如采购 Agent 委托报价 Agent |

两者互补：一个 Agent 对外用 A2A 与其他 Agent 协作，对内用 MCP 接入自己的工具。

### 用过哪些 AI 网关框架？为什么 AI 系统需要单独做网关层？
常见的大模型网关方案包括：LiteLLM（开源，统一 OpenAI 兼容接口、支持 100+ 模型、带成本统计）、One API / New API（国内常用的多渠道分发和额度管理）、OpenRouter（托管式多模型路由服务）、Portkey、Kong AI Gateway、Higress（基于 Envoy 的 AI 网关），以及基于 Spring Cloud Gateway、Nginx、Envoy 自研扩展的 LLM Gateway。

**为什么要单独做网关层**：普通 API 网关关注路由、鉴权、限流、负载均衡；大模型调用还有一系列特有需求：
- 多厂商接口格式不同，需要统一协议适配。
- 计费按 Token 而不是请求次数，限流也需要按 Token（TPM）维度。
- 响应是长时间的流式 SSE，对超时和连接管理要求不同。
- 需要 Prompt / 响应审计、敏感信息脱敏、内容安全审核。
- 需要按成本、延迟、能力做模型路由，以及供应商故障时自动切换。
- 需要控制上下文长度、做语义缓存来降成本。

### AI 网关一般解决哪些问题？为什么不能让业务系统直接调大模型？
**AI 网关解决的问题**
- **统一接入**：屏蔽 OpenAI、Claude、Gemini、通义、本地模型等的接口差异，对外统一请求和响应格式。
- **统一鉴权与密钥托管**：业务系统只访问内部网关，厂商 API Key 集中保管、不外泄。
- **限流配额**：按用户、部门、应用、模型维度限制 RPM / TPM。
- **计费与成本**：统计 Token 消耗、调用次数、费用，支持预算告警。
- **模型路由**：按任务类型、成本、延迟、可用性选择模型。
- **熔断降级**：某个模型或供应商不可用时自动切换备用模型。
- **审计**：记录请求、响应和上下文，用于排查和合规。
- **安全治理**：敏感信息脱敏、Prompt 注入检测、输出内容审核。
- **缓存**：对高频请求做精确缓存或语义缓存，降低成本和延迟。

**业务系统直接调模型的问题**
- 接入方式不统一，每个系统重复开发适配。
- API Key 分散在各系统，泄露风险高。
- 成本无法统一统计和管控。
- 限流、熔断、重试各自实现，难以统一治理。
- 切换模型要改每个业务系统，成本高。
- Prompt 和响应日志分散，难以审计。

### 公司内部接了多个大模型，如何设计统一的大模型网关层？
可以按分层架构设计，对上提供统一 API（通常兼容 OpenAI 格式，降低业务改造成本），对下适配各家模型。

- **接入层**：统一的 Chat、Embedding、Rerank 等接口，支持同步和 SSE 流式。
- **鉴权层**：API Key、JWT、OAuth2，按应用、用户、部门做权限和模型白名单。
- **路由层**：按请求类型和策略选模型：
  - 简单问答走低成本模型，复杂推理走高能力模型；
  - Embedding 走向量模型，代码任务走代码模型；
  - 敏感数据业务走私有化部署模型；
  - 同一模型多个渠道按权重和健康度负载均衡。
- **策略层**：限流（RPM / TPM）、超时、重试、熔断、降级、灰度发布和 A/B 测试。
- **安全层**：Prompt 注入检测、敏感信息脱敏、输出内容审核。
- **成本层**：Token 计量、费用统计、预算控制和超额告警。
- **缓存层**：精确缓存、语义缓存，以及 Embedding 结果缓存；同时利用厂商的 Prompt Caching。
- **观测层**：日志、Trace、首 token 延迟、总耗时、错误率、Token 消耗、模型命中率。
- **适配层**：每家厂商一个 Adapter，如 OpenAIAdapter、ClaudeAdapter、QwenAdapter、vLLMAdapter，负责请求转换、流式协议转换和错误码映射。

设计要点：网关本身无状态便于水平扩展；流式转发要注意背压和连接超时；路由和配额配置支持热更新。

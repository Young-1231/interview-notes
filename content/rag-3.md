## RAG 评估
### 如何评估一个 RAG 系统的效果？有哪些核心指标？
做法是**构建标准测试集，分开评估检索和生成，再看工程指标**。测试集包括问题、标准答案和标准引用文档。

分阶段评估的好处是便于定位问题：召回阶段没命中正确文档，说明要优化检索链路；召回正确但回答错误，说明要优化 Prompt、上下文组织或生成环节。

**1. 检索侧**
- Recall@K：相关文档是否出现在前 K 个结果里，覆盖得全不全。
- Precision@K：前 K 个结果中相关文档的比例。
- Hit Rate@K：前 K 个结果中至少命中一个相关文档的问题占比。
- MRR：第一个相关结果名次的倒数，再对所有问题求平均。
- NDCG@K：考虑分级相关性和位置的排序质量。

**2. 生成侧**
- 答案正确性：与标准答案对比，可以人工评，也可以用 LLM-as-a-Judge。
- 忠实度（Faithfulness）：答案是否都能被检索内容支持，衡量幻觉程度。
- 答案相关性：是否回答了用户的问题。
- 完整性：是否覆盖了问题需要的关键点。
- 引用准确性：引用的来源是否真的支撑对应结论。
- 可读性：表达是否清晰。

**3. 工程侧**：端到端延迟、首 Token 延迟（TTFT）、P95/P99、QPS、单次调用成本、缓存命中率、失败率。

**工具**：Ragas、RAGChecker、TruLens 等可以自动化计算大部分指标；上线后再结合用户反馈（点赞、点踩、转人工率）持续评估。

### RAG 经典的准确率评估指标有哪些？
分为**检索指标**（Query 与 Chunk 的匹配质量）和**生成指标**（生成答案与参考答案的一致性）。

**检索指标**

| 指标 | 计算 | 适用 |
| --- | --- | --- |
| MRR | 对每个 Query 取 1 / 第一个相关结果的名次（Top K 内没有则为 0），再对所有 Query 求平均 | 只要找到一个关键证据就能回答的问题 |
| NDCG@K | DCG@K / IDCG@K | 多个相关结果、相关性有强弱之分 |
| Precision@K | Top K 中相关数 / K | 关注结果是否干净 |
| Recall@K | Top K 中相关数 / 全部相关数 | 需要多个证据共同支撑答案 |

NDCG 中 $DCG@K=\sum_{i=1}^{K}\frac{2^{rel_i}-1}{\log_2(i+1)}$，IDCG 是理想排序下的 DCG。相关性 [2,1,0] 时 NDCG = 1；[1,2,0] 相关数量一样，但重要结果没排最前，NDCG 更低。

**生成指标**
- **BLEU**：n-gram 精确率（带短句惩罚），偏字面，语义相同但表述不同时分低。
- **ROUGE**：偏召回，看参考答案被覆盖多少（ROUGE-1/2 看一元/二元词，ROUGE-L 看最长公共子序列）。
- **METEOR**：考虑词干、同义词和词序，更接近人工判断。
- **EM**：规范化后完全一致得 1，否则 0，适合人名、数字、日期；“2024 年”vs“2024”也得 0。
- **Token 级 F1**：按重合词算 P、R 再求 F1，比 EM 宽松，适合短答案。

这些指标依赖人工标注的相关性和参考答案，而且对开放式回答只能做字面比较，所以现在多和 LLM-as-a-Judge 结合使用。

### 基于大模型的 RAG 评估（LLM-as-a-Judge）怎么做？
**传统指标的局限**
- **检索侧**：MRR、NDCG、Precision、Recall 都要提前标注 Query 与 Chunk 的相关关系。真实问题往往对应多个 Chunk，答案还可能跨 Chunk，标注难、人工成本高，换场景又要重新标注。
- **生成侧**：BLEU、ROUGE 只看词语重合，语义一致但表述不同时分数偏低；EM 又过于严格，不适合开放式问答。

**LLM-as-a-Judge 的做法**：用一个较强的 LLM 当评审，按照预设的评分标准（rubric）评估：
- **评估对象**：答案是否被上下文支持（忠实度）、是否回答了问题（相关性）、与参考答案是否语义一致（正确性）、检索上下文是否相关和充分。
- **评分方式**：直接打分（如 1–5 分）、二元判断、两两比较（pairwise，A 和 B 哪个更好），或先把答案拆成原子陈述（claim）再逐条验证。claim 级验证更稳定、更可解释。
- **提升可靠性**：给出明确的评分标准和示例，让模型先写理由再打分；用温度 0；pairwise 比较时交换 A/B 顺序做两次，抵消位置偏差；用少量人工标注校准评审结果与人工判断的一致性。
- **已知偏差**：位置偏差、偏好更长的答案（冗长偏差）、偏好与自己风格相近的输出（自我偏好），以及评审模型本身也可能判断错误。

常用框架有 **Ragas**（指标级打分，上手简单）和 **RAGChecker**（claim 级细粒度诊断）。

### 了解 RAGAs、RAGChecker 等评价框架吗？
两者都基于 LLM 自动评估。**Ragas 粒度较粗，上手快；RAGChecker 做 claim 级细粒度诊断**，能定位问题出在检索还是生成。

**Ragas**

输入是 question、answer（response）、contexts，以及可选的 ground_truth（reference）。

```json
{
  "question": "法国的首都是什么？",
  "answer": "巴黎是法国的首都。",
  "contexts": ["巴黎是法国的首都，也是最大的城市。", "法国位于欧洲西部。"],
  "ground_truth": "法国的首都是巴黎。"
}
```

| 指标 | 计算 | 需要标准答案 |
| --- | --- | --- |
| Faithfulness | 答案拆成 claim，能被上下文支持的比例（3 个中 2 个有依据得 ≈ 0.67） | 否 |
| Answer Relevance（0.2 起叫 Response Relevancy） | 由答案反推 N 个问题，与原问题的平均余弦相似度 | 否 |
| Context Precision | 相关 Chunk 是否排在前面：各相关位置的 Precision@k 求平均，v = [1,0,1,1] 时 ≈ 0.81 | 可选 |
| Context Recall | 标准答案的 claim 被上下文支持的比例 | 是 |

优点是简单、可批量自动化；缺点是粒度粗，分数受评审 LLM 和 Prompt 影响波动明显。

**RAGChecker（Amazon Science 开源）**

类似“按点给分”：把**回复和标准答案**都拆成原子 claim，再逐条核对，输入为 query、gt_answer、response、retrieved_context。四组比较：回复 vs 标准答案（正确性）、标准答案 vs 回复（完整性）、回复 vs 上下文（忠实度和幻觉）、标准答案 vs 上下文（检索质量）。

![](images/Java+AI八股-image-32.png)

| 模块 | 指标 | 含义 |
| --- | --- | --- |
| 整体 | Precision / Recall / F1 | 回复的正确性、完整性、综合质量 |
| 检索 | Claim Recall / Context Precision | 标准答案 claim 覆盖率 / 相关 Chunk 比例 |
| 生成 | Context Utilization | 用上了多少相关上下文 |
| 生成 | Noise Sensitivity / Hallucination | 被噪声误导的程度 / 幻觉，越低越好 |
| 生成 | Self-knowledge / Faithfulness | 用自身知识的程度 / 与上下文一致程度 |

优点：能区分漏召回、噪声干扰、幻觉等具体问题，更稳定。缺点：需要标准答案，LLM 调用多、成本高。

**选型**：快速迭代、没有标准答案时用 Ragas；需要定位问题、做严肃评测时用 RAGChecker。

### 除了准确率，RAG 系统还有哪些评价指标？
还可以从**系统性能、可扩展性、成本、用户体验**几个方面评估。

**1. 系统性能**
- 平均响应时间，以及分阶段耗时（改写、检索、Rerank、生成）。
- P95 / P99 延迟：看长尾慢请求是否严重。
- 首 Token 延迟（TTFT）：流式输出时最影响用户体感。
- 延迟分布直方图：观察请求集中区间和长尾。

**2. 可扩展性**
- 数据规模扩展：文档量增长后，延迟是否明显上升、检索准确率是否下降。
- 吞吐量：QPS。
- 高并发表现：压测下是否出现超时、错误率上升。

**3. 成本与稳定性**：单次请求 Token 消耗和费用、缓存命中率、失败率和降级比例。

**4. 用户体验**
- 人工满意度：人工打分、点赞和点踩比例、用户反馈。
- 答案可读性：表达清晰、自然，便于理解。
- 业务指标：问题解决率、转人工率、引用点击率。

## 幻觉与工程优化
### 用了 RAG 为什么还会有幻觉？常见原因有哪些？怎么降低？
RAG 能降低幻觉，但不能消除。原因可以按**数据、检索、上下文、生成**四个环节归类。

**常见原因**
- **知识库层**：知识缺失，模型只能编造补全；文档本身有错误或多版本冲突，模型采纳了过时或错误的内容。
- **切片层**：切块割裂语义，片段不完整，模型自行补全。
- **检索层**：召回率低，没找到相关内容；排序偏差，相关内容排在后面被截掉；Query 意图模糊，检索方向跑偏；混入大量无关文档。
- **上下文层**：上下文过长、噪声多，造成窗口污染；关键信息在长上下文中间被忽略（Lost in the Middle）；超出窗口被截断。
- **生成层**：模型过度依赖参数知识、忽视检索内容；生成时添加上下文里没有的细节；即使信息不足也倾向于给出流畅、看似合理的回答；采样带来随机性。
- **Prompt 层**：约束不够强，没有要求“只基于给定内容回答”。

**降低幻觉的方法**
1. **提升检索质量**：优化切块、混合检索、多路召回、Rerank、相似度阈值、Query 改写。
2. **治理知识库**：补全缺失知识，做版本管理，优先最新和权威的文档，并处理冲突内容。
3. **强化 Prompt 约束**：明确“只能基于以下内容回答，内容不足时回答不知道”，要求逐条标注引用。
4. **引用溯源**：返回来源和页码，让答案可核验。
5. **答案校验**：生成后让模型或 NLI 模型检查每个结论是否被上下文支持，不支持的就删除或重新生成；Self-RAG、CRAG 等方法把检索质量判断和自我反思纳入流程。
6. **调低随机性**：降低 temperature。
7. **高风险场景人工审核**：法律、医疗、金融等领域。
8. **持续评估**：用 Faithfulness 等指标监控幻觉率。

### 什么是上下文窗口污染？如何避免无关文档混入？
**上下文窗口污染**：检索召回的大量无关、冗余或过时文档被塞进 Prompt，占用窗口长度、稀释关键信息、干扰模型判断，进而诱发幻觉或错误答案。

**规避方法**
- **相似度阈值**：低于阈值的结果直接丢弃，宁缺毋滥。
- **Rerank 精排**：用高精度模型把真正有价值的文档排到前面，只取 Top N。
- **精细化切块**：每块聚焦一个主题，避免大块带入无关内容。
- **元数据过滤**：按时间、版本、业务线、权限过滤，排除过期和不相关的数据源。
- **去重**：去掉重复和近重复的片段。
- **上下文压缩**：只抽取与问题相关的句子。
- **控制数量和顺序**：限制进入 Prompt 的 Chunk 数，最相关的放在开头或结尾。
- **多轮对话清理**：只保留与当前问题相关的历史，必要时对历史做摘要。

### RAG 有哪些痛点？能做哪些优化？ | 高频
**痛点**集中在检索和生成两个阶段：
- **检索阶段**：召回不准（大量不相关文档带来噪声）、召回不全（遗漏关键信息，长文档和多跳问题尤其明显）。
- **生成阶段**：文本块太多超出上下文、推理变慢、成本升高；检索结果多而杂，模型抓不住重点，甚至出现幻觉。

**优化**围绕链路的四个环节展开：

1. **文档解析与切分**
   - 用 MinerU 等版面分析和 OCR 工具把 PDF、Word 转成 Markdown，保留标题、表格、公式等结构。
   - 固定长度切分会破坏语义，块太小信息不够、需要召回很多块，块太大 Embedding 效果差、费 Token。更推荐结构化或语义切分（按章节、段落、特殊标识符），配合 Overlap 和标题元数据。
2. **向量化与存储**
   - 根据语言、领域、长度和成本选 Embedding 模型。维度越高表达能力可能越强，但存储和计算成本也越高，要权衡；必要时做领域微调。
   - 选择合适的 ANN 索引，完善元数据和过滤字段。
3. **检索与召回**
   - 用户问题往往模糊，用 Query 改写转成更准确的检索语句（会增加延迟，实时性要求高的场景要慎用或用小模型）。
   - 多路召回：稀疏召回（BM25）+ 稠密召回（向量）+ 标题或标签召回；多路分数难以对齐，用 RRF 融合，再串联 Rerank，既过滤冗余，又提升精度。
4. **生成与输出**
   - 设计 Prompt 模板，要求基于上下文作答、标注引用、不足时说明。
   - 上下文压缩、合理排序，对答案做校验和后处理。

此外还要建立评估集和监控，持续迭代。

### RAG 的瓶颈在哪？落地中最难解决的问题是什么？
成熟的 RAG 不是简单的“向量库 + 大模型”，而是围绕**知识治理、检索优化、生成控制和效果评估**构建的工程系统。

**技术瓶颈**
- **检索质量上限**：可能召回不相关内容或遗漏关键信息，复杂推理、多跳问题尤其明显；召回没命中，后面再强也补不回来。
- **上下文窗口**：窗口虽然越来越大，但塞入大量检索块会增加成本和延迟，还会稀释关键信息。
- **切块导致信息损失**：破坏文档的全局结构，跨块信息难以关联；对“全文主要讲了什么”这类全局问题，基础 RAG 效果差。
- **实时性与一致性**：高频更新的知识库需要快速增量索引和同步，还要处理新旧版本。
- **成本与延迟**：每次请求都要经过改写、检索、重排、生成，相比纯 LLM 调用开销更大，大规模并发下难以保持低延迟。

**落地最难的三件事**
1. **知识质量**：原始文档重复、过期、冲突、格式混乱，再好的检索和模型也生成不了高质量答案。RAG 的上限很大程度取决于知识库质量，需要持续治理。
2. **检索准确性**：真实问题有口语化表达、多轮追问、专业术语、编号和缩写，单纯向量检索很难都召回准，需要 Query 改写、混合检索、多路召回、Rerank 等一整套优化。
3. **答案可信度**：即使检索正确，模型仍可能总结错误、遗漏重点或产生幻觉，需要引用溯源、Prompt 约束、答案校验和人工反馈闭环。

还有一个常被忽视的问题：**缺少评测集**。没有量化评估，就无法判断每项优化是否真的有效。

### RAG 如何实现加速？
目标是减少重复计算、降低检索和网络开销、提高吞吐。分三个层面：

**1. Embedding 阶段**
- **批量请求**：一次发送多段文本，避免逐条调用的网络开销。
- **异步并发**：用 asyncio 等并行请求，离线入库时尤其有效。
- **缓存**：高频 Query 的向量存入 Redis 或本地缓存；文档向量全部离线预计算。
- **模型分层**：简单、高频场景用轻量模型，复杂场景再用强模型；本地部署可以用 ONNX、TensorRT、量化等方式加速推理。
- **合理切块**：块太多会增加编码和检索负担。

**2. 检索阶段**
- **高效 ANN 索引**：HNSW、IVF 等，调优 ef、nprobe 等参数平衡速度和召回。
- **批量或并发检索**：多路召回并行执行。
- **先过滤后检索**：用标签、时间、业务条件缩小候选集。
- **分阶段检索**：先粗召回再精排；控制 Top K，减轻 Rerank 和生成的负担。
- **Rerank 加速**：用轻量模型、限制候选数、批量推理。

**3. 系统架构**
- **异步流水线**：可以并行的步骤并行执行（如改写和关键词检索同时进行），减少串行等待。
- **流式输出**：LLM 结果通过 SSE 流式返回，降低首 Token 延迟的体感。
- **任务队列与批处理**：高并发请求聚合处理，推理服务用 vLLM 等做 continuous batching。
- **负载均衡**：多实例部署，多个 API Key 分摊限流，避免单点瓶颈。
- **冷热分层**：热数据放内存索引，冷数据放低成本存储（如 DiskANN、对象存储）。
- **预计算与缓存**：热门问题的答案做语义缓存（相似问题直接命中），开启 LLM 的 Prompt Caching（固定的系统提示放在前缀），对热门路由结果做预热。

### 知识库如何动态更新？新增文档后怎么快速生效？
核心是**增量入库 + 版本管理 + 异步处理**，不做全量重建。

1. **新增**：上传后触发解析、清洗、切块、向量化，写入向量库；文档 ID、版本号、更新时间、状态等写入元数据表。
2. **修改**：根据文档 ID 找到旧版本的全部 Chunk，标记失效或删除，再写入新版本。可以用内容哈希判断哪些 Chunk 真正变了，只重算变化的部分。
3. **删除**：物理删除向量，或逻辑删除（状态字段 + 检索过滤），之后再定期清理。
4. **版本管理**：同一文档可能有多个版本，检索时按版本或状态过滤，优先最新版本，避免召回旧内容。可以先写入新版本，再一次性切换状态，避免更新过程中出现两个版本同时可见或都不可见。
5. **异步任务**：解析和向量化耗时较长，用消息队列（Kafka、RabbitMQ 等）异步处理，支持失败重试和进度追踪。
6. **快速生效**：写入后让数据尽快可查。不同向量库的可见性机制不同，例如 Milvus 有 flush 和一致性级别设置，ES 有 refresh 间隔，需要确认配置。同时清理相关的语义缓存和答案缓存。
7. **同步一致**：向量索引、倒排索引、元数据库要同时更新，可以监听数据源变更（CDC）自动触发。

大批量更新时，HNSW 等索引的删除标记会累积，需要定期做 compaction 或重建索引，保证检索性能和召回率。

## 进阶 RAG 范式
### 除了基础 RAG，你还了解哪些高级 RAG 架构或范式？
| 范式 | 核心思想 |
| --- | --- |
| Naive RAG | 切块 → 向量检索 → 拼进 Prompt 生成，是最基础的流程 |
| Advanced RAG | 在检索前后加优化：Query 改写、混合检索、Rerank、上下文压缩、引用溯源 |
| Modular RAG | 把检索、改写、路由、记忆等拆成可组合的模块，按需编排流程 |
| Conversational RAG | 面向多轮对话，结合历史做 Query 改写，解决指代和省略问题 |
| Hybrid RAG | 组合向量检索、关键词检索、结构化数据库查询、知识图谱检索 |
| GraphRAG | 用知识图谱组织实体和关系，支持多跳推理和全局总结 |
| Agentic RAG | Agent 自主决定是否检索、检索什么、检索几次、调用哪些工具 |
| Self-RAG | 训练模型输出反思标记（reflection tokens），自主判断是否需要检索、检索结果是否相关、答案是否被支持 |
| Corrective RAG（CRAG） | 用评估器给检索结果打分，质量差就改写后重新检索或转向网络搜索，并对文档做精炼 |
| Adaptive RAG | 按问题复杂度路由：简单问题不检索，中等问题单次检索，复杂问题多步检索 |
| RAPTOR | 递归聚类并生成摘要，构建树状索引，支持不同抽象层级的检索 |
| Multimodal RAG | 检索图片、表格、图表，用多模态模型理解和生成 |

### 了解过 Agentic RAG 吗？
Agentic RAG 是在 RAG 中引入 Agent 的自主决策能力，把“检索 → 生成”从固定的一次性流程，变成**动态、迭代、可调整**的过程：由系统自己决定怎么检索、检索几次、是否调用其他工具、是否需要反思和修正。

**关键特点**
1. **自主决策**：根据问题复杂度选择策略，例如是否需要检索、查哪个知识库、要不要联网搜索或查数据库。
2. **迭代改进**：得到初步结果后判断信息是否足够、答案是否可靠，不够就改写后再检索，形成“检索 → 评估 → 再检索”的闭环。
3. **工具融合**：检索只是工具之一，还可以调用 API、SQL、搜索引擎、业务系统，适合需要实时数据的场景。

**典型模块**：LLM 作为推理引擎；记忆模块（短期上下文、长期经验）；Planning 模块（任务拆解，如 ReAct、Plan-and-Execute）；Reflection 模块（结果校验）；工具调用模块（向量库、外部系统）。

**多 Agent 模式**：路由 Agent 分发任务，检索、验证、总结、业务接口调用分别由不同的 Agent 负责，最后汇总结果。

**代价**：多轮 LLM 调用导致延迟和成本上升，行为更难预测和调试，需要设置最大迭代次数、超时，并做好可观测性。适合复杂、多步骤的问题，简单 FAQ 用传统 RAG 就够了。

### 什么是多轮对话？
多轮对话是用户和系统连续多轮交互，后续提问依赖前文语境，例如先问“这台打印机怎么样”，再问“它的功能是什么”。

在 RAG 中，多轮对话的核心实现是**Query 改写**：用一个改写模块（通常是 LLM）结合历史对话改写当前问题，把模糊的问题变成能独立理解的查询，再去检索和回答。主要手段有两个：

- **指代消解**：把“它”“他”“那个”等代词替换为具体实体，例如“它的功能”改写成“这台打印机的功能”。
- **省略补全**：补齐缺失的信息，例如上一句问“我的电脑配置怎么样”，下一句“那性能呢”补全为“我的电脑性能怎么样”，脱离历史也能理解。

工程上还要做**会话记忆管理**：完整保留最近几轮对话，较早的历史做摘要，控制 Token 消耗；按会话 ID 存储历史（如存在 Redis 中）。

### 多轮对话 RAG 主要解决什么问题？
主要解决：**当前提问依赖历史对话，单独看是模糊或不完整的，直接拿去检索会召回不到相关文档，或者召回错误文档**。例如“那它的价格呢？”，单独检索根本不知道“它”指什么。

**解决方式**：在检索前加一个改写模块（Condense Question / Query Rewrite），结合历史对话做指代消解和省略补全，把问题还原成独立完整的查询，再送入检索链路。改写后的查询能明显提升召回精度，进而保证回答准确。

**其他要点**
- **话题切换判断**：识别用户是在追问还是换了新话题，避免把无关历史拼进查询。
- **历史管理**：生成时带上必要的对话历史，但要控制长度（滑动窗口 + 摘要）。
- **上下文复用**：追问同一主题时，可以复用上一轮的检索结果，减少重复检索。

## GraphRAG 与知识图谱
### 知识图谱的三要素是什么？
知识图谱的三要素是**实体（Entity）、关系（Relation）、属性（Attribute）**。知识通常用三元组表示：(头实体, 关系, 尾实体) 或 (实体, 属性, 属性值)。

- **实体**：现实世界中的对象或概念，如人、地点、组织、产品、事件，在图中是节点。可以直观理解为“名词”。
- **关系**：实体之间的语义联系，如“任职于”“位于”“推出”，在图中是有向边。可以理解为连接名词的“动词”。
- **属性**：实体或关系的描述性特征，以键值对表示，如实体的“成立时间”，关系的“生效时间”。

**以苹果公司为例**
- 实体：苹果公司（组织）、蒂姆·库克（人物）、库比蒂诺（地点）、iPhone（产品）。
- 关系：(苹果公司)-[CEO 是]->(蒂姆·库克)、(苹果公司)-[总部位于]->(库比蒂诺)、(苹果公司)-[推出]->(iPhone)。
- 属性：苹果公司{成立时间: 1976 年, 股票代码: AAPL}；iPhone{首发年份: 2007 年, 操作系统: iOS}。

### 知识图谱构建的核心流程是什么？
核心步骤是**实体抽取 → 关系抽取 → 知识融合与对齐 → 存储与更新**。GraphRAG 里的建图也是这个思路，只是主要由 LLM 来抽取。

![](images/Java+AI八股-image-37.png)

1. **数据准备**：收集结构化、半结构化和非结构化数据，非结构化文本先做解析和切块。
2. **实体抽取（NER）**：识别人名、组织、地点、产品等实体。方法包括规则和词典（正则、领域词表）、深度学习序列标注（BERT + CRF 等）、LLM 抽取（按 Schema 用 Prompt 抽取）。
3. **关系抽取**：识别实体之间的语义关系。方法有规则模板、监督学习分类，以及实体和关系的联合抽取，现在也常用 LLM 直接输出三元组；同时抽取属性。
4. **知识融合与对齐**：处理多来源数据的冲突与重复。
   - 实体消歧：区分同名不同义的实体，如水果“苹果”和苹果公司；
   - 共指消解：识别同一实体的不同表述，如“苹果公司”“Apple”“它”；
   - 实体对齐：合并不同知识库中的同一实体。
5. **质量校验与存储**：去掉错误三元组，写入图数据库，设计 Schema（本体）。
6. **持续更新**：增量抽取新文档，并处理与已有知识的冲突。

### 知识图谱用什么存储？有哪些图数据库？
知识图谱可以存在 RDF 三元组库中（如 Apache Jena，用 SPARQL 查询），工程上更常用**属性图数据库**：

| 图数据库 | 特点 |
| --- | --- |
| Neo4j | 最成熟的原生属性图数据库，使用 Cypher 查询语言，社区活跃，适合关联查询和路径分析；GraphRAG 场景用得最多 |
| NebulaGraph | 国产开源分布式图数据库，水平扩展能力强，适合超大规模图谱 |
| JanusGraph | 开源分布式图数据库，存储后端可选 HBase、Cassandra 等，使用 Gremlin 查询 |
| HugeGraph | 百度开源，支持百亿级节点和边，与大数据生态对接好 |
| ArangoDB | 多模型数据库，同时支持图、文档和 KV，灵活，但纯图场景性能不如原生图库 |
| Amazon Neptune | 托管图数据库，同时支持属性图（Gremlin、openCypher）和 RDF（SPARQL） |

一般掌握 Neo4j 和 Cypher 就够应对面试了，例如：

```cypher
MATCH (c:Company {name: '苹果公司'})-[:CEO_IS]->(p:Person) RETURN p.name
```

### 什么场景下会用知识图谱而不是单纯的向量检索？
问题不只是“语义相似”，而是涉及**明确的实体关系、多跳推理、路径解释或全局聚合**时，就适合用知识图谱。向量检索擅长找相似的内容，不擅长表达强结构化的关系。

**适用场景**
1. **实体关系复杂**：金融风控中用户、账户、设备、手机号、交易之间的关联网络。
2. **多跳查询**：“某客户关联了哪些高风险账户，这些账户又关联了哪些设备”。向量检索很难一次召回整条链路。
3. **需要可解释的路径**：风控、医疗、法律等场景，不仅要给结论，还要说明关联路径和依据。
4. **层级和依赖关系明确**：组织架构、产品依赖、供应链、论文引用、代码调用关系。
5. **精确的聚合或枚举**：“列出所有供应商为 X 的产品”，图查询或 SQL 比相似度检索更准。
6. **全局性问题**：“这批文档的主要主题有哪些”，可以借助 GraphRAG 的社区摘要回答。

**和 RAG 的结合**：先识别问题中的关键实体，在图谱中查询相关关系和路径（如用 Text-to-Cypher 或子图扩展），同时用向量检索召回相关文本，两者一起交给大模型生成答案。

**代价**：建图和维护成本高。纯文档问答、关系不重要的场景，用向量检索加 Rerank 就够了。

### GraphRAG 解决了 RAG 的什么问题？ | 高频
GraphRAG（微软 2024 年提出）在索引阶段先用 LLM 从文档中抽取实体和关系构建知识图谱，再做社区划分并生成社区摘要。它主要解决传统 RAG **关系建模不足、全局理解弱、多跳推理难**的问题。

- **平面检索问题**：传统 RAG 把 Chunk 当作相互独立的单元，只能找到“相似”的片段，不知道它们之间的联系。GraphRAG 用实体和关系把信息连成网络，支持沿关系做多跳检索。
- **语境缺失**：检索到的片段可能缺少上下文。GraphRAG 能带上实体的关联信息和所属社区的摘要，提供更完整的上下文。
- **全局性问题（核心价值）**：像“这批文档的主要主题是什么”这类问题，答案分散在全库中，Top-K 检索只能看到局部片段。GraphRAG 通过层次化的社区摘要做 map-reduce，能整合分散信息，回答跨文档的总结和分析类问题。
- **检索更有针对性**：从相关实体出发，只沿相关节点和路径扩展，而不是在全库做相似度匹配。

一句话：传统 RAG 擅长回答局部事实问题，GraphRAG 补上了关系推理和全局总结能力。

### GraphRAG 的知识图谱是怎么建立的？ | 高频
本质是把原始文本逐步转成**实体 → 关系 → 社区 → 摘要**的结构化知识体系：

1. **文本切分**：切成 TextUnit（Chunk），保留与源文档的对应关系。
2. **实体与关系抽取**：LLM 从每个 Chunk 抽取实体（名称、类型、描述）和关系（源、目标、描述、强度），也可抽 claim；可多轮抽取（gleaning）减少遗漏。
3. **图谱融合**：同名同类型实体合并，多处描述由 LLM 汇总，去重去噪。
4. **分层社区检测**：用 Leiden 做层次化社区划分，每个社区对应一个主题或子主题。
5. **社区摘要**：LLM 为每个社区生成报告（主要实体、关系、关键发现），底层摘要作为上层输入，形成多层摘要。
6. **向量化**：实体描述、文本单元、社区报告做 Embedding，供 local / global 检索。

**Leiden（常见追问）**：对 Louvain 的改进，解决 Louvain 可能产出内部不连通社区的问题，且通常收敛更快。迭代三步：局部移动（节点移到增益最大的邻居社区）→ **细化**（社区内再细分，保证内部连通，这是关键改进）→ 聚合（社区压成超级节点再重复），自然得到层次结构。易错点：分辨率限制是模块度目标函数本身的问题，Leiden 用模块度时同样存在，改用 CPM 等目标才能缓解。

### GraphRAG 常见的检索方式有哪些？ | 高频
微软 GraphRAG 主要提供 **Local Search** 和 **Global Search** 两种方式，后来又加入了 DRIFT Search。

- **Local Search（局部检索）**：适合询问具体实体细节的问题，例如“某科研项目的负责人是谁”。先用向量相似度找到与问题相关的实体，再沿图扩展，收集相关的实体描述、关系、所属社区报告和原始文本单元，拼成上下文交给 LLM 回答。
- **Global Search（全局检索）**：适合跨文档的全局总结问题，例如“这批文档的主要主题有哪些”“本季度所有产品的销售趋势如何”。在某个社区层级上，对所有社区报告做 **map-reduce**：map 阶段每批报告各自生成带重要性评分的要点，reduce 阶段筛选高分要点汇总成最终答案。成本较高。
- **DRIFT Search**：结合两者，先用社区报告得到全局视角和后续子问题，再用 local search 逐步深入细节。
- **其他图检索方式**：从实体出发的 N 跳子图扩展、路径查询、Text-to-Cypher 直接查询图数据库，以及图检索与向量检索的混合。

### GraphRAG 相比传统 RAG 有什么劣势？ | 高频
主要劣势是**前期构建成本高、更新不灵活、维护复杂**。

- **建图成本高**：实体关系抽取、描述汇总、社区摘要都要大量调用 LLM，Token 消耗通常是普通向量索引的数倍到数十倍以上，耗时也长。
- **增量更新难**：传统 RAG 新增文档只需切块和向量化。GraphRAG 新增内容可能影响已有实体、关系和社区结构，社区和摘要往往要部分或全部重算，增删改都比较麻烦。
- **实时性弱**：数据变化快的场景，图结构和摘要跟不上更新。
- **维护成本高**：需要持续处理实体去重、消歧、关系冲突和图谱一致性；抽取质量依赖 LLM，抽错的实体和关系会在图里传播。
- **查询成本**：Global Search 的 map-reduce 要处理大量社区报告，延迟高、费用高。
- **系统复杂度高**：涉及图存储、图算法、抽取 Prompt 调优、分层摘要等模块，链路长，排查和调优困难。
- **简单问题收益有限**：对单点事实问答，效果不一定比向量检索加 Rerank 更好，性价比低。

### 还有哪些 GraphRAG 算法？分别解决了什么问题？ | 高频
改进主要沿两个方向：**降低建图和查询成本**，以及**解决图谱难以更新的问题**。

| 方案 | 核心思路 | 解决的问题 |
| --- | --- | --- |
| LightRAG（港大，2024） | 轻量图索引，不做重量级的社区聚类和社区报告；双层检索（low-level 检索具体实体，high-level 检索主题和关系关键词），结合图和向量；新文档抽取后直接合并进已有图 | 建图成本高、增量更新难 |
| LazyGraphRAG（微软，2024） | 索引阶段不用 LLM 做摘要，只用轻量 NLP 抽取名词短语和共现关系；把 LLM 的摘要推迟到查询时按需进行，可以通过预算参数在成本和质量之间调节 | 前期索引成本过高，官方称索引成本与向量 RAG 相当，约为完整 GraphRAG 的 0.1% |
| Fast GraphRAG（Circlemind） | 用 Personalized PageRank 在图上做相关性传播和检索，支持增量更新 | 速度、成本和动态数据 |
| HippoRAG | 借鉴海马体记忆理论，构建知识图谱后用 Personalized PageRank 做多跳检索 | 单步检索完成多跳推理，成本低 |
| KG-RAG / Think-on-Graph 等 | LLM 在图上逐步探索推理路径 | 复杂多跳推理 |

面试时重点讲 LightRAG（增量更新 + 双层检索）和 LazyGraphRAG（摘要推迟到查询时），这两个最常被问到。

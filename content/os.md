## 进程、调度与死锁
### 什么是进程、线程？它们之间有什么区别 | 高频
进程是资源分配的基本单位，线程是 CPU 调度的基本单位；一个进程内可以有多个线程，它们共享进程的资源。

**进程**：程序的一次执行过程，拥有独立的虚拟地址空间、页表、打开的文件等资源。

**线程**：进程内的一个执行流。同一进程的线程共享地址空间、堆、全局变量和打开的文件，但每个线程有自己独立的栈、寄存器和程序计数器。

| 对比 | 进程 | 线程 |
| --- | --- | --- |
| 资源 | 独立地址空间 | 共享所属进程的资源 |
| 创建/切换开销 | 大，切换要换页表，TLB 失效 | 小，同进程内切换不用换页表 |
| 通信 | 需要 IPC（管道、消息队列、共享内存、Socket 等） | 直接读写共享内存，但要自己做同步 |
| 健壮性 | 一个进程崩溃一般不影响其他进程 | 一个线程崩溃（如段错误）会导致整个进程退出 |

**常见追问**
- Linux 内核不严格区分进程和线程，两者都是 `task_struct`，创建时通过 `clone()` 的共享标志（如 `CLONE_VM`、`CLONE_FILES`）决定共享哪些资源。
- 协程是用户态调度的轻量执行单元，切换不进入内核，开销比线程更小。

### 进程有哪些状态？它们之间是如何转换的
进程有三种基本状态：就绪、运行、阻塞；完整的五状态模型再加上创建和终止。

- **就绪**：已具备运行条件，只差 CPU。
- **运行**：正在 CPU 上执行。
- **阻塞**（等待）：在等某个事件，比如 I/O 完成，即使给它 CPU 也没法运行。

**转换关系**
- 就绪 → 运行：被调度程序选中，分配到 CPU。
- 运行 → 就绪：时间片用完，或被更高优先级的进程抢占。
- 运行 → 阻塞：主动等待事件，比如发起 I/O 请求、等待锁。
- 阻塞 → 就绪：等待的事件发生，比如 I/O 完成。

注意：阻塞不能直接变成运行，必须先回到就绪队列再被调度；就绪也不能直接变成阻塞，因为只有正在运行的进程才会发起等待。

### 常见的进程调度算法有哪些？
常见的有先来先服务、短作业优先、优先级调度、时间片轮转和多级反馈队列。

| 算法 | 思路 | 特点 |
| --- | --- | --- |
| 先来先服务（FCFS） | 按到达顺序调度，非抢占 | 简单；短作业排在长作业后面时平均等待时间长 |
| 短作业优先（SJF） | 优先调度预计运行时间最短的 | 平均周转时间最短；长作业可能饥饿，且运行时间难以准确预估 |
| 优先级调度 | 优先调度优先级高的，可抢占或非抢占 | 低优先级可能饥饿，常用"老化"（等待越久优先级越高）缓解 |
| 时间片轮转（RR） | 就绪队列轮流执行一个固定时间片 | 公平、响应快，适合分时系统；时间片太小切换开销大，太大退化成 FCFS |
| 多级反馈队列 | 多个优先级队列，高优先级队列时间片短；用完时间片就降级 | 兼顾响应时间和吞吐，不需要预知运行时间 |

Linux 的普通进程在 2.6.23 到 6.5 使用 CFS（完全公平调度，按虚拟运行时间选进程），6.6 起换成 EEVDF；实时进程使用 `SCHED_FIFO` / `SCHED_RR`。

### 什么是死锁？产生死锁的四个必要条件是什么 | 高频
死锁是指多个进程（或线程）因争夺资源而互相等待对方释放资源，导致都无法继续推进。

**四个必要条件**（必须同时满足才会死锁）
1. **互斥**：资源同一时刻只能被一个进程占用。
2. **占有并等待**：进程已经持有至少一个资源，又在等待别的进程持有的资源。
3. **不可剥夺**：已分配的资源只能由持有者主动释放，不能被强行拿走。
4. **循环等待**：存在一个进程-资源的环形等待链，P1 等 P2、P2 等 P3……Pn 等 P1。

例子：线程 A 持有锁 1 再去申请锁 2，线程 B 持有锁 2 再去申请锁 1。Java 中可以用 `jstack` 直接检测出这种死锁。

### 如何避免死锁？请介绍几种常见的死锁预防策略
处理死锁有四类思路：预防、避免、检测与恢复、忽略。最容易混的是预防和避免：预防是静态地破坏必要条件，避免是分配资源时动态判断。

**死锁预防**：破坏四个必要条件之一。
- 破坏"占有并等待"：一次性申请全部资源，申请不全就一个都不拿。缺点是资源利用率低。
- 破坏"不可剥夺"：申请新资源失败时，主动释放已持有的资源；或者允许高优先级进程抢占。Java 里对应 `tryLock(timeout)`，拿不到就释放已有的锁再重试。
- 破坏"循环等待"：给资源统一编号，所有进程都按编号顺序申请。这是工程中最常用的方法，比如多把锁总是按固定顺序加锁。
- 破坏"互斥"：一般做不到，很多资源天然互斥（如打印机、写锁）。

**死锁避免**：分配资源前先判断，如果分配后系统仍处于安全状态（存在一个能让所有进程都执行完的序列）才分配，代表算法是银行家算法。

**检测与恢复**：允许死锁发生，通过资源分配图检测环路，然后终止某些进程或剥夺资源来解除。

**忽略**（鸵鸟策略）：通用操作系统大多这样处理，交给应用层自己解决。

## 内存管理
### 什么是虚拟内存？它解决了什么问题 | 高频
虚拟内存是给每个进程一个独立、连续的虚拟地址空间，由 MMU 通过页表把虚拟地址映射到物理内存，暂时不用的页可以放到磁盘（swap）上。

**解决的问题**
- **进程隔离**：每个进程只能访问自己的地址空间，互不干扰，也不能直接访问内核内存。
- **突破物理内存大小**：只把正在用的页装入内存，程序可以使用比物理内存更大的地址空间。
- **简化内存管理**：进程看到的是连续地址，物理页可以离散分配；链接、加载时也不用关心真实物理地址。
- **便于共享**：多个进程的虚拟页可以映射到同一个物理页，比如共享库、共享内存、`fork` 后的写时复制。

**地址翻译过程**
1. CPU 发出虚拟地址，MMU 先查 TLB（页表项的硬件缓存），命中就直接得到物理地址。
2. TLB 未命中时查内存中的多级页表（x86-64 常见 4 级，支持的 CPU 可启用 5 级），并把结果填入 TLB。
3. 页表项无效时触发缺页异常，内核分配物理页或从磁盘 / swap 调入，更新页表后重新执行这条指令。

多级页表的作用是节省页表本身占用的内存：没有用到的地址区间不需要分配下级页表。

### 什么是分页和分段？它们有什么区别
分页把内存切成固定大小的页，分段按程序逻辑切成大小不一的段；现代操作系统（如 x86-64 上的 Linux）以分页为主，分段基本只保留形式。

- **分页**：虚拟地址空间和物理内存都划分为固定大小的页（常见 4KB），通过页表映射。对程序员透明。
- **分段**：按逻辑模块划分为代码段、数据段、栈段等，每段长度可变，通过段表（段基址 + 段长）映射。

| 对比 | 分页 | 分段 |
| --- | --- | --- |
| 大小 | 固定 | 可变，由程序逻辑决定 |
| 划分依据 | 物理管理需要，无逻辑意义 | 程序的逻辑结构 |
| 对用户 | 透明 | 可见，程序员或编译器参与划分 |
| 碎片 | 没有外部碎片，最后一页可能有内部碎片 | 没有内部碎片，会产生外部碎片 |
| 共享与保护 | 以页为单位，不够直观 | 以段为单位，便于共享和设置权限 |

段页式结合了两者：先分段，段内再分页，地址由段号、页号、页内偏移组成。

### LRU 算法怎么实现的？ | 高频
LRU（Least Recently Used）在缓存满时淘汰最久没被访问的数据。用"哈希表 + 双向链表"可以让 `get` 和 `put` 都做到 O(1)。

- 哈希表：key → 链表节点，O(1) 定位节点。
- 双向链表：维护访问顺序，靠近头部的是最近访问的，尾部是最久未访问的。双向链表才能 O(1) 删除任意节点。
- `get`：查哈希表，不存在返回 -1；存在就把节点移到头部。
- `put`：key 已存在就更新值并移到头部；不存在就新建节点插到头部，超过容量时删除尾部节点，并从哈希表中移除它的 key。
- 用哨兵头尾节点（dummy head / tail）可以省掉大量判空。

```java
class LRUCache {
    class Node { int key, val; Node prev, next; Node(int k, int v) { key = k; val = v; } }
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0), tail = new Node(0, 0);
    private final int capacity;

    public LRUCache(int capacity) { this.capacity = capacity; head.next = tail; tail.prev = head; }
    public int get(int key) {
        Node node = map.get(key);
        if (node == null) return -1;
        remove(node); addFirst(node);
        return node.val;
    }
    public void put(int key, int value) {
        Node node = map.get(key);
        if (node != null) { node.val = value; remove(node); addFirst(node); return; }
        if (map.size() == capacity) {
            Node last = tail.prev;
            remove(last); map.remove(last.key);   // 节点里存 key 就是为了这里能删哈希表
        }
        node = new Node(key, value); addFirst(node); map.put(key, node);
    }
    private void remove(Node n) { n.prev.next = n.next; n.next.prev = n.prev; }
    private void addFirst(Node n) { n.next = head.next; n.prev = head; head.next.prev = n; head.next = n; }
}
```

手撕时一般要求自己写节点和链表。实际项目中可以直接用 `LinkedHashMap`：构造时 `accessOrder = true`，并重写 `removeEldestEntry` 在 `size() > capacity` 时返回 true。它不是线程安全的，并发场景要加锁或用 Caffeine 这类缓存库。

LRU 也是操作系统页面置换算法之一，其他还有 FIFO、OPT（理论最优，无法实现）、Clock（LRU 的近似实现）、LFU。

### 什么是内存对齐？为什么需要内存对齐
内存对齐是指数据的起始地址是某个数（通常是它自身大小）的整数倍，比如 4 字节的 int 放在 4 的倍数地址上。编译器会在结构体成员之间插入填充字节来满足对齐。

**为什么需要**
- **访问效率**：CPU 按字长或缓存行读取内存，对齐的数据一次就能读完；未对齐的数据可能跨两个字或两个缓存行，要读两次再拼接。
- **硬件限制**：有些架构（如部分 ARM、SPARC）访问未对齐地址会直接触发异常。
- **原子性**：跨缓存行的数据无法保证单条指令的原子读写。

代价是占用更多空间，所以定义结构体时把大成员放前面、小成员放后面，可以减少填充。Java 对象也按 8 字节对齐，这是对象头之外有时会有 padding 的原因。

### 什么是大端字节序和小端字节序？
多字节数据在内存中的存放顺序不同：大端是高位字节存在低地址，小端是低位字节存在低地址。

以 `0x12345678` 从低地址到高地址存放为例：
- 大端：`12 34 56 78`，和人的书写顺序一致。
- 小端：`78 56 34 12`。

x86 和绝大多数 ARM 运行环境是小端；网络字节序规定为大端，所以 socket 编程要用 `htonl` / `ntohl` 等函数转换。Java 虚拟机内部和 `DataOutputStream`、`ByteBuffer`（默认）都按大端处理，`ByteBuffer.order()` 可以改成小端。

判断本机字节序：把 int 1 的首字节取出来，是 1 就是小端。

## 内核、文件与 I/O
### 什么是用户态和内核态？为什么要有这两种状态
用户态和内核态是 CPU 的两种特权级别：用户程序运行在用户态，只能执行非特权指令、访问自己的地址空间；内核运行在内核态，可以执行特权指令、访问全部内存和硬件。x86 上分别对应 Ring 3 和 Ring 0。

**为什么要区分**
- **安全与稳定**：I/O、修改页表、关中断这类特权操作只能由内核完成，防止用户程序有意或无意破坏系统、访问其他进程的数据。
- **统一管理资源**：用户程序必须通过系统调用向内核申请资源，内核可以做权限检查和调度。

**代价**：用户态和内核态切换要保存和恢复寄存器、切换栈，还可能影响缓存和 TLB，所以频繁的系统调用有开销。这也是零拷贝、批量 I/O、epoll 等优化的出发点。

### 用户态切换到内核态的触发方式有哪些
有三种：系统调用、异常、外设中断。

1. **系统调用**：用户程序主动请求内核服务，比如 `read`、`write`、`fork`、`mmap`。x86-64 上通过 `syscall` 指令进入内核。
2. **异常**：当前指令执行出错或需要内核处理，比如缺页异常、除零、非法指令。属于同步事件。
3. **外设中断**：硬件设备发出中断信号，比如网卡收到数据包、磁盘 I/O 完成、时钟中断。属于异步事件，与当前执行的指令无关。

系统调用本质上也是一种由指令主动触发的陷入（trap）。处理完后内核恢复上下文，返回用户态继续执行。

### 软链接和硬链接的区别是什么 | 高频
硬链接是同一个 inode 的另一个文件名；软链接是一个独立的文件，内容是目标路径。

| 对比 | 硬链接 | 软链接（符号链接） |
| --- | --- | --- |
| 本质 | 目录项指向同一个 inode | 独立的文件，有自己的 inode，存的是路径 |
| 跨文件系统 | 不能 | 可以 |
| 链接目录 | 不能（防止目录树出现环） | 可以 |
| 删除源文件 | 不影响，数据仍可通过其他链接访问 | 链接失效，变成悬空链接 |
| 创建命令 | `ln src dst` | `ln -s src dst` |

**文件数据什么时候真正被删除**：inode 的硬链接计数降为 0，并且没有进程还打开着这个文件。所以删掉一个正在被进程写入的日志文件，磁盘空间不会立刻释放。

### 什么是零拷贝（Zero-Copy）技术 | 高频
零拷贝是减少数据在内核缓冲区和用户缓冲区之间的 CPU 拷贝、以及用户态/内核态切换次数的 I/O 优化，典型场景是把文件发送到网络。

**传统 read + write**：4 次拷贝（2 次 DMA + 2 次 CPU），4 次上下文切换。
1. 磁盘 → 内核 page cache（DMA）
2. page cache → 用户缓冲区（CPU）
3. 用户缓冲区 → socket 缓冲区（CPU）
4. socket 缓冲区 → 网卡（DMA）

**mmap + write**：把内核缓冲区映射到用户空间，省掉第 2 步的 CPU 拷贝。剩 3 次拷贝（2 DMA + 1 CPU），仍是 4 次上下文切换。

**sendfile**（Linux 2.1 引入）：一次系统调用完成，数据不经过用户态，只有 2 次上下文切换。从 Linux 2.4 起，如果网卡支持 SG-DMA，内核只把文件描述信息（地址和长度）追加到 socket 缓冲区，网卡直接从 page cache 读取，CPU 拷贝次数降为 0，只剩 2 次 DMA 拷贝。

| 方式 | CPU 拷贝 | DMA 拷贝 | 上下文切换 |
| --- | --- | --- | --- |
| read + write | 2 | 2 | 4 |
| mmap + write | 1 | 2 | 4 |
| sendfile | 1 | 2 | 2 |
| sendfile + SG-DMA | 0 | 2 | 2 |

**Java 与中间件**
- `FileChannel.transferTo()` 在 Linux 上底层使用 `sendfile`；`FileChannel.map()` 得到的 `MappedByteBuffer` 对应 mmap。
- Kafka 把日志发送给消费者时用 `transferTo`（sendfile），RocketMQ 读写 CommitLog 用 mmap。
- 零拷贝的前提是应用不需要修改数据内容；需要加工数据时还是要读到用户态。

## 记忆基础与分类

### Agent 为什么需要 Memory？如何设计一个 Agent 的记忆系统？
LLM 本身无状态，每次请求只看到本次传入的上下文。Memory 就是在模型外部维护状态，再按需把相关内容拼回上下文的一层工程能力。

**为什么需要**
- 多步任务要记住已执行的步骤、工具结果和下一步计划。
- 多轮对话要保持连贯，不能每轮都像第一次交互。
- 跨会话要记住用户偏好、项目约束、历史决策和可复用经验。

**分层设计**

| 层 | 保存内容 | 典型实现 |
| --- | --- | --- |
| 短期 / 工作记忆 | 当前会话消息、工具结果、计划与待办、中间变量 | 上下文窗口 + 会话级 State（按 `thread_id` 隔离，用 checkpointer、Redis 持久化） |
| 长期记忆 | 用户画像、稳定事实、历史任务总结、经验规则 | 关系库 / KV 存结构化字段，向量库做语义召回，也可以是 Markdown 文件 |
| 摘要层 | 早期对话的压缩版本 | 滚动摘要、阶段摘要 |

**关键设计点**
- 写入：不是什么都记。先抽取、去重、判断价值，再结构化写入。
- 读取：按当前任务检索 Top-K 后注入，而不是全量拼接。
- 治理：过期、衰减、冲突消解，每条记忆带来源和置信度。
- 安全：按 `user_id` / 租户隔离，敏感信息脱敏，支持用户查看和删除。

### Agent 的记忆系统分为哪几层？短期记忆和长期记忆有什么区别？
短期记忆服务当前任务，直接放在上下文里；长期记忆跨会话持久化，要检索后才进入上下文。

常见的三层：
1. **上下文窗口**：模型本次推理实际看到的 token，容量等于模型上下文长度。
2. **短期 / 工作记忆**：本会话、本任务的完整状态（对话、工具返回、推理中间步骤、计划）。它可以比窗口大，一部分放在外部 State 里，每轮选择性放进窗口。
3. **长期记忆**：持久化到数据库、向量库或文件，跨会话、跨任务可用，需要时检索加载进短期记忆。

| 维度 | 短期记忆（工作记忆） | 长期记忆 |
| --- | --- | --- |
| 存储位置 | 上下文、会话 State、checkpoint | 关系库、KV、向量库、文件 |
| 生命周期 | 绑定会话 / 任务，结束后清空或按 TTL 保留 | 跨会话保留，可设置过期和删除 |
| 读取方式 | 直接送入 LLM，无检索开销 | 检索、过滤、摘要后再注入 |
| 容量限制 | 受上下文窗口约束 | 只受存储限制，但召回质量会随规模下降 |
| 写入成本 | 追加消息即可 | 需要抽取、向量化、去重、入库 |
| 典型作用 | 支撑本次任务的连贯推理 | 个性化、跨会话连续性、经验复用 |
### 什么是情景记忆、语义记忆和程序记忆？在 Agent 中分别存什么？
这三个概念来自认知心理学的长期记忆分类，Agent 领域常引用 CoALA 框架（2023）的划分，LangGraph 的 LangMem SDK 也按这三类组织。区分方法：情景是"发生过什么"，语义是"知道什么"，程序是"怎么做"。

| 类型 | 定义 | Agent 中存什么 | 常见用法 |
| --- | --- | --- | --- |
| 情景记忆 Episodic | 带时间和场景的具体事件 | 历史对话、任务执行轨迹、某次成功或失败的完整案例 | 向量检索召回相似案例，作为 few-shot 或经验参考 |
| 语义记忆 Semantic | 脱离具体场景的事实和知识 | 用户画像（姓名、偏好、技术栈）、业务规则、领域知识 | 结构化 profile 精确读取，或事实集合语义检索 |
| 程序记忆 Procedural | 做事的方法和流程 | System Prompt 中的规则、Skill、工具调用模板、排错步骤 | 更新它等于改 Prompt / Skill，影响之后所有任务 |

例如"用户是 Java 后端，只用 Spring Boot 3"是语义记忆；"上周帮用户排查过一次连接池泄漏，最后是没关 ResultSet"是情景记忆；"排查连接泄漏先看活跃连接数，再 dump 线程栈"沉淀成步骤后就是程序记忆。

### 常见的记忆模块有哪些？ | 高频
按实现方式，常见四类：

1. **短期记忆（Short-term）**：保存最近对话和当前推理过程，本质依赖上下文窗口，容量有限，超出后早期信息被丢弃或压缩。
2. **长期记忆（Long-term）**：借助外部存储（数据库、向量库）持久化历史交互、用户信息和经验，特点是可持久化、可检索，支持跨会话复用。
3. **混合记忆（Hybrid）**：当前上下文 + 检索到的长期记忆一起进入 Prompt，兼顾当前连贯性和历史信息，是生产系统最常见的形态。
4. **摘要记忆（Summary）**：把旧对话提炼成关键事实、结论或阶段摘要来替代原始内容，减少 token 占用。

LangChain 早期的 `ConversationBufferMemory`、`ConversationBufferWindowMemory`、`ConversationSummaryMemory`、`VectorStoreRetrieverMemory` 分别对应全量、窗口、摘要、检索几种模式。LangChain 0.3 起这些类已被标记为弃用，推荐改用 LangGraph 的持久化机制（checkpointer + store）。

### RAG 算不算 Memory？Memory Agent 的主要风险是什么？ | 核心
Memory Agent 指会保存和检索历史信息、不只依赖当前对话窗口的 Agent。

![](<images/Java八股（后端)+Agent八股8-截屏2026-06-06 15.31.55.png>)

**RAG 与 Memory**：广义上 RAG 是一种检索型记忆，底层也常共用向量检索，但侧重点不同：

| | RAG | Memory |
| --- | --- | --- |
| 数据来源 | 预先导入的文档、知识库 | Agent 在交互中自己写入 |
| 读写 | 基本只读 | 读写都有，随交互演化 |
| 作用域 | 通常所有用户共享 | 按用户 / 会话隔离 |
| 目标 | 补充领域知识 | 个性化、历史状态、经验复用 |

**主要风险**
- 记错：抽取错误或把模型的推断当成事实写入。
- 记脏：网页、邮件等不可信内容中的指令被写进记忆，形成持久化的提示注入。
- 过期：旧偏好、旧状态没有更新，持续误导判断。
- 隐私：跨用户串数据、记住了不该记的敏感信息。
- 膨胀：记忆无限增长，召回噪声变大，效果反而下降。

## 短期与长期记忆的实现

### Agent 中的短期记忆和长期记忆分别怎么存储和实现？ | 高频
短期记忆跟随会话存储，按 `thread_id` / `session_id` 隔离；长期记忆独立持久化，按 `user_id` / `namespace` 组织。
**短期记忆**
- 内容：消息列表、工具调用和结果、当前计划 / TodoList、中间变量。
- 载体：进程内 State（开发测试）；生产用 checkpoint 持久化到 Postgres、Redis 等，支持服务重启后恢复和多实例共享。
- 生命周期：会话结束后清空，或按 TTL 保留一段时间。
- 每轮调用前通过裁剪 / 摘要控制进入窗口的部分。

**长期记忆**
- 结构化事实与偏好：MySQL / Postgres 存 profile，Redis 做热缓存，精确读取。
- 非结构化经验和历史事件：向量库（Milvus、pgvector、Chroma 等）+ 元数据过滤，语义召回。
- 关系密集的知识：图数据库或知识图谱（如 Zep 的 Graphiti、Mem0 的图模式）。
- 文件型记忆：Markdown 文件也是一种长期记忆，例如 Claude Code 的 `CLAUDE.md`、Anthropic API 的 memory tool（2025 年 9 月发布的 beta，模型通过工具读写 `/memories` 目录，存储由应用端实现）。
- 现成方案：LangGraph Store、LangMem、Mem0、Letta（原 MemGPT）、Zep。

**数据流**：用户输入 → 读取会话状态 + 按 query 检索长期记忆 → 组装 Prompt → 推理和工具调用 → 更新会话状态 → 抽取值得长期保存的信息，异步写回长期记忆。

### 为什么不能把所有历史消息都直接塞进 Prompt？
因为窗口有限、成本线性增长、延迟变高，而且无关历史会拉低模型效果。

1. **窗口上限**：即使是 1M token 的窗口，长期运行的 Agent 也会写满。
2. **成本**：每次调用都要为全部输入 token 付费，多轮下来是累加的。Prompt Cache 能降低重复前缀的价格，但不能消除。
3. **延迟**：首 token 延迟随输入长度增加。
4. **效果**：长上下文中间位置的信息容易被忽略（Lost in the Middle，2023），无关和矛盾内容会干扰判断，即 Context Rot。
5. **安全与隐私**：历史里可能有过期指令、提示注入或不该再暴露的敏感数据。

更合理的做法：最近几轮保留原始内容，早期内容压成摘要，关键事实抽成结构化字段，完整记录存外部，按需检索注入。

### LangGraph 中 Checkpointer 和 Store 有什么区别？
Checkpointer 记住"这个线程执行到哪里、当前状态是什么"（短期记忆）；Store 记住"跨线程以后仍可能有用的知识"（长期记忆）。两者通常一起使用。

| | Checkpointer | Store |
| --- | --- | --- |
| 保存对象 | 每个 super-step 后的 Graph State 快照 | 应用自定义的 JSON 文档（key-value） |
| 作用域 | 单个 `thread_id` | 跨 thread，按 namespace 元组组织，如 `(user_id, "memories")` |
| 典型内容 | messages、当前节点、中断状态、节点输出 | 用户偏好、事实、经验、共享知识 |
| 写入方式 | 图执行时自动保存 | 节点或工具里显式 `store.put()` |
| 读取方式 | `graph.get_state()`、`get_state_history()`，按 thread 恢复 | `store.get()`、`store.search()`（可配置 embedding 做语义检索） |
| 主要用途 | 多轮会话、断点续跑、Human-in-the-loop、time travel、容错 | 个性化、跨会话长期记忆 |
| 实现 | `InMemorySaver`、`PostgresSaver`、`SqliteSaver`、Redis / MongoDB 等 | `InMemoryStore`、`PostgresStore`、Redis 等 |

```python
graph = builder.compile(checkpointer=PostgresSaver(conn), store=PostgresStore(conn))
graph.invoke(inputs, config={"configurable": {"thread_id": "t-1", "user_id": "u-1"}})
```

注意：`interrupt()` 实现的人工审批依赖 checkpointer，没有 checkpointer 时无法暂停后恢复。

### TodoList 与 Agent 的短期记忆有什么关系？ | 扩展
TodoList 是短期记忆里面向执行的一部分，属于工作记忆。

- 对话历史、Observation 记录"已经发生了什么"；TodoList 组织"接下来要做什么、做到哪了"。
- 它把隐含在长对话里的计划显式化，长任务中模型不容易忘记目标和遗漏步骤。
- 实现上通常是一个工具（如 Claude Code 的 TodoWrite），模型主动更新条目状态（pending / in_progress / completed），Harness 把最新列表放在上下文中显著的位置，靠近末尾的位置注意力更强。
- 上下文压缩时 TodoList 属于必须保留的状态，也可以写到文件里，压缩或重置后再读回来。

## 记忆写入、更新与治理

### 工具调用的结果属于短期记忆还是长期记忆？
默认属于短期工作记忆，只服务当前任务，不会自动进入长期记忆。

- 原始结果往往体积大、时效性强，比如日志、查询结果、网页正文，长期保存价值低。
- 只有经过筛选、确认有复用价值的结论才写入长期记忆，例如"某接口必须带 X-Tenant 头"或某次排错的根因。写入的是提炼后的结论，不是原始输出。
- 在短期记忆里，旧的工具结果也是最先被清理的对象（见上下文管理部分）。

### 用户偏好应该存在哪一层？为什么不适合只放在向量库里？
用户偏好属于长期语义记忆，优先用结构化 profile（关系库 / KV，Redis 做热缓存）存储，会话开始时整体加载进上下文。

不适合只靠向量库的原因：
1. **偏好是确定性键值**：回复语言、输出格式、技术栈、禁用项都是 key-value，需要精确读取，不需要模糊匹配。
2. **召回不确定**：相似度检索可能漏掉关键偏好，或召回无关条目。"必须遵守的配置"不能依赖 Top-K 是否命中。
3. **更新困难**：偏好会变（"我搬到上海了"），结构化字段可以直接覆盖或带版本更新；向量库里新旧两条相似文本会同时被召回，形成冲突。
4. **性能**：profile 体积小、读取频繁，KV 查询比 embedding + ANN 检索快且便宜。

向量库适合存数量多、表述多样、需要按语义召回的内容，比如历史事件和经验案例。实践中常组合：profile 结构化常驻上下文，长尾细节进向量库。
### Agent 应该在什么时候写入记忆？如何判断信息是否值得记？
值得记的信息是稳定、跨任务可复用、未来会影响行为的信息；一次性细节不记。

**写入时机**
1. 用户明确要求："以后回复简短一点"、"记住我用 Go"。
2. 出现稳定事实：身份、偏好、长期项目约束、组织术语。
3. 任务结束产生可复用经验：如"这个系统上传 CSV 前必须先转 UTF-8"，属于情景 / 程序记忆。
4. 旧记忆被更新、纠正或证伪：执行替换（supersede）、撤回（retract）或重新验证，而不是再追加一条。

**两种写入方式**
- 热路径（in the hot path）：对话中由 Agent 调用 `save_memory` 之类的工具即时写入，实时性好，但增加延迟，也要靠模型自己判断。
- 后台（background）：会话结束或空闲时由独立流程批量抽取、去重、合并，不影响响应速度，质量更可控。LangMem 两种都支持。

**价值判断**：可以从稳定性、复用概率、影响范围、来源可信度几个维度打分，低于阈值不写；推断出的信息标为低置信度，不当作事实。

### 如何设计长期记忆的写回策略、衰减策略和冲突消解？ | 高频
长期记忆要回答三个问题：什么值得写回、什么时候该忘、冲突怎么处理。

**写回策略**
- 只写高价值稳定信息：偏好、身份属性、长期目标、反复出现的业务事实。
- 结构化抽取：把"我更喜欢用 Python"写成 `preferred_language: Python`，而不是整段原始内容。
- 写前去重：与已有记忆做相似度比对，决定 ADD / UPDATE / DELETE / NONE（Mem0 的写入流程就是让 LLM 在这几种操作里选一种）。
- 每条记忆带来源、时间、置信度、适用范围。

**衰减策略**
- 给记忆打分，综合考虑时效、访问频率和重要性。Generative Agents（Stanford，2023）的检索打分就是 recency（指数衰减）+ importance + relevance 加权。
- 热点信息随时间降权；稳定偏好低频刷新，不轻易删除。
- 冷数据降权后不参与召回但仍保留（软删除），方便恢复和审计；低置信度记忆设置 TTL。

**冲突消解**
- 结合时间戳、来源可信度和置信度裁决：新的高可信事实替换旧事实，旧记录标记为失效而不是物理删除；低可信内容只作为候选。
- 带时间维度的事实存有效区间（如 Zep / Graphiti 的 bi-temporal 设计），可以回答"当时是什么"。
- 更严格的做法是事件流 + 物化视图：所有写入先存成不可变 Event，再异步聚合成 Profile，方便审计和回滚。
- 用户有权查看、修改、删除记忆，这也是合规要求。

### 多 Agent 系统中共享记忆怎么设计？如何避免读写冲突？
按作用域分层，按权限控制写入，用单写者、版本号或队列解决并发。

**分层**
| 层 | 内容 | 读写权限 |
| --- | --- | --- |
| 全局共享 | 公共知识、业务规则、已验证经验 | 所有 Agent 可读，仅管理流程可写 |
| 任务 / 组内共享 | 任务进度、产物引用、已确认事实 | 组内可读，由协调者统一写入 |
| 私有 | 单个 Agent 的草稿、临时推理 | 只有自己可读写 |

存储上，结构化状态放 Redis / 数据库，共享的情景和语义记忆放向量库，按 namespace 隔离分组和权限。

**防冲突**
1. 单一写入负责人：子 Agent 只提交结果，由 Supervisor / 协调者合并写入。这是最简单可靠的方式。
2. 乐观锁：每条记录带版本号，写入时 compare-and-set，冲突则重读后合并。
3. 分布式锁：Redis 锁串行化对同一 key 的写，注意设置过期和锁粒度。
4. 消息队列异步写入：记忆片段投递到 MQ，按 key 分区有序消费，也能削峰。
5. 追加而不覆盖：用 append-only 记录 + 读时合并，或 LangGraph State 的 reducer（如 `add_messages`）合并并行分支的输出。

另外，每条共享记忆要标明是事实还是推断、是否已确认，避免一个 Agent 的猜测被其他 Agent 当成事实。

## 上下文管理与压缩

### Agent 的上下文由哪些部分组成？如何确定优先级？
常见组成：
1. System / Developer 指令（角色、规则、工具使用规范）
2. 工具定义（schema 和描述）
3. 当前用户请求
4. 任务状态：目标、约束、计划、待办
5. 最近的会话历史
6. 长期记忆和检索内容
7. 工具结果、文件片段、环境信息

**两种优先级要分开**

指令冲突时按权限：
```text
System > Developer > 当前用户指令 > 较早的用户指令
```
工具输出、网页、文件和检索结果属于数据，不能覆盖上层指令。其中出现"忽略之前的规则"之类的文字也不能当成指令。

决定哪些内容留在窗口里时按价值：
```text
硬约束 > 当前目标 > 未完成事项 > 最新可靠状态 > 直接证据 > 背景信息
```
相关性、可靠性、时效性比出现顺序更重要。

**布局**：稳定内容（System Prompt、工具定义）放在前面，便于命中 Prompt Cache；易变内容放后面；关键目标和待办可以在末尾重复提醒。
### 记忆超出上下文窗口怎么办？滑动窗口、消息裁剪、摘要压缩和检索各适合什么场景？ | 高频
核心思路是选择性保留，不全量放入上下文。生产系统通常组合使用：最近几轮保留原始内容，旧对话变成摘要，关键事实结构化存储，完整记录放外部，需要时检索回来。

| 方法 | 做法 | 优点 | 缺点 | 适合场景 |
| --- | --- | --- | --- | --- |
| 滑动窗口 | 只保留最近 N 轮或最近 N 个 token | 实现简单、零额外调用、无摘要失真 | 早期但仍有效的约束和决定会丢 | 闲聊、客服、局部连续的短任务 |
| 消息裁剪 | 删除寒暄、重复内容、旧工具结果、调试噪声 | 成本低，损失小 | 按时间或长度粗暴裁剪可能误删依据 | 任何场景的第一步 |
| 摘要压缩 | LLM 把旧对话浓缩成摘要替换原始内容 | 保留因果和决策，同样窗口能承载更多历史 | 额外调用增加成本和延迟；会丢细节，多轮后漂移 | 长对话、跨阶段任务 |
| 检索式上下文 | 历史分块存向量库 / 数据库，按当前 query 召回 | 容量几乎无限，按需加载 | 检索不到就等于看不见，依赖索引和查询质量 | 大型知识库、长周期项目、稀疏访问的历史 |
| 结构化记忆 | 抽取目标、约束、偏好、已完成步骤成字段 | 精确、稳定、体积小 | 需要设计 schema 和抽取逻辑 | 关键状态和偏好 |

**实现注意**
- 裁剪时保持消息结构合法：tool_use 和对应的 tool_result 要成对保留或成对删除，否则 API 会报错。
- 摘要建议是累积式的（上一版摘要 + 新增对话一起重写），并保留 System Prompt、硬约束和当前任务状态不参与压缩。
- 摘要的输出要预留空间，不能等到窗口完全写满才压缩。

### 上下文压缩应该在什么时候触发？为什么不能等窗口快满再处理？
可以按多种信号触发，而不只看是否快满：
- token 用量达到某个比例（不同系统阈值不同，可以设成窗口的 50%–80%）
- 一个任务阶段结束，例如调研完成、开始实现
- 连续产生多份较大的工具结果
- 上下文出现重复、过期或互相矛盾的信息
- 模型开始忘记约束、重复工作、引用旧状态
- 成本和延迟明显上升

**为什么不能等快满**
1. 效果在达到硬上限之前就会下降，中间位置的信息尤其容易被忽略。
2. 生成摘要本身要消耗输入和输出 token，剩余空间太少时摘要质量差，甚至生成失败。
3. 一次大的工具返回或长输出可能直接超限导致请求失败。

Claude Code 的自动压缩也是在接近上限、仍预留出摘要和输出空间时触发，用户也可以在阶段切换时主动执行 `/compact`。

### 如何检测并减少多轮摘要带来的信息丢失、事实漂移和错误累积？
多轮"摘要的摘要"会逐渐丢失细节，还会把早期错误固化下来。控制方法：

- **保留原始记录**：原始对话和工具输出存在外部，摘要只是索引，不是唯一真相。
- **定期从原始内容重建**：每隔几个压缩周期从原始记录重新生成摘要，不要永远基于上一版继续压缩。
- **结构化摘要**：用固定字段（目标、约束、已完成、待办、关键决策、文件路径、关键数字）代替自由文本，便于逐字段对比。
- **压缩前后校验**：对比任务清单是否有事项消失、状态改变、或出现无来源的新事实。
- **证据绑定**：高风险事实附上原始来源位置，使用时重新读取。
- **不可变断言**：如"不得修改生产数据"、"输出必须是 JSON"，不参与压缩，每次调用前检查它们仍在上下文中。
- **版本化**：摘要记录版本、时间、覆盖的消息范围。发现冲突时回到原始内容核对，不让新摘要自行调和。
### 如何处理体积巨大的工具输出，避免它一直占用上下文？
原则：原始输出放外部，上下文里只留摘要和引用，需要时再按需读取。

1. 进入上下文前截断或提炼：限制单次返回的长度（如只保留首尾若干行），或让工具直接返回结构化的关键字段。
2. 原始内容落盘：保存到文件、对象存储或数据库，上下文里只放查询条件、结果摘要、相关片段和存储路径。
3. 附元数据：时间、版本、来源、内容哈希，便于判断是否过期。
4. 按需读取：后续按页、按行号区间、按关键词（grep）读取需要的部分。
5. 及时清理：旧的工具结果在后续轮次中替换为占位符（如"[已清除，见 xxx]"），新结果产生后移除失效的旧结果。

例如十万行日志可以压缩为：错误类型、首次出现位置、出现次数、相关时间段和原始文件路径。Agent 继续调查时再读对应区间。

Claude Code 对超大工具结果的处理就是写入磁盘、上下文只保留预览和路径；Anthropic API 2025 年 9 月推出的 context editing（beta）也可以在上下文变长时自动清除较早的工具调用结果。

### 什么是 Context Rot？如何缓解？
Context Rot 指上下文变长后模型表现逐渐下降，而且在达到窗口上限之前就会发生。Chroma 在 2025 年 7 月发布的同名研究测试了多个主流模型，发现输入越长性能越差，与干扰项多少、信息位置都有关系。原因主要不是装不下，而是有效信息被噪声、旧状态、重复内容和矛盾信息稀释，模型会抓错证据、忽略早期约束、按失效的计划继续行动。

**缓解方法**
- 相关性过滤：只保留对当前步骤直接有用的内容。
- 按需检索（just-in-time）：上下文里放引用（文件路径、查询语句），需要时再用工具加载，而不是预先全部塞入。
- 上下文隔离：调研、编码、测试分给不同的子 Agent 或会话，主 Agent 只接收结论。
- 生命周期管理：工具结果和临时记忆设有效期，过期清理。
- 冲突处理：同一事实有多个版本时显式标明当前有效版本。
- 阶段切换：一个阶段完成后写下进度笔记，用干净的上下文开始下一阶段。
- 结构化笔记：把进度和决策写到外部文件（如 `NOTES.md`、TodoList），不依赖聊天历史。

Anthropic 在 2025 年 9 月的文章 *Effective context engineering for AI agents* 里把长任务的对策归纳为三类：compaction（压缩）、structured note-taking（结构化笔记）、sub-agent 架构。

### 工程上的上下文压缩一般怎么分层做？
原则是先做便宜、低损耗的处理，最后才用重型摘要。从轻到重：

1. **工具结果瘦身**：超大输出落盘，上下文只留预览和路径。
2. **清理旧工具结果**：较早的工具调用结果替换为占位符，保留调用记录本身。成本低，信息损失小，因为需要时可以重新调用工具。
3. **裁剪噪声消息**：去掉重复、寒暄、失败的中间尝试。
4. **摘要压缩**：对较早的历史生成结构化摘要（目标、决策、文件状态、待办、用户偏好），替换原始内容，保留最近几轮原始内容。
5. **全量压缩 / 重置**：接近上限时把整段历史压缩成一份摘要作为新的起点，或者写好进度文件后开一个新会话（context reset）。

**受保护内容**：System Prompt、用户明确给出的硬约束、当前任务状态和 TodoList 在任何压缩步骤里都不删除。

**和 Prompt Cache 的关系**：缓存按前缀匹配，修改或删除前面的消息会让之后的缓存失效。所以压缩不宜过于频繁，最好一次释放较多空间；清理工具结果时尽量从较早的位置成批进行。

Claude Code 的具体实现见 Harness 部分的相关题目。

### 上下文窗口越来越大时，会带来哪些性能和成本问题？怎么优化？
**问题**
1. 成本：输入 token 越多，每次调用费用越高；Agent 多轮调用，成本是累加的。
2. 延迟：预填充时间随输入长度增加，首 token 变慢。
3. 注意力分散：无关信息越多，模型越难抓重点（Context Rot、Lost in the Middle）。
4. 稳定性：长上下文中更容易出现冲突信息，导致判断错误。
5. 超长定价：部分模型对超过一定长度的输入按更高单价计费，例如 Claude Sonnet 4 / 4.5 的 1M 上下文（beta）在输入超过 200K token 时整体按更高费率计价。

**优化**
1. 上下文裁剪：只保留最近和最相关的信息，旧工具结果及时清理。
2. 历史摘要：长对话压缩成结构化摘要。
3. RAG / 按需检索：只召回相关片段。
4. Prompt Caching：稳定前缀（System Prompt、工具定义、长文档）放在最前面并开启缓存。Anthropic 的缓存读取价格约为基础输入价的 10%，OpenAI 对达到长度门槛的提示词自动缓存。
5. 结果缓存：相同请求或中间结果复用，避免重复调用。
6. 模型分层：路由、摘要、分类等简单任务用小模型，复杂推理再用大模型。
7. 工具结果压缩：只返回关键字段和结论。
8. 子 Agent 隔离：探索性任务在子上下文里完成，主上下文只接收结论。

核心原则：上下文不是越长越好，而是相关信息越精准越好。

### Skills 能直接全部塞进 System Prompt 吗？ | 高频
不应该全部塞进去。Skill 数量多时会占满窗口，而且无关描述是噪声，会降低模型选对 Skill 的准确率。正确做法是注册表 + 按需加载（渐进式披露，progressive disclosure）。

**Anthropic Agent Skills 的做法（2025 年 10 月发布，同年 12 月作为开放标准发布）**
- 每个 Skill 是一个目录，核心是带 YAML frontmatter（`name`、`description`）的 `SKILL.md`，可附带脚本和参考文件。
- 第一层：启动时只把每个 Skill 的 name 和 description 放进上下文，每个只有几十个 token。
- 第二层：模型判断任务相关时才读取完整的 `SKILL.md`。
- 第三层：`SKILL.md` 里引用的其他文件、脚本，执行到需要时再读或直接运行，脚本代码本身不必进入上下文。

**通用工程做法**
- System Prompt 只保留最小规则和调用协议，Skill 放在外部注册表。
- Skill 很多时先做路由：用规则、分类模型或向量检索筛出 Top-K，再注入它们的说明、参数 schema 和示例。
- 长 Skill 拆成摘要版和完整版，先让模型凭摘要决定是否使用，确定后再加载完整版。

工具定义也有同样的问题。MCP 工具很多时，Claude Code 等客户端会延迟加载工具 schema，先只给名字，需要时再通过工具搜索拉取完整定义。

## Vibe Coding

### Vibe Coding 是什么？核心理念是什么？
Vibe Coding 由 Andrej Karpathy（OpenAI 联合创始人、前 Tesla AI 负责人）在 2025 年 2 月的一条推文中提出：完全顺着感觉走，用自然语言描述需求，接受 AI 生成的改动，基本不去读代码，出了错就把报错贴回去让 AI 修。这个词后来被 Collins 词典选为 2025 年度词汇。

**原始含义和边界**
- Karpathy 的原意是用于一次性的周末小项目，"忘掉代码的存在"。
- 现在常被泛指所有"用自然语言驱动 AI 写代码"的开发方式。面试中要区分两种：
  - 狭义 Vibe Coding：不审查代码，只看运行效果，适合原型、Demo、个人工具。
  - 工程化的 AI 辅助开发（也称 agentic coding）：人仍然对代码负责，通过明确的约束、测试和 Review 保证质量，适合生产代码。

**核心理念**
- 角色转变：开发者从逐行写代码，转为描述需求、设计约束、验收结果、把关架构。
- 快速反馈：描述 → 生成 → 运行 → 反馈，小步迭代，从最小可运行版本开始。
- 低成本试错：让 AI 快速生成多种实现来比较，重复性工作交给 AI，人专注于判断和决策。
- 结果导向：以"能跑通、符合预期"为主要验收标准，所以必须有可执行的验证手段（测试、运行截图、日志），否则质量没有保障。

### Vibe Coding 的典型工作流程是什么？
主线是"描述 → 生成 → 运行验证 → 反馈迭代"的循环，工程化之后一般是：

1. **描述需求**：用自然语言说清目标、用户场景和期望效果；复杂需求先让 AI 澄清问题或写成需求文档。
2. **探索与规划**：让 Agent 先读代码库、理解现有结构，再出实现方案（如 Claude Code 的 Plan Mode），人确认方案后再动手。
3. **生成初始骨架**：目录、核心文件、依赖配置，先跑起来，判断方向是否正确。
4. **迭代开发**：在可运行的基础上逐步加功能，每一步运行测试或查看效果，用具体的反馈（哪个文件、哪个行为不对、违反了哪条约束）修正。
5. **精修**：针对边界情况、界面细节、性能做定向优化。
6. **审查与提交**：看 diff、跑完整测试，按需提交。
7. **沉淀上下文**：把关键决策、约定、常用命令写进 `CLAUDE.md` / `AGENTS.md` 或文档，下一次会话直接复用。

### 平时怎么用 AI coding？
回答时可以按任务规模分两类场景讲清楚，并强调验证和人的把关。

**对话式（网页端 / IDE 聊天）**：单文件、单函数、单次交互的小任务，比如写正则、解释报错、给函数补单测、解释陌生代码。快、零配置，但不能理解项目结构，也不能执行和多步迭代。

**Agent 式（Claude Code、Codex、Cursor Agent）**：跨文件的功能开发、重构、排查问题。
1. 先让 Agent 读目录结构和关键配置，或者维护好 `CLAUDE.md`，让它知道技术栈、构建和测试命令。
2. 需求描述具体：技术栈、涉及的文件、接口格式、边界条件、错误处理和验收标准。
3. 复杂任务先进 Plan Mode 出方案，确认后再执行；拆成小步，每步跑测试、看 `git diff`。
4. 方向跑偏时不硬纠，而是回退（`/rewind` 或 git）或 `/clear` 后重新描述当前状态和期望。
5. 独立的调研、测试、审查交给 subagent，主会话保持干净。
6. 用 Hooks 自动跑格式化和测试，用权限规则限制危险命令。

人负责架构决策和最终兜底，所有生成代码都要过 Review，重点看逻辑正确性、边界处理和安全问题。

### CLI 和 IDE 中的 Vibe Coding 有什么区别？
CLI 偏任务执行和自动化，IDE 偏代码编辑和即时辅助。

| 维度 | CLI（Claude Code、Codex CLI） | IDE（Cursor、Copilot、各类插件） |
| --- | --- | --- |
| 交互方式 | 终端对话，Agent 自主读文件、改代码、跑命令 | 结合当前文件、光标、选区，补全、内联编辑和侧边栏 Agent |
| 擅长 | 多步长任务：修一批测试、迁移、批量重构、分析日志 | 写代码过程中的即时协作：补全、局部修改、解释代码 |
| 上下文获取 | Agent 用 grep / glob 等工具按需搜索 | 编辑器状态 + 代码库索引（如 Cursor 的 embedding 索引） |
| 自动化 | 容易脚本化，可以在 CI 里无头运行（如 `claude -p`） | 主要是交互式使用 |
| 风险 | 能执行任意命令，更依赖权限控制、沙箱和审批 | 主要集中在文件修改上 |
| 审查改动 | 看终端里的 diff 或 git | 编辑器内的可视化 diff，逐块接受 |

两者在融合：Claude Code 有 VS Code / JetBrains 扩展和桌面端，Cursor 也有 CLI 和云端 Agent。选型看任务形态：明确目标的长任务用 CLI，边写边改用 IDE。
## 编码 Agent 工具对比

### Claude Code 是什么？有什么特点？
Claude Code 是 Anthropic 的 agentic coding 工具，2025 年 2 月随 Claude 3.7 Sonnet 以研究预览发布，2025 年 5 月随 Claude 4 正式可用。它主要运行在终端，也提供 VS Code / JetBrains 扩展、桌面端和网页版；底层能力以 Claude Agent SDK（2025 年 9 月由 Claude Code SDK 更名）的形式开放。

它不是单纯的代码生成器，而是把 Claude 放进一个带工具、权限和执行流程的运行环境（harness）里，在本地直接读代码、改文件、跑命令和测试、操作 git、创建 PR。

**主要特点**
- **Agentic search**：不预建向量索引，用 Glob、Grep、Read 等工具按需搜索代码库。
- **细粒度工具**：Read、Edit、Write、Bash、WebFetch、TodoWrite、Task（启动子 Agent）等；工具选择本身表达意图（Edit 局部修改、Write 全量写入），权限可按工具控制。
- **权限与 Hooks**：allow / ask / deny 规则 + 权限模式，可选 Bash 沙箱；Hooks 在生命周期事件上执行确定性脚本。
- **项目记忆与长任务**：`CLAUDE.md` 分层加载规则；自动压缩上下文、任务清单、Checkpoints 回滚、Subagents 隔离上下文。
- **扩展**：MCP Server、Skills（2025 年 10 月）、斜杠命令、Plugins 和插件市场（2025 年 10 月）。
- **无头模式**：`claude -p` 输出文本或 JSON，接入脚本和 CI，有官方 GitHub Actions。

整体可概括为五层：工具层 → 权限层 → Hooks 层 → 上下文管理层 → 项目知识层（`CLAUDE.md`、Skills）。

### Claude Code 源码里体现了哪些设计理念？
核心是一个简单的 Agent 循环：模型思考 → 调用工具 → 观察结果 → 再思考，直到模型不再请求工具。Anthropic 一直强调"保持简单"：一个主循环、一份扁平的消息历史，复杂度放在工具、权限和上下文管理上，而不是复杂的多 Agent 编排。

2026 年 3 月 Claude Code 的 npm 包误带了 source map，源码因此流出，社区分析后总结出的几个设计点：

- **单线程主循环**：每轮先做上下文检查和压缩，再调用模型；模型返回的工具调用被解析、校验、执行，结果作为 tool_result 追加到历史，进入下一轮。
- **按并发安全性调度工具**：只读工具（Read、Glob、Grep）可以并行执行，写类工具（Edit、Write、Bash）串行执行，避免竞态。
- **确定性优先的权限链**：一次工具调用大致经过 输入校验 → PreToolUse Hooks → 权限规则（deny / ask / allow）→ 工具自身的权限检查 → 权限模式决策（询问用户或自动放行）。前几关都是硬逻辑，不依赖模型判断。整类被 deny 的工具不会出现在发给模型的工具列表里，模型根本不知道它存在，也就无法被提示注入诱导调用。
- **从便宜到昂贵的上下文管理**：先清理旧工具结果，再做摘要压缩，尽量保护 Prompt Cache 前缀。
- **子 Agent 隔离**：子任务在独立上下文中执行，只把结论返回主循环；子 Agent 尽量复用父 Agent 的 System Prompt 和工具定义以命中 Prompt Cache。
- **模型可见的待办**：TodoWrite 让计划显式化，减少长任务中的目标遗忘。

### Cursor 是什么？有什么特点？
Cursor 是 Anysphere 公司基于 VS Code 分支开发的 AI 代码编辑器，定位是以 AI 为核心的开发环境，而不是普通的补全插件。

- **Tab 补全**：自研模型做多行补全和"下一处修改"预测，这是它最早建立口碑的功能。
- **代码库索引**：对仓库做 embedding 索引，支持语义检索和 `@` 引用文件、文档、符号。
- **Agent 模式**：在编辑器里自主多步执行修改、跑终端命令，改动以 diff 形式供逐块接受。
- **规则**：`.cursor/rules/` 下的规则文件（可按路径匹配生效），也支持读取 `AGENTS.md`。
- **多入口**：2025 年 8 月推出 Cursor CLI，还有在云端运行的后台 / 云端 Agent。
- **模型**：可切换 Claude、GPT、Gemini 等第三方模型，2025 年 10 月的 Cursor 2.0 推出了自研编码模型 Composer。
- **扩展**：支持 MCP、Hooks 等，生态在从"AI 编辑器"走向"AI 开发平台"。

### Claude Code 和 Cursor 各有哪些优势？
核心区别：Claude Code 是终端优先的自主执行 Agent，强在长任务闭环和工程化约束；Cursor 是 IDE 优先的 AI 编辑器，强在编辑体验和人机实时协作。

| 维度 | Claude Code | Cursor |
| --- | --- | --- |
| 形态 | 终端 CLI 为主，另有 IDE 扩展、桌面和网页 | VS Code 分支的编辑器，另有 CLI |
| 代码理解 | Agent 按需 grep / glob 搜索 | embedding 索引 + 编辑器上下文 |
| 强项 | 跨文件长任务、自动跑测试修复、脚本化 / CI、子 Agent 并行 | Tab 补全、内联编辑、可视化 diff 审查 |
| 可控性 | 权限规则、Hooks、沙箱、Plan Mode、Checkpoints | 规则文件、审批、Hooks |
| 模型 | Claude 系列 | 多厂商模型可切换，另有自研 Composer |
| 适合人群 | 习惯终端、让 Agent 跑完整流程 | 习惯 IDE、希望边写边协作 |

两者能力在快速趋同（都有 MCP、Hooks、子 Agent、规则文件），实际选择更多取决于工作习惯和任务形态，也常常组合使用。

### Codex 和 Claude Code 各有什么优势？
两者都是终端优先的编码 Agent，差异主要在模型、运行环境和安全默认值上，没有一方全面领先。

**OpenAI Codex**
- 产品形态：开源的 Codex CLI（2025 年 4 月发布，后来用 Rust 重写）、云端 Codex（2025 年 5 月，任务在云端容器里并行运行，完成后提交 PR）、IDE 扩展。
- 模型：GPT-5 系列及针对编码优化的 Codex 专用模型（如 2025 年 9 月的 GPT-5-Codex）。
- 安全默认：CLI 默认在操作系统级沙箱中运行（macOS Seatbelt、Linux Landlock + seccomp），沙箱模式分 `read-only`、`workspace-write`、`danger-full-access`，`workspace-write` 默认禁止联网；审批策略可单独配置。
- 项目规则读 `AGENTS.md`。
- 订阅额度相对宽松，适合大量批量任务和后台并行。

**Claude Code**
- 模型：Claude Sonnet / Opus 系列，默认 200K 上下文，部分模型提供 1M 上下文（beta）。
- 工程化扩展更丰富：Hooks、Subagents、Skills、Plugins、Checkpoints、细粒度权限规则。Bash 沙箱是可选开启的（`/sandbox`），默认依靠逐次审批。
- 项目规则读 `CLAUDE.md`。

**澄清两个常见误区**
- 两者都不会把整个仓库塞进上下文，都是靠工具按需搜索读取。大上下文能减少压缩次数，但并不等于"读懂全量项目"。
- 准确性、幻觉多少、速度、token 成本随模型版本变化很快，不宜用固定结论回答。更好的说法是用自己的任务集做评估（见下一题）。

### 如何评估 Codex 和 Claude Code 的效果、成本、速度和完成质量？
不要靠一次演示或主观印象，而是建立一组来自真实工作的固定任务，在尽量相同的条件下运行。

**任务集**：小 bug 修复、跨文件功能开发、补测试、重构、陌生仓库调研、安全修复。每个任务固定代码版本、验收测试、权限、工具、时间上限和提示词。公开基准可以参考 SWE-bench Verified、Terminal-Bench，但要以自己的仓库为准。

| 维度 | 可记录的指标 |
| --- | --- |
| 效果 | 测试通过率、需求覆盖率、引入的回归数、人工审查评分 |
| 完成质量 | 首次成功率、返工次数、遗漏需求、无关改动、安全问题 |
| 速度 | 首个可用补丁的时间、总耗时、人工审查和修复时间 |
| 成本 | 模型费用、计算费用、重试成本、人工介入时间 |
| 自主性 | 需要澄清、审批和人工接管的次数 |
| 可维护性 | diff 大小、复杂度变化、新增依赖、代码风格和文档 |

**注意点**
- 模型输出有波动，同一任务多跑几次，看均值和方差。
- 盲评：审查者不知道结果来自哪个工具。
- 成本看"每个最终被接受的任务的总成本"，包括失败重试和人工修复，而不只是 token 单价。
- 结论通常不是谁全面胜出，而是哪个工具更适合哪类仓库、任务和权限环境。
## Claude Code 核心机制

### CLAUDE.md 在 Claude Code 中有什么作用？如何分层？
`CLAUDE.md` 是 Claude Code 的持久化项目记忆：启动时自动加载进上下文，让 Agent 每次会话都知道项目规则，不用在 Prompt 里重复说明。它是普通的 Markdown，作为上下文提供给模型，属于"建议"而不是强制约束，需要强制执行的规则应该用 Hooks 或权限配置实现。

**加载位置**（按官方文档，从通用到具体）
| 层级 | 位置 | 用途 |
| --- | --- | --- |
| 企业策略 | 系统级目录（如 macOS 的 `/Library/Application Support/ClaudeCode/CLAUDE.md`） | 组织统一下发的规范 |
| 用户级 | `~/.claude/CLAUDE.md` | 个人在所有项目里的偏好 |
| 项目级 | `./CLAUDE.md` 或 `./.claude/CLAUDE.md` | 团队共享，提交到 git |
| 本地项目级 | `./CLAUDE.local.md` | 个人的项目内偏好，不提交 |

- 启动时从当前目录向上递归查找并加载各级 `CLAUDE.md`；子目录里的 `CLAUDE.md` 在 Agent 读取该子目录的文件时才按需加载。
- 多份同时生效，越具体的规则在冲突时优先级越高。
- 支持 `@path/to/file` 语法导入其他文件。
- `/init` 根据代码库自动生成初始版本，`/memory` 打开编辑。
- 压缩上下文后 `CLAUDE.md` 仍然保留，因为它不属于会被摘要的对话历史。

**写什么**
- 构建、测试、lint 命令
- 代码风格和必须遵守的约定
- 目录结构中容易误改的关键位置
- 无法从代码推断的业务约束和注意事项
- 团队的工作流约定（分支、提交规范）

**最佳实践**：少而精，经常修订。不要写成知识库，不要重复模型自己能搜到的信息。规则太多会稀释注意力，反而降低遵循度。长内容可以拆到单独文件，用导入或 Skills 按需加载。

### AGENTS.md 和 CLAUDE.md 有什么区别？
两者作用相同：给编码 Agent 的项目说明文件，相当于"写给 Agent 看的 README"。区别在于标准化程度和支持的工具。

| | AGENTS.md | CLAUDE.md |
| --- | --- | --- |
| 性质 | 跨工具的开放约定 | Claude Code 专用 |
| 来源 | OpenAI Codex 首先使用，2025 年 8 月由 OpenAI、Google、Cursor、Factory、Sourcegraph 等联合推广；2025 年 12 月捐给 Linux Foundation 下的 Agentic AI Foundation | Anthropic 随 Claude Code 推出 |
| 支持的工具 | Codex、Cursor、GitHub Copilot、Gemini CLI、Jules、Amp、Windsurf 等 | Claude Code |
| 格式 | 纯 Markdown，没有强制结构 | Markdown，支持 `@` 导入 |
| 分层 | 最近目录的 `AGENTS.md` 优先，适合 monorepo 的子项目 | 用户级、项目级、本地级、子目录多层合并 |

两者的内容不存在本质差异，都是构建命令、代码规范、测试要求、注意事项。差别只在于哪个工具会读。

**同时使用多个工具时**：维护一份 `AGENTS.md` 作为唯一来源，在 `CLAUDE.md` 里写 `@AGENTS.md` 导入，或者建软链接，避免两份规则不同步。截至 2025 年底，Claude Code 官方文档仍以 `CLAUDE.md` 为准，不会自动读取 `AGENTS.md`。

### Hooks 机制有什么作用？有哪些类型？
Hooks 是在 Claude Code 生命周期的特定事件上自动执行的用户自定义逻辑（通常是 shell 命令），2025 年 6 月推出。它的价值在于把"希望模型做到"变成"一定会执行"：Prompt 里写"改完记得跑格式化"是概率性的，Hook 是确定性的。这正是 Harness Engineering 的典型做法。

**主要事件**
| 事件 | 时机 | 典型用途 |
| --- | --- | --- |
| PreToolUse | 工具调用执行前 | 拦截危险命令、保护敏感路径、修改参数、审计 |
| PostToolUse | 工具调用成功后 | 自动格式化、lint、跑相关测试，把结果反馈给 Claude |
| UserPromptSubmit | 用户提交 Prompt 后、模型处理前 | 注入额外上下文、拦截含敏感信息的输入 |
| Stop | 主 Agent 准备结束回答时 | 检查测试是否通过，没通过就阻止结束，让它继续修 |
| SubagentStop | 子 Agent 结束时 | 校验子任务产物 |
| PreCompact | 压缩上下文之前 | 备份完整记录、保存关键信息 |
| SessionStart / SessionEnd | 会话开始 / 结束 | 加载开发上下文（如最近的 issue）、清理和统计 |
| Notification | Claude Code 发出通知时（如等待权限确认） | 桌面提醒、发到 IM |

**配置与控制**
```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "./scripts/check-bash.sh" }] }
    ]
  }
}
```
- 写在用户级或项目级 settings.json，也可由插件提供；`matcher` 按工具名匹配（支持正则）。
- Hook 通过 stdin 收到 JSON 事件信息（工具名、参数、会话 ID 等）。
- 退出码 0 成功；退出码 2 阻断，stderr 反馈给 Claude（PreToolUse 中阻止调用，Stop 中阻止结束）；其他退出码是非阻断错误。
- 也可输出 JSON 精细控制，如 PreToolUse 返回 `allow` / `deny` / `ask` 或修改工具参数；除 shell 命令外还支持 prompt 类型 Hook。

**安全提醒**：Hook 以当前用户权限执行任意命令，引入第三方或仓库里的 Hook 配置前要先审查。
### Claude Code 有哪些交互模式和权限模式？如何选择？
权限模式决定 Agent 执行操作前是否需要确认，交互中按 Shift+Tab 在 default → acceptEdits → plan 之间循环切换，也可以在启动参数（`--permission-mode`）或 settings.json 的 `defaultMode` 里设置。

| 模式 | 行为 | 适合场景 |
| --- | --- | --- |
| default（默认） | 读操作直接执行；首次编辑文件、执行未授权的命令时询问用户 | 日常开发、不熟悉的仓库 |
| acceptEdits（自动接受编辑） | 文件编辑自动通过，Bash 命令等仍按规则询问 | 范围明确的批量修改，配合 git 随时回退 |
| plan（规划模式） | 只能读和分析，不能修改文件或执行有副作用的命令；输出方案，用户批准后再执行 | 复杂任务、高风险变更、第一次接触的项目 |
| bypassPermissions | 跳过所有权限确认（`--dangerously-skip-permissions`） | 只应在隔离的容器或虚拟机里使用 |

**权限规则**：settings.json 的 `permissions` 里配置 `allow` / `ask` / `deny`，如 `Bash(npm run test:*)`、`Read(./.env)`；deny 优先级最高，其次 ask，再是 allow。配置分企业策略、用户、项目、本地多层，企业策略无法被下层覆盖。

**沙箱**：2025 年 10 月起 Bash 支持可选沙箱（`/sandbox`），基于 macOS Seatbelt 和 Linux bubblewrap 做文件系统和网络隔离，沙箱内命令可少弹确认。

**运行方式**：交互式 `claude`；无头模式 `claude -p "..."`，支持 `--output-format json`，用于脚本和 CI；`claude -c` / `-r` 恢复会话。

**选择建议**：简单任务用 default；低风险批量改动用 acceptEdits；复杂或陌生的任务先用 plan 出方案；无人值守的自动化用无头模式加严格的 allow / deny 规则和沙箱，而不是直接 bypass。

### Claude Code 的 Checkpoints 机制有什么作用？
Checkpoints 是 Claude Code 2.0（2025 年 9 月）引入的回退能力：Claude 编辑文件前会自动保存代码状态，每次用户提交 Prompt 都形成一个可以回到的节点，出问题时能撤回到之前的状态。

**使用方式**
- 按两次 Esc 或输入 `/rewind` 打开回退菜单，选择要回到的节点。
- 可以选择只恢复代码、只恢复对话，或者两者都恢复。只回退对话适合"代码保留，换个思路重新问"。
- Checkpoint 跟随会话保存，恢复历史会话后仍可使用（有保留期限）。

**局限**
- 只跟踪 Claude 文件编辑工具产生的改动。通过 Bash 执行的命令（如 `rm`、`mv`、数据库操作、`npm install`）造成的变化不会被跟踪，也无法回退。
- 不跟踪你在会话外手动修改的文件或其他会话的改动。
- 它是会话级的本地撤销，不能替代 git。重要节点仍然要提交，远程副作用（推送、部署、发消息）无法撤回。

**用法建议**：大胆尝试方案时依靠 checkpoints 快速试错；大范围重构前先 git commit；有副作用的命令要靠权限审批来把关，而不是指望回退。

### Claude Code 如何处理上下文爆炸的问题？
Claude Code 的策略是从便宜到昂贵逐级处理，并且尽量不破坏 Prompt Cache：

1. **控制输入**：按需搜索和读取（Grep、Glob、带行号范围的 Read），不一次性加载整个仓库；超大工具结果写到磁盘，上下文里只保留预览和路径。
2. **清理旧工具结果（microcompact）**：较早的工具调用结果被清除或替换为占位，保留最近的若干个。这一步成本很低，因为需要时可以重新读取。
3. **自动压缩（auto-compact）**：上下文接近窗口上限时（会预留出生成摘要和继续回答的空间），把历史对话交给模型生成结构化摘要，包括用户的请求和意图、关键技术决策、修改过的文件和代码片段、遇到的错误和修复、待办事项、当前进展，然后用摘要加最近的内容替代原始历史，继续工作。
4. **手动控制**：`/compact [关注点]` 在阶段切换时主动压缩，可以指定摘要重点；`/clear` 清空对话开始新任务；`/context` 查看各部分占用了多少 token。
5. **上下文隔离**：调研、搜索类任务交给 subagent，在独立上下文中完成，只把结论返回主会话。
6. **外部状态**：TodoWrite 任务清单、`CLAUDE.md` 和进度文件不依赖对话历史，压缩后仍在。PreCompact Hook 可以在压缩前备份完整记录。

具体的触发阈值、分层细节在不同版本之间变化过（社区对泄露源码的分析里还提到过基于会话记忆文件的增量压缩），回答时讲清楚分层思路即可，不必背具体百分比。

**和 API 层能力的关系**：Anthropic API 在 2025 年 9 月推出了 context editing（自动清理旧工具结果）和 memory tool（模型通过文件读写跨会话记忆），思路和 Claude Code 一致：先清理、再压缩、重要状态写到外部。
### Claude Code 的 Subagent 是什么？什么时候用？
Subagent 是主 Agent 通过 Task 工具启动的子 Agent，在独立的上下文窗口中执行一个任务，结束后只把最终结果返回给主 Agent。自定义 subagent 在 2025 年 7 月推出。

**核心特性**
- **独立上下文**：不继承主会话的对话历史，只拿到主 Agent 写给它的任务描述，所以描述必须完整（目标、范围、需要返回什么）。中间过程留在子上下文里，主上下文只增加一份结论。
- **独立配置**：每个 subagent 可以有自己的 System Prompt、允许使用的工具列表和模型。比如审查类 subagent 只给 Read、Grep、Glob，不给 Edit 和 Bash。
- **可并行**：主 Agent 可以一次启动多个 subagent 同时工作。
- **不能嵌套**：subagent 不能再启动 subagent，避免无限递归。
- **内置类型**：general-purpose 等通用子 Agent；后续版本增加了只读的 Explore（快速搜索代码库）和 Plan Mode 下用于调研的 Plan subagent。

**定义方式**：`/agents` 命令交互式创建，或者直接写 Markdown 文件，项目级放 `.claude/agents/`，用户级放 `~/.claude/agents/`：
```markdown
---
name: code-reviewer
description: 代码修改完成后主动用于审查质量和安全问题
tools: Read, Grep, Glob
model: sonnet
---
你是资深代码审查者，检查正确性、安全性和可维护性……
```
`description` 决定主 Agent 什么时候自动委派给它，也可以在 Prompt 里点名让它使用某个 subagent。

**适用场景**
1. 广度搜索和调研：在大代码库里找相关文件、读大量文档，只要结论。
2. 独立的验证：跑测试、代码审查、安全检查，提供一个不受实现过程影响的视角。
3. 并行处理互不依赖的任务：比如同时调研几个模块。
4. 保护主上下文：主会话已经很长，或者子任务会产生大量噪声输出时。

**不适合**：强耦合、需要频繁共享中间状态的工作（例如多个子 Agent 同时修改同一组文件），容易产生冲突。子 Agent 也有启动开销，简单任务直接在主会话做更快。

### 介绍一下 Claude Code 主循环（query loop）的流程
Claude Code 的核心是一个单线程的 Agent 循环（社区分析泄露源码时将其对应到 `query.ts`）：每次调用模型后，只要模型返回了工具调用就执行工具并继续，直到模型给出不含工具调用的最终回答。

**单轮流程**
1. **上下文准备**：检查 token 用量，必要时清理旧工具结果或压缩；组装 System Prompt、`CLAUDE.md`、工具定义和消息历史。
2. **调用模型**：流式请求 Claude API，模型输出文本和若干 tool_use。
3. **工具调度**：解析工具名和参数，逐个经过输入校验和权限链（Hooks、规则、模式、必要时询问用户）。只读工具可以并发执行，写操作串行执行。
4. **回填结果**：工具结果作为 tool_result 追加到消息历史；被拒绝的调用也会以结果的形式告诉模型。
5. **继续循环**：带着新的观察再次调用模型。典型的代码问题会经历"Grep / Glob 定位候选文件 → 并行 Read 多个文件 → 发现新线索再搜索"这样的多次迭代。
6. **结束**：模型不再请求工具时输出最终回答；Stop Hook 可以在这里拦截，比如测试没通过就让它继续。用户也可以随时按 Esc 中断。

设计上刻意保持简单：一份扁平的消息历史，没有复杂的状态机或多 Agent 编排，可靠性主要靠工具设计、权限和上下文管理保证。

### 除了推理循环，还有一层 session 循环（QueryEngine）是做什么的？
可以这样回答：Claude Code 是双层结构，外层管会话，内层管推理。内层是上一题的 query 循环，处理一次用户输入内的多次"模型调用 + 工具执行"；外层（社区分析中对应 `QueryEngine.ts`）管理整个会话的生命周期。

**外层负责**
1. **接收和预处理输入**：识别斜杠命令（如 `/compact`、`/clear`、自定义命令）并本地处理；解析附件、`@` 文件引用；触发 UserPromptSubmit Hook。
2. **组装消息**：把用户输入和 System Prompt、`CLAUDE.md` 等上下文拼好。
3. **持久化**：消息写入会话 transcript（本地 JSONL 文件），支持 `--continue` / `--resume` 恢复会话。
4. **驱动内层循环**：把消息交给 query 循环，并在流式输出过程中同步更新状态：追加对话历史、累计 token 和费用、检查是否需要压缩。
5. **等待下一轮**：内层结束后把结果呈现给用户，回到第 1 步等待新的输入。

这种分层让内层专注于"一次任务怎么做完"，外层负责"会话怎么持续、怎么恢复、怎么控制成本"。无头模式和 Agent SDK 复用的就是这一套引擎。
## 编码 Agent 实践

### 如何向 Codex、Claude Code 等编码 Agent 提供需求、约束和验收标准，避免结果偏离目标？
公式：清晰目标 + 硬性约束 + 可执行的验收标准 + 禁止项 + 交付规范，并且让 Agent 能自己验证。

1. **分层描述需求**
   - 一句话目标：最终交付什么。
   - 业务规则逐条列出，不让 AI 猜：如手机号必须 11 位、地址最多 5 条、删除用逻辑删除。
   - 输入输出：字段、类型、是否必填、返回结构。
   - 给出相关文件和参考实现的位置（"仿照 `OrderService` 的写法"），比抽象描述有效得多。
2. **约束清单**
   - 技术约束：语言、框架和版本、可以用和不能引入的依赖。
   - 架构约束：分层、模块边界、哪些目录不能改。
   - 代码规范：注释、命名、统一的返回封装、异常处理方式。
   - 长期有效的约束写进 `CLAUDE.md` / `AGENTS.md`，不要每次重复。
3. **可执行的验收标准**
   - 功能：具体的测试用例，最好先写好测试（TDD），让 Agent 以"测试全部通过"为目标。
   - 非功能：如接口 P99 < 200ms、SQL 全部参数化、不允许拼接 SQL。
   - 告诉 Agent 怎么验证：执行哪个测试命令、怎么启动服务、看什么结果。能自我验证的 Agent 偏差小很多。
4. **禁止清单**：不准硬编码密钥、不准用已废弃 API、不准删除或跳过已有测试、不准修改范围外的文件。
5. **交付规范**：先列改动文件，再给 diff、执行命令和测试结果。
6. **先计划后执行**：复杂任务先让 Agent 在 Plan Mode 下出方案或提问澄清，确认后再写代码。
7. **精确纠偏**：偏离时不要只说"不对"，而要指出具体位置和违反的规则，例如"`UserService` 第 35 行硬编码了超时时间，违反约束第 3 条，改成读取配置"。多次纠偏不成功时，回退并带着更清晰的描述重新开始，比在错误路径上继续修效果更好。

### 如何管理编码 Agent 的上下文，避免长任务中的上下文污染和目标漂移？
长任务出问题通常不是上下文不够长，而是无效信息越来越多，Agent 分不清哪些指令仍然有效。

1. **任务契约写进文件**：目标、验收标准、禁止修改的范围、非目标写到仓库里的文件（如 `PLAN.md`、`TASK.md`），而不是只留在聊天记录里，压缩或重开会话后仍能读回来。
2. **按需读取**：先搜索再读取相关代码，不要一开始就塞入整个仓库、完整日志或大量文档。
3. **状态外置**：任务清单（TodoWrite）、决策记录、测试结果、git 提交记录保存进度。聊天上下文不能是唯一的信息来源。
4. **按阶段重置**：调研、实现、测试、审查可以分开会话。切换阶段时用 `/compact` 并指定保留重点，或 `/clear` 后只带入整理好的摘要和相关文件。
5. **定期做目标校验**：每个阶段结束让 Agent 汇报
```text
原始目标：
已完成：
已验证：
尚未解决：
下一步：
不应修改：
```
6. **隔离支线任务**：依赖调研、跑测试、安全审查交给 subagent，主 Agent 只接收结论、证据和文件位置。
7. **外部内容视为不可信**：Issue、网页、日志、仓库文件里可能有提示注入，它们只能提供数据，不能改变指令、权限或任务目标。

**判断是否漂移**：把当前 diff 和最初的验收标准逐项对照，无法对应到任何一条标准的改动，要么给出理由，要么撤回。

### 如何审查和验证 AI 生成代码的正确性、可维护性和安全性？
把生成的代码当作未经验证的外部贡献，而不是默认正确的成品。

**正确性**
- 阅读完整 diff，确认修改范围和需求一致。
- 运行已有测试，补充正常、边界和失败场景。
- 重点检查 Agent 是否为了让测试通过而删断言、跳过测试、改预期值或者对测试做特殊处理。
- 跑类型检查、静态分析、构建和集成测试。
- 在干净环境（CI）中复现，避免依赖会话里的临时状态。
- 关键算法用属性测试、差分测试或独立实现做对照。

**可维护性**：命名、复杂度、重复代码、接口兼容性、错误处理、文档，有没有引入不必要的依赖。能通过测试但把小问题扩成大重构的改动，要求缩小范围。

**安全**：从数据流入手，检查输入校验、认证和权限判断、命令注入和 SQL 注入、路径穿越、敏感信息泄露（日志、硬编码密钥）、不安全的反序列化、依赖风险（包括 AI 编造的不存在的包名被抢注的风险）、网络和文件访问。可以配合 SAST、依赖扫描和 Claude Code 的 `/security-review` 等工具。

**避免自证**：不要让同一个 Agent 既实现、又写唯一的测试、又做最终验收。让另一个 Agent（独立上下文）或人按原始需求独立设计测试和审查。

### 如何通过沙箱、权限审批和最小权限原则控制编码 Agent 的风险？
沙箱限制技术能力，审批确认高风险意图，最小权限减少出错后的影响范围，三者要同时用。

**最小权限**
- 默认只读，按任务逐步开放；只允许访问当前仓库和必要目录。
- 默认禁止读取凭据、SSH 密钥、`.env` 和生产配置（如 Claude Code 中配置 `deny: ["Read(./.env)", "Read(~/.ssh/**)"]`）。
- 网络按域名或用途开放，不给无限制的联网权限，防止数据外泄。
- 使用短期、可撤销、范围受限的凭据；开发、测试、生产环境隔离。

**审批**
- 安装依赖、修改仓库外的文件、部署、写外部系统需要审批。
- 删除文件、改数据库、推送代码、发消息、操作生产环境需要二次确认。
- 审批信息要具体：执行什么命令、访问什么资源、可能有什么影响、怎么恢复，而不是一句"是否继续"。

**沙箱**
- 操作系统级沙箱：Codex CLI 默认启用（macOS Seatbelt、Linux Landlock + seccomp），Claude Code 可以通过 `/sandbox` 开启（Seatbelt、bubblewrap），限制可写目录和网络。
- 无人值守或跳过权限确认（`--dangerously-skip-permissions`）时，只在容器、devcontainer 或虚拟机里运行。

**审计**：保存工具调用记录、审批记录和最终 diff，便于追溯。Claude Code 可以用 PreToolUse / PostToolUse Hooks 把每次调用写入审计系统。
## Harness Engineering

### 什么是 Harness Engineering？
Harness 原意是马具、挽具，引申为约束和驾驭的装置。在 Agent 领域，harness 指包裹在模型外面的整套运行系统：工具、上下文管理、权限、反馈回路、状态与恢复、验证流程。Harness Engineering 就是设计这套系统，让模型在其中可靠地完成长任务。

![](images/Java八股（后端\)+Agent八股8-image-22.png)

**背景**：Claude Code、Codex 这类产品本身就被称为 agent harness，Anthropic 的 Agent SDK 文档也用这个词。2026 年初，OpenAI 发表介绍团队用 Codex 以"人不手写代码"的方式开发产品的文章（*Harness engineering*），这个说法随之流行。核心观点是：工程师的主要工作从写代码转为设计环境、明确意图、构建反馈回路，让 Agent 可以可靠地工作。

**基本流程**：人设定目标和边界 → Agent 制定计划并执行动作 → 环境执行并反馈（编译、测试、日志、截图）→ Agent 根据反馈修正 → 验证通过后交付。

**例子**：一个写代码的 Agent 不能只是模型说"我来改"。它需要能读文件、搜索代码、编辑文件、跑测试、看到报错并据此修复，不能误删用户代码，最后报告改了什么。这一整套执行轨道就是 harness。

![](images/Java八股（后端\)+Agent八股8-image-23.png)

**常见实践**
- 把知识放进仓库：`AGENTS.md` 只做简短的目录，详细的设计文档、规范、计划放在仓库内的文档里，Agent 按需读取。
- 让 Agent 能看到结果：接入测试、日志、指标、浏览器截图等，让它自己验证。
- 用机器可执行的规则约束：lint、结构测试、架构依赖检查、Hooks，而不是只写在 Prompt 里。
- 持续清理：定期让 Agent 修复文档和代码中的偏差，防止"垃圾"累积。

### 怎么理解 Agent = Model + Harness？Harness 包含哪些工程能力？
模型只负责"下一步该做什么"的推理和生成；它本身无状态、不能行动、不保证安全，也不会自己验证结果。Agent 的实际表现取决于模型能力和 harness 质量两部分，同一个模型放在不同的 harness 里，完成长任务的效果可能差别很大。

**Harness 的工程能力**
| 能力 | 内容 |
| --- | --- |
| Agent 循环 | 调用模型、解析工具调用、执行、回填结果、终止条件和最大步数 |
| 工具系统 | 工具定义和描述、参数校验、并发调度、结果截断、MCP 接入 |
| 上下文治理 | System Prompt、项目规则加载、按需检索、压缩、清理、子 Agent 隔离 |
| 状态与记忆 | 会话持久化、checkpoint、断点续跑、进度文件、长期记忆 |
| 权限与安全 | 权限规则、审批、沙箱、凭据管理、提示注入防护 |
| 反馈与验证 | 测试、lint、类型检查、运行截图，让 Agent 能自我纠错 |
| 编排 | 子 Agent、并行任务、工作流 |
| 扩展 | Hooks、Skills、插件、热插拔 |
| 可观测 | trace、日志、token 和成本统计、评估 |
| 多租户 | 租户隔离、配额、审计 |

### Prompt Engineering、Context Engineering、Harness Engineering 有什么区别和递进关系？
可以概括为：Prompt Engineering 是写好指令，Context Engineering 是管理模型在每一步看到的信息，Harness Engineering 是设计整个执行系统。三者是包含关系而非替代关系，后者覆盖前者。

| | Prompt Engineering | Context Engineering | Harness Engineering |
| --- | --- | --- | --- |
| 关注点 | 单次请求怎么写提示词 | 多轮、多步中每次调用应该放进哪些 token | 模型之外的整个运行环境 |
| 典型手段 | 角色设定、few-shot、CoT、输出格式约束 | 检索、记忆、压缩、工具结果清理、子 Agent 隔离 | 工具和权限、反馈回路、状态恢复、验证、编排、可观测 |
| 解决的问题 | 单轮输出质量 | 长任务中的上下文爆炸和 Context Rot | 长时间自主运行的可靠性、安全性和可运维性 |
| 局限 | 撑不住多步复杂任务，规则写在 Prompt 里只是"建议" | 只管"看到什么"，不管"能做什么"和"怎么验证" | 工程成本高，需要按模型能力持续调整 |

"Context Engineering"这个说法在 2025 年中流行开来（Shopify CEO Tobi Lütke 和 Andrej Karpathy 都公开推崇过这个词，Anthropic 在 2025 年 9 月发文系统阐述）。"三代范式"是业内的一种归纳方式，并不是严格的学术划分，回答时讲清楚各自解决的问题和局限即可。

### 什么是上下文焦虑（context anxiety）？Context Reset 怎么实现？
上下文焦虑最早由 Cognition 团队在 2025 年 9 月评测 Claude Sonnet 4.5 时描述：模型能感知到自己的上下文快用完了，于是提前收尾、走捷径、在任务没真正完成时就总结退出，即使实际上还有空间。广义上也泛指上下文越长、模型越容易跑偏的现象。

**两种应对方式**
- **Compaction（压缩）**：在同一个会话里把历史压缩成摘要继续。连续性好，但模型仍然"知道"自己跑了很久，摘要可能丢细节。
- **Context Reset（重置）**：结束当前上下文，启动一个全新的会话，靠外部的交接材料恢复状态。上下文是干净的，没有焦虑和噪声，但交接材料必须足够好。

**Context Reset 的实现**（参考 Anthropic 2025 年 11 月的 *Effective harnesses for long-running agents*）
1. 初始化阶段：第一个会话负责搭建环境，写出完整的功能清单（如 JSON 格式，每项带 `passes: false`）、进度文件（如 `progress.txt`）、启动脚本（如 `init.sh`），并做一次 git 提交。
2. 每个后续会话开始时固定执行：读进度文件和 git log → 运行启动脚本和基础测试，确认环境正常 → 选一个未完成的功能。
3. 每个会话只做一个增量，端到端验证通过后才把对应功能标为完成。
4. 结束前提交 git、更新进度文件，留下干净可交接的状态，然后重置上下文，由下一个会话接手。

触发重置的条件可以是：token 用量达到阈值、完成一个功能或阶段、检测到重复动作或无进展。是否需要重置还是压缩就够用，取决于模型：模型越能保持长程专注，越可以更多依赖压缩。

### Harness 如何解决长会话衰减、记忆漂移和任务遗忘？
核心思路是：不依赖聊天历史保存状态，而是把关键信息外置、分层，并定期用干净的上下文重新开始。

1. **状态外置**：目标、计划、待办、进度、决策写进文件（TodoList、`progress.txt`、`PLAN.md`）和 git 提交记录，任何时候都可以从这些材料恢复。
2. **分层记忆**：短期保留最近的原始细节；较早的历史压缩成结构化摘要；稳定的规则放 `CLAUDE.md` / `AGENTS.md`；跨会话的经验进长期记忆。
3. **主动清理**：旧的工具结果及时清除，阶段完成后压缩或重置，不让无关内容无限堆积。
4. **关键约束保护**：System Prompt、硬约束和当前任务状态不参与压缩，必要时在上下文末尾重复提醒。
5. **任务拆小**：每次会话只做一个可验证的增量，减少单个上下文需要承载的内容。
6. **验证锚定**：用测试和验收清单判断进度，而不是相信模型自己说"已完成"；Stop Hook 可以强制在结束前跑测试。
7. **子 Agent 隔离**：探索性和高噪声的工作放到子上下文里。
### Harness 的状态管理解决什么问题？内存状态、持久化状态和 Checkpoint 怎么设计？
状态管理解决的问题：多轮会话状态丢失、任务中断后无法恢复、多个会话之间状态串扰、长任务无法断点续跑、需要人工审批时无法暂停等待。

| 层 | 内容 | 实现 | 特点 |
| --- | --- | --- | --- |
| 内存状态 | 当前步骤的中间变量、正在执行的工具调用 | 进程内对象 | 最快，进程挂掉就丢 |
| 持久化状态 | 会话消息、任务进度、产物引用 | Redis（热数据，带 TTL）+ 数据库（持久） | 服务重启和多实例部署后可以恢复 |
| Checkpoint | 关键节点的完整状态快照 | 每步或每个节点结束后写入，如 LangGraph 的 checkpointer（Postgres、Redis） | 失败时回到最近的快照续跑，支持 Human-in-the-loop 和回溯 |

**设计要点**
- 按 `tenant_id` / `user_id` / `thread_id` 隔离，避免串扰。
- checkpoint 在每个节点结束时写入，记录版本号，支持查看历史和从任意点分叉。
- 工具调用要幂等或带幂等键：从 checkpoint 恢复时可能重新执行最后一步，不能重复扣款或重复发消息。
- 等待人工审批时把状态持久化后释放资源，审批回调到来后再从 checkpoint 恢复。
- 外部副作用（文件、数据库、远程调用）无法通过回滚状态撤销，要单独设计补偿或审批。
- 大对象存外部（对象存储），状态里只放引用，控制快照体积。

### Harness 编排引擎如何支持串行、并行、分支、循环和子 Agent？
用图或 DSL 描述流程，由编排引擎统一驱动执行、保存状态和处理异常。LangGraph（StateGraph）、Temporal 一类的持久化工作流引擎都是这种思路。

- **串行**：上一节点的输出写入共享状态，作为下一节点的输入。
- **并行**：没有依赖的节点同时执行（fan-out），全部完成后汇聚（fan-in）；共享状态的同一字段要用 reducer 合并，避免互相覆盖。LangGraph 的 `Send` API 可以动态生成并行任务（map-reduce）。
- **分支**：条件边按状态或模型的判断路由到不同节点。
- **循环**：节点可以指回自己或上游，如"生成 → 测试 → 修复"，必须有退出条件以及最大迭代次数和预算兜底。
- **子 Agent / 子图**：子 Agent 作为一个节点或一个工具调用嵌入，拥有独立的上下文和状态，只把结果写回父状态。
- **人工节点**：在高风险节点前中断，持久化后等待审批再恢复。
- **容错**：节点级重试（指数退避）、超时、降级（换模型或换工具）、补偿动作，所有步骤可观测。

设计原则：确定性的部分用代码和流程定死，只在需要判断的节点交给模型，这比让模型自由决定所有步骤更可靠、更便宜。

### Harness 如何实现 Skill / Tool 的全生命周期管理？
覆盖注册、发现、加载、执行、治理、观测和下线几个阶段。

1. **注册**：集中的注册表记录名称、描述、参数 schema、版本、负责人、权限级别、是否有副作用。Skill 可以按 Agent Skills 的格式打包（`SKILL.md` + 脚本），工具可以通过 MCP Server 统一暴露，一次接入，多个 Agent 复用。
2. **测试与发布**：走 CI 流水线：单元测试、在沙箱中做集成测试、评估模型能否正确选择和调用；版本化发布，支持灰度和回滚。
3. **发现与加载**：按需加载，不把所有工具都放进上下文。先给名称和简短描述，需要时再加载完整定义（渐进式披露 / 工具搜索）；工具很多时先做路由筛选。
4. **执行**：参数 schema 校验、超时、重试、结果截断；有副作用的操作走审批，危险操作在沙箱里执行。
5. **治理**：权限按角色和租户绑定，策略即代码（policy as code）对新增和变更做前置检查；第三方 Skill 和 MCP Server 要审查来源，警惕工具描述里的提示注入（tool poisoning）。
6. **观测**：调用次数、成功率、延迟、token 消耗、被模型误用的情况，生命周期事件记录审计日志。
7. **下线**：先标记为弃用，引导迁移到新版本，确认无调用后归档。

### 多租户企业场景下，Harness 怎么做权限隔离、审计追溯和高危审批？
**权限隔离**
- 租户隔离：数据、记忆、向量库 namespace、会话状态都带 `tenant_id`，在存储层和查询层强制过滤，而不是依赖模型。
- RBAC：角色绑定可用的 Skill / Tool 列表和数据范围，不可用的工具不出现在模型的工具列表里。
- 凭据：每个租户或用户使用自己的短期凭据（OAuth 委托授权），Agent 以用户身份访问下游系统，不使用共享的超级账号。
- 资源配额：按租户限制 token、调用次数和并发。

**审计追溯**
- 全链路 trace ID 贯穿用户请求、每次模型调用、工具调用和下游接口。
- 记录输入、模型决策、工具参数和结果、审批人和审批结果、最终产出，日志只追加不可修改，敏感字段脱敏。
- 能回答"谁、在什么时间、通过哪个 Agent、调用了什么、产生了什么影响"。

**高危审批**
- 给工具标记风险等级（只读、可逆写入、不可逆或资金相关）。
- 高危调用触发时，编排引擎暂停并持久化状态，推送审批单（内容包括操作、参数、影响范围、回滚方案），审批通过后从 checkpoint 恢复执行，拒绝则把原因反馈给 Agent 让它调整。
- 审批在执行层强制生效，Prompt 里的"请先确认"不能作为安全措施。

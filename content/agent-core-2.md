## 工具调用与 Function Call

### Function Call 是干什么用的？ | 高频
Function Call（Function Calling / Tool Calling）让大模型能**以结构化方式请求调用外部函数**，解决模型只能生成文本、不能执行操作、拿不到实时数据的问题。

- **作用**：把 LLM 从"回答问题"升级为"执行任务"，比如查实时数据、调业务接口、读写数据库、发邮件。
- **核心能力**：把自然语言转换成结构化调用，即选出合适的函数，并按 Schema 生成 JSON 参数。
- **基本机制**：开发者预先声明函数（名称、描述、参数 Schema）→ 模型判断需要时输出函数名和参数 → **由应用程序真正执行函数** → 结果再交回模型生成回答。

模型本身从不执行函数，它只输出"想调用什么、参数是什么"，执行权和安全控制都在应用侧。

### Function Call 的基本结构和格式是什么？ | 高频
函数定义一般用 JSON 描述，参数部分遵循 JSON Schema。三个关键字段：

- **name**：函数唯一标识，执行层据此路由到具体实现。
- **description**：函数功能和适用场景的自然语言描述，是模型**判断是否调用、调用哪个**的核心依据。
- **parameters**：输入参数的 JSON Schema。
  - `type`：通常为 `object`。
  - `properties`：每个参数的名称、类型（`string`、`integer`、`boolean`、`array`、`enum` 等）和含义说明。
  - `required`：必填参数列表，约束模型生成完整可执行的调用。

```json
{
  "name": "get_weather",
  "description": "查询指定城市某一天的天气。用户询问天气、温度、是否下雨时使用",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {"type": "string", "description": "城市名称，例如：北京"},
      "date": {"type": "string", "description": "日期，格式 YYYY-MM-DD"}
    },
    "required": ["city", "date"]
  }
}
```

不同厂商外层包装略有差异：OpenAI 是 `{"type": "function", "function": {name, description, parameters}}`，Anthropic 是 `{name, description, input_schema}`，但内核都是 name + description + JSON Schema。模型返回的调用结果一般包含调用 ID、函数名和参数（arguments），应用执行后要带着同一个 ID 回传结果。

### 大模型调用 Function Call 的流程是什么？ | 高频
本质是一个"模型请求 → 应用执行 → 结果回传"的循环。

1. **发送请求**：应用把用户消息和可用工具列表（函数定义）一起发给模型。
2. **模型决策**：模型判断能否直接回答。需要工具时，返回一个或多个工具调用（函数名 + JSON 参数），而不是最终文本。
3. **应用执行**：应用解析函数名和参数，做校验和权限检查后调用真实服务（如天气 API）。
4. **结果回传**：把执行结果作为 tool 消息（带上对应的调用 ID）追加到对话，再次请求模型。
5. **继续生成**：模型根据结果决定再调下一个工具，或输出最终自然语言回答。
6. **循环直到结束**：只要模型还返回工具调用就继续执行；返回普通文本时流程结束。

例："查明天上海天气，然后发邮件告诉张三"：

```json
{"name": "get_weather", "arguments": {"city": "上海", "date": "2026-11-07"}}
```

应用返回 `{"temperature": "18°C", "condition": "晴"}` 后，模型再发起：

```json
{"name": "send_email", "arguments": {"to": "zhangsan@example.com", "content": "明天上海晴，18°C"}}
```

执行完成后模型输出"已查询并发送邮件"。主流 API 也支持一次返回多个并行工具调用，应用可并发执行后一起回传。

### 大模型是如何获得 Function Call 能力的？ | 高频
Function Call 能力不是预训练天然具备的，而是在具备较强指令遵循和结构化输出能力的基础模型上，**通过 SFT（常再加 RLHF / RL）专门训练出来的**。

**要学会的两件事**
- **意图识别 / 调用决策**：判断该直接回答，还是需要调工具；该调哪个工具。
- **参数抽取与格式化**：从用户输入中准确抽取参数，按 Schema 生成合法 JSON。

**SFT 过程**
1. **数据构建**：每条样本包含可用函数描述、对话历史、当前用户输入，以及期望输出（函数调用或直接回答）。多轮样本还要包含工具返回和基于结果的后续回复。
2. **基础模型选择**：选指令理解强的模型，如 Qwen、Llama、GLM 等。
3. **格式组织**：用模型的 Chat Template 把工具描述放进 system 或专门的工具区，工具调用用特殊 token 或固定标签包裹（如 `<tool_call>...</tool_call>`），使模型学会稳定的调用格式。
4. **微调**：全参或 LoRA 微调，通常只对 assistant 输出部分计算 loss。

**训练数据的基本结构**
- 系统提示 / 全局指令（可选）：角色、能力边界。
- 可用工具描述区：每个函数的结构化定义。
- 对话历史：user、assistant、tool 消息交替。
- 生成触发位：提示模型开始输出的位置（如 assistant 起始标记）。

推理阶段还可以用**约束解码**（JSON Schema / 语法约束）保证输出一定是合法 JSON，这是工程层面的补充，不改变模型的决策能力。

### 如何提高大模型调用 Function Call 的能力？ | 高频
从模型、提示、Schema、工程四个层面入手。

- **高质量训练数据（SFT）**：覆盖真实场景，重点加入该调 / 不该调的对比样本、缺参追问、多工具串联、工具失败等边界样本，提升意图识别和参数准确率。
- **优化函数描述**：description 写清功能、适用场景和**不适用场景**，参数说明给出格式和示例，消除工具之间的语义重叠。
- **Prompt 设计**：在 system prompt 中写明工具使用规则、优先级、何时应先追问用户，并配 few-shot 示例。
- **严格的 Schema**：明确类型、必填项、枚举值、格式约束，必要时开启 strict / 结构化输出模式，减少非法参数。
- **结果校验与重试**：校验 JSON 合法性、参数完整性和业务规则，失败时把具体错误信息回传给模型让它修正，限制重试次数。
- **工具路由（Tool Routing）**：工具很多时先按意图或向量检索筛出少量候选工具再交给模型，缩小选择范围。
- **控制工具数量与粒度**：合并语义相近的工具，避免一次性暴露几十上百个工具。

### LLM 怎么匹配工具参数？ | 高频
模型基于工具 Schema 理解每个参数的含义，从对话上下文中抽取并规范化值，再由应用侧校验。分四步：

1. **读取工具定义**：工具名、参数名、类型、必填 / 选填、枚举和取值范围、描述与示例。这些都在 Prompt 中提供给模型。
2. **理解意图并抽取值**：从用户 query 和历史对话中抽取时间、地点、ID、关键词等实体，映射到对应参数。
3. **对齐与类型转换**：把文本转成要求的类型和格式，如"明天"转成具体日期、"五百"转成 `500`、口语表达映射到枚举值；未提及的选填参数用默认值。
4. **校验与纠错**：应用侧检查必填项、类型、范围和业务合法性。缺参或歧义时不应让模型猜，而是反问用户补充；校验失败则把错误回传给模型重新生成。

关键原则：参数缺失时追问而不是编造，参数校验必须在执行前由代码完成。

### Agent 线上频繁选错工具，如何排查？ | 高频
按"**工具定义 → 路由候选集 → Prompt 与示例 → 回放 Trace → 执行前校验**"的顺序排查。选错工具很多时候不是模型能力问题，而是候选构造、描述边界或上下文把它带偏了。

1. **检查工具描述和 Schema**：描述是否清晰，工具职责是否重叠，参数能否区分场景。两个工具写得很像、参数语义太泛，模型自然容易选错。
2. **检查路由层**：是否一次给了太多候选工具，导致噪声竞争；路由粒度是否太粗，把不相关的相似工具放进了同一候选集。
3. **检查 Prompt 和 few-shot**：提示词是否有误导，示例是否把相似场景映射到了错误工具，最近是否改过 system prompt 或工具描述。
4. **回放 Trace**：看模型选工具前到底看到了什么，包括候选工具列表、历史记忆、用户输入和中间状态。判断是否有记忆污染、输入歧义或无关信息混入。按错误类型聚类统计，看是集中在某几个工具对，还是普遍现象。
5. **检查执行前二次校验**：是否有参数与工具匹配校验、意图与工具一致性检查。没有这一层，第一步选偏就会直接放大到执行层。

**修复措施**
- 短期：补负样本示例、收紧 Schema 和描述边界、修正路由规则。
- 长期：语义持续接近的工具合并成一个工具，内部按参数路由；把线上 bad case 沉淀成评测集做回归；必要时用这些数据微调。

**延伸：如何训练工具调用能力**

目标是让模型不仅会调，还知道什么时候不调、参数怎么补齐、失败后怎么处理。

- **正样本**：该调用的场景，包括单工具和多工具串并联，覆盖"选择 → 填参 → 执行 → 整合结果"的完整轨迹。
- **负样本**：闲聊、模型自身知识可答、工具无法解决的任务，教模型克制调用。
- **边界样本**：缺参时追问、工具返回空或报错时降级、多个工具都可用时按优先级选择。

数据来源：人工标注轨迹（质量最高、成本最高）、线上日志回放清洗、模板规则合成（快速扩量）、强模型生成轨迹再人工抽检修正（效率与质量折中）。

### （追问）构造工具调用数据集遇到过什么难点，怎么解决？ | 高频
最大的问题往往不是数据量不够，而是**数据不真实**：人工构造的样本过于标准，用户表达完整、参数齐全、工具永远成功，上线后用户一句话没说全，模型就不会处理了。

**常见难点和解法**
- **分布偏离线上**：引入真实线上 query，按意图、复杂度、缺参情况、歧义程度分桶统计，针对薄弱桶补数据。
- **标注一致性差**：同一问题不同标注人员给出不同工具路径。先统一 Schema、工具选择规范和决策标准，写标注指南，做交叉标注和一致性抽检。
- **长尾样本少**：用模板改写、同义改写、对抗生成和人工补充边界案例，优先覆盖最容易出事故的场景（缺参、歧义、工具失败、不该调用）。
- **工具结果缺失**：只有调用没有真实返回会导致模型不会处理异常。用 Mock 或沙箱真实执行，补充返回空、超时、报错的样本。
- **工具变更后数据过期**：数据与工具 Schema 版本绑定，工具变更时重新生成或迁移样本。

### Agent CLI 是什么？为什么要用 CLI？
Agent CLI 是**运行在终端里的 Agent**：用户用自然语言或命令下达任务，Agent 直接读文件、执行 Shell 命令、改代码、跑测试并返回结果。典型产品有 Claude Code、Codex CLI、Gemini CLI 等。

**为什么用 CLI**
1. **天然适合自动化**：CLI 是文本输入、文本输出，模型容易生成命令、读取输出、决定下一步，比操作 GUI 简单可靠得多。
2. **直接连接真实工作环境**：文件系统、`git`、构建工具、测试命令、脚本、容器、远程服务都能直接用，可以闭环完成"读代码 → 改文件 → 跑测试 → 看报错 → 继续修"。
3. **可组合、可脚本化**：能接管道、脚本和 CI/CD，例如 `git diff` 交给 Agent 审查，把日志 pipe 给 Agent 分析，或用非交互模式在流水线里自动执行任务。
4. **复用现有生态**：海量工具已有成熟 CLI，Agent 不必为每个能力单独封装 API；模型对常用命令也有大量训练语料。
5. **执行可观测、可控**：命令、输出、文件 Diff 都可见；可接入权限确认、沙箱、Hooks 和审计日志。
6. **适合长链路任务**：网页对话适合解释概念，IDE 补全适合边写边提示，CLI Agent 适合自主跑完一整段流程，如批量重构、修复测试、代码审查、运维巡检。

### CLI 命令行调用的优缺点是什么？
CLI 调用直接、轻量、能力强，适合本地开发和自动化；短板是安全边界弱、输出不结构化、依赖环境。

| | 内容 |
| --- | --- |
| 优点 | 调用直接：`git`、`npm test`、`python script.py` 无需额外封装服务 |
| | 生态成熟：大量开发工具自带 CLI，可直接复用 |
| | 易自动化：天然支持脚本、管道、CI/CD 编排 |
| | 执行能力强：读写文件、构建、测试、查日志，适合代码修复和运维排查 |
| | 上下文开销小：不必把大量工具 Schema 塞进上下文，按需用 `--help` 学习 |
| 缺点 | 安全风险高：权限大，错误命令可能删文件、改环境、泄露凭证，需要权限确认、沙箱、命令白名单和审计 |
| | 输出不结构化：`stdout` / `stderr` 是文本，需要模型自行解析，稳定性不如结构化 API（可优先用 `--json` 等结构化输出选项） |
| | 依赖本地环境：工具版本、环境变量、路径、权限不同会导致结果不一致 |
| | 参数无统一 Schema：模型可能拼错命令或误用参数，交互式命令还可能卡住 |
| | 输出过长：大量日志会挤占上下文，需要截断或过滤 |

## 上下文与 Harness Engineering

### 上下文很长时，为什么模型仍会遗忘信息？
上下文窗口决定模型最多能看到多少，注意力分配和上下文组织决定模型能真正用好多少。

模型没有像人一样"记住"整段对话，它每次只是基于当前输入预测下一个 Token。信息在窗口里，不等于模型能准确关注到它。

**常见原因**
- **信息被稀释**：大量无关内容分散注意力，有效信息占比下降。
- **Lost in the Middle**：模型通常对开头和结尾的信息更敏感，对中间部分利用较差（Liu et al., 2023）。
- **相似指令互相干扰**：多条相近或冲突的要求让模型抓错重点，旧指令可能覆盖新指令。
- **上下文已被截断或摘要**：框架为控制长度做了裁剪或压缩，细节其实已经丢失。
- **有效长度小于标称长度**：长上下文评测（如 RULER）显示，许多模型在远低于标称窗口的长度上就开始明显退化，这种现象也被称为 context rot。

**工程对策**：不把历史原样全塞进去，而是保留最近对话 + 滚动摘要 + RAG 按需检索 + 结构化状态（任务、进度、关键决策单独存放）+ 长期记忆；关键约束放在 system prompt 或靠近末尾的位置重复强调。

### 什么是 Harness Engineering？ | 高频
Harness 原意是马具、挽具。Harness Engineering 指**设计和优化模型之外的运行环境**，用工程机制约束、引导和保护 Agent，提升其稳定性、可控性和可靠性。常见的说法是 Agent = Model + Harness：除模型权重外的一切都属于 Harness。

- **关注对象**：Agent Loop、工具体系、权限与沙箱、Hooks、上下文管理与压缩、状态与进度持久化、子 Agent 编排、验证（测试、Linter）、异常处理与回滚、可观测性。
- **核心目标**：不只靠 Prompt 提醒模型少犯错，而是把关键约束固化为机制，让系统从机制上避免出错。
- **软约束 vs 硬约束**：Prompt 是概率性的软约束，模型可能听也可能不听；Harness 提供确定性的硬约束，如权限隔离、调用校验、流程限制、测试门禁、失败回滚，让 Agent 只能按规则做。
- **思路转变**：Agent 出问题时，不是反复改 Prompt 让它"下次记住"，而是改环境和机制，让同类错误没有机会再发生。比如 Agent 总忘跑测试，就加一个提交前自动跑测试的 Hook。

### Harness、Prompt、Context 工程有什么关系？ | 高频
三者是 Agent 工程关注点逐层外扩的演进：从"怎么跟模型说"，到"给模型看什么"，再到"模型在什么环境里运行"。可以概括为：**教会 AI、喂给 AI、管住 AI**。

| | Prompt Engineering | Context Engineering | Harness Engineering |
| --- | --- | --- | --- |
| 核心问题 | 怎么把任务说清楚 | 每一步给模型放哪些信息 | 模型运行在什么环境、受什么约束 |
| 手段 | 角色设定、指令、few-shot、CoT、输出格式 | RAG、记忆注入、工具结果裁剪、摘要压缩、上下文隔离 | Agent Loop、工具与权限、沙箱、Hooks、状态持久化、验证与回滚 |
| 约束性质 | 软约束，依赖模型理解 | 提升相关性和准确性，仍是输入层优化 | 硬约束，由机制保证 |
| 作用范围 | 单次调用 | 多轮、多步的信息流 | 整个系统的执行边界 |

**关系**：不是替代，而是包含与协作。Prompt 是 Context 的一部分，Context 管理又是 Harness 的一个组成。Prompt 负责激发能力，Context 负责提供任务所需信息，Harness 负责守住系统边界和执行底线。

### Harness Engineering 的设计边界在哪里？ | 高频
边界是**只约束真正需要约束的部分**：守住底线、拦住高风险错误，而不是替模型规定每一步。约束过多会降低灵活性和效率，随着模型变强还会变成负担。

**不该做的**
- **不约束模型能自己发现的问题**：命名、格式、风格交给 Linter、Formatter、类型检查，把结果反馈给模型即可，不在 Harness 里写大量细则。
- **不预设所有情况**：异常无法穷举，与其为每种错误写一个 Hook，不如设计通用的报错反馈、重试和回滚机制。
- **不写死执行路径**：约束目标、边界和验收标准，不规定具体步骤，否则就退化成 Workflow，压缩了模型的规划能力。

**原则**
- **少而精**：重点放在安全、合规、稳定性和关键结果正确性。
- **渐进式**：先建立最基本的约束，根据线上暴露的问题逐步补充。
- **定期收敛**：模型升级后重新审视哪些约束已不必要，及时删除。

### Anthropic Harness 架构包含哪些核心组件？ | 高频
以 Anthropic 关于长时运行 Agent 的工程实践（Effective harnesses for long-running agents，2025 年 11 月）为代表，核心是让 Agent 能**跨多个上下文窗口持续、增量地推进一个大任务**，并且每一步可观测、可验证。

- **需求规格**：用户给出的高层需求（App Spec），定义要做什么和验收标准。
- **Initializer Agent（初始化 Agent）**：只在第一个会话运行，负责搭建环境：生成详细的功能清单（feature list，JSON 格式，每项初始标记为未通过）、编写 `init.sh` 启动脚本、创建进度文件、做首次 git 提交。不负责具体功能实现。
- **Coding Agent（编码循环 Agent）**：之后每个会话运行，每次只做一个功能：读取进度文件和 git log 了解现状 → 跑起项目做冒烟测试 → 实现一个功能 → 测试通过后更新功能清单状态 → 提交 git 并写进度说明，保证会话结束时代码处于干净可交接状态。
- **外部记忆**：功能清单、进度文件（如 `claude-progress.txt`）和 git 历史，承载跨会话的状态，弥补上下文窗口不能延续的问题。
- **确定性验证**：用测试和浏览器自动化（如 Puppeteer MCP）做端到端验证，功能是否完成由测试结果判断，而不是模型自述。
- **隔离环境**：Agent 在沙箱 / 独立环境中运行，允许试错而不影响真实系统；git 提供随时回滚的能力。

特点：职责拆分、状态外置、增量推进、结果可验证。

### Anthropic Harness 工程实践有哪些关键要点？ | 高频
Anthropic 公开的 Agent 工程文章（Building effective agents、Effective context engineering for AI agents、长时运行 Agent harness 等）反复强调的要点可以归纳为：

- **从简单开始**：先用最简单的方案（单次调用、Workflow），确有必要才上自主 Agent；优先用可组合的简单模式，而不是复杂框架。
- **重视工具设计（ACI）**：像设计人机界面一样设计 Agent-Computer Interface，工具描述写清楚、参数难以误用（poka-yoke），返回信息精简有用。
- **上下文工程**：把上下文当有限资源，用压缩（compaction）、结构化笔记（进度文件、TODO）、子 Agent 隔离上下文、按需检索（just-in-time）来管理长任务。
- **增量推进**：一次只做一个功能，每次结束都留下可工作的状态和交接说明，避免一次性做太多导致半成品和上下文耗尽。
- **状态外置与交接**：功能清单、进度文件、git 提交在会话之间传递状态，新会话可以快速接手。
- **确定性验证**：用测试、Linter、端到端自动化检查结果，防止 Agent 未验证就宣布完成。
- **护栏与检查点**：权限控制、沙箱、Hooks 在关键操作前后拦截；检查点支持回退到之前的状态。
- **子 Agent / 多 Agent**：复杂任务由主 Agent 协调、子 Agent 在独立上下文中并行处理，主 Agent 只接收压缩后的结果。
- **Human-in-the-loop**：关键决策和高风险操作由人确认，其余逐步放权。
- **透明**：让 Agent 展示计划和执行步骤，便于人理解和纠偏。

这些实践的目的不是让模型更聪明，而是让系统更稳、更可管、更不容易出错。

### Anthropic 的 Human-in-the-loop 有什么特别之处？ | 高频
特别之处在于不把人当成"最后兜底的审核员"，而是**人和 Agent 共享控制权**：人只在真正重要的节点介入，信任随表现逐步建立，同时保留随时中断和事后追溯的能力。

- **关键决策点暴露**：不是所有操作都要人工审批，而是把高风险、不可逆、影响范围大的操作（删除、发布、对外发送、写生产数据）暴露给人确认。
- **渐进授权**：早期确认多，系统表现稳定后，常见操作可以加入允许列表自动执行，最终走向"Agent 自主执行、人类抽查"。Claude Code 的权限模式（逐次确认、自动接受编辑、按规则 allow / deny）就是这种思路。
- **可解释的决策**：Agent 先给出计划、说明为什么这样做，人可以在执行前审阅和修改（如 Plan 模式），而不是被动点"确认"。
- **随时可中断、可回退**：人可以在执行中打断并纠偏，检查点让操作可以撤回。可撤销往往比事先阻止体验更好。
- **事后审计**：自动执行的操作同样保留完整日志，人可以事后复盘。
- **减少打扰**：确认太多会让人疲劳、机械点通过，反而降低安全性，因此要用允许列表、沙箱隔离等手段减少不必要的确认。

### 如何评估 Harness 系统的设计质量？ | 高频
看它是否让 Agent 更可靠，同时不拖累效率，并且自身易观察、易扩展、易维护。

| 维度 | 关注问题 | 参考指标 |
| --- | --- | --- |
| 可靠性 | 能否防住关键错误 | 上线前后事故率、高风险操作拦截率、任务成功率 |
| 可用性 | 是否影响正常工作效率 | 平均任务完成时间、误拦截率、人工介入频率 |
| 可观测性 | 出问题能否快速发现和定位 | Trace / 日志覆盖率、问题定位时间、审计信息完整性 |
| 可扩展性 | 新增工具和规则的成本 | 新规则接入耗时、规则冲突率、配置复杂度 |
| 可维护性 | 是否变成技术负担 | 过时规则占比、规则重复度、文档完整性 |
| 成本 | 额外开销是否可接受 | 单任务 Token 和耗时、验证环节的额外成本 |

可靠性和可用性需要平衡：约束越多越安全，但会降低效率、增加人工打扰。还可以用固定评测集对比"同一模型、不同 Harness"的成功率，直接衡量 Harness 本身的贡献。

## 多智能体与工程化

### 单智能体和多智能体有什么区别？Agent 如何分类？ | 高频
按结构可以分为三类，核心区别是**任务由一个 Agent 完成，还是多个 Agent 协作完成**。

| 类型 | 结构 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 单智能体 | 一个 Agent 负责理解、拆解、调工具、生成结果 | 结构简单、成本低、易调试、上下文一致 | 复杂任务下上下文膨胀、能力瓶颈 | 流程清晰、复杂度中低的任务 |
| 多智能体 | 多个 Agent 承担规划、执行、校验等不同角色 | 分工专业化、可并行、互相校验更可靠 | 通信协调复杂，Token 成本高，错误会在 Agent 间传播 | 跨领域、可并行拆分的复杂任务 |
| 混合（主从） | 主 Agent 控制流程，关键环节调用子 Agent | 结构清晰、易扩展，子 Agent 隔离上下文 | 主 Agent 成为瓶颈，需要设计好任务交接 | 实际应用中最常见 |

**选择建议**：先用单 Agent 把问题做好，只有在上下文放不下、需要并行、需要不同专业能力或独立校验时才拆成多 Agent。多 Agent 不是越多越好，每多一个 Agent 都会增加协调和成本。

### 多个 Agent 之间如何协作？如何设计动态路由与切换机制？
优先选择**显式协调**（中心调度或共享状态）而不是 Agent 之间的自由对话。显式协调让每个 Agent 的输入输出、责任和超时都清楚，否则协作最终会变成没人负责。

**常见协作模式**
- **中心调度（Supervisor / Orchestrator-Worker）**：Manager Agent 拆分和分发任务，Worker 只执行子任务，结果汇总回 Manager。
- **流水线**：上一个 Agent 的输出是下一个的输入，如检索 → 分析 → 写作 → 审核。
- **专家路由**：按意图路由到财务、法务、运维等专家 Agent。
- **协商 / 辩论**：多个 Agent 给出方案或互相质疑，由仲裁 Agent 选择最终答案。
- **共享黑板**：Agent 读写同一份共享状态，调度器根据状态决定谁来处理下一步。

**动态路由设计**
1. **Agent Registry**：每个 Agent 注册能力描述、工具列表、权限范围、适用场景和输入输出格式。
2. **路由决策**：先做意图识别，再按任务类型、所需工具、权限和历史上下文匹配 Agent。可规则路由（快、稳定）、语义 / LLM 路由（灵活），或两者结合。
3. **动态切换（Handoff）**：执行中发现缺少权限、工具不匹配或结果置信度低时，转交给更合适的 Agent，并携带结构化的交接信息（目标、已完成部分、关键结论）。

**必须的约束**
- 转交层数上限、超时、失败后由谁兜底，提前定义清楚，防止互相甩锅或无限递归转交。A2A 这类 Agent 间协议同样需要这些边界。
- 结果冲突时由调度器按可信度、时效性或预设优先级裁决。
- 每个任务有明确的责任 Agent，调度器记录完整转交链，出问题能追溯到每一步。

### 设计企业级 AI Agent 系统要重点考虑哪些工程问题？
企业级 Agent 的重点不是"更智能"，而是**可控、可靠、安全、可观测、可落地**。

- **权限控制**：用户、Agent、工具三层权限边界；Agent 继承调用用户的权限，遵循最小权限原则。
- **数据安全**：敏感数据脱敏后才进入 Prompt，租户隔离，防范提示注入和数据外泄，遵守数据出境与合规要求。
- **工具治理**：工具统一注册、鉴权、限流、超时、重试、降级和版本管理；写操作做幂等。
- **可观测性**：每次模型调用、工具调用、Token、耗时、错误都进入 Trace，支持按会话回放。
- **成本控制**：语义缓存和 Prompt 缓存、模型分层（简单任务用小模型）、上下文压缩、调用预算。
- **稳定性**：超时、最大步数、循环检测、模型服务降级和多供应商兜底、失败重试与断点续跑。
- **结果可追溯**：记录 Agent 用了哪些数据、调了哪些工具、依据是什么，满足审计要求。
- **人机协同**：删除数据、发邮件、审批、转账等高风险操作必须人工确认。
- **评测与发布**：离线评测集 + 线上指标，Prompt、工具、模型变更走灰度和回归测试。

## 失败案例与效果评估

### Agent 为什么容易死循环？长任务中如何避免无限推理？ | 高频
死循环通常不是模型单方面的问题，而是**状态、停止条件和异常处理没有设计完整**。Agent 每一步都由模型决定下一步，只要停止条件不清楚，就可能反复做同一件事。

**典型场景**：工具一直返回"未找到"，Prompt 又要求"必须找到答案"，Agent 就不断改写搜索词、重复调用同一个工具。

**常见原因**
- 没有明确的完成条件。
- 工具报错信息模糊，模型不知道该重试还是换方案。
- 没记录已经尝试过的动作和参数。
- 模型误判工具结果，以为任务没完成。
- Prompt 中目标互相冲突。
- 工具有副作用，系统没有状态检查和幂等控制，重试导致状态越来越乱。

**防护手段**
- **最大步数**：最基础的硬上限。简单任务设低（如 5 轮），多步检索和复杂任务适当放宽（如 20–50 轮），但不能无限大。
- **明确终止条件**：拿到最终答案、工具返回明确结果、状态满足预定义完成条件就结束，避免"答完了还在转"。
- **重复行为检测**：连续多次调用同一工具且参数相同、输出高度相似或状态无变化时提前中断或强制换策略。
- **资源预算**：限制总时长、Token、工具调用次数和费用，超阈值即停止。
- **错误处理与回退**：工具错误返回清晰、可操作的信息；重试次数设上限，多次失败后返回兜底答案或失败原因。
- **记录尝试历史**：把已尝试的工具和参数放入状态，提示模型不要重复。
- **人工兜底**：高风险或高成本任务在不收敛时转人工确认。

### 如何防止 Agent 在复杂任务里跑偏？如何解决幻觉、循环调用等常见问题？ | 高频
核心是**减少不可逆错误**：不要让模型在错误假设上不断叠加操作。复杂任务需要的不是更多上下文，而是更干净的信息和更明确的检查点。

常见问题：幻觉、循环调用、工具误用、任务跑偏、结果不可控、成本过高、权限风险。

**防跑偏**
- **目标锚定**：Prompt 中写明目标、边界、输出格式和禁止事项；每一步执行前重新对齐当前阶段目标（如每轮注入 TodoList），防止做完子任务忘了主目标。
- **阶段检查点**：分析后确认关键信息，执行前检查参数和目标对象，执行后校验结果是否符合预期。
- **偏离即回滚**：检查点发现偏离时，回到最近的正确状态重新开始或触发重规划，而不是硬着头皮继续。
- **上下文压缩与状态清理**：每完成一个阶段做局部摘要，只保留后续需要的信息，避免上下文污染。
- **减少不可逆操作**：发消息、写库、调外部接口等有副作用的操作前加校验或人工确认。

**防幻觉**
- 用 RAG 或工具查询真实数据，而不是依赖模型记忆。
- 要求引用来源或给出依据。
- 关键结果做规则校验或独立模型二次审核。
- 允许回答"不确定"，不强行生成。

**防循环调用**：最大步数、最大工具调用次数、超时，记录已调用的工具和参数，多次得到相同结果就终止并返回失败原因（详见上一题）。

总体思路：把 Agent 当作一个不完全可靠的执行者来设计，用权限、规则、监控、审计和人工确认把风险控制住。

### 如何评估一个 Agent 系统的效果？
不能只看回答是否流畅，而要看任务有没有真正完成。一般从四个层面评估：

| 层面 | 关注点 | 指标示例 |
| --- | --- | --- |
| 回答质量 | 结果是否准确、完整、有依据 | 正确率、忠实度（是否基于证据）、幻觉率 |
| 工具质量 | 工具选得对不对、参数对不对、调用是否成功 | 工具选择准确率、参数正确率、调用成功率、无效调用占比 |
| 任务质量 | 用户目标是否达成 | 任务完成率、平均步数、追问轮数、人工接管率 |
| 系统质量 | 工程表现 | 端到端延迟、Token 与成本、错误率、稳定性 |

**评估方法**
- **离线评测集**：覆盖典型、边界和历史 bad case，含标准答案或可执行的验证（如单元测试、数据库最终状态）。
- **轨迹评估**：不只看最终答案，还检查中间步骤是否合理、是否有冗余调用。
- **LLM-as-Judge + 人工抽检**：开放式结果用模型按评分标准打分，并定期人工校准。
- **多次运行**：Agent 有随机性，同一任务跑多次看成功率分布（如 pass@k、pass^k）。
- **线上指标**：用户满意度、任务转化率、人工介入率，配合 A/B 测试评估变更。

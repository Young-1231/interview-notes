## 基本概念与选型

### 你怎么理解 Multi-Agent？相比 Single-Agent 最大的优势是什么？ | 核心
Multi-Agent 是把一个复杂任务拆给多个 Agent，每个 Agent 负责一个角色或子任务，最后合并结果。比如写行业报告：Research Agent 搜资料，Analyst Agent 分析数据，Writer Agent 成稿，Reviewer Agent 挑错。

![](images/Java八股（后端\)+Agent八股8-image-11.png)

![](images/Java八股（后端\)+Agent八股8-image-12.png)

"多个 Agent"不一定是多个不同的模型，可以是同一个模型配上不同的 Prompt、工具、上下文和权限。

**主要优势**
- 上下文隔离：每个 Agent 只装自己子任务需要的信息，单个窗口不会被撑爆，也不容易被无关内容干扰。这是实践中最核心的收益。
- 并行：互不依赖的子任务同时执行，缩短总耗时。
- 专业化：每个 Agent 的 Prompt、工具和权限更聚焦，权限可以按角色最小化。
- 独立复核：生成和审查分开，避免自己检查自己。
- 可扩展：新业务接入新的专家 Agent，不改动其他部分。

**代价**
Anthropic 在 2025 年 6 月公开的多 Agent 研究系统数据：单 Agent 的 token 消耗约为普通对话的 4 倍，多 Agent 系统约为 15 倍；在其内部评测中，Opus 4 做主 Agent、Sonnet 4 做子 Agent 的组合比单个 Opus 4 高 90.2%，而且性能差异的约 80% 可以由 token 消耗量解释。也就是说收益很大程度来自"能花更多 token"，只适合价值高、可并行的任务。此外还有通信成本、状态一致性、循环调用和调试难度。

### Multi-Agent 一定比 Single-Agent 好吗？单 Agent 和多 Agent 的边界在哪里？
不一定。任务简单、线性、强依赖同一份状态时，单 Agent 更快、更便宜、更好调试。

**边界**
- 单 Agent：一个模型实例（一个上下文）承担全部决策，靠 Prompt、记忆和工具完成所有步骤。适合任务链路短、能力维度单一、步骤之间强耦合的场景。
- 多 Agent：多个独立上下文各自决策，通过消息或共享状态协作。适合可拆分、跨领域、需要不同权限或独立复核的场景。

关键区别不是"角色有几个"，而是有没有多个独立的上下文和决策者。如果所谓不同角色只是换了几句提示词，没有真正的信息、权限或能力边界，用单 Agent 加多个工具就够了。

**强耦合任务的风险**：Cognition（Devin 团队）2025 年 6 月的文章 *Don't Build Multi-Agents* 指出，子 Agent 之间看不到彼此的决策，并行写代码时容易做出相互冲突的隐含假设。所以多数写代码场景更适合单线程主 Agent，子 Agent 只做只读调研、搜索这类可以独立完成的工作。

### 什么情况下应该用多 Agent，而不是单 Agent 加多个工具？
**适合多 Agent**
- 任务能拆成相对独立的子任务，并行能明显缩短时间（如广度优先的调研）。
- 子任务需要差异很大的知识、Prompt、工具或安全权限，例如一个 Agent 只能查数据，另一个才能提交审批。
- 信息量超出单个上下文能有效处理的范围。
- 需要独立复核，例如一个写代码，另一个测试或做安全审计。
- 企业内多业务线（HR、财务、法务、运维）各有独立的专家 Agent，需要统一入口。
- 希望某个环节失败时局部重试，而不是整体重跑。

**适合单 Agent + 工具**
- 流程基本线性，步骤之间强依赖。
- 所有操作围绕同一份状态频繁读写（典型如改同一个代码库）。
- 任务很短，协调开销可能比执行本身还大。
- 对延迟、成本或结果一致性要求很高。

**判断方法**
```text
多 Agent 收益 = 并行收益 + 专业化收益 + 独立复核收益
多 Agent 成本 = 通信成本 + 重复工作 + 状态同步 + 额外推理和工具调用
```
先用单 Agent 做基线，确认瓶颈确实是上下文、并行或权限，再拆。

### Multi-Agent 架构和 Workflow 有什么区别？ | 高频
核心区别是控制流由谁决定：Workflow 由代码预先定义路径，Multi-Agent 由模型在运行时动态决定。

Anthropic 在 2024 年 12 月的 *Building effective agents* 中给了明确划分：workflow 是 LLM 和工具按预定义的代码路径编排；agent 是 LLM 动态决定自己的流程和工具使用。

| 维度 | Workflow | Multi-Agent |
| --- | --- | --- |
| 执行路径 | 预先固化：节点、顺序、条件路由 | 运行时由 Agent 决定分工和下一步 |
| 可预测性 | 高，可复现、可审计 | 较低，同一输入可能走不同路径 |
| 灵活性 | 低，新情况需要改流程 | 高，能根据中间结果调整策略 |
| 成本与延迟 | 可控 | 波动大，通常更高 |
| 调试 | 容易定位到节点 | 需要完整 trace |
| 典型场景 | 报销审批、合同流转、工单派发、固定的 RAG 流程 | 开放式调研、软件开发、市场分析 |

两者不是二选一。常见模式（prompt chaining、routing、parallelization、orchestrator-workers、evaluator-optimizer）中，前几种是 workflow，orchestrator-workers 已经接近多 Agent。生产中常用 Workflow 做骨架保证合规和可控，在需要灵活性的节点嵌入 Agent。LangGraph 这类框架两种都能表达。

## 架构模式

### Multi-Agent 有哪几种典型的协作架构？
按控制方式可以分为四类，生产中多为混合。

![](images/Java八股（后端\)+Agent八股8-image-14.png)

1. **中心化（主从 / Supervisor / Orchestrator-Workers）**
   - 一个主 Agent 拆解任务、分配给专业子 Agent、汇总结果；子 Agent 没有全局决策权。
   - 优点：流程清晰、输出统一、好管控。缺点：主 Agent 是瓶颈和单点故障，所有信息都经过它中转。
   - Anthropic 的 Research 功能就是这种结构：主 Agent 规划并并行启动多个子 Agent 搜索，再汇总。
2. **流水线（Sequential / Pipeline）**
   - 按固定顺序串联，前一个的输出作为后一个的输入。
   - 优点：适合工序明确的线性任务，好调试。缺点：一环失败整体阻塞，没有并行能力，错误会向后传递。
3. **去中心化（对等 / Swarm / Network）**
   - Agent 地位平等，通过 handoff 或消息直接把任务交给更合适的 Agent，没有固定的指挥者。
   - 优点：灵活，少一次中心中转，延迟更低。缺点：路由不可预测，容易循环、分工混乱，难以全局控制预算。
4. **混合 / 层级（Hierarchical）**
   - 例如顶层 Supervisor 拆分任务，各小组内部走流水线或对等协作。大型系统的主流方案。

另外，辩论 / 投票（多个 Agent 独立给出答案再比较）和生成-评审（Generator + Critic 循环）也常被单独列为协作模式。

![](images/Java八股（后端\)+Agent八股8-image-15.png)
### Supervisor、Swarm、Hierarchical 和 Network 四种架构有什么区别？
这组名词主要来自 LangGraph 的多 Agent 文档，它还提供了 `langgraph-supervisor` 和 `langgraph-swarm` 两个现成的库。

| 架构 | 控制方式 | 适合什么任务 | 主要问题 |
| --- | --- | --- | --- |
| Supervisor | 中心 Supervisor 决定下一个调用哪个 Agent，子 Agent 完成后把控制权交回 | 流程清晰、需要统一调度和验收 | Supervisor 是瓶颈和单点；多一次中转，token 和延迟更高 |
| Hierarchical | Supervisor 管 Supervisor，按领域分组，多层管理 | 大型任务，多个团队或领域共同参与 | 层级越多，信息损失和管理开销越大 |
| Network | 每个 Agent 都能直接与其他任意 Agent 通信（多对多），自己决定交给谁 | 没有清晰层级、协作关系动态变化 | 路由、权限、循环控制最难，行为难预测 |
| Swarm | 去中心化的 handoff：当前 Agent 根据专长把控制权交给另一个 Agent，系统记住最后活跃的 Agent，下一轮用户输入直接交给它 | 多个专家轮流直接面对用户，如客服分流 | 没有全局视角，可能来回转交，预算难控制 |

**补充**
- Supervisor 最常见的写法是 agent-as-tool：把子 Agent 包装成工具，由 Supervisor 用 tool calling 调用。
- 易混点：Swarm 和 Network 都去中心化，但 Swarm 强调同一时刻只有一个活跃 Agent、通过 handoff 移交控制权；Network 允许任意 Agent 之间通信。OpenAI 2024 年 10 月开源的实验性 Swarm 框架，2025 年 3 月由 OpenAI Agents SDK 取代，handoff 保留为一等概念。

实践中常用混合架构：顶层 Supervisor 控制预算和验收，领域小组内部用 Network 或 Swarm。

### 如何划分不同 Agent 的角色、职责、工具权限和任务边界？
不要先想出"研究员、分析师、战略家"这类听起来合理的角色再找任务，而应该从工作对象和责任边界反推角色。

**每个 Agent 至少写清楚**
1. 负责交付什么结果。
2. 可以读取哪些数据。
3. 可以修改哪些资源。
4. 明确不归它处理的事情。
5. 输入和输出的格式（最好是结构化 schema）。
6. 完成、失败、阻塞分别怎么判定。
7. 可以消耗多少时间、token 和工具调用次数。
8. 什么情况必须移交或升级给人。

**划分的四条边界**
- 能力边界：检索、编码、测试、合规审查。
- 信息边界：财务 Agent 看不到人事资料。
- 权限边界：分析 Agent 只读，执行 Agent 才能写入或发布。
- 产物边界：每个文件或业务对象只有一个写入负责人。

最后一条最重要。多个 Agent 可以同时提出修改建议，但不能无约束地写同一份状态，要么设单一写入负责人，要么用带版本号的提交和合并机制。

**委派时的任务描述**：Anthropic 的经验是主 Agent 给子 Agent 的指令要包含目标、输出格式、可用工具和来源建议、明确的任务边界，否则子 Agent 会重复劳动或遗漏。另外要按任务复杂度决定投入多少个子 Agent，简单问题一个 Agent 就够了。

### 多个 Agent 应该通过消息传递、共享状态还是黑板模式协作？
三者解决的问题不同，最好组合使用。

| 方式 | 适合传递 | 优点 | 注意点 |
| --- | --- | --- | --- |
| 消息传递 | 控制信息：委派、确认、拒绝、进度、阻塞、完成 | 边界清晰，天然有时序 | 消息链过长后难追踪 |
| 共享状态 | 业务数据和中间产物：任务表、文件、数据库记录、测试结果 | 所有人看到同一份事实 | 需要版本号、访问控制和并发写规则 |
| 黑板模式 | 开放式协作：发现、假设、候选方案、待解决问题 | Agent 按内容自行认领，适合研究和故障排查 | 必须有去重、过期和认领机制 |

**稳妥的组合**
- 消息系统做控制面。
- 版本化存储做数据面。
- 黑板只放可复用的发现和开放问题。
- 大内容传引用（文件路径、对象 ID），不直接塞进消息。Anthropic 的做法是子 Agent 把产物写到外部存储，只给主 Agent 回传轻量引用，避免信息经过主 Agent 转述时失真。
- 共享任务状态，不共享每个 Agent 的完整思考过程。

LangGraph 里的对应：所有 Agent 读写同一个 State 就是共享状态，用 reducer 合并并行写入；通过 `Command(goto=..., update=...)` 做 handoff 相当于消息传递。

## 协作难点与治理

### 多 Agent 协作的难点有哪些？ | 扩展
最难的不是让多个 Agent 说话，而是让它们对世界状态的理解保持一致。

1. **状态一致性**：一个 Agent 基于旧信息做了判断，后面的 Agent 接着推就会把错误放大。不同 Agent 调用不同工具，看到的上下文版本可能都不一样，最后输出互相冲突。
2. **上下文传递损失**：主 Agent 给子 Agent 的任务描述不完整，子 Agent 误解任务；子 Agent 的结果被压缩转述时丢失关键细节。
3. **隐含决策冲突**：并行的子 Agent 各自做了不同假设（如代码风格、接口格式），合并时才发现不兼容。
4. **重复劳动与循环**：多个 Agent 做了同一件事，或者来回转交、互相推诿。
5. **错误累积**：多步、多 Agent 链路中每一步的小概率错误会相乘。
6. **成本与延迟**：token 消耗成倍增加，串行等待拉长关键路径。
7. **调试与评估**：行为非确定，需要完整 trace 才能复现；难以归因是哪个 Agent 的问题。

对策是**共享状态、任务边界和仲裁机制**：每个 Agent 清楚自己能改什么、不能改什么；共享信息标明哪些是事实、哪些是推断、哪些已经确认；冲突有明确的裁决规则。没有这层约束，多 Agent 只会放大单 Agent 的混乱。
### 多个 Agent 输出冲突时，如何通过仲裁、投票或评估器达成一致？
先区分冲突类型，再按顺序处理。

**冲突类型**
- 事实冲突：查证证据和数据来源。
- 规则冲突：服从权限更高或版本更新的规则。
- 方案冲突：按明确指标比较。
- 偏好冲突：交给有决策权的人或业务负责人。

**处理顺序**
1. 先做确定性检查：格式、类型、测试、规则校验。
2. 比较证据：来源、时间、版本、能否复现。
3. 独立评估器按统一评分表打分。
4. 仍无法判断时由领域 Agent 或 Supervisor 仲裁。
5. 涉及业务偏好、高风险或不可逆的决策时交给人。

**投票的局限**：投票只适合多个真正独立的候选。五个用同一模型、同一提示词、同一数据的 Agent 不是独立的，很可能把同一个错误重复五次，多数票不能代替证据。要提高独立性，可以换模型、换提示词、换信息来源。

**评估器的要求**：不能只看语言是否流畅，要检查约束是否满足、事实是否一致、测试是否通过、风险和产物是否可用。LLM 评委存在位置偏差和偏好冗长等问题，成对比较时要交换顺序再评一次。

### 如何避免多 Agent 系统中的死循环、重复执行和互相推诿？
要靠系统层面的硬约束，不能只在提示词里写"请勿重复"。

- 每个任务有唯一 ID 和幂等键。
- 任务依赖关系必须是有向无环图（DAG）。
- 设置最大 handoff 次数、最大重试次数、截止时间和 token 预算。LangGraph 默认的 `recursion_limit` 就是一种兜底。
- 重试前记录上次失败原因，输入不变时禁止原样重跑。
- 每个任务同一时间只有一个负责人或有效租约。
- 用内容哈希、任务签名或输入版本识别重复工作。
- Agent 声称完成时必须提交产物或验证证据。
- Agent 声称阻塞时必须说明缺什么、谁能提供、已经尝试过什么。
- 任务转回给原 Agent 时，必须带有新信息或修改后的要求。
- Supervisor 定期检测环形委派、长时间无进展和重复的工具调用。

**熔断规则**：比如同一失败连续出现两次就停止自动重试，第三次必须换执行方案或升级给人。

### 如何实现多 Agent 的上下文隔离、最小信息传递和共享记忆？
不要把完整对话复制给每个 Agent，那样既浪费 token，又扩大隐私和提示注入的风险。

**最小任务包**：给每个 Agent 一份只包含以下内容的任务描述
- 当前目标
- 必要背景
- 输入产物的引用和版本
- 相关约束
- 验收标准
- 和本任务直接相关的历史决策

**记忆分层**
| 层级 | 保存内容 | 生命周期 |
| --- | --- | --- |
| 私有工作上下文 | 草稿、临时推理、中间尝试 | 单次任务 |
| 任务共享状态 | 任务进度、产物、已确认事实 | 项目期间 |
| 长期记忆 | 稳定规则、用户偏好、已验证经验 | 跨任务 |

写入长期记忆前要筛选，临时假设、失败的猜测和未经确认的结论不能进去。每条共享记忆最好带来源、创建者、时间、适用范围、置信度和失效条件。

**返回方向同样要压缩**：子 Agent 在自己的上下文里可能用掉几万 token，返回给主 Agent 的应该是精炼的结论、证据和文件位置（通常一两千 token），大内容传引用，主 Agent 需要细节时再按权限读取原始材料。Claude Code 的 subagent 就是这种模式。

### 如何评估多 Agent 系统的贡献、协作效率、成本和整体效果？
| 维度 | 可用指标 |
| --- | --- |
| 任务质量 | 成功率、测试通过率、事实错误率、人工接受率 |
| Agent 贡献 | 独立产物的采用率、发现的缺陷数、移除该 Agent 后的质量变化 |
| 协作效率 | 并行加速比、等待时间、handoff 次数、重复工作率 |
| 稳定性 | 超时率、重试率、死循环次数、需要人工接管的比例 |
| 成本 | token、模型调用、工具调用、运行时间、外部服务费用 |

**贡献归因**：不要看某个 Agent 发了多少消息。可靠的做法是消融实验：移除某个 Agent 或替换成简单规则，比较质量、时间和成本的变化。

**最重要的基线**：同样任务、同样工具权限、相近预算下的单 Agent。对比时记录：
- 单 Agent 与多 Agent 的成功率和成本
- 多 Agent 是否真正缩短了关键路径
- 质量提升来自协作，还是只是来自更多的推理预算

**评估方法**：多 Agent 的执行路径不确定，更适合评估最终结果是否达标，而不是检查是否走了预设的步骤；可以从一二十个真实用例起步，用 LLM 评委按评分表打分，再配合人工抽查。生产环境要有完整 tracing。

如果多 Agent 只让结果提升一点，却让延迟、成本和故障面成倍增加，就不是好的设计。实用的起点是：一个 Supervisor、少量职责明确的执行 Agent、一个独立验证 Agent、加上版本化的共享状态。等真实数据证明瓶颈存在后，再引入多层管理、动态网络或 Swarm。
## A2A 与协议

### 什么是 A2A？主要解决什么问题？ | 扩展
A2A（Agent2Agent Protocol）是让不同框架、不同厂商、不同部署位置的 Agent 互相发现能力并协作完成任务的开放协议。Google 于 2025 年 4 月发布，2025 年 6 月捐给 Linux Foundation 托管。

**解决的问题**：单个 Agent 通过 Function Calling / MCP 接工具，但企业里有很多独立开发的 Agent（不同团队、不同框架），彼此无法互通。A2A 定义了它们之间的标准接口，把对方当成一个不透明的"同事"：只看它能做什么，不暴露它内部的工具、记忆和推理过程。

**核心概念**
- **Agent Card**：JSON 能力名片，含名称、描述、地址、skills、是否支持流式、认证方式，发布在 well-known 路径（v0.3 起为 `/.well-known/agent-card.json`）供发现。
- **Task**：有状态的工作单元，状态有 `submitted`、`working`、`input-required`、`completed`、`failed`、`canceled` 等；`input-required` 表示需要调用方补充信息，支持多轮交互。
- **Message / Part / Artifact**：Message 是一轮通信（角色 `user` / `agent`），由 TextPart、FilePart、DataPart 组成；Artifact 是任务产出，同样由 Part 组成。

**通信方式**：HTTP(S) + JSON-RPC 2.0，方法如 `message/send`、`message/stream`、`tasks/get`、`tasks/cancel`；长任务用 SSE 推进度或 webhook 推送通知；v0.3（2025 年 7 月）起支持 gRPC；认证复用 OAuth 2.0、API Key 等标准机制。

IBM 主导的 ACP（Agent Communication Protocol）在 2025 年 8 月并入了 A2A。

### 一次 A2A 任务的完整交互流程是怎样的？
以客户端 Agent（Client）委托远程 Agent（Remote）完成任务为例：

1. **发现**：Client 获取 Remote 的 Agent Card（从 well-known 路径或注册中心），根据 skills 判断它能否胜任，并按声明的认证方式拿到凭据。
2. **发起任务**：Client 调用 `message/send`（同步拿结果）或 `message/stream`（SSE 流式），发送一条由 TextPart / FilePart / DataPart 组成的 Message。
3. **执行与进度**：Remote 创建 Task，状态从 `submitted` 进入 `working`。流式模式下持续推送状态更新事件（TaskStatusUpdateEvent）和产物更新事件（TaskArtifactUpdateEvent）；耗时很长的任务可以用 push notification 回调 Client 注册的 webhook，Client 也可以用 `tasks/get` 轮询。
4. **多轮补充**：Remote 缺信息时把状态设为 `input-required` 并说明需要什么，Client 在同一个 Task（带 taskId / contextId）下继续发消息补充。
5. **完成**：状态变为 `completed`，结果以 Artifact 返回；失败为 `failed`，Client 可以随时 `tasks/cancel`。

**和普通 RPC 调用的区别**：任务是有状态、可长时间运行、可多轮交互的；双方只交换消息和产物，不共享内部的记忆、工具和推理过程，因此不同框架（LangGraph、CrewAI、ADK 等）实现的 Agent 也能互通。

**对应的协作能力**：这套流程覆盖了 Agent 间协作最常用的几件事：任务委派、进度和结果回传、缺少信息时的协商。在单个系统内部，同样的思想也可以用消息队列或 handoff 实现，不一定要走 A2A 协议。

### MCP、A2A、Function Calling 三者有什么本质区别？工程里怎么选？ | 扩展
三者分属不同层级，是叠加关系，不是互相替代：Function Calling 解决"模型怎么调用函数"，MCP 解决"Agent 怎么以标准方式接入工具和数据"，A2A 解决"Agent 和 Agent 怎么协作"。

| 维度 | Function Calling | MCP | A2A |
| --- | --- | --- | --- |
| 层级 | 模型能力 / API 特性 | Agent 与工具、数据之间 | Agent 与 Agent 之间 |
| 提出方 | 各模型厂商（OpenAI 2023 年 6 月首先推出） | Anthropic，2024 年 11 月 | Google，2025 年 4 月 |
| 交互对象 | 应用内定义的函数 | MCP Server 暴露的 tools、resources、prompts | 远程的、不透明的 Agent |
| 协议 | 各家 API 自己的格式，没有统一线协议 | JSON-RPC 2.0；传输为 stdio 或 Streamable HTTP | JSON-RPC 2.0 over HTTP，SSE / webhook，v0.3 起支持 gRPC |
| 状态 | 单次调用，无状态 | 会话内有能力协商，工具调用一般是同步的 | 有状态的 Task，支持长时间运行和多轮交互 |
| 典型场景 | 查天气、查库存、调用内部 API | 接文件系统、数据库、GitHub、Slack，一次接入多个客户端复用 | 跨团队、跨厂商的专家 Agent 分工协作 |

**易错点**
- MCP 不替代 Function Calling：MCP Client 把 Server 的工具列表转成模型的工具定义，模型输出调用请求后再由 Client 转发给 Server 执行，MCP 标准化的是工具的发现和接入。
- A2A 和"把 Agent 包装成 MCP 工具"的区别：A2A 把远程 Agent 当黑盒，支持长任务、多轮补充信息、流式进度和产物交付。

**工程选型**：少量应用内函数直接用 Function Calling；工具要跨 Agent / 客户端复用或接第三方系统用 MCP；和其他团队或厂商的独立 Agent 协作用 A2A。常见组合是对内 MCP、对外 A2A。

MCP 于 2025 年 12 月捐给 Linux Foundation 下的 AAIF，A2A 也由 Linux Foundation 托管。

## 自进化 Agent

### 什么是自进化 Agent？它与普通的 Reflection Agent 有什么区别？
自进化 Agent 是能从执行结果中提取经验，并把经验持久化成可复用资产的 Agent。下次遇到相似任务时，它使用更新后的 Prompt、Memory、Skill、Policy，必要时也可以使用经过训练的新模型。这里的"进化"是工程意义上的持续改进，不等于 Agent 可以任意改写自己的代码或参数。

![](images/Java八股（后端\)+Agent八股8-image-16.png)

**Reflection Agent** 更像做完以后复盘：
- 根据错误信息生成反思。
- 在当前任务中重试，或把反思放进短期记忆。
- 通常不验证反思是否正确，也不管理版本和发布。

例如 Reflexion（2023）把语言形式的反馈写入情景记忆，用于后续尝试，但不更新模型参数；Self-Refine（2023）让模型反复执行生成、反馈、修改，主要改善当前这一次的输出。

**自进化多出的三个环节**
1. 把反思转化为持久资产。
2. 用独立测试验证这些资产是否真的有效。
3. 管理资产的发布、监控和回滚。

两者不是截然分开的类别。Reflection 是自进化闭环里的一个步骤，当反思被持久化、经过验证、用于未来任务时，就进入了自进化的范畴。

### Agent 可以进化哪些组件？Prompt、Memory、Skill、Tool、Policy 还是模型参数？
| 组件 | 适合沉淀的内容 | 成本和风险 | 建议 |
| --- | --- | --- | --- |
| Prompt | 任务说明、规划方法、输出约束、错误处理提示 | 成本低，但容易过拟合评测集 | 可以高频更新 |
| Memory | 事实、案例、用户偏好、历史轨迹、失败记录 | 容易污染、冲突、无限膨胀 | 默认首选层 |
| Skill | 可执行步骤、代码模板、工具组合、检查清单 | 复用价值高，但错误会被批量放大 | 测试后再发布 |
| Tool | 工具描述、参数 schema、路由规则、适配代码 | 涉及真实的外部操作 | 只允许修改受控部分 |
| Policy | 工具选择、停止条件、重试策略、任务分解规则 | 影响面大 | 任务策略和安全策略分开管理 |
| 模型参数 | 领域知识、稳定的行为模式、长期能力 | 成本高、难解释、可能遗忘旧能力 | 最后考虑，离线训练 |

优先级通常是 Memory 和 Prompt 先行，Skill 和 Policy 其次，模型参数最后。改动越靠近权限和安全，审批越要严格。
### 如何构建"执行—评估—反思—更新—验证"的自进化闭环？
可落地的闭环：

`执行 → 记录 → 评估 → 反思 → 提议更新 → 隔离验证 → 发布 → 持续监控`

**执行与记录**：记录完整轨迹，而不只是最终回答
- 任务输入和环境状态
- 使用的 Prompt、模型和工具版本
- 每一步的观察、决策和工具调用
- 工具返回值、错误和重试
- 最终结果、耗时、成本、人工干预
- 权限拒绝、安全拦截等事件

原始轨迹用不可变日志保存，后续的总结可以修改，证据不能被覆盖。

**评估**：优先使用可验证的信号
1. 编译器、单元测试、数据库约束等确定性检查。
2. 环境返回的任务结果。
3. 有明确评分标准的人工或模型评价。
4. Agent 自己的判断（最弱）。

不能把 Agent 的自我评价当成唯一证据，LLM 评委也有位置偏差等问题。

**反思**：不只回答"哪里错了"，还要区分
- 观察到的事实是什么。
- 哪个决策最可能导致结果变化。
- 是偶发错误还是可复现的模式。
- 新规则适用于什么条件，什么情况下不该用。
- 怎么用实验验证这个判断。

**更新**：反思器只生成候选变更（Prompt 补丁、Memory 条目、Skill 草案、Policy 修改），不能直接覆盖线上版本。每项变更带上来源轨迹、适用范围、置信度、支持案例与反例、预期改善的指标、过期时间或复审条件。

**验证**：候选版本要经过
- 失败案例重放
- 独立的留出集
- 原有能力的回归测试
- 分布外任务和对抗性输入
- 多次随机运行（结果有方差）
- 成本、延迟和安全检查

验证集不能同时用于反思和 Prompt 搜索，否则 Agent 只是在适应测试题。

**发布与监控**：灰度发布，监控关键指标，退化时自动回滚到上一版本。

### 如何把一次任务的成功或失败经验沉淀为 Memory、Skill 和 Policy？
三者回答不同的问题：
- Memory 记录"发生过什么"。
- Skill 描述"怎样完成一类任务"。
- Policy 决定"什么时候用哪种方法，以及什么行为不允许"。

**例子：一次数据库迁移失败**
- Memory：某数据库版本不支持某条语法，轨迹中出现了具体报错。
- Skill：迁移前先识别版本，在事务内做兼容性检查，失败时回滚。
- Policy：涉及生产迁移时必须先生成计划、确认备份并取得审批。

**成功经验不能原样复制**：一次成功可能来自运气、缓存状态或隐藏前提。要提取最小充分条件，并通过删减步骤或更换环境来验证。

**失败经验建议结构化保存**
```text
任务特征
失败动作
环境反馈
直接原因
可能的深层原因
已验证的修复方法
适用条件
反例
证据轨迹
置信度
```

### 如何为自进化过程设计可靠的奖励信号和评估指标？
不要急着把所有目标压成一个分数，先设硬门槛，再比较效果：

```text
安全和权限检查通过
    ↓
任务是否完成
    ↓
结果质量
    ↓
成本、延迟、工具调用量、人工介入
```

**奖励信号的可靠性大致排序**

`确定性验证器 > 环境结果 > 专用判别器 > 多评委共识 > 单个 LLM 评委 > Agent 自评`

**建议同时跟踪**：任务成功率、约束违反率、严重错误率、首次成功率与重试次数、成本和延迟、跨任务迁移效果、相对基线的回归率、结果方差、置信度校准、人工接管率、安全事件数。

**防止奖励投机（reward hacking）**：用隐藏测试、轮换测试集、反例、多个独立评估器和人工抽查；成对比较时交换候选顺序；警惕 Agent 通过删断言、跳过测试来"通过"。高风险任务中，奖励只能决定候选方案的排序，不能覆盖权限和安全门槛。

### 如何防止错误反馈、记忆污染和灾难性遗忘导致能力退化？
记忆系统需要像数据治理一样管理，而不是一个无限增长的向量库。

- 原始轨迹、候选经验、已验证知识分库存放。
- 每条记录保存来源、时间、适用版本、置信度和权限级别。
- 从网页、邮件等不可信内容提取的数据只能作为事实候选，不能成为系统指令（防止持久化的提示注入）。
- 检测重复、冲突和过期的记忆。
- 低置信度经验设置过期时间。
- 检索时按任务范围、权限和证据强度过滤。
- 新经验先在隔离区观察，验证后再晋升。
- 保留旧版本和有代表性的旧任务，持续做回归测试。
- 微调时混入旧能力样本，比较新旧模型的能力矩阵，防止灾难性遗忘。

特别注意不要把"任务失败"直接解读为"策略错误"。工具故障、权限变化、评估器错误和环境随机性都会制造错误的反馈信号。

### 如何限制 Agent 修改自身代码、工具和权限带来的安全风险？
最重要的原则：Agent 可以提出修改，但不能自己批准。

**两个边界**
- Agent 控制面：提出 Prompt、Skill、代码或路由策略的候选修改。
- 安全执行面：决定候选能否运行、能访问什么资源、是否需要人工批准。它必须独立于 Agent。

**执行面的措施**
- 最小权限和短期凭证，工具和参数白名单。
- 文件、网络、进程隔离，沙箱执行。
- 结构化的参数校验。
- 调用次数、金额和资源配额。
- 高影响操作需要人工审批。
- 不可篡改的审计日志，经过签名的 Skill 和工具包。
- 紧急停止开关，安全规则与任务策略分离。

Agent 不应自行安装工具、扩大网络权限、读取新的密钥、修改审计系统或删除历史记录。自己生成的代码先当成普通数据保存，通过静态检查、沙箱测试和审批后才能成为可调用的 Skill。

只在 Prompt 里告诉 Agent "不要越权"并不可靠，权限必须在执行层落实。成熟的自进化系统不是能随意改写自己的 Agent，而是能提出改进、用证据验证改进、在受控发布体系里采用改进的 Agent。

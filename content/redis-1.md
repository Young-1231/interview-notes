## Redis 基础与使用场景
### 你在项目中用 Redis 做什么？有哪些业务场景？为什么选 Redis 而不是其他缓存？ | 高频
Redis 是基于内存的 KV 数据库，最常见的用途是做缓存，此外还能借助丰富的数据结构做分布式锁、计数器、排行榜、限流、Session 共享等。

**常见业务场景**
- **缓存**：用户信息、商品详情等热点数据，降低数据库压力。
- **分布式锁**：`SET key uuid NX PX 30000` 一条命令原子加锁（2.6.12 起支持）；生产上常用 Redisson。
- **计数器**：`INCR`/`HINCRBY` 原子自增，如点赞数、阅读量，可先写 Redis 再定时同步数据库。
- **全局 ID**：`INCRBY userid 1000` 一次取一段号段，用于分库分表。
- **排行榜**：ZSet 以热度为 score，`ZREVRANGE` 取榜单，`ZREVRANK` 取排名。
- **限流**：`INCR` 固定窗口、ZSet 滑动窗口、Lua 令牌桶。
- **消息队列**：List（`LPUSH` + `BRPOP`）或 5.0 起的 Stream（消费者组、ACK）。
- **分布式 Session**：Session 存 Redis，应用无状态。

**为什么选 Redis（对比 Memcached、本地缓存）**
- 数据结构丰富，Memcached 只有简单 KV。
- 支持持久化（RDB、AOF、混合），重启可恢复。
- 主从、Sentinel、Cluster 提供高可用与扩展。
- 单命令原子执行，配合 Lua 可原子完成复杂逻辑。
- 内存操作 + I/O 多路复用，单实例可达 10 万级 QPS。

### 为什么用 Redis 做缓存？为什么不用本地缓存？
Redis 是独立部署的集中式缓存，多个应用实例共享同一份数据；本地缓存只在单个进程内有效。两者不是互斥的，热点数据常常做「本地缓存 + Redis」两级缓存。

| 对比 | 本地缓存（Caffeine、Guava） | Redis |
| --- | --- | --- |
| 访问速度 | 最快，进程内访问，无网络开销 | 需要一次网络往返，亚毫秒级 |
| 数据共享 | 每个实例各存一份，多实例之间不一致 | 所有实例共享，一致性好维护 |
| 容量 | 受 JVM 堆限制，过大会加重 GC | 可单独扩容，Cluster 可水平扩展 |
| 可靠性 | 应用重启即丢失 | 支持持久化和主从高可用 |
| 功能 | 简单 KV | 丰富数据结构、过期、分布式锁、Pub/Sub 等 |

**不单独用本地缓存的原因**：分布式部署下各节点的缓存难以同步，更新时要广播失效；容量受堆内存限制；重启后缓存全部失效，容易产生大量回源。
**注意**：Redis 是集中式依赖，要做好高可用，并处理穿透、击穿、雪崩问题。

### Redis 有事务吗？支持回滚吗？ | 滴滴、小红书、银行、阿里、招商银行
Redis 有事务（`MULTI`、`EXEC`、`DISCARD`、`WATCH`），但不支持回滚，只保证事务内的命令按顺序、不被其他客户端命令插入地执行。

**执行流程**
- `MULTI` 开启事务，之后的命令只入队（返回 `QUEUED`），不执行。
- `EXEC` 一次性按顺序执行队列中的所有命令；`DISCARD` 放弃事务。
- `WATCH key`：乐观锁。被 WATCH 的 key 在 `EXEC` 之前被其他客户端修改，`EXEC` 返回 nil，整个事务不执行，业务可以重试。

**出错时的行为**
- 入队时就出错（命令不存在、参数个数错误）：2.6.5 起 `EXEC` 直接拒绝，整个事务都不执行。
- 执行时出错（如对 String 执行 `LPUSH`）：只有出错的那条命令失败，其他命令照常执行，已执行的不会回滚。

**为什么不支持回滚**：运行时错误基本都是编程错误（类型用错），应在开发阶段发现；不做回滚可以保持实现简单、性能高。

**补充**：Lua 脚本同样能保证执行期间不被其他命令插入，且可以写条件逻辑，实际项目中比 `MULTI` 更常用；但脚本中途报错，已执行的写操作同样不会回滚。

### Redis 管道（Pipeline）有什么作用？
Pipeline 让客户端把多条命令一次性发送给服务端，再一次性读取所有结果，把 N 次网络往返（RTT）压缩成 1 次，大幅提升批量操作的吞吐量。

- **原理**：客户端不等每条命令的响应就继续发送，服务端按顺序执行并把结果缓存起来一起返回。同时也减少了 `read`/`write` 系统调用次数。
- **不保证原子性**：Pipeline 中的命令之间可能穿插其他客户端的命令，某条失败不影响其他命令。需要原子性用事务或 Lua 脚本。
- **注意**：单个 Pipeline 不宜过大，否则客户端等待时间长、服务端要缓存大量回复占用内存，一般分批（如每批几百到上千条）发送。Cluster 模式下，Pipeline 中的 key 需要按槽分组发送到对应节点。

| 对比 | Pipeline | 事务（MULTI/EXEC） | Lua 脚本 |
| --- | --- | --- | --- |
| 减少 RTT | 是 | 命令逐条入队，仍有多次 RTT（可与 Pipeline 结合） | 是 |
| 原子性（不被插入） | 否 | 是 | 是 |
| 条件逻辑 | 否 | 否 | 是 |

### 如何从海量 key 中找出某一固定前缀的 key？（SCAN）
用 `SCAN` 渐进式遍历，不要用 `KEYS prefix:*`。`KEYS` 会一次性遍历全部 key，在单线程执行模型下会长时间阻塞，线上一般禁用。

```bash
SCAN 0 MATCH user:* COUNT 1000
# 返回下一个游标和本批 key，用返回的游标继续 SCAN，直到游标为 0
```

**要点**
- **游标迭代**：每次调用只扫描全局哈希表的一小部分桶，返回新游标，直到游标返回 0 才算遍历完整。
- **COUNT 只是提示**：表示每次迭代大致要做多少工作量（默认 10），不是返回数量上限。返回的 key 数可能多于或少于 COUNT；带 MATCH 时过滤在扫描之后进行，可能返回空列表但游标还没结束，必须继续迭代。
- **可能返回重复 key**：遍历过程中如果发生 rehash，同一个 key 可能被返回多次，业务侧要去重。遍历期间新增或删除的 key 不保证一定被返回。
- **集合类型**：`HSCAN`、`SSCAN`、`ZSCAN` 用同样方式遍历大集合的元素。
- **Cluster 模式**：`SCAN` 只扫描当前节点，需要对每个主节点分别执行。
- **更好的做法**：如果经常需要按前缀查找，应在业务上额外维护一个索引集合（如 Set），而不是依赖全库扫描。

## 数据类型与底层结构
### Redis 有哪些数据类型？各自特点和使用场景？ | 高频 | 农业银行、交通银行
常用的 5 种基本类型是 String、Hash、List、Set、ZSet，另外还有 Bitmap、HyperLogLog、GEO、Stream 等特殊类型。

| 类型 | 特点 | 典型场景 |
| --- | --- | --- |
| String | 可存字符串、整数、浮点数、二进制，单值最大 512MB，支持 `INCR` 原子自增 | 缓存对象（JSON）、计数器、分布式锁、Session |
| Hash | field-value 映射，类似 `Map<String, String>`，可单独读写某个字段 | 存对象（用户信息、购物车），字段级更新 |
| List | 按插入顺序排列，可两端插入、弹出 | 消息队列（`LPUSH` + `BRPOP`）、最新消息列表、时间线 |
| Set | 无序、元素唯一，支持交集、并集、差集 | 标签、去重、共同好友、抽奖 |
| ZSet | 元素唯一，每个元素带一个 score，按 score 排序 | 排行榜、延迟队列、按权重排序 |
| Bitmap（2.2） | 基于 String 的位操作 | 签到、在线状态、布隆过滤器 |
| HyperLogLog（2.8.9） | 基数估算，固定约 12KB，标准误差 0.81% | UV 统计、独立 IP 数 |
| GEO（3.2） | 基于 ZSet 存经纬度（GeoHash 作 score） | 附近的人、距离计算 |
| Stream（5.0） | 持久化消息流，支持消费者组、ACK | 可靠的轻量级消息队列 |

**底层结构**（详见下一题）：SDS、listpack（7.0 起全面取代 ziplist）、dict（扩缩容时**渐进式 rehash**，每次增删改查顺带迁移一个桶）、quicklist、intset、skiplist。

### Redis 常见 5 种数据结构的底层实现是什么？ | 高频
每种类型都会根据数据量和元素大小在「紧凑编码」和「通用编码」之间切换，可以用 `OBJECT ENCODING key` 查看。

| 类型 | 底层编码 | 切换条件（默认配置） |
| --- | --- | --- |
| String | int、embstr、raw（都基于 SDS） | 整数用 int；短字符串（≤ 44 字节）用 embstr，与对象头一次分配；更长用 raw |
| List | quicklist；7.2 起元素少时用 listpack | quicklist 节点在 7.0 前是 ziplist、7.0 起是 listpack；7.2 起小列表直接用 listpack |
| Hash | listpack（7.0 前 ziplist）、hashtable | 元素数 ≤ 128 且每个值 ≤ 64 字节用 listpack，否则转 hashtable |
| Set | intset、listpack（7.2+）、hashtable | 全是整数且数量 ≤ 512 用 intset；7.2 起元素少（≤ 128）且不全是整数时用 listpack；其余用 hashtable |
| ZSet | listpack（7.0 前 ziplist）、skiplist + dict | 元素数 ≤ 128 且每个元素 ≤ 64 字节用 listpack，否则用 skiplist + dict |

**要点**
- **SDS 相比 C 字符串**：O(1) 获取长度、二进制安全、杜绝缓冲区溢出、预分配减少重分配。
- **listpack 取代 ziplist**：ziplist 节点记录前一节点长度，插入大元素可能引发**连锁更新**；listpack 只记录自身长度，避免了这个问题。
- **编码只升级不降级**：转成 hashtable/skiplist 后，即使元素减少也不会转回紧凑编码。

### 跳表节点的查询过程是怎样的？ | 高频
跳表是在有序链表上加多级「索引」的结构。查询时从最高层的头节点开始：右边节点小于目标就向右走，大于等于目标（或到头）就下降一层，直到在第 0 层找到目标或确认不存在，平均时间复杂度 O(log N)。

![](images/Java+AI八股-image-9.png)

**示例**：查找 40

```text
Level 2：HEAD ───────────────► 30 ─────────────► NULL
Level 1：HEAD ─────► 10 ─────► 30 ─────► 50 ───► NULL
Level 0：HEAD ─► 10 ─► 20 ─► 30 ─► 40 ─► 50 ─► NULL
```

1. Level 2：HEAD 右边是 30，30 < 40，右移到 30；30 右边是 NULL，下降。
2. Level 1：30 右边是 50，50 > 40，不能右移，下降。
3. Level 0：30 右边是 40，命中。

**Redis 跳表的实现细节**
- 节点按 **score 升序**排列，score 相同时按 member 字典序排列。
- 每个节点的层高随机生成：每多一层的概率是 1/4，最大 32 层（5.0 前为 64 层），因此插入、删除无需全局调整，只修改相邻节点指针。
- 每层指针带 **span（跨度）**，查找过程中累加跨度即可得到排名，所以 `ZRANK` 也是 O(log N)。
- 第 0 层有 **backward 后退指针**，支持 `ZREVRANGE` 等逆序遍历。

### ZSet 用的什么数据结构？为什么用跳表而不用 B+ 树？ | 高频
ZSet 小数据量时用 listpack（7.0 前是 ziplist）；超过阈值（128 个元素或单个元素超过 64 字节）后用 **skiplist + dict** 组合。

**为什么同时用 skiplist 和 dict**
- dict：member → score 的映射，`ZSCORE`、判断成员是否存在都是 O(1)。
- skiplist：按 score 有序，支持 `ZRANGEBYSCORE` 范围查询和 `ZRANK` 排名，O(log N)。
- 两者共享同一个 member 对象，不会存两份字符串。

**为什么用跳表不用 B+ 树**
- **场景不同**：B+ 树的设计目标是减少磁盘 I/O，一个节点对应一个磁盘页，树矮、扇出大；Redis 是纯内存操作，没有磁盘 I/O 的问题，B+ 树的优势用不上。
- **实现简单**：跳表本质是多层链表，代码量小、易调试；B+ 树要处理节点分裂、合并、重平衡，实现复杂。
- **写入更稳定**：跳表插入只需随机层高并修改相邻节点指针，不需要页分裂和数据搬移。
- **范围查询同样高效**：定位到起点后沿第 0 层链表顺序遍历即可，效果和 B+ 树叶子链表类似。
- **内存可控**：平均每个节点约 1.33 个指针（p = 1/4），内存开销不比平衡树大。

**跳表 vs 平衡树（红黑树）**：两者查找复杂度相当，但红黑树范围查询需要中序遍历，实现也更复杂；跳表范围查询更直接，并发改造也更容易。

### 用户会话 Session 用什么数据类型存？ | 高频
一般用 **String** 存序列化后的 JSON，并设置过期时间；如果 Session 里的字段需要频繁单独修改，用 **Hash**。

```bash
SETEX session:token:abc123 1800 '{"userId":1001,"username":"Tom","role":"admin"}'
```

**选 String 的理由**
- 存储简单：Session 一般按 token 整体读取、整体写入，序列化成 JSON 直接存即可。
- 天然支持过期：`SETEX` 或 `SET ... EX` 设置 TTL，和 Session 的有效期机制对应；用户每次访问时刷新 TTL 即可实现滑动过期。
- 读取效率高：一次 `GET` 取回全部数据。

**选 Hash 的场景**：只需更新最后访问时间、权限等个别字段时，`HSET` 改单个 field，不必反序列化、重写整个对象。注意 Hash 的过期时间只能设在整个 key 上（7.4 起支持 field 级过期 `HEXPIRE`）。

**大模型会话场景**：多轮对话消息更适合用 List 按时间顺序 `RPUSH`，读取时用 `LRANGE key -N -1` 只取最近 N 条，避免 Session 变成大 key。

### Redis 的 Set 是否有序、是否可重复？ | 高频
Set 是**无序、不可重复**的集合。

- **无序**：元素没有固定顺序，`SMEMBERS` 的返回顺序不保证一致。intset 编码下内部恰好按整数大小有序存储，但这是实现细节，不能依赖。需要有序请用 ZSet。
- **不可重复**：重复 `SADD` 同一个元素不会报错，返回 0，集合不变。
- **底层实现**：intset（全是整数且元素少）、listpack（7.2 起，元素少且不全是整数）、hashtable（其他情况，value 为 NULL 的 dict），因此 `SADD`、`SREM`、`SISMEMBER` 平均 O(1)。
- **常用场景**：去重、标签、关注/粉丝、共同好友（`SINTER`）、抽奖（`SRANDMEMBER`/`SPOP`）。

## 线程模型与性能
### Redis 是单线程的，为什么还这么快？ | 高频 | 招商银行、农业银行、滴滴
先澄清：Redis 只是**命令执行**是单线程的。快的原因主要有四点：纯内存操作、I/O 多路复用、单线程执行没有锁竞争和上下文切换、底层数据结构高效。

- **基于内存（最主要原因）**：数据都在内存中，读写不涉及磁盘 I/O，单次操作是纳秒到微秒级。
- **I/O 多路复用**：用 epoll（Linux）/ kqueue（BSD、macOS）让一个线程同时监听成千上万个连接，只处理已就绪的事件，不用为每个连接建线程。
- **单线程执行命令**：没有多线程的锁竞争、线程切换和上下文切换开销，命令天然串行、原子。
- **高效的数据结构**：SDS、dict（渐进式 rehash）、skiplist、listpack、intset 等，大部分操作是 O(1) 或 O(log N)，小数据量还用紧凑编码节省内存。
- **瓶颈不在 CPU**：多数命令计算量很小，性能瓶颈通常是内存和网络带宽，单线程已足够。

**线程模型补充**
- Redis 6.0 起可开启 I/O 多线程（`io-threads`，默认关闭），把网络读写和协议解析分给多个线程，命令执行仍在主线程。
- 另有后台 bio 线程负责关闭文件、AOF fsync、lazy free 异步释放内存。
- RDB 快照和 AOF 重写由 fork 出的**子进程**完成，不是线程。

### Redis 是单线程还是多线程？
不能简单说单线程或多线程：**命令执行（读写内存数据）一直是单线程**，但整个 Redis 进程从来不是只有一个线程。

| 版本 | 变化 |
| --- | --- |
| 早期 | 网络 I/O 与命令执行都在主线程，靠 I/O 多路复用支撑高并发 |
| 2.4 起 | 引入后台 bio 线程，处理关闭文件、AOF fsync |
| 4.0 起 | 新增 lazy free：`UNLINK`、`FLUSHALL ASYNC`、`FLUSHDB ASYNC` 以及 `lazyfree-*` 配置，让大 key 的内存释放交给后台线程 |
| 6.0 起 | 引入网络 I/O 多线程（默认关闭），多个 I/O 线程并行读请求、解析协议、写回响应，命令仍由主线程串行执行 |

**注意区分**
- `bgsave`、`bgrewriteaof` 是 **fork 出的子进程**，利用 Copy-On-Write 生成文件，不是后台线程。
- 多线程只是用来分担耗时任务和网络 I/O，不会有多个线程同时修改数据，所以 Redis 命令依然不需要加锁、天然原子。

### Redis 为什么用单线程执行命令？
因为 Redis 的瓶颈不在 CPU，而在内存和网络 I/O；单线程执行命令能让实现简单、性能稳定，同时避免多线程带来的额外开销。

- **避免锁竞争**：所有数据结构共享在内存中，多线程执行命令就需要对每个结构加锁，既复杂又损耗性能；单线程串行执行天然线程安全，每条命令都是原子的。
- **减少上下文切换**：Redis 命令通常在微秒级完成，多线程切换的开销可能比命令本身还大。
- **内存操作本身够快**：简单命令单线程即可达到每秒 10 万级 QPS。
- **配合 I/O 多路复用**：一个线程即可管理大量连接，并发能力不依赖多线程。
- **实现与调试简单**：没有死锁、竞态问题，数据结构可以针对单线程优化（如渐进式 rehash）。

**代价**：单个慢命令（`KEYS *`、大 key 的 `HGETALL`/`DEL`、复杂 Lua 脚本）会阻塞所有请求；也无法用多核做计算。多核扩展一般靠部署多个实例或 Cluster。

### 为什么 Redis 6.0 之后引入多线程？一定比单线程快吗？
6.0 引入的多线程只针对**网络 I/O**（读 socket、解析协议、写回响应），命令执行仍是单线程。目的是在高并发、网络 I/O 成为瓶颈时利用多核 CPU。

**为什么引入**
- 随着硬件发展，单个 Redis 实例在高并发小请求下，CPU 大量时间花在 socket 读写和协议解析上，主线程成为瓶颈，而多核闲置。
- 把 I/O 交给多个线程并行处理，主线程只专注执行命令，简单命令为主的高并发场景下吞吐量可以明显提升。
- 命令执行保持单线程，不需要引入复杂的并发控制，兼容原有的原子语义。

**配置**
```conf
io-threads 4            # 默认 1，即关闭；一般设置为小于 CPU 核数，如 4 核设 2~3
io-threads-do-reads yes # 默认只用多线程写回响应，开启后读请求也用多线程
```

**一定比单线程快吗？不一定**
- 适合：高并发、连接多、网络流量大、CPU 核数充足的场景。
- 帮助不大：QPS 不高时网络本来不是瓶颈；瓶颈在慢命令或大 key（命令执行仍在主线程）；CPU 核数少时线程反而争抢资源。
- 所以默认关闭，需要压测确认收益后再开启。

### Redis 的 IO 多路复用原理是什么？
I/O 多路复用是让**一个线程同时监听多个 socket**：把所有连接的文件描述符交给内核监听，内核在某些描述符就绪（可读/可写）时通知 Redis，Redis 只处理就绪的连接，从而用单线程处理大量并发连接。

**Redis 的事件驱动模型（Reactor）**
- **多路复用器**：封装了 epoll / kqueue / evport / select，按平台自动选择效率最高的实现（Linux 下是 epoll）。
- **事件循环 aeEventLoop**：主线程循环调用 `epoll_wait` 等待事件。
- **事件分派器与处理器**：
  - 连接应答处理器：监听 socket 可读时 `accept` 新连接，并为它注册读事件。
  - 命令请求处理器：客户端 socket 可读时读取数据、解析命令并执行。
  - 命令回复处理器：结果写入输出缓冲区，socket 可写时发回客户端。
- **时间事件**：同一循环中还处理定时任务 `serverCron`（过期 key 定期删除、rehash、统计等）。

**好处**：不用为每个连接创建线程，没有线程切换开销；配合非阻塞 I/O，线程不会阻塞在某个连接的读写上。

### IO 多路复用有哪些实现方式？（select / poll / epoll）
常见实现有 select、poll、epoll（Linux），以及 BSD/macOS 上的 kqueue。Redis 在 Linux 上使用 epoll。

| 对比 | select | poll | epoll |
| --- | --- | --- | --- |
| fd 存储 | fd_set 位图，有上限（默认 1024） | pollfd 数组，没有固定上限 | 内核红黑树存监听的 fd，就绪链表存就绪 fd |
| 每次调用 | 把整个 fd 集合从用户态拷贝到内核态 | 同 select | 通过 `epoll_ctl` 注册一次，`epoll_wait` 无需重复拷贝 |
| 就绪检测 | 内核线性遍历所有 fd，O(n) | 同 select，O(n) | 回调机制把就绪 fd 加入就绪链表，O(1) 获取 |
| 返回 | 用户还要再遍历一遍找就绪 fd | 同 select | 只返回就绪的 fd |
| 触发方式 | 水平触发 | 水平触发 | 支持水平触发（LT）和边缘触发（ET） |

**结论**：select/poll 的开销随连接数线性增长，适合连接少的场景；epoll 只关心活跃连接，在大量连接、少量活跃的场景下性能优势明显。kqueue 是 BSD 系统上的同类实现，机制与 epoll 类似。

### Redis 后台线程是做什么的？
Redis 的后台线程（bio，background I/O）用来处理可能阻塞主线程的耗时操作，主要有三类，各有一个线程和任务队列：

- **关闭文件（BIO_CLOSE_FILE）**：如 AOF 重写完成后关闭旧文件，`close` 大文件可能很慢。
- **AOF 刷盘（BIO_AOF_FSYNC）**：`appendfsync everysec` 时，每秒的 `fsync` 由后台线程执行。
- **惰性释放内存（BIO_LAZY_FREE，4.0 起）**：`UNLINK`、`FLUSHALL ASYNC`、`FLUSHDB ASYNC`，以及开启 `lazyfree-lazy-eviction`、`lazyfree-lazy-expire`、`lazyfree-lazy-server-del` 等配置后，对淘汰、过期、隐式删除的 key 的内存释放。

**容易混淆的点**
- RDB 快照（`bgsave`）和 AOF 重写（`bgrewriteaof`）由 **fork 出的子进程**完成，不是后台线程。
- 内存淘汰策略的判断和执行在**主线程**中进行，只有开启 `lazyfree-lazy-eviction` 后，被淘汰 key 的内存释放才交给后台线程。
- 6.0 的 I/O 线程是另一套线程，负责网络读写，与 bio 线程不同。

## 持久化
### Redis 持久化机制有哪些？RDB 和 AOF 有什么区别、各自优缺点？ | 高频 | 邮政储蓄银行、字节、网易
Redis 有三种持久化方式：RDB 快照、AOF 日志，以及 4.0 引入的混合持久化。默认配置下 RDB 开启、AOF 关闭（`appendonly no`）；两者同时开启时，重启优先用 AOF 恢复。

- **RDB**：按条件（`save 900 1` 等）或手动 `bgsave` 把某一时刻的内存数据生成压缩的二进制快照文件 `dump.rdb`。
- **AOF**：把每条写命令以 RESP 协议文本追加到日志，重启时按顺序重放。开启后默认 `appendfsync everysec`。
- **混合持久化**：AOF 重写时先写 RDB 格式的全量数据，再追加增量命令。`aof-use-rdb-preamble` 从 5.0 起默认 yes。

| 对比 | RDB | AOF |
| --- | --- | --- |
| 内容 | 某时刻的数据快照（二进制、压缩） | 写命令日志（文本） |
| 数据安全 | 会丢失最后一次快照之后的数据，通常是分钟级 | 取决于刷盘策略：everysec 最多丢约 1 秒，always 几乎不丢，no 由操作系统决定 |
| 文件体积 | 小，适合备份和全量复制 | 大，需要定期重写 |
| 恢复速度 | 快，直接加载 | 慢，要逐条重放命令 |
| 性能影响 | fork 子进程时有短暂阻塞，数据量大时生成成本高 | 每次写都要追加，always 策略对性能影响大 |
| 可读性 | 不可读 | 可读，误操作（如 `FLUSHALL`）后可手工编辑 AOF 恢复 |

**如何选择**：只做缓存可只开 RDB 甚至不开；数据安全要求高时开 AOF（everysec）+ 混合持久化，保留 RDB 做冷备。always 性能下降明显，一般不用。

**版本变化**：7.0 起为 Multi Part AOF（base 文件 + incr 增量文件 + manifest），重写不再需要重写缓冲区。

### RDB 异步持久化（bgsave）的原理是什么？ | 高频
`bgsave` 由主进程 fork 出子进程，子进程把内存数据写成 RDB 文件，主进程继续处理请求；两者通过操作系统的 **Copy-On-Write** 共享内存。

**触发方式**
```conf
save 900 1      # 900 秒内至少 1 个 key 被修改
save 300 10     # 300 秒内至少 10 个 key 被修改
save 60 10000   # 60 秒内至少 10000 个 key 被修改
```
- 满足 `save` 条件时自动执行 `bgsave`；主从全量复制、正常 `SHUTDOWN` 时也会触发。
- `save` 命令：主进程直接执行，期间阻塞所有客户端请求，线上不推荐。
- `bgsave` 命令：fork 子进程执行，是常用方式。

**执行过程**
1. **fork 子进程**：主进程 fork 时要复制页表（不复制物理内存），这一步会阻塞主进程，内存越大页表越大，阻塞时间越长（可通过 `INFO stats` 的 `latest_fork_usec` 观察）。
2. **子进程写文件**：子进程遍历共享内存中的数据，写入临时 RDB 文件，完成后原子替换旧文件。
3. **Copy-On-Write**：fork 后主子进程共享物理页，页被标记为只读。主进程修改某个页时，内核先复制该页，主进程在副本上修改，子进程看到的仍是 fork 那一刻的数据，所以快照是一致的。

**注意点**
- 写入频繁时大量页被复制，内存最坏可能接近翻倍，要预留内存，避免 OOM。
- 建议关闭 Linux 透明大页（THP），否则一次写入就复制 2MB 的大页，放大 COW 开销。
- 同一时间只允许一个 `bgsave` 或 `bgrewriteaof` 子进程。

### AOF 持久化的原理和刷盘策略？ | 高频
AOF（Append Only File）把每条写命令追加到日志文件，重启时按顺序重放来恢复数据。

**写入流程**
1. 主线程先执行写命令、修改内存。
2. 把命令按 RESP 格式追加到 `aof_buf` 缓冲区。
3. 在事件循环中把 `aof_buf` 写入（`write`）AOF 文件，此时数据在内核的 page cache 中。
4. 按刷盘策略调用 `fsync` 真正落盘。

先执行命令再写日志的好处：不用校验命令是否合法（错误命令不会被记录），也不阻塞当前命令；代价是命令执行后、写日志前宕机，这条命令会丢失。

**三种刷盘策略（appendfsync）**

| 策略 | 做法 | 数据安全 | 性能 |
| --- | --- | --- | --- |
| always | 每次写命令后同步 fsync | 最高，几乎不丢 | 最差 |
| everysec（默认） | 每秒由后台线程执行一次 fsync | 最多丢约 1 秒数据（磁盘慢时可能略多） | 折中 |
| no | 不主动 fsync，由操作系统决定（Linux 通常约 30 秒） | 可能丢较多 | 最好 |

### 为什么需要 AOF 重写？重写是怎么做的？ | 高频
AOF 只追加，文件会越来越大，恢复也越来越慢；而同一个 key 的多次修改只有最终状态有意义。AOF 重写就是根据**当前内存中的数据**生成一份最精简的命令集合，替换旧 AOF。

```text
SET name a
SET name b
SET name c      # 重写后只需要保留 SET name c
```

**注意**：重写不读取、分析旧 AOF 文件，而是直接遍历当前数据库，每个 key 生成一条（或几条批量）写入命令。

**触发方式**
- 手动：`BGREWRITEAOF`。
- 自动：同时满足两个条件
  - `auto-aof-rewrite-percentage 100`：当前 AOF 比上次重写后增长了 100%。
  - `auto-aof-rewrite-min-size 64mb`：AOF 至少达到 64MB，避免文件很小时频繁重写。

**重写过程（7.0 之前）**
1. 主进程 fork 子进程，子进程根据内存快照写新的 AOF 临时文件。
2. 重写期间主进程继续处理命令，新命令同时写入 `aof_buf`（保证旧 AOF 正常）和 **AOF 重写缓冲区**。
3. 子进程完成后通知主进程，主进程把重写缓冲区的内容追加到新文件，再原子替换旧文件。

**7.0 起（Multi Part AOF）**：重写时主进程直接打开一个新的 incr 文件写入增量命令，子进程只生成新的 base 文件，完成后更新 manifest，不再需要重写缓冲区，减少了内存开销和主进程的拷贝工作。

重写会消耗 CPU、内存（COW）和磁盘 I/O，应避开业务高峰。

### 什么是混合持久化（RDB + AOF）？ | 高频
混合持久化是 4.0 引入、5.0 起默认开启（`aof-use-rdb-preamble yes`）的 AOF 重写方式：重写时新 AOF 文件的开头是 RDB 格式的全量数据，后面是 AOF 格式的增量命令，兼顾 RDB 恢复快和 AOF 丢数据少的优点。

```text
[RDB 格式的全量数据][AOF 格式的增量写命令]
```

- **RDB 部分**：重写开始时，子进程把当前内存数据以 RDB 格式写入文件开头，加载速度和 RDB 一样快。
- **AOF 部分**：重写期间及之后的写命令以 AOF 格式追加在后面，保留最新变更，丢失数据量和 AOF 一致（everysec 最多约 1 秒）。
- 7.0 起体现为 Multi Part AOF 中 base 文件是 RDB 格式，incr 文件是 AOF 格式。

**优点**：恢复速度比纯 AOF 快，数据安全性比纯 RDB 高。
**缺点**：AOF 文件中 RDB 部分是二进制，不再完全可读；4.0 之前的版本无法识别这种格式，不向下兼容。

## 过期删除与内存淘汰
### Redis 的过期删除策略是什么？内存满了怎么办？ | 高频
Redis 用「**惰性删除 + 定期删除**」处理过期 key；内存达到 `maxmemory` 上限后，再由**内存淘汰策略**（`maxmemory-policy`）决定删除哪些 key。这是两套不同的机制。

![](images/Java+AI八股-image-10.png)

**常见的过期删除策略**

| 策略 | 做法 | 优缺点 |
| --- | --- | --- |
| 定时删除 | 为每个 key 设定时器，到期立即删除 | 内存最友好，但定时器多，CPU 开销最大；Redis 不采用 |
| 惰性删除 | 访问 key 时才检查是否过期，过期就删 | CPU 最友好，但不被访问的过期 key 会一直占内存 |
| 定期删除 | 周期性随机抽查一批设置了过期时间的 key，删除其中过期的 | 折中，需要控制频率和时长 |

**Redis 的实现**
- **惰性删除**：所有读写命令执行前都会调用 `expireIfNeeded` 检查 key 是否过期。
- **定期删除**：`serverCron` 默认每秒 10 次（`hz 10`，即每 100ms）执行：从带过期时间的 key 中随机抽取 20 个，删除其中已过期的；如果过期比例超过 25%，就继续抽取下一轮，同时有执行时长上限（默认不超过 25ms），避免长时间阻塞主线程。
- 两者结合：惰性删除保证访问时不会读到过期数据，定期删除回收不被访问的过期 key。

**内存满了怎么办**：内存使用超过 `maxmemory` 时，每次执行命令前按 `maxmemory-policy` 淘汰 key。默认 `noeviction`，写命令直接报错，读命令照常执行；纯缓存场景一般配置 `allkeys-lru` 或 `allkeys-lfu`。详见下面两题。

### 删除一个 key 会立刻被清理吗？持久化时对过期键怎么处理？ | 滴滴、小红书、银行、阿里
主动删除时：`DEL` 立即删除并同步释放内存；`UNLINK`（4.0 起）立即从键空间摘除，内存交给后台线程异步释放。而**过期 key 不会到点立刻删除**，要等惰性删除（被访问时）或定期删除（被抽查到）。

**RDB 对过期键的处理**
- 生成 RDB 时：跳过已过期的 key，不写入文件。
- 加载 RDB 时：主节点会检查并忽略已过期的 key；从节点会全部载入，但随后主从全量同步时会被主节点的数据覆盖，因此没有影响。

**AOF 对过期键的处理**
- 写入阶段：过期 key 被惰性或定期删除时，向 AOF 追加一条 `DEL` 命令。
- 重写阶段：AOF 重写时会跳过已过期的 key。

**主从复制中的过期键**
- 从节点不会主动删除过期 key，统一等主节点删除后同步过来的 `DEL`，保证主从一致。
- 3.2 起客户端读从节点时，如果 key 已逻辑过期，会返回空，避免读到过期数据。

**删除大 key**：推荐用 `UNLINK`，或开启 `lazyfree-lazy-expire`、`lazyfree-lazy-server-del` 等配置，避免同步释放大量内存阻塞主线程。

### Redis 有哪些内存淘汰策略？ | 高频
内存达到 `maxmemory` 后，Redis 按 `maxmemory-policy` 选择淘汰对象。目前共 **8 种**（4.0 新增两种 LFU），默认 `noeviction`。

| 范围 | 策略 | 说明 |
| --- | --- | --- |
| 不淘汰 | `noeviction`（默认） | 不删除任何 key，写命令返回 OOM 错误，读命令正常 |
| 只在设置了过期时间的 key 中淘汰 | `volatile-lru` | 淘汰最久未使用的 |
| | `volatile-lfu`（4.0+） | 淘汰访问频率最低的 |
| | `volatile-random` | 随机淘汰 |
| | `volatile-ttl` | 优先淘汰剩余 TTL 最短的 |
| 在所有 key 中淘汰 | `allkeys-lru` | 淘汰最久未使用的 |
| | `allkeys-lfu`（4.0+） | 淘汰访问频率最低的 |
| | `allkeys-random` | 随机淘汰 |

`volatile-*` 策略下，如果没有设置过期时间的 key 可淘汰，行为与 `noeviction` 相同。

![](images/Java+AI八股-image-11.png)

**Redis 的 LRU 和 LFU 都是近似实现**
- **近似 LRU**：对象头 24 位 `lru` 字段记录最近访问时间，淘汰时随机采样 `maxmemory-samples`（默认 5）个 key，淘汰最久未访问的；不用维护全局链表，省内存也省移动开销。
- **LFU（4.0+）**：复用 24 位字段，高 16 位存上次访问时间，低 8 位存对数增长的访问计数（最大 255），长时间不访问会衰减，解决 LRU 的缓存污染（偶尔访问一次的冷数据长期驻留）。

### 内存淘汰策略如何选择？ | 高频
核心看两点：是不是所有数据都允许被淘汰、访问模式是看「最近」还是看「频率」。

- **纯缓存场景**（所有数据都能从数据库重建）：用 `allkeys-lru`，最通用；如果热点长期稳定、存在大量偶尔访问的冷数据，用 `allkeys-lfu`。
- **缓存与持久数据混用**：需要长期保存的 key 不设过期时间，缓存 key 设过期时间，选 `volatile-lru` 或 `volatile-lfu`，只在缓存 key 中淘汰。更推荐把两类数据拆到不同实例。
- **数据访问概率均匀**：`allkeys-random`。
- **希望按过期时间先后淘汰**：`volatile-ttl`，适合 TTL 能反映数据价值的场景。
- **不允许丢任何数据**（Redis 当存储用）：`noeviction`，必须配合内存监控、告警和扩容，否则写入会失败。

**大模型会话 Session 场景**：Session 是临时上下文，所有 Session key 都应设置 TTL，选 `volatile-lru`，长时间不活跃的会话优先淘汰，同时不影响未设置 TTL 的关键数据；如果存在少量高频会话（如企业知识库、客服连续对话），可选 `volatile-lfu`。不建议用 `noeviction`。

**配套建议**：合理设置 `maxmemory`（一般为物理内存的 60%~70%，给 fork 的 COW 和碎片留空间）；开启 `lazyfree-lazy-eviction` 让淘汰大 key 时异步释放内存。

1. List、Set、Map的区别

List 和 Set 都继承 Collection,存单个元素;Map 存键值对,不继承 Collection。

List Set Map
存储 单个元素 单个元素 key-value
有序 按插入顺序,可按下标访问 一般无序(LinkedHashSet 保持插入序,TreeSet 排序) 一般无序(LinkedHashMap / TreeMap 有序)
重复 允许重复 不允许重复(依赖 equals/hashCode 或比较器) key 不重复,value 可重复
null 允许多个 HashSet 允许一个 null,TreeSet 不允许 HashMap 允许一个 null key;TreeMap、ConcurrentHashMap 不允许 null key

核心区别:wait 会释放锁,sleep 不会释放锁。

3. JVM的堆分为哪几部分

堆分为新生代和老年代,新生代又分为 Eden 区和两个 Survivor 区(S0/S1)。

  • 新生代:默认占堆的 1/3(-XX:NewRatio=2,老年代:新生代 = 2:1)。Eden:S0:S1 默认 8:1:1(-XX:SurvivorRatio=8)。新对象在 Eden 分配,Minor GC 时存活对象复制到一个 Survivor 区,两个 Survivor 轮流使用,每次只用一个。
  • 老年代:对象年龄达到阈值(-XX:MaxTenuringThreshold,默认 15)、大对象、Survivor 放不下的对象进入老年代,满了触发 Major/Full GC。
  • 方法区:JDK 7 及之前用永久代实现,属于堆的一部分;JDK 8 移除永久代,改为元空间(Metaspace),使用本地内存,不在堆里。字符串常量池和静态变量在 JDK 7 已移到堆中。

补充:G1(JDK 9 起默认收集器)把堆划分为大小相等的 Region,新生代/老年代只是逻辑概念,还有专门存大对象的 Humongous Region。

4. 消息中间件有什么作用，哪些场景下需要用到异步？

消息中间件的三大作用是解耦、异步、削峰。

  • 解耦:生产者只管发消息,新增下游系统只需订阅,不用改上游代码。
  • 异步:非核心步骤放到 MQ 后台处理,主流程快速返回,降低响应时间。
  • 削峰:突发流量先进队列,消费者按自身能力拉取,保护数据库等下游。
  • 此外还能做广播通知、基于可靠消息实现最终一致性、延迟任务(如订单超时取消)。

适合异步的场景:主流程不依赖其结果、允许短暂延迟的操作。例如:用户注册后发邮件/短信;下单后加积分、发优惠券、通知物流;秒杀下单先扣 Redis 库存再异步落库;日志、埋点采集;搜索索引同步。

引入 MQ 的代价:系统复杂度和可用性风险上升,需要处理消息丢失、重复消费、顺序性和一致性问题。需要强实时、强一致返回结果的步骤(如支付扣款结果)不适合异步。

5. 如何对当日产生的上百万条数据的日志信息做删除？

不要一条 DELETE 删完,应该分批删除,或者从设计上用分区表 / 按天分表直接删整块。

  • 问题:一次删上百万行会形成大事务,长时间持有锁、产生大量 undo/binlog,导致主从延迟,失败回滚也很慢。
  • 分批删除:按主键范围或 LIMIT 分批,每批几千行,批次间短暂停顿:
DELETE FROM log WHERE create_time >= '2026-11-06' AND create_time < '2026-11-07' LIMIT 5000;

循环执行直到影响行数为 0,create_time 上要有索引。

  • 分区表(推荐):按天做 RANGE 分区,删除当天数据直接 ALTER TABLE log DROP PARTITION p20261106;(或 TRUNCATE PARTITION),几乎瞬间完成,不逐行写日志。
  • 按天分表:日志写入 log_20261106,删除时 DROP TABLE 或 TRUNCATE。
  • 保留少量删大量:可以把要保留的数据导到新表,再 RENAME 互换,然后删除旧表。

删除放在业务低峰期执行;DELETE 后表空间不会自动收缩,需要时用 OPTIMIZE TABLE 回收。

6. IO多路复用机制是什么

IO 多路复用是指一个线程通过一个系统调用同时监听多个文件描述符(socket),哪个 fd 就绪就处理哪个,避免为每个连接开一个线程阻塞等待。Linux 上有 select、poll、epoll 三种实现。

select poll epoll
存储 fd 位图 fd_set 链表/数组 pollfd 内核红黑树 + 就绪链表
连接上限 默认 1024 无硬限制 无硬限制
每次调用 把整个 fd 集合拷贝到内核 同样全量拷贝 epoll_ctl 注册一次,不用重复拷贝
找就绪 fd 遍历 O(n) 遍历 O(n) 回调放入就绪链表,epoll_wait 直接返回就绪 fd
触发方式 水平触发 水平触发 支持水平触发 LT 和边缘触发 ET

epoll 适合大量连接但活跃连接少的场景。Redis、Nginx、Netty 底层都用 epoll;Java NIO 的 Selector 在 Linux 上也基于 epoll。

7. 事务的四大特性（ACID）

ACID 指原子性、一致性、隔离性、持久性。在 InnoDB 中,A、I、D 是手段,C 是目的。

  • 原子性(Atomicity):事务中的操作要么全部成功,要么全部回滚。靠 undo log 实现,回滚时按 undo log 做反向操作。
  • 一致性(Consistency):事务前后数据满足完整性约束和业务规则,比如转账前后总金额不变。由其他三个特性加上应用逻辑共同保证。
  • 隔离性(Isolation):并发事务之间互不干扰。靠锁(写写冲突)和 MVCC(读写并发)实现,隔离程度由隔离级别决定。
  • 持久性(Durability):事务提交后修改永久保存,宕机也不丢。靠 redo log 实现:采用 WAL,先写 redo log 再刷数据页,崩溃后用 redo log 恢复。innodb_flush_log_at_trx_commit=1 时每次提交都刷盘。

8. Spring依赖注入的三种方式

三种方式是构造器注入、Setter 注入、字段注入,Spring 官方推荐构造器注入。

// 1. 构造器注入:只有一个构造器时可省略 @Autowired(Spring 4.3+)
@Service
public class OrderService {
    private final UserService userService;
    public OrderService(UserService userService) { this.userService = userService; }
}
// 2. Setter 注入
@Autowired
public void setUserService(UserService userService) { this.userService = userService; }
// 3. 字段注入
@Autowired
private UserService userService;
方式 优点 缺点
构造器 依赖可设为 final、不可变;对象创建即完整;便于单元测试;能暴露循环依赖 依赖多时构造器参数长
Setter 适合可选依赖,可重新注入 对象可能处于依赖未注入的状态
字段 代码最简洁 不能用 final;脱离容器难以测试;隐藏依赖关系

注意:构造器注入的循环依赖无法靠三级缓存解决,启动直接报错;Spring Boot 2.6 起默认也禁止了字段/Setter 的循环依赖。

9. springAOP中before和after是干什么的，切点的注解？

@Before 是前置通知,在目标方法执行前运行;@After 是后置(最终)通知,在目标方法执行后运行,无论正常返回还是抛异常都会执行,类似 finally。切点用 @Pointcut 定义。

@Aspect
@Component
public class LogAspect {
    @Pointcut("execution(* com.example.service..*.*(..))")
    public void servicePointcut() {}

    @Before("servicePointcut()")
    public void before(JoinPoint jp) { /* 参数校验、记录入参 */ }

    @After("servicePointcut()")
    public void after(JoinPoint jp) { /* 释放资源、记录结束 */ }
}
  • 五种通知:@Before、@After、@AfterReturning(正常返回后,可拿返回值)、@AfterThrowing(抛异常后)、@Around(环绕,可控制是否执行目标方法)。
  • 常用切点表达式:execution(...) 按方法签名匹配;@annotation(com.xx.Log) 匹配带指定注解的方法;within(...) 按类型匹配。
  • 切面类需要 @Aspect 加上 @Component 注册为 Bean。
  • 执行顺序(Spring 5.2.7+):Around 前 → Before → 目标方法 → AfterReturning/AfterThrowing → After → Around 后。

11. 脏读是什么，脏读发生在哪种隔离级别下

脏读是指一个事务读到了另一个事务还未提交的数据,如果对方回滚,读到的就是从没真正存在过的数据。只有在 READ UNCOMMITTED(读未提交) 级别下会发生。

隔离级别 脏读 不可重复读 幻读
READ UNCOMMITTED 可能 可能 可能
READ COMMITTED 不会 可能 可能
REPEATABLE READ(MySQL 默认) 不会 不会 可能(InnoDB 大部分避免)
SERIALIZABLE 不会 不会 不会
  • 不可重复读:同一事务内两次读同一行,结果不同,因为中间有其他事务提交了修改。
  • 幻读:同一事务内两次范围查询,行数不同,因为中间有其他事务插入了数据。
  • InnoDB 在 RR 下,快照读通过 MVCC 的 ReadView 避免幻读,当前读(SELECT ... FOR UPDATE)通过 Next-Key Lock 避免幻读;但快照读和当前读混用时仍可能出现幻读。
  • RC 及以上不会脏读,是因为 MVCC 只读取已提交版本。

12. Java的锁的优化

JDK 6 对 synchronized 做了大量优化,核心是锁升级:无锁 → 偏向锁 → 轻量级锁 → 重量级锁,升级不可逆。

  • 偏向锁:锁总被同一个线程获取时,在对象头 Mark Word 记录线程 ID,之后该线程进入同步块无需 CAS。注意 JDK 15 起默认禁用偏向锁,JDK 18 移除了相关代码。
  • 轻量级锁:有少量线程交替竞争时,线程在栈帧中创建 Lock Record,用 CAS 把 Mark Word 替换为指向它的指针,失败则自旋重试。
  • 重量级锁:自旋失败或竞争激烈时膨胀为重量级锁,依赖 ObjectMonitor 和操作系统互斥量,线程阻塞需要切换到内核态。
  • 自适应自旋:根据上次自旋是否成功动态调整自旋次数。
  • 锁消除:JIT 通过逃逸分析发现锁对象不会被其他线程访问,直接去掉锁。
  • 锁粗化:连续对同一对象反复加锁解锁时,合并成一次范围更大的锁。

代码层面的优化:减小锁粒度、缩短持锁时间、读写分离用 ReentrantReadWriteLock、用 CAS 或原子类代替锁、使用 ConcurrentHashMap 等并发容器。

13. 线程的状态

Java 线程在 Thread.State 中定义了 6 种状态:NEW、RUNNABLE、BLOCKED、WAITING、TIMED_WAITING、TERMINATED。

状态 含义 进入方式
NEW 已创建未启动 new Thread()
RUNNABLE 可运行,包含操作系统层面的就绪和运行中 start()
BLOCKED 等待获取 synchronized 监视器锁 竞争锁失败
WAITING 无限期等待其他线程唤醒 wait()、join()、LockSupport.park()
TIMED_WAITING 限时等待 sleep(ms)、wait(ms)、join(ms)、parkNanos
TERMINATED 执行结束 run() 正常结束或抛出异常

注意点:

  • Java 没有单独的 RUNNING 状态,线程阻塞在 IO 上时也显示 RUNNABLE。
  • 用 ReentrantLock 等 AQS 锁阻塞时,线程状态是 WAITING / TIMED_WAITING,不是 BLOCKED,因为底层用的是 park。
  • 一个线程只能 start() 一次,再次调用会抛 IllegalThreadStateException。

14. @RequestMapping注解作用，提交方式除了get和post还有哪些

@RequestMapping 用来把 HTTP 请求映射到 Controller 的类或方法上,可以按 URL、请求方法、参数、请求头、Content-Type 等条件匹配。

@RestController
@RequestMapping("/users")              // 类上:公共前缀
public class UserController {
    @RequestMapping(value = "/{id}", method = RequestMethod.GET, produces = "application/json")
    public User get(@PathVariable Long id) { ... }

    @PostMapping                       // 等价于 @RequestMapping(method = POST)
    public void create(@RequestBody User u) { ... }
}
  • 常用属性:value/path、method、params、headers、consumes(请求 Content-Type)、produces(响应类型)。
  • 简化注解:@GetMapping、@PostMapping、@PutMapping、@DeleteMapping、@PatchMapping。

HTTP/1.1 请求方法共 8 种:GET、POST、PUT(整体更新/替换)、DELETE(删除)、PATCH(局部更新)、HEAD(只要响应头)、OPTIONS(查询支持的方法,CORS 预检请求用它)、TRACE(回显请求,用于诊断,一般禁用)。另有 CONNECT,用于代理建立隧道。GET、HEAD、PUT、DELETE、OPTIONS、TRACE 是幂等的,POST 不幂等,PATCH 不保证幂等。

15. MVC的流程

Spring MVC 的核心是前端控制器 DispatcherServlet,处理流程如下:

  1. 用户请求到达 DispatcherServlet。
  2. DispatcherServlet 调用 HandlerMapping,根据 URL 找到对应的 Handler(Controller 方法),返回 HandlerExecutionChain(Handler 加上拦截器)。
  3. 通过 HandlerAdapter 适配并调用 Handler,调用前执行拦截器的 preHandle;参数解析器完成参数绑定。
  4. Controller 执行业务逻辑,返回 ModelAndView,之后执行拦截器的 postHandle。
  5. ViewResolver 把逻辑视图名解析为具体 View。
  6. View 用 Model 数据渲染(JSP、Thymeleaf 等),写入响应,最后执行拦截器的 afterCompletion。

前后端分离时用 @RestController / @ResponseBody,不走视图解析和渲染,而是由 HttpMessageConverter(如 Jackson)把返回对象序列化为 JSON 直接写入响应体。异常由 HandlerExceptionResolver 处理,常配合 @RestControllerAdvice + @ExceptionHandler 做全局异常处理。

17. spring的Bean生命周期

可以概括为:实例化 → 属性填充 → 初始化 → 使用 → 销毁,其中初始化阶段有多个扩展点。

  1. 实例化:根据 BeanDefinition 通过反射调用构造器创建对象。
  2. 属性填充:依赖注入,处理 @Autowired、@Value 等。
  3. Aware 回调:BeanNameAware、BeanFactoryAware、ApplicationContextAware 等,注入容器相关对象。
  4. BeanPostProcessor 前置处理:postProcessBeforeInitialization,@PostConstruct 在这一步执行。
  5. 初始化方法:InitializingBean.afterPropertiesSet(),然后是自定义的 init-method / @Bean(initMethod=...)。
  6. BeanPostProcessor 后置处理:postProcessAfterInitialization,AOP 代理对象就在这里生成。
  7. 使用:Bean 放入单例池,供应用使用。
  8. 销毁:容器关闭时依次执行 @PreDestroy、DisposableBean.destroy()、自定义 destroy-method。

补充:只有单例 Bean 由容器管理完整生命周期;prototype Bean 容器只负责创建,不调用销毁方法。循环依赖靠三级缓存在实例化后提前暴露早期引用来解决。

18. 讲讲csrf原理

CSRF(跨站请求伪造)是指攻击者诱导已登录用户访问恶意页面,利用浏览器访问目标站点时自动携带 Cookie 的特性,以用户身份发起非本意的请求,比如转账、改密码。

攻击条件:

  • 用户已登录目标站点,身份凭证存在 Cookie 中且未过期。
  • 目标站点仅凭 Cookie 识别身份,且请求参数可以被预测。
  • 用户访问了攻击者的页面,页面里有自动提交的表单,或 <img src="https://bank.com/transfer?to=x&amount=1000">。

攻击者拿不到 Cookie,也读不到响应(受同源策略限制),只是借用户的浏览器发出请求。

防御:

  • CSRF Token:服务端生成随机 Token,放在表单隐藏字段或请求头中,提交时校验。攻击者无法跨域读取页面,因此拿不到 Token。这是最主要的手段。
  • SameSite Cookie:设为 Strict 或 Lax,跨站请求时不携带 Cookie。Chrome 从 2020 年起对未声明的 Cookie 默认按 Lax 处理,Lax 仍允许顶级导航的 GET 请求带 Cookie。
  • 校验 Origin / Referer 请求头是否来自本站。
  • 关键操作二次验证:短信验证码、输入密码。
  • 用 Authorization: Bearer <token> 请求头传 JWT 而不是 Cookie,天然不受 CSRF 影响。
  • GET 请求不做修改操作。

与 XSS 的区别:XSS 是在目标站点注入并执行脚本;CSRF 是借用用户身份,不需要注入脚本。存在 XSS 时 CSRF Token 可能被窃取,防御会失效。

20. 介绍一下MVC机制

MVC 是一种把应用分成 Model(模型)、View(视图)、Controller(控制器) 三层的设计模式,目的是让数据、展示和控制逻辑解耦。

  • Model:数据和业务逻辑,包括实体类、Service、DAO。
  • View:展示数据,如 JSP、Thymeleaf 页面;前后端分离时 View 由前端负责,后端返回 JSON。
  • Controller:接收请求、调用 Model 处理、选择视图或返回数据,是两者之间的协调者。

好处:职责分离,前后端可以并行开发;同一个 Model 可以对应多个 View;便于维护和测试。

注意:MVC 和后端分层架构(Controller / Service / DAO)不是一回事。在分层架构里,Service 和 DAO 都属于 MVC 中 Model 的范畴。

24. 内存溢出

内存溢出(OOM,OutOfMemoryError)是指 JVM 内存不够分配新对象,GC 之后仍无法回收出足够空间。除了程序计数器,其他运行时数据区都可能发生 OOM。

区域 报错信息 常见原因
堆 Java heap space 内存泄漏(静态集合不断增长、ThreadLocal 未 remove)、一次性加载大量数据、-Xmx 设置过小
堆 / GC GC overhead limit exceeded 98% 以上的时间在做 GC,但回收不到 2% 的堆
元空间(JDK 8+) Metaspace 动态生成大量类(CGLIB、反射)、类加载器泄漏
虚拟机栈 通常是 StackOverflowError;无法创建线程时为 unable to create new native thread 递归过深;线程过多
直接内存 Direct buffer memory NIO/Netty 的 DirectByteBuffer 未释放

排查思路:

  1. 添加启动参数 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=...,OOM 时自动导出堆转储;也可以用 jmap -dump:live,format=b,file=heap.hprof <pid> 手动导出。
  2. 用 MAT 或 VisualVM 分析,找出占用最大的对象和 GC Roots 引用链。
  3. 判断是内存泄漏(修改代码)还是内存溢出(堆确实不够,调大 -Xmx 或优化数据结构)。
  4. 用 jstat -gcutil 观察 GC 情况。

注意区分:内存泄漏是对象不再使用却无法被回收,泄漏积累下去最终会导致内存溢出。

27. synchronize

synchronized 是 JVM 层面的可重入、非公平、独占的互斥锁,保证原子性、可见性和有序性。

用法:

  • 修饰实例方法:锁当前对象 this。
  • 修饰静态方法:锁当前类的 Class 对象。
  • 修饰代码块:锁括号中指定的对象。

底层原理:

  • 同步代码块编译后生成 monitorenter 和 monitorexit 字节码指令(通常有两个 monitorexit,第二个用于异常时释放锁);同步方法通过方法的 ACC_SYNCHRONIZED 标志实现。
  • 每个对象关联一个 Monitor,HotSpot 中的实现是 ObjectMonitor,包含 _owner(持有锁的线程)、_recursions(重入次数)、_EntryList(等待锁的线程)、_WaitSet(调用了 wait 的线程)。
  • 锁状态记录在对象头的 Mark Word 中。

锁升级(JDK 6 引入):无锁 → 偏向锁 → 轻量级锁(CAS + 自旋) → 重量级锁(ObjectMonitor,线程阻塞)。JDK 15 起偏向锁默认关闭。

与 ReentrantLock 对比:synchronized 自动加锁和释放锁,不能中断等待,只能是非公平锁,只有一个等待队列;ReentrantLock 需要手动 unlock,支持 lockInterruptibly、tryLock 超时、公平锁和多个 Condition。

分布式事务没有完美方案,要在强一致性和性能/可用性之间权衡。基于 CAP 和 BASE 理论,大多数互联网业务选择最终一致性。

方案 原理 一致性 优缺点
2PC / XA 协调者先让各参与者准备(Prepare),全部成功再提交(Commit) 强一致 同步阻塞、性能差;协调者单点问题

TCC Try 预留资源 → Confirm 确认 → Cancel 取消 最终一致 性能好,但业务侵入大;需要处理空回滚、悬挂和幂等

Saga 长事务拆成多个本地事务,失败时按反向顺序执行补偿操作 最终一致 适合长流程;没有隔离性

选型:金融等需要强一致的场景用 XA 或 TCC;一般业务优先选 MQ 可靠消息或 Seata AT。最好的方案是通过业务设计尽量避免分布式事务。

29. Java多态的原理？怎么实现的？

多态是指同一个方法调用,根据对象的实际类型执行不同的实现。Java 运行时多态依靠动态绑定实现,底层是虚方法表(vtable)。

三个必要条件:继承或实现接口、子类重写方法、父类引用指向子类对象。

Animal a = new Dog();
a.speak();   // 编译期按 Animal 检查方法是否存在,运行时调用 Dog.speak()

底层实现:

  • 编译期:编译器只知道静态类型 Animal,生成 invokevirtual Animal.speak 指令(接口方法用 invokeinterface)。
  • 类加载的链接阶段:JVM 为每个类建立虚方法表,表中存放各方法实际入口地址。子类重写的方法会覆盖对应的表项,没有重写的指向父类实现;同一个方法在父子类表中的索引相同。
  • 运行期:执行 invokevirtual 时,根据栈上对象的实际类型(通过对象头中的类型指针找到 Klass),在该类的 vtable 中按索引找到方法并调用。
  • 接口方法使用接口方法表(itable)查找。JIT 还会通过内联缓存、类层次分析做去虚拟化优化。

补充:方法重载是编译期确定的(静态分派);static、private、final 方法和构造器不参与多态(用 invokestatic/invokespecial 调用,在编译期或类加载时就确定了目标)。字段也没有多态,访问字段看的是引用的静态类型。

30. C++三特性

C++ 面向对象的三大特性是封装、继承、多态,与 Java 相同,但实现细节有差异。

  • 封装:把数据和操作数据的方法封装在类中,用 public/protected/private 控制访问。C++ 的 class 默认是 private,struct 默认是 public;还可以用 friend 友元突破访问限制。

31. 如何保证线程安全

线程安全问题来自多个线程同时读写共享的可变数据。解决思路是围绕原子性、可见性、有序性,从"不共享、不可变、加同步"三个方向入手。

  • 互斥同步(加锁):synchronized、ReentrantLock;读多写少的场景用 ReentrantReadWriteLock 或 StampedLock。
  • 非阻塞同步(CAS):AtomicInteger、AtomicReference;高并发计数用 LongAdder,它把热点分散到多个 Cell 上,减少 CAS 冲突。
  • volatile:保证可见性和有序性(禁止指令重排),但不保证复合操作的原子性,count++ 仍然不安全。适合状态标志位和 DCL 单例。
  • 不共享数据:用局部变量(线程栈私有);用 ThreadLocal 为每个线程保存一份副本,用完要 remove,防止线程池场景下的内存泄漏。
  • 不可变对象:final 字段、String、不可变集合,一经创建就无法修改,天然线程安全。
  • 并发容器:ConcurrentHashMap、CopyOnWriteArrayList、BlockingQueue,替代 HashMap、ArrayList。
  • 并发工具类:CountDownLatch、Semaphore、CyclicBarrier 协调多个线程。
  • 分布式场景:单机锁失效,需要用 Redis/Redisson 或 ZooKeeper 实现分布式锁,或用数据库的乐观锁(版本号)。

32. 索引，什么情况下失效？

索引失效的本质是查询无法利用 B+ 树的有序性,或者优化器判断全表扫描的成本更低。常见情况:

  • 违反最左前缀原则:联合索引 (a,b,c),查询条件只有 b、c 时用不上索引。另外,范围查询(>、<)右边的列无法继续用于索引过滤(MySQL 8.0.13+ 的 Skip Scan 在部分场景可以跳过最左列)。
  • 对索引列做运算或使用函数:WHERE YEAR(create_time) = 2026、WHERE id + 1 = 10。
  • 隐式类型转换:字符串类型的列用数字比较,如 phone = 13800000000,MySQL 会对列做类型转换,导致索引失效;反过来,数字列和字符串比较不会失效。
  • 左模糊或全模糊:LIKE '%abc'、LIKE '%abc%' 用不上索引;LIKE 'abc%' 可以用。
  • OR 连接的条件中有一个列没有索引:整个查询会退化为全表扫描。
  • !=、<>、NOT IN、IS NOT NULL:不一定失效,优化器会根据成本决定,当需要回表的行数太多时会选择全表扫描。
  • 优化器估算全表扫描更快:例如区分度低的列(性别),或者扫描范围超过表中很大比例的数据。
  • 字符集或排序规则不一致:关联查询时两个表的字段字符集不同,会导致索引失效。

排查方法:用 EXPLAIN 查看 type(是否为 ALL)、key(实际使用的索引)、rows(预估扫描行数)、Extra(Using filesort、Using temporary 等)。

33. JMM内存模型

JMM(Java 内存模型)是一套规范,定义了多线程环境下共享变量的读写规则,用来屏蔽不同硬件和操作系统的差异,解决可见性、原子性、有序性问题。注意它和 JVM 运行时数据区(堆、栈)不是一个概念。

抽象结构:所有共享变量存放在主内存中;每个线程有自己的工作内存(对应 CPU 缓存和寄存器的抽象),保存共享变量的副本。线程只能操作工作内存,不能直接读写主内存,线程之间也不能直接访问对方的工作内存,必须通过主内存传递数据。

三大特性及其保证方式:

  • 原子性:synchronized、Lock、原子类。
  • 可见性:volatile(写操作立即刷新到主内存,读操作从主内存读取)、synchronized(解锁前把数据刷回主内存)、final。
  • 有序性:volatile 通过插入内存屏障禁止指令重排序;synchronized 保证同一时刻只有一个线程执行同步块。

happens-before 原则(前一个操作的结果对后一个操作可见):

  • 程序顺序规则:单线程中,前面的操作 happens-before 后面的操作。
  • 监视器锁规则:解锁 happens-before 之后对同一把锁的加锁。
  • volatile 规则:对 volatile 变量的写 happens-before 之后对它的读。
  • 线程启动规则:start() happens-before 线程中的所有操作。
  • 线程终止规则:线程中的所有操作 happens-before 其他线程检测到它结束(join() 返回)。
  • 传递性:A hb B,B hb C,则 A hb C。

34. MQ消息可靠性

要保证消息不丢,需要在生产端、Broker、消费端三个环节都做保障。以 RabbitMQ 为例:

  • 生产端:
    • 开启 Publisher Confirm:Broker 收到消息后返回 ack,收到 nack 或超时就重试。
    • 开启 Publisher Return:消息路由到队列失败时回调通知生产者。
    • 发送前把消息记录到数据库,定时任务扫描未确认的消息进行补偿重发。
  • Broker 端:
    • 交换机、队列声明为持久化(durable),消息设置为持久化(deliveryMode=2)。
    • 用仲裁队列(Quorum Queue)或镜像集群做高可用。
    • 惰性队列(Lazy Queue)把消息直接写入磁盘,防止消息堆积导致内存溢出。
  • 消费端:
    • 改为手动 ack,业务处理成功后再确认;处理失败时 nack 并重新入队。
    • 配置有限次数的本地重试,超过次数后投递到死信队列,由人工处理。

Kafka 的对应做法:生产端设置 acks=all、retries、开启幂等;Broker 端设置副本数 replication.factor>=3、min.insync.replicas>=2、unclean.leader.election.enable=false;消费端关闭自动提交 offset,业务处理完成后再手动提交。

可靠性措施会带来重复消息,所以消费端必须保证幂等:可以用唯一消息 ID 去重(Redis 或数据库唯一索引)、业务状态机判断、数据库乐观锁。

35. 浏览器中输入一个web页面的url以后会有哪些流程

41. Spring的两个核心思想

Spring 的两个核心思想是 IoC(控制反转) 和 AOP(面向切面编程)。

IoC:

  • 对象的创建和依赖关系由 Spring 容器管理,而不是由代码自己 new。控制权从程序转移到了容器,所以叫控制反转。
  • DI(依赖注入) 是 IoC 的实现方式:容器在创建 Bean 时,把它依赖的对象注入进来。注入方式有构造器注入、Setter 注入、字段注入。
  • 好处是降低耦合:面向接口编程,替换实现类不需要修改调用方;Bean 默认是单例,由容器统一管理生命周期;方便单元测试时注入 Mock 对象。
  • 容器的核心接口是 BeanFactory,常用的是它的子接口 ApplicationContext。

AOP:

  • 把与业务无关、但多个模块都需要的横切逻辑(日志、事务、权限校验、监控)抽取成切面,在不修改业务代码的情况下织入目标方法。
  • 核心概念:切面(Aspect)、切点(Pointcut)、通知(Advice)、连接点(JoinPoint)、织入(Weaving)。
  • 实现方式是动态代理:目标类实现了接口时可以用 JDK 动态代理,否则用 CGLIB 生成子类。注意 Spring Boot 2.x 起默认 proxyTargetClass=true,统一使用 CGLIB。
  • 典型应用:@Transactional 声明式事务就是基于 AOP 实现的。

两者的关系:AOP 依赖 IoC。代理对象是在 Bean 初始化之后,由 BeanPostProcessor 生成并替换原始 Bean,放入容器中的。

42. 如果数据在亿级，然后userid区分度不高，服务器配置不好，如何优化

user_id 区分度不高,说明单个 user_id 对应的数据很多,只靠 user_id 单列索引过滤效果差。思路是:用联合索引提高过滤效率 → 冷热数据分离减少数据量 → 分区/分表 → 把查询转移到其他存储,在硬件有限的情况下优先做低成本的优化。

  1. SQL 和索引优化(成本最低):
    • 分析高频查询条件,建立联合索引,把 user_id 和区分度高的列组合起来,例如 (user_id, create_time)。
    • 尽量使用覆盖索引,避免回表。
    • 禁止 SELECT *;深分页改用游标方式(基于上一页最后一条记录的 ID 或时间查询)。
    • 用 EXPLAIN 和慢查询日志定位问题 SQL。
  2. 冷热数据分离、归档:亿级数据中大部分通常是历史数据。把 3 个月或 1 年前的数据迁移到归档表或其他存储,线上表只保留热数据,数据量可以降低一个数量级。
  3. 分区表:按时间做 RANGE 分区,查询时只扫描相关分区;清理历史数据时直接删除分区。
  4. 分库分表:单表数据仍然很大时,用 ShardingSphere 分表。分片键选择查询最常用的条件:按 user_id 哈希分片可以让同一用户的数据落在同一张表;按时间分片适合按时间范围查询。
  5. 缓存和异构存储:
    • 热点查询结果放入 Redis。
    • 复杂条件查询、统计分析同步到 Elasticsearch 或 ClickHouse,通过 Canal 订阅 binlog 实现数据同步。
  6. 服务器配置有限时的参数调优:合理设置 innodb_buffer_pool_size(专用数据库服务器一般设为物理内存的 50%–70%);读写分离,把读请求分散到从库;统计类查询改为离线预计算,结果存入汇总表。

43. 说一说ArrayList的初始大小，扩容机制

ArrayList 底层是 Object[] 数组。使用无参构造时,初始容量是 0(懒加载),第一次 add 时扩容为 10;之后每次扩容为原来的 1.5 倍。

  • 初始化(JDK 8):无参构造函数把 elementData 指向一个共享的空数组 DEFAULTCAPACITY_EMPTY_ELEMENTDATA,第一次添加元素时才分配容量为 10 的数组。指定初始容量的构造函数会直接创建对应大小的数组;传入 0 时使用另一个空数组 EMPTY_ELEMENTDATA,第一次扩容到 1,不是 10。
  • 扩容时机:添加元素时,如果所需的最小容量 size + 1 大于数组长度,就调用 grow() 扩容。
  • 扩容大小:newCapacity = oldCapacity + (oldCapacity >> 1),即 1.5 倍。如果 1.5 倍仍然不够(例如 addAll 一次添加大量元素),直接使用所需的最小容量。容量上限约为 Integer.MAX_VALUE - 8。
  • 扩容方式:调用 Arrays.copyOf 创建新数组并复制原数据,时间复杂度为 O(n)。

优化建议:能预估数据量时,在构造函数中指定初始容量,或者调用 ensureCapacity,避免频繁扩容和数组拷贝。另外,ArrayList 不会自动缩容,需要时可以调用 trimToSize()。

补充:ArrayList 线程不安全。并发场景下可以使用 CopyOnWriteArrayList,或者用 Collections.synchronizedList 包装。Vector 每次扩容为原来的 2 倍。

45. 如何防止超卖？

超卖的根本原因是**"查询库存 → 判断 → 扣减库存"这三步不是原子操作**,并发时多个线程同时读到库存充足,导致都扣减成功。解决思路是让"判断加扣减"变成原子操作,并且按流量大小分层处理。

  • 数据库乐观锁(最简单可靠):
UPDATE stock SET count = count - 1 WHERE id = ? AND count > 0;

根据影响行数判断是否扣减成功,影响行数为 0 表示库存不足。count > 0 的写法比版本号方式失败率更低。行锁保证了这条语句是原子的,但高并发时会有大量请求竞争同一行的锁,数据库压力大。

  • 悲观锁:SELECT ... FOR UPDATE 锁住库存行,性能较差。
  • Redis 预扣库存(高并发场景):活动开始前把库存加载到 Redis,用 Lua 脚本原子地完成"判断库存、判断用户是否已经下过单、扣减库存、记录用户"。扣减成功后发送 MQ 消息,异步创建订单并扣减数据库库存,数据库层用乐观锁兜底。
  • 分布式锁:用 Redisson 对商品 ID 加锁,性能低于 Lua 脚本方案,适合处理"一人一单"这类需要加锁判断的逻辑。
  • 一人一单:在订单表上建立 (user_id, voucher_id) 唯一索引兜底,防止同一用户重复下单。
  • 配套措施:前端按钮防重复点击;网关限流;库存售罄后在本地内存中标记,后续请求直接返回;订单超时未支付时,通过延迟消息回补库存。

注意:单机的 synchronized 在集群部署时无效,不能防止超卖。

47. Kafka防止消息丢失的办法

需要在 Producer、Broker、Consumer 三个环节都做保障。

Producer 端:

  • 设置 acks=all(等价于 -1):消息被 ISR 中所有副本写入后才算发送成功。注意 Kafka 3.0 起默认值已经是 acks=all,并且默认开启幂等(enable.idempotence=true)。
  • 设置 retries(默认值很大)和 delivery.timeout.ms,在可重试的错误下自动重试。
  • 使用带回调的发送方法 send(record, callback),在回调中处理发送失败的情况(记录日志、落库后补偿重发)。不要只调用 send() 而不检查结果。

Broker 端:

  • replication.factor >= 3:每个分区至少 3 个副本。
  • min.insync.replicas >= 2:配合 acks=all 使用,ISR 中至少有 2 个副本时才允许写入,不满足时生产者会收到异常。
  • unclean.leader.election.enable=false(默认值):禁止落后太多、不在 ISR 中的副本被选为 Leader,否则会丢失数据。
  • Kafka 写入消息后先放在操作系统的页缓存中,依赖多副本机制保证可靠性,而不是每条消息都同步刷盘。

Consumer 端:

  • 关闭自动提交 enable.auto.commit=false,在业务处理完成后再手动提交 offset(commitSync / commitAsync)。
  • 如果先提交 offset 再处理业务,处理失败时消息就丢失了;先处理业务再提交 offset,可能导致重复消费,所以消费逻辑需要保证幂等。

48. Kafka防止重复消费

重复消费不可能完全避免:Consumer 处理完消息但还没提交 offset 时宕机,或者发生 Rebalance,都会导致消息被重新投递;Producer 重试也可能导致消息重复写入。所以核心思路是消费端做幂等,再配合减少重复的手段。

消费端幂等(根本方案):

  • 唯一键去重:每条消息携带唯一的业务 ID(如订单号),消费时把它写入有唯一索引的去重表,或用 Redis 的 SET key NX。写入失败说明已经处理过,直接跳过。
  • 数据库唯一约束:插入数据时依靠唯一索引拦截重复数据。
  • 状态机判断:更新时带上状态条件,例如 UPDATE order SET status='PAID' WHERE id=? AND status='UNPAID',重复执行时不会产生影响。
  • 乐观锁版本号:更新时校验版本号。

减少重复的手段:

  • Producer 开启幂等:enable.idempotence=true,Broker 通过 ProducerID + 序列号对单分区、单会话内的重复消息去重。
  • 跨分区需要 Exactly-Once 时使用 Kafka 事务(transactional.id),配合 Consumer 的 isolation.level=read_committed。Kafka 事务只保证 Kafka 内部"消费 → 处理 → 生产"链路的精确一次,写外部数据库时仍需要幂等处理。
  • 合理设置 max.poll.interval.ms 和 max.poll.records,避免单批处理时间过长被判定为消费者下线,从而触发 Rebalance 导致重复消费。
  • 业务处理完成后及时提交 offset。

49. 如果要实现用户权限管理要怎么办

主流方案是 RBAC(基于角色的访问控制):用户关联角色,角色关联权限,不直接给用户分配权限,方便批量管理。

数据库设计(5 张表):用户表、角色表、权限表(菜单、按钮、接口,通常是树形结构),以及用户-角色关联表、角色-权限关联表。用户和角色、角色和权限都是多对多关系。

实现流程:

  1. 认证:用户登录后,服务端生成 Token(JWT,或者生成随机 Token 存入 Redis),同时查询该用户的角色和权限标识(如 order:delete)缓存到 Redis。
  2. 鉴权:拦截器或 Spring Security 的过滤器解析 Token,得到用户身份;通过注解 @PreAuthorize("hasAuthority('order:delete')") 或自定义注解加 AOP,校验当前用户是否拥有接口所需的权限,没有权限时返回 403。
  3. 前端:后端根据用户权限返回菜单和按钮权限,前端动态生成路由、控制按钮显示。前端控制只是体验优化,必须以后端校验为准。

进阶需求:

  • 数据权限:例如只能查看本部门的数据。可以通过 MyBatis 拦截器动态拼接 SQL 条件实现。
  • 权限变更实时生效:修改用户权限后清除对应的 Redis 缓存。
  • 安全措施:密码用 BCrypt 加盐哈希存储;敏感操作记录审计日志;遵循最小权限原则。
  • 成熟框架:Spring Security、Sa-Token、Apache Shiro。

51. 虚拟内存和物理内存区别

物理内存是实际的内存条(RAM);虚拟内存是操作系统为每个进程提供的一个独立、连续的地址空间。进程使用的都是虚拟地址,由 MMU 通过页表把虚拟地址映射到物理地址。

虚拟内存 物理内存
本质 逻辑地址空间,由操作系统抽象出来 真实的硬件存储
大小 由地址位数决定(64 位 Linux 用户空间通常为 128TB),可以大于物理内存 受实际安装的内存条限制
隔离 每个进程独立,互不可见 所有进程共享
连续性 对进程来说是连续的 实际分配的物理页可以不连续

虚拟内存的作用:

  • 进程隔离:一个进程无法访问另一个进程的内存,安全性更高。
  • 按需加载:程序只需加载正在使用的页。访问的页不在物理内存中时触发缺页中断,操作系统再从磁盘把这一页调入内存;内存不足时,通过页面置换算法(LRU、Clock)把不常用的页换出到磁盘的 swap 分区。
  • 简化编程:每个程序都可以使用相同的地址布局(代码段、数据段、堆、栈)。
  • 共享内存:多个进程的虚拟页可以映射到同一个物理页,例如共享库、mmap、fork 之后的写时复制(Copy-On-Write)。

地址转换:通常采用多级页表(x86-64 为 4 级页表)减少页表占用的空间,并用 TLB(快表)缓存最近使用的地址映射,加快地址转换速度。

52. OOM的情况

OOM(java.lang.OutOfMemoryError)是指 JVM 无法为对象分配足够内存,GC 之后仍然无法释放出足够空间时抛出的错误。除了程序计数器,其他运行时数据区都可能发生 OOM:

类型 常见原因
Java heap space(最常见) 内存泄漏(静态集合只增不删、ThreadLocal 未 remove、连接未关闭、缓存无上限);一次加载大量数据(不分页查询、大文件入内存);-Xmx 过小
GC overhead limit exceeded 超过 98% 时间在 GC 却回收不到 2% 堆内存,接近堆溢出的信号
Metaspace(JDK 7 及以前是 PermGen space) 动态代理 / CGLIB 生成大量类;热部署导致类加载器泄漏
Direct buffer memory NIO / Netty 堆外内存未释放或超过 -XX:MaxDirectMemorySize
unable to create new native thread 线程过多,超过 ulimit -u 或可用内存

53. 进程调度的算法

进程调度算法决定就绪队列中的哪个进程获得 CPU。常见算法有:

算法 原理 特点
先来先服务 FCFS 按到达顺序执行 非抢占,实现简单;长作业在前时短作业等待时间长(护航效应)
短作业优先 SJF 优先执行预计运行时间最短的作业 平均等待时间最短;长作业可能饥饿;需要预估运行时间
最短剩余时间优先 SRTF SJF 的抢占式版本 新到达的进程剩余时间更短时抢占 CPU
高响应比优先 HRRN 响应比 = (等待时间 + 要求服务时间) / 要求服务时间,选最高者 兼顾短作业和等待时间长的作业,避免饥饿
时间片轮转 RR 每个进程轮流执行一个时间片,用完放到队尾 抢占式,公平,响应快;时间片太小时切换开销大,太大时退化为 FCFS
优先级调度 优先级高的进程先执行 可以是抢占式或非抢占式;低优先级进程可能饥饿,通过"老化"(随等待时间提升优先级)解决
多级反馈队列 MLFQ 设置多个优先级不同的队列,优先级越高时间片越短;新进程进入最高优先级队列,时间片用完还没结束就降级到下一级队列 综合了以上算法的优点,短作业响应快,长作业也能执行完成

补充:Linux 2.6.23 起普通进程使用 CFS(完全公平调度器),用红黑树按虚拟运行时间 vruntime 排序,每次选择 vruntime 最小的进程运行;Linux 6.6 起被 EEVDF 调度器取代。实时进程使用 SCHED_FIFO 和 SCHED_RR 策略。

57. Http和Https的区别

HTTPS = HTTP + TLS/SSL。HTTPS 在 HTTP 和 TCP 之间加了一层 TLS,提供加密、身份认证、完整性校验,解决了 HTTP 明文传输带来的被窃听、被篡改、被冒充的问题。

HTTP HTTPS
安全性 明文传输 经过 TLS 加密传输
默认端口 80 443
证书 不需要 需要 CA 签发的数字证书
建立连接 TCP 三次握手后即可传输数据 TCP 握手之后还要进行 TLS 握手:TLS 1.2 需要 2-RTT,TLS 1.3 只需要 1-RTT
性能 开销小 握手和加解密有额外开销,但现代硬件和 TLS 1.3 下影响很小
URL http:// https://

HTTPS 的原理:

  • 非对称加密协商密钥,对称加密传输数据:TLS 握手期间,客户端和服务器通过 ECDHE(TLS 1.3 只允许使用具有前向安全性的密钥交换算法)协商出会话密钥,之后用 AES-GCM、ChaCha20 等对称算法加密实际传输的数据。
  • 数字证书防止中间人攻击:服务器发送自己的证书,浏览器用内置的 CA 根证书沿证书链验证签名,并检查证书中的域名和有效期,确认服务器身份。
  • 完整性校验:使用 AEAD 加密模式或 MAC,防止数据在传输过程中被篡改。

补充:HTTP/2 在浏览器中实际上要求使用 HTTPS;HTTP/3 基于 QUIC 协议(运行在 UDP 之上),内置了 TLS 1.3。

59. tcp四层结构

TCP/IP 模型分四层,从上到下是应用层、传输层、网络层(网际层)、网络接口层,对应 OSI 七层的简化。

层 作用 典型协议 / 设备
应用层 为应用提供服务,对应 OSI 的应用、表示、会话层 HTTP、HTTPS、DNS、FTP、SMTP、SSH
传输层 端到端(进程到进程)通信,端口寻址、可靠性、流量控制 TCP、UDP
网络层 主机到主机的寻址与路由 IP、ICMP、ARP(常归于此层)、路由器
网络接口层 对应 OSI 数据链路层 + 物理层,负责帧的收发 Ethernet、MAC 地址、交换机、网卡

数据发送时逐层封装:应用数据 → 加 TCP/UDP 头成为段(Segment)→ 加 IP 头成为包(Packet)→ 加帧头帧尾成为帧(Frame)→ 比特流;接收方逐层解封装。

面试常追问:TCP 在传输层,靠序号、确认应答、超时重传、滑动窗口、拥塞控制保证可靠;IP 在网络层,只负责尽力而为的投递。

61. 预防解决死锁的方法

死锁要同时满足四个必要条件:互斥、占有并等待、不可剥夺、循环等待,破坏任意一个即可预防。

预防(破坏条件)

  • 破坏占有并等待:一次性申请所有资源,拿不全就都不拿。
  • 破坏不可剥夺:申请不到时主动释放已持有的资源,如 ReentrantLock.tryLock(timeout),超时就释放并重试。
  • 破坏循环等待:所有线程按固定顺序加锁(如按账户 ID 从小到大),这是实践中最常用的方法。
  • 互斥一般无法破坏(资源本身就是独占的)。

避免:分配前判断是否进入不安全状态,典型是银行家算法。

检测与解除:

  • Java 中用 jstack <pid> 或 JConsole / Arthas 的 thread -b 查看,会直接报告 "Found one Java-level deadlock"。
  • 解除:重启、撤销某个线程、回滚。
  • 数据库层面:InnoDB 有死锁检测(innodb_deadlock_detect,默认开启),会回滚代价较小的事务;另有 innodb_lock_wait_timeout(默认 50 秒)兜底。

实际编码:缩小锁范围、避免嵌套锁、统一加锁顺序、使用带超时的锁。

62. 数据库的表锁和行锁有什么作用？

作用都是在并发访问时保证数据一致性,区别在锁粒度:表锁锁整张表,行锁只锁涉及的行。

维度 表锁 行锁
粒度 整张表 单行(InnoDB 实际锁的是索引记录)
加锁开销 小,加锁快 大,加锁慢
并发度 低,冲突概率高 高
死锁 不会出现 可能出现
支持引擎 MyISAM、InnoDB 都支持 InnoDB 支持,MyISAM 不支持

要点:

  • InnoDB 的行锁加在索引上,如果 UPDATE / DELETE 的条件没有走索引,会扫描全表并锁住所有扫描到的记录,效果近似锁表。
  • 行锁类型:记录锁(Record Lock)、间隙锁(Gap Lock)、临键锁(Next-Key Lock);在 RR 隔离级别下用临键锁防止幻读。
  • 表级还有意向锁(IS/IX),用于快速判断表里是否有行锁,避免加表锁时逐行检查;以及 MDL 元数据锁,防止 DML 期间表结构被修改。
  • 显式表锁:LOCK TABLES t READ/WRITE;显式行锁:SELECT ... FOR UPDATE(排他)、SELECT ... FOR SHARE(MySQL 8.0,共享,旧写法 LOCK IN SHARE MODE)。

63. 了不了解dos攻击，怎么防范？

DoS(拒绝服务)攻击是耗尽目标的带宽、连接或计算资源,让正常用户无法访问;用大量肉鸡同时发起就是 DDoS。

常见类型

  • 流量型:UDP Flood、ICMP Flood、DNS / NTP 反射放大攻击,直接打满带宽。
  • 协议型:SYN Flood,伪造源 IP 只发 SYN 不回 ACK,占满服务端半连接队列。
  • 应用层:CC 攻击,大量请求高消耗接口(搜索、登录);慢速攻击(Slowloris)长时间占住连接。

防范

  • 网络层:接入云厂商的高防 IP / 流量清洗、CDN 分散流量;运营商黑洞路由兜底。
  • 协议层:开启 net.ipv4.tcp_syncookies,调大 tcp_max_syn_backlog,减少 SYN+ACK 重试次数。
  • 应用层:网关 / Nginx 限流(limit_req、limit_conn)、IP 黑名单、验证码、WAF 识别异常请求;设置合理的请求超时和连接数上限。
  • 架构上:服务水平扩容、弹性伸缩、核心接口与非核心接口隔离。

66. 讲一下RPC的原理

RPC(远程过程调用)让调用远程服务像调用本地方法一样,核心是动态代理 + 序列化 + 网络传输 + 服务注册发现。

一次调用流程

  1. 客户端调用接口,实际调用的是动态代理(JDK Proxy / Javassist)生成的代理对象。
  2. 代理把接口名、方法名、参数类型、参数值封装成请求对象,序列化(Hessian、Protobuf、JSON、Kryo)。
  3. 从注册中心(Nacos、ZooKeeper)拿到服务提供者地址列表,经负载均衡选一个节点。
  4. 按自定义协议编码(魔数、版本、序列化方式、请求 ID、消息长度 + 消息体,解决 TCP 粘包),通过 Netty 等网络框架发送。
  5. 服务端解码、反序列化,根据接口名找到本地实现,反射调用,把结果按原路返回。
  6. 客户端用请求 ID 匹配响应,唤醒等待的调用(同步调用本质是异步 + Future)。

配套能力:超时、重试、熔断降级、限流、链路追踪。典型框架:Dubbo、gRPC(HTTP/2 + Protobuf)。

与 HTTP 接口对比:RPC 一般基于 TCP 自定义协议,报文更紧凑、性能更好,服务治理能力更完善;HTTP 通用性强、跨语言方便。

67. redis为什么是单线程

准确说法:Redis 执行命令的核心逻辑是单线程的,持久化、异步删除、(6.0 起)网络 I/O 等用了其他线程。

为什么单线程还快

  • 纯内存操作,瓶颈通常在网络和内存,不在 CPU。
  • I/O 多路复用(Linux 上是 epoll),一个线程就能处理大量连接。
  • 避免了多线程的上下文切换和锁竞争,实现简单,天然保证单条命令的原子性。
  • 数据结构高效:SDS、哈希表渐进式 rehash、跳表、listpack 等。

版本演进

  • Redis 4.0:引入后台线程做 UNLINK、FLUSHALL ASYNC 等异步删除。
  • Redis 6.0:引入多线程 网络 I/O(io-threads,默认关闭),读写 socket 和协议解析并行,命令执行仍是单线程。

注意:因为单线程,KEYS *、大 key 删除、HGETALL 大哈希等慢操作会阻塞所有请求,应改用 SCAN、UNLINK 等。要利用多核,可以部署多个实例或 Redis Cluster。

68. threadlocal的实现

ThreadLocal 为每个线程提供变量副本,数据实际存在线程自己的 ThreadLocalMap 里,ThreadLocal 对象本身只是 key。

结构

  • 每个 Thread 有成员变量 threadLocals,类型是 ThreadLocal.ThreadLocalMap。
  • ThreadLocalMap 内部是 Entry[] 数组,Entry 继承 WeakReference<ThreadLocal<?>>:key 是弱引用的 ThreadLocal,value 是强引用。
  • 哈希冲突用开放地址法(线性探测),不是链表;哈希值由 0x61c88647(斐波那契散列)递增生成,分布均匀。

get / set:取当前线程 → 拿到它的 ThreadLocalMap → 以当前 ThreadLocal 为 key 读写。

内存泄漏

  • ThreadLocal 外部强引用断开后,key 被 GC 回收变成 null,但 value 仍被 Thread → ThreadLocalMap → Entry → value 强引用。线程池中线程长期存活,value 就一直回收不掉。
  • get/set/remove 时会顺带清理 key 为 null 的 Entry,但不保证及时。
  • 正确做法:用完在 finally 中调用 remove(),尤其在线程池中,否则还会造成数据串用(如用户信息串到下一个请求)。

扩展:InheritableThreadLocal 可把值传给子线程;线程池场景用阿里的 TransmittableThreadLocal。

  1. 看日志和链路追踪(SkyWalking、traceId):是偶发还是持续、是全部请求还是特定参数,耗时花在哪个环节。

处理与防护

  • 设置合理的连接 / 读超时,不用默认无限等待。
  • 幂等接口才重试,带退避;非幂等接口超时后先查询结果再决定。
  • 熔断降级(Sentinel、Resilience4j),耗时长的改为异步 + 回调或消息通知。
  • 加监控告警,关注 P99 耗时和超时率。

71. Redis相关布隆过滤器解决什么问题，具体原理是什么？

布隆过滤器用来快速判断一个元素"一定不存在"或"可能存在",典型用途是解决缓存穿透(大量查询不存在的数据直接打到数据库)。

原理

  • 一个长度为 m 的位数组 + k 个哈希函数。
  • 添加:元素经 k 个哈希函数得到 k 个位置,全部置 1。
  • 查询:k 个位置有一个是 0 就一定不存在;全是 1 只能说可能存在(这些位可能被别的元素置 1,即误判)。
  • 误判率与 m、k、元素数 n 有关,位数组越大误判越低;最优 k ≈ (m/n)·ln2。

特点:空间占用极小、查询 O(k);存在误判(只会误判"存在",不会漏判);标准布隆过滤器不支持删除,删除需要计数布隆过滤器或布谷鸟过滤器。

在 Redis 中使用

  • Redisson RBloomFilter(基于 Bitmap,tryInit(预期数量, 误判率))。
  • RedisBloom 模块的 BF.ADD / BF.EXISTS(Redis Stack 自带)。

用于缓存穿透:启动时把所有合法 ID 写入布隆过滤器,请求先查过滤器,不存在直接返回;新增数据时同步加入。数据删除后无法移除,可以定期重建。另一种方案是缓存空值并设置较短 TTL。

73. Mysql联合索引的设计原则

核心是最左前缀匹配:联合索引 (a, b, c) 按 a、b、c 依次排序,查询要从最左列开始连续使用才能充分利用索引。

设计原则

  • 区分度高、最常用于等值查询的列放前面;但如果某列经常单独作为查询条件,优先放最左,让更多查询能复用。
  • 范围查询列放后面:a = ? AND b > ? AND c = ? 中 b 是范围查询,c 无法用于索引定位(只能借助索引下推过滤),所以应建成 (a, c, b)。
  • 考虑排序和分组:WHERE a = ? ORDER BY b 用 (a, b) 可以避免 filesort。
  • 尽量覆盖索引:把查询需要的列都放进索引,避免回表。
  • 复用和精简:有了 (a, b) 就不需要再单独建 (a);单表索引一般控制在 5 个左右,字段数不宜过多,长字符串用前缀索引。
  • 避免在索引列上做函数运算、隐式类型转换、前导 % 模糊匹配,这些会导致索引失效。

补充:MySQL 5.6 起有索引下推(ICP),在存储引擎层用索引中的后续列过滤,减少回表;MySQL 8.0.13 起支持索引跳跃扫描(Skip Scan),最左列区分度低时可能跳过最左列使用索引,但不能依赖它来设计索引。用 EXPLAIN 验证 key、key_len、Extra。

方案

  1. 能改成前缀匹配就改:LIKE '关键词%' 可以走索引。
  2. 覆盖索引减少开销:只查被索引覆盖的列时,即便 %xx% 也只需扫描更小的二级索引树,而不是聚簇索引,速度能明显提升(仍是全索引扫描)。
  3. MySQL 全文索引:FULLTEXT + MATCH ... AGAINST,InnoDB 从 5.6 开始支持,中文需要用 ngram 解析器(5.7.6 起内置,WITH PARSER ngram)。适合中等规模、对搜索要求不高的场景。
  4. 引入搜索引擎(推荐):Elasticsearch 使用倒排索引 + IK 中文分词,支持相关性排序、高亮、拼音等。通过 Canal 订阅 binlog 或 MQ 将 MySQL 数据同步到 ES,MySQL 负责存储,ES 负责检索。
  5. 辅助手段:先用其他有索引的条件缩小范围再模糊匹配;热门搜索结果缓存到 Redis;分页限制返回数量。

回答时说明取舍:全文索引零额外组件但功能弱;ES 效果好但要维护数据同步,存在短暂的不一致。

76. 如何保证交易，订单等不会重复处理

本质是保证接口幂等:同一个请求执行一次和执行多次的结果相同。常见方案:

  • 唯一索引:订单号、支付流水号等加唯一约束,重复插入时报 DuplicateKeyException,捕获后返回已有结果。最简单可靠的兜底。
  • Token 机制(防表单重复提交):进入页面先获取 token 存 Redis,提交时携带,服务端用 DEL 或 Lua 原子删除,删除成功才处理。
  • 状态机 + 乐观锁:更新时带上前置状态或版本号,如 UPDATE orders SET status = 'PAID' WHERE id = ? AND status = 'UNPAID',影响行数为 0 说明已处理过。
  • 分布式锁:以业务唯一键加 Redis 锁,防止并发重复处理,锁内仍需检查是否已处理(锁只解决并发,不解决先后重复)。
  • 去重表:以请求 ID / 消息 ID 作唯一键,与业务操作放在同一个本地事务中。

分层防护:前端按钮防重复点击;网关或接口层用 Token / 请求 ID;服务层用状态机 + 乐观锁;数据库用唯一索引兜底。支付回调、MQ 消费是最需要做幂等的地方。

77. hashmap底层怎么实现的

JDK 8 中 HashMap 底层是数组 + 链表 + 红黑树。

核心结构

  • Node<K,V>[] table 数组,每个桶存链表或红黑树(TreeNode)。
  • 默认初始容量 16(首次 put 时才初始化),负载因子 0.75,容量始终是 2 的幂。

put 流程

  1. 计算 hash:(h = key.hashCode()) ^ (h >>> 16),让高 16 位参与运算,减少冲突。
  2. 定位下标:(n - 1) & hash,等价于取模但更快(要求 n 是 2 的幂)。
  3. 桶为空直接放入;否则比较 key,相同则覆盖 value;不同则尾插到链表(JDK 7 是头插,并发扩容时可能形成环)。
  4. 链表长度达到 8 且数组长度 ≥ 64 时树化为红黑树;数组小于 64 时优先扩容。红黑树节点数降到 6 时退化为链表。
  5. 元素个数超过 容量 × 0.75 时扩容为 2 倍。

扩容优化:JDK 8 扩容时不需要重新计算 hash,看 hash & oldCap 是 0 还是 1:为 0 留在原下标,为 1 移到 原下标 + oldCap,链表拆成高低两条并保持原顺序。

其他要点:允许一个 null key(放在下标 0)和多个 null value;线程不安全,并发场景用 ConcurrentHashMap(JDK 8 是 CAS + synchronized 锁桶头节点)。key 作为对象时要同时重写 hashCode 和 equals。

78. 1000w条数据求topk，优化思路

核心思路:用大小为 K 的堆维护候选集,数据量超过内存时分治 + 归并。

内存能放下时

  • 小顶堆(求最大的 K 个):先放入 K 个元素,之后每个元素与堆顶比较,比堆顶大就替换堆顶并下沉。时间 O(N log K),空间 O(K)。Java 用 PriorityQueue。
  • 快速选择(Quickselect):基于快排的 partition,平均 O(N),但需要全部数据在内存中且会修改原数组。
  • 不推荐全量排序 O(N log N)。

数据很大或内存受限时

  1. 分治:按 hash(key) % M 把数据拆成 M 个小文件(相同 key 进同一文件,适用于求高频 TopK)。
  2. 每个小文件内部用 HashMap 统计频次,再用小顶堆求局部 TopK。
  3. 把各文件的 TopK 合并,再求一次全局 TopK。
  4. 可以多线程 / 多机并行处理各分片(MapReduce 思路)。

其他优化

  • 数据取值范围有限(如分数 0–100)时可用计数排序 / 桶,O(N)。
  • 实时排行榜场景直接用 Redis ZSET:ZADD 更新,ZREVRANGE key 0 K-1 取 TopK。
  • 1000 万个 int 约 40MB,单机内存通常放得下,直接小顶堆即可;要说明"先评估数据量和内存,再选方案"。

79. spring事务传播方式

Spring 定义了 7 种传播行为,决定方法 A 调用带事务的方法 B 时,B 如何使用事务。

传播行为 当前有事务 当前无事务
REQUIRED(默认) 加入当前事务 新建事务
REQUIRES_NEW 挂起当前事务,新建独立事务 新建事务
NESTED 在当前事务中创建保存点,嵌套事务回滚只回到保存点 新建事务
SUPPORTS 加入当前事务 以非事务方式执行
NOT_SUPPORTED 挂起当前事务,以非事务执行 以非事务方式执行
MANDATORY 加入当前事务 抛异常
NEVER 抛异常 以非事务方式执行

常考区别

  • REQUIRED:A、B 同一个事务,B 异常即使被 A catch,整个事务也会被标记为 rollback-only,提交时抛 UnexpectedRollbackException。
  • REQUIRES_NEW:B 独立提交 / 回滚,A 回滚不影响已提交的 B;常用于记录操作日志。
  • NESTED:B 回滚不影响 A(A catch 住即可);A 回滚会连带 B 回滚。依赖 JDBC 保存点。

注意:传播行为依赖 Spring 代理,同类内部方法自调用不生效;默认只对 RuntimeException 和 Error 回滚,受检异常需要 rollbackFor = Exception.class。

80. 了解双亲委派吗?

双亲委派是 JVM 类加载的机制:类加载器收到加载请求时,先委托父加载器加载,父加载器无法完成时才自己加载。

类加载器层次(JDK 8)

  • 启动类加载器(Bootstrap):C++ 实现,加载 JAVA_HOME/jre/lib 下的核心类库(rt.jar)。
  • 扩展类加载器(Extension):加载 jre/lib/ext。
  • 应用类加载器(Application):加载 classpath 上的类。
  • 自定义类加载器:继承 ClassLoader。

JDK 9 模块化后,扩展类加载器被**平台类加载器(Platform)**取代。注意这里的"父子"是组合关系(parent 字段),不是继承。

流程(ClassLoader.loadClass):先查是否已加载 → 委托 parent.loadClass → 父为 null 则交给 Bootstrap → 都找不到才调用自己的 findClass。

好处

  • 避免重复加载,同一个类只由一个加载器加载。
  • 安全:防止核心类被篡改,自己写的 java.lang.String 不会被加载(而且 java.* 包名会被 JVM 禁止定义)。

打破双亲委派

  • 自定义类加载器重写 loadClass(只想保持双亲委派应重写 findClass)。
  • SPI(如 JDBC):核心接口由 Bootstrap 加载,实现类在 classpath,通过线程上下文类加载器加载。
  • Tomcat:每个 Web 应用有独立的 WebappClassLoader,优先加载自己的类,实现应用隔离。
  • OSGi、热部署等。

81. rocketmq相关：怎么保证消息消费端幂等性

RocketMQ 只保证 At Least Once(至少一次),网络抖动、消费超时、Rebalance、生产者重试都会导致重复消费,所以要在消费端做幂等。

关键:选择业务唯一键

  • 不要只依赖 msgId:生产者重试时 msgId 可能不同。应在发送时设置业务唯一标识(如订单号)作为消息 Key(message.setKeys(orderNo)),消费端以它去重。

常见方案

  • 数据库唯一索引:把业务 ID 写入去重表或业务表的唯一键,与业务操作放在同一个本地事务中;插入冲突说明已消费,直接返回成功。
  • 状态机 / 条件更新:UPDATE ... SET status = 'DONE' WHERE id = ? AND status = 'INIT',影响行数为 0 则跳过。
  • Redis 去重:SET key value NX EX 过期时间,设置成功才处理。注意要处理"处理中"状态:先置为 processing,业务成功后置为 done,失败时删除 key 以便重试;否则加锁后宕机会导致消息被误判为已消费。
  • 乐观锁 / 版本号。

配套

  • 消费成功后返回 CONSUME_SUCCESS,失败返回 RECONSUME_LATER 进入重试队列,多次失败(默认 16 次)进入死信队列,需监控并人工处理。
  • 生产端也要可靠:同步发送 + 重试、事务消息,配合消费端幂等实现最终一致。

82. 用你的理解讲讲数据库的三范式。

三范式是设计关系表时减少数据冗余和更新异常的规范,逐级递进。

  • 第一范式(1NF):每个字段都是不可再分的原子值。例如"联系方式"里同时存电话和邮箱就违反 1NF,应拆成两列。
  • 第二范式(2NF):满足 1NF,且非主键字段必须完全依赖于整个主键,不能只依赖联合主键的一部分。例如选课表 (学号, 课程号, 姓名, 成绩),姓名只依赖学号,应把学生信息拆到学生表。
  • 第三范式(3NF):满足 2NF,且非主键字段不能传递依赖于主键。例如学生表 (学号, 姓名, 院系ID, 院系名称),院系名称依赖院系ID,应拆出院系表。

不满足范式的问题:数据冗余、插入异常、删除异常、更新异常(改一处要改多处)。

实际取舍:范式越高,表越多、查询需要的 JOIN 越多。互联网业务常做适当反范式,例如在订单表冗余商品名称和价格快照(本身就有业务含义),或冗余字段避免高频 JOIN,用空间换查询性能,但要保证冗余数据的更新一致。

没有绝对优劣,要按业务规模、团队规模和发展阶段选择:早期单体更快,规模变大后再拆分。

维度 单体架构 分布式(微服务)架构
开发部署 简单,一个包部署 服务多,需要 CI/CD、容器化、服务治理
性能 进程内调用,无网络开销 远程调用有延迟和失败风险

84. CAS介绍一下原理,有哪些问题?

CAS(Compare And Swap)是无锁的原子操作:比较内存值 V 与预期值 A,相等才更新为新值 B,否则失败,整个过程由 CPU 指令保证原子性。

原理

  • 硬件层面:x86 上是 lock cmpxchg 指令。
  • Java 层面:Unsafe.compareAndSwapInt 等 native 方法(JDK 9 起还有 VarHandle),AtomicInteger、ConcurrentHashMap、AQS 都基于 CAS。
  • 一般配合自旋:失败就重新读取最新值再试,如 getAndIncrement 的循环。

问题

  1. ABA 问题:值从 A 变成 B 又变回 A,CAS 检测不到变化。解决:加版本号,AtomicStampedReference(版本戳)或 AtomicMarkableReference。
  2. 自旋开销大:竞争激烈时长时间失败重试,浪费 CPU。解决:限制自旋次数,或改用锁;高并发计数用 LongAdder(分段累加,减少竞争)。
  3. 只能保证单个变量的原子性:多个变量需要用 AtomicReference 封装成一个对象,或者加锁。

与锁对比:CAS 是乐观策略,适合读多写少、竞争不激烈的场景;竞争激烈时 synchronized / ReentrantLock 反而更稳定。

85. JVM的垃圾回收机制

垃圾回收(GC)是 JVM 自动识别并回收堆中不再使用的对象,主要回答:怎么判断垃圾、用什么算法回收、有哪些收集器。

判断对象是否存活

  • 引用计数法:无法解决循环引用,JVM 不采用。
  • 可达性分析:从 GC Roots(栈中局部变量引用的对象、静态变量、常量、JNI 引用、活跃线程、同步锁持有的对象等)出发,不可达的对象可被回收。
  • 引用类型:强、软(内存不足时回收)、弱(下次 GC 回收)、虚引用。

回收算法

  • 标记-清除:有内存碎片。
  • 标记-复制:无碎片,浪费一半空间,适合存活率低的新生代。
  • 标记-整理:无碎片,移动对象成本高,适合老年代。
  • 分代收集:新生代(Eden : S0 : S1 默认 8:1:1)用复制算法,对象经过多次 Minor GC 仍存活(默认阈值 15)晋升老年代;老年代用标记-清除或标记-整理。

常见收集器

收集器 特点
Serial / Serial Old 单线程,适合客户端小内存
Parallel Scavenge / Parallel Old 吞吐量优先,JDK 8 默认
CMS 低停顿、并发标记清除,有碎片;JDK 9 标记废弃,JDK 14 移除
G1 把堆分成多个 Region,可预测停顿(-XX:MaxGCPauseMillis),JDK 9 起默认
ZGC / Shenandoah 停顿通常在毫秒以内;ZGC 在 JDK 15 转正,JDK 21 引入分代 ZGC

GC 类型:Minor GC(新生代)、Major GC(老年代)、Full GC(整个堆 + 元空间),所有收集器都有 STW,调优目标是减少 Full GC 和停顿时间。

87. SQL注入怎么发现存在该漏洞?

SQL 注入是用户输入被拼接进 SQL 并被当作代码执行。发现手段分为代码审计、手工测试、工具扫描三类。

代码审计(开发最常用)

  • 搜索字符串拼接 SQL 的地方:Java 中 Statement + "... where id = " + id;MyBatis 中的 ${}(直接文本替换),重点看 ORDER BY ${}、LIKE '%${}%'、动态表名列名。

  • 在参数中加单引号 ',看是否报 SQL 语法错误(报错型)。
  • 布尔盲注:id=1 AND 1=1 与 id=1 AND 1=2 返回结果是否不同。
  • 时间盲注:id=1 AND SLEEP(5),观察响应是否延迟。
  • 联合查询:UNION SELECT ... 看能否回显额外数据。

工具:sqlmap(自动检测和利用)、Burp Suite、OWASP ZAP、AWVS 等。只能在授权的系统上测试。

防御:使用 PreparedStatement 预编译 / MyBatis #{};无法预编译的(排序字段、表名)用白名单校验;数据库账号最小权限;不向前端暴露 SQL 错误详情;WAF 兜底。

88. service层分批调用mapper层那有1w条数据过来，这个传参太大了，微服务吃不消怎么办？

问题本质:一次传输和处理的数据量太大,导致请求体过大、内存占用高、SQL 过长(超过 max_allowed_packet、IN 列表过长)、接口超时。解决思路是分批、精简、异步。

分批处理

  • service 层把 1 万条拆成每批 500–1000 条,循环调用 mapper,例如 Guava Lists.partition(list, 500)。
  • 批量插入用 MyBatis <foreach> 生成多值 INSERT,或使用 ExecutorType.BATCH 的 SqlSession,JDBC URL 加 rewriteBatchedStatements=true 提升 MySQL 批处理性能。
  • 每批单独提交事务,避免大事务长时间占锁;需要整体一致时记录批次状态,支持失败重试。

减少传输量

  • 微服务之间不传完整对象,只传 ID 或必要字段,由下游自行查询。
  • 大批量数据可以先写到文件存储(OSS)或中间表,只传文件地址或批次号。

异步化

  • 调用方把任务发到 MQ,下游按批消费,削峰并支持重试;前端轮询或回调获取处理结果。
  • 并行处理分批时用有界线程池,控制并发,避免打垮数据库。

90. mysql怎么实现事务

InnoDB 通过 undo log、redo log、锁、MVCC 实现事务的 ACID。

特性 实现方式
原子性(A) undo log:记录修改前的数据,回滚时按 undo log 逆向恢复
持久性(D) redo log:WAL(先写日志再写磁盘),提交时刷 redo log,崩溃后重放恢复
隔离性(I) 锁(行锁、间隙锁、临键锁)控制写写冲突 + MVCC 实现快照读
一致性(C) 目标,由 A、I、D 共同保证,加上约束检查和应用层逻辑

关键细节

  • redo log 是物理日志,循环写,innodb_flush_log_at_trx_commit = 1(默认)时每次提交都刷盘,保证不丢。
  • binlog 是 Server 层逻辑日志,用于主从复制和数据恢复;redo log 与 binlog 通过两阶段提交(redo prepare → 写 binlog → redo commit)保证一致。
  • MVCC:每行有隐藏列 DB_TRX_ID(最后修改的事务 ID)和 DB_ROLL_PTR(指向 undo log 版本链);快照读时根据 ReadView 判断哪个版本可见。RC 每次查询生成新的 ReadView,RR 在事务第一次快照读时生成并复用,因此 RR 可重复读。
  • 当前读(SELECT ... FOR UPDATE、UPDATE、DELETE)读最新版本并加锁,RR 下用临键锁防止幻读。
  • InnoDB 默认隔离级别是 RR(可重复读)。

使用:BEGIN / START TRANSACTION → SQL → COMMIT / ROLLBACK;Spring 中用 @Transactional。MyISAM 不支持事务。

93. Redis分布式锁

核心是 SET key value NX EX 过期时间 加锁、Lua 脚本校验 value 后删除解锁;生产中通常直接用 Redisson。

正确的加锁

SET lock:order:1001 <uuid+线程ID> NX EX 30
  • NX 保证互斥,EX 防止持有锁的进程宕机后死锁,两者要在一条命令里原子完成(不能先 SETNX 再 EXPIRE)。
  • value 用唯一标识,防止误删别人的锁。

正确的解锁(Lua 保证原子性)

if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end

常见问题与 Redisson 的方案

  • 锁过期但业务未执行完:Redisson 的 看门狗(Watchdog) 在未指定 leaseTime 时,默认锁 30 秒,每 10 秒(1/3 时间)续期一次,客户端宕机后停止续期,锁自然过期。
  • 可重入:Redisson 用 Hash 结构存 线程标识 → 重入次数。
  • 等待重试:tryLock(waitTime, leaseTime, unit),基于 Pub/Sub 等待锁释放,而不是忙等。
  • 主从切换丢锁:主节点加锁后还没同步到从节点就宕机,新主上没有锁。RedLock 向多个独立节点加锁、过半成功才算成功,但有争议且成本高,Redisson 已将其标记为弃用;强一致要求的场景可用 ZooKeeper 或 etcd,同时业务上用数据库唯一约束或版本号兜底(fencing token 思想)。

95. 线程池

线程池通过复用线程来执行任务,好处是降低线程创建销毁开销、提高响应速度、控制并发数量、便于统一管理和监控。

7 个核心参数(ThreadPoolExecutor):corePoolSize 核心线程数、maximumPoolSize 最大线程数、keepAliveTime + unit 非核心线程空闲存活时间、workQueue 任务队列、threadFactory 线程工厂(用于命名)、handler 拒绝策略。

执行流程:线程数 < 核心数则建核心线程 → 否则入队 → 队列满且 < 最大数则建非核心线程 → 否则执行拒绝策略。

拒绝策略:AbortPolicy(默认,抛异常)、CallerRunsPolicy(调用者执行,起反压作用)、DiscardPolicy、DiscardOldestPolicy。

为什么不用 Executors:FixedThreadPool、SingleThreadExecutor 用无界队列,堆积会 OOM;CachedThreadPool 最大线程数 Integer.MAX_VALUE。应手动创建并用有界队列。

参数设置:CPU 密集型约 N + 1,IO 密集型约 2N 或 N × (1 + 等待时间/计算时间),以压测为准,可接入动态线程池。

易错点:submit 的异常封装在 Future 里,不调 get() 看不到;execute 会直接抛出。shutdown() 等已提交任务完成,shutdownNow() 中断执行中任务。JDK 21 起 IO 密集型可考虑 Executors.newVirtualThreadPerTaskExecutor()。

99. 项目中怎么保证数据库与缓存的一致性?

常用方案是旁路缓存(Cache Aside):先更新数据库,再删除缓存,配合过期时间兜底;对一致性要求更高的场景再加延迟双删或 binlog 异步删除。

为什么删缓存而不是更新缓存:更新缓存在并发写时容易乱序,导致缓存中是旧值;而且写多读少时频繁更新缓存是浪费。删除后由下一次读请求按需加载。

为什么先更新数据库再删缓存

  • 先删缓存再更新数据库:删除后、更新前有读请求进来,会把旧值重新写回缓存,不一致的时间窗口较大。
  • 先更新数据库再删缓存:只有在"缓存恰好失效 + 读请求读到旧值 + 写回缓存发生在删除之后"时才会不一致,概率很低。

进一步保证

  • 缓存设置过期时间:即使出现不一致,也能在 TTL 到期后自动恢复(最终一致)。
  • 删除失败重试:删除缓存失败时把 key 发送到 MQ 重试。
  • 延迟双删:更新数据库前后各删一次,第二次延迟几百毫秒,覆盖并发读写回旧值的情况。
  • 订阅 binlog:用 Canal 监听 MySQL binlog,异步删除缓存,与业务代码解耦,配合重试更可靠。
  • 强一致要求:读写加分布式锁或读写锁,会牺牲性能;真正要求强一致的数据(如余额)直接读数据库。

项目中可以这样讲:例如店铺详情使用 Cache Aside + TTL,更新店铺时在同一个 @Transactional 方法中先更新数据库,再删除缓存;同时说明缓存穿透(缓存空值 / 布隆过滤器)、击穿(互斥锁 / 逻辑过期)、雪崩(随机 TTL)的处理方式。

100. tcp三次握手

三次握手用于建立可靠的 TCP 连接,同步双方的初始序列号(ISN),并确认双方的收发能力都正常。

过程

  1. 客户端发送 SYN,seq = x,进入 SYN_SENT 状态。
  2. 服务端回复 SYN + ACK,seq = y, ack = x + 1,进入 SYN_RCVD 状态。
  3. 客户端发送 ACK,ack = y + 1,双方进入 ESTABLISHED 状态。第三次握手可以携带数据。

为什么是三次而不是两次

  • 防止已失效的连接请求被服务端接受:旧的 SYN 延迟到达时,如果两次握手就建立连接,服务端会白白分配资源;三次握手时客户端会发现不是自己期望的连接并回复 RST。
  • 双方都要确认对方收到了自己的 ISN:两次握手只能确认客户端的序列号,服务端的 ISN 得不到确认。
  • 四次没有必要:服务端的 SYN 和 ACK 可以合并成一个报文发送。

相关考点

  • 服务端维护半连接队列(SYN 队列)和全连接队列(accept 队列,大小受 backlog 和 somaxconn 限制)。
  • SYN Flood 攻击会占满半连接队列,防御手段是开启 SYN Cookie。
  • SYN + ACK 丢失时服务端会重传,次数由 tcp_synack_retries 控制。ISN 是随机生成的,防止被预测和旧报文干扰。

101. 消息队列怎么使用的?

回答框架:用 MQ 解决了什么问题(异步、解耦、削峰)→ 具体业务场景 → 如何保证可靠(不丢失、不重复、顺序)→ 选型理由。

三大作用

  • 异步:下单后发短信、加积分等非核心流程发送消息异步处理,缩短接口响应时间。
  • 解耦:订单服务只发布"订单已支付"事件,库存、物流、营销服务各自订阅,新增下游时无需修改订单服务。
  • 削峰:秒杀请求先写入 MQ,下游按消费能力平稳处理,保护数据库。

使用流程(以 RocketMQ / Spring Boot 为例):生产者通过 RocketMQTemplate 发送消息到 Topic(可以用 Tag 区分子类型)→ 消费者通过 @RocketMQMessageListener 订阅 Topic 和消费者组 → 处理成功后确认消费,失败则进入重试。

可靠性保证

  • 不丢失:生产端同步发送 + 重试 / 事务消息;Broker 同步刷盘 + 主从同步复制;消费端处理完业务后再确认。
  • 不重复:消费端做幂等(唯一索引、去重表、状态机)。
  • 顺序:同一业务 key 的消息发送到同一个队列(MessageQueueSelector),消费端顺序消费。
  • 消息堆积:增加消费者实例(不超过队列数)、批量消费、排查慢消费。
  • 延迟消息可用于订单超时自动取消。

选型:RocketMQ 适合业务消息和事务消息;Kafka 吞吐量高,适合日志和大数据;RabbitMQ 路由灵活、延迟低,适合中小规模。

103. 死锁

死锁是两个或多个线程互相持有对方需要的资源,又都在等待对方释放,导致永久阻塞。

四个必要条件(同时满足才会死锁)

  1. 互斥:资源同一时刻只能被一个线程占用。
  2. 占有并等待:持有资源的同时还在申请新资源。
  3. 不可剥夺:已获得的资源不能被强行抢走。
  4. 循环等待:线程之间形成资源等待环。

典型代码:线程 1 先锁 A 再锁 B,线程 2 先锁 B 再锁 A,两者同时执行就会死锁。

// 线程1
synchronized (lockA) { synchronized (lockB) { /* ... */ } }
// 线程2
synchronized (lockB) { synchronized (lockA) { /* ... */ } }

预防:破坏后三个条件之一。

  • 统一加锁顺序(破坏循环等待),最常用。
  • 一次性申请全部资源(破坏占有并等待)。
  • 使用 tryLock(timeout),超时释放已持有的锁(破坏不可剥夺)。

避免:银行家算法,分配前判断是否处于安全状态。

排查:jps 找到进程 → jstack <pid>,输出中会出现 "Found one Java-level deadlock" 及相互等待的线程和锁;也可以用 JConsole、VisualVM 的死锁检测,或 Arthas thread -b。数据库死锁用 SHOW ENGINE INNODB STATUS 查看最近一次死锁信息。

区分:活锁是线程不断重试、相互让步但都无法推进(线程没有阻塞);饥饿是某线程长期得不到资源。

104. tcp和udp的区别

一句话:TCP 面向连接、可靠、基于字节流;UDP 无连接、不可靠、基于数据报,开销小、实时性好。

维度 TCP UDP
连接 面向连接(三次握手、四次挥手) 无连接
可靠性 可靠:序号、确认应答、超时重传、流量控制、拥塞控制 尽力交付,不保证不丢、不重、有序
传输方式 字节流,存在"粘包"问题,需要应用层定义边界 数据报,保留消息边界
通信模式 只支持一对一 支持一对一、一对多、广播、多播
首部开销 20–60 字节 固定 8 字节
速度 较慢 快,实时性好
应用场景 HTTP/1.1、HTTP/2、文件传输、邮件、SSH DNS、音视频通话、直播、游戏、DHCP

补充:HTTP/3 基于 QUIC,QUIC 运行在 UDP 之上,在用户态实现了可靠传输、拥塞控制和 TLS 1.3 加密,解决了 TCP 的队头阻塞问题,并支持连接迁移。所以"UDP 不可靠"指协议本身,应用层可以在 UDP 之上自行实现可靠性。

105. get和post

从语义上讲:GET 用于获取资源,是安全且幂等的;POST 用于提交数据进行处理,既不安全也不幂等。

维度 GET POST
语义 获取资源 提交数据、创建资源
参数位置 通常放在 URL 查询字符串 通常放在请求体
长度限制 HTTP 协议本身不限制,浏览器和服务器对 URL 长度有限制(常见为几 KB 到几十 KB) 协议不限制,由服务端配置决定
缓存 可以被浏览器和 CDN 缓存 默认不缓存
历史记录 / 书签 参数保留在浏览器历史中,可以收藏 不保留
幂等性 幂等 非幂等
编码 只能进行 URL 编码 支持 application/json、form-data、x-www-form-urlencoded 等多种格式

常见误区

  • "POST 比 GET 安全":两者都是明文传输,POST 只是参数不会显示在 URL 和日志中;真正的安全依赖 HTTPS。
  • "GET 不能有请求体":规范没有禁止,但语义未定义,很多服务器和代理会忽略,不建议使用。
  • "POST 会发送两个 TCP 包":这只是部分浏览器或客户端的实现行为(例如先发 Header 并使用 Expect: 100-continue),不是协议规定。

108. 重载和重写的区别

一句话:重载(Overload)是同一个类中方法名相同、参数列表不同,在编译期确定调用哪个方法;重写(Override)是子类重新实现父类的方法,在运行期根据对象实际类型动态分派,是多态的体现。

维度 重载 重写
发生位置 同一个类(或父子类之间) 子类与父类之间
方法名 相同 相同
参数列表 必须不同(类型、个数或顺序) 必须相同
返回值 无要求,仅返回值不同不能构成重载 相同或是其子类型(协变返回)
访问修饰符 无要求 不能比父类更严格(父类 protected,子类不能是 private)
异常 无要求 受检异常不能比父类更多、更宽泛
绑定时机 编译期(静态分派) 运行期(动态分派)

注意

  • private、static、final 方法不能被重写:static 方法在子类中同名定义叫隐藏,不是重写;构造方法可以重载,但不能重写。
  • 重写时建议加上 @Override,编译器会检查方法签名是否正确。

109. 回表

回表是指通过二级索引找到主键值后,再回到主键索引(聚簇索引)查询完整行数据的过程,多了一次 B+ 树查找。

为什么会回表:InnoDB 中聚簇索引的叶子节点存储整行数据;二级索引的叶子节点只存储索引列 + 主键值。如果查询的列不全在二级索引中,就需要拿着主键回到聚簇索引查找。

例如表 user(id 主键, name 有索引, age):

SELECT * FROM user WHERE name = 'Tom';      -- 先查 name 索引得到 id,再回聚簇索引查整行:回表
SELECT id, name FROM user WHERE name = 'Tom'; -- name 索引中已包含 id 和 name:覆盖索引,不回表

怎么减少回表

  • 覆盖索引:建立联合索引,把查询需要的列都包含进去,EXPLAIN 的 Extra 中会显示 Using index。
  • 避免 SELECT *,只查需要的列。
  • 索引下推(ICP,MySQL 5.6+):在存储引擎层先用联合索引中的其他列过滤,减少回表次数,Extra 中显示 Using index condition。
  • MRR(Multi-Range Read):把要回表的主键排序后再查询,将随机 IO 变成顺序 IO。
  • 深分页优化:先用覆盖索引查出主键,再关联回表,如 SELECT * FROM t JOIN (SELECT id FROM t ORDER BY id LIMIT 100000, 10) tmp USING(id)。

回表行数过多时,优化器可能认为全表扫描成本更低而放弃使用索引。

111. js这门语言性能方面怎么样?

结论:现代 JavaScript 引擎(V8、SpiderMonkey、JavaScriptCore)使用 JIT 编译,性能对绝大多数 Web 和 IO 密集型场景已经足够;但它是单线程、动态类型、带 GC 的语言,计算密集型任务不如 C++、Rust、Java 等。

性能好的原因

  • JIT 编译:V8 中 Ignition 解释器先执行字节码,热点代码交给 TurboFan 优化编译为机器码;引擎会基于类型反馈做推测优化,类型变化时进行反优化(deopt)。
  • 隐藏类(Hidden Class / Shape)+ 内联缓存(Inline Cache):同一结构的对象共享隐藏类,加速属性访问。
  • 事件循环 + 异步非阻塞 IO:Node.js 在 IO 密集场景(网关、BFF、实时通信)下吞吐量高。
  • 分代 GC:V8 新生代使用 Scavenge(复制算法),老年代使用标记-清除 / 整理,并通过增量和并发标记降低停顿。

局限

  • 主线程单线程:长时间计算会阻塞 UI 渲染和事件处理。可以用 Web Worker(浏览器)或 worker_threads(Node.js)将计算移出主线程。
  • 动态类型导致优化不稳定,对象形状频繁变化、数组中混合存放不同类型都会降低性能。
  • GC 停顿和内存占用较高。

常见优化手段

  • 保持对象结构稳定(在构造函数中初始化所有属性,避免 delete 属性),数组元素类型一致。
  • 减少 DOM 操作和强制同步布局(批量读写、requestAnimationFrame),防抖与节流,长列表使用虚拟滚动。
  • 及时清理事件监听器和定时器,避免闭包导致内存泄漏。
  • 计算密集型任务使用 WebAssembly;代码分割、懒加载、tree-shaking 减少包体积。

112. 索引结构

MySQL InnoDB 默认使用 B+ 树索引,另外还有哈希索引、全文索引等。

B+ 树的特点

  • 多路平衡查找树,非叶子节点只存键和子节点指针,数据全部存放在叶子节点。
  • 叶子节点之间通过双向链表连接,适合范围查询和排序。
  • InnoDB 的页大小默认为 16KB,每个节点就是一页,扇出可以达到上千;3 层 B+ 树大约可以存储两千多万行(按每行约 1KB 估算),一次查询只需 2–3 次磁盘 IO(根节点通常常驻内存)。

为什么不用其他结构

结构 不适合的原因
哈希表 只支持等值查询,不支持范围查询和排序
二叉搜索树 / AVL / 红黑树 每个节点只有两个分支,树太高,磁盘 IO 次数多
B 树 非叶子节点也存数据,单页能放的键更少,树更高;范围查询需要中序遍历

InnoDB 中的两类索引

  • 聚簇索引(主键索引):叶子节点存储整行数据,一张表只有一个。没有主键时选择第一个非空唯一索引,都没有则使用隐藏的 6 字节 DB_ROW_ID。
  • 二级索引(辅助索引):叶子节点存储索引列 + 主键值,查询其他列时需要回表。

对比 MyISAM:MyISAM 也使用 B+ 树,但属于非聚簇索引,叶子节点存储的是数据文件中的行地址,索引和数据分开存放。

补充:主键建议使用自增或趋势递增的 ID(如雪花算法),顺序插入可以避免页分裂;使用 UUID 作为主键会导致随机插入和频繁页分裂。InnoDB 还有自适应哈希索引,由引擎针对热点数据自动创建,不能手动创建。

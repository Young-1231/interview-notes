## 导读
分布式八股高频考点：CAP/BASE、分布式锁（Redis SET NX EX + Lua 解锁 + Redisson 看门狗、Redlock 争议、ZK 临时顺序节点）、分布式事务（2PC/TCC/Saga/本地消息表）、雪花算法与时钟回拨、一致性哈希、MQ 幂等与积压。
- 先背：Redis 锁的三个要点（原子加锁、只删自己的锁、续期）、看门狗的 30s/10s、雪花算法的 1+41+10+12 位划分。
- 最容易混的：CAP 的 C（线性一致）和 ACID 的 C；2PC 和 TCC 的阶段划分；Redis 哨兵和 Cluster 解决的问题。

## 纠正: RPC与HTTP调用有什么区别
原文说"HTTP 是短连接、文本协议"，这个说法过时了。HTTP/1.1 默认就是持久连接（keep-alive）；HTTP/2 是二进制分帧协议，支持在一条连接上多路复用。
RPC 也不是和 HTTP 并列的一种协议，而是一种调用方式，底层可以基于 TCP 自定义协议（如 Dubbo 协议），也可以基于 HTTP（gRPC 就基于 HTTP/2）。两者真正的区别在于：RPC 框架通常自带序列化、服务发现、负载均衡、超时重试等治理能力，HTTP/REST 更通用、更适合对外开放。

## 补充: 什么是CAP理论
CAP 里的 C 指线性一致性（读到最新的写），和 ACID 里的 C（满足约束、处于合法状态）不是一回事。
P 是必选项，CP/AP 的取舍只在发生分区时才需要做，没有分区时 C 和 A 可以同时满足。常见例子：ZooKeeper、etcd 偏 CP；Eureka、Cassandra 偏 AP；Nacos 的临时实例走 AP（Distro 协议），持久实例走 CP（Raft）。BASE（基本可用、软状态、最终一致）是 AP 方向的工程实践。

## 补充: Redlock 红锁原理是什么
Martin Kleppmann 的核心批评：进程暂停（GC）或网络延迟会让客户端在锁已经过期后还以为自己持有锁。正确的做法是加 fencing token（单调递增的版本号），由存储端拒绝旧 token 的写入，而 Redlock 本身给不出这种 token。
另外，Redisson 新版本已经把 RedissonRedLock 标记为 deprecated。

## 补充: 如何确保锁不会被其他线程误删
看门狗只在加锁时没有指定 leaseTime 时才生效。调用 lock(10, TimeUnit.SECONDS) 这类显式指定过期时间的方法，不会自动续期。
Redisson 锁是可重入的，用 Redis Hash 存储（field 是 UUID:threadId，value 是重入次数）。客户端宕机后续期停止，锁最多 30s 后过期。

## 自测
### CAP 三者为什么只能满足两项？
分布式系统必须容忍网络分区（P）。分区发生时，要么拒绝请求以保证一致（CP），要么继续响应但可能读到旧数据（AP）。
### BASE 是什么？
基本可用（Basically Available）、软状态（Soft state）、最终一致（Eventually consistent），是放弃强一致、追求可用性的工程思路。
### Redis 分布式锁加锁、解锁的正确姿势？
加锁用 SET key uuid NX EX 30，原子地设置值和过期时间。解锁用 Lua 脚本，先比较 value 是不是自己的 uuid，是才 DEL，保证判断和删除是原子的。
### Redisson 看门狗的默认参数？
默认锁过期时间 30s，每 10s（过期时间的 1/3）续期一次，重置为 30s。指定了 leaseTime 就不续期。
### Redis 主从架构下的分布式锁有什么风险？
主从复制是异步的。主节点加锁成功后还没同步到从节点就宕机，从节点升为新主后锁丢失，另一个客户端可以再次加锁。
### Redlock 怎样才算加锁成功？
在 N 个（通常 5 个）独立的 Redis master 上依次加锁。有 N/2+1 个成功，并且总耗时小于锁的有效期，才算成功。否则要向所有节点释放锁。
### ZooKeeper 分布式锁的原理？
在锁目录下创建临时顺序节点，序号最小的节点获得锁。其他节点只监听自己的前一个节点，避免羊群效应。会话断开时临时节点自动删除，锁随之释放。
### 2PC 的问题有哪些？
同步阻塞（参与者在 prepare 后一直持有资源）、协调者单点故障、第二阶段消息丢失时可能导致数据不一致。
### TCC 和 2PC 有什么区别？
2PC 是资源层（数据库 XA）的协议，prepare 阶段持有数据库锁。TCC 是业务层的协议，Try 阶段预留业务资源。TCC 需要处理空回滚、幂等和悬挂这三个问题。
### Saga 怎么保证一致性？
把长事务拆成多个本地事务依次执行。某一步失败时，按相反顺序执行前面各步的补偿操作。不保证隔离性，只保证最终一致。
### 本地消息表的核心思想？
业务数据和消息记录写在同一个本地事务里，再由后台任务投递到 MQ 并失败重试。消费端必须幂等。
### 雪花算法由哪几部分组成？
1 位符号位 + 41 位毫秒时间戳（约 69 年）+ 10 位机器 ID + 12 位序列号（每毫秒最多 4096 个）。
### 时钟回拨怎么处理？
回拨幅度小就等待追平，幅度大就报错拒绝生成。也可以借用备用的 workerId，或者像美团 Leaf、百度 UidGenerator 那样不依赖实时时钟。
### 一致性哈希中虚拟节点的作用？
每个物理节点映射成多个虚拟节点，散布在环上，让数据分布更均匀。节点下线时，负载会分摊到多个节点上，而不是全压到下一个节点。
### Redis Cluster 怎么分片？
固定 16384 个哈希槽，用 CRC16(key) mod 16384 算出槽位，每个 master 负责一部分槽。它不是一致性哈希环。
### MQ 怎么保证消费幂等？
用业务唯一 ID 做去重：数据库唯一约束、Redis SETNX 记录已处理的 ID，或者用状态机判断是否已处理。
### 消息积压几百万条怎么办？
先修复消费端的故障或慢逻辑。然后扩容消费者，必要时临时建一个分区更多的 topic，把积压消息转发过去，用更多消费实例并行处理。
### Redis 主从、哨兵、Cluster 分别解决什么问题？
主从解决数据备份和读写分离；哨兵解决主节点故障时的自动切换；Cluster 解决容量和写性能的水平扩展。

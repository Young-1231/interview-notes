项目概述与登录 7高频 0

介绍一下黑马点评项目的整体架构和亮点

黑马点评是一个类似大众点评的本地生活 App 后端，技术栈为 Spring Boot + MyBatis-Plus + MySQL + Redis（含 Redisson），前端由 Nginx 部署并反向代理到后端集群。项目的核心是把 Redis 的各种数据结构用到具体业务里。

登录模块怎么设计的？为什么用 Redis 代替 Session？

基于 Session 的问题：Tomcat 的 Session 保存在单机内存里，部署多台 Tomcat 时请求被 Nginx 轮询到其他节点就拿不到登录态。Session 复制会占用内存、存在同步延迟，所以改用 Redis 集中存储，所有节点共享。

流程

  1. 发送验证码：校验手机号格式 → 生成 6 位验证码 → SET login:code:{phone} code EX 120（2 分钟有效）→ 调用短信服务（项目中用日志模拟）。
  2. 登录 / 注册：校验手机号和验证码（与 Redis 中的比对）→ 根据手机号查用户，不存在就自动注册 → 生成随机 token（UUID）→ 把用户信息转为 UserDTO（只含 id、昵称、头像，不存密码等敏感字段）以 Hash 结构存入 login:token:{token}，TTL 30 分钟 → 把 token 返回前端，前端放在请求头 authorization 里。
  3. 登录校验：拦截器从请求头取 token → 去 Redis 查用户 → 存在就放入 ThreadLocal（UserHolder）并刷新 TTL，不存在就拦截返回 401。

为什么用 Hash 存用户信息：可以单独读写某个字段，比 String 存整个 JSON 更灵活，内存也略省。注意 StringRedisTemplate 要求所有 value 为字符串，BeanUtil.beanToMap 时要把 Long 类型的 id 转成 String，否则会抛 ClassCastException，这是项目中一个常见的坑。

为什么 key 用随机 token 而不是手机号：token 要返回给前端保存，用手机号既泄露隐私，也容易被伪造。

登录拦截器为什么要拆成两个？

如果只有一个拦截器，并且只拦截需要登录的路径（如 /user/me、下单），那么用户一直只访问首页、商户详情这类不需要登录的页面时，token 的 TTL 不会刷新，30 分钟后即使用户在活跃使用也会被强制登出。

拆成两个：

  • RefreshTokenInterceptor（order(0)，拦截所有路径 /**）：有 token 就去 Redis 查用户，查到就存入 ThreadLocal 并刷新 TTL；没有 token 或查不到都直接放行，不做拦截。
  • LoginInterceptor（order(1)，只拦截需要登录的路径）：只判断 ThreadLocal 里有没有用户，没有就返回 401。

在 RefreshTokenInterceptor.afterCompletion() 中调用 UserHolder.removeUser() 清理 ThreadLocal。拦截器的 order 值越小越先执行。

ThreadLocal 里存了哪些信息？有什么问题？为什么 value 不能被 GC 回收？

项目中存了什么：UserHolder 用 ThreadLocal 保存当前请求的登录用户 UserDTO（id、昵称、头像），业务代码随时 UserHolder.getUser() 获取，不必层层传参。

底层实现：每个 Thread 持有一个 ThreadLocalMap，数据存在线程自己身上，天然隔离。Entry extends WeakReference<ThreadLocal<?>>：key 是 ThreadLocal 的弱引用，value 是强引用。

为什么 value 回收不了：外部不再强引用 ThreadLocal 后，key 在 GC 时被回收，Entry 变成 key 为 null 的条目；但 value 仍沿 Thread → ThreadLocalMap → Entry → value 强引用可达。Tomcat 工作线程来自线程池、长期存活，value 就一直留在内存里。

更现实的问题是数据串号：线程复用时上一个请求没清理，下一个请求可能读到上一个用户的信息。

怎么办

  • 在 finally 或拦截器 afterCompletion 中调用 remove()。
  • get/set/remove 会顺带清理 key 为 null 的条目，但只是兜底；key 用弱引用是为了让 ThreadLocal 对象本身能被回收。
  • 异步线程拿不到父线程的值，可用 InheritableThreadLocal（线程池下无效）或 TransmittableThreadLocal。

如果改用 JWT，令牌怎么刷新？怎么注销？

项目本身用的是"随机 token + Redis"，登录态在服务端，注销直接删除 Redis 中的 key 即可，刷新就是延长 TTL。JWT 是无状态的，签发后服务端无法让它提前失效，所以需要额外设计。

刷新：双 token 机制

  • 登录时签发短期的 access token（如 15 到 30 分钟）和长期的 refresh token（如 7 天）。
  • 请求只携带 access token；过期后，客户端用 refresh token 调用刷新接口。
  • 服务端校验 refresh token（签名、有效期、是否在黑名单或已被使用）后签发新的 access token，通常同时轮换一个新的 refresh token，旧的作废，防止 refresh token 被盗后长期可用。
  • refresh token 建议在服务端（Redis）留存，便于吊销。

注销

  • 黑名单：退出登录时把 access token 的 jti（唯一 ID）写入 Redis，TTL 设为 token 剩余有效期，每次请求校验是否在黑名单中；同时删除或拉黑 refresh token。
  • 版本号：Redis 中为每个用户存一个 token 版本号，JWT 载荷带上版本号，修改密码或强制下线时版本号加 1，旧 token 全部失效。

权衡：一旦引入黑名单，每次请求都要查 Redis，JWT"无状态"的优势就被削弱了。所以在需要随时踢人下线的业务中，"token + Redis 存会话"往往更简单直接，这也是项目选择这种方式的原因。

数据库主键怎么做的？订单 ID 为什么不用自增？

普通表（用户、商户、博客）用 MySQL 自增主键；优惠券订单表用自己实现的全局唯一 ID 生成器。

订单不用自增的原因

  • 规律性太明显：订单号连续，用户或竞争对手可以轻易推算出每天的订单量。
  • 分库分表后会重复：多个库各自自增，ID 会冲突。
  • 单表数据量受限，未来必然要拆分。

全局 ID 生成器（RedisIdWorker）：64 位 long，1 位符号位 + 31 位时间戳 + 32 位序列号。

  • 时间戳：当前秒数减去一个自定义起始时间（如 2022-01-01），31 位秒数可以用约 68 年。
  • 序列号：Redis INCR icr:{业务名}:{yyyy:MM:dd}，按天拼接 key，既避免单个 key 自增到上限（32 位约 42 亿），又方便统计每天的订单量。
  • 最终 timestamp << 32 | count，整体趋势递增，对 InnoDB 的 B+ 树插入友好。

其他方案对比

  • UUID：无序、36 个字符太长，作为主键会导致页分裂、索引膨胀，不推荐。
  • 雪花算法：1 位符号 + 41 位毫秒时间戳 + 10 位机器 ID + 12 位序列号，本地生成、性能最好，但依赖机器时钟，时钟回拨可能产生重复 ID，需要额外处理（等待、报错或借用备用位）。
  • 号段模式（美团 Leaf、滴滴 TinyID）：从数据库批量取一段 ID 缓存在本地，适合大规模场景。

这个项目中遇到的最大技术挑战是什么？怎么解决的？

建议选"秒杀下单的并发安全与性能"这条主线，因为它有清晰的问题演进，也能自然串联 Spring 事务、锁、Redis、MQ 等多个考点。可以按以下顺序讲：

  1. 超卖：最初"先查库存再扣减"，并发下多个线程同时查到库存 > 0，导致超卖。用乐观锁 update ... set stock = stock - 1 where id = ? and stock > 0 解决，比"版本号必须相等"的写法失败率更低。
  2. 一人一单的并发问题：先查订单是否存在再插入，并发下同一个用户可以下多单。用 synchronized (userId.toString().intern()) 按用户加锁。这里遇到两个坑：
    • 锁必须加在事务外面，否则锁释放了事务还没提交，其他线程依然查不到订单。
    • 在同一个类中调用 @Transactional 方法是自调用，事务不生效，需要通过 AopContext.currentProxy() 拿到代理对象来调用（并开启 exposeProxy = true）。
  3. 集群下 synchronized 失效：多台 Tomcat 各自有 JVM 锁，改用 Redis 分布式锁。自己实现的 SETNX 锁又遇到误删他人锁、判断和删除非原子的问题，用"线程标识 + Lua 脚本释放"解决，最后换成 Redisson（可重入、可重试、看门狗续期）。
  4. 性能：全流程串行访问数据库，吞吐量很低。改为 Lua 脚本在 Redis 中原子判断库存和一人一单，成功就把订单信息放入消息队列，由后台线程异步写库，接口响应时间大幅下降。消息队列从 JVM 阻塞队列演进到 Redis Stream（或 MQ），解决内存上限和宕机丢失的问题。

讲的时候要给出可量化的结果（如压测 QPS、平均响应时间的变化），并说明每一步方案的局限，体现思考过程。

缓存设计与一致性 7高频 2

缓存是怎么设计的？key 和 value 分别存什么？

缓存哪些数据：读多写少、对一致性要求不是特别高的数据。

业务 key 类型 / value TTL
验证码 login:code:{phone} String，6 位验证码 2 分钟
登录态 login:token:{token} Hash，UserDTO 各字段 30 分钟，访问时刷新
商户详情 cache:shop:{id} String，商户对象 JSON（名称、地址、坐标、评分、营业时间等静态信息） 30 分钟 + 随机值
商户空值 cache:shop:{id} 空字符串 "" 2 分钟
商户类型列表 cache:shop-type String（JSON 数组）或 List 较长，变化极少
互斥锁 lock:shop:{id} String，"1" 10 秒
秒杀库存 seckill:stock:{voucherId} String，库存数量 活动结束后过期
一人一单 seckill:order:{voucherId} Set，已下单的 userId 同上

静态信息有没有缓存：商户的名称、地址、图片、营业时间，优惠券的标题、规则、面额、使用期限都属于静态或准静态信息，会和详情一起缓存；而库存这种高频变动的数据单独用一个 key 存储，扣减时不影响详情缓存。图片等静态资源本身走 Nginx / CDN。

设计原则

  • key 统一用 业务:子业务:id 的格式，可读、便于排查和批量管理。
  • 设置 TTL 兜底，避免冷数据长期占用内存，也作为一致性的最终保障。
  • 不同 key 的 TTL 加随机值，防止同时过期引发雪崩。
  • 控制 value 大小，避免 bigkey（单个 String 尽量不超过 10 KB）。

为什么"先更新数据库再删除缓存"？为什么不更新缓存，也不先删缓存？高频

项目采用 Cache Aside（旁路缓存）：读时缓存未命中就查库并写入缓存；写时先更新数据库，再删除缓存，并设置 TTL 兜底。

为什么删除而不是更新缓存

  • 写多读少时浪费：每次更新都去重算并写缓存，但中间这些值可能根本没人读；删除后等下次读时再懒加载即可。
  • 并发更新会写入旧值：线程 A、B 先后更新数据库为 1、2，但写缓存的顺序可能变成 B 先、A 后，缓存最终是 1，与数据库的 2 不一致。删除操作是幂等的，不存在这个问题。
  • 缓存值可能需要多张表组合计算，更新成本高。

为什么不先删缓存再更新数据库

  1. 线程 A 删除缓存。
  2. 线程 B 查询缓存未命中，读到数据库中的旧值，写回缓存。
  3. 线程 A 更新数据库。

结果缓存中一直是旧值，直到 TTL 过期。更新数据库比读数据库慢，第 2 步完全可能插进来，概率较高。

先更新数据库再删缓存也不是绝对安全：缓存恰好过期 → 线程 A 读到旧值 → 线程 B 更新数据库并删除缓存 → 线程 A 把旧值写入缓存。但这要求"A 的读库 + 写缓存"比"B 的写库 + 删缓存"还慢，而写库通常远慢于写缓存，所以概率很低，再加上 TTL 兜底，是工程上公认的较优方案。

保证操作的完整性

  • 单体项目中，更新数据库和删除缓存放在同一个 @Transactional 方法中，删除缓存失败就抛异常回滚。分布式系统中则依靠 MQ 或 TCC 等方案。
  • 删除失败时：重试，或订阅 binlog（Canal）异步删除。
  • 如果对一致性要求更高，可以用延迟双删：删缓存 → 更新数据库 → 延迟几百毫秒再删一次。缺点是延迟时间不好确定。
  • 强一致需求（如账户余额）不应该依赖缓存，或者使用读写锁，牺牲性能。

缓存删除失败，MQ 重试最多几次？超过次数怎么处理？

方案：更新数据库后删除缓存，失败则把要删的 key 发送到 MQ，由消费者重试删除。更推荐的做法是用 Canal 订阅 MySQL binlog，把变更投递到 MQ 后由消费者删除缓存，与业务代码解耦，也不会因为应用宕机而漏删。

重试次数：没有统一标准，一般 3 到 5 次，间隔递增（如 1s、5s、30s），避免在 Redis 故障时频繁重试雪上加霜。RocketMQ 消费失败默认最多重试 16 次，间隔从 10 秒逐步增加到 2 小时，可以通过 maxReconsumeTimes 调小。

超过次数之后

  1. 进入死信队列（RocketMQ 为 %DLQ%{消费组}；RabbitMQ 需要配置死信交换机），持久化保存不丢失。
  2. 记录日志并触发监控告警，人工排查 Redis 故障或网络问题。
  3. 由定时任务或人工从死信队列中重新投递。
  4. TTL 兜底：缓存总会过期，过期后重新从数据库加载最新值，保证最终一致。所以缓存的 TTL 不能设成永久。

缓存穿透、缓存击穿、缓存雪崩是什么？怎么解决？高频

问题 含义 解决方案
缓存穿透 请求的数据在缓存和数据库中都不存在，缓存永远不生效，每次都打到数据库，常见于恶意攻击（随机或负数 ID） 缓存空值；布隆过滤器；参数校验（ID 格式、范围）；限流、拉黑异常用户
缓存击穿 某个热点 key 过期或缓存重建耗时较长，大量并发请求同时未命中，瞬间全部打到数据库（热点 key 问题） 互斥锁；逻辑过期；热点 key 预热
缓存雪崩 大量 key 同一时间过期，或 Redis 服务宕机，大量请求打到数据库 TTL 加随机值；Redis 高可用（哨兵、集群）；限流、熔断、降级；多级缓存；提前预热

项目中的实现

  • 穿透：缓存空值。数据库查不到时写入空字符串 ""，TTL 2 分钟。缺点是占额外内存，TTL 内可能短暂不一致。
  • 击穿：互斥锁。未命中时 SETNX lock:shop:{id}（TTL 10 秒）抢锁，抢到的线程再查一次缓存（double check）后查库重建，没抢到的休眠 50 ms 重试。
  • 击穿：逻辑过期。热点 key 不设 TTL，value 中存 expireTime，需要预热。发现逻辑过期就抢锁、开独立线程异步重建，所有线程直接返回旧数据。
  • 用泛型 + Function<ID, R> dbFallback 封装成工具类 CacheClient 复用。
对比 互斥锁 逻辑过期
一致性 强 弱（重建完成前返回旧数据）
性能 线程需要等待 不等待
适用 一致性优先 可用性优先，如活动页面

布隆过滤器是什么？原理、优缺点？为什么是假阳性而不是假阴性？

布隆过滤器是一种空间效率很高的概率型数据结构，用来判断"一个元素是否可能在集合中"。在项目中用于缓存穿透：请求进来先问布隆过滤器，判断不存在就直接返回，不再查 Redis 和数据库。

原理：一个长度为 m 的 bit 数组 + k 个哈希函数。

  • 添加：对元素做 k 次哈希，得到 k 个位置，全部置为 1。
  • 查询：同样算出 k 个位置，只要有一个是 0，元素一定不存在；全部为 1，元素可能存在。

为什么只有假阳性，没有假阴性

  • 假阳性：哈希位置会重叠，未添加的元素的 k 个位置可能恰好都被其他元素置 1。
  • 没有假阴性：添加过的元素 k 个位置一定是 1，且 bit 只会从 0 变 1（不删除的前提下），查询不可能遇到 0。
  • 误判率随 m 增大而降低；给定 m 和 n，最优 k = (m / n) · ln2。Guava、Redisson 可按「预计元素数 + 期望误判率」自动计算。

优点：空间极小（1 亿元素、1% 误判率约 114 MB）；查询插入 O(k)；不存元素本身。

缺点

  • 存在误判，数据量超过预估后误判率急剧上升，只能重建。
  • 不支持删除：bit 被多个元素共享，置 0 会产生假阴性。
  • 需要预热已有 ID，新增数据必须同步写入，否则会被误拦截。

实现方式：单机 Guava BloomFilter；分布式用 Redisson RBloomFilter（基于 BitMap）或 RedisBloom 的 BF.ADD / BF.EXISTS。

布隆过滤器不支持删除，有什么替代方案？用过计数布隆过滤器吗？

计数布隆过滤器（Counting Bloom Filter）

  • 把每个 bit 换成一个小计数器（通常 4 位）。添加时 k 个计数器加 1，删除时减 1，查询时判断 k 个计数器是否都大于 0。
  • 缺点：空间是普通布隆过滤器的数倍（4 位计数器就是 4 倍）；计数器有溢出风险（4 位最大 15，溢出后不能再正确删除）；只能删除确实添加过的元素，误删一个不存在的元素会把其他元素的计数减掉，产生假阴性。

布谷鸟过滤器（Cuckoo Filter）

  • 存储元素的指纹（fingerprint），使用布谷鸟哈希，每个元素有两个候选桶，冲突时把旧指纹"踢"到另一个候选桶。
  • 支持删除；在误判率较低时空间效率比布隆过滤器更好；查询只需访问两个桶，速度快。
  • 缺点：容量满时插入可能失败；同一个元素重复插入有次数上限；同样不能删除未插入过的元素。RedisBloom 模块提供了 CF.ADD / CF.DEL。

定期重建：最常用、最简单。保留普通布隆过滤器，定时（如每天凌晨）扫描数据库中有效的 ID 重新构建一个新的过滤器，构建完成后原子切换（例如 Redis 中写入新 key 后再切换引用，或用 RENAME）。

接受少量误判：被删除的数据在过滤器中仍判断为存在时，请求会继续查 Redis 和数据库，最终查不到，再配合缓存空值即可，对数据库的压力很小。

商户删除或更新后，布隆过滤器怎么更新？秒杀场景用布隆过滤器还有什么问题？

商户信息更新：布隆过滤器只存 ID，不存商户的具体内容，所以修改商户的名称、地址等信息不需要更新布隆过滤器，只需要按照"更新数据库 → 删除缓存"处理缓存一致性即可。

新增商户：在写入数据库的同时（或通过 binlog / MQ 异步）把新 ID add 到布隆过滤器。注意上线前必须先写入，否则会被误判为不存在而拦截，效果上相当于假阴性。

删除商户：过滤器中的 bit 无法清除，会一直判断为"可能存在"，请求会继续走到缓存和数据库，查不到就缓存空值返回，业务上没有错误，只是这部分请求没被拦截。处理方式：

  • 容忍：删除操作占比通常很低，影响可以忽略。
  • 定期重建：清理掉已删除 ID 积累的误判。
  • 需要实时删除时，换用计数布隆过滤器或布谷鸟过滤器。

秒杀场景中除了误判之外的问题

  • 实时性：秒杀的优惠券、商品是临时上架的，必须保证上架前已写入过滤器，否则会误拦截真实请求。
  • 热点集中：分布式布隆过滤器存储在 Redis 的一个 key 中，所有请求都访问这个 key，形成热点 key 和 bigkey，可能成为瓶颈。可以在本地也放一份（Guava），或者按 ID 分片到多个 key。
  • 作用有限：秒杀的商品数量少且固定，攻击者刷的往往是真实存在的商品，布隆过滤器拦不住，还是要靠限流、验证码、一人一单校验。
  • 扩容困难：数据量超出预估时误判率上升，只能整体重建。
  • 增加复杂度：多一个需要维护一致性的组件，以及重建期间的切换问题。

多级缓存 6高频 0

本地缓存和 Redis 怎么协同？什么时候优先用本地缓存？

采用 Caffeine（L1，进程内）+ Redis（L2，分布式）+ MySQL 的多级缓存。

读流程

  1. 先查 Caffeine，命中直接返回（纳秒到微秒级，没有网络开销）。
  2. 未命中查 Redis，命中则回填 Caffeine 后返回。
  3. Redis 也未命中，按缓存击穿的方案（互斥锁）查询数据库，回填 Redis 和 Caffeine。数据库也没有就缓存空值。

写流程：更新数据库 → 删除 Redis 缓存 → 通知所有节点删除本地缓存（Redis Pub/Sub 或 MQ 广播）。更彻底的方式是由 Canal 监听 binlog，统一触发 Redis 和各节点本地缓存的删除。

适合放本地缓存的数据

  • 极热点数据：秒杀活动的商品和优惠券详情、首页推荐、店铺类型列表。
  • 变化很少、能接受短暂不一致的数据：配置、字典、类目。
  • 体量小的数据：本地缓存占用 JVM 堆内存，必须限制 maximumSize，否则会影响 GC 甚至 OOM。

不适合放本地缓存的数据：库存、余额这类实时变动、要求强一致的数据；数据量大的数据；用户维度的个性化数据（命中率低）。

本地缓存的 TTL 要明显短于 Redis（如本地 1 到 5 分钟、Redis 30 分钟），让本地缓存的不一致窗口有上限。

集群环境下，各节点的本地缓存不同步，怎么保证一致性？

本地缓存在每个 JVM 里各有一份，不可能做到强一致，目标是缩短不一致的窗口，可以组合使用以下方案：

  1. 广播失效（主要手段）：数据变更后，通过 Redis Pub/Sub 或 MQ 的广播模式（RocketMQ MessageModel.BROADCASTING、Kafka 每个节点用独立的消费组）发送失效消息，各节点收到后 invalidate 对应的 key，下次读时再从 Redis 加载。
  2. 短 TTL 兜底：本地缓存设置较短的过期时间（expireAfterWrite），即使通知丢失，过期后也会自动加载最新数据。Redis Pub/Sub 不持久化，节点断线期间的消息会丢失，所以 TTL 兜底是必需的。
  3. binlog 驱动：Canal 监听数据库变更，把失效事件投递到 MQ 广播，避免业务代码漏发通知。
  4. 版本号校验：Redis 中为数据维护一个版本号，本地缓存中也保存版本号；读取时比较两者（只读一个很小的版本号 key），不一致就重新加载。代价是每次读都多一次 Redis 访问。
  5. 请求路由：网关或 Nginx 按 key 做一致性哈希，让同一数据的请求固定落在同一个节点上，每份数据只有一个本地副本，但节点扩缩容时会发生迁移，负载也可能不均衡。

本地缓存删除失败怎么办：本地删除就是内存操作，几乎不会失败；真正的风险是通知没送达（节点宕机、网络抖动、Pub/Sub 消息丢失）。处理方式是用可靠的 MQ 替代 Pub/Sub，加上短 TTL 兜底，必要时由定时任务对比版本号。业务上必须强一致的数据，就不要放本地缓存。

热点数据只用 Redis 行不行？会有什么问题？

可以，大多数场景只用 Redis 就够了。单个 Redis 节点可以支撑数万到十万级 QPS，在 QPS 只有几千的场景下引入本地缓存只会增加一致性维护的复杂度，属于过度设计。

流量大了之后只用 Redis 的问题

  • 热 key 单点瓶颈：Redis Cluster 中同一个 key 只会落在一个分片上，加机器也分散不了。秒杀开始的瞬间所有请求都访问同一个商品 key，会把这一个分片的 CPU 或网卡打满，进而影响该分片上的其他 key。
  • 网络开销：每次访问都有一次网络往返（通常 0.x 到 1 ms），本地缓存只需要纳秒到微秒级；网卡带宽也可能被大 value 打满。
  • 可用性：Redis 一旦故障或发生主从切换，所有请求直接打到数据库，没有缓冲层。

本地缓存的价值：扛住热 key、降低 Redis 负载、降低响应时间，在 Redis 故障时还能作为降级的兜底。

热 key 的其他解决方式：把热 key 复制成多份（key_1 到 key_N，读取时随机选一个）分散到不同分片；使用读写分离让从节点分担读流量；用京东 hotkey 这类热点探测框架自动识别热 key 并推送到本地缓存。

Caffeine 的淘汰策略是什么？为什么选它？

Caffeine 使用 W-TinyLFU（Window TinyLFU），结合了 LRU 和 LFU 的优点，命中率接近理论最优，是 Spring Boot 2.x 起官方推荐的本地缓存（取代了 Guava Cache）。

结构

  • Window 区（约占 1%）：LRU。新数据先进入这里，让突发的新热点有机会留下来，不会因为一开始频率低就被立刻淘汰。
  • Main 区（约占 99%）：分段 LRU（SLRU），分为 Probation（试用区，约 20%）和 Protected（保护区，约 80%）。Probation 中的数据再次被访问就晋升到 Protected。
  • TinyLFU 准入过滤：Window 区淘汰出来的候选者要与 Probation 区的淘汰者比较访问频率，频率高的留下。频率由 Count-Min Sketch 统计：多个哈希函数映射到 4 bit 的计数器数组，取最小值作为估计频率，占用空间极小。
  • 衰减（保鲜）：总访问次数达到阈值后，所有计数器减半，让过去的热点逐渐冷却，适应访问模式的变化。
  • Window 与 Main 的比例会根据命中率通过爬山算法动态调整。

为什么选它

  • 纯 LRU：一次批量扫描（如遍历全表）就会把真正的热点数据全部挤出去，抗扫描能力差。
  • 纯 LFU：需要为每个 key 维护精确计数，内存开销大；历史热点即使不再访问，计数仍然很高，长期赖着不走，对新热点反应慢。
  • W-TinyLFU 用很小的空间近似统计频率，既能抵抗扫描，又能快速接纳新热点，还能淘汰过气热点，综合命中率比 LRU、LFU 都高。

此外 Caffeine 的读写操作先写入环形缓冲区再异步批量处理，减少锁竞争，并发性能也优于 Guava Cache。常用配置：maximumSize、expireAfterWrite、expireAfterAccess、refreshAfterWrite、recordStats。

秒杀 8 点开始，缓存的过期时间设置为覆盖这个时间点，能解决什么问题？有什么缺点？

解决的问题：本质是缓存预热 + 避免热点 key 在活动期间过期。活动开始前就把商品详情、库存加载进缓存，并让 TTL 覆盖整个活动时间段（例如 7:50 预热，到活动结束后再过期），可以：

  • 避免缓存击穿：活动开始瞬间所有请求都命中缓存，不会出现"热点 key 刚好过期，大量请求同时去查数据库"的情况。
  • 避免冷启动：第一批请求不需要回源数据库，数据库只承担下单写入。

缺点

  • 数据提前暴露：缓存里有数据不代表活动已开始。如果后端接口不做时间校验，用户可以绕过前端倒计时提前抢购，所以下单接口必须校验 beginTime / endTime，秒杀地址也可以在活动开始后才下发（动态 URL）。
  • 一致性问题：预热到活动开始之间如果运营修改了商品信息，必须同步更新缓存，否则用户看到旧数据。
  • 时间点难以精确：活动延期或提前，TTL 都要跟着调整；如果大量 key 设置同一个过期时间点，活动结束时会同时过期，可能引发小规模雪崩，需要加随机偏移。
  • 内存占用：TTL 偏长，活动结束后数据还在占用内存。
  • 无法防穿透：请求不存在的商品 ID 依然会穿透，仍需空值缓存或布隆过滤器。

更好的做法：预热 + 逻辑过期（热点 key 物理上不过期，靠 value 中的过期时间字段异步重建），活动结束后由定时任务或 TTL 统一清理。

Redis 集群宕机有什么兜底方案？二级缓存场景下怎么避免雪崩？

Redis 整体不可用时的兜底

  1. 本地缓存兜底：Caffeine 中还有的热点数据继续提供服务，可以在故障时延长本地缓存的有效期，牺牲新鲜度保证可用。
  2. 熔断降级：Sentinel / Resilience4j 检测到 Redis 调用异常率过高时触发熔断，快速失败，避免线程被 Redis 超时拖住。
  3. 限流后读数据库：降级到数据库时必须严格限流，只放少量请求过去，否则会把数据库也一起打垮。
  4. 业务降级：非核心功能（点赞、推荐、排行榜）直接关闭或返回默认值；秒杀这类强依赖 Redis 的功能暂停，返回"活动火爆，请稍后再试"。
  5. 高可用部署：哨兵或 Cluster + 持久化，跨机房部署；更高要求下同城双活 / 异地多活，通过 DNS 或网关切换流量。

二级缓存下避免雪崩

  • TTL 加随机偏移：Redis 和本地缓存的过期时间都加上随机值，避免同一批 key 同时过期；本地缓存的 TTL 要和 Redis 错开。
  • 热点 key 不过期或逻辑过期，后台异步刷新；Caffeine 可用 refreshAfterWrite，到期后第一次访问时异步刷新、先返回旧值。
  • 缓存重建加锁：同一个 key 只允许一个线程回源，其他线程等待或返回旧值。
  • 预热：服务启动或发版后先加载热点数据，避免冷启动时所有节点本地缓存同时为空。
  • 限流和熔断作为最后一道防线，保护数据库。
  • 热点探测：用滑动窗口统计 key 的访问频率，识别出热点后提前延长其过期时间或推送到本地缓存。

Redis 集群有哪几种方式？哨兵的主观下线和客观下线是什么？怎么选领导哨兵和新主节点？

三种部署方式

方式 解决的问题 局限
主从复制 数据备份、读写分离 主节点故障需要人工切换
哨兵 Sentinel 在主从基础上实现监控、自动故障转移、通知客户端新主地址 写能力和容量仍受限于单个主节点
Cluster 分片集群 16384 个哈希槽分布在多个主节点上，水平扩展容量和写性能，内置故障转移 多 key 操作要求在同一个槽（用 hash tag {}），不支持多数据库

主观下线（SDOWN）：哨兵每秒向各实例发 PING，某实例在 down-after-milliseconds 内没有有效回复，该哨兵就认为它主观下线。这只是单个哨兵的判断，可能是它自己网络有问题。

客观下线（ODOWN）：只针对主节点。哨兵通过 SENTINEL is-master-down-by-addr 询问其他哨兵，认为下线的数量达到 quorum（一般设为哨兵数的一半加一，可配置）即判定客观下线。

选举领导哨兵（类 Raft）：候选者把纪元 epoch 加 1 请求投票，每个哨兵一个纪元只投一票、先到先得；得票既超过半数又不少于 quorum 的成为 Leader，否则进入下一纪元重选。所以哨兵至少 3 个且为奇数。

选新主节点

  1. 过滤：排除已下线、与主节点断开超过 down-after-milliseconds × 10、replica-priority 为 0 的从节点。
  2. 优先级：replica-priority 值越小越优先，默认 100。
  3. 复制偏移量：offset 最大的，数据最新。
  4. run ID：字典序最小的。

故障转移：新主执行 REPLICAOF NO ONE，其他从节点改为复制新主，旧主恢复后成为从节点，并通过发布订阅通知客户端新地址。

秒杀场景下 Redis 主从会有什么问题？

核心问题都源于主从复制是异步的。

  • 故障切换导致超卖：已扣减的库存未同步就宕机，新主上库存比实际多；一人一单 Set 中的 userId 同样可能丢失。
  • 分布式锁丢失：加锁未同步就宕机，其他客户端在新主上又能加锁成功。
  • 读写分离读到旧数据：从从节点读库存会因复制延迟判断错误。
  • 脑裂：分区期间旧主仍接受写入，恢复后降为从节点并清空数据，期间写入全部丢失。

应对方式

  • 秒杀 key 读写只走主节点，扣减和校验放在同一个 Lua 脚本中原子执行。
  • 配置 min-replicas-to-write 1、min-replicas-max-lag 10，没有从节点及时确认就拒绝写入，减少（不能杜绝）丢失；关键写可用 WAIT，但仍不是强一致。
  • 以数据库为最终防线：库存乐观锁 stock > 0，订单表 (user_id, voucher_id) 唯一索引，再定时对账修复 Redis 库存。
  • 分布式锁：可用 MultiLock；RedLock 依赖时钟、防不住 GC 停顿，Redisson 已将 RedissonRedLock 标记为废弃。严格互斥用 ZooKeeper / etcd 或 fencing token。

一人一单的分布式锁是怎么演进的？

1. 单机 synchronized：按用户加锁 synchronized (userId.toString().intern())，同一用户串行、不同用户并行。intern() 保证相同值的字符串是同一个对象，否则每次 toString() 都是新对象，锁不住。注意两点：锁要包住整个事务方法（先提交事务再释放锁）；事务方法要通过代理对象调用，避免自调用导致事务失效。

2. 集群下失效：多个 Tomcat 节点各有自己的 JVM 和锁监视器，同一用户的请求被负载到不同节点时会同时拿到锁，必须使用分布式锁。

3. 基于 Redis 的简单分布式锁

  • 加锁：SET lock:order:{userId} {threadFlag} NX EX 10，一条命令原子地完成"不存在才设置"和设置过期时间。不能先 SETNX 再 EXPIRE，中间宕机会留下永不过期的锁。
  • 误删问题：线程 1 业务阻塞超时，锁自动释放，线程 2 拿到锁；线程 1 执行完后把线程 2 的锁删了。解决：value 存线程标识（UUID + 线程 ID，UUID 区分不同 JVM），释放前判断是不是自己的锁。
  • 判断与删除不是原子的：判断完是自己的锁后，正好发生 GC 停顿，期间锁过期被别人拿走，恢复后还是会误删。解决：用 Lua 脚本把"判断 + 删除"放在一起原子执行。
-- KEYS[1] 锁的 key，ARGV[1] 当前线程标识
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
end
return 0

4. 仍然存在的问题，于是换成 Redisson

  • 不可重入：同一线程无法再次获取同一把锁。
  • 不可重试：获取失败直接返回，没有等待重试机制。
  • 超时释放：业务执行时间超过 TTL 时锁被提前释放，有安全隐患。
  • 主从一致性：主节点宕机时锁可能丢失。

Redisson 分别用 Hash 结构计数实现可重入、用发布订阅 + 信号量实现等待重试、用看门狗自动续期、用 MultiLock 应对主从一致性问题。

Redisson 看门狗机制是怎么实现自动续期的？可重入是怎么实现的？

**看门狗（Watchdog）**解决"业务执行时间不确定，锁的过期时间设短了会提前释放、设长了宕机后要等很久才释放"的问题。

  • 生效条件：只有在加锁时没有指定 leaseTime（如 lock()、tryLock(waitTime, TimeUnit)）才会启用。显式调用 lock(10, TimeUnit.SECONDS) 或 tryLock(waitTime, leaseTime, unit) 时不会自动续期，锁到时间就过期。
  • 默认参数：锁的初始过期时间为 lockWatchdogTimeout，默认 30 秒；加锁成功后启动一个定时任务（基于 Netty 的 HashedWheelTimer），每隔 lockWatchdogTimeout / 3 即 10 秒检查一次：如果锁仍被当前线程持有，就用 Lua 脚本把过期时间重新设为 30 秒，然后安排下一次续期。
  • 停止续期：调用 unlock() 时取消定时任务；如果客户端宕机，定时任务随之消失，锁最多 30 秒后自动过期，不会出现死锁。
  • 所以一定要在 finally 中 unlock()，并且只能由加锁的线程释放（否则抛 IllegalMonitorStateException）。

可重入：锁用 Hash 结构存储，key 为锁名，field 为 UUID:threadId，value 为重入次数。

  • 加锁 Lua：锁不存在则 HINCRBY 设为 1 并设置过期时间；存在且 field 是自己则计数加 1 并重置过期时间；否则返回锁的剩余 TTL。
  • 释放 Lua：计数减 1，减到 0 时删除 key，并 PUBLISH 一条解锁消息。

可重试：tryLock(waitTime, ...) 获取失败时不会忙等，而是订阅该锁的解锁频道，收到解锁消息或等待到锁的剩余 TTL 后再重试，直到超过 waitTime。

超卖怎么解决的？用乐观锁 CAS 还是 Redis + Lua？高频

超卖的根因是"查询库存"和"扣减库存"不是原子操作：多个线程同时查到库存为 1，都去扣减，库存变成负数。

方案 做法 优点 缺点 适用
悲观锁 synchronized / 分布式锁串行化，或 SELECT ... FOR UPDATE 简单可靠 串行执行，吞吐量低 并发量不高
数据库乐观锁 UPDATE seckill_voucher SET stock = stock - 1 WHERE voucher_id = ? AND stock > 0 实现简单，数据库层面强一致 高并发时所有请求打到数据库，行锁竞争激烈 并发量中低
Redis + Lua 在 Redis 中原子判断并扣减库存，异步写入数据库 纯内存操作，性能高 Redis 与数据库是最终一致，需要处理同步、宕机、对账 高并发秒杀

乐观锁的细节：版本号法或 CAS 法（WHERE stock = 查询到的值）要求数据没被改过，并发时 100 个请求只有 1 个成功，大量请求失败，库存卖不完。改为 stock > 0 只要还有库存就能成功，失败率大大降低。InnoDB 执行这条 UPDATE 时会对该行加行锁，所以单条语句本身就是原子的。

项目的最终方案：Lua 脚本在 Redis 中原子完成"库存判断 + 一人一单判断 + 扣减 + 记录用户 + 写入消息队列"，异步下单时数据库仍保留 stock > 0 的条件作为兜底。两层结合：Redis 挡住绝大部分流量，数据库保证最终不会超卖。

Redis + Lua 防超卖的脚本怎么写？

准备：新增秒杀券时把库存写入 Redis：SET seckill:stock:{voucherId} 100。

脚本逻辑：判断库存 → 判断用户是否已下单 → 扣减库存 → 记录用户 → 把订单信息写入 Stream 消息队列。返回 0 表示成功，1 表示库存不足，2 表示重复下单。

-- KEYS[1] 库存 key    seckill:stock:{voucherId}
-- KEYS[2] 已下单用户  seckill:order:{voucherId}
-- KEYS[3] 消息队列    stream.orders
-- ARGV[1] voucherId  ARGV[2] userId  ARGV[3] orderId
local stock = tonumber(redis.call('get', KEYS[1]))
if stock == nil or stock <= 0 then
    return 1                                  -- 库存不足（key 不存在也视为不可售）
end
if redis.call('sismember', KEYS[2], ARGV[2]) == 1 then
    return 2                                  -- 一人一单
end
redis.call('incrby', KEYS[1], -1)
redis.call('sadd', KEYS[2], ARGV[2])
redis.call('xadd', KEYS[3], '*', 'voucherId', ARGV[1], 'userId', ARGV[2], 'id', ARGV[3])
return 0

Long r = stringRedisTemplate.execute(SECKILL_SCRIPT,
        List.of(STOCK_KEY + voucherId, ORDER_KEY + voucherId, "stream.orders"),
        voucherId.toString(), userId.toString(), String.valueOf(orderId));
if (r != 0) return Result.fail(r == 1 ? "库存不足" : "不能重复下单");
return Result.ok(orderId);                    // 立即返回订单 ID，订单异步落库

要点

  • 为什么用 Lua：Redis 单线程执行整个脚本，期间不会插入其他客户端的命令，"判断 + 扣减"是原子的；多条命令一次发送，也减少了网络往返。脚本预先加载（DefaultRedisScript），底层用 EVALSHA 执行。
  • 所有写操作放在检查之后：Lua 脚本执行中途报错时，已执行的写命令不会回滚，所以先做完全部判断再写。
  • get 不存在的 key 返回 false，tonumber 后是 nil，直接和数字比较会报错，要先判空。
  • Redis Cluster：脚本访问的所有 key 必须在同一个槽，应通过 KEYS 传入，并使用 hash tag 让它们落在同一节点，例如 seckill:stock:{1001}、seckill:order:{1001}。在脚本里拼接 key 的写法只适用于单机。
  • 用户的下单资格（活动是否开始、是否结束）在调用脚本之前校验，也可以把开始和结束时间放进 Redis 由脚本判断。

秒杀下单怎么异步化？阻塞队列和 Redis Stream 怎么选？

同步下单的问题：查询优惠券、判断库存、查询订单、扣减库存、创建订单全部串行访问数据库，还有分布式锁，耗时长、吞吐量低。

异步化思路：把"有没有资格"和"真正下单"拆开。资格判断由 Lua 在 Redis 中完成，成功后把订单信息（userId、voucherId、orderId）放入队列，立即返回订单 ID；后台线程从队列取出消息，写入数据库。

版本一：JVM 阻塞队列

  • BlockingQueue<VoucherOrder> orderTasks = new ArrayBlockingQueue<>(1024 * 1024)，@PostConstruct 时向单线程线程池提交一个消费任务，循环 take() 后创建订单。
  • 问题：内存限制（队列占用 JVM 堆，容量有限，满了就丢或阻塞）、数据安全（服务宕机或重启时队列中的订单全部丢失；取出后处理失败也没有重试）、无法在多实例之间共享。

版本二：Redis Stream 消费者组（Redis 5.0+）

XGROUP CREATE stream.orders g1 0 MKSTREAM                              # 创建消费者组
XREADGROUP GROUP g1 c1 COUNT 1 BLOCK 2000 STREAMS stream.orders >      # 读取未消费的新消息
XACK stream.orders g1 <messageId>                                       # 处理成功后确认
XREADGROUP GROUP g1 c1 COUNT 1 STREAMS stream.orders 0                  # 读取 pending-list 中已读未确认的消息
  • 消费流程：循环阻塞读取 > 的新消息 → 创建订单 → XACK。出现异常时进入 pending-list 处理逻辑，用 ID 0 读取已投递但未确认的消息并重试，直到 pending-list 为空。
  • 优点：消息持久化（依赖 Redis 持久化）；消费者组内多个消费者竞争消费，可水平扩展；有 ACK 和 pending-list，消费失败可重试；支持阻塞读取和消息回溯。
  • 局限：可靠性依赖 Redis 持久化和主从（主从切换可能丢消息）；没有死信队列、延迟消息等完善功能。

版本三：专业 MQ（RocketMQ / Kafka / RabbitMQ）：更大的流量、更严格的可靠性要求时使用，消息持久化、多副本、失败重试、死信队列、事务消息都更成熟。

Lua 脚本执行出现异常，或 Redis 突然宕机，数据一致性怎么保证？

Lua 执行异常：脚本执行是原子的（不会被其他命令打断），但不是事务性的：中途报错时，前面已执行的写命令不会回滚。所以：

  • 先校验后写入，把可能出错的逻辑（类型转换、参数判空）全放在写操作之前，脚本上线前充分测试。
  • 写操作尽量少、顺序合理，例如先扣库存再写用户集合，即使后续失败，结果也只是"少卖"而不会"超卖"，再由对账补偿。
  • 脚本执行超过 busy-reply-threshold（旧名 lua-time-limit，默认 5 秒）后，Redis 开始对其他命令返回 BUSY；没有执行过写操作的脚本可以 SCRIPT KILL，执行过写操作的只能 SHUTDOWN NOSAVE。所以脚本必须短小。

Redis 宕机

  • 持久化：开启 AOF，appendfsync everysec 最多丢失约 1 秒的数据；Redis 4.0+ 开启 RDB + AOF 混合持久化，加快重启恢复速度。
  • 高可用：哨兵或 Cluster 自动故障转移；配置 min-replicas-to-write 减少切换时的数据丢失。
  • 丢失后的影响分析：如果丢的是"扣库存 + 写用户集合"，Redis 库存比实际多，可能多卖；如果丢的是 Stream 中的消息，用户拿到了订单 ID 但订单没有落库。
  • 数据库兜底：落库时数据库仍用 stock > 0 扣减（防止超卖），订单表 (user_id, voucher_id) 唯一索引（防止一人多单）。
  • 对账补偿：恢复后用数据库中的订单数据重建 Redis 库存和已下单用户集合；定时任务比对 Redis 与 MySQL，修复差异；对"已返回成功但订单未落库"的情况通知用户或自动补单。
  • 幂等：每笔订单的 orderId 在进入 Redis 前就生成，重试、重复消费时都以 orderId 去重。

异步下单的可靠性 5高频 1

库存扣减和订单创建在同一个消费者里处理吗？其中一步失败怎么回滚？

项目中的分工

  • Redis 层（同步，在请求线程中）：Lua 脚本扣减 Redis 库存、记录已下单用户、写入消息，立即返回结果。
  • 数据库层（异步，在同一个消费者里）：消费者在同一个本地事务中完成 MySQL 库存扣减（stock = stock - 1 WHERE stock > 0）和订单插入。两者在同一个数据库，用 @Transactional 就能保证要么都成功、要么都回滚，不需要分布式事务。

失败的处理

  • 数据库事务内任一步失败：事务整体回滚，消息不 ACK，留在 pending-list（或 MQ 重试队列）中重试。
  • 重试多次仍失败（如库存已不足、数据异常）：进入死信，并补偿 Redis：库存加回 1，从已下单集合中移除该用户，让名额回到池子里；同时通知用户下单失败。补偿操作也要幂等，例如以 orderId 记录是否已补偿。
  • 订单创建成功但用户未支付：属于另一条链路，用延迟消息（RocketMQ 延时消息、RabbitMQ TTL + 死信）或定时任务在超时（如 15 分钟）后关闭订单，在事务中回补 MySQL 库存，再回补 Redis 库存。

如果库存服务和订单服务拆成了两个微服务，就变成了分布式事务问题，常用方案：

  • 本地消息表：订单服务在本地事务中同时写订单和一条"待扣库存"消息，定时任务扫描投递，库存服务幂等消费。
  • RocketMQ 事务消息：先发半消息 → 执行本地事务 → 根据结果提交或回滚消息；Broker 通过回查确认未决状态。
  • TCC：库存的 Try 阶段冻结库存，Confirm 正式扣减，Cancel 释放冻结。
  • Seata AT 模式：自动生成回滚日志，适合对性能要求不高的场景。

消费端出现重复消费等幂等问题怎么办？高频

为什么会重复：MQ 一般只保证 at least once。生产者重试、消费者处理成功但 ACK 前宕机、Redis Stream 中 pending 消息被重新读取、Rebalance 等都会导致同一条消息被消费多次，结果是重复创建订单或重复扣减库存。

核心思路：给每笔业务一个全局唯一 ID（秒杀中就是 Lua 调用前生成的 orderId），以它为依据去重。

方案 做法 适用
唯一索引 订单表主键为 orderId，并对 (user_id, voucher_id) 建唯一索引，重复插入时捕获 DuplicateKeyException 视为成功 订单创建，最可靠的兜底
先查后写 消费前按 orderId 查询，已存在就直接 ACK；需要配合唯一索引，因为并发时查询和插入之间有间隙 降低异常开销
状态机 UPDATE ... SET status = 2 WHERE id = ? AND status = 1，状态只能单向流转，重复执行影响行数为 0 订单状态变更
乐观锁 / 条件更新 stock = stock - 1 WHERE id = ? AND stock > 0，或使用版本号 库存扣减
去重表 / Redis SETNX 以消息 ID 为 key 执行 SET NX EX，成功才处理；或建去重表，与业务写入放在同一个事务中 通用、高并发

项目中的组合：

  1. 消息携带 orderId。
  2. 消费时开启本地事务：插入订单（主键 + 唯一索引防重）与扣减库存在同一事务中。
  3. 插入时如果唯一键冲突，说明已处理过，整个事务回滚（库存不会被重复扣减），然后直接 ACK。
  4. 正常完成后 ACK。

关键在于"判重"和"业务写入"要在同一个事务里，或者依赖数据库约束，单独用 Redis 判重在"判重成功但业务失败"时会丢消息，需要在失败时删除去重标记。

消息的生产和消费流程是怎样的？如何保证消息不丢失、不重复消费？

以 RocketMQ 为例（项目中如果使用 Redis Stream，答法类似：持久化 + ACK + pending-list 重试）。

流程

  1. 生产者从 NameServer 获取 Topic 的路由信息，选择一个 MessageQueue 发送给对应的 Broker。发送方式有同步（等待 Broker 确认）、异步（回调）、单向（不关心结果，可能丢失）。
  2. Broker 把所有消息顺序写入 CommitLog，再异步构建 ConsumeQueue（消费索引）和 IndexFile；根据配置同步或异步刷盘，主从之间同步或异步复制。
  3. 消费者（Push 模式本质是长轮询拉取）从 Broker 拉取消息，同一消费者组内按队列分配实现负载均衡，处理成功后提交消费位点 offset；失败则返回 RECONSUME_LATER，进入重试队列，超过最大次数（默认 16）进入死信队列。

不丢失：三个环节都要保证

环节 措施
生产端 同步发送并检查结果，失败重试；或使用事务消息；发送失败落库，由定时任务补发
Broker 同步刷盘 flushDiskType = SYNC_FLUSH；主从同步复制（SYNC_MASTER）或使用 DLedger 多副本
消费端 业务处理成功后才返回 CONSUME_SUCCESS；不要在消费线程中再异步处理后立即返回成功

不重复：RocketMQ 和 Kafka 默认都只保证 at least once（Kafka 的幂等生产者和事务能实现 exactly once 语义，但仅限于 Kafka 内部的读写链路），所以重复消费无法完全避免，必须在消费端做幂等：唯一业务键 + 唯一索引、状态机、去重表等，见上一题。

秒杀结束后 Redis 库存同步回 MySQL，部分失败怎么办？

先澄清：在项目的设计中，每个订单的异步消费都会同时扣减 MySQL 库存，MySQL 本身就是逐笔更新的，不依赖"活动结束后一次性同步"。活动结束后要做的是对账，确认两边一致。

如果采用"Redis 扣减、结束后批量回写 MySQL"的设计，部分失败的处理思路是记录状态 + 幂等重试 + 对账兜底：

  • 以订单为准，而不是以 Redis 数字为准：MySQL 库存应等于"初始库存 − 有效订单数"，按订单表计算并更新，结果天然幂等，重复执行也不会扣多。
  • 记录同步状态：每个券或商品一条同步记录（待同步 / 成功 / 失败），只重试失败的部分。
  • 重试：失败项进入重试队列，采用指数退避（如 1 分钟、5 分钟、15 分钟），每次重试都是幂等的"设置为某值"或"按订单重算"，而不是"再减一次"。
  • 死信与告警：超过重试次数进入死信，发出告警并人工介入。
  • 定时全量对账：比对 Redis 已下单用户集合、Redis 库存、MySQL 订单数和 MySQL 库存，自动修复差异；对"Redis 记录了用户但 MySQL 没有订单"的数据补单或通知用户。
  • 对账完成后清理 Redis 中的秒杀 key。

秒杀下单异步化后，怎么让用户及时知道下单结果？

异步后接口只返回"排队中"和 orderId，真正的结果要另外通知。

方式 做法 特点
前端轮询 每 1 秒左右调用结果查询接口，查询订单是否已落库 实现最简单；请求量大，查询要走缓存
结果缓存 消费者处理完把结果写入 Redis，如 seckill:result:{orderId}（TTL 几分钟），查询接口只读 Redis 配合轮询，避免查数据库
WebSocket / SSE 推送 处理完成后服务端主动推送 实时性好；要维护长连接，多实例时需要通过 MQ 或 Redis Pub/Sub 把消息路由到持有该连接的节点
站外通知 短信、App 推送、站内信 用户离开页面也能收到，作为补充

推荐组合：Lua 校验通过的那一刻，用户的抢购资格就已经确定，可以先提示"抢购成功，订单处理中"；前端以 1 秒间隔轮询结果缓存，最多轮询 5 到 10 次，超时后提示"请稍后到订单列表查看"；落库失败时补偿 Redis 库存并通知用户。

  2. 网关 / Nginx：按 IP 限流（limit_req，漏桶）；黑名单 IP 直接拒绝；Sentinel 网关限流，按参数（userId、IP）维度做热点参数限流。
  3. 接口层：
    • 用户维度：如每个用户每秒最多 1 次、每分钟最多 5 次，用 Redis INCR + EXPIRE 的固定窗口，或 ZSet 实现的滑动窗口计数。
    • 设备维度：按设备 ID 限流，同一设备关联的账号数量限制。
    • 活动维度：活动总 QPS 限流，保护后端（令牌桶，如 Guava RateLimiter 或 Redisson RRateLimiter）。
    • 接口签名（时间戳 + nonce + 签名）防止篡改和重放。
  4. 业务层兜底：一人一单（Redis Set + 数据库唯一索引）；超过阈值的可疑请求触发二次验证码，而不是直接拒绝，减少误伤。
  5. 风控：基于账号画像、设备、IP 信誉、行为序列做实时评分，高风险请求拦截，事后还可以对异常订单回收券。

秒杀中怎么防止有人用程序恶意刷优惠券？

目标是让脚本"拿不到地址、过不了验证、刷不出数量、抢到也会被回收"。

  • 提高门槛：下单前必须登录并完成验证码；秒杀接口地址在活动开始后动态生成（如 /seckill/{path}/order，path 与用户绑定、一次有效），脚本无法提前构造请求。
  • 限制频率：IP、用户、设备多维度限流；短时间内频繁请求的账号自动拉黑一段时间。
  • 限制数量：一人一单或一人限 N 张，在 Redis Lua 中原子校验，并由数据库唯一索引兜底；同一手机号、同一设备、同一收货地址视为同一个人。
  • 防重放：请求带时间戳和随机数并签名，服务端校验签名有效期，nonce 在 Redis 中只能使用一次。
  • 风控与事后处理：识别黑产账号（注册时间、行为轨迹、设备指纹）；领券后异步审核，异常领取进行回收或冻结；对异常订单进行对账，取消后回补库存。

要实现一个支持百万级用户的秒杀系统，有哪些措施？

核心思想是层层过滤：越往后请求越少，只有真正有资格的请求才到达数据库。

  1. 前端与接入层：页面静态化，静态资源上 CDN；按钮置灰、倒计时以服务器时间为准；验证码把瞬时峰值拉平；Nginx 限流和黑名单。
  2. 网关限流：Sentinel 网关限流、热点参数限流；超过系统容量的请求直接返回"活动火爆"。
  3. 独立部署：秒杀服务与普通业务隔离，单独部署和扩容，避免秒杀流量拖垮主站。
  4. 缓存预热：活动开始前把商品、库存加载到 Redis 和本地缓存；本地缓存可以加一个"已售罄"标记，售罄后不再访问 Redis。
  5. 库存原子扣减：Redis + Lua 原子判断库存和一人一单；热点商品的库存可以分段（拆成多个 key 分散到不同分片）。
  6. 异步削峰：抢到资格后写入 MQ，后端按数据库能承受的速度消费下单。
  7. 数据库保护：乐观锁 stock > 0 兜底；订单表唯一索引；必要时分库分表、读写分离。
  8. 防刷：多维度限流、风控、一人一单。
  9. 高可用：Redis 集群 + 持久化、MQ 多副本；熔断降级预案；提前全链路压测，确定各层容量。
  10. 最终一致：对账任务、超时未支付订单自动关闭并回补库存。

秒杀上线后流量增长 100 倍，现有架构哪里会出问题？怎么重构？

先定位瓶颈（按请求链路从前往后，结合压测和监控）

  • 数据库：连接池耗尽、行锁竞争（同一张券的库存行）、慢查询引发连锁超时，这是最先出问题的地方。
  • Redis：单个热点 key 打满一个分片的 CPU 或带宽；单实例内存和连接数不够；主从切换时丢数据。
  • 应用服务：Tomcat 线程池被慢请求占满，请求排队；JVM 阻塞队列内存溢出。
  • 异步链路：消息堆积，下单结果延迟很长；消费速度跟不上。
  • 一致性：本地缓存在多节点间的同步问题被放大。

重构方向

  1. 入口削峰：CDN、页面静态化、前端按钮控制和验证码；网关多维度限流，超过容量的请求快速失败。
  2. 服务水平扩展：应用无状态化（登录态已在 Redis），用 K8s 按 CPU / QPS 自动扩容；秒杀服务独立拆分部署。
  3. 缓存层：Redis 改为 Cluster 分片，热点 key 拆分或复制多份；加上 Caffeine 本地缓存和"售罄标记"，减少对 Redis 的访问。
  4. 消息队列：Redis Stream 替换为 RocketMQ / Kafka，增加分区和消费者实例，消费端批量写库。
  5. 数据库：读写分离；订单表按 userId 分库分表；库存热点行可以拆分为多行分别扣减，或者合并请求批量扣减。
  6. 熔断降级：Sentinel 熔断对下游的调用；非核心功能（推荐、评论、点赞）降级关闭，资源让给核心链路。
  7. 容量规划与压测：全链路压测确定每一层的极限，设定限流阈值；准备好降级开关和应急预案。

回答时要先指出具体的瓶颈，再说对应的手段，而不是罗列技术名词。

做过分库分表吗？怎么设计？

如果项目没有实际做过，可以说明"当前数据量单表足够，但考虑过扩展方案"，然后讲设计思路。

什么时候需要：单表数据量达到千万级（经验值，取决于行大小和索引）、B+ 树层级增加导致查询变慢，或者单库的写入 QPS、连接数、磁盘成为瓶颈。在此之前优先考虑索引优化、读写分离、归档冷数据。

拆分方式

  • 垂直拆分：按业务拆库（用户库、商户库、订单库）；按字段拆表，把大字段或不常用字段拆出去。
  • 水平拆分：同一张表的数据按分片键分布到多个库表中。

订单表的设计示例

  • 分片键选 user_id：最常见的查询是"我的订单"，同一用户的订单落在同一个分片，避免跨库查询。商家维度的查询通过异构索引表或同步到 Elasticsearch 解决。
  • 路由算法：hash(user_id) % 分片数，分布均匀；或者按范围、按时间分片，便于扩容和归档，但可能产生热点。
  • 基因法：把 user_id 的低几位嵌入订单号，按订单号查询时也能直接定位分片。
  • 全局 ID：不能使用自增主键，改用雪花算法或号段模式，项目中的 Redis 全局 ID 生成器也可以。
  • 中间件：ShardingSphere-JDBC（客户端分片，性能好）或 MyCat / ShardingSphere-Proxy（代理模式）。

带来的问题：跨分片的 join、排序、分页（需要归并或改用 ES）；分布式事务；扩容时的数据迁移（可以按 2 的倍数扩容，或使用一致性哈希减少迁移量）；运维复杂度提高。

附近的商户怎么实现？比如用户在天安门，查看附近的店铺

用 Redis GEO。GEO 底层就是一个 ZSet：把经纬度通过 GeoHash 编码为 52 位整数作为 score，地理位置相近的点编码也相近，所以可以通过 score 范围查询快速找到附近的点。

存储：按商户类型分组，每种类型一个 key，member 为商户 ID：

GEOADD shop:geo:{typeId} 116.397 39.908 1001     # 经度在前，纬度在后

查询（Redis 6.2+ 推荐使用 GEOSEARCH，GEORADIUS 已被标记为废弃）：

GEOSEARCH shop:geo:1 FROMLONLAT 116.397 39.908 BYRADIUS 5 km ASC COUNT 10 WITHDIST

GeoResults<RedisGeoCommands.GeoLocation<String>> results = stringRedisTemplate.opsForGeo().search(
        "shop:geo:" + typeId,
        GeoReference.fromCoordinate(x, y),
        new Distance(5000),
        RedisGeoCommands.GeoSearchCommandArgs.newGeoSearchArgs().includeDistance().limit(end));

项目中的流程

  1. 启动时或通过定时任务，按类型把所有商户的坐标批量导入 GEO（数据量大时用 pipeline 分批写入）。
  2. 前端传入用户的经纬度、商户类型和页码；没有坐标时退化为按数据库普通分页查询。
  3. GEOSEARCH 查出距离由近到远的 0 到 end 条（end = current × pageSize），在代码中跳过前 from 条实现分页（GEO 不支持 offset，只能查到第 end 条再截取）。
  4. 根据商户 ID 列表批量查询数据库，用 ORDER BY FIELD(id, ...) 保持距离顺序，并把距离设置到返回对象中。

注意点：商户坐标变更时要同步更新 GEO；GEO 只存 ID 和坐标，详情仍然查缓存或数据库；GeoHash 有精度误差，结果是近似的，适合"附近店铺"这种场景；全国范围的大量商户应按城市或类型拆分 key，避免 bigkey。

点赞和点赞排行榜怎么实现？

需求：同一用户对同一篇笔记只能点赞一次，再次点击取消点赞；详情页展示最早点赞的前 5 个用户。

数据结构选择：一开始可以用 Set（SISMEMBER 判断是否点过赞），但 Set 无序，做不了"按点赞时间排序"，所以改用 ZSet：key 为 blog:liked:{blogId}，member 为 userId，score 为点赞时间戳。

流程

  • 点赞 / 取消：ZSCORE 判断当前用户是否已点赞（ZSet 没有 ZISMEMBER，用 ZSCORE 返回值是否为 null 判断）。未点赞：数据库 liked = liked + 1，成功后 ZADD；已点赞：数据库 liked = liked - 1，成功后 ZREM。
  • 排行榜：ZRANGE blog:liked:{blogId} 0 4 取最早点赞的 5 个 userId，再到数据库批量查询用户。用 WHERE id IN (...) 查询时数据库会按主键顺序返回，需要加 ORDER BY FIELD(id, 5, 1, 3...) 保持点赞顺序。
  • 查询笔记时，用 ZSCORE 判断当前登录用户是否已点赞，用于前端高亮。

注意点：数据库更新成功后再操作 Redis，保证计数一致；"判断 + 修改"并发时可能重复点赞，可以用 Lua 脚本或在数据库中建 (user_id, blog_id) 点赞记录表的唯一索引兜底；点赞量很大的热门内容可以只在 Redis 计数，定时批量回写数据库。

关注、共同关注和 Feed 流是怎么做的？滚动分页怎么实现？

关注与共同关注：关注关系存表 tb_follow，同时写入 Redis Set follows:{userId}；共同关注用 SINTER follows:{me} follows:{other} 求交集。

Feed 流：项目采用 Timeline（按时间排序），不做智能推荐。三种实现：

模式 做法 优点 缺点
拉模式（读扩散） 发帖只写自己的发件箱，读时拉取所有关注者的发件箱并合并排序 节省内存，写入简单 读取延迟高，关注很多人时很慢
推模式（写扩散） 发帖时推送到所有粉丝的收件箱 读取快，延迟低 大 V 粉丝多时写入量巨大，内存占用高
推拉结合 普通用户推模式；大 V 对活跃粉丝推送，对普通粉丝改为拉取 兼顾两者 实现复杂

项目用户量不大，采用推模式：发布笔记时把笔记 ID 写入每个粉丝的收件箱 ZSet feed:{fanId}，score 为发布时间戳。

为什么不用下标分页：翻页期间有新内容插入，下标整体后移，下一页会重复。所以用滚动分页：记住上一页最后一条的 score，从它之后继续查。

ZREVRANGEBYSCORE feed:{userId} {max} 0 WITHSCORES LIMIT {offset} 3
  • 第一次：max 为当前时间戳，offset 为 0。
  • 后续：max 为上一页最小时间戳 minTime，offset 为上一页中 score 等于 minTime 的条数，跳过时间戳相同、已返回的数据。
  • 接口返回 List<Blog>、minTime、offset，前端下次带回。

用户签到怎么实现？连续签到天数怎么统计？

用 BitMap：每个用户每个月一个 key，sign:{userId}:{yyyyMM}，一个月最多 31 天，只需要 31 个 bit（4 字节）。同样的数据存数据库表，每次签到都是一行，1000 万用户一年就有几十亿行。BitMap 底层是 String，最大 512 MB，即 2^32 个 bit。

签到：SETBIT sign:1010:202611 {dayOfMonth - 1} 1（offset 从 0 开始，所以 1 号对应 offset 0）。

统计本月截至今天的连续签到天数

  1. 用 BITFIELD sign:1010:202611 GET u{dayOfMonth} 0 取出从 1 号到今天的所有 bit，得到一个无符号十进制数。
  2. 从最低位（今天）开始往前，与 1 做按位与：结果为 1 说明当天签到了，计数加 1，然后右移一位继续判断；遇到 0（未签到）就停止。
List<Long> result = stringRedisTemplate.opsForValue().bitField(key,
        BitFieldSubCommands.create().get(BitFieldSubCommands.BitFieldType.unsigned(dayOfMonth)).valueAt(0));
long num = result.get(0);
int count = 0;
while ((num & 1) == 1) {   // 今天没签到时直接返回 0
    count++;
    num >>>= 1;
}

其他统计：BITCOUNT 统计本月总签到天数；GETBIT 判断某天是否签到；BITPOS key 1 找到本月第一次签到的日期。跨月的连续签到需要把上个月的 key 也取出来接着判断。

UV 统计怎么做？为什么用 HyperLogLog？

UV（Unique Visitor） 是独立访客数，同一用户一天内多次访问只算一次，需要去重；PV（Page View）是页面访问量，直接计数即可。

UV 用 Set 精确去重，用户量大时内存会爆炸；用 HyperLogLog（HLL），是一种基于概率的基数估计算法：

  • 每个 key 最多只占 12 KB 内存（数据量小时用稀疏编码，更省），就能统计接近 2^64 个不同元素的基数。
  • 存在误差，标准误差约 0.81%，对 UV 这种统计类指标完全可以接受。
  • 只能统计数量，不能取出元素本身，也不能判断某个元素是否存在。

命令

PFADD uv:shop:1001:20261106 user1 user2 user3    # 添加访问用户，重复添加不影响计数
PFCOUNT uv:shop:1001:20261106                    # 当天的 UV
PFMERGE uv:shop:1001:202611 uv:shop:1001:20261101 uv:shop:1001:20261102   # 合并多天，得到月 UV

原理简述：对元素求 64 位哈希，用其中 14 位选出 16384 个桶（寄存器）中的一个，在剩余的 50 位中从低位开始数到第一个 1 出现的位置，每个桶记录见过的最大值；再根据所有桶的调和平均数估计基数。"连续出现 k 个 0 的概率是 1/2^k"，所以观察到的最长连续 0 越长，说明元素越多。

需要精确值（如计费、结算）时不能用 HLL，应使用 Set 或 BitMap（userId 为连续整数时，BitMap 也能精确统计，1 亿用户约 12 MB）。

智能客服的 Function Call 定义了哪些函数？

Function Call（Tool Calling）的做法：把业务能力描述成带名称、说明和 JSON Schema 参数的函数提供给大模型，模型根据用户的问题决定调用哪个函数、填什么参数，由后端真正执行，再把结果交给模型组织成自然语言回复。

结合点评业务，可以定义：

函数 参数 作用
searchNearbyShops 经纬度、类型、半径 调用 GEO 查询附近店铺
getShopDetail shopId 查询店铺详情、营业时间、评分（走缓存）
listVouchers shopId 查询店铺可用的优惠券和秒杀券、剩余库存
queryMyOrders 状态、时间范围 查询当前用户的订单状态
getVoucherRule voucherId 查询使用规则、有效期
transferToHuman 问题摘要 转人工客服

设计要点

  • 用户身份由后端注入：userId 从登录态（ThreadLocal）获取，不作为模型可填写的参数，防止模型被提示词诱导去查询其他人的数据。
  • 只读优先：查询类函数可以直接执行；下单、退款、领券这类写操作要求用户在界面上二次确认，或者只返回操作链接，不让模型直接执行。
  • 参数校验：模型生成的参数可能不合法或不存在，后端执行前要校验，并把错误信息返回给模型。
  • 函数说明要写清楚适用场景，函数数量不宜过多，以免模型选错。
  • 可以用 Spring AI 的 @Tool 注解或 LangChain4j 的 @Tool 来声明。

大模型对话上下文在 Redis 中怎么存储？

对话上下文是按会话、按顺序追加的消息列表，推荐用 List（或 Stream），会话元信息单独用 Hash 存储。

chat:session:{sessionId}    Hash   userId、title、model、createTime、lastActiveTime
chat:history:{sessionId}    List   每个元素是一条消息 JSON：{"role":"user|assistant|tool","content":"...","ts":...}
chat:sessions:{userId}      ZSet   member 为 sessionId，score 为最近活跃时间，用于会话列表
  • 追加：每轮对话 RPUSH 用户消息和模型回复，同时刷新 TTL（如 7 天无活动则过期）。
  • 窗口截断：LTRIM chat:history:{sid} -N -1 只保留最近 N 条，或者在拼接 prompt 时用 LRANGE 取最近若干条，并按 token 数控制上限，避免超出模型的上下文窗口。
  • 摘要记忆：更早的历史由模型压缩成一段摘要，存在 Hash 的 summary 字段中，拼接 prompt 时放在最前面。
  • 持久化：Redis 只作为热数据缓存，完整的对话记录异步写入 MySQL，用于审计和后续查询。
  • 用 Hash 存一整段 JSON 的问题是每次都要整体读写，并发追加时还会覆盖；List 天然有序、可以原子追加，更合适。

大模型服务超时或不可用时怎么处理？有什么降级方案？

基础防护

  • 超时控制：设置连接超时和读取超时；使用流式输出（SSE），以首个 token 的延迟作为健康指标，用户也能更早看到内容。
  • 有限重试：只对超时、429、5xx 等可重试的错误重试 1 到 2 次，带指数退避和抖动，避免重试风暴。
  • 熔断：用 Sentinel / Resilience4j 统计失败率和慢调用比例，超过阈值后熔断一段时间，期间快速走降级逻辑，过后半开探测恢复。
  • 隔离：大模型调用使用独立的线程池，避免拖垮其他业务接口。

多级降级

等级 触发条件 策略
正常 服务健康 主模型提供完整对话能力
